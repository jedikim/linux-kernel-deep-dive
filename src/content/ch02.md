::: {.lead}
운영체제 교과서는 프로세스와 스레드를 다른 것으로 가르칩니다. 프로세스는 자원을 갖고, 스레드는 그 안의 실행 흐름이라고 합니다. 리눅스 커널에는 그 둘을 가르는 타입이 없습니다. 프로세스도 스레드도 커널 스레드도 `struct task_struct` 하나입니다. 차이는 그 구조체 안의 포인터들이 다른 태스크와 같은 곳을 가리키느냐뿐입니다. 이 장은 `task_struct`를 지도처럼 펼쳐 놓고, "무엇을 공유하는가"라는 질문 하나로 프로세스, 스레드, 커널 스레드를 설명합니다.
:::

::: {.goals}
- `task_struct`에는 무엇이 들어 있고, 왜 자원은 구조체 밖에 포인터로 떼어 두었는가?
- 프로세스와 스레드는 커널 안에서 무엇이 다른가?
- `getpid()`와 `gettid()`는 각각 `task_struct`의 어느 필드를 돌려주는가?
- 커널 스레드는 유저 태스크와 무엇이 다른가? `mm`이 NULL인 태스크는 어느 주소 공간에서 도는가?
- 고루틴이나 가상 스레드는 커널에 어떻게 보이는가?
- 커널은 "지금 실행 중인 태스크"를 어떻게 찾는가? 커널 스택이 넘치면 무슨 일이 생기는가?
:::

## 태스크 하나에 구조체 하나 {#one-struct}

운영체제가 실행 단위 하나에 대해 기억해 두는 정보의 묶음을 교과서는 PCB(process control block)라고 부릅니다. 리눅스에서 그 구조체가 `struct task_struct`입니다. `include/linux/sched.h`에 있고, 정의만 850줄이 넘습니다. 스케줄러, 메모리 관리, 파일시스템, 시그널, 추적 도구가 저마다 필드를 얹어 왔기 때문입니다.

::: {.fig src="task-struct-map.svg"}
`task_struct`의 필드를 여섯 묶음으로 나눈 지도. 위의 네 묶음과 맨 아래 묶음은 구조체 안에 직접 들어 있고, 보라색 묶음은 바깥 구조체를 가리키는 포인터입니다.
:::

구조체의 첫머리는 이렇게 시작합니다.

```{.c file="include/linux/sched.h" line="835"}
struct task_struct {
#ifdef CONFIG_THREAD_INFO_IN_TASK
	/*
	 * For reasons of header soup (see current_thread_info()), this
	 * must be the first element of task_struct.
	 */
	struct thread_info		thread_info;
#endif
	unsigned int			__state;

	/* saved state for "spinlock sleepers" */
	unsigned int			saved_state;

	/*
	 * This begins the randomizable portion of task_struct. Only
	 * scheduling-critical items should be added above here.
	 */
	randomized_struct_fields_start

	void				*stack;
	refcount_t			usage;
	/* Per task flags (PF_*), defined further below: */
	unsigned int			flags;
	unsigned int			ptrace;
	/* ... */
```

읽을 곳은 네 군데입니다.

- `thread_info`가 맨 앞입니다. `TIF_NEED_RESCHED` 같은 플래그가 여기 들어 있습니다([6장](ch06.html)). 맨 앞이어야 하는 까닭은 `current_thread_info()`가 `current` 포인터를 그대로 `struct thread_info *`로 바꿔 쓰기 때문입니다.
- `__state`는 태스크가 실행 가능한지 잠들었는지를 나타냅니다. [3장](ch03.html)의 주제입니다.
- `stack`은 이 태스크의 커널 스택을 가리킵니다. 뒤의 [커널 스택 절](#stack-current)에서 봅니다.
- `usage`는 참조 카운트입니다. 태스크가 끝난 뒤에도 누군가 이 구조체를 가리키고 있으면 메모리를 풀지 않습니다.

나머지 필드를 다 읽을 필요는 없습니다. 묶음으로 보면 됩니다.

| 묶음 | 대표 필드 | 다루는 곳 |
|---|---|---|
| 상태 | `__state`, `exit_state`, `flags` | [3장](ch03.html) |
| 스케줄링 | `prio`, `se`, `rt`, `dl`, `sched_class`, `cpus_ptr` | [4장](ch04.html), [5장](ch05.html) |
| 식별 | `pid`, `tgid`, `thread_pid`, `comm` | 이 장 |
| 가족 관계 | `real_parent`, `children`, `sibling`, `group_leader` | 이 장 |
| 자원 포인터 | `mm`, `fs`, `files`, `signal`, `sighand`, `nsproxy`, `cred` | 이 장, [17장](ch17.html), [20장](ch20.html), [22장](ch22.html) |
| 스택과 CPU 상태 | `stack`, `thread_info`, `thread` | 이 장, [4장](ch04.html) |

`flags`는 `PF_`로 시작하는 태스크별 플래그입니다. `PF_KTHREAD`(커널 스레드), `PF_EXITING`(종료 중)처럼 태스크의 종류나 처지를 나타냅니다. `__state`와는 다른 것입니다. `comm`은 `ps`에 보이는 16바이트짜리 이름입니다.

### 가족 관계

태스크는 자기를 만든 태스크를 부모로 갖습니다. 이 관계가 필드 넷으로 표현됩니다.

```{.c file="include/linux/sched.h" line="1093"}
	/* Real parent process: */
	struct task_struct __rcu	*real_parent;

	/* Recipient of SIGCHLD, wait4() reports: */
	struct task_struct __rcu	*parent;

	/*
	 * Children/sibling form the list of natural children:
	 */
	struct list_head		children;
	struct list_head		sibling;
	struct task_struct		*group_leader;
```

`real_parent`는 낳은 부모이고 `parent`는 종료 통지를 받을 태스크입니다. 평소에는 둘이 같습니다. 디버거가 `ptrace`로 붙으면 `parent`만 디버거로 바뀝니다. `children`은 자식 리스트의 머리이고, `sibling`은 부모의 그 리스트에 자신을 매다는 고리입니다.

::: {.fig src="family.svg"}
부모의 `children`과 자식들의 `sibling`이 리스트 하나를 이룹니다. 자식에서 부모로는 `real_parent` 포인터로 한 번에 갑니다.
:::

이 관계의 뿌리는 부팅 때 만들어지는 태스크 셋입니다. PID 0은 부팅 코드 자신이 변한 idle 태스크(`swapper`)입니다. PID 1은 `init`, PID 2는 `kthreadd`로, 둘 다 `rest_init()`(`init/main.c`)이 만듭니다. 보통의 유저 프로세스는 PID 1의 자손이고 커널 스레드는 PID 2의 자식입니다. 부모가 먼저 죽은 태스크가 누구에게 입양되는지는 [3장](ch03.html)에서 봅니다.

## 포인터로 떼어 둔 이유 {#sharing}

그림 2-1의 보라색 묶음을 다시 봅니다. 주소 공간, 열린 파일, 시그널 핸들러는 `task_struct` 안에 들어 있지 않고 포인터로 떨어져 있습니다. 이유는 하나입니다. **여러 태스크가 같은 것을 가리킬 수 있게** 하려는 것입니다.

[1장](ch01.html)에서 `copy_process()`가 자원마다 `copy_*()` 함수를 부르는 것을 봤습니다. 각 함수는 clone 플래그를 보고 둘 중 하나를 합니다. 플래그가 서 있으면 부모가 가리키는 구조체의 참조 카운트를 올리고 자식도 그것을 가리키게 둡니다. 없으면 새 구조체를 만들어 복사합니다. 플래그는 `include/uapi/linux/sched.h`에 있습니다.

```{.c file="include/uapi/linux/sched.h" line="10"}
#define CSIGNAL		0x000000ff	/* signal mask to be sent at exit */
#define CLONE_VM	0x00000100	/* set if VM shared between processes */
#define CLONE_FS	0x00000200	/* set if fs info shared between processes */
#define CLONE_FILES	0x00000400	/* set if open files shared between processes */
#define CLONE_SIGHAND	0x00000800	/* set if signal handlers and blocked signals shared */
#define CLONE_PIDFD	0x00001000	/* set if a pidfd should be placed in parent */
#define CLONE_PTRACE	0x00002000	/* set if we want to let tracing continue on the child too */
#define CLONE_VFORK	0x00004000	/* set if the parent wants the child to wake it up on mm_release */
#define CLONE_PARENT	0x00008000	/* set if we want to have the same parent as the cloner */
#define CLONE_THREAD	0x00010000	/* Same thread group? */
#define CLONE_NEWNS	0x00020000	/* New mount namespace group */
#define CLONE_SYSVSEM	0x00040000	/* share system V SEM_UNDO semantics */
```

공유를 정하는 플래그와 구조체의 대응은 이렇습니다.

| 플래그 | 함께 쓰게 되는 것 | `task_struct` 필드 | 처리하는 함수 |
|---|---|---|---|
| `CLONE_VM` | 주소 공간 (`mm_struct`) | `mm` | `copy_mm()` |
| `CLONE_FS` | 루트·현재 디렉터리, umask (`fs_struct`) | `fs` | `copy_fs()` |
| `CLONE_FILES` | 파일 디스크립터 표 (`files_struct`) | `files` | `copy_files()` |
| `CLONE_SIGHAND` | 시그널 핸들러 표 (`sighand_struct`) | `sighand` | `copy_sighand()` |
| `CLONE_THREAD` | 스레드 그룹 (`signal_struct`) | `signal` | `copy_signal()` |
| `CLONE_SYSVSEM` | System V 세마포어 되돌리기 목록 | `sysvsem` | `copy_semundo()` |
| `CLONE_IO` | I/O 컨텍스트 | `io_context` | `copy_io()` |
| `CLONE_NEW*` | (반대) 서 있으면 새 네임스페이스 | `nsproxy` | `copy_namespaces()` |

이제 프로세스와 스레드를 정의할 수 있습니다. **스레드는 이 플래그들을 거의 다 켜고 만든 태스크이고, 프로세스는 다 끄고 만든 태스크입니다.**

::: {.fig src="process-vs-thread.svg"}
`fork()`로 만든 자식과 `pthread_create()`로 만든 스레드. 만드는 함수는 같고(`copy_process()`), 넘긴 플래그만 다릅니다.
:::

glibc의 `pthread_create()`가 넘기는 플래그는 `CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SYSVSEM | CLONE_SIGHAND | CLONE_THREAD | CLONE_SETTLS | CLONE_PARENT_SETTID | CLONE_CHILD_CLEARTID`입니다. 앞의 여섯이 공유를 정하고, 뒤의 셋은 스레드 지역 저장소와 스레드 ID를 다루는 부가 기능입니다. `fork()`는 공유 플래그를 하나도 넘기지 않습니다.

둘 사이의 조합도 가능합니다. `CLONE_VM`만 켜면 주소 공간은 같이 쓰지만 파일 표와 PID는 따로인 태스크가 생깁니다. `vfork()`가 그런 경우입니다. `CLONE_FILES`만 켜서 파일 표만 같이 쓰는 프로세스도 만들 수 있습니다. 다만 아무 조합이나 되지는 않습니다. `CLONE_THREAD`는 `CLONE_SIGHAND`를, `CLONE_SIGHAND`는 `CLONE_VM`을 요구합니다.

::: {.design}
"프로세스"와 "스레드"를 서로 다른 타입으로 만들었다면 생성 함수도, 스케줄러도, 시그널 전달도 타입마다 따로 필요했을 것입니다. 리눅스는 실행 단위를 한 가지(태스크)로 두고, 자원을 독립된 구조체로 떼어 참조 카운트를 붙였습니다. 그러자 "프로세스냐 스레드냐"라는 이분법이 "어느 자원을 공유하느냐"라는 플래그 조합으로 바뀌었습니다. 스케줄러는 태스크만 알면 되고, 자원 구조체는 누가 자신을 가리키는지 몰라도 됩니다. 종류를 타입으로 나누기 전에, 독립된 속성의 조합으로 표현할 수 있는지 먼저 따져 볼 만합니다. 컨테이너가 커널에 새 실행 단위를 더하지 않고 `CLONE_NEW*` 플래그 몇 개로 만들어진 것도 이 구조 덕분입니다([22장](ch22.html)).
:::

::: {.myth}
"스레드는 프로세스보다 훨씬 가볍다." 리눅스에서 둘은 같은 함수로 만들어지고, 어느 쪽이든 `task_struct` 하나와 커널 스택 하나를 씁니다. 스케줄러가 다루는 비용도 같습니다. 차이는 두 군데에서 납니다. 만들 때 스레드는 페이지 테이블과 파일 표를 복사하지 않습니다. 그리고 같은 `mm`을 쓰는 태스크끼리 스위치할 때는 페이지 테이블을 바꾸지 않습니다. "가볍다"의 실체는 이 두 가지이고, 그 밖의 비용은 스레드도 프로세스만큼 듭니다.
:::

## PID와 TGID {#pid-tgid}

스레드가 태스크라면 스레드마다 PID가 있어야 합니다. 실제로 있습니다. 그런데 POSIX는 한 프로세스의 모든 스레드에서 `getpid()`가 같은 값을 돌려주기를 요구합니다. 리눅스는 번호를 둘로 나눠 이 요구를 맞춥니다.

- `pid`: 태스크마다 다른 번호입니다. 유저 공간에서는 스레드 ID(TID)라고 부릅니다.
- `tgid`: 스레드 그룹 ID입니다. 유저 공간에서 PID라고 부르는 것이 이것입니다.

```{.c file="kernel/sys.c" line="999"}
SYSCALL_DEFINE0(getpid)
{
	return task_tgid_vnr(current);
}

/* Thread ID - the internal kernel "pid" */
SYSCALL_DEFINE0(gettid)
{
	return task_pid_vnr(current);
}
```

`getpid()`가 돌려주는 것은 `tgid`입니다. 두 번호는 `copy_process()`에서 정해집니다.

```{.c file="kernel/fork.c" line="2396"}
	p->pid = pid_nr(pid);
	if (clone_flags & CLONE_THREAD) {
		p->group_leader = current->group_leader;
		p->tgid = current->tgid;
	} else {
		p->group_leader = p;
		p->tgid = p->pid;
	}
```

`CLONE_THREAD` 없이 만든 태스크는 자기 `pid`를 `tgid`로 삼고 스스로 **그룹 리더**가 됩니다. `CLONE_THREAD`로 만든 태스크는 새 `pid`를 받되, `tgid`와 리더는 만든 쪽의 것을 물려받습니다.

::: {.fig src="pid-tgid.svg"}
스레드 셋으로 된 프로세스. 커널에는 태스크가 셋이고 `pid`도 셋이지만, 유저 공간이 PID라고 부르는 `tgid`는 하나입니다.
:::

스레드 그룹은 `signal_struct`를 함께 쓰는 태스크들의 모임입니다. 커널의 판정 함수가 그대로 정의입니다.

```{.c file="include/linux/sched/signal.h" line="707"}
static inline
bool same_thread_group(struct task_struct *p1, struct task_struct *p2)
{
	return p1->signal == p2->signal;
}
```

`signal_struct`에는 이름과 달리 시그널만 들어 있지 않습니다. 프로세스 전체에 속하는 상태가 여기 모여 있습니다. 프로세스로 온 시그널의 대기열(`shared_pending`), 자원 한도(`rlim`), 스레드 수(`nr_threads`), 그룹의 태스크를 잇는 리스트(`thread_head`), 종료 코드, 누적 CPU 시간 같은 것입니다. `kill(pid, sig)`로 보낸 시그널이 "그 프로세스의 스레드 가운데 아무나"에게 전달되는 것도 이 구조체의 대기열에 걸리기 때문입니다.

::: {.old}
오래된 자료에는 "리눅스의 스레드는 프로세스와 같아서 스레드마다 `getpid()` 값이 다르다"는 설명이 있습니다. LinuxThreads라는 예전 구현이 실제로 그랬습니다. 스레드를 `CLONE_VM` 등으로 만든 별개의 프로세스로 두고 관리용 스레드를 따로 돌렸기 때문에, 스레드마다 PID가 달랐고 프로세스 전체에 시그널을 보낼 방법이 없었습니다. 커널에 `CLONE_THREAD`와 스레드 그룹이 들어오고, glibc 2.3.2부터 NPTL이 이것을 쓰면서 모든 스레드가 같은 PID를 갖게 되었습니다. "스레드도 태스크"라는 뼈대는 그대로이고, 그 위에 "한 프로세스로 보이게 묶는 장치"가 더해진 것입니다.
:::

번호와 태스크를 잇는 것은 `struct pid`입니다. 커널 안에서는 숫자 PID를 들고 다니지 않습니다. 숫자는 태스크가 죽은 뒤 다른 태스크에 다시 배정될 수 있기 때문입니다. `struct pid`는 작은 참조 카운트 객체로, 번호 하나가 쓰이는 동안만 그 번호를 대표합니다. PID 네임스페이스 단계마다의 번호(`numbers[]`)와 이 번호를 쓰는 태스크들의 리스트를 갖습니다. 같은 객체가 네 가지 구실로 쓰입니다(`enum pid_type`). 태스크의 ID(`PIDTYPE_PID`), 스레드 그룹의 ID(`PIDTYPE_TGID`), 프로세스 그룹의 ID(`PIDTYPE_PGID`), 세션의 ID(`PIDTYPE_SID`)입니다. 유저 공간에서 같은 문제를 푸는 도구가 [1장](ch01.html)에서 본 pidfd입니다. pidfd는 `struct pid`를 가리키는 파일 디스크립터입니다.

::: {.lab}
스레드가 여럿인 프로세스를 하나 골라 번호를 확인합니다.

```console
$ grep -E '^(Name|Tgid|Pid|PPid|Threads)' /proc/$(pidof rsyslogd)/status
Name:	rsyslogd
Tgid:	843
Pid:	843
PPid:	1
Threads:	4

$ ls /proc/843/task
843  861  862  863

$ grep -E '^(Tgid|Pid)' /proc/843/task/862/status
Tgid:	843
Pid:	862

$ ps -o pid,lwp,nlwp,comm -L -p 843
    PID     LWP NLWP COMMAND
    843     843    4 rsyslogd
    843     861    4 in:imuxsock
    ...
```

번호는 예시입니다. `/proc/<pid>/status`의 `Pid`가 커널의 `pid`이고 `Tgid`가 `tgid`입니다. `ps`의 `LWP`(light-weight process) 열이 커널의 `pid`입니다. `/proc/862`는 `ls /proc`에는 보이지 않지만 직접 열면 열립니다. `/proc`의 목록은 그룹 리더만 보여 주기 때문입니다.
:::

## 커널 스레드 {#kthreads}

**커널 스레드**(kernel thread)는 유저 모드로 나가지 않고 커널 안에서만 도는 태스크입니다. 메모리를 회수하는 `kswapd`, 미뤄 둔 일을 처리하는 `kworker`, softirq를 대신 돌리는 `ksoftirqd`가 그 예입니다. `ps`에서 이름이 대괄호로 둘러싸여 보이는 것들입니다.

커널 스레드도 `task_struct`이고 [1장](ch01.html)에서 본 `kernel_clone()`으로 만들어집니다. 다만 커널 코드가 직접 만들지 않고 `kthreadd`에게 부탁합니다. `kthread_create()`는 요청을 리스트에 넣고 `kthreadd`를 깨운 뒤 기다립니다(`kthread_run()`은 만든 스레드를 곧바로 깨우기까지 하는 매크로입니다). `kthreadd`는 요청을 하나씩 꺼내 이 함수를 부릅니다.

```{.c file="kernel/kthread.c" line="451"}
static void create_kthread(struct kthread_create_info *create)
{
	int pid;

#ifdef CONFIG_NUMA
	current->pref_node_fork = create->node;
#endif
	/* We want our own signal handler (we take no signals by default). */
	pid = kernel_thread(kthread, create, create->full_name,
			    CLONE_FS | CLONE_FILES | SIGCHLD);
	/* ... */
}
```

`kthreadd`를 거치는 이유는 물려받는 환경 때문입니다. 태스크는 부모의 것을 복사해 만들어집니다. 드라이버 코드가 어떤 유저 프로세스의 시스템 콜 도중에 직접 스레드를 만들면, 그 프로세스의 cgroup, CPU 친화성, 시그널 설정이 커널 스레드에 딸려 옵니다. 모든 커널 스레드를 `kthreadd` 한 곳에서 만들면 언제나 같은, 깨끗한 환경에서 출발합니다. 그래서 커널 스레드의 부모는 모두 PID 2입니다.

새 커널 스레드는 `ret_from_fork()`에서 유저 모드로 나가지 않고 넘겨받은 함수를 부릅니다. [1장](ch01.html)에서 본 `fn` 가지입니다. `copy_thread()`가 `inactive_task_frame`의 `bx` 칸에 함수 주소를 넣어 두면, 그 값이 `ret_from_fork()`의 `fn` 인자가 됩니다.

### mm이 없는 태스크

커널 스레드는 유저 주소 공간이 없습니다. `mm`이 NULL입니다. 그러면 어느 페이지 테이블로 돌까요. 답은 "방금까지 돌던 태스크의 것"입니다.

모든 프로세스의 페이지 테이블은 위쪽 절반에 같은 커널 영역을 매핑하고 있습니다. 커널 스레드는 커널 영역만 건드리므로 어느 프로세스의 페이지 테이블 위에서든 돌 수 있습니다. 스케줄러는 이 점을 이용해 커널 스레드로 스위치할 때 페이지 테이블을 바꾸지 않습니다.

```{.c file="kernel/sched/core.c" line="5487"}
	/*
	 * kernel -> kernel   lazy + transfer active
	 *   user -> kernel   lazy + mmgrab_lazy_tlb() active
	 *
	 * kernel ->   user   switch + mmdrop_lazy_tlb() active
	 *   user ->   user   switch
	 */
	if (!next->mm) {				// to kernel
		enter_lazy_tlb(prev->active_mm, next);

		next->active_mm = prev->active_mm;
		if (prev->mm)				// from user
			mmgrab_lazy_tlb(prev->active_mm);
		else
			prev->active_mm = NULL;
	} else {					// to user
		/* ... */
		switch_mm_irqs_off(prev->active_mm, next->mm, next);
		/* ... */
	}
```

`task_struct`에 `mm`과 `active_mm`이 따로 있는 까닭이 여기 있습니다. `mm`은 태스크가 **소유한** 주소 공간이고 `active_mm`은 지금 **CPU에 실려 있는** 주소 공간입니다. 유저 태스크는 둘이 같습니다. 커널 스레드는 `mm`이 NULL이고 `active_mm`은 앞 태스크에게서 빌린 것입니다.

::: {.fig src="lazy-tlb.svg"}
커널 스레드로 갈 때는 페이지 테이블을 바꾸지 않고, 다른 유저 태스크로 갈 때에만 바꿉니다. 커널 스레드 뒤에 다시 A가 돌면 한 번도 바꾸지 않습니다.
:::

이 기법을 **lazy TLB**라고 합니다. 페이지 테이블을 바꾸면 TLB에 쌓인 주소 변환 캐시를 버리거나 구분해 관리해야 합니다. 커널 스레드는 잠깐 돌고 물러나는 일이 많으므로, 바꾸지 않고 버티면 원래 태스크가 돌아왔을 때 TLB가 그대로 살아 있습니다. 빌린 `mm`이 그 사이에 해제되지 않도록 `mmgrab_lazy_tlb()`로 붙들어 둡니다.

### 유저 워커: 커널 안에서만 도는 유저 스레드

v7.3에는 세 번째 부류가 있습니다. io_uring의 워커와 vhost 워커입니다. 이들은 커널 코드만 실행하지만 커널 스레드가 아닙니다.

```{.c file="kernel/fork.c" line="2706"}
struct task_struct *create_io_thread(int (*fn)(void *), void *arg, int node)
{
	unsigned long flags = CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD|
			      CLONE_IO|CLONE_VM|CLONE_UNTRACED;
	struct kernel_clone_args args = {
		.flags		= flags,
		.fn		= fn,
		.fn_arg		= arg,
		.io_thread	= 1,
		.user_worker	= 1,
	};

	return copy_process(NULL, 0, node, &args);
}
```

플래그가 `pthread_create()`와 거의 같습니다. 이 태스크는 io_uring을 쓰는 프로세스의 **스레드**로 만들어집니다. 같은 `mm`, 같은 파일 표, 같은 스레드 그룹입니다. 다만 `fn`이 있으므로 유저 모드로 나가지 않고 커널 함수를 돕니다.

| | 유저 태스크 | 커널 스레드 | 유저 워커 |
|---|---|---|---|
| 예 | `bash`, `nginx` | `kswapd0`, `ksoftirqd/0` | `iou-wrk-<pid>` |
| `mm` | 자기 것 | NULL (`active_mm`을 빌림) | 만든 프로세스의 것 |
| 유저 모드 실행 | 한다 | 안 한다 | 안 한다 |
| `flags` | — | `PF_KTHREAD` | `PF_USER_WORKER` (+ `PF_IO_WORKER`) |
| 소속 | 자기 스레드 그룹 | `kthreadd`의 자식 | 만든 프로세스의 스레드 그룹 |
| cgroup·자격 증명 | 자기 것 | 루트 cgroup, 커널의 것 | 만든 프로세스의 것 |

유저 워커가 필요했던 까닭이 마지막 줄에 있습니다. 프로세스를 대신해 I/O를 하는 스레드가 커널 스레드이면, 그 일의 CPU 시간이 프로세스의 cgroup에 계산되지 않고 프로세스의 자격 증명과 한도도 따로 흉내 내야 합니다. 프로세스의 스레드로 만들면 이것들이 저절로 맞습니다.

## 유저 수준 스레드 {#user-threads}

커널이 아는 실행 단위는 태스크뿐입니다. 그 위에 유저 공간이 스레드를 어떻게 얹느냐에 따라 세 가지 모델이 있습니다.

::: {.fig src="thread-models.svg"}
유저 스레드와 커널 태스크를 잇는 세 가지 방법. 리눅스의 pthread는 1:1이고, Go와 Java의 가상 스레드는 M:N입니다.
:::

**1:1.** 유저 스레드 하나가 커널 태스크 하나입니다. glibc의 pthread(NPTL)가 이 모델입니다. 앞 절에서 본 `CLONE_THREAD` 태스크가 곧 스레드입니다. 스케줄링을 전부 커널이 하므로 한 스레드가 시스템 콜에서 블록되어도 나머지는 계속 돌고, 코어 여러 개에 퍼져 실행됩니다. 대신 스레드를 만들고 스위치할 때마다 커널을 거칩니다.

**N:1.** 태스크 하나 위에서 유저 공간 라이브러리가 여러 실행 흐름을 번갈아 돌립니다. 스위치가 함수 호출 수준으로 쌉니다. 그러나 커널은 태스크 하나만 보므로, 그중 하나가 블로킹 시스템 콜에 들어가면 전부 멈춥니다. 코어도 하나만 씁니다.

**M:N.** 런타임이 커널 태스크를 코어 수만큼 만들어 두고, 그 위에 훨씬 많은 유저 스레드를 실어 나릅니다. Go의 고루틴과 Java의 가상 스레드가 이렇게 동작합니다. 런타임은 블록될 만한 입출력을 `epoll`이나 io_uring 같은 비동기 인터페이스로 바꿔, 유저 스레드가 기다리는 동안 그 태스크에 다른 유저 스레드를 올립니다.

어느 모델이든 커널의 스케줄러, 우선순위, CPU 친화성, cgroup 한도는 **태스크**에 적용됩니다. 고루틴 십만 개를 띄운 프로그램도 `/proc/<pid>/task`에는 코어 수와 비슷한 수의 태스크만 보입니다. 고루틴 하나의 우선순위를 `nice`로 올릴 수 없는 것도 그래서입니다.

## 커널 스택과 current {#stack-current}

태스크는 유저 모드에서 쓰는 스택과 별개로 **커널 스택**을 하나씩 갖습니다. 시스템 콜이나 인터럽트로 커널에 들어오면 CPU는 스택을 이쪽으로 바꿉니다. 유저 스택은 믿을 수 없기 때문입니다. 유저 프로그램이 스택 포인터를 아무 주소로나 바꿔 놓을 수 있습니다.

커널 스택은 작고 고정된 크기입니다. x86-64에서는 `THREAD_SIZE`가 4페이지, 16KB입니다. 유저 스택처럼 필요할 때 자라지 않습니다. 그래서 커널 코드는 큰 배열을 지역 변수로 두지 않고 깊은 재귀도 피합니다.

::: {.fig src="kernel-stack-current.svg"}
v7.3의 커널 스택 배치와 예전 방식. 지금은 `thread_info`가 스택 밖에 있고, 스택 양쪽에 매핑되지 않은 가드 페이지가 있습니다.
:::

`CONFIG_VMAP_STACK`이 켜져 있으면(x86-64와 arm64의 기본값) 스택은 vmalloc 영역에 가상 주소로 매핑됩니다. 앞뒤에 매핑이 없는 가드 페이지가 놓이므로, 스택이 넘치면 그 자리에서 페이지 폴트가 납니다. x86은 폴트 주소가 가드 페이지이면 `handle_stack_overflow()`를 불러 "stack guard page was hit" 메시지와 함께 커널을 멈춥니다. 조용히 옆의 메모리를 덮어쓰고 한참 뒤에 엉뚱한 곳에서 죽는 것보다 훨씬 낫습니다.

### current: 지금 실행 중인 태스크

커널 코드에는 `current`가 수없이 나옵니다. `current->mm`, `current->pid`처럼 "이 코드를 실행하고 있는 태스크"를 가리킵니다. x86-64에서는 CPU별 변수 하나입니다.

```{.c file="arch/x86/include/asm/current.h" line="15"}
DECLARE_PER_CPU_CACHE_HOT(struct task_struct *, current_task);
/* const-qualified alias provided by the linker. */
DECLARE_PER_CPU_CACHE_HOT(struct task_struct * const __percpu_seg_override,
			  const_current_task);

static __always_inline struct task_struct *get_current(void)
{
	if (IS_ENABLED(CONFIG_USE_X86_SEG_SUPPORT))
		return this_cpu_read_const(const_current_task);

	return this_cpu_read_stable(current_task);
}

#define current get_current()
```

CPU마다 `current_task` 변수가 하나씩 있고, 컨텍스트 스위치 때 `__switch_to()`가 `raw_cpu_write(current_task, next_p)`로 갱신합니다. 읽는 쪽은 `%gs` 세그먼트를 기준으로 한 메모리 읽기 명령어 하나입니다. `CACHE_HOT`은 자주 읽는 CPU별 변수들을 같은 캐시 라인에 모아 두라는 표시입니다. [6장](ch06.html)의 `__preempt_count`도 같은 묶음에 있습니다.

`this_cpu_read_stable()`의 "stable"은 컴파일러에게 주는 약속입니다. 한 함수 안에서 `current`를 여러 번 읽어도 값이 같으니 한 번만 읽고 재사용해도 된다는 뜻입니다. 태스크가 다른 CPU로 옮겨 가도 그 CPU의 `current_task`는 여전히 그 태스크이므로 약속이 성립합니다.

다른 아키텍처는 다른 방법을 씁니다. arm64는 커널 모드에서 쓰지 않는 `sp_el0` 레지스터에 `task_struct`의 주소를 넣어 둡니다. 어느 쪽이든 `current`는 메모리나 레지스터를 한 번 읽는 값입니다.

::: {.old}
많은 자료가 커널 스택을 "8KB(2페이지)이고 맨 아래에 `thread_info`가 있다"고 그립니다. 그리고 `current`는 스택 포인터의 아래 비트를 지워 `thread_info`를 찾고, 그 안의 `task` 포인터를 읽는 것이라고 설명합니다. v7.3의 x86-64는 세 가지가 모두 다릅니다. 스택은 16KB입니다. `thread_info`는 `task_struct`의 첫 필드이고 `task` 포인터는 없어졌습니다. `current`는 스택과 무관한 CPU별 변수입니다. `thread_info`를 스택에서 빼낸 것과 스택을 가드 페이지로 감싼 것은 v4.9에서 함께 들어왔습니다. 예전 배치에서는 스택이 넘치면 바로 아래의 `thread_info`부터 덮어썼고, 공격자가 그 점을 노릴 수 있었습니다.
:::

## 구조체의 배치 {#layout}

`task_struct`의 끝부분은 이렇게 생겼습니다.

```{.c file="include/linux/sched.h" line="1683"}
	/* CPU-specific state of this task: */
	struct thread_struct		thread;

	/*
	 * New fields for task_struct should be added above here, so that
	 * they are included in the randomized portion of task_struct.
	 */
	randomized_struct_fields_end
} __attribute__ ((aligned (64)));
```

필드의 순서에는 이유가 있습니다.

- **맨 앞**: `thread_info`와 `__state`입니다. 시스템 콜 출구, 인터럽트 복귀, 스케줄러가 끊임없이 읽는 값입니다. 첫머리의 주석은 "스케줄링에 결정적인 항목만 이 위에 넣으라"고 적고 있습니다.
- **가운데**: `randomized_struct_fields_start`와 `_end` 사이입니다. `CONFIG_RANDSTRUCT`를 켜고 빌드하면 컴파일러가 이 구간의 필드 순서를 빌드마다 무작위로 섞습니다. 커널 메모리를 덮어쓸 수 있는 공격자가 `cred` 포인터의 위치를 미리 알지 못하게 하려는 것입니다.
- **맨 뒤**: `thread`는 아키텍처별 CPU 상태입니다. x86에서는 FPU 레지스터 저장 영역이 구조체 바로 뒤에 한 덩어리로 붙어 할당되고, 그 크기는 CPU가 지원하는 확장 명령어에 따라 부팅 때 정해집니다.
- **정렬**: 구조체 전체를 64바이트 경계에 맞춥니다. 캐시 라인 하나의 크기입니다.

```{.c file="include/linux/compiler_types.h" line="468"}
#if defined(RANDSTRUCT) && !defined(__CHECKER__)
# define __randomize_layout __designated_init __attribute__((randomize_layout))
# define __no_randomize_layout __attribute__((no_randomize_layout))
/* This anon struct can add padding, so only enable it under randstruct. */
# define randomized_struct_fields_start	struct {
# define randomized_struct_fields_end	} __randomize_layout;
#else
```

두 매크로의 정체는 이름 없는 구조체의 여는 괄호와 닫는 괄호입니다. 섞어도 되는 필드를 이름 없는 구조체로 감싸 놓고, 그 구조체에만 무작위 배치 속성을 붙입니다. 옵션을 끄면 매크로는 빈 문자열이 되어 평범한 구조체로 돌아갑니다.

::: {.design}
`task_struct`는 커널의 거의 모든 서브시스템이 필드를 더하는 공유 자원입니다. 그런 구조체에서는 "어디에 넣느냐"가 성능과 보안을 좌우합니다. 그래서 규칙을 주석이 아니라 구조 자체에 새겼습니다. 가장 자주 읽는 필드의 자리는 구조체 맨 앞으로 고정하고, 나머지 구간은 매크로 두 줄로 울타리를 쳐서 "여기 안에 넣으면 된다"고 알려 줍니다. 필드를 더하는 사람이 캐시와 보안을 일일이 따지지 않아도 기본값이 안전하게 되어 있습니다. 한편 필드 대부분은 `#ifdef CONFIG_...`로 싸여 있어, 기능을 끈 커널에서는 그 필드가 아예 없습니다. 구조체의 크기와 필드 오프셋이 빌드 설정마다 다르다는 뜻이고, 커널 모듈이 그 커널의 헤더로 빌드되어야 하는 이유이기도 합니다.
:::

::: {.lab}
실행 중인 커널의 `task_struct`를 들여다봅니다. 커널이 BTF(타입 정보)를 내장하고 있으면(`/sys/kernel/btf/vmlinux`가 있으면) 디버그 심볼 없이도 됩니다.

```console
$ pahole -C task_struct /sys/kernel/btf/vmlinux | head -12
struct task_struct {
	struct thread_info         thread_info;          /*     0    24 */
	unsigned int               __state;              /*    24     4 */
	unsigned int               saved_state;          /*    28     4 */
	void *                     stack;                /*    32     8 */
	...

$ pahole -C task_struct /sys/kernel/btf/vmlinux | tail -4
	/* size: ..., cachelines: ..., members: ... */
	...

# grep -E '^# name|^task_struct' /proc/slabinfo
```

주석의 두 숫자는 필드의 오프셋과 크기입니다. 끝의 요약 줄에서 구조체 전체 크기와 차지하는 캐시 라인 수를 볼 수 있습니다. `/proc/slabinfo`의 `objsize` 열은 x86에서 FPU 영역까지 더한 실제 할당 크기입니다. `pahole`이 없으면 `bpftool btf dump file /sys/kernel/btf/vmlinux format c`의 출력에서 `struct task_struct {`를 찾아도 됩니다.

커널 스레드는 `ps`로 가려냅니다.

```console
$ ps -o pid,ppid,comm -p 1,2 --ppid 2 | head -6
    PID    PPID COMMAND
      1       0 systemd
      2       0 kthreadd
      3       2 pool_workqueue_release
      4       2 kworker/R-rcu_gp
      ...
$ grep -E 'Kthread|VmRSS' /proc/2/status
Kthread:	1
```

`PPID`가 2인 것은 모두 커널 스레드입니다. `/proc/<pid>/status`의 `Kthread` 줄이 `PF_KTHREAD` 플래그이고, `mm`이 없으므로 `Vm`으로 시작하는 줄은 나오지 않습니다.
:::

## 정리 {#summary}

- 리눅스의 실행 단위는 태스크 하나이고, 구조체는 `struct task_struct` 하나입니다. 프로세스, 스레드, 커널 스레드를 가르는 타입은 없습니다.
- 주소 공간, 파일 표, 시그널 핸들러 같은 자원은 `task_struct` 밖의 구조체에 있고 포인터로 가리킵니다. clone 플래그가 자원마다 공유할지 복사할지를 정합니다.
- 스레드는 `CLONE_VM | CLONE_FILES | CLONE_FS | CLONE_SIGHAND | CLONE_THREAD`로 만든 태스크입니다. 스레드 그룹은 `signal_struct`를 함께 쓰는 태스크들입니다.
- 태스크마다 `pid`가 다르고, 스레드 그룹은 `tgid`를 함께 씁니다. `getpid()`는 `tgid`를, `gettid()`는 `pid`를 돌려줍니다.
- 커널 스레드는 `mm`이 NULL이고 `kthreadd`가 만듭니다. 스위치될 때 앞 태스크의 주소 공간을 `active_mm`으로 빌려 페이지 테이블 교체를 피합니다.
- io_uring 워커 같은 유저 워커는 커널 코드만 실행하지만 만든 프로세스의 스레드입니다.
- 고루틴이나 가상 스레드는 커널에 보이지 않습니다. 커널이 스케줄하는 것은 그것들을 실어 나르는 태스크입니다.
- x86-64에서 `current`는 CPU별 변수이고, 커널 스택은 가드 페이지로 감싼 16KB입니다. `thread_info`는 `task_struct`의 첫 필드입니다.

## 확인 문제 {#quiz}

::: {.q}
스레드 넷으로 된 프로세스가 있습니다. 메인 스레드가 아닌 스레드 하나가 `fork()`를 부르면 자식 프로세스에는 태스크가 몇 개 생깁니까? 자식의 `pid`와 `tgid`는 어떻게 정해집니까?

::: {.a}
하나입니다. `fork()`는 호출한 태스크 하나만 복제합니다. `copy_process()`는 `current`의 `task_struct`를 복사할 뿐 스레드 그룹의 다른 태스크는 건드리지 않습니다. `CLONE_THREAD`가 없으므로 자식은 새 `pid`를 받고 그것을 `tgid`로 삼으며 스스로 그룹 리더가 됩니다. `CLONE_VM`도 없으므로 주소 공간은 통째로 복사되어, 다른 스레드들이 쓰던 스택과 락의 상태가 메모리에 그대로 남습니다. 그 스레드들은 자식에 없으므로, 그들이 쥐고 있던 뮤텍스는 자식에서 영영 풀리지 않습니다. 다중 스레드 프로그램에서 `fork()` 뒤에 곧바로 `exec`를 불러야 하는 이유입니다.
:::
:::

::: {.q}
`CLONE_VM`은 켜고 `CLONE_THREAD`는 끈 채 `clone()`을 부르면 어떤 태스크가 생깁니까? `ps`와 `kill`은 이 태스크를 어떻게 다룹니까?

::: {.a}
부모와 `mm_struct`를 함께 쓰지만 `signal_struct`는 따로인 태스크입니다. 주소 공간이 같으므로 메모리를 고치면 서로에게 보입니다. 그러나 스레드 그룹이 다르므로 `tgid`가 자기 `pid`와 같고, `ps`에는 별개의 프로세스로 나옵니다. 부모에게 보낸 `SIGTERM`은 이 태스크에 전달되지 않고, 부모가 `exit_group()`으로 끝나도 이 태스크는 남습니다. `vfork()`로 생긴 자식이 `exec` 전까지 이런 상태입니다.
:::
:::

::: {.q}
커널 스레드가 실행 중일 때 `current->mm`과 `current->active_mm`은 각각 무엇을 가리킵니까? 커널 스레드에서 유저 메모리에 접근하는 `copy_from_user()`를 부르면 안 되는 이유는 무엇입니까?

::: {.a}
`mm`은 NULL이고, `active_mm`은 이 CPU에서 직전에 돌던 유저 태스크의 `mm_struct`입니다(직전 태스크도 커널 스레드였다면 그 태스크가 빌려 쓰던 것을 넘겨받습니다). CPU에 실린 페이지 테이블이 그 `mm`의 것이므로 유저 영역 주소로 접근하면 우연히 그 자리에 있던 프로세스의 메모리를 읽거나 쓰게 됩니다. 커널 스레드는 어느 프로세스를 위해 일하는지 정해져 있지 않으므로 그 접근은 뜻이 없고 위험합니다. 특정 프로세스의 메모리를 다뤄야 하는 커널 스레드는 `kthread_use_mm()`으로 그 `mm`을 명시적으로 빌려야 합니다. io_uring 워커가 커널 스레드가 아니라 프로세스의 스레드로 만들어지는 이유 가운데 하나도 이것입니다.
:::
:::

::: {.q}
Go 프로그램이 고루틴 만 개를 띄우고, 각 고루틴이 네트워크 소켓에서 읽기를 기다립니다. `/proc/<pid>/task` 아래의 디렉터리는 대략 몇 개이고, 그 태스크들은 커널에서 어떤 상태입니까?

::: {.a}
만 개가 아니라 코어 수와 비슷한 규모입니다. 고루틴은 Go 런타임이 관리하는 유저 수준 스레드이고 커널은 그 존재를 모릅니다. 런타임은 소켓을 논블로킹으로 열고 `epoll`에 등록해 둔 뒤, 읽을 것이 없는 고루틴을 유저 공간에서 재워 두고 태스크에는 다른 고루틴을 올립니다. 돌릴 고루틴이 하나도 없으면 태스크들은 `epoll_wait()`나 futex에서 잠듭니다. 커널에서 보면 잠든 태스크 몇 개가 있을 뿐입니다.
:::
:::

::: {.q}
x86-64의 v7.3 커널에서 커널 함수가 16KB 넘게 재귀해 스택을 넘겼습니다. `CONFIG_VMAP_STACK`이 켜진 경우와 꺼진 경우에 각각 무슨 일이 일어납니까?

::: {.a}
켜진 경우, 스택은 vmalloc 영역에 매핑되어 있고 그 아래 주소는 매핑이 없는 가드 페이지입니다. 스택 포인터가 가드 페이지로 내려가 쓰는 순간 페이지 폴트가 납니다. 폴트 정보를 쌓을 스택조차 남지 않았으면 CPU가 이중 폴트를 내고, 이것은 따로 마련된 스택에서 처리됩니다. 어느 쪽 핸들러든 폴트 주소가 스택의 가드 페이지임을 확인하면 `handle_stack_overflow()`로 "stack guard page was hit"을 찍고 멈춥니다. 꺼진 경우, 스택은 연속된 물리 페이지이고 그 아래에는 다른 용도로 할당된 메모리가 있습니다. 넘친 쓰기는 그 메모리를 조용히 덮어씁니다. 스택의 가장 낮은 주소에 써 둔 `STACK_END_MAGIC`이 망가졌는지를 스케줄러가 디버그 옵션으로 검사할 수는 있지만, 덮어쓴 뒤에야 알게 됩니다.
:::
:::

## 용어 {#terms}

::: {.terms}
task_struct
:   태스크 하나의 모든 정보를 담는 구조체. 리눅스의 PCB.

스레드 그룹 (thread group)
:   `signal_struct`를 함께 쓰는 태스크들의 모임. 유저 공간이 프로세스 하나로 보는 단위.

tgid
:   스레드 그룹의 ID. 그룹 리더의 `pid`와 같고, `getpid()`가 돌려주는 값.

그룹 리더 (group leader)
:   스레드 그룹에서 맨 처음 만들어진 태스크. `pid`와 `tgid`가 같다.

struct pid
:   숫자 PID를 대신해 커널 안에서 태스크, 스레드 그룹, 프로세스 그룹, 세션을 가리키는 참조 카운트 객체.

커널 스레드 (kernel thread)
:   유저 모드로 나가지 않고 커널 안에서만 도는 태스크. `mm`이 NULL이고 `PF_KTHREAD`가 서 있다.

active_mm
:   지금 CPU에 실려 있는 주소 공간. 커널 스레드에서는 앞 태스크에게서 빌린 것이다.

lazy TLB
:   커널 스레드로 스위치할 때 페이지 테이블을 바꾸지 않고 버티는 기법.

유저 워커 (user worker)
:   프로세스의 스레드로 만들어지지만 커널 코드만 실행하는 태스크. io_uring 워커가 그 예.

커널 스택 (kernel stack)
:   태스크가 커널 모드에서 쓰는 고정 크기 스택. 태스크마다 하나.

current
:   지금 이 CPU에서 실행 중인 태스크의 `task_struct`를 가리키는 매크로.

thread_info
:   스레드 플래그 등 진입·복귀 경로가 자주 읽는 값을 담는 작은 구조체. `task_struct`의 첫 필드.
:::
