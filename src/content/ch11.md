::: {.lead}
인터럽트 핸들러는 인터럽트를 끈 채 실행됩니다. 핸들러가 1밀리초를 쓰면 그 CPU는 1밀리초 동안 다른 장치의 신호를 받지 못하고, 깨어나야 할 태스크도 그만큼 늦습니다. 그런데 패킷 하나를 받아 소켓에 넣기까지의 일은 수십 마이크로초가 넘고, 어떤 일은 락을 기다리며 잠들어야 합니다. 그래서 커널은 일을 둘로 가릅니다. 지금 당장 해야 하는 조금과, 인터럽트를 다시 켠 뒤에 해도 되는 나머지입니다. 이 장은 그 나머지를 맡기는 방법들이 왜 여럿이고, v7.3에서 무엇이 남았는지를 봅니다.
:::

::: {.goals}
- 인터럽트 처리를 top half와 bottom half로 나누는 기준은 무엇인가?
- softirq는 누가 예약하고, 어느 자리에서 실행되는가?
- softirq 처리가 길어지면 왜 `ksoftirqd`로 넘기는가?
- 태스크릿은 softirq와 무엇이 다르고, 왜 걷어 내는 중인가?
- 워크큐의 `kworker` 스레드 수는 누가 정하는가?
- 새 드라이버는 softirq, BH 워크큐, 워크큐, 스레드 IRQ 가운데 무엇을 골라야 하는가?
:::

## 왜 일을 나누는가 {#why-split}

[10장](ch10.html)에서 본 대로, 장치가 인터럽트를 걸면 커널은 `irq_desc`를 찾아 드라이버가 등록한 핸들러를 부릅니다. 이 핸들러가 도는 동안에는 제약이 셋 있습니다.

- **그 CPU의 인터럽트가 꺼져 있습니다.** 다른 장치의 인터럽트도, 타이머 틱도 들어오지 못합니다.
- **잠들 수 없습니다.** 핸들러는 끊긴 태스크의 문맥을 빌려 돌 뿐 자기 태스크가 없습니다. `schedule()`을 불러 CPU를 내놓으면 돌아올 자리가 없습니다. 뮤텍스, `GFP_KERNEL` 할당, 유저 메모리 접근이 모두 막힙니다.
- **선점되지 않습니다.** `preempt_count`의 hardirq 칸이 0이 아니기 때문입니다([6장](ch06.html)).

그래서 핸들러는 짧아야 합니다. 핸들러가 하는 일을 **top half**, 뒤로 미룬 일을 **bottom half**라고 부릅니다. top half에는 미루면 안 되는 일만 남깁니다. 장치가 정말 인터럽트를 걸었는지 확인하고, 장치의 인터럽트 원인을 지우고, 사라지기 전에 꺼내야 하는 데이터를 꺼내고, 나머지 일을 예약합니다.

::: {.fig src="split-timeline.svg"}
인터럽트 하나가 만든 일이 세 컨텍스트로 나뉘어 실행됩니다. 뒤로 갈수록 제약이 풀리고, 대신 실행 시점이 늦어집니다.
:::

실제 핸들러를 하나 봅니다. 인텔 기가비트 NIC 드라이버 e1000e의 MSI 인터럽트 핸들러입니다.

```{.c file="drivers/net/ethernet/intel/e1000e/netdev.c" line="1770"}
static irqreturn_t e1000_intr_msi(int __always_unused irq, void *data)
{
	struct net_device *netdev = data;
	struct e1000_adapter *adapter = netdev_priv(netdev);
	struct e1000_hw *hw = &adapter->hw;
	u32 icr = er32(ICR);

	/* read ICR disables interrupts using IAM */
	if (icr & E1000_ICR_LSC) {
		hw->mac.get_link_status = true;
		/* ... */
		/* guard against interrupt when we're going down */
		if (!test_bit(__E1000_DOWN, &adapter->state))
			mod_timer(&adapter->watchdog_timer, jiffies + 1);
	}

	/* Reset on uncorrectable ECC error */
	if ((icr & E1000_ICR_ECCER) && (hw->mac.type >= e1000_pch_lpt)) {
		/* ... */

		/* Do the reset outside of interrupt context */
		schedule_work(&adapter->reset_task);

		/* return immediately since reset is imminent */
		return IRQ_HANDLED;
	}

	if (napi_schedule_prep(&adapter->napi)) {
		/* ... */
		__napi_schedule_irqoff(&adapter->napi);
	}

	return IRQ_HANDLED;
}
```

읽을 곳은 네 군데입니다.

- `er32(ICR)`가 top half의 본체입니다. 인터럽트 원인 레지스터를 읽으면 장치 쪽 인터럽트가 함께 막힙니다. 이 일은 미룰 수 없습니다.
- 링크 상태가 바뀌었으면 `mod_timer()`로 타이머를 겁니다. 타이머 콜백은 `TIMER_SOFTIRQ`에서 실행됩니다.
- 어댑터를 리셋해야 하면 `schedule_work()`로 워크큐에 넘깁니다. 리셋은 잠들 수 있는 긴 작업이기 때문입니다.
- 받은 패킷은 여기서 처리하지 않습니다. `__napi_schedule_irqoff()`가 `NET_RX_SOFTIRQ`를 예약할 뿐입니다. 패킷 처리는 [12장](ch12.html)에서 따라갑니다.

핸들러 하나가 일을 세 곳에 나눠 맡겼습니다. 이 장의 나머지는 그 맡기는 곳들이 어떻게 생겼는지입니다.

::: {.old}
옛 자료는 top half를 다시 둘로 나눕니다. PIC에 응답하는 "critical" 부분은 인터럽트를 끈 채 돌고, 드라이버 핸들러를 부르는 "non-critical" 부분은 `SA_INTERRUPT` 플래그가 없으면 `local_irq_enable()`로 인터럽트를 켠 채 돈다는 설명입니다. v7.3에는 이 구분이 없습니다. 모든 핸들러가 인터럽트를 끈 채 실행됩니다. 핸들러가 인터럽트를 켜고 돌아오면 `__handle_irq_event_percpu()`가 "enabled interrupts" 경고를 찍고 다시 끕니다. 인터럽트를 켠 채 도는 핸들러는 중첩 깊이를 예측할 수 없어 스택을 넘칠 위험이 있었고, 2.6.35에서 `IRQF_DISABLED` 플래그가 뜻을 잃으면서 정리되었습니다. 길게 걸리는 일은 핸들러 안에서 인터럽트를 켜는 대신 bottom half로 보내는 것이 지금의 규칙입니다.
:::

::: {.design}
급한 일과 미룰 수 있는 일을 가르는 구조는 커널만의 것이 아닙니다. 웹 서버는 요청을 받는 스레드에서 검증과 응답만 하고, 메일 발송이나 썸네일 생성은 작업 큐로 넘깁니다. 새 일을 받아들이는 경로가 막히면 시스템 전체가 멈추므로, 그 경로에는 상한이 분명한 일만 둡니다. 커널에는 조건이 하나 더 붙습니다. 미룬 일을 어떤 실행 컨텍스트에서 돌리느냐에 따라 할 수 있는 일이 달라집니다. 그래서 큐가 하나가 아니라 여럿입니다.
:::

## softirq: 번호 열 개와 비트맵 {#softirq}

**softirq**는 가장 낮은 층의 bottom half입니다. 종류가 컴파일할 때 정해져 있고, 모듈이 새로 등록할 수 없습니다. v7.3에는 열 개가 있습니다.

```{.c file="include/linux/interrupt.h" line="550"}
enum
{
	HI_SOFTIRQ=0,
	TIMER_SOFTIRQ,
	NET_TX_SOFTIRQ,
	NET_RX_SOFTIRQ,
	BLOCK_SOFTIRQ,
	IRQ_POLL_SOFTIRQ,
	TASKLET_SOFTIRQ,
	SCHED_SOFTIRQ,
	HRTIMER_SOFTIRQ,
	RCU_SOFTIRQ,    /* Preferable RCU should always be the last softirq */

	NR_SOFTIRQS
};
```

자료구조는 둘입니다. 하나는 번호마다 핸들러 함수를 담은 전역 배열 `softirq_vec[]`입니다. 다른 하나는 CPU마다 따로 있는 **pending 비트맵**입니다. 비트 n이 서 있으면 "이 CPU에서 n번 softirq를 실행해야 한다"는 뜻입니다. x86에서는 이 비트맵이 16비트 CPU별 변수 `__softirq_pending`입니다.

::: {.fig src="pending-vec.svg"}
pending 비트맵은 CPU마다, 핸들러 배열은 시스템에 하나입니다. 같은 번호의 비트가 두 CPU에 동시에 설 수 있습니다.
:::

핸들러를 등록하는 `open_softirq()`와 실행을 예약하는 `raise_softirq()`는 이 두 자료구조를 건드리는 것이 전부입니다.

```{.c file="kernel/softirq.c" line="796"}
inline void raise_softirq_irqoff(unsigned int nr)
{
	__raise_softirq_irqoff(nr);

	/*
	 * If we're in an interrupt or softirq, we're done
	 * (this also catches softirq-disabled code). We will
	 * actually run the softirq once we return from
	 * the irq or softirq.
	 *
	 * Otherwise we wake up ksoftirqd to make sure we
	 * schedule the softirq soon.
	 */
	if (!in_interrupt() && should_wake_ksoftirqd())
		wakeup_softirqd();
}

/* ... */
void __raise_softirq_irqoff(unsigned int nr)
{
	lockdep_assert_irqs_disabled();
	trace_softirq_raise(nr);
	or_softirq_pending(1UL << nr);
}

void open_softirq(int nr, void (*action)(void))
{
	softirq_vec[nr].action = action;
}
```

예약은 비트 하나를 OR로 세우는 일입니다. 큐에 무엇을 넣지도, 메모리를 할당하지도 않습니다. 대신 softirq는 "무슨 일을 할지"를 전달받지 못합니다. `net_rx_action()`은 불렸을 때 자기 CPU의 폴링 목록을 스스로 찾아봅니다. 예약할 때 일감을 CPU별 목록에 걸어 두고, 핸들러가 그 목록을 비우는 것이 softirq를 쓰는 코드의 공통된 모양입니다.

주석의 뒷부분도 봐 둡니다. 인터럽트나 softirq 안에서 예약했다면 비트만 세우고 끝입니다. 돌아가는 길에 누군가 실행해 줄 것이기 때문입니다. 그렇지 않은 자리, 곧 보통의 태스크 컨텍스트에서 예약했다면 실행해 줄 "돌아가는 길"이 없으므로 `ksoftirqd`를 깨웁니다.

## softirq가 실행되는 세 자리 {#where-softirq}

비트를 세우는 것과 핸들러가 불리는 것은 다른 시점입니다. pending 비트를 확인하고 핸들러를 부르는 자리는 셋입니다.

::: {.fig src="softirq-entry-points.svg"}
세 길이 모두 `handle_softirqs()`로 모입니다. 조건이 깨지면 남은 일은 ③으로 넘어갑니다.
:::

**① 인터럽트에서 돌아가는 길.** 가장 흔한 경로입니다. 아키텍처의 진입 코드는 핸들러를 부른 뒤 `irq_exit_rcu()`를 부릅니다.

```{.c file="kernel/softirq.c" line="743"}
static inline void __irq_exit_rcu(void)
{
#ifndef __ARCH_IRQ_EXIT_IRQS_DISABLED
	local_irq_disable();
#else
	lockdep_assert_irqs_disabled();
#endif
	account_hardirq_exit(current);
	preempt_count_sub(HARDIRQ_OFFSET);
	if (!in_interrupt() && local_softirq_pending()) {
		/*
		 * If we left hrtimers unarmed, make sure to arm them now,
		 * before enabling interrupts to run softirq.
		 */
		hrtimer_rearm_deferred();
		invoke_softirq();
	}
	/* ... */
}
```

`preempt_count`에서 hardirq 칸을 내린 다음 `in_interrupt()`를 확인합니다. 참이면 실행하지 않습니다. 참이 되는 것은 끊긴 코드가 softirq를 실행 중이었거나 `local_bh_disable()`로 막아 둔 구간이었을 때입니다. 그래서 **softirq는 같은 CPU에서 자기 자신 위에 중첩되지 않습니다.**

`invoke_softirq()`는 보통 그 자리에서 `__do_softirq()`를 부릅니다. 부팅 인자 `threadirqs`로 인터럽트 강제 스레드화를 켠 커널에서는 여기서 실행하지 않고 `ksoftirqd`를 깨웁니다.

**② BH를 다시 켤 때.** 태스크 컨텍스트의 코드가 `local_bh_disable()`이나 `spin_lock_bh()`로 softirq를 막아 둔 동안 인터럽트가 와서 비트를 세웠다면, ①의 검사에 걸려 실행되지 못한 채 남아 있습니다. `local_bh_enable()`은 막은 횟수를 내리고, 0이 되었는데 pending이 있으면 그 자리에서 `do_softirq()`를 부릅니다. `preempt_enable()`이 미뤄 둔 재스케줄을 처리하는 것과 같은 구조입니다.

**③ `ksoftirqd`.** CPU마다 하나씩 있는 커널 스레드 `ksoftirqd/N`입니다. 깨어나면 pending을 확인하고 `handle_softirqs(true)`를 부릅니다. 보통의 `SCHED_OTHER` 태스크이므로 다른 태스크와 CPU를 나눠 씁니다. 필요한 이유는 다음 절에 있습니다.

## 한도와 ksoftirqd {#limits}

세 길이 모이는 함수가 `handle_softirqs()`입니다.

```{.c file="kernel/softirq.c" line="602"}
static void handle_softirqs(bool ksirqd)
{
	unsigned long end = jiffies + MAX_SOFTIRQ_TIME;
	unsigned long old_flags = current->flags;
	int max_restart = MAX_SOFTIRQ_RESTART;
	/* ... */
	pending = local_softirq_pending();
	softirq_handle_begin();
	/* ... */
restart:
	/* Reset the pending bitmask before enabling irqs */
	set_softirq_pending(0);

	local_irq_enable();

	h = softirq_vec;
	while ((softirq_bit = ffs(pending))) {
		/* ... */
		h += softirq_bit - 1;
		/* ... */
		trace_softirq_entry(vec_nr);
		h->action();
		trace_softirq_exit(vec_nr);
		/* ... */
		h++;
		pending >>= softirq_bit;
	}
	/* ... */
	local_irq_disable();

	pending = local_softirq_pending();
	if (pending) {
		if (time_before(jiffies, end) && !need_resched() &&
		    --max_restart)
			goto restart;

		wakeup_softirqd();
	}
	/* ... */
}
```

흐름은 이렇습니다.

1. pending 비트맵을 지역 변수로 복사하고 원본을 0으로 지웁니다.
2. `softirq_handle_begin()`이 `preempt_count`의 softirq 칸을 올립니다. 이제 `in_serving_softirq()`가 참이고, 이 CPU에서 softirq가 다시 시작되지 않습니다.
3. **인터럽트를 켭니다.** softirq 핸들러는 인터럽트가 켜진 채 돕니다. top half와의 결정적인 차이입니다.
4. `ffs()`로 가장 낮은 비트부터 찾아 `action()`을 부릅니다.
5. 인터럽트를 끄고 pending을 다시 봅니다. 핸들러가 도는 사이에 새 인터럽트가 와서 비트를 또 세웠을 수 있습니다.

5에서 pending이 남아 있으면 계속 돌지 그만둘지 정해야 합니다. 계속 도는 것은 조건 셋이 모두 참일 때입니다.

```{.c file="kernel/softirq.c" line="561"}
 * These limits have been established via experimentation.
 * The two things to balance is latency against fairness -
 * we want to handle softirqs as soon as possible, but they
 * should not be able to lock up the box.
 */
#define MAX_SOFTIRQ_TIME  msecs_to_jiffies(2)
#define MAX_SOFTIRQ_RESTART 10
```

2ms가 지나지 않았고, 재스케줄 요청이 없고, 재시작이 10회 미만이어야 합니다. 하나라도 깨지면 `wakeup_softirqd()`로 `ksoftirqd`를 깨우고 빠져나옵니다. 시간은 `jiffies`로 재므로 거칩니다. `HZ=250`이면 2ms가 1틱으로 올림되어 실제 한도는 0–4ms 사이입니다.

한도가 없으면 어떻게 될까요. 패킷이 쉬지 않고 들어오는 서버를 생각합니다. 인터럽트 복귀 길에서 softirq를 실행하는데, 실행하는 동안 패킷이 또 와서 비트가 다시 섭니다. 이 고리가 끊기지 않으면 끊긴 태스크는 영영 돌아오지 못합니다. softirq는 스케줄러 바깥에서 돌기 때문에, 스케줄러가 아무리 공정해도 유저 태스크가 굶습니다. `ksoftirqd`로 넘긴다는 것은 **남은 softirq 일을 스케줄러가 보는 태스크로 바꾼다**는 뜻입니다. 그러면 유저 태스크와 softirq 처리가 CPU를 나눠 쓰게 됩니다.

::: {.myth}
"`ksoftirqd`가 CPU를 많이 쓰니 `ksoftirqd`에 문제가 있다." 아닙니다. `ksoftirqd`의 CPU 사용량은 인터럽트 복귀 길에서 다 처리하지 못하고 넘어온 softirq 일의 양입니다. 볼 곳은 `/proc/softirqs`에서 어느 번호가 어느 CPU에서 빠르게 느는가입니다. 네트워크 수신이 한 CPU에 몰려 있다면 수신 큐를 여러 CPU로 펴는 설정([12장](ch12.html))이 해법입니다.
:::

::: {.old}
softirq 실행 함수를 `__do_softirq()`로, 핸들러 호출을 `h->action(h)`로 적은 자료가 많습니다. v7.3에서 본체는 `handle_softirqs(bool ksirqd)`이고 `__do_softirq()`는 이것을 `false`로 부르는 한 줄짜리 껍데기입니다. 인자는 `ksoftirqd`에서 불렸는지를 알려 RCU에 정지 상태를 보고하는 데 씁니다. 핸들러의 인자도 사라져 `void (*action)(void)`가 되었습니다. 아무 핸들러도 쓰지 않던 인자였습니다.
:::

::: {.lab}
softirq가 어느 CPU에서 얼마나 실행되었는지 봅니다.

```console
$ cat /proc/softirqs
                    CPU0       CPU1       CPU2       CPU3
          HI:          2          0          1          0
       TIMER:     184220     179034     181467     176950
      NET_RX:      52811        973       1210        877
         RCU:     223901     219876     221344     218002
...
```

예시에서는 `NET_RX`가 CPU 0에 몰려 있습니다. `watch -d -n1 cat /proc/softirqs`는 늘어나는 칸을 강조해 줍니다. `top`의 `%Cpu(s)` 줄에서 `si`는 softirq 처리에 쓴 시간의 비율이고, `hi`는 hardirq입니다. `ps -e | grep ksoftirqd`로 CPU마다 스레드가 하나씩 있는 것도 확인할 수 있습니다.

번호별 실행 횟수를 추적점으로 셉니다. 키로 나오는 숫자는 앞의 열거형 번호입니다(3이 `NET_RX`).


## softirq의 성질, 태스크릿, BH 워크큐 {#tasklet}

softirq 핸들러의 성질을 정리합니다.

- 인터럽트가 켜져 있습니다. 핸들러가 도는 중에 hardirq가 끼어들 수 있습니다.
- 잠들 수 없습니다. `ksoftirqd`에서 실행될 때도 `preempt_count`의 softirq 칸이 올라가 있어 원자적 컨텍스트입니다.
- 같은 CPU에서는 중첩되지 않습니다.
- **같은 softirq가 여러 CPU에서 동시에 돕니다.** 두 CPU가 같은 순간에 `net_rx_action()`을 실행할 수 있습니다.

마지막 성질 때문에 softirq 핸들러는 공유 데이터를 스스로 지켜야 합니다. 네트워크 스택이 CPU별 큐를 쓰고 소켓마다 락을 두는 이유입니다. 어떤 락이 필요한지는 [13장](ch13.html)에서 다룹니다.

이 부담을 덜어 주려고 softirq 위에 얹은 것이 **태스크릿**(tasklet)입니다. 태스크릿은 실행 중에 만들 수 있고, **같은 태스크릿은 한 번에 한 CPU에서만** 돕니다.

::: {.fig src="softirq-vs-tasklet.svg"}
직렬화 범위가 세대마다 좁아졌습니다. 옛 BH는 전체에서 하나, 태스크릿은 자기 자신과만, softirq는 직렬화하지 않습니다.
:::

구현은 `HI_SOFTIRQ`와 `TASKLET_SOFTIRQ`의 핸들러에 있습니다. CPU별 목록에서 태스크릿을 하나씩 꺼내 실행합니다.

```{.c file="kernel/softirq.c" line="951"}
	while (list) {
		struct tasklet_struct *t = list;

		list = list->next;

		if (tasklet_trylock(t)) {
			if (!atomic_read(&t->count)) {
				if (tasklet_clear_sched(t)) {
					if (t->use_callback) {
						/* ... */
						t->callback(t);
						/* ... */
					} else {
						/* ... */
					}
				}
				tasklet_unlock(t);
				tasklet_callback_sync_wait_running();
				continue;
			}
			tasklet_unlock(t);
		}

		local_irq_disable();
		t->next = NULL;
		*tl_head->tail = t;
		tl_head->tail = &t->next;
		__raise_softirq_irqoff(softirq_nr);
		local_irq_enable();
	}
```

`tasklet_trylock()`은 `state`의 `TASKLET_STATE_RUN` 비트를 원자적으로 세워 봅니다. 다른 CPU가 이미 이 태스크릿을 실행 중이면 실패하고, 아래쪽 코드가 태스크릿을 목록 끝에 다시 걸고 softirq를 한 번 더 예약합니다. 이것이 직렬화의 전부입니다.

### 태스크릿을 걷어 내는 중

v7.3의 `include/linux/interrupt.h`는 태스크릿 선언 위에 "This API is deprecated"라고 적고 스레드 IRQ를 쓰라고 권합니다. 이유는 여럿입니다.

- 실행 시점을 제어할 수 없습니다. 태스크릿은 softirq로 돌기 때문에 우선순위가 가장 높은 실시간 태스크보다도 먼저 실행됩니다. 지연 시간을 관리하려는 쪽에서 보면 스케줄러가 손댈 수 없는 구간입니다.
- 인터페이스에 오래된 결함이 있습니다. 한 번 쓰고 스스로를 해제하는 태스크릿은, 콜백이 돌아온 뒤에도 실행기가 그 구조체의 상태 비트를 건드리기 때문에 해제된 메모리에 쓰게 됩니다.
- softirq와 워크큐 사이에 메커니즘이 하나 더 있다는 것 자체가 부담입니다.

대체재가 **BH 워크큐**입니다. 워크큐의 API를 그대로 쓰되, 워크 함수가 스레드가 아니라 softirq 컨텍스트에서 실행됩니다. `alloc_workqueue()`에 `WQ_BH` 플래그를 주거나 미리 만들어진 `system_bh_wq`, `system_bh_highpri_wq`를 씁니다. TCP가 이미 이렇게 바뀌었습니다.

```{.c file="net/ipv4/tcp_output.c" line="1418"}
	/* queue this socket to BH workqueue */
	local_irq_save(flags);
	tsq = this_cpu_ptr(&tsq_work);
	empty = list_empty(&tsq->head);
	list_add(&tp->tsq_node, &tsq->head);
	if (empty)
		queue_work(system_bh_wq, &tsq->work);
	local_irq_restore(flags);
```

BH 워크가 실제로 실행되는 자리는 태스크릿과 같은 softirq입니다.

```{.c file="kernel/softirq.c" line="986"}
static __latent_entropy void tasklet_action(void)
{
	workqueue_softirq_action(false);
	tasklet_action_common(this_cpu_ptr(&tasklet_vec), TASKLET_SOFTIRQ);
}
```

`TASKLET_SOFTIRQ` 핸들러가 태스크릿 목록보다 먼저 BH 워크큐의 풀을 비웁니다. `kernel/workqueue.c`의 주석은 태스크릿 사용처를 모두 옮기고 나면 이 softirq를 워크큐가 직접 쓰겠다고 적어 두었습니다. BH 워크는 잠들 수 없다는 점은 태스크릿과 같지만, `delayed_work`, `flush_work()`, `cancel_work_sync()`, `disable_work_sync()` 같은 워크큐의 도구를 그대로 쓸 수 있고, 앞의 해제 문제도 없습니다.

## 워크큐 {#workqueue}

**워크큐**(workqueue)는 미룬 일을 커널 스레드에서 실행합니다. 프로세스 컨텍스트이므로 잠들 수 있습니다. 뮤텍스를 잡고, `GFP_KERNEL`로 할당하고, 장치의 응답을 기다릴 수 있습니다. 대가는 지연입니다. 스레드가 깨어나 스케줄러에게 CPU를 받을 때까지 기다려야 합니다.

쓰는 쪽에서 보면 단순합니다. 함수 포인터를 담은 `work_struct`를 구조체에 넣어 두고, 필요할 때 `queue_work(wq, &work)`나 `schedule_work(&work)`로 예약합니다. 일정 시간 뒤에 실행하려면 타이머가 붙은 `delayed_work`를 씁니다.

안쪽은 네 층입니다.

::: {.fig src="workqueue-structure.svg"}
v7.3의 워크큐 구조. `kworker/0:1`의 0은 CPU 번호, `kworker/u8:3`의 8은 unbound 풀의 ID입니다.
:::

- `workqueue_struct`: 코드가 일을 넣는 대상입니다. 플래그와 이름을 가질 뿐 스레드를 갖지 않습니다.
- `worker_pool`: 대기 중인 워크의 목록(`worklist`)과 워커 스레드의 묶음입니다. CPU마다 일반 풀과 높은 우선순위 풀이 하나씩 있고, 특정 CPU에 묶이지 않는 unbound 풀이 따로 있습니다.
- `pool_workqueue`: 워크큐와 풀을 잇는 고리입니다. 워크큐별 통계와 동시 실행 한도(`max_active`)를 여기서 셉니다.
- `worker`: `kworker` 스레드 하나입니다.

요점은 **스레드가 워크큐가 아니라 풀에 속한다**는 것입니다. 시스템에 워크큐가 수백 개 있어도 CPU 하나의 일반 풀은 하나이고, 그 풀의 `kworker` 몇 개가 모든 워크큐의 일을 처리합니다.

### 동시성 관리

풀에 `kworker`를 몇 개 둘지는 누가 정할까요. 워크 함수가 CPU만 쓴다면 CPU당 하나면 충분합니다. 둘을 깨워 봐야 번갈아 돌 뿐입니다. 문제는 워크 함수가 잠들 때입니다. 하나뿐인 워커가 디스크 I/O를 기다리며 잠들면, 뒤에 쌓인 워크는 CPU가 놀고 있는데도 실행되지 못합니다.

**동시성 관리 워크큐**(concurrency managed workqueue, CMWQ)는 이것을 스케줄러와 손잡고 풉니다. 풀은 "지금 실행 중인 워커 수" `nr_running`을 셉니다. 깨울지 말지는 이 숫자로 정합니다.

```{.c file="kernel/workqueue.c" line="952"}
static bool need_more_worker(struct worker_pool *pool)
{
	return !list_empty(&pool->worklist) && !pool->nr_running;
}
```

할 일이 있고 실행 중인 워커가 없을 때만 워커를 더 깨웁니다. 그리고 워커가 잠드는 순간을 스케줄러가 알려 줍니다. `kworker`가 `schedule()`로 들어가 잠들려 할 때 스케줄러가 이 함수를 부릅니다.

```{.c file="kernel/workqueue.c" line="1484"}
void wq_worker_sleeping(struct task_struct *task)
{
	struct worker *worker = kthread_data(task);
	struct worker_pool *pool;

	/* ... */
	if (worker->flags & WORKER_NOT_RUNNING)
		return;

	pool = worker->pool;
	/* ... */
	WRITE_ONCE(worker->sleeping, 1);
	raw_spin_lock_irq(&pool->lock);
	/* ... */
	pool->nr_running--;
	if (kick_pool(pool))
		worker->current_pwq->stats[PWQ_STAT_CM_WAKEUP]++;

	raw_spin_unlock_irq(&pool->lock);
}
```

잠드는 워커가 `nr_running`을 내리고 `kick_pool()`을 부릅니다. 숫자가 0이 되었고 대기 중인 워크가 있으면 쉬고 있던 다른 워커가 깨어납니다. 쉬는 워커가 없으면 새로 만듭니다. 풀은 "CPU에서 실제로 돌고 있는 워커가 하나"인 상태를 유지하려 합니다. 워크 함수가 잠들지 않으면 워커는 하나로 충분하고, 자주 잠들면 그만큼 늘어납니다.

unbound 풀은 이 관리를 하지 않습니다. 대신 워커가 **친화성 범위**(affinity scope) 안의 아무 CPU에서나 돌 수 있어, 배치를 스케줄러에 맡깁니다. v7.3의 기본 범위는 `cache_shard`입니다. 마지막 단계 캐시를 공유하는 CPU들을 코어 8개 이하의 조각으로 나눈 것으로, 워크를 넣은 CPU 가까이에서 실행해 캐시를 살립니다. CPU를 오래 쓰는 일은 unbound 워크큐에 넣습니다.

::: {.old}
옛 자료의 워크큐는 "워크큐를 만들면 CPU마다 전용 스레드가 생긴다"는 구조입니다. 워크큐가 늘수록 스레드가 CPU 수의 배수로 늘어, 부팅만으로 PID 공간을 다 쓰는 시스템이 나왔습니다. 2.6.36의 CMWQ가 풀을 공유하게 바꾼 뒤로 `ps`에 보이는 이름은 `kworker/…`입니다.

API의 이름도 최근에 바뀌었습니다. `schedule_work()`가 쓰는 기본 워크큐는 오랫동안 `system_wq`였습니다. v7.3의 헤더는 이렇습니다.

```{.c file="include/linux/workqueue.h" line="465"}
extern struct workqueue_struct *system_wq; /* use system_percpu_wq, this will be removed */
extern struct workqueue_struct *system_percpu_wq;
extern struct workqueue_struct *system_highpri_wq;
extern struct workqueue_struct *system_long_wq;
extern struct workqueue_struct *system_unbound_wq;
extern struct workqueue_struct *system_dfl_wq;
```

`system_wq`는 `system_percpu_wq`로, `system_unbound_wq`는 `system_dfl_wq`로 옮겨 가는 중입니다. 옛 이름에 워크를 넣으면 커널이 한 번 경고를 찍습니다. `alloc_workqueue()`에도 `WQ_PERCPU`와 `WQ_UNBOUND` 가운데 하나를 명시하게 되었습니다. "dfl"(default)이라는 이름에 방향이 담겨 있습니다. CPU에 묶지 않는 쪽을 기본으로 삼으려는 것입니다. CPU별 워크는 쉬고 있는 CPU를 깨우고, 격리해 둔 CPU에 일을 밀어 넣기 때문입니다.
:::

::: {.warn}
`flush_work()`와 `cancel_work_sync()`는 그 워크 함수가 끝날 때까지 잠듭니다. 워크 함수가 잡으려는 뮤텍스를 쥔 채 이 함수들을 부르면, 워크는 뮤텍스를 기다리고 나는 워크를 기다리는 교착이 됩니다. 드라이버를 내릴 때 흔히 나오는 버그입니다.
:::

::: {.lab}
`kworker`의 이름에는 정보가 들어 있습니다.

```console
$ ps -e -o pid,ni,comm | grep kworker
      8 -20 kworker/0:0H-events_highpri
     37   0 kworker/1:1-events
    112   0 kworker/u16:3+events_unbound
    215 -20 kworker/R-nvme-wq
```

- `kworker/1:1`: CPU 1의 풀에 속한 1번 워커.
- 끝의 `H`: 높은 우선순위 풀(nice -20).
- `kworker/u16:3`: unbound 풀. `u` 뒤의 숫자는 CPU 수가 아니라 풀의 ID입니다.
- `kworker/R-이름`: 그 워크큐의 구조 워커(rescuer). 메모리가 모자라 새 워커를 만들지 못할 때 대신 일합니다.
- `-events`, `+events_unbound`: 마지막으로 실행한 워크큐의 이름. `+`는 지금 실행 중이라는 뜻입니다.

워크큐별 통계는 커널 소스의 `tools/workqueue/wq_monitor.py`로 봅니다. drgn과 커널 디버그 정보가 필요합니다. `CMW` 열이 앞에서 본 `PWQ_STAT_CM_WAKEUP`, 곧 워커가 잠들어 다른 워커를 깨운 횟수입니다.
:::

## 스레드 IRQ 핸들러 {#threaded-irq}

워크큐는 여러 곳에서 온 일을 풀 하나가 섞어 처리합니다. 인터럽트 하나에 딸린 일이라면 더 직접적인 방법이 있습니다. 그 인터럽트 전용의 커널 스레드를 두는 것입니다. **스레드 IRQ 핸들러**(threaded IRQ handler)입니다.

`request_threaded_irq()`는 핸들러를 둘 받습니다. hardirq에서 도는 1차 핸들러 `handler`와, 전용 스레드에서 도는 `thread_fn`입니다. 1차 핸들러는 자기 장치의 인터럽트인지만 확인하고 `IRQ_WAKE_THREAD`를 돌려줍니다. 그러면 IRQ 계층이 스레드를 깨웁니다.

::: {.fig src="threaded-irq.svg"}
1차 핸들러는 스레드를 깨우기만 합니다. 스레드 함수는 잠들 수 있고, `IRQF_ONESHOT`이면 그동안 같은 인터럽트가 다시 걸리지 않습니다.
:::

스레드의 본체는 짧습니다.

```{.c file="kernel/irq/manage.c" line="1245"}
static int irq_thread(void *data)
{
	/* ... */
	if (action->handler == irq_forced_secondary_handler)
		sched_set_fifo_secondary(current);
	else
		sched_set_fifo(current);

	if (force_irqthreads() && test_bit(IRQTF_FORCED_THREAD,
					   &action->thread_flags))
		handler_fn = irq_forced_thread_fn;
	else
		handler_fn = irq_thread_fn;
	/* ... */
	while (!irq_wait_for_interrupt(desc, action)) {
		irqreturn_t action_ret;

		action_ret = handler_fn(desc, action);
		if (action_ret == IRQ_WAKE_THREAD)
			irq_wake_secondary(desc, action);

		wake_threads_waitq(desc);
	}
	/* ... */
}
```

읽을 곳은 세 군데입니다.

- `sched_set_fifo()`가 스레드를 `SCHED_FIFO` 우선순위 50으로 만듭니다. 일반 태스크보다 먼저 돌지만, softirq와 달리 **스케줄러가 보는 태스크**입니다. `chrt`로 우선순위를 바꿀 수 있고, 더 급한 실시간 태스크가 있으면 그쪽이 먼저 돕니다.
- 반복문은 `irq_wait_for_interrupt()`에서 잠들었다가, 1차 핸들러가 깨우면 `thread_fn`을 한 번 부르고 다시 잠듭니다.
- 스레드 이름은 `irq/번호-이름`입니다. `ps`에서 `irq/42-sensor`처럼 보입니다.

`IRQF_ONESHOT` 플래그는 스레드 함수가 끝날 때까지 그 IRQ 선을 막아 둡니다. 레벨 트리거 인터럽트에 필요합니다. 장치가 선을 계속 당기고 있는데 원인을 지우는 일이 스레드 함수에 있다면, 선을 막지 않으면 1차 핸들러가 끝나자마자 같은 인터럽트가 또 걸립니다. 1차 핸들러를 `NULL`로 주면 커널이 `IRQ_WAKE_THREAD`만 돌려주는 기본 핸들러를 넣는데, 이때는 `IRQF_ONESHOT`이 없으면 등록이 거부됩니다.

스레드 IRQ가 잘 맞는 곳은 I2C나 SPI 뒤에 있는 장치입니다. 인터럽트 원인을 읽는 것부터 버스 전송이 필요하고, 버스 전송은 잠듭니다. hardirq에서는 할 수 있는 일이 없으므로 1차 핸들러를 비우고 전부 스레드에서 합니다.

## PREEMPT_RT에서 달라지는 것 {#rt}

[6장](ch06.html)에서 본 `PREEMPT_RT` 커널은 "끊을 수 없는 구간"을 없애는 것이 목표입니다. hardirq 핸들러와 softirq는 그 구간의 대표입니다. RT 커널은 둘 다 스레드로 옮깁니다.

**인터럽트 강제 스레드화.** `request_irq()`로 등록한 보통의 핸들러도 `irq/N-이름` 스레드에서 실행됩니다. hardirq에서는 스레드를 깨우는 일만 합니다. `IRQF_NO_THREAD`나 `IRQF_PERCPU`를 준 핸들러(타이머 등)는 예외입니다. 일반 커널에서도 부팅 인자 `threadirqs`로 같은 동작을 켤 수 있습니다.

**softirq가 태스크 컨텍스트에서 실행됩니다.** 인터럽트 복귀 길의 ①이 사라집니다. RT의 `invoke_softirq()`는 `ksoftirqd`를 깨우기만 합니다. softirq는 `ksoftirqd`나, 강제 스레드화된 IRQ 스레드가 `local_bh_enable()`을 부르는 자리에서 실행되고, 그 도중에 선점될 수 있습니다. 타이머 softirq는 일반 태스크에 밀리지 않도록 `ktimers/N`이라는 낮은 우선순위 `SCHED_FIFO` 스레드가 따로 맡습니다.

**`local_bh_disable()`의 뜻이 달라집니다.** 일반 커널에서 이 함수는 `preempt_count`의 softirq 칸을 올립니다. 선점도 함께 꺼지므로 "이 CPU에서 나 말고는 아무도 이 데이터를 못 만진다"는 보장이 따라옵니다. RT에서는 그렇지 않습니다.

```{.c file="kernel/softirq.c" line="188"}
	/* First entry of a task into a BH disabled section? */
	if (!current->softirq_disable_cnt) {
		if (preemptible()) {
			if (IS_ENABLED(CONFIG_PREEMPT_RT_NEEDS_BH_LOCK))
				local_lock(&softirq_ctrl.lock);
			else
				migrate_disable();

			/* Required to meet the RCU bottomhalf requirements. */
			rcu_read_lock();
		} else {
			DEBUG_LOCKS_WARN_ON(this_cpu_read(softirq_ctrl.cnt));
		}
	}
```

분기가 둘입니다. `PREEMPT_RT_NEEDS_BH_LOCK`을 켜면 CPU별 락 `softirq_ctrl.lock`을 잡습니다. 일반 커널과 같은 직렬화가 유지되지만, 이 락 하나에 그 CPU의 모든 softirq 처리와 BH 구간이 줄을 섭니다. 끄면(기본값) `migrate_disable()`만 합니다. 태스크가 다른 CPU로 옮겨지지 않을 뿐, 같은 CPU의 다른 태스크가 끼어들어 같은 CPU별 데이터를 만질 수 있습니다.

`kernel/Kconfig.preempt`의 도움말은 이 락을 "per-CPU BKL"이라고 부릅니다. 한때 커널 전체를 감싸던 큰 락에 빗댄 이름입니다. 락을 없앨 수 있었던 것은 `local_bh_disable()`에 암묵적으로 기대던 코드를 찾아, 보호하려는 데이터마다 `local_lock_nested_bh()` 같은 명시적인 락을 붙이는 작업이 먼저 있었기 때문입니다. "BH를 껐으니 안전하다"는 가정은 RT에서 통하지 않습니다.

## 무엇을 고를까 {#choose}

지금까지 나온 방법을 한 표에 놓습니다.

| | 실행 컨텍스트 | 잠들 수 있나 | 같은 것이 여러 CPU에서 동시에 | 인터럽트 | 언제 고르나 |
|---|---|---|---|---|---|
| hardirq 핸들러 | hardirq | 아니오 | 아니오 (IRQ 하나는 한 번에 한 CPU) | 꺼짐 | 장치 확인, 미룰 수 없는 일 |
| softirq | softirq | 아니오 | 예 | 켜짐 | 네트워크, 블록, 타이머 같은 핵심 서브시스템. 새로 추가하지 않음 |
| 태스크릿 | softirq | 아니오 | 아니오 (다른 태스크릿과는 예) | 켜짐 | 새 코드에 쓰지 않음 |
| BH 워크큐 | softirq | 아니오 | 아니오 (같은 워크는 하나만) | 켜짐 | 스케줄러 지연을 견딜 수 없는 짧은 일 |
| 워크큐 | 프로세스 (`kworker`) | 예 | 아니오 (같은 워크는 하나만) | 켜짐 | 잠들어야 하는 일반적인 뒷일 |
| 스레드 IRQ | 프로세스 (`irq/N`) | 예 | 아니오 | 켜짐 | 인터럽트마다 하는, 잠드는 처리 |
| 전용 커널 스레드 | 프로세스 | 예 | 만들기 나름 | 켜짐 | 계속 돌아야 하는 독립된 루프 |

"같은 워크는 하나만"이라는 칸은 워크큐가 주는 보장입니다. 같은 `work_struct`는 예약이 겹쳐도 한 번만 큐에 들어가고, 실행 중인 워크를 다시 예약하면 다른 CPU에서 겹쳐 돌지 않도록 같은 풀로 보냅니다.

::: {.fig src="choose-flow.svg"}
질문은 둘입니다. 잠들어야 하는가, 그리고 스케줄러를 거치는 지연을 견딜 수 있는가.
:::

대부분의 드라이버에게 답은 워크큐나 스레드 IRQ입니다. softirq 컨텍스트가 정말 필요한 경우는 초당 수십만 번 일어나는 일을 스레드 깨우기 없이 이어서 처리해야 할 때이고, 그런 코드는 이미 네트워크와 블록 계층 안에 있습니다. softirq 열거형 위의 주석도 새 softirq를 만들지 말라고 적어 두었습니다.

::: {.fig src="evolution.svg"}
bottom half 메커니즘의 세대교체. 가로 간격은 실제 시간에 비례하지 않습니다.
:::

::: {.design}
이 역사에서 눈에 띄는 것은 메커니즘이 늘었다가 줄어드는 움직임입니다. 옛 BH가 SMP에서 병목이 되자 softirq와 태스크릿이, 잠들어야 하는 일을 위해 워크큐가, 실시간을 위해 스레드 IRQ가 들어왔습니다. 그때마다 드라이버 작성자가 알아야 할 것이 늘었습니다. BH 워크큐는 반대 방향입니다. 새 메커니즘을 만들지 않고, 이미 있는 워크큐 API에 플래그 하나를 더해 태스크릿의 자리를 덮었습니다. 인터페이스를 하나로 모으고 차이를 속성으로 표현하면, 쓰는 쪽은 배울 것이 줄고 유지하는 쪽은 한 구현만 고치면 됩니다. 다만 500곳이 넘던 태스크릿 사용처를 옮기는 일은 한 릴리스에 끝나지 않습니다. 옛 인터페이스에 "쓰지 마시오"를 적어 새 사용을 막고, 몇 년에 걸쳐 하나씩 바꿔 가는 것이 커널이 인터페이스를 없애는 방식입니다.
:::

## 정리 {#summary}

- 인터럽트 핸들러는 인터럽트를 끈 채 돌고 잠들 수 없습니다. 그래서 급한 일(top half)만 하고 나머지(bottom half)는 미룹니다.
- softirq는 열 개의 정적 번호, 전역 핸들러 배열, CPU별 pending 비트맵으로 이루어집니다. 예약은 비트 하나를 세우는 일입니다.
- softirq는 인터럽트 복귀 길, `local_bh_enable()`, `ksoftirqd` 세 자리에서 실행됩니다. 2ms, 재시작 10회, 재스케줄 요청 가운데 하나에 걸리면 남은 일을 `ksoftirqd`로 넘겨 유저 태스크가 굶지 않게 합니다.
- softirq 핸들러는 인터럽트가 켜진 채, 잠들지 못하는 상태로, 여러 CPU에서 동시에 돕니다.
- 태스크릿은 자기 자신과 직렬화되는 softirq 위의 층이고, v7.3에서는 폐기 중입니다. 대체재는 softirq에서 실행되는 BH 워크큐입니다.
- 워크큐는 일을 `kworker` 스레드에서 실행합니다. 스레드는 워크큐가 아니라 공유 풀에 속하고, 풀은 워커가 잠들 때 다른 워커를 깨워 동시성을 관리합니다.
- 스레드 IRQ는 인터럽트마다 `SCHED_FIFO` 스레드를 둡니다. `PREEMPT_RT`는 모든 핸들러와 softirq를 이 방식으로 태스크 컨텍스트에 옮깁니다.

## 확인 문제 {#quiz}

::: {.q}
태스크가 `spin_lock_bh()`로 락을 쥐고 있는 동안 NIC 인터럽트가 와서 `NET_RX_SOFTIRQ`가 예약되었습니다. 이 softirq는 언제 실행됩니까?

::: {.a}
인터럽트 복귀 길의 `__irq_exit_rcu()`는 `in_interrupt()`를 확인합니다. `spin_lock_bh()`가 `preempt_count`의 softirq 칸을 올려 두었으므로 이 검사가 참이고, softirq는 실행되지 않은 채 pending 비트만 남습니다. 태스크가 `spin_unlock_bh()`를 부르면 `__local_bh_enable_ip()`가 softirq 칸을 내리고, pending이 있음을 보고 그 자리에서 `do_softirq()`를 부릅니다. BH를 꺼 둔 구간이 길면 그만큼 패킷 처리가 늦어집니다.
:::
:::

::: {.q}
`handle_softirqs()`가 pending 비트맵을 지역 변수로 복사한 뒤 원본을 0으로 지우고 나서야 인터럽트를 켜는 이유는 무엇입니까?

::: {.a}
인터럽트를 켠 뒤에는 hardirq가 끼어들어 새 비트를 세울 수 있습니다. 원본을 먼저 지워 두어야 "이번에 처리할 것"(지역 변수)과 "처리 중에 새로 생긴 것"(원본)이 섞이지 않습니다. 순서가 반대라면 그 사이에 선 비트가 지워져 softirq 하나를 잃습니다. 핸들러를 다 부른 뒤 인터럽트를 끄고 원본을 읽으면 새로 생긴 일만 보입니다.
:::
:::

::: {.q}
같은 CPU의 일반 풀에 워크 A, B가 차례로 들어 있고 `kworker`는 하나만 깨어 있습니다. A가 뮤텍스를 기다리며 잠들면 B는 어떻게 실행됩니까?

::: {.a}
A를 실행하던 `kworker`가 `schedule()`로 들어갈 때 스케줄러가 `wq_worker_sleeping()`을 부릅니다. 이 함수가 풀의 `nr_running`을 0으로 내리고 `kick_pool()`을 부릅니다. `need_more_worker()`는 대기 목록이 비어 있지 않고 `nr_running`이 0이면 참이므로, 쉬고 있던 다른 `kworker`가 깨어나 B를 실행합니다. 쉬는 워커가 없으면 새 워커를 만듭니다. A의 워커가 깨어나면 `wq_worker_running()`이 `nr_running`을 다시 올립니다.
:::
:::

::: {.q}
I2C 버스에 연결된 터치 컨트롤러의 드라이버를 씁니다. 인터럽트가 오면 I2C로 좌표를 읽어야 합니다. 어떤 방법을 고르고, 어떤 플래그가 필요합니까?

::: {.a}
I2C 전송은 잠들기 때문에 hardirq나 softirq 컨텍스트에서 할 수 없습니다. 인터럽트마다 하는 처리이므로 스레드 IRQ가 맞습니다. `request_threaded_irq(irq, NULL, thread_fn, IRQF_ONESHOT | 트리거 플래그, …)`로 등록합니다. 1차 핸들러가 `NULL`이면 커널의 기본 핸들러가 `IRQ_WAKE_THREAD`만 돌려줍니다. 장치의 인터럽트 원인은 스레드 함수가 I2C로 읽어야 지워지므로, 그때까지 선을 막아 두는 `IRQF_ONESHOT`이 반드시 필요하고 없으면 등록이 거부됩니다.
:::
:::

## 용어 {#terms}

::: {.terms}
top half / bottom half
:   인터럽트 처리 가운데 인터럽트를 끈 채 바로 하는 부분과, 뒤로 미뤄 인터럽트를 켠 채 하는 부분.

softirq
:   컴파일할 때 번호가 정해진 bottom half. CPU별 pending 비트로 예약되고 여러 CPU에서 동시에 실행된다.

ksoftirqd
:   인터럽트 복귀 길에서 다 처리하지 못한 softirq를 맡는 CPU별 커널 스레드.

태스크릿 (tasklet)
:   softirq 위에서 도는, 같은 것이 동시에 둘 실행되지 않는 bottom half. 폐기 중이다.

BH 워크큐 (BH workqueue)
:   워크 함수를 softirq 컨텍스트에서 실행하는 워크큐. `WQ_BH` 플래그로 만든다.

워크큐 (workqueue)
:   미룬 일을 커널 스레드에서 실행하는 메커니즘. 워크 함수가 잠들 수 있다.

워커 풀 (worker pool)
:   대기 중인 워크의 목록과 그것을 처리하는 `kworker` 스레드의 묶음. 여러 워크큐가 함께 쓴다.

동시성 관리 워크큐 (concurrency managed workqueue)
:   워커가 잠들 때 다른 워커를 깨워, 풀마다 실행 중인 워커 수를 최소로 유지하는 워크큐 구현.

친화성 범위 (affinity scope)
:   unbound 워크큐의 워커가 돌 수 있는 CPU 묶음의 단위.

스레드 IRQ 핸들러 (threaded IRQ handler)
:   인터럽트 전용 커널 스레드에서 실행되는 핸들러.

IRQF_ONESHOT
:   스레드 함수가 끝날 때까지 IRQ 선을 막아 두라는 플래그.

강제 스레드화 (forced threading)
:   일반 핸들러까지 모두 IRQ 스레드에서 실행하게 하는 설정. `PREEMPT_RT`에서는 항상 켜진다.
:::
