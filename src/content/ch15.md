::: {.lead}
우선순위는 "급한 일을 먼저 한다"는 약속입니다. 그런데 락이 끼면 이 약속이 뒤집힐 수 있습니다. 가장 급한 태스크가 덜 급한 태스크 때문에 기다리고, 그 기다림이 언제 끝날지 아무도 말할 수 없게 됩니다. 1997년 화성 탐사선이 바로 이 문제로 재시작을 반복했습니다. 리눅스는 락 주인에게 우선순위를 빌려주는 방법으로 이 문제를 풀어 왔고, v7.3에서는 우선순위가 아니라 실행할 차례 자체를 빌려주는 두 번째 방법이 자라고 있습니다.
:::

::: {.goals}
- 우선순위 역전에서 정말로 위험한 것은 무엇인가?
- `rt_mutex`는 대기자를 어떻게 세우고, 주인의 우선순위를 언제 올리고 내리는가?
- 락 주인이 또 다른 락을 기다리고 있을 때 상속은 어떻게 전파되는가?
- 유저 공간의 뮤텍스는 어떻게 시스템 콜 없이 잡히고, 경합이 생기면 커널의 무엇과 이어지는가?
- 우선순위 상속으로 풀리지 않는 경우는 무엇인가?
- 프록시 실행은 `rq->donor`와 `rq->curr`를 왜 나누는가?
:::

## 가장 급한 태스크가 가장 오래 기다릴 때 {#inversion}

태스크 셋이 있습니다. 우선순위는 H가 가장 높고 M이 중간, L이 가장 낮습니다. H와 L은 같은 락을 쓰고 M은 그 락과 아무 상관이 없습니다.

1. L이 락을 잡습니다.
2. H가 깨어나 L을 선점하고, 같은 락을 요청합니다. L이 쥐고 있으므로 H는 잠듭니다.
3. L이 이어서 실행됩니다. 여기까지는 어쩔 수 없습니다. 락을 공유하는 이상 H는 L의 임계 구역만큼은 기다려야 합니다.
4. M이 깨어납니다. M은 L보다 우선순위가 높으므로 L을 선점합니다.
5. M이 실행되는 동안 L은 락을 풀지 못하고, H는 계속 잠들어 있습니다.

::: {.fig src="inversion-timeline.svg"}
같은 상황의 두 결말. 빨간 빗금이 H가 기다리는 시간입니다.
:::

결과적으로 M이 H보다 먼저 실행됩니다. 이것이 **우선순위 역전**(priority inversion)입니다. 3번까지의 기다림은 길이가 정해져 있습니다. L의 임계 구역이 끝나면 끝납니다. 문제는 4번부터입니다. M이 얼마나 오래 실행될지는 락과 무관하므로 **H의 기다림에 상한이 없습니다.** M 같은 태스크가 여럿이면 더 길어집니다. 커널 문서는 이것을 "상한 없는 우선순위 역전"이라 부르며 앞의 것과 구분합니다.

평균 성능이 중요한 시스템에서는 드물게 생기는 지연으로 끝납니다. 기한이 있는 시스템에서는 고장입니다.

::: {.note title="화성에서 일어난 일"}
1997년 7월 화성에 착륙한 패스파인더는 임무 도중 컴퓨터가 스스로 재시작하는 문제를 겪었습니다. 비행 소프트웨어 책임자 Glenn Reeves가 그해 12월에 밝힌 경위는 이렇습니다. 탐사선은 VxWorks 위에서 여러 태스크를 돌렸습니다. 우선순위가 높은 데이터 분배 태스크 `bc_dist`와 우선순위가 낮은 기상 관측 태스크 `ASI/MET`는 파이프로 데이터를 주고받았고, 그 경로의 `select()` 구현 안에 뮤텍스 세마포어가 하나 있었습니다. `ASI/MET`가 이 뮤텍스를 쥔 순간 중간 우선순위 태스크들이 실행되면, `bc_dist`는 제때 일을 마치지 못했습니다. 버스 주기를 관리하는 최상위 우선순위 태스크 `bc_sched`가 다음 주기를 준비하다 이를 발견하면 오류로 판정했고, 탐사선은 컴퓨터를 재시작했습니다.

VxWorks의 뮤텍스에는 우선순위 상속을 켜는 옵션이 있었고 그 뮤텍스에서는 꺼져 있었습니다. 팀은 지상의 복제 장비에서 문제를 재현한 뒤, 옵션을 켜는 패치를 탐사선에 올려 보내 해결했습니다. 같은 증상은 발사 전 시험에서도 나타났지만 재현되지 않아 뒤로 밀려 있었습니다.
:::

## 두 가지 해법: 상속과 상한 {#protocols}

역전을 끊으려면 L이 락을 쥔 동안 M이 L을 선점하지 못하게 해야 합니다. 방법은 둘입니다.

::: {.fig src="pi-vs-ceiling.svg"}
파란 선은 락 주인 L의 우선순위입니다. 두 방법은 올리는 시점과 올리는 높이가 다릅니다.
:::

**우선순위 상속**(priority inheritance, PI)은 H가 락을 기다리기 시작하는 순간 L의 우선순위를 H만큼 올립니다. L은 H의 우선순위로 임계 구역을 마치고, 락을 풀면서 원래 우선순위로 돌아갑니다. 그림 15-1의 아래쪽이 이 경우입니다. **우선순위 상한**(priority ceiling)은 락마다 "이 락을 쓸 태스크 가운데 가장 높은 우선순위"를 미리 정해 두고, 락을 잡는 태스크를 그 값으로 올립니다.

POSIX 스레드는 둘 다 뮤텍스 속성으로 정의합니다(`PTHREAD_PRIO_INHERIT`, `PTHREAD_PRIO_PROTECT`). 리눅스 커널이 직접 구현하는 것은 상속입니다. 상한은 락마다 올바른 값을 사람이 정해야 하는데, 수만 개의 락을 수천 명이 고치는 코드에서는 그 값을 유지할 수 없습니다. 상속은 설정할 것이 없고, 경합이 없으면 아무 비용도 치르지 않습니다. 대신 구현이 어렵습니다. 이 장의 절반은 그 구현입니다.

## rt_mutex의 자료구조 {#rtmutex}

우선순위 상속을 하는 커널의 락이 **rt_mutex**입니다. 핵심은 세 필드입니다.

```{.c file="include/linux/rtmutex.h" line="23"}
struct rt_mutex_base {
	raw_spinlock_t		wait_lock;
	struct rb_root_cached   waiters __guarded_by(&wait_lock);
	struct task_struct	*owner  __guarded_by(&wait_lock);
};
```

[14장](ch14.html)의 뮤텍스와 견주면 차이가 둘 있습니다. 대기자를 도착한 순서가 아니라 **우선순위순 레드-블랙 트리**(`waiters`)로 세웁니다. 그리고 낙관적 스핀용 큐가 없습니다. `owner`는 14장과 같은 요령으로 포인터의 비트 0을 "대기자 있음" 표시로 씁니다. 경합이 없으면 `owner`를 `NULL`에서 `current`로 바꾸는 `cmpxchg` 한 번으로 잡습니다.

상속에 필요한 나머지 정보는 태스크 쪽에 있습니다.

```{.c file="include/linux/sched.h" line="1248"}
	/* Protection of the PI data structures: */
	raw_spinlock_t			pi_lock;
	/* ... */
#ifdef CONFIG_RT_MUTEXES
	/* PI waiters blocked on a rt_mutex held by this task: */
	struct rb_root_cached		pi_waiters;
	/* Updated under owner's pi_lock and rq lock */
	struct task_struct		*pi_top_task;
	/* Deadlock detection and priority inheritance handling: */
	struct rt_mutex_waiter		*pi_blocked_on;
#endif
```

::: {.fig src="rtmutex-structure.svg"}
락 하나, 주인 하나, 대기자 둘. 대기자 구조체는 잠든 태스크의 커널 스택에 놓이고 트리 두 곳에 동시에 들어갑니다.
:::

- `pi_blocked_on`: 이 태스크가 **기다리는** 락. 잠들어 있지 않으면 `NULL`입니다.
- `pi_waiters`: 이 태스크가 **쥐고 있는** 락들의 대기자 가운데, 락마다 가장 급한 하나(**top waiter**)씩을 모은 트리입니다.
- `pi_top_task`: `pi_waiters`에서 가장 급한 태스크. 지금 이 태스크에게 우선순위를 빌려주고 있는 태스크입니다.

트리가 둘인 이유가 있습니다. 한 태스크는 락을 여러 개 쥘 수 있으므로, 자기에게 걸린 대기자 전체에서 가장 급한 것을 빨리 찾아야 합니다. 락마다 top waiter 하나만 올려 두면 `pi_waiters`의 맨 왼쪽이 곧 답입니다. 대기자 구조체 `rt_mutex_waiter`는 두 트리용 노드(`tree`, `pi_tree`)를 따로 갖고, 정렬 키인 우선순위와 데드라인도 노드마다 복사해 둡니다. 두 트리를 지키는 락이 서로 달라서(`wait_lock`과 주인의 `pi_lock`) 키를 공유할 수 없기 때문입니다.

::: {.old}
옛 자료는 rt_mutex의 대기자를 우선순위순 연결 리스트(`plist`)로 그립니다. v7.3에서는 `rb_root_cached`, 곧 맨 왼쪽 노드를 캐시하는 레드-블랙 트리입니다. 3.14(2014)에서 `SCHED_DEADLINE`이 들어올 때 바뀌었습니다. `plist`는 정수 우선순위 하나로 정렬하는 리스트인데, 데드라인 태스크끼리는 64비트 데드라인으로 순서를 가려야 했습니다. 비교 함수 `rt_waiter_node_less()`는 우선순위를 먼저 보고, 둘 다 데드라인 태스크면 데드라인이 이른 쪽을 앞에 둡니다.
:::

## 올리고 내리기 {#boost}

태스크가 rt_mutex를 잡지 못해 잠들기 직전에 부르는 함수입니다.

```{.c file="kernel/locking/rtmutex.c" line="1212"}
static int __sched task_blocks_on_rt_mutex(struct rt_mutex_base *lock,
					   struct rt_mutex_waiter *waiter,
					   struct task_struct *task,
					   struct ww_acquire_ctx *ww_ctx,
					   enum rtmutex_chainwalk chwalk,
					   struct wake_q_head *wake_q)
	__must_hold(&lock->wait_lock)
{
	struct task_struct *owner = rt_mutex_owner(lock);
	struct rt_mutex_waiter *top_waiter = waiter;
	/* ... */
	raw_spin_lock(&task->pi_lock);
	waiter->task = task;
	waiter->lock = lock;
	waiter_update_prio(waiter, task);
	waiter_clone_prio(waiter, task);

	/* Get the top priority waiter on the lock */
	if (rt_mutex_has_waiters(lock))
		top_waiter = rt_mutex_top_waiter(lock);
	rt_mutex_enqueue(lock, waiter);

	task->pi_blocked_on = waiter;

	raw_spin_unlock(&task->pi_lock);
	/* ... */
	raw_spin_lock(&owner->pi_lock);
	if (waiter == rt_mutex_top_waiter(lock)) {
		rt_mutex_dequeue_pi(owner, top_waiter);
		rt_mutex_enqueue_pi(owner, waiter);

		rt_mutex_adjust_prio(lock, owner);
		if (owner->pi_blocked_on)
			chain_walk = 1;
	} else if (rt_mutex_cond_detect_deadlock(waiter, chwalk)) {
		chain_walk = 1;
	}
	/* ... */
}
```

읽을 곳은 세 군데입니다.

- 앞 절반은 대기자를 락의 트리에 넣고 `pi_blocked_on`에 적습니다. 이 태스크가 무엇을 기다리는지가 이때 기록됩니다.
- 새 대기자가 그 락의 top waiter가 되었을 때만 주인 쪽을 건드립니다. 주인의 `pi_waiters`에서 예전 top waiter를 빼고 새 대기자를 넣은 뒤 `rt_mutex_adjust_prio()`를 부릅니다. 덜 급한 대기자가 줄 뒤에 서는 것은 주인의 우선순위에 영향이 없습니다.
- 주인도 다른 락을 기다리는 중이면(`owner->pi_blocked_on`) 사슬을 따라가야 한다고 표시합니다. [다음 절](#chain)의 주제입니다.

```{.c file="kernel/locking/rtmutex.c" line="535"}
static __always_inline void rt_mutex_adjust_prio(struct rt_mutex_base *lock,
						 struct task_struct *p)
{
	struct task_struct *pi_task = NULL;

	lockdep_assert_held(&lock->wait_lock);
	lockdep_assert(rt_mutex_owner(lock) == p);
	lockdep_assert_held(&p->pi_lock);

	if (task_has_pi_waiters(p))
		pi_task = task_top_pi_waiter(p)->task;

	rt_mutex_setprio(p, pi_task);
}
```

올릴 때와 내릴 때를 구분하는 코드가 없습니다. "지금 나에게 걸린 대기자 가운데 가장 급한 태스크"를 다시 구해 스케줄러에 넘길 뿐입니다. 대기자가 없으면 `pi_task`는 `NULL`이고 원래 우선순위로 돌아갑니다.

```{.c file="kernel/sched/core.c" line="7693"}
void rt_mutex_setprio(struct task_struct *p, struct task_struct *pi_task)
{
	/* ... */
	/* XXX used to be waiter->prio, not waiter->task->prio */
	prio = __rt_effective_prio(pi_task, p->normal_prio);
	/* ... */
	p->pi_top_task = pi_task;
	/* ... */
	prev_class = p->sched_class;
	next_class = __setscheduler_class(p->policy, prio);
	/* ... */
	scoped_guard (sched_change, p, queue_flag) {
		/* ... */
		p->sched_class = next_class;
		p->prio = prio;
	}
	/* ... */
}
```

`task_struct`에는 우선순위가 둘 있습니다. `normal_prio`는 정책과 설정에서 나온 **본래** 값이고, `prio`는 스케줄러가 실제로 쓰는 **유효** 값입니다. 상속은 `prio`만 바꿉니다. `__rt_effective_prio()`는 둘 중 급한 쪽, 곧 숫자가 작은 쪽을 고릅니다. 커널 안에서 `SCHED_FIFO` 80은 `prio` 19이고 nice 0인 일반 태스크는 120입니다. 우선순위의 숫자 체계는 [4장](ch04.html)에 있습니다.

눈여겨볼 것은 `sched_class`도 함께 바뀐다는 점입니다. 일반 태스크 L이 실시간 태스크 H에게서 우선순위 19를 물려받으면, L은 그동안 fair 클래스가 아니라 RT 클래스의 런큐에서 스케줄됩니다. 숫자만 바꾸는 것으로는 부족합니다. fair 클래스 안에서는 `prio` 19가 아무 뜻도 없기 때문입니다.

내리는 쪽은 unlock입니다. `rt_mutex_slowunlock()`은 top waiter를 자기 `pi_waiters`에서 빼고 `rt_mutex_adjust_prio()`로 우선순위를 다시 계산한 **다음에** 그 대기자를 깨웁니다. 순서가 반대면 같은 우선순위의 태스크 둘이 잠깐 함께 실행 가능해집니다. 내린 뒤 깨우기 전에 선점당하면 그것이 새로운 역전이 되므로, 그 사이는 `preempt_disable()`로 막습니다.

## 사슬을 따라가기 {#chain}

L이 락 B를 쥐고 있고, T가 락 A를 쥔 채 B를 기다리고 있습니다. 여기에 H가 A를 요청합니다. T를 H의 우선순위로 올리는 것만으로는 부족합니다. T는 잠들어 있으니 우선순위가 높아도 실행되지 않습니다. 실제로 일해서 락을 풀어야 하는 것은 L입니다. 상속은 L까지 전파되어야 합니다.

::: {.fig src="pi-chain.svg"}
태스크와 락이 번갈아 이어진 **PI 사슬**. 한 태스크는 한 번에 한 락만 기다리므로 사슬은 갈라지지 않습니다.
:::

`rt_mutex_adjust_prio_chain()`이 이 사슬을 걷습니다. 함수 앞의 주석이 한 단계를 요약합니다.

```{.c file="kernel/locking/rtmutex.c" line="659"}
 * [1]	  lock(task->pi_lock);			[R] acquire [P1]
 * [2]	  waiter = task->pi_blocked_on;		[P1]
 * [3]	  check_exit_conditions_1();		[P1]
 * [4]	  lock = waiter->lock;			[P1]
 * [5]	  if (!try_lock(lock->wait_lock)) {	[P1] try to acquire [L]
 *	    unlock(task->pi_lock);		release [P1]
 *	    goto retry;
 *	  }
 * [6]	  check_exit_conditions_2();		[P1] + [L]
 * [7]	  requeue_lock_waiter(lock, waiter);	[P1] + [L]
 * [8]	  unlock(task->pi_lock);		release [P1]
 *	  put_task_struct(task);		release [R]
 * [9]	  check_exit_conditions_3();		[L]
 * [10]	  task = owner(lock);			[L]
 *	  get_task_struct(task);		[L] acquire [R]
 *	  lock(task->pi_lock);			[L] acquire [P2]
 * [11]	  requeue_pi_waiter(tsk, waiters(lock));[P2] + [L]
 * [12]	  check_exit_conditions_4();		[P2] + [L]
 * [13]	  unlock(task->pi_lock);		release [P2]
 *	  unlock(lock->wait_lock);		release [L]
 *	  goto again;
```

`[R]`은 태스크 참조 카운트, `[P1]`과 `[P2]`는 기다리는 태스크와 주인의 `pi_lock`, `[L]`은 락의 `wait_lock`입니다. 한 바퀴가 사슬의 한 칸입니다. [7]에서 락의 트리 안에서 대기자의 자리를 고치고, [11]에서 주인의 `pi_waiters`를 고쳐 주인의 우선순위를 다시 정한 뒤, 주인을 새 `task`로 삼아 처음으로 돌아갑니다. 주인의 `pi_blocked_on`이 `NULL`이면 [3]에서 끝납니다.

이 함수가 긴 까닭은 **단계 사이에 락을 모두 놓기** 때문입니다. 사슬 전체를 한꺼번에 잠그면 간단하지만, 그동안 선점이 꺼지고 사슬이 길수록 지연이 커집니다. 지연을 줄이려고 만든 코드가 지연을 만들면 안 됩니다. 그래서 한 번에 최대 두 개의 락만 쥐고, 다음 칸으로 가기 전에 전부 놓습니다. 그사이 세상이 바뀔 수 있으므로 `check_exit_conditions`가 네 번이나 나옵니다. 락이 풀렸는지, 태스크가 다른 락으로 옮겨 갔는지, 더 급한 대기자가 생겨 더 볼 필요가 없어졌는지를 매번 확인합니다.

사슬을 걷다가 출발한 태스크로 되돌아오면 교착입니다. 이 경우 `-EDEADLK`를 돌려줍니다. 걷는 깊이는 `max_lock_depth`(기본값 1024, `/proc/sys/kernel/max_lock_depth`)로 제한합니다.

::: {.design}
긴 자료구조를 고칠 때 전체를 잠그는 대신 **한 칸씩 잠그고, 놓고, 다시 확인하는** 방식입니다. 대가는 "놓은 사이에 바뀐 것"을 처리하는 코드입니다. 이 함수의 대부분이 그 처리입니다. 하지만 락을 쥐는 시간이 사슬 길이와 무관하게 일정해집니다. 실시간 코드에서는 평균이 아니라 최악의 경우를 묶어야 하므로 이 교환이 맞습니다. 주석에 단계 번호와 그 단계에서 유효한 락을 표로 적어 둔 것도 배울 점입니다. 락 규칙이 복잡한 코드는 "어느 줄에서 무엇이 보호되고 있는가"를 글로 고정해 두어야 다음 사람이 고칠 수 있습니다.
:::

## futex: 유저 공간 락의 재료 {#futex}

지금까지는 커널 안의 락이었습니다. 유저 프로그램의 `pthread_mutex_lock()`은 어떻게 될까요. 락을 잡을 때마다 시스템 콜을 부르면 느립니다. 대부분의 락은 경합이 없는데도 매번 커널을 드나들게 됩니다.

**futex**(fast userspace mutex)는 이 문제를 이렇게 나눕니다. 락의 상태는 유저 공간 메모리의 32비트 워드에 두고, 경합이 없는 동안은 유저 공간에서 원자 연산만으로 잡고 풉니다. 커널은 **기다려야 할 때와 깨워야 할 때만** 부릅니다.

::: {.fig src="futex-paths.svg"}
경합이 없는 락은 커널이 그 존재조차 모릅니다. 커널에는 "이 주소에서 기다리는 스레드들"의 큐만 있습니다.
:::

커널이 제공하는 것은 두 연산입니다. `FUTEX_WAIT`은 "이 주소의 값이 아직 내가 본 값이면 재워 달라", `FUTEX_WAKE`는 "이 주소에서 자는 스레드를 깨워 달라"입니다.

```{.c file="kernel/futex/waitwake.c" line="622"}
int futex_wait_setup(u32 __user *uaddr, u32 val, unsigned int flags,
		     struct futex_q *q, union futex_key *key2,
		     struct task_struct *task)
{
	/* ... */
	ret = get_futex_key(uaddr, flags, &q->key, FUTEX_READ);
	/* ... */
		CLASS(hbr, hbr)(&q->key);
		auto hb = hbr.hb;

		futex_q_lock(q, hb);

		ret = futex_get_value_locked(&uval, uaddr);
		/* ... */
		if (uval != val) {
			futex_q_unlock(hb);
			__release(q->lock_ptr);
			return -EWOULDBLOCK;
		}
		/* ... */
		if (task == current)
			set_current_state(TASK_INTERRUPTIBLE|TASK_FREEZABLE);
		futex_queue(q, hb, task);
	/* ... */
}
```

값 비교가 핵심입니다. 유저 공간에서 "잠겨 있네, 자야겠다"고 판단한 뒤 시스템 콜이 실행되기 전에 락이 풀릴 수 있습니다. 그대로 잠들면 깨워 줄 사람이 없습니다. 그래서 커널은 해시 버킷의 락을 **잡은 채로** 워드를 다시 읽고, 값이 달라졌으면 재우지 않고 돌려보냅니다. 깨우는 쪽도 같은 버킷 락을 잡으므로, 값 확인과 큐 삽입 사이에 깨우기가 끼어들 수 없습니다. [3장](ch03.html)에서 본 "상태를 바꾸고, 조건을 다시 확인하고, 잠든다"와 같은 구조입니다.

futex에는 커널 객체가 따로 없습니다. 주소가 곧 이름입니다. `get_futex_key()`는 주소를 키로 바꿉니다. 한 프로세스 안에서만 쓰는 futex는 (`mm`, 가상 주소)가 키이고, 프로세스 사이에 공유 메모리로 나눠 쓰는 futex는 (inode, 페이지 오프셋)이 키입니다. 키를 해시해 버킷을 고르고, 버킷마다 스핀락과 대기자 리스트가 있습니다.

::: {.old}
많은 자료가 futex 해시 테이블을 "시스템 전체에 하나"로 설명합니다. v7.3에는 `CONFIG_FUTEX_PRIVATE_HASH`가 있어, 스레드를 만든 프로세스는 자기만의 해시 테이블(`struct futex_private_hash`)을 따로 갖고 프로세스 안에서만 쓰는 futex를 거기에 둡니다. 전역 테이블에서는 아무 관계 없는 두 프로세스의 futex가 같은 버킷에 떨어져 서로의 버킷 락을 다툴 수 있었고, 실시간 프로그램에는 이것이 남의 프로세스 때문에 생기는 지연이었습니다. 기본 크기는 스레드 수에 맞춰 커지고, `prctl(PR_FUTEX_HASH, ...)`로 직접 정할 수 있습니다.
:::

시스템 콜도 늘었습니다. 원래의 `futex()`는 연산 번호로 십여 가지 동작을 가르는 다중화 콜입니다. 5.16(2022)에 여러 futex를 한꺼번에 기다리는 `futex_waitv()`가 들어왔고, v7.3에는 동작별로 나눈 `futex_wake()`, `futex_wait()`, `futex_requeue()`도 있습니다. 시스템 콜 설계가 이렇게 바뀌는 이유는 [19장](ch19.html)에서 다룹니다.

락을 쥔 스레드가 죽으면 어떻게 될까요. 커널은 유저 공간 락의 주인을 모르므로 풀어 줄 수 없습니다. **robust futex**는 스레드가 자기가 쥔 락의 목록을 유저 공간에 유지하고 그 머리 주소를 `set_robust_list()`로 커널에 알려 두는 방식입니다. 스레드가 종료할 때 커널이 목록을 따라가며 각 워드에 `FUTEX_OWNER_DIED` 비트를 세우고 대기자를 깨웁니다.

## PI futex: 유저 공간 락에 rt_mutex 붙이기 {#pi-futex}

보통의 futex에서 커널은 누가 락을 쥐고 있는지 모릅니다. 주인을 모르면 우선순위를 빌려줄 수도 없습니다. **PI futex**는 워드에 주인을 적는 규약을 정합니다.

::: {.fig src="pi-futex-state.svg"}
PI futex의 워드와, 경합이 생겼을 때 커널이 만드는 상태. 유저 공간의 락 하나에 커널의 rt_mutex 하나가 붙습니다.
:::

- 잡을 때: 워드를 0에서 **자기 TID**로 바꿉니다. 성공하면 끝입니다. 커널은 관여하지 않습니다.
- 실패하면 `FUTEX_LOCK_PI`를 부릅니다. 커널은 워드에 적힌 TID로 주인 태스크를 찾고, `futex_pi_state`를 만들어 그 안의 rt_mutex 주인을 그 태스크로 둡니다. 그리고 워드에 `FUTEX_WAITERS` 비트를 세운 뒤 호출한 스레드를 그 rt_mutex에서 재웁니다. 이 순간 앞의 두 절에서 본 상속과 사슬 전파가 그대로 일어납니다.
- 풀 때: 워드를 자기 TID에서 0으로 바꿉니다. `FUTEX_WAITERS` 때문에 실패하면 `FUTEX_UNLOCK_PI`를 부르고, 커널이 rt_mutex를 풀며 다음 주인의 TID를 워드에 씁니다.

유저 공간의 빠른 경로는 보통의 futex와 똑같이 원자 연산 한 번입니다. 상속의 비용은 경합이 실제로 생겼을 때만 치릅니다. `pthread_mutexattr_setprotocol()`에 `PTHREAD_PRIO_INHERIT`를 주면 glibc가 이 연산들을 씁니다.

::: {.lab}
PI 뮤텍스를 쥔 스레드의 우선순위가 오르는 것을 봅니다.

```{.c name="pi.c"}
#define _GNU_SOURCE
#include <pthread.h>
#include <sched.h>
#include <stdio.h>
#include <unistd.h>

static pthread_mutex_t m;

static void *low(void *arg)
{
	pthread_mutex_lock(&m);
	printf("L: tid %d\n", gettid());
	sleep(30);			/* 락을 쥔 채 머문다 */
	pthread_mutex_unlock(&m);
	return NULL;
}

static void *high(void *arg)
{
	struct sched_param sp = { .sched_priority = 80 };

	pthread_setschedparam(pthread_self(), SCHED_FIFO, &sp);
	pthread_mutex_lock(&m);		/* 여기서 FUTEX_LOCK_PI */
	pthread_mutex_unlock(&m);
	return NULL;
}

int main(void)
{
	pthread_mutexattr_t a;
	pthread_t l, h;

	pthread_mutexattr_init(&a);
	pthread_mutexattr_setprotocol(&a, PTHREAD_PRIO_INHERIT);
	pthread_mutex_init(&m, &a);
	pthread_create(&l, NULL, low, NULL);
	sleep(1);
	pthread_create(&h, NULL, high, NULL);
	pthread_join(h, NULL);
	pthread_join(l, NULL);
	return 0;
}
```

`SCHED_FIFO`를 쓰려면 root 권한이 필요합니다. 다른 터미널에서 추적을 먼저 켭니다.

```console
# bpftrace -e 'tracepoint:sched:sched_pi_setprio {
      printf("%d: %d -> %d\n", args->pid, args->oldprio, args->newprio); }'

# gcc -O2 -pthread pi.c -o pi && ./pi
L: tid 4321
```

H가 락을 요청하는 순간 `4321: 120 -> 19`가, 30초 뒤 L이 락을 풀 때 `4321: 19 -> 120`이 찍힙니다(TID는 예시). 그사이 `grep -E '^(policy|prio)' /proc/4321/sched`를 보면 `policy`는 0(`SCHED_OTHER`)인데 `prio`가 19입니다. 정책은 그대로이고 유효 우선순위만 빌린 것입니다.
:::

## 상속이 닿지 않는 곳 {#limits}

rt_mutex의 상속에는 한계가 여럿 있습니다.

**일반 커널의 락 대부분은 rt_mutex가 아닙니다.** [14장](ch14.html)의 `struct mutex`에는 상속이 없고, 스핀락은 쥔 동안 선점이 꺼지므로 M이 L을 선점하는 일 자체가 없습니다. 커널 락 전반에 상속이 걸리는 것은 PREEMPT_RT에서입니다. 거기서는 `spinlock_t`, `rwlock_t`, `mutex`가 모두 rt_mutex 위에 구현됩니다. 일반 커널에서 상속을 받는 것은 `rt_mutex`를 직접 쓰는 몇몇 곳과 PI futex입니다.

**주인이 없으면 올려 줄 대상이 없습니다.** 세마포어가 그렇습니다. 읽기-쓰기 락의 읽는 쪽도 그렇습니다. 읽는 쪽은 여럿이고, 쓰는 쪽 하나의 우선순위를 여러 읽는 쪽에 동시에 빌려주는 방법이 마땅치 않습니다. RT 커널의 rwsem에서 기다리는 읽는 쪽이 쓰는 쪽을 올려 줄 수는 있어도 그 반대는 안 되는 이유입니다.

**"우선순위" 하나로 표현되지 않는 태스크가 있습니다.**

```{.c file="kernel/locking/rtmutex.c" line="355"}
static __always_inline int __waiter_prio(struct task_struct *task)
{
	int prio = task->prio;

	if (!rt_or_dl_prio(prio))
		return DEFAULT_PRIO;

	return prio;
}
```

실시간이 아닌 태스크는 nice 값이 무엇이든 모두 `DEFAULT_PRIO`(120) 하나로 취급합니다. fair 클래스에서 태스크가 CPU를 얼마나 받는지는 가중치, cgroup의 몫, [5장](ch05.html)의 lag과 가상 데드라인으로 정해지는데, 이것은 정수 하나로 옮길 수 없습니다. 그래서 일반 태스크끼리의 역전에는 상속이 아무 일도 하지 않습니다. nice 19인 태스크가 락을 쥔 채 CPU를 거의 못 받고 있어도, 그 락을 기다리는 nice -20 태스크는 도울 방법이 없습니다.

데드라인 클래스도 마찬가지입니다. `SCHED_DEADLINE` 태스크는 우선순위가 아니라 (실행 시간, 주기, 데드라인)으로 스케줄됩니다. `rt_mutex_setprio()`는 이 경우 주인이 대기자의 데드라인 매개변수를 빌려 쓰게 합니다(`p->dl.pi_se`). 다만 `Documentation/scheduler/sched-deadline.rst`는 데드라인 상속의 다듬기를 여전히 앞으로의 과제로 적고 있습니다.

RCU에도 같은 문제가 있습니다. 선점 가능한 RCU에서 읽기 구간 안의 태스크가 선점당하면 유예 기간이 끝나지 않습니다. `CONFIG_RCU_BOOST`는 그런 태스크의 우선순위를 rt_mutex를 이용해 올려 줍니다. [16장](ch16.html)에서 다시 나옵니다.

## 프록시 실행: 우선순위가 아니라 차례를 빌려준다 {#proxy}

앞 절의 한계는 "주인의 우선순위 숫자를 고친다"는 접근에서 나옵니다. **프록시 실행**(proxy execution)은 질문을 바꿉니다. 스케줄러가 H를 골랐는데 H가 락을 기다리는 중이라면, **H의 차례에 락 주인 L을 대신 실행하면** 됩니다. L의 우선순위나 가중치는 건드리지 않습니다.

그러려면 그동안 하나였던 것을 둘로 나눠야 합니다.

- **스케줄링 컨텍스트**: 스케줄러가 누구의 차례로 계산하는가. 우선순위, 타임 슬라이스, `vruntime`, 데드라인.
- **실행 컨텍스트**: CPU에서 실제로 누구의 코드가 도는가. 스택, 레지스터, CPU 친화성.

```{.c file="kernel/sched/sched.h" line="1174"}
#ifdef CONFIG_SCHED_PROXY_EXEC
	struct task_struct __rcu	*donor;  /* Scheduling context */
	struct task_struct __rcu	*curr;   /* Execution context */
#else
	union {
		struct task_struct __rcu *donor; /* Scheduler context */
		struct task_struct __rcu *curr;  /* Execution context */
	};
#endif
```

프록시 실행을 끈 빌드에서는 `union`이라 둘이 같은 포인터입니다. [6장](ch06.html)의 `sched_tick()`이 `rq->curr`가 아니라 `donor`의 `task_tick`을 부르던 것이 이 구분 때문입니다. 틱은 "차례의 주인"에게 청구합니다.

::: {.fig src="proxy-contexts.svg"}
H가 뮤텍스를 기다리는 동안 H는 런큐를 떠나지 않습니다. 스케줄러가 H를 고르면 `blocked_on`과 `owner`를 따라가 L을 실행합니다.
:::

구현의 출발점은 **락을 기다리는 태스크를 런큐에서 빼지 않는 것**입니다. `task_struct`의 `blocked_on`이 기다리는 뮤텍스를 가리키고, 태스크는 "막혀 있음" 표시(`is_blocked`)만 단 채 런큐에 남습니다. 그래야 스케줄러가 평소 규칙대로 그 태스크를 고를 수 있습니다.

```{.c file="kernel/sched/core.c" line="7197"}
pick_again:
	assert_balance_callbacks_empty(rq);
	next = pick_next_task(rq, &rf);
	rq->next_class = next->sched_class;
	if (sched_proxy_exec()) {
		struct task_struct *prev_donor = rq->donor;

		rq_set_donor(rq, next);
		next->blocked_donor = NULL;
		if (unlikely(next->is_blocked)) {
			next = find_proxy_task(rq, next, &rf);
			if (!next) {
				zap_balance_callbacks(rq);
				goto pick_again;
			}
			/* ... */
		}
		/* ... */
	} else {
		rq_set_donor(rq, next);
	}
```

`pick_next_task()`가 고른 태스크가 `donor`가 됩니다. 그 태스크가 막혀 있으면 `find_proxy_task()`가 실제로 실행할 태스크를 찾아 `next`를 바꿉니다. 이어지는 컨텍스트 스위치에서 `rq->curr`가 되는 것은 이 바뀐 `next`입니다.

```{.c file="kernel/sched/core.c" line="6930"}
	/* Follow blocked_on chain. */
	for (p = donor; p->is_blocked; p = owner) {
		/* if its PROXY_WAKING, do return migration or run if current */
		struct mutex *mutex = p->blocked_on;
		/* ... */
		guard(raw_spinlock)(&mutex->wait_lock);
		guard(raw_spinlock)(&p->blocked_lock);
		/* ... */
		owner = __mutex_owner(mutex);
		/* ... */
		if (!READ_ONCE(owner->on_rq) || owner->se.sched_delayed) {
			/* XXX Don't handle blocked owners/delayed dequeue yet */
			if (curr_in_chain)
				return proxy_resched_idle(rq);
			__clear_task_blocked_on(p, NULL);
			goto deactivate;
		}

		owner_cpu = task_cpu(owner);
		if (owner_cpu != this_cpu) {
			/* ... */
			if (curr_in_chain)
				return proxy_resched_idle(rq);
			goto migrate_task;
		}
		/* ... */
		owner->blocked_donor = p;
	}
	WARN_ON_ONCE(owner && !owner->on_rq);
	return owner;
```

읽을 곳은 네 군데입니다.

- 반복문이 곧 사슬 걷기입니다. `blocked_on` → 뮤텍스 → `owner`를 주인이 막혀 있지 않을 때까지 따라갑니다. rt_mutex처럼 우선순위를 칸마다 고쳐 쓸 필요가 없습니다. 맨 끝의 실행 가능한 주인을 찾아 실행하면 끝입니다.
- 주인이 **다른 CPU**에 있으면 `migrate_task`로 갑니다. 기다리는 태스크 `p`를 주인의 CPU로 옮깁니다. 스케줄링 컨텍스트는 실행되지 않으므로 CPU 친화성을 무시하고 옮길 수 있고, 실행 컨텍스트인 주인은 제 친화성을 지킵니다.
- 주인이 런큐에 없으면, 곧 I/O 같은 다른 이유로 잠들어 있으면 포기합니다(`XXX` 주석). 이때는 `p`를 런큐에서 빼고 평범하게 재웁니다.
- `owner->blocked_donor = p`는 되돌아가는 링크입니다. 주인이 `mutex_unlock()`을 부르면 이 링크를 보고 락을 가로채기 없이 그 태스크에게 직접 넘깁니다. [14장](ch14.html)의 핸드오프가 여기에 쓰입니다.

v7.3에서 이 기능은 아직 좁게 열려 있습니다.

```{.kconfig file="init/Kconfig" line="942"}
config SCHED_PROXY_EXEC
	bool "Proxy Execution"
	# Avoid some build failures w/ PREEMPT_RT until it can be fixed
	depends on !PREEMPT_RT
	# Need to investigate how to inform sched_ext of split contexts
	depends on !SCHED_CLASS_EXT
	# Not particularly useful until we get to multi-rq proxying
	depends on EXPERT
```

PREEMPT_RT, sched_ext와 함께 켤 수 없고 `EXPERT` 뒤에 있습니다. 대상도 `struct mutex`뿐입니다. `blocked_on`의 타입이 `struct mutex *`이므로 rwsem이나 futex는 아직 따라가지 못합니다. 켠 커널에서는 부팅 인자 `sched_proxy_exec=`로 끄고 켭니다.

::: {.design}
이 기능은 문제를 다시 정의해서 풀린 사례입니다. "락 주인의 우선순위를 얼마로 올릴까"라고 물으면 fair 클래스와 데드라인 클래스에는 답이 없습니다. "급한 태스크의 차례에 누구를 실행할까"라고 물으면 스케줄링 클래스가 무엇이든 답이 같습니다. 클래스마다 따로 상속 규칙을 만들 필요가 없어집니다.

들어오는 방식도 볼 만합니다. 프록시 실행은 여러 해 동안 메일링 리스트에서 다듬어졌고, 한 번에 병합되지 않았습니다. `rq->curr`를 쓰던 코드를 `donor`와 `curr`로 가르는 정리, `blocked_on` 필드, 같은 런큐 안에서만 되는 첫 구현(6.17), CPU를 넘는 이주가 차례로 들어왔습니다. 각 단계는 기능을 끈 빌드의 동작을 그대로 두도록 짜였습니다. 스케줄러의 핵심 경로를 고치는 큰 변경이 리뷰 가능한 크기로 나뉘어 들어오는 전형입니다.
:::

## 정리 {#summary}

- 우선순위 역전의 위험은 중간 우선순위 태스크가 락 주인을 선점해, 높은 우선순위 태스크의 기다림에 상한이 없어지는 데 있습니다.
- 우선순위 상속은 락을 기다리는 태스크가 생길 때 주인의 유효 우선순위(`prio`)를 올리고, 락을 풀 때 다시 계산합니다. 본래 우선순위(`normal_prio`)는 그대로입니다.
- `rt_mutex`는 대기자를 우선순위순 트리로 세우고, 주인은 자기가 쥔 락들의 top waiter를 `pi_waiters`에 모읍니다. 주인의 우선순위는 그 트리의 맨 앞을 따릅니다.
- 주인이 다른 락을 기다리고 있으면 `rt_mutex_adjust_prio_chain()`이 사슬을 따라 전파합니다. 한 칸마다 락을 놓고 다시 확인합니다.
- futex는 락 상태를 유저 공간 워드에 두고, 기다리고 깨울 때만 커널을 부릅니다. PI futex는 워드에 주인의 TID를 적어 커널이 rt_mutex를 붙일 수 있게 합니다.
- 상속은 실시간 우선순위에만 뜻이 있습니다. 일반 태스크와 데드라인 태스크의 스케줄링 속성은 정수 하나로 옮길 수 없습니다.
- 프록시 실행은 스케줄링 컨텍스트(`rq->donor`)와 실행 컨텍스트(`rq->curr`)를 나눠, 기다리는 태스크의 차례에 락 주인을 실행합니다. v7.3에서는 `struct mutex`에 한해 선택 기능으로 들어 있습니다.

## 확인 문제 {#quiz}

::: {.q}
H(높음)와 L(낮음)만 있고 중간 우선순위 태스크가 전혀 없는 시스템에서도 H는 L이 쥔 락을 기다립니다. 이것은 고쳐야 할 문제입니까? 우선순위 상속은 이 경우 무엇을 바꿉니까?

::: {.a}
고칠 수 없고 고칠 필요도 없는 기다림입니다. 락을 공유하는 이상 H는 L의 임계 구역이 끝날 때까지는 기다려야 하고, 그 길이는 L의 코드로 정해집니다. CPU가 하나라면 H가 잠든 뒤 실행할 수 있는 태스크는 L뿐이므로 상속이 있든 없든 결과가 같습니다. 상속이 뜻을 갖는 것은 L을 선점할 수 있는 제삼의 태스크가 있을 때입니다. 상속은 그 태스크가 끼어들지 못하게 해서 기다림을 "L의 임계 구역 길이"로 묶습니다.
:::
:::

::: {.q}
태스크 L이 rt_mutex A와 B를 쥐고 있습니다. A에는 우선순위 30과 50인 대기자가, B에는 우선순위 40인 대기자가 있습니다(숫자가 작을수록 급함). L의 `pi_waiters` 트리에는 무엇이 들어 있고, L의 `prio`는 얼마입니까? L이 A를 풀면 어떻게 됩니까?

::: {.a}
`pi_waiters`에는 락마다 top waiter 하나씩, A의 30과 B의 40이 들어 있습니다. A의 50은 A의 `waiters` 트리에만 있습니다. 맨 왼쪽이 30이므로 `pi_top_task`는 그 태스크이고 L의 `prio`는 `min(normal_prio, 30)`입니다. L이 A를 풀면 `mark_wakeup_next_waiter()`가 A의 top waiter(30)를 L의 `pi_waiters`에서 빼고 `rt_mutex_adjust_prio()`를 부릅니다. 남은 것은 B의 40이므로 L의 `prio`는 40이 됩니다. 원래 값으로 한 번에 돌아가는 것이 아니라, 아직 쥐고 있는 락의 대기자에 맞춰 다시 계산됩니다. 한편 A의 새 주인이 된 태스크의 `pi_waiters`에는 A에 남은 50이 들어갑니다.
:::
:::

::: {.q}
`futex_wait_setup()`은 해시 버킷 락을 잡은 뒤에 유저 공간의 워드를 다시 읽습니다. 락을 잡기 전에 읽고 비교하면 어떤 일이 생길 수 있습니까?

::: {.a}
깨우기를 놓칩니다. 기다리려는 스레드가 워드를 읽어 "아직 잠겨 있다"고 확인한 직후, 버킷 락을 잡기 전에, 다른 스레드가 워드를 0으로 바꾸고 `FUTEX_WAKE`를 부를 수 있습니다. 깨우는 쪽이 버킷을 보면 아직 큐에 아무도 없으므로 그냥 돌아갑니다. 그 뒤에 기다리는 스레드가 큐에 들어가 잠들면 깨워 줄 사람이 없습니다. 버킷 락을 쥔 채 값을 확인하고 큐에 넣으면, 깨우는 쪽은 큐 삽입이 끝난 뒤에야 버킷을 볼 수 있거나, 기다리는 쪽이 바뀐 값을 보고 `-EWOULDBLOCK`으로 돌아가거나 둘 중 하나가 됩니다.
:::
:::

::: {.q}
nice 0인 일반 태스크 둘이 PI futex 하나를 공유합니다. 하나가 락을 쥔 채 선점당해 있고 다른 하나가 `FUTEX_LOCK_PI`로 기다립니다. 락 주인의 `prio`는 바뀝니까? 프록시 실행이 켜진 커널에서 두 태스크가 커널의 `struct mutex`를 다투는 경우와 견주어 보세요.

::: {.a}
바뀌지 않습니다. 대기자의 정렬 키를 만드는 `__waiter_prio()`가 실시간이 아닌 태스크를 모두 `DEFAULT_PRIO`(120)로 취급하고, `rt_mutex_setprio()`는 `min(normal_prio, pi_task->prio)`를 계산하는데 둘 다 120입니다. 주인은 fair 클래스에서 자기 몫대로만 CPU를 받습니다. 프록시 실행에서는 다릅니다. 기다리는 태스크는 런큐에 남아 있다가 fair 클래스가 그 태스크를 고르면(`donor`), 그 차례에 락 주인이 실행됩니다(`curr`). 주인은 자기 몫에 더해 대기자의 몫으로도 실행되므로 락이 더 빨리 풀립니다. 다만 v7.3의 프록시 실행은 `struct mutex`만 따라가므로 futex에는 적용되지 않습니다.
:::
:::

::: {.q}
프록시 실행에서 락 주인이 디스크 I/O를 기다리며 잠들어 있으면 `find_proxy_task()`는 어떻게 합니까? 왜 그 경우에는 대신 실행해 줄 수 없습니까?

::: {.a}
주인의 `on_rq`가 0이므로 `XXX` 주석이 달린 분기로 가서, 기다리는 태스크의 `blocked_on`을 지우고 런큐에서 뺍니다(`deactivate`). 그 태스크는 프록시 실행이 없을 때처럼 평범하게 잠들고, 락이 풀릴 때 깨어납니다. 프록시 실행이 빌려줄 수 있는 것은 CPU를 쓸 차례뿐입니다. 주인이 CPU가 아니라 I/O 완료 같은 사건을 기다리고 있다면 차례를 줘도 실행할 코드가 없습니다.
:::
:::

## 용어 {#terms}

::: {.terms}
우선순위 역전 (priority inversion)
:   높은 우선순위 태스크가 낮은 우선순위 태스크가 쥔 자원 때문에 기다리는 사이, 중간 우선순위 태스크가 먼저 실행되는 현상.

우선순위 상속 (priority inheritance)
:   락을 기다리는 태스크의 우선순위를 락 주인이 임시로 물려받게 하는 규약.

우선순위 상한 (priority ceiling)
:   락마다 미리 정한 우선순위로, 락을 잡는 태스크를 올리는 규약.

rt_mutex
:   우선순위 상속을 지원하는 커널의 잠드는 락. 대기자를 우선순위순 트리로 세운다.

top waiter
:   한 락의 대기자 가운데 가장 급한 태스크.

PI 사슬 (PI chain)
:   기다리는 태스크, 락, 그 주인이 번갈아 이어진 줄. 상속은 이 줄을 따라 전파된다.

futex
:   락 상태를 유저 공간의 워드에 두고, 기다리고 깨울 때만 커널을 부르는 동기화 기본 요소.

PI futex
:   워드에 주인의 TID를 적어, 경합이 생기면 커널이 rt_mutex를 붙여 우선순위 상속을 하는 futex.

robust futex
:   락을 쥔 스레드가 죽었을 때 커널이 대기자에게 알려 줄 수 있게 한 futex.

프록시 실행 (proxy execution)
:   락을 기다리는 태스크의 차례에 락 주인을 대신 실행하는 스케줄러 기능.

스케줄링 컨텍스트 (scheduling context)
:   스케줄러가 차례와 실행 시간을 계산하는 대상. `rq->donor`.

실행 컨텍스트 (execution context)
:   CPU에서 실제로 실행되는 태스크. `rq->curr`.
:::
