::: {.lead}
가상 머신 안의 운영체제는 자기가 하드웨어를 직접 다룬다고 믿습니다. 페이지 테이블을 고치고, 인터럽트를 끄고, 장치 레지스터에 값을 씁니다. 그 믿음을 깨지 않으면서 호스트를 지키려면, 누군가 게스트의 위험한 동작을 가로채 대신 처리해야 합니다. 리눅스는 그 일을 맡을 하이퍼바이저를 따로 만들지 않고, 모듈 하나를 얹어 커널 자신을 하이퍼바이저로 만들었습니다. 이 장은 그 모듈, KVM이 게스트를 실행하고 가로채는 길을 따라갑니다.
:::

::: {.goals}
- 게스트 커널은 어느 특권 수준에서 실행되며, 무엇이 게스트를 멈추게 하는가?
- `ioctl(KVM_RUN)` 한 번은 커널 안에서 어떤 반복문을 도는가?
- vCPU가 호스트의 스레드라는 말은 코드에서 어떻게 드러나는가?
- 게스트의 가상 주소 하나를 물리 주소로 바꾸는 데 메모리를 왜 최대 24번 읽는가?
- posted interrupt는 VM exit 없이 어떻게 게스트에 인터럽트를 넣는가?
- virtio와 vhost, 패스스루는 I/O 경로에서 무엇을 줄이는가?
:::

## 가두고 흉내 내기 {#trap-emulate}

가상화의 고전적인 방법은 **가두고 흉내 내기**(trap and emulate)입니다. 게스트 운영체제를 특권이 낮은 모드에서 실행합니다. 게스트가 특권 명령어를 실행하면 CPU가 예외를 일으키고, 하이퍼바이저가 그 명령어의 효과를 게스트의 가상 상태에만 적용한 뒤 게스트로 돌아갑니다.

이 방법이 성립하려면 시스템 상태를 읽거나 바꾸는 명령어가 낮은 특권에서 빠짐없이 예외를 일으켜야 합니다. x86은 이 조건을 지키지 못했습니다. `POPF`는 링 3에서 실행하면 인터럽트 플래그를 바꾸려는 시도를 예외 없이 무시합니다. `SGDT`나 `SMSW`는 링 3에서도 진짜 시스템 레지스터의 값을 읽어 줍니다. 링 3에 갇힌 게스트 커널은 인터럽트를 껐다고 믿은 채 계속 실행됩니다.

소프트웨어로 이 틈을 메운 방법이 둘 있었습니다. **바이너리 변환**(binary translation)은 게스트 커널 코드를 실행 직전에 훑어 문제가 되는 명령어를 안전한 코드로 바꿉니다. **반가상화**(paravirtualization)는 게스트 커널의 소스를 고쳐 문제의 명령어 대신 하이퍼바이저를 부르게 합니다.

2005년과 2006년에 인텔 VT-x와 AMD-V가 나오면서 CPU가 직접 문제를 풀었습니다. 발상은 링을 건드리지 않고 **축을 하나 더 만드는 것**입니다.

::: {.fig src="vmx-modes.svg"}
VT-x는 링 0–3과 직교하는 두 모드를 더합니다. 게스트 커널은 non-root 모드의 진짜 링 0에서 실행되고, 정해 둔 동작만 VM exit을 일으켜 호스트로 넘어옵니다.
:::

호스트는 **VMX root 모드**에서, 게스트는 **VMX non-root 모드**에서 실행됩니다. non-root 모드에도 링 0–3이 그대로 있어서 게스트 커널은 링 0에서 실행됩니다. 다만 하이퍼바이저가 지정한 명령어와 사건은 **VM exit**을 일으켜 root 모드로 넘어갑니다.

root에서 non-root로 가는 것이 **VM 진입**(VM entry)이고 명령어는 `VMLAUNCH`(처음)와 `VMRESUME`(그다음부터)입니다. 두 모드 사이에서 CPU가 저장하고 복원할 상태는 vCPU마다 하나씩 있는 **VMCS**(virtual machine control structure)에 담깁니다. VMCS에는 게스트 상태, 호스트 상태, 그리고 "무엇이 exit을 일으키는가"를 정하는 실행 제어 필드가 들어 있습니다. AMD의 SVM은 같은 구조를 다른 이름으로 부릅니다. 자료구조는 VMCB, 진입 명령어는 `VMRUN`입니다.

KVM은 두 제조사의 차이를 함수 포인터 구조체 `struct kvm_x86_ops`로 덮습니다. 인텔 쪽 구현이 `arch/x86/kvm/vmx/main.c`의 `vt_x86_ops`, AMD 쪽이 `arch/x86/kvm/svm/svm.c`의 `svm_x86_ops`입니다. 공통 코드는 `kvm_x86_call(vcpu_run)(vcpu, ...)`처럼 부르고, 이 매크로는 스태틱 콜로 펼쳐집니다. 인터페이스 하나에 구현 둘을 끼우는 이 방식은 [25장](ch25.html)의 첫 번째 패턴입니다.

::: {.old}
"x86은 가상화할 수 없는 구조라서 하이퍼바이저가 게스트 코드를 바이너리 변환한다"는 설명은 하드웨어 지원이 나오기 전의 이야기입니다. KVM은 처음부터 VT-x나 AMD-V가 있는 CPU에서만 동작하도록 만들어졌고, 바이너리 변환 코드를 가진 적이 없습니다. v7.3의 KVM이 명령어를 소프트웨어로 해석하는 것은 MMIO 접근처럼 exit 정보만으로는 게스트가 하려던 일을 알 수 없을 때뿐입니다(`arch/x86/kvm/emulate.c`).
:::

## KVM의 구조 {#architecture}

KVM은 커널 모듈입니다. x86에서는 공통 부분인 `kvm.ko`와 제조사별 `kvm-intel.ko` 또는 `kvm-amd.ko`로 나뉩니다. 모듈이 올라가면 문자 장치 `/dev/kvm`이 생기고, 유저 공간은 이 파일에 `ioctl()`을 보내 가상 머신을 만듭니다.

::: {.fig src="kvm-architecture.svg"}
가상 머신 하나는 호스트에서 보면 프로세스 하나입니다. vCPU는 그 프로세스의 스레드이고, 게스트 메모리는 그 프로세스의 가상 메모리입니다.
:::

API는 파일 디스크립터 세 층으로 되어 있습니다.

| 파일 디스크립터 | 얻는 방법 | 대표 ioctl |
|---|---|---|
| 시스템 fd | `open("/dev/kvm")` | `KVM_CREATE_VM`, `KVM_GET_VCPU_MMAP_SIZE` |
| VM fd | `ioctl(kvm, KVM_CREATE_VM)` | `KVM_SET_USER_MEMORY_REGION`, `KVM_CREATE_VCPU`, `KVM_IRQFD` |
| vCPU fd | `ioctl(vm, KVM_CREATE_VCPU)` | `KVM_RUN`, `KVM_SET_REGS`, `KVM_SET_SREGS` |

호출 순서는 다음과 같습니다. 완전한 프로그램이 아니라 뼈대만 보인 것이고, 오류 처리와 레지스터 초기화는 뺐습니다.

```{.c name="kvm-skeleton.c"}
int kvm = open("/dev/kvm", O_RDWR | O_CLOEXEC);
int vm  = ioctl(kvm, KVM_CREATE_VM, 0);

/* 게스트 RAM: 이 프로세스의 평범한 익명 메모리 */
void *mem = mmap(NULL, 2 << 20, PROT_READ | PROT_WRITE,
		 MAP_SHARED | MAP_ANONYMOUS, -1, 0);
struct kvm_userspace_memory_region region = {
	.slot = 0, .guest_phys_addr = 0,
	.memory_size = 2 << 20, .userspace_addr = (__u64)mem,
};
ioctl(vm, KVM_SET_USER_MEMORY_REGION, &region);

int vcpu = ioctl(vm, KVM_CREATE_VCPU, 0);
int size = ioctl(kvm, KVM_GET_VCPU_MMAP_SIZE, 0);
struct kvm_run *run = mmap(NULL, size, PROT_READ | PROT_WRITE,
			   MAP_SHARED, vcpu, 0);

for (;;) {
	ioctl(vcpu, KVM_RUN, 0);		/* 게스트 실행. exit이 나면 돌아온다 */
	switch (run->exit_reason) {
	case KVM_EXIT_IO:   /* run->io.port, run->io.direction ... */ break;
	case KVM_EXIT_HLT:  return 0;
	}
}
```

이 뼈대에 KVM 설계의 핵심 두 가지가 드러나 있습니다.

**게스트 메모리는 호스트 프로세스의 가상 메모리입니다.** `mmap()`으로 잡은 평범한 메모리를 "게스트 물리 주소 0번지부터"라고 등록했을 뿐입니다. 그래서 게스트 메모리는 필요할 때 할당되고, 스왑되고, 큰 페이지로 합쳐집니다. [17장](ch17.html)과 [18장](ch18.html)의 메모리 관리가 그대로 적용됩니다.

**vCPU는 호스트의 스레드입니다.** `KVM_RUN`을 부른 스레드가 곧 그 vCPU입니다. 호스트 스케줄러는 이 스레드를 보통의 태스크로 다룹니다([4장](ch04.html)). 친화성, 우선순위, cgroup의 CPU 제한이 vCPU에 그대로 걸립니다.

`KVM_RUN`을 받는 `kvm_vcpu_ioctl()`(`virt/kvm/kvm_main.c`)은 `vcpu->kvm->mm != current->mm`이면 `-EIO`로 거절합니다. 게스트 메모리가 있는 주소 공간에서만 vCPU를 돌릴 수 있다는 뜻입니다. 이어서 `vcpu->mutex`를 잡아 한 vCPU를 한 번에 한 스레드만 실행하게 합니다.

유저 공간에 남은 몫은 **VMM**(virtual machine monitor)이 맡습니다. QEMU가 대표적입니다. VMM은 게스트 메모리를 잡고, 가상 장치를 흉내 내고, 디스크 이미지와 네트워크를 호스트의 파일과 소켓에 잇습니다. KVM은 CPU와 메모리의 가상화, 그리고 자주 쓰이는 몇 가지 장치(인터럽트 컨트롤러, 타이머)만 맡습니다.

::: {.design}
KVM은 하이퍼바이저를 새로 쓰지 않았습니다. 하이퍼바이저에 필요한 것은 스케줄러, 메모리 관리자, 장치 드라이버, 전원 관리인데 리눅스에는 이미 다 있습니다. vCPU를 스레드로, 게스트 메모리를 가상 메모리로 정의하자 그 전부가 따라왔습니다. 스케줄러가 바뀌면 vCPU가, 큰 페이지 처리가 개선되면 게스트 메모리가 그 혜택을 받습니다. 새로 만든 부분은 "CPU를 게스트 모드로 넣고 빼는 일"에 한정되었습니다. 새 개념을 기존 추상화에 끼워 맞출 수 있는지 먼저 따져 보면 만들어야 할 코드의 양이 달라집니다.
:::

## vCPU 실행 루프 {#run-loop}

`KVM_RUN`은 `kvm_arch_vcpu_ioctl_run()`을 거쳐 `vcpu_run()`에 닿습니다. 이 함수가 vCPU의 주 반복문입니다.

```{.c file="arch/x86/kvm/x86.c" line="8635"}
static int vcpu_run(struct kvm_vcpu *vcpu)
{
	int r;

	vcpu->run->exit_reason = KVM_EXIT_UNKNOWN;

	for (;;) {
		/* ... */
		if (kvm_vcpu_running(vcpu)) {
			r = vcpu_enter_guest(vcpu);
		} else {
			r = vcpu_block(vcpu);
		}

		if (r <= 0)
			break;

		/* ... */
		if (__xfer_to_guest_mode_work_pending()) {
			kvm_vcpu_srcu_read_unlock(vcpu);
			r = kvm_xfer_to_guest_mode_handle_work(vcpu);
			kvm_vcpu_srcu_read_lock(vcpu);
			if (r)
				return r;
		}
	}

	return r;
}
```

읽을 곳은 세 군데입니다.

- vCPU가 실행할 수 있는 상태면 `vcpu_enter_guest()`로 게스트에 들어갑니다. 게스트가 `HLT`로 멈춘 상태면 `vcpu_block()`으로 스레드를 재웁니다.
- 반환값이 규약입니다. **1이면 커널 안에서 처리가 끝났으니 계속 돌고, 0 이하면 유저 공간으로 나갑니다.**
- 한 바퀴 돌 때마다 `__xfer_to_guest_mode_work_pending()`으로 스레드 플래그를 봅니다.

마지막 항목이 "vCPU는 스레드"라는 말의 실체입니다. 호출되는 함수를 보겠습니다.

```{.c file="kernel/entry/virt.c" line="5"}
static int xfer_to_guest_mode_work(unsigned long ti_work)
{
	do {
		int ret;

		if (ti_work & (_TIF_SIGPENDING | _TIF_NOTIFY_SIGNAL))
			return -EINTR;

		if (ti_work & (_TIF_NEED_RESCHED | _TIF_NEED_RESCHED_LAZY))
			schedule();
		/* ... */
		ti_work = read_thread_flags();
	} while (ti_work & XFER_TO_GUEST_MODE_WORK);
	return 0;
}
```

[6장](ch06.html)의 `__exit_to_user_mode_loop()`와 같은 모양입니다. 커널은 게스트 모드로 들어가는 일을 유저 모드로 돌아가는 일과 같은 종류로 취급합니다. 호스트의 틱이 게스트를 끊는 과정도 이것으로 설명됩니다. 게스트 실행 중에 호스트 인터럽트가 오면 VM exit이 나고, 호스트 핸들러가 `TIF_NEED_RESCHED`를 세우고, 반복문의 이 자리에서 vCPU 스레드가 CPU를 내놓습니다.

### 진입과 exit

`vcpu_enter_guest()`는 밀린 요청을 처리하고, 주입할 인터럽트를 정하고, 선점과 인터럽트를 끈 뒤 제조사 코드를 부릅니다. VMX에서는 `vmx_vcpu_run()`을 거쳐 어셈블리 `__vmx_vcpu_run()`에 닿습니다. 호스트 레지스터를 스택에 넣고 게스트 레지스터를 불러온 다음, 이 몇 줄이 실행됩니다.

```{.asm file="arch/x86/kvm/vmx/vmenter.S" line="89"}
	/* Check @flags to see if VMLAUNCH or VMRESUME is needed. */
	testl $KVM_ENTER_VMRESUME, (%_ASM_SP)
	jz .Lvmlaunch

	/* ... */
.Lvmresume:
	vmresume
	jmp .Lvmfail

.Lvmlaunch:
	vmlaunch
	jmp .Lvmfail

	_ASM_EXTABLE(.Lvmresume, .Lfixup)
	_ASM_EXTABLE(.Lvmlaunch, .Lfixup)

SYM_INNER_LABEL_ALIGN(vmx_vmexit, SYM_L_GLOBAL)

	/* Restore unwind state from before the VMRESUME/VMLAUNCH. */
	UNWIND_HINT_RESTORE
	ENDBR

	/* Temporarily save guest's RDI. */
	push %_ASM_DI
```

`vmresume` 다음 줄이 `jmp .Lvmfail`입니다. 진입에 성공하면 CPU는 다음 줄로 가지 않고 게스트의 RIP로 건너뜁니다. VM exit이 나면 CPU는 VMCS의 `HOST_RIP` 필드에 적힌 주소에서 호스트 실행을 이어 가는데, KVM은 이 필드에 `vmx_vmexit` 레이블의 주소를 넣어 둡니다. 호스트에서 보면 `vmresume`를 실행했더니 한참 뒤에 바로 아래 레이블로 돌아온 셈입니다. 다음 줄로 넘어갔다면 진입 자체가 실패한 것입니다.

exit이 나면 `vmx_vcpu_enter_exit()`가 VMCS에서 exit 사유를 읽고, `vmx_handle_exit()`가 표에서 핸들러를 찾아 부릅니다.

```{.c file="arch/x86/kvm/vmx/vmx.c" line="6329"}
static int (*kvm_vmx_exit_handlers[])(struct kvm_vcpu *vcpu) = {
	[EXIT_REASON_EXCEPTION_NMI]           = handle_exception_nmi,
	[EXIT_REASON_EXTERNAL_INTERRUPT]      = handle_external_interrupt,
	/* ... */
	[EXIT_REASON_IO_INSTRUCTION]          = handle_io,
	[EXIT_REASON_CR_ACCESS]               = handle_cr,
	/* ... */
	[EXIT_REASON_CPUID]                   = kvm_emulate_cpuid,
	/* ... */
	[EXIT_REASON_MSR_WRITE]               = kvm_emulate_wrmsr,
	/* ... */
	[EXIT_REASON_HLT]                     = kvm_emulate_halt,
	/* ... */
	[EXIT_REASON_EPT_VIOLATION]	      = handle_ept_violation,
	/* ... */
};
```

이 표가 "게스트가 혼자 할 수 없는 일"의 목록입니다. `CPUID`, 제어 레지스터와 MSR 접근, 포트 I/O, `HLT`, 2단계 페이지 테이블에 매핑이 없는 메모리 접근이 들어 있습니다.

::: {.fig src="run-loop.svg"}
`KVM_RUN` 한 번이 도는 길. exit의 대부분은 커널 안에서 끝나 게스트로 되돌아가고, 유저 공간의 도움이 필요한 exit만 `ioctl()`에서 복귀합니다.
:::

exit이 끝나는 길은 셋입니다.

1. **빠른 경로.** `vmx_exit_handlers_fastpath()`가 인터럽트를 켜기도 전에 처리하고 곧바로 다시 진입합니다. v7.3에서 대상은 타이머를 맞추는 `MSR_IA32_TSC_DEADLINE` 쓰기, IPI를 보내는 x2APIC ICR 쓰기, 선점 타이머 만료, `HLT`, `INVD`입니다.
2. **커널 안에서 처리.** 핸들러가 1을 돌려주면 `vcpu_run()`이 한 바퀴 더 돕니다. `CPUID`나 EPT 위반 대부분이 여기서 끝납니다.
3. **유저 공간으로.** 핸들러가 `kvm_run` 구조체에 사유를 적고 0을 돌려주면 `ioctl()`이 복귀합니다.

`kvm_run`은 vCPU fd를 `mmap()`해서 얻는, 커널과 VMM이 함께 보는 페이지입니다. 포트 I/O가 그 길을 어떻게 타는지 보겠습니다.

```{.c file="arch/x86/kvm/x86.c" line="5343"}
static int emulator_pio_in_out(struct kvm_vcpu *vcpu, int size,
			       unsigned short port, void *data,
			       unsigned int count, bool in)
{
	/* ... */
	for (i = 0; i < count; i++) {
		if (in)
			r = kvm_io_bus_read(vcpu, KVM_PIO_BUS, port, size, data);
		else
			r = kvm_io_bus_write(vcpu, KVM_PIO_BUS, port, size, data);

		if (r) {
			if (i == 0)
				goto userspace_io;
			/* ... */
		}

		data += size;
	}
	return 1;

userspace_io:
	/* ... */
	vcpu->run->exit_reason = KVM_EXIT_IO;
	vcpu->run->io.direction = in ? KVM_EXIT_IO_IN : KVM_EXIT_IO_OUT;
	/* ... */
	vcpu->run->io.port = port;
	return 0;
}
```

먼저 커널 안에 등록된 장치(`kvm_io_bus`)에 물어봅니다. 그 포트를 맡은 장치가 커널에 있으면 1을 돌려주고 끝납니다. 없으면 `kvm_run`에 포트 번호와 방향을 적고 0을 돌려줍니다. 앞의 뼈대 코드에서 `run->exit_reason`이 `KVM_EXIT_IO`가 되는 순간입니다.

::: {.design}
VM exit 한 번의 비용은 어디서 끝나느냐에 따라 크게 다릅니다. 유저 공간까지 가면 `ioctl()` 복귀, VMM의 처리, 다시 `ioctl()` 진입이 더해집니다. KVM이 인터럽트 컨트롤러와 타이머를 커널 안에 구현하고 타이머 MSR 쓰기를 빠른 경로로 올린 것은 이 exit들이 자주 나기 때문입니다. 드물게 쓰이는 장치는 유저 공간에 둡니다. 거기서는 버그가 나도 VMM 프로세스 하나만 죽습니다. 자주 가는 길만 특권 코드에 두고 나머지는 밖으로 내보낸다는 기준은 다른 시스템의 경계를 정할 때도 쓸 수 있습니다.
:::

::: {.lab}
KVM이 켜져 있는지, 어떤 exit이 많이 나는지 봅니다. 게스트가 하나 이상 돌고 있어야 합니다.

## 메모리 가상화 {#memory}

게스트 안에는 주소가 두 종류 있습니다. 게스트의 프로세스가 쓰는 **게스트 가상 주소**(GVA)와, 게스트 커널이 물리 메모리라고 믿는 **게스트 물리 주소**(GPA)입니다. 게스트의 페이지 테이블은 GVA를 GPA로 바꿉니다. 그런데 GPA는 진짜 물리 주소가 아닙니다. 호스트가 GPA를 **호스트 물리 주소**(HPA)로 한 번 더 바꿔야 합니다.

### memslot: GPA에서 호스트 가상 주소로

`KVM_SET_USER_MEMORY_REGION`으로 등록한 구간 하나가 **memslot**입니다. memslot은 "GPA의 이 범위는 VMM 프로세스의 이 가상 주소 범위에 있다"는 대응입니다. 변환은 덧셈 하나입니다.

```{.c file="include/linux/kvm_host.h" line="1923"}
static inline unsigned long
__gfn_to_hva_memslot(const struct kvm_memory_slot *slot, gfn_t gfn)
{
	/* ... */
	unsigned long offset = gfn - slot->base_gfn;
	offset = array_index_nospec(offset, slot->npages);
	return slot->userspace_addr + offset * PAGE_SIZE;
}
```

`gfn`은 게스트 페이지 프레임 번호, 반환값은 호스트 가상 주소(HVA)입니다. HVA에서 HPA로 가는 마지막 단계는 호스트의 보통 페이지 테이블이 맡습니다. 그 페이지가 아직 없으면 호스트의 페이지 폴트 처리가 만들어 줍니다.

### 섀도 페이지 테이블에서 EPT로

CPU의 MMU가 페이지 테이블을 한 벌만 따라갈 수 있던 시절에는 KVM이 **섀도 페이지 테이블**(shadow page table)을 만들었습니다. 게스트의 페이지 테이블(GVA→GPA)과 memslot(GPA→HPA)을 합성해 GVA→HPA 테이블을 따로 만들고, CPU에는 이것을 줍니다. 게스트가 자기 페이지 테이블을 고칠 때마다 KVM이 가로채 섀도 쪽을 맞춰야 하므로 exit이 많고 코드가 복잡합니다.

지금의 CPU는 테이블 두 벌을 직접 따라갑니다. 인텔의 **EPT**(extended page table), AMD의 NPT이고, KVM은 둘을 묶어 TDP(two-dimensional paging)라고 부릅니다. 게스트는 자기 CR3와 페이지 테이블을 exit 없이 마음대로 고칩니다. 호스트는 GPA→HPA 테이블 하나만 관리합니다.

대가는 TLB 미스의 비용입니다.

::: {.fig src="two-dim-walk.svg"}
4단계 게스트 테이블과 4단계 EPT의 2차원 페이지 워크. 게스트 테이블의 엔트리 주소도 GPA이므로, 그것을 읽으려 할 때마다 EPT를 처음부터 다시 따라가야 합니다.
:::

게스트의 4단계 테이블을 한 단계 내려갈 때마다 "다음 테이블이 있는 GPA"를 HPA로 바꿔야 하고, 그 변환에 EPT 4단계가 듭니다. 마지막에 나온 데이터 페이지의 GPA도 EPT로 한 번 더 바꿉니다. 합치면 5 × 4번의 EPT 참조에 게스트 테이블 읽기 4번, 최악의 경우 24번입니다. 가상화하지 않았을 때는 4번입니다. 그래서 가상화 환경에서는 TLB가 한 엔트리로 덮는 범위를 넓히는 큰 페이지가 더 중요합니다.

### EPT 위반 처리

게스트가 EPT에 매핑이 없는 GPA를 건드리면 `EXIT_REASON_EPT_VIOLATION`으로 exit이 납니다. 호스트의 페이지 폴트와 같은 역할입니다. `handle_ept_violation()`에서 시작해 MMU의 다음 함수에 닿습니다.

```{.c file="arch/x86/kvm/mmu/mmu.c" line="4941"}
static int kvm_tdp_mmu_page_fault(struct kvm_vcpu *vcpu,
				  struct kvm_page_fault *fault)
{
	int r;
	/* ... */
	r = kvm_mmu_faultin_pfn(vcpu, fault, ACC_ALL);
	if (r != RET_PF_CONTINUE)
		return r;

	r = RET_PF_RETRY;
	read_lock(&vcpu->kvm->mmu_lock);

	if (is_page_fault_stale(vcpu, fault))
		goto out_unlock;

	r = kvm_tdp_mmu_map(vcpu, fault);

out_unlock:
	kvm_mmu_finish_page_fault(vcpu, fault, r);
	read_unlock(&vcpu->kvm->mmu_lock);
	return r;
}
```

읽을 곳은 세 군데입니다.

- `kvm_mmu_faultin_pfn()`이 memslot으로 HVA를 구하고 호스트의 메모리 관리에 그 페이지를 요청합니다. 이때 호스트 쪽 페이지 폴트가 처리될 수 있습니다.
- `mmu_lock`을 **읽기**로 잡습니다. 여러 vCPU가 동시에 폴트를 처리할 수 있다는 뜻입니다. 엔트리 설치는 원자적 비교-교환으로 하고 테이블 해제는 RCU로 미룹니다. 이것이 **TDP MMU**입니다. vCPU와 메모리가 많은 게스트를 위해 따로 쓴 구현으로, 5.10에 들어와 5.15부터 64비트 x86의 기본이 되었습니다.
- `is_page_fault_stale()`은 락을 잡기 전에 구한 페이지가 그 사이에 무효가 되지 않았는지 확인합니다.

호스트가 게스트 메모리를 회수하거나 옮길 때는 반대 방향의 알림이 필요합니다. KVM은 VMM의 `mm`에 **MMU 알림자**(mmu notifier)를 등록해 둡니다. 호스트가 어떤 가상 주소 범위의 매핑을 없애려 하면 `kvm_mmu_notifier_invalidate_range_start()`가 불리고, KVM은 그 범위에 해당하는 EPT 엔트리를 지웁니다. 게스트 메모리가 스왑되거나 이주될 수 있는 것은 이 연결 덕분입니다.

::: {.note title="더티 로깅과 guest_memfd"}
라이브 마이그레이션은 게스트를 멈추지 않고 메모리를 복사하므로, 복사한 뒤에 게스트가 다시 쓴 페이지를 알아야 합니다. memslot에 `KVM_MEM_LOG_DIRTY_PAGES` 플래그를 켜면 KVM이 쓰기를 추적해 `KVM_GET_DIRTY_LOG`로 비트맵을 내줍니다.

기밀 VM에서는 VMM이 게스트 메모리를 읽을 수 있다는 점이 문제가 됩니다. `KVM_CREATE_GUEST_MEMFD`로 만드는 **guest_memfd**는 VM에 묶인 메모리 파일이고, 게스트의 비공개 메모리를 유저 공간 매핑 없이 뒷받침합니다. 6.8에 들어왔습니다.
:::

## 인터럽트 가상화 {#interrupts}

게스트도 타이머 인터럽트와 장치 인터럽트를 받아야 합니다. [9장](ch09.html)에서 본 로컬 APIC를 KVM은 `arch/x86/kvm/lapic.c`에서 소프트웨어로 흉내 냅니다. vCPU마다 가상 LAPIC가 있고, 요청 레지스터(IRR)와 처리 중 레지스터(ISR)를 메모리에 둡니다.

가상 인터럽트를 게스트에 넣는 가장 단순한 방법은 다음과 같습니다.

1. 가상 LAPIC의 IRR에 벡터를 기록하고 vCPU에 `KVM_REQ_EVENT` 요청을 겁니다.
2. 대상 vCPU가 게스트 안에 있으면 `kvm_vcpu_kick()`으로 그 CPU에 IPI를 보내 강제로 exit시킵니다.
3. 다음 진입 직전에 `vcpu_enter_guest()`가 요청을 보고 VMCS의 진입 인터럽트 필드에 벡터를 씁니다.
4. VM 진입과 함께 CPU가 게스트의 IDT를 따라 핸들러를 실행합니다.

인터럽트 하나에 exit이 한 번 들고, 게스트가 EOI를 쓸 때 또 한 번 듭니다. 인터럽트가 잦은 네트워크 부하에서는 이 비용이 처리량을 깎습니다.

**APICv**는 이 일을 CPU에 맡깁니다. 게스트의 LAPIC 레지스터를 **가상 APIC 페이지**라는 메모리 한 장에 두고, CPU가 non-root 모드 안에서 그 페이지의 IRR을 읽어 인터럽트를 전달하고 EOI도 처리합니다. 여기에 **posted interrupt**가 더해지면 주입에도 exit이 필요 없습니다.

vCPU마다 **PI 디스크립터**(`struct pi_desc`, `arch/x86/include/asm/posted_intr.h`)가 하나 있고 VMCS가 그 주소를 압니다. 캐시 라인 하나 크기인 이 구조체에는 벡터 256개에 대한 비트맵 `pir`, 알림이 이미 나갔는지를 나타내는 ON 비트, 그리고 **통지 벡터** `nv`가 들어 있습니다. 보내는 쪽 코드는 짧습니다.

```{.c file="arch/x86/kvm/vmx/common.h" line="167"}
static inline void __vmx_deliver_posted_interrupt(struct kvm_vcpu *vcpu,
						  struct pi_desc *pi_desc, int vector)
{
	if (pi_test_and_set_pir(vector, pi_desc))
		return;

	/* If a previous notification has sent the IPI, nothing to do.  */
	if (pi_test_and_set_on(pi_desc))
		return;
	/* ... */
	kvm_vcpu_trigger_posted_interrupt(vcpu, POSTED_INTR_VECTOR);
}
```

PIR에 벡터 비트를 세우고, ON 비트를 세우고, 대상 CPU에 통지 벡터(`POSTED_INTR_VECTOR`, 0xf2)로 IPI를 보냅니다. non-root 모드의 CPU는 들어온 인터럽트의 벡터가 VMCS에 적힌 통지 벡터와 같으면 **exit하지 않습니다.** PIR을 가상 IRR에 합치고 게스트에 인터럽트를 전달합니다. 대상 vCPU가 게스트 밖에 있었다면 다음 진입 직전에 KVM이 PIR을 직접 합칩니다(`sync_pir_to_irr`).

::: {.fig src="interrupt-injection.svg"}
위는 exit을 거치는 주입, 아래는 posted interrupt입니다. 아래쪽에서는 받는 CPU가 게스트 모드를 떠나지 않습니다.
:::

AMD의 대응 기능은 AVIC이고 구현은 `arch/x86/kvm/svm/avic.c`에 있습니다.

VMM이나 다른 커널 서브시스템이 KVM과 인터럽트를 주고받는 통로는 eventfd입니다. **irqfd**는 "이 eventfd에 신호가 오면 게스트에 이 인터럽트를 넣어라"이고, **ioeventfd**는 반대로 "게스트가 이 주소에 쓰면 이 eventfd에 신호를 보내라"입니다.

ioeventfd로 등록된 주소에 게스트가 쓰면 exit은 나지만, KVM은 유저 공간으로 돌아가지 않고 `ioeventfd_write()`(`virt/kvm/eventfd.c`)에서 `eventfd_signal()`만 부른 뒤 게스트를 다시 실행합니다. 그 eventfd를 누가 기다리는지는 KVM이 알 필요가 없습니다. 다음 절의 virtio와 vhost가 이 통로를 씁니다.

## I/O 가상화 {#io}

게스트에 장치를 보여 주는 방법은 넷입니다. 뒤로 갈수록 exit이 줄고, 게스트와 호스트가 더 많이 엮입니다.

::: {.fig src="io-paths.svg"}
패킷 하나를 내보낼 때 거치는 층. 에뮬레이션은 레지스터 접근마다 VMM까지 올라가고, 패스스루는 호스트를 거치지 않습니다.
:::

**에뮬레이션.** VMM이 실제로 있는 장치(예: 인텔 e1000)의 레지스터를 흉내 냅니다. 게스트는 원래 드라이버를 그대로 씁니다. 대신 레지스터 접근 하나하나가 exit이고 대부분 유저 공간까지 갑니다.

**virtio.** 게스트가 가상 머신 안에 있다는 사실을 숨기지 않습니다. 실제 장치를 흉내 내는 대신 가상화에 맞게 설계한 장치 규격을 정하고, 게스트에는 그 드라이버를 넣습니다. 핵심 자료구조는 게스트와 장치가 공유하는 메모리 위의 큐, **virtqueue**입니다.

```{.c file="include/uapi/linux/virtio_ring.h" line="104"}
struct vring_desc {
	__virtio64 addr;
	__virtio32 len;
	__virtio16 flags;
	__virtio16 next;
};

struct vring_avail {
	__virtio16 flags;
	__virtio16 idx;
	__virtio16 ring[];
};

/* u32 is used here for ids for padding reasons. */
struct vring_used_elem {
	/* Index of start of used descriptor chain. */
	__virtio32 id;
	/* Total length of the descriptor chain which was used (written to) */
	__virtio32 len;
};
```

::: {.fig src="virtqueue.svg"}
분할(split) virtqueue의 세 영역. 드라이버는 avail 링에만 쓰고 장치는 used 링에만 씁니다. 양쪽이 같은 칸을 고치는 일이 없어서 락이 필요 없습니다.
:::

- **디스크립터 테이블**: 버퍼의 주소(GPA)와 길이를 적은 칸들입니다. `next`로 이어 사슬을 만듭니다.
- **avail 링**: 드라이버가 "이 사슬을 처리해 달라"고 사슬의 머리 번호를 넣는 곳입니다.
- **used 링**: 장치가 "이 사슬을 다 썼다"고 돌려주는 곳입니다. 원소가 위의 `vring_used_elem`입니다.

데이터는 공유 메모리로 오가므로 exit이 필요 없습니다. exit이 필요한 순간은 "큐에 새 일이 있다"고 알릴 때뿐이고, 이것을 **킥**(kick)이라고 합니다. 킥조차 매번 하지 않습니다.

```{.c file="drivers/virtio/virtio_ring.c" line="843"}
static bool virtqueue_kick_prepare_split(struct vring_virtqueue *vq)
{
	u16 new, old;
	bool needs_kick;
	/* ... */
	old = vq->split.avail_idx_shadow - vq->num_added;
	new = vq->split.avail_idx_shadow;
	vq->num_added = 0;
	/* ... */
	if (vq->event) {
		needs_kick = vring_need_event(vring_read_split_avail_event(vq),
					      new, old);
	} else {
		needs_kick = !(vq->split.vring.used->flags &
					cpu_to_virtio16(vq->vq.vdev,
						VRING_USED_F_NO_NOTIFY));
	}
	END_USE(vq);
	return needs_kick;
}
```

장치가 이미 큐를 처리하는 중이면 알릴 필요가 없습니다. 장치는 used 링의 `flags`에 `VRING_USED_F_NO_NOTIFY`를 세워 "지금은 알리지 마시오"라고 표시하거나, "avail 인덱스가 이 값을 넘으면 알려 달라"는 문턱을 적어 둡니다(`vq->event`가 참인 경우). 드라이버는 버퍼 여러 개를 넣고 킥은 필요할 때 한 번만 합니다. 부하가 높을수록 버퍼당 exit 수가 줄어듭니다. [12장](ch12.html)의 NAPI와 같은 발상입니다.

**vhost.** virtio에서도 장치 쪽 처리는 VMM 프로세스가 합니다. 킥이 오면 VMM으로 나가고, VMM이 다시 시스템 콜로 호스트의 네트워크 스택에 패킷을 넣습니다. vhost는 virtqueue의 장치 쪽을 호스트 커널로 옮깁니다(`drivers/vhost/`). 킥은 ioeventfd로 받고 완료는 irqfd로 알립니다. 데이터 경로에서 VMM이 빠집니다.

**패스스루.** 실제 장치를 게스트에 통째로 줍니다. 게스트는 그 장치의 진짜 드라이버를 쓰고, 장치 레지스터에 접근해도 exit이 나지 않습니다. 이때 장치가 DMA로 호스트의 아무 메모리나 읽고 쓰지 못하게 막는 것이 **IOMMU**입니다. 장치가 내는 주소를 게스트의 메모리로만 변환합니다. 호스트 쪽 틀은 VFIO입니다(`drivers/vfio/`). 장치 하나를 여러 게스트에 나눠 주려면 장치가 여러 가상 기능(VF)으로 나뉘는 SR-IOV를 지원해야 합니다.

넷 가운데 앞의 셋은 게스트가 보는 장치가 소프트웨어이므로 게스트를 다른 호스트로 옮기는 라이브 마이그레이션이 쉽습니다. 패스스루는 장치 안에 상태가 있어 어렵습니다.

::: {.design}
에뮬레이션은 "게스트를 한 줄도 고치지 않는다"는 제약을 지키는 대신 exit을 치릅니다. virtio는 그 제약을 풀었습니다. 게스트가 협조하면 인터페이스를 처음부터 다시 설계할 수 있고, 레지스터 대신 공유 메모리 큐를, 접근마다의 exit 대신 묶음 통지를 쓸 수 있습니다. 양쪽을 다 고칠 수 있을 때는 기존 인터페이스를 빠르게 흉내 내는 것보다 경계에 맞는 인터페이스를 새로 정하는 편이 낫습니다. 뒤에 나오는 kvmclock과 PV 스핀락도 같은 선택입니다.
:::

## 게스트의 시간과 락 {#time-locks}

vCPU는 스레드이므로 호스트 스케줄러가 언제든 CPU에서 내릴 수 있습니다. 게스트는 그 사실을 모릅니다. 여기서 두 가지 문제가 생깁니다.

### 시간이 건너뛴다

vCPU가 10밀리초 동안 쫓겨나 있었다면 게스트가 보기에는 명령어 하나를 실행하는 사이에 10밀리초가 지나간 것입니다. KVM은 게스트에 반가상화 시계 **kvmclock**을 줍니다. 호스트가 시간 계산에 필요한 값을 게스트와 공유하는 페이지에 적어 두고, 게스트는 exit 없이 그 값과 TSC로 현재 시각을 계산합니다. 게스트의 클록소스 이름이 `kvm-clock`입니다([8장](ch08.html)).

쫓겨나 있던 시간 자체도 알려 줍니다. **스틸 타임**(steal time)입니다. 호스트가 vCPU마다 공유 구조체에 누적 시간을 적고, 게스트는 `kvm_steal_clock()`(`arch/x86/kernel/kvm.c`)으로 읽습니다. 구조체의 `version`이 홀수이거나 읽는 도중에 바뀌었으면 다시 읽습니다. [14장](ch14.html)의 seqlock과 같은 규약을 호스트와 게스트 사이에 쓴 것입니다. 게스트의 스케줄러는 이 값을 태스크의 실행 시간에서 빼고, `top`의 `st` 열로 보여 줍니다.

### 락 주인이 쫓겨난다

[6장](ch06.html)에서 봤듯이 스핀락은 락을 쥔 태스크가 쫓겨나 기다리는 쪽이 헛도는 일을 막으려고 선점을 끕니다. 게스트 커널도 그렇게 합니다. 그러나 그것은 게스트 안의 약속일 뿐입니다. 호스트는 락을 쥔 vCPU를 통째로 내릴 수 있고, 그동안 다른 vCPU들은 풀릴 가망이 없는 락을 기다리며 호스트의 CPU를 태웁니다. 락 주인 선점이 한 층 아래에서 다시 나타난 것입니다.

대응은 양쪽에서 합니다. 게스트 쪽은 **PV 스핀락**입니다. 일정 횟수를 돌아도 락을 얻지 못하면 `kvm_wait()`(`arch/x86/kernel/kvm.c`)가 `halt()`를 실행합니다. exit이 나고 호스트는 이 vCPU 스레드를 재웁니다. 락을 푸는 쪽은 `kvm_kick_cpu()`로 하이퍼콜 `KVM_HC_KICK_CPU`를 불러 기다리던 vCPU를 깨웁니다. 헛도는 시간이 잠든 시간으로 바뀝니다.

호스트 쪽 대응은 하드웨어의 PAUSE 루프 감지입니다. 게스트가 `PAUSE`를 짧은 간격으로 되풀이하면 CPU가 exit을 내고(`EXIT_REASON_PAUSE_INSTRUCTION`), KVM의 `handle_pause()`가 다른 vCPU에 CPU를 양보합니다.

### 멈춘 vCPU는 잠든 스레드다

게스트가 할 일이 없어 `HLT`를 실행하면 `vcpu_run()`은 `vcpu_block()`으로 갑니다. 그 끝에 있는 코드입니다.

```{.c file="virt/kvm/kvm_main.c" line="3676"}
bool kvm_vcpu_block(struct kvm_vcpu *vcpu)
{
	struct rcuwait *wait = kvm_arch_vcpu_get_wait(vcpu);
	bool waited = false;
	/* ... */
	for (;;) {
		set_current_state(TASK_INTERRUPTIBLE);

		if (kvm_vcpu_check_block(vcpu) < 0)
			break;

		waited = true;
		schedule();
	}
	/* ... */
	return waited;
}
```

[3장](ch03.html)에서 본 잠들기 관용구 그대로입니다. 상태를 바꾸고, 조건을 확인하고, `schedule()`을 부릅니다. 쉬는 게스트는 호스트의 CPU를 쓰지 않습니다.

다만 잠들었다 깨는 데는 스케줄러를 두 번 거치는 비용이 듭니다. 인터럽트가 곧 올 것 같으면 잠들지 않고 잠깐 기다리는 편이 쌉니다. `kvm_vcpu_halt()`는 `kvm_vcpu_block()`을 부르기 전에 정해진 시간만큼 돌면서 깨울 일이 생기는지 봅니다. 이것이 **halt polling**이고, x86의 기본 상한은 200마이크로초입니다(`KVM_HALT_POLL_NS_DEFAULT`). 폴링이 성공했는지에 따라 vCPU마다 시간을 늘리고 줄입니다.

::: {.lab}
게스트 안에서 확인합니다.

```console
$ cat /sys/devices/system/clocksource/clocksource0/current_clocksource
kvm-clock
$ sudo dmesg | grep -i 'pv spinlock'
[    0.3...] kvm-guest: PV spinlocks enabled
$ grep '^cpu ' /proc/stat
cpu  4705 150 1120 16250 520 0 30 142 0 0
```

`/proc/stat`의 `cpu` 줄에서 여덟 번째 숫자가 스틸 타임입니다. 호스트의 CPU가 모자랄수록 빨리 늘어납니다. vCPU가 하나뿐인 게스트에서는 PV 스핀락이 꺼졌다는 메시지가 대신 나옵니다. halt polling의 상한은 호스트의 `/sys/module/kvm/parameters/halt_poll_ns`에 있습니다.
:::

## 중첩 가상화, 기밀 VM, arm64 {#beyond}

**중첩 가상화**는 게스트 안에서 다시 하이퍼바이저를 돌리는 것입니다. CPU의 VMX는 한 층만 지원하므로 게스트(L1)가 실행한 `VMLAUNCH`는 exit을 일으킵니다. 핸들러 표의 VMX 명령어 자리는 평소 게스트에 `#UD` 예외를 넣는 `handle_vmx_instruction()`이지만, 중첩을 켜면(`nested=1`) `handle_vmlaunch()` 같은 실제 핸들러로 바뀝니다. KVM(L0)이 L1의 VMCS를 읽어 자기 것과 합친 VMCS로 L2를 대신 실행합니다. 구현은 `arch/x86/kvm/vmx/nested.c`와 `svm/nested.c`입니다.

**기밀 VM**(confidential VM)은 호스트를 믿지 않는 게스트입니다. 지금까지의 모델에서 호스트 커널과 VMM은 게스트 메모리와 레지스터를 모두 볼 수 있습니다. AMD SEV-SNP와 인텔 TDX는 CPU가 게스트 메모리를 암호화하고 vCPU 상태를 호스트로부터 숨깁니다. KVM은 자원을 대 주되 내용은 보지 못합니다. v7.3에서 구현은 `arch/x86/kvm/svm/sev.c`와 `arch/x86/kvm/vmx/tdx.c`에 있고, 앞에서 본 guest_memfd가 비공개 메모리를 맡습니다.

**arm64**(`arch/arm64/kvm/`)는 VMX 같은 직교 모드 대신 예외 수준 EL2를 하이퍼바이저용으로 두고, 2단계 주소 변환은 stage-2 페이지 테이블이 맡습니다. `/dev/kvm`과 ioctl, `kvm_run`, memslot은 x86과 같습니다. `virt/kvm/`의 공통 코드를 아키텍처들이 함께 쓰기 때문입니다.

## 컨테이너, VM, 마이크로VM {#isolation}

[22장](ch22.html)의 컨테이너와 이 장의 가상 머신은 둘 다 워크로드를 격리하지만 경계가 놓인 자리가 다릅니다.

::: {.fig src="isolation-boundaries.svg"}
격리 경계의 위치. 컨테이너는 호스트 커널의 시스템 콜 인터페이스가 경계이고, 가상 머신은 VM exit과 장치 모델이 경계입니다.
:::

컨테이너 안의 프로세스는 호스트 커널의 시스템 콜을 직접 부릅니다. 커널에 권한 상승 버그가 하나 있으면 경계가 뚫립니다. 게스트가 호스트에 닿는 길은 VM exit뿐이고, 그 건너편에는 KVM의 exit 핸들러와 VMM의 장치 에뮬레이션이 있습니다. 표면이 좁지만, 흉내 내는 장치가 많을수록 다시 넓어집니다.

**마이크로VM**은 이 표면을 줄인 가상 머신입니다. 옛 PC의 장치들을 흉내 내지 않고 virtio 장치 몇 개만 둔 작은 VMM을 씁니다. 커널 쪽 KVM은 그대로입니다. KVM이 장치 모델을 유저 공간에 맡겼기 때문에 가능한 일입니다. 어떤 기계를 보여 줄지는 VMM이 정하고, KVM은 CPU와 메모리를 가상화하는 메커니즘만 줍니다.

## 정리 {#summary}

- VT-x와 AMD-V는 링과 직교하는 게스트 모드를 더했습니다. 게스트 커널은 진짜 링 0에서 실행되고, VMCS에 지정된 동작만 VM exit을 일으킵니다.
- KVM은 `/dev/kvm`의 ioctl로 쓰는 커널 모듈입니다. vCPU는 `KVM_RUN`을 부른 스레드이고 게스트 메모리는 VMM 프로세스의 가상 메모리입니다. 스케줄링과 메모리 관리는 호스트 커널의 것을 그대로 씁니다.
- `vcpu_run()`은 게스트 진입과 exit 처리를 되풀이합니다. exit은 빠른 경로, 커널 안 처리, 유저 공간 복귀 가운데 하나로 끝나고, 뒤로 갈수록 비쌉니다.
- 메모리는 게스트 페이지 테이블과 EPT 두 벌로 변환합니다. TLB 미스의 최악 비용은 메모리 참조 24번입니다.
- posted interrupt는 디스크립터의 PIR 비트와 통지 벡터 IPI로 exit 없이 인터럽트를 넣습니다.
- I/O는 에뮬레이션, virtio, vhost, 패스스루 순으로 exit이 줄어듭니다. virtqueue는 공유 메모리 큐와 통지 억제로 버퍼당 exit을 줄입니다.
- 호스트가 vCPU를 내릴 수 있어서 게스트에는 스틸 타임과 락 주인 선점 문제가 생깁니다. kvmclock, PV 스핀락, halt polling이 그 대응입니다.

## 확인 문제 {#quiz}

::: {.q}
게스트가 실행되는 도중에 호스트의 타이머 인터럽트가 왔고, 호스트 스케줄러가 이 vCPU 스레드 대신 다른 태스크를 돌리기로 했습니다. vCPU 스레드가 CPU를 내놓기까지의 과정을 설명해 보세요.

::: {.a}
호스트 인터럽트는 `EXIT_REASON_EXTERNAL_INTERRUPT`로 VM exit을 일으킵니다. 호스트의 타이머 핸들러가 `TIF_NEED_RESCHED`(또는 LAZY 비트)를 세웁니다. exit 핸들러가 1을 돌려주어 `vcpu_run()`의 반복문이 계속되고, 반복문 끝에서 `xfer_to_guest_mode_work()`가 플래그를 보고 `schedule()`을 부릅니다. 유저 모드 복귀 길의 유저 선점과 같은 구조입니다.
:::
:::

::: {.q}
EPT를 쓰면 섀도 페이지 테이블보다 VM exit이 줄어드는데, TLB 미스 한 번의 비용은 오히려 늘어납니다. 각각의 이유를 설명해 보세요.

::: {.a}
섀도 방식에서는 게스트가 자기 페이지 테이블이나 CR3를 고칠 때마다 KVM이 가로채 GVA→HPA 테이블을 맞춰야 하므로 exit이 납니다. EPT에서는 CPU가 두 테이블을 직접 따라가므로 KVM이 끼어들 필요가 없습니다. 대신 게스트 테이블의 각 단계가 GPA로 적혀 있어, 한 단계를 읽을 때마다 EPT 4단계를 따라가야 합니다. 최대 24번의 메모리 참조가 듭니다. 섀도 테이블은 한 벌이므로 4번입니다.
:::
:::

::: {.q}
virtio 드라이버가 버퍼 100개를 큐에 넣었는데 VM exit은 한 번만 났습니다. 어떤 장치가 이것을 가능하게 합니까?

::: {.a}
버퍼를 넣는 일은 공유 메모리의 디스크립터 테이블과 avail 링에 쓰는 것이라 exit이 없습니다. exit이 나는 것은 킥뿐인데, `virtqueue_kick_prepare_split()`이 장치가 알림을 원하는지 먼저 확인합니다. 장치가 큐를 처리 중이면 `VRING_USED_F_NO_NOTIFY`를 세우거나 이벤트 인덱스로 문턱을 적어 두므로 드라이버는 킥을 생략합니다. 드라이버도 여러 버퍼를 넣은 뒤 킥을 한 번만 부릅니다.
:::
:::

::: {.q}
게스트 커널은 스핀락을 쥘 때 선점을 끕니다. 그런데도 가상 머신에서 락 주인 선점이 문제가 되는 이유와, PV 스핀락이 그것을 어떻게 줄이는지 설명해 보세요.

::: {.a}
게스트의 `preempt_disable()`은 게스트 스케줄러만 막습니다. 호스트 스케줄러에게 vCPU는 보통의 스레드라서, 게스트가 락을 쥐고 있는지와 무관하게 내릴 수 있습니다. 그러면 다른 vCPU들은 락이 풀릴 때까지 호스트 CPU를 태우며 돕니다. PV 스핀락은 일정 횟수 이상 돌면 `kvm_wait()`에서 `halt()`를 실행해 exit을 내고, 호스트는 그 vCPU 스레드를 재웁니다. 락을 푸는 쪽이 `KVM_HC_KICK_CPU` 하이퍼콜로 깨웁니다. 헛돌던 CPU 시간이 락 주인에게 돌아갈 수 있습니다.
:::
:::

## 용어 {#terms}

::: {.terms}
VM exit
:   게스트 실행 중에 지정된 사건이 일어나 CPU가 호스트 모드로 넘어오는 일. 반대 방향이 VM 진입이다.

VMCS
:   인텔 VT-x에서 vCPU 하나의 게스트 상태, 호스트 상태, 실행 제어를 담는 구조. AMD에서는 VMCB.

VMM (virtual machine monitor)
:   게스트 메모리를 잡고 가상 장치를 흉내 내는 유저 공간 프로그램. QEMU가 대표적이다.

memslot
:   게스트 물리 주소 범위를 VMM 프로세스의 가상 주소 범위에 대응시킨 등록 단위.

EPT (extended page table)
:   게스트 물리 주소를 호스트 물리 주소로 바꾸는 두 번째 페이지 테이블. AMD에서는 NPT, 둘을 묶어 TDP.

TDP MMU
:   EPT·NPT 전용으로 다시 쓴 KVM의 MMU 구현. 폴트를 읽기 락과 RCU로 병렬 처리한다.

posted interrupt
:   디스크립터의 비트맵과 통지 벡터를 써서 VM exit 없이 게스트에 인터럽트를 전달하는 하드웨어 기능.

virtqueue
:   virtio 드라이버와 장치가 공유 메모리로 버퍼를 주고받는 큐. 디스크립터 테이블, avail 링, used 링으로 이루어진다.

스틸 타임 (steal time)
:   vCPU가 실행하려 했으나 호스트가 다른 일에 CPU를 써서 실행되지 못한 시간.

halt polling
:   멈춘 vCPU를 바로 재우지 않고 짧은 시간 돌면서 깨울 일을 기다리는 기법.
:::
