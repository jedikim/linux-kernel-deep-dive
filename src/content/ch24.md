::: {.lead}
커널의 동작을 바꾸는 길은 오랫동안 둘뿐이었습니다. 소스를 고쳐 다시 빌드하거나, 모듈을 올리는 것입니다. 앞의 것은 느리고, 뒤의 것은 위험합니다. 모듈은 커널의 모든 권한을 갖고 실행되므로 포인터 하나를 잘못 다루면 시스템이 멈춥니다. eBPF는 세 번째 길입니다. 유저가 준 코드를 커널 안에서 실행하되, 실행하기 전에 그 코드가 커널을 망가뜨릴 수 없음을 커널이 직접 증명합니다. 이 장은 그 증명이 어떻게 이루어지고, 통과한 코드가 커널의 어디에 붙는지 따라갑니다.
:::

::: {.goals}
- C로 쓴 BPF 프로그램은 어떤 단계를 거쳐 커널 안에서 실행되는가?
- 검증기는 레지스터마다 무엇을 추적하며, 널 확인을 빠뜨린 프로그램을 어떻게 알아내는가?
- 맵, 헬퍼, kfunc는 각각 무엇이고 안정성 약속이 어떻게 다른가?
- 커널 버전마다 구조체 배치가 다른데 BPF 프로그램 하나가 어떻게 여러 커널에서 도는가?
- struct_ops는 커널의 함수 포인터 테이블을 어떻게 BPF 프로그램으로 채우는가?
- BPF로 쓴 스케줄러가 잘못 동작하면 커널은 어떻게 대응하는가?
:::

## 패킷 필터에서 커널 안의 실행 환경으로 {#origin}

BPF는 패킷 필터로 시작했습니다. `tcpdump port 22`처럼 원하는 패킷만 유저 공간으로 올리려면 걸러 내는 일을 커널 안에서 해야 합니다. 그래서 필터 조건을 작은 가상 기계의 명령어로 표현해 커널에 넘기고, 커널이 패킷마다 그 명령어를 실행하게 했습니다. 지금은 이것을 **클래식 BPF**(cBPF)라고 부릅니다. 레지스터가 둘뿐이고 패킷을 읽는 일밖에 못 했습니다.

**eBPF**는 같은 발상을 범용으로 넓힌 것입니다. 가상 기계는 64비트 레지스터 열 개(R0–R9)와 읽기 전용 프레임 포인터(R10)를 갖습니다. R0은 반환값, R1–R5는 함수 인자, R6–R9는 호출 뒤에도 보존되는 레지스터입니다. 이 배치는 64비트 CPU의 호출 규약에 일대일로 대응하도록 고른 것입니다. 프로그램은 패킷뿐 아니라 커널의 여러 지점에 붙을 수 있고, 맵이라는 자료구조에 상태를 저장하며, 정해진 커널 함수를 부를 수 있습니다. 이 책에서 BPF라고 하면 eBPF를 가리킵니다.

핵심 약속은 하나입니다. **검증기가 안전하다고 확인한 프로그램만 실행된다.** 안전하다는 것은 구체적으로 다음을 뜻합니다.

- 반드시 끝난다. 무한 반복이 없다.
- 허락된 메모리만 읽고 쓴다. 범위를 벗어나거나 널 포인터를 따라가지 않는다.
- 얻은 자원(락, 참조)을 반드시 돌려준다.
- 초기화하지 않은 값을 읽지 않고, 커널 주소를 유저에게 흘리지 않는다.

::: {.old}
"BPF 프로그램에는 반복문을 쓸 수 없고 명령어는 4096개까지"라는 설명이 아직 많습니다. `kernel/bpf/verifier.c` 머리의 주석에도 같은 내용이 남아 있습니다. v7.3의 실제는 다릅니다. 4096개(`BPF_MAXINSNS`)는 권한 없는 프로그램에만 적용됩니다. `CAP_BPF`가 있으면 검증기가 **처리한** 명령어 수 100만(`BPF_COMPLEXITY_LIMIT_INSNS`)이 한도입니다. 5.2에서 바뀌었습니다. 뒤로 가는 분기도 `CAP_BPF`가 있으면 허용되고(`kernel/bpf/cfg.c`), 검증기가 반복을 한 바퀴씩 따라가며 끝나는지 확인합니다. 5.3에서 들어온 유계 루프입니다.
:::

## 소스에서 훅까지 {#pipeline}

BPF 프로그램은 보통 C로 씁니다. 다음은 프로세스별로 `openat()` 호출 횟수를 세는 프로그램입니다.

```{.c name="count.bpf.c"}
struct {
	__uint(type, BPF_MAP_TYPE_HASH);
	__uint(max_entries, 1024);
	__type(key, u32);
	__type(value, u64);
} counts SEC(".maps");

SEC("tracepoint/syscalls/sys_enter_openat")
int count_openat(void *ctx)
{
	u32 pid = bpf_get_current_pid_tgid() >> 32;
	u64 one = 1, *val;

	val = bpf_map_lookup_elem(&counts, &pid);
	if (val)
		__sync_fetch_and_add(val, 1);
	else
		bpf_map_update_elem(&counts, &pid, &one, BPF_ANY);
	return 0;
}

char LICENSE[] SEC("license") = "GPL";
```

::: {.fig src="pipeline.svg"}
C 소스가 훅에서 실행되기까지. 유저 공간에서 일어나는 일과 `bpf()` 시스템 콜 한 번 안에서 커널이 하는 일이 나뉩니다.
:::

1. **컴파일.** `clang --target=bpf`가 C를 BPF 바이트코드로 바꿔 ELF 파일에 담습니다. 맵 정의, 타입 정보(BTF), 재배치 기록도 같이 들어갑니다.
2. **로드.** 로더(대개 libbpf)가 맵을 먼저 만들고, 바이트코드의 맵 참조를 맵의 fd로 채운 뒤 `bpf(BPF_PROG_LOAD, ...)`를 부릅니다.
3. **검증.** 커널의 `bpf_prog_load()`가 권한을 확인하고 `bpf_check()`를 부릅니다. 통과하지 못하면 여기서 오류와 함께 로그가 돌아옵니다.
4. **JIT.** `bpf_check()`의 마지막 단계가 바이트코드를 CPU의 기계어로 번역합니다. `CONFIG_BPF_JIT_ALWAYS_ON`이면 인터프리터는 커널에 아예 들어 있지 않습니다.
5. **부착.** 프로그램 fd를 훅에 붙입니다. 위 예에서는 `SEC()`에 적은 추적점입니다. 붙인 결과는 **링크**(bpf_link)라는 객체가 되고, 링크의 fd가 닫히면 프로그램도 떨어집니다.
6. **실행.** 그 뒤로 추적점을 지날 때마다 커널이 번역된 함수를 부릅니다. 호출 자체는 `prog->bpf_func`를 부르는 것이 전부입니다(`include/linux/filter.h`의 `__bpf_prog_run()`).

JIT가 단순한 까닭은 BPF의 레지스터 배치가 처음부터 실제 CPU에 맞춰져 있기 때문입니다. x86-64 JIT의 대응표입니다.

```{.c file="arch/x86/net/bpf_jit_comp.c" line="183"}
static const int reg2hex[] = {
	[BPF_REG_0] = 0,  /* RAX */
	[BPF_REG_1] = 7,  /* RDI */
	[BPF_REG_2] = 6,  /* RSI */
	[BPF_REG_3] = 2,  /* RDX */
	[BPF_REG_4] = 1,  /* RCX */
	[BPF_REG_5] = 0,  /* R8  */
	[BPF_REG_6] = 3,  /* RBX callee saved */
	[BPF_REG_7] = 5,  /* R13 callee saved */
	[BPF_REG_8] = 6,  /* R14 callee saved */
	[BPF_REG_9] = 7,  /* R15 callee saved */
	[BPF_REG_FP] = 5, /* RBP readonly */
	/* ... */
};
```

R1–R5가 RDI, RSI, RDX, RCX, R8입니다. x86-64에서 C 함수가 인자를 받는 레지스터 그대로입니다. BPF 프로그램이 커널 함수를 부를 때 인자를 옮길 필요 없이 `call` 명령어 하나면 됩니다. 반환값 R0도 RAX입니다.

## 검증기 {#verifier}

`bpf_check()`는 정적 분석기입니다. 프로그램을 실행하지 않고, 실행될 수 있는 모든 경로를 따라가며 각 지점에서 레지스터와 스택에 무엇이 들어 있을 수 있는지 추적합니다. v7.3에서 본격적인 분석에 들어가기 직전의 준비 단계는 이렇습니다.

```{.c file="kernel/bpf/verifier.c" line="21362"}
	ret = bpf_check_cfg(env);
	if (ret < 0)
		goto skip_full_check;
	/* ... */
	ret = bpf_compute_const_regs(env);
	if (ret < 0)
		goto skip_full_check;

	ret = bpf_prune_dead_branches(env);
	if (ret < 0)
		goto skip_full_check;
	/* ... */
	ret = bpf_compute_scc(env);
	if (ret < 0)
		goto skip_full_check;

	ret = bpf_compute_live_registers(env);
	if (ret < 0)
		goto skip_full_check;
	/* ... */
	ret = do_check_main(env);
	ret = ret ?: do_check_subprogs(env);
```

컴파일러의 패스 목록처럼 읽힙니다. `bpf_check_cfg()`는 제어 흐름 그래프를 만들어 도달할 수 없는 명령어와 범위를 벗어난 점프를 거릅니다. 그 뒤의 단계들은 상수 레지스터, 죽은 분기, 강연결 요소(반복문), 살아 있는 레지스터를 미리 계산합니다. 모두 마지막 줄의 `do_check_main()`이 덜 헤매게 하려는 준비입니다. `do_check_main()`이 명령어를 하나씩 따라가며 상태를 갱신하는 본 분석입니다.

### 레지스터 상태

검증기가 레지스터마다 들고 다니는 정보는 `struct bpf_reg_state`(`include/linux/bpf_verifier.h`)입니다. 중요한 것은 넷입니다.

| 필드 | 뜻 |
|---|---|
| `type` | 이 레지스터에 든 것의 종류. `SCALAR_VALUE`(그냥 숫자), `PTR_TO_CTX`, `PTR_TO_STACK`, `PTR_TO_MAP_VALUE`, `PTR_TO_BTF_ID`(커널 구조체) 등. 플래그 `PTR_MAYBE_NULL`이 붙을 수 있습니다. |
| `var_off` | **tnum**. 비트마다 0인지, 1인지, 모르는지를 추적합니다. |
| `r64`, `r32` | 값의 범위. 64비트로 본 범위와 아래 32비트로 본 범위입니다. |
| `id` | 같은 출처에서 나온 레지스터들을 묶는 번호. 하나를 널 확인하면 나머지도 함께 확정됩니다. |

포인터는 종류마다 할 수 있는 일이 다릅니다. `PTR_TO_MAP_VALUE`는 맵 값 크기 안에서만 읽고 쓸 수 있습니다. `SCALAR_VALUE`는 역참조할 수 없습니다. 포인터에 숫자를 더할 수는 있지만 그 숫자의 범위가 알려져 있어야 합니다. 배열 인덱스로 쓸 값이 `r64` 기준으로 0 이상 15 이하임을 검증기가 알아야, 원소 16개짜리 배열 접근이 통과합니다. 그 범위는 프로그램 안의 `if (idx < 16)` 같은 비교문에서 얻습니다.

::: {.old}
많은 자료가 레지스터의 범위를 `smin_value`, `smax_value`, `umin_value`, `umax_value`와 그 32비트판까지 필드 여덟 개로 설명합니다. 부호 있는 범위와 부호 없는 범위를 따로 들고 서로 맞추는 방식이었습니다. v7.3에는 이 필드들이 없습니다. 범위 하나를 "원 위의 호"로 나타내는 `struct cnum64`와 `struct cnum32`(`include/linux/cnum.h`) 둘로 바뀌었습니다. 시작값 `base`와 길이 `size`만으로 부호 있는 범위와 없는 범위를 한 번에 표현합니다. 코드에서 옛 이름이 필요한 자리는 `reg_smin()`, `reg_umax()` 같은 접근 함수를 씁니다.
:::

### 널 확인을 강제하는 방법

앞의 예제에서 `if (val)`을 지우면 어떻게 될까요. 검증기는 `bpf_map_lookup_elem()`이 무엇을 돌려주는지 헬퍼의 선언에서 읽습니다.

```{.c file="kernel/bpf/helpers.c" line="44"}
BPF_CALL_2(bpf_map_lookup_elem, struct bpf_map *, map, void *, key)
{
	WARN_ON_ONCE(!bpf_rcu_lock_held());
	return (unsigned long) map->ops->map_lookup_elem(map, key);
}

const struct bpf_func_proto bpf_map_lookup_elem_proto = {
	.func		= bpf_map_lookup_elem,
	.gpl_only	= false,
	.pkt_access	= true,
	.ret_type	= RET_PTR_TO_MAP_VALUE_OR_NULL,
	.arg1_type	= ARG_CONST_MAP_PTR,
	.arg2_type	= ARG_PTR_TO_MAP_KEY,
};
```

`.ret_type`이 `RET_PTR_TO_MAP_VALUE_OR_NULL`입니다. 이 헬퍼를 부른 뒤 R0의 종류는 "맵 값이거나 널"이 됩니다. 이 종류는 역참조가 허락되지 않습니다. 프로그램이 R0을 0과 비교하는 분기를 지나면 검증기는 두 갈래의 상태를 따로 만들고, 다음 함수로 각 갈래의 종류를 고칩니다.

```{.c file="kernel/bpf/verifier.c" line="16689"}
static void mark_ptr_or_null_reg(struct bpf_func_state *state,
				 struct bpf_reg_state *reg, u32 id,
				 bool is_null)
{
	if (type_may_be_null(reg->type) && reg->id == id &&
	    (is_rcu_reg(reg) || !WARN_ON_ONCE(!reg->id))) {
		/* ... */
		if (is_null) {
			/* ... */
			__mark_reg_known_zero(reg);
			reg->type = SCALAR_VALUE;

			return;
		}

		mark_ptr_not_null_reg(reg);
		/* ... */
	}
}
```

널인 갈래에서는 레지스터가 값 0인 숫자가 되고, 널이 아닌 갈래에서는 `PTR_MAYBE_NULL`이 떨어져 진짜 `PTR_TO_MAP_VALUE`가 됩니다. `reg->id == id` 조건 덕분에 R0을 다른 레지스터에 복사해 두었더라도 함께 바뀝니다.

::: {.fig src="verifier-states.svg"}
맵 조회 뒤 R0의 상태가 분기를 지나며 갈라지는 과정. 검증기는 두 갈래를 모두 끝까지 따라갑니다.
:::

확인 없이 역참조하면 `check_mem_access()`가 거부하고 로그를 남깁니다. `Documentation/bpf/verifier.rst`에 실린 예입니다.

```console
4: (85) call 1
5: (7a) *(u64 *)(r0 +0) = 0
R0 invalid mem access 'map_value_or_null'
```

`call 1`은 1번 헬퍼, 곧 `bpf_map_lookup_elem()` 호출입니다. 바로 다음 명령어가 R0을 주소로 써서 거부되었습니다. v7.3의 검증기는 이 한 줄에 더해 이유와 고치는 방법을 풀어 쓴 진단도 로그에 넣습니다(`kernel/bpf/diagnostics.c`).

자원도 같은 방식으로 따라갑니다. 소켓이나 태스크의 참조를 얻는 함수(kfunc에서는 `KF_ACQUIRE` 플래그)가 돌려준 포인터에는 번호가 붙습니다. 검증기는 프로그램이 끝나는 모든 경로에서 그 포인터가 짝이 되는 해제 함수에 넘겨졌는지 확인하고, 하나라도 남아 있으면 거부합니다. 락도 마찬가지입니다. 잡은 채로 끝나는 경로가 있으면 통과하지 못합니다.

### 끝난다는 보장

검증기는 분기마다 두 갈래를 모두 따라가므로 경로 수가 지수적으로 늘 수 있습니다. 그래서 이미 본 상태를 기억해 둡니다. 어떤 명령어에 다시 왔는데 지금 상태가 예전에 안전하다고 확인한 상태에 포함되면 더 따라가지 않습니다(**상태 가지치기**). 반복문에서는 반대로 씁니다. 같은 자리에 완전히 같은 상태로 돌아왔다면 아무 진전이 없었다는 뜻이므로 `infinite loop detected`로 거부합니다.

그래도 남는 경우는 예산으로 막습니다. 처리한 명령어가 100만 개를 넘으면 거부합니다. 스택은 프로그램당 512바이트(`MAX_BPF_STACK`)이고 함수 호출 깊이에도 한도가 있습니다. 반복 횟수를 미리 알 수 없는 반복은 `bpf_loop()` 헬퍼나 `bpf_for()` 같은 반복자로 씁니다. 이 경우 검증기는 횟수만큼 따라가지 않고 본문이 몇 번을 돌든 안전한지를 확인하며, 횟수 제한은 커널 쪽 구현이 맡습니다.

::: {.design}
모듈을 올릴 때 커널은 작성자를 믿습니다. BPF 프로그램을 올릴 때는 프로그램을 **검사**합니다. 검사는 로드할 때 한 번만 하므로 실행 중에는 경계 검사도, 널 검사도 없습니다. 검증기가 이미 증명했기 때문입니다. 실행 중 검사를 로드 시점의 증명으로 바꾸면 안전과 속도를 같이 얻습니다. 대가는 표현력입니다. 검증기가 증명하지 못하는 프로그램은 실제로 안전하더라도 거부됩니다. 그래서 BPF 프로그램을 쓴다는 것은 절반쯤은 검증기가 따라올 수 있게 쓰는 일입니다.
:::

## 맵, 헬퍼, kfunc {#maps}

BPF 프로그램은 호출이 끝나면 스택이 사라집니다. 호출 사이에 남길 상태, 유저 공간과 주고받을 데이터는 **맵**(map)에 둡니다.

::: {.fig src="maps-shared.svg"}
맵은 커널 안의 객체이고 fd로 가리킵니다. BPF 프로그램은 헬퍼로, 유저 프로그램은 `bpf()` 시스템 콜로 같은 맵에 접근합니다.
:::

v7.3의 `enum bpf_map_type`에는 서른 개가 넘는 종류가 있습니다. 자주 쓰는 것만 추리면 이렇습니다.

| 종류 | 용도 |
|---|---|
| `HASH`, `ARRAY` | 키로 값을 찾는 기본 맵 |
| `PERCPU_HASH`, `PERCPU_ARRAY` | CPU마다 값을 따로 둡니다. 카운터에 락이 필요 없습니다([13장](ch13.html)). |
| `LRU_HASH` | 가득 차면 오래 안 쓴 항목을 버립니다. |
| `LPM_TRIE` | 가장 길게 일치하는 접두사 찾기. IP 주소 대역 |
| `RINGBUF` | 커널에서 유저로 사건을 흘려보내는 링 버퍼 |
| `TASK_STORAGE`, `CGRP_STORAGE` | 태스크나 cgroup 객체에 딸려 다니는 저장소 |
| `ARENA` | BPF 프로그램과 유저 프로세스가 함께 매핑하는 메모리 영역 |
| `STRUCT_OPS` | 뒤에서 볼 struct_ops의 그릇 |

맵도 [25장](ch25.html)의 ops 테이블 패턴입니다. 앞의 헬퍼가 `map->ops->map_lookup_elem()`을 부르던 것을 보았습니다. 해시 맵은 `htab_map_ops`가, 배열은 `array_map_ops`가 그 자리를 채웁니다.

BPF 프로그램이 부를 수 있는 커널 함수는 두 종류입니다.

**헬퍼**(helper)는 번호가 매겨진 고정 목록입니다. `bpf_map_lookup_elem`은 1번이고 이 번호는 UAPI의 일부라 바뀌지 않습니다. 프로그램 유형마다 쓸 수 있는 헬퍼가 다릅니다.

**kfunc**는 BPF에 열어 준 보통의 커널 함수입니다. 번호가 없고, 인자와 반환 타입을 BTF로 기술합니다. 정의에 `__bpf_kfunc`를 붙이고 집합에 등록하면 끝입니다.

```{.c file="kernel/sched/ext/ext.c" line="9141"}
BTF_KFUNCS_START(scx_kfunc_ids_enqueue_dispatch)
BTF_ID_FLAGS(func, scx_bpf_dsq_insert, KF_IMPLICIT_ARGS | KF_RCU)
BTF_ID_FLAGS(func, scx_bpf_dsq_insert___v2, KF_IMPLICIT_ARGS | KF_RCU)
BTF_ID_FLAGS(func, __scx_bpf_dsq_insert_vtime, KF_IMPLICIT_ARGS | KF_RCU)
BTF_ID_FLAGS(func, scx_bpf_dsq_insert_vtime, KF_RCU)
BTF_KFUNCS_END(scx_kfunc_ids_enqueue_dispatch)
```

플래그가 검증기에 주는 지시입니다. `KF_RCU`는 RCU로 보호된 포인터를 인자로 받는다는 뜻입니다. 함수 이름에 붙은 `___v2`가 kfunc의 성격을 보여 줍니다. kfunc에는 ABI 안정성 약속이 없습니다. 서명을 바꿔야 하면 새 이름으로 추가하고 옛것은 나중에 지웁니다. v7.3에서 새 기능은 헬퍼가 아니라 kfunc로 들어옵니다(`Documentation/bpf/bpf_design_QA.rst`). UAPI에 묶이는 번호를 더 늘리지 않으려는 것입니다.

## BTF와 CO-RE {#btf}

추적 프로그램은 `task_struct` 같은 커널 구조체의 필드를 읽습니다. 그런데 구조체의 배치는 커널 버전과 빌드 설정마다 다릅니다. 필드가 추가되면 그 뒤 필드의 오프셋이 전부 밀립니다. 예전에는 대상 기계마다 그 커널의 헤더로 프로그램을 다시 컴파일했습니다.

**BTF**(BPF type format)는 타입 정보를 담는 간결한 형식입니다. 커널은 빌드될 때 자기 자신의 모든 구조체, 함수 서명을 BTF로 만들어 품고, `/sys/kernel/btf/vmlinux`로 내보입니다. 검증기가 `PTR_TO_BTF_ID` 포인터의 필드 접근을 검사할 수 있는 것도, kfunc의 인자 타입을 아는 것도 이 정보 덕분입니다.

**CO-RE**(compile once, run everywhere)는 BTF를 써서 프로그램을 로드할 때 고쳐 씁니다.

::: {.fig src="core-relocation.svg"}
컴파일러는 오프셋 대신 "어느 구조체의 어느 필드"라는 기록을 남기고, 로더가 실행 중인 커널의 BTF에서 실제 오프셋을 찾아 명령어를 고칩니다.
:::

컴파일러는 필드 접근 명령어마다 재배치 기록(`struct bpf_core_relo`)을 남깁니다. 기록에는 명령어 위치, 구조체의 타입 번호, 접근 경로가 들어 있습니다. 로더는 프로그램의 BTF와 대상 커널의 BTF에서 이름이 같은 구조체와 필드를 찾아 명령어의 오프셋을 바꿉니다. 필드가 그 커널에 없을 때를 대비해 "이 필드가 있는가"를 묻는 재배치도 있습니다. 재배치를 계산하는 코드는 libbpf와 커널이 같은 파일을 씁니다. `kernel/bpf/relo_core.c`는 `tools/lib/bpf/relo_core.c`를 포함하는 한 줄입니다.

## 훅의 지도 {#hooks}

검증을 통과한 프로그램은 **훅**(hook)에 붙어야 실행됩니다. 프로그램 유형(`enum bpf_prog_type`)이 어떤 훅에 붙을 수 있는지, 인자로 무엇을 받는지, 어떤 헬퍼를 쓸 수 있는지, 반환값이 무슨 뜻인지를 정합니다.

::: {.fig src="hook-map.svg"}
커널 서브시스템 위에 놓인 BPF 훅. 왼쪽은 관찰만 하는 훅이고 오른쪽은 반환값으로 커널의 결정을 바꾸는 훅입니다.
:::

| 훅 | 붙는 자리 | 프로그램이 하는 일 |
|---|---|---|
| 추적점 | 커널 소스에 미리 심어 둔 지점 | 관찰. 인자는 추적점이 정의한 필드 |
| kprobe, fentry/fexit | 거의 모든 커널 함수의 진입과 반환 | 관찰. fentry는 BPF 트램펄린을 써서 더 쌉니다. |
| uprobe | 유저 프로그램의 함수 | 관찰 |
| perf 이벤트 | 주기적 샘플, 하드웨어 카운터 | 프로파일링 |
| XDP, tc | 드라이버의 수신 경로, qdisc 계층 | 패킷을 통과·폐기·전달 ([12장](ch12.html)) |
| cgroup | cgroup에 속한 소켓, 장치 접근, sysctl | 허용·거부 ([22장](ch22.html)) |
| LSM | 보안 훅 | 접근 허용·거부 |
| struct_ops | 커널의 ops 테이블 | 커널 알고리즘을 통째로 구현 |

추적 계열은 관찰만 합니다. 커널 메모리를 읽어 맵에 적을 뿐 커널의 진행을 바꾸지 못합니다. 네트워크, cgroup, LSM 계열은 반환값이 판정입니다. XDP 프로그램이 `XDP_DROP`을 돌려주면 그 패킷은 버려집니다.

::: {.lab}
이 책의 실습에 여러 번 나온 `bpftrace` 한 줄도 BPF 프로그램입니다.

```console
# bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'
```

`bpftrace`는 이 스크립트를 BPF 바이트코드로 컴파일하고, `@`를 해시 맵으로 만들고, 프로그램을 추적점에 붙입니다. 앞의 `count.bpf.c`와 같은 일을 합니다. Ctrl-C를 누르면 맵을 읽어 출력합니다. 실행 중에 다른 터미널에서 확인합니다.

```console
# bpftool prog list
...
412: tracepoint  name sys_enter_opena  tag ...  gpl
        loaded_at ...  uid 0
        xlated 232B  jited 141B  memlock 4096B  map_ids 87
# bpftool map dump id 87 | head
# bpftool prog dump xlated id 412 | head
```

`xlated`는 검증기가 고쳐 쓴 뒤의 바이트코드 크기, `jited`는 기계어 크기입니다. 번호와 크기는 예시입니다. 붙을 수 있는 추적점은 `bpftrace -l 'tracepoint:sched:*'`로, 커널의 타입 정보는 `bpftool btf dump file /sys/kernel/btf/vmlinux format c | head`로 봅니다.
:::

## struct_ops: ops 테이블을 BPF로 채우기 {#struct-ops}

커널은 서브시스템의 구현을 함수 포인터 구조체로 갈아 끼웁니다. TCP 혼잡 제어는 `struct tcp_congestion_ops`, 스케줄링 클래스는 `struct sched_class`입니다. 지금까지 이 구조체를 채울 수 있는 것은 커널 코드와 모듈뿐이었습니다. **struct_ops**는 그 자리를 BPF 프로그램으로 채우게 합니다.

방법은 맵입니다. `BPF_MAP_TYPE_STRUCT_OPS` 맵의 값이 곧 그 구조체이고, 유저 공간은 함수 포인터 자리마다 BPF 프로그램의 fd를 적어 맵을 갱신합니다. 커널이 받아서 하는 일입니다.

```{.c file="kernel/bpf/bpf_struct_ops.c" line="726"}
static long bpf_struct_ops_map_update_elem(struct bpf_map *map, void *key,
					   void *value, u64 flags)
{
	/* ... */
	for_each_member(i, t, member) {
		/* ... */
		prog_fd = (int)(*(unsigned long *)(udata + moff));
		/* Similar check as the attr->attach_prog_fd */
		if (!prog_fd)
			continue;

		prog = bpf_prog_get(prog_fd);
		/* ... */
		err = bpf_struct_ops_prepare_trampoline(tnodes, &link->node,
						&st_ops->func_models[i],
						*(void **)(st_ops->cfi_stubs + moff),
						&image, &image_off,
						st_map->image_pages_cnt < MAX_TRAMP_IMAGE_PAGES);
		/* ... */
		*(void **)(kdata + moff) = image + trampoline_start + cfi_get_offset();
		/* ... */
	}
	/* ... */
	err = st_ops->reg(kdata, NULL);
	/* ... */
}
```

읽을 곳은 세 군데입니다.

- 구조체의 멤버를 BTF로 하나씩 훑습니다(`for_each_member`). 구조체의 배치를 BTF로 알기 때문에 어떤 구조체든 같은 코드로 처리합니다.
- 멤버마다 **트램펄린**을 만듭니다. 커널은 이 포인터를 C 호출 규약으로 부르고 BPF 프로그램은 인자를 컨텍스트 하나로 받으므로, 그 사이를 잇는 작은 기계어 조각이 필요합니다. `kdata`의 함수 포인터 자리에는 그 조각의 주소가 들어갑니다.
- 다 채워지면 `st_ops->reg(kdata, ...)`로 서브시스템에 등록합니다. 서브시스템이 보기에 `kdata`는 모듈이 등록한 것과 다르지 않은 보통의 ops 구조체입니다.

::: {.fig src="struct-ops.svg"}
유저가 채운 struct_ops 맵이 커널의 ops 구조체가 되기까지. 서브시스템의 호출부는 상대가 BPF라는 사실을 모릅니다.
:::

::: {.design}
struct_ops가 가능했던 것은 커널이 이미 확장 지점을 ops 테이블이라는 **인터페이스**로 정리해 두었기 때문입니다. 호출부는 구조체의 함수 포인터만 부르고, 누가 채웠는지 묻지 않습니다. BPF는 그 인터페이스에 새 종류의 구현자로 들어갔을 뿐입니다. 내부를 인터페이스 뒤에 두면 나중에 생각지 못한 방식의 확장이 그 인터페이스에 꽂힙니다.
:::

## 사례: sched_ext {#sched-ext}

struct_ops를 가장 크게 쓰는 곳이 [5장](ch05.html)에서 소개한 **sched_ext**입니다. 스케줄링 클래스 하나를 통째로 BPF에 맡깁니다. BPF 쪽이 채우는 테이블입니다.

```{.c file="kernel/sched/ext/internal.h" line="347"}
struct sched_ext_ops {
	/* ... */
	s32 (*select_cpu)(struct task_struct *p, s32 prev_cpu, u64 wake_flags);
	/* ... */
	void (*enqueue)(struct task_struct *p, u64 enq_flags);
	/* ... */
	void (*dispatch)(s32 cpu, struct task_struct *prev);
	/* ... */
```

태스크가 깨어나면 `select_cpu`, 실행 가능해지면 `enqueue`, CPU가 다음에 돌릴 태스크가 필요하면 `dispatch`가 불립니다. 커널 소스에 들어 있는 가장 작은 스케줄러 `scx_simple`은 이 테이블을 이렇게 채웁니다.

```{.c file="tools/sched_ext/scx_simple.bpf.c" line="152"}
SCX_OPS_DEFINE(simple_ops,
	       .select_cpu		= (void *)simple_select_cpu,
	       .enqueue			= (void *)simple_enqueue,
	       .dispatch		= (void *)simple_dispatch,
	       .running			= (void *)simple_running,
	       .stopping		= (void *)simple_stopping,
	       .enable			= (void *)simple_enable,
	       .init			= (void *)simple_init,
	       .exit			= (void *)simple_exit,
	       .name			= "simple");
```

커널 코드가 ops 테이블을 지정 초기화로 채우는 것과 모양이 같습니다. 다른 점은 오른쪽의 함수들이 BPF 프로그램이고, 이 구조체가 `.struct_ops.link`라는 ELF 섹션에 놓인다는 것입니다. 로더가 그 섹션을 보고 struct_ops 맵을 만들어 앞 절의 경로로 등록합니다. `simple_enqueue()`와 `simple_dispatch()`의 내용은 [5장](ch05.html)에서 읽었습니다. 실행 가능해진 태스크를 모든 CPU가 함께 쓰는 큐에 가상 시간 순으로 넣고, CPU가 일거리를 찾으면 맨 앞을 꺼내 주는 것이 전부입니다. 큐 자체와 락, 컨텍스트 스위치는 커널이 맡고, BPF 프로그램은 kfunc(`scx_bpf_dsq_insert()`)를 불러 "누구를 어디에 넣을지"만 정합니다.

같은 파일에는 이 장의 앞에서 본 것들이 그대로 들어 있습니다.

```{.c file="tools/sched_ext/scx_simple.bpf.c" line="41"}
struct {
	__uint(type, BPF_MAP_TYPE_PERCPU_ARRAY);
	__uint(key_size, sizeof(u32));
	__uint(value_size, sizeof(u64));
	__uint(max_entries, 2);			/* [local, global] */
} stats SEC(".maps");

static void stat_inc(u32 idx)
{
	u64 *cnt_p = bpf_map_lookup_elem(&stats, &idx);
	if (cnt_p)
		(*cnt_p)++;
}
```

통계를 세는 CPU별 배열 맵과, 조회 결과를 널 확인한 뒤에만 쓰는 코드입니다. `if (cnt_p)`를 지우면 이 스케줄러는 로드되지 않습니다.

### 스케줄러가 틀렸을 때

검증기는 이 프로그램이 메모리를 망가뜨리지 않는다는 것만 보장합니다. 정책이 옳은지는 보장하지 못합니다. `enqueue`에서 받은 태스크를 어느 큐에도 넣지 않는 스케줄러는 검증을 통과하지만, 그 태스크는 영영 실행되지 않습니다. 그래서 sched_ext는 실행 중 감시를 따로 둡니다.

```{.c file="kernel/sched/ext/ext.c" line="3788"}
static bool check_rq_for_timeouts(struct rq *rq)
{
	/* ... */
	list_for_each_entry(p, &rq->scx.runnable_list, scx.runnable_node) {
		struct scx_sched *sch = scx_task_sched(p);
		unsigned long last_runnable = p->scx.runnable_at;

		if (unlikely(time_after(jiffies,
					last_runnable + READ_ONCE(sch->watchdog_timeout)))) {
			/* ... */
			__scx_exit(sch, SCX_EXIT_ERROR_STALL, 0, cpu_of(rq),
				   "%s[%d] failed to run for %u.%03us",
				   p->comm, p->pid, dur_ms / 1000,
				   dur_ms % 1000);
			timed_out = true;
			break;
		}
	}
	/* ... */
}
```

워치독이 주기적으로 모든 런큐를 돌며, 실행 가능해진 뒤 제한 시간 안에 한 번도 CPU를 받지 못한 태스크가 있는지 봅니다. 있으면 BPF 스케줄러를 내립니다. 내리는 과정(`scx_root_disable()`)은 모든 태스크의 `sched_class`를 원래 클래스로 되돌리는 것이고, 대부분은 fair 클래스입니다. BPF 스케줄러가 kfunc를 잘못된 인자로 불렀을 때, 그리고 관리자가 SysRq-S를 눌렀을 때도 같은 길로 갑니다.

::: {.fig src="scx-fallback.svg"}
BPF 스케줄러는 세 가지 경로로 내려갑니다. 어느 경우든 태스크는 fair 클래스로 돌아가 계속 실행됩니다.
:::

::: {.design}
스케줄러는 틀리면 시스템이 멈추는 코드입니다. 그런 코드를 유저가 바꿀 수 있게 열어 준 근거는 "틀려도 되돌릴 수 있다"는 것입니다. 정적 검증은 메모리 안전을, 워치독은 진행을, SysRq는 사람의 개입을 맡습니다. 위험한 실험을 허용하려면 먼저 실패를 감지해 안전한 상태로 돌아가는 길을 만들어야 합니다. 그 길이 있으면 실험의 비용은 "시스템 정지"에서 "잠깐의 지연"으로 내려갑니다.
:::

## 권한과 한계, 그리고 모듈 {#limits}

BPF 프로그램을 로드하는 것은 특권 작업입니다. `bpf_prog_load()`의 앞부분입니다.

```{.c file="kernel/bpf/syscall.c" line="2992"}
	if (sysctl_unprivileged_bpf_disabled && !bpf_cap)
		goto put_token;

	if (attr->insn_cnt == 0 ||
	    attr->insn_cnt > (bpf_cap ? BPF_COMPLEXITY_LIMIT_INSNS : BPF_MAXINSNS)) {
		err = -E2BIG;
		goto put_token;
	}
	if (type != BPF_PROG_TYPE_SOCKET_FILTER &&
	    type != BPF_PROG_TYPE_CGROUP_SKB &&
	    !bpf_cap)
		goto put_token;

	if (is_net_admin_prog_type(type) && !bpf_token_capable(token, CAP_NET_ADMIN))
		goto put_token;
	if (is_perfmon_prog_type(type) && !bpf_token_capable(token, CAP_PERFMON))
		goto put_token;
```

`bpf_cap`은 `CAP_BPF`가 있는지입니다. 읽을 곳은 세 군데입니다.

- `sysctl_unprivileged_bpf_disabled`가 0이 아니면 `CAP_BPF` 없이는 아무것도 로드할 수 없습니다. v7.3의 Kconfig 기본값(`BPF_UNPRIV_DEFAULT_OFF=y`)에서 이 값은 2입니다. 권한 없는 BPF는 기본으로 꺼져 있습니다.
- 꺼져 있지 않더라도 권한 없이 로드할 수 있는 유형은 소켓 필터와 cgroup skb 둘뿐입니다.
- 네트워크 유형은 `CAP_NET_ADMIN`을, 추적 유형은 `CAP_PERFMON`을 더 요구합니다. 커널 메모리를 읽을 수 있는 프로그램과 패킷을 바꿀 수 있는 프로그램의 위험이 다르기 때문입니다.

권한 없는 BPF가 닫힌 까닭은 추측 실행입니다. CPU가 분기를 잘못 예측해 잠깐 실행하는 경로에서는 범위 검사를 건너뛴 접근이 일어날 수 있고, 그 흔적이 캐시에 남습니다. 커널 안에서 원하는 코드를 돌릴 수 있다는 것은 이런 공격을 만들기에 좋은 조건입니다. 검증기가 권한 없는 프로그램에는 방어 코드를 끼워 넣지만, Kconfig 도움말이 밝히듯 대응이 안 된 하드웨어에서는 악용될 수 있습니다. 검증기 자신의 버그도 있습니다. 2만 줄이 넘는 분석기가 범위를 잘못 계산하면 그것이 곧 권한 상승 취약점이 됩니다.

실행 컨텍스트의 제약도 있습니다. 대부분의 훅은 잠들 수 없는 자리에서 불립니다([13장](ch13.html)). 그래서 프로그램은 기본적으로 잠들 수 있는 함수를 부르지 못합니다. `BPF_F_SLEEPABLE`로 로드한 프로그램만 `bpf_copy_from_user()`처럼 잠들 수 있는 헬퍼를 쓸 수 있고, 그런 프로그램은 잠들어도 되는 훅에만 붙습니다. 앞에서 본 `scx_simple`의 `init` 콜백이 `BPF_STRUCT_OPS_SLEEPABLE`로 선언된 것이 그 예입니다.

::: {.lab}
권한 설정과 JIT 상태를 봅니다.

```console
$ sysctl kernel.unprivileged_bpf_disabled
kernel.unprivileged_bpf_disabled = 2
$ cat /proc/sys/net/core/bpf_jit_enable
1
```

sched_ext를 켠 커널(`CONFIG_SCHED_CLASS_EXT`)에서는 안전장치를 직접 시험할 수 있습니다. [5장](ch05.html)의 방법으로 `scx_simple`을 올린 뒤 SysRq-S를 보냅니다.

```console
# cat /sys/kernel/sched_ext/state
enabled
# echo S > /proc/sysrq-trigger
# cat /sys/kernel/sched_ext/state
disabled
```

BPF 스케줄러가 내려가는 동안에도 시스템은 계속 동작합니다. `scx_simple`은 커널이 알려 준 종료 사유를 출력하고 끝납니다.
:::

::: {.note title="토큰과 서명"}
컨테이너 안의 프로세스에 BPF 권한을 일부만 넘기는 장치가 **BPF 토큰**입니다(`kernel/bpf/token.c`). 위 코드의 `bpf_token_capable()`이 그 자리입니다. 토큰이 있으면 능력 검사를 초기 네임스페이스가 아니라 토큰이 속한 유저 네임스페이스 기준으로 합니다. v7.3에는 프로그램 **서명**도 들어 있습니다(`Documentation/bpf/signing.rst`). 서명은 프로그램이 누구에게서 왔고 고쳐지지 않았는지를 확인할 뿐이고, 검증기를 건너뛰게 해 주지는 않습니다.
:::

### 모듈과 무엇이 다른가

| | 커널 모듈 | BPF 프로그램 |
|---|---|---|
| 안전 | 작성자를 믿습니다. 버그는 커널 패닉 | 로드할 때 검증합니다. 통과하지 못하면 거부 |
| 할 수 있는 일 | 커널 코드가 할 수 있는 모든 것 | 훅에서, 헬퍼와 kfunc로 허락된 것만 |
| 커널 버전 | 버전마다 다시 빌드해야 합니다. 내부 API는 안정적이지 않습니다([26장](ch26.html)). | CO-RE로 한 바이너리가 여러 버전에서 돕니다. kfunc는 바뀔 수 있습니다. |
| 올리고 내리기 | `insmod`, `rmmod`. 쓰는 중이면 못 내립니다. | fd와 링크의 수명을 따릅니다. bpffs에 고정하지 않았다면 프로세스와 함께 내려갑니다. |
| 맞는 용도 | 장치 드라이버, 파일시스템 | 관찰, 필터링, 정책 |

BPF는 모듈을 대체하지 않습니다. 하드웨어를 직접 다루는 드라이버는 BPF로 쓸 수 없습니다. BPF가 맡는 것은 **정책**입니다. 어떤 패킷을 버릴지, 어떤 태스크를 먼저 돌릴지, 어떤 접근을 막을지입니다. 메커니즘은 커널이 구현해 두고, 그 메커니즘을 어떻게 쓸지를 실행 중에 바꿀 수 있게 한 것입니다. [22장](ch22.html)의 cgroup이 파일 인터페이스로 하던 일을 코드로 넓힌 셈입니다.

## 정리 {#summary}

- BPF는 유저가 준 코드를 커널 안에서 실행하되, 로드할 때 검증기가 안전을 증명한 것만 받습니다. 실행 중에는 검사가 없습니다.
- 프로그램은 C에서 바이트코드로 컴파일되고, `bpf(BPF_PROG_LOAD)` 한 번 안에서 검증과 JIT를 거친 뒤 훅에 붙습니다. BPF 레지스터는 실제 CPU의 호출 규약에 맞춰져 있습니다.
- 검증기는 모든 경로를 따라가며 레지스터마다 종류, 비트 단위 정보(tnum), 범위(cnum)를 추적합니다. 널일 수 있는 포인터는 분기로 확인하기 전에는 역참조할 수 없습니다.
- 상태는 맵에 둡니다. 커널 함수는 번호가 고정된 헬퍼와, BTF로 기술되고 안정성 약속이 없는 kfunc로 부릅니다.
- BTF는 커널의 타입 정보이고, CO-RE는 로드할 때 구조체 오프셋을 그 커널에 맞게 고칩니다.
- struct_ops는 커널의 ops 구조체를 BPF 프로그램으로 채웁니다. sched_ext는 이것으로 스케줄링 클래스를 BPF에 맡기고, 워치독과 SysRq로 잘못된 스케줄러를 내립니다.
- 로드에는 `CAP_BPF`가 필요하고 권한 없는 BPF는 기본으로 꺼져 있습니다. BPF는 메커니즘이 아니라 정책을 바꾸는 도구입니다.

## 확인 문제 {#quiz}

::: {.q}
`bpf_map_lookup_elem()`의 반환값을 널 확인 없이 역참조하는 프로그램을 검증기가 거부합니다. 검증기는 이 헬퍼가 널을 돌려줄 수 있다는 것을 어디서 알며, `if (val)` 뒤에서는 왜 역참조를 허용합니까?

::: {.a}
헬퍼의 선언 `bpf_map_lookup_elem_proto`의 `.ret_type`이 `RET_PTR_TO_MAP_VALUE_OR_NULL`입니다. 호출 뒤 R0의 종류는 `PTR_TO_MAP_VALUE`에 `PTR_MAYBE_NULL` 플래그가 붙은 것이 되고, `check_mem_access()`는 이 종류의 역참조를 거부합니다. 프로그램이 R0을 0과 비교하는 분기를 지나면 검증기가 두 갈래의 상태를 따로 만들고 `mark_ptr_or_null_reg()`로 고칩니다. 널이 아닌 갈래에서는 플래그가 떨어져 `PTR_TO_MAP_VALUE`가 되므로 역참조가 통과합니다.
:::
:::

::: {.q}
BPF 프로그램이 실행될 때는 배열 접근에 경계 검사가 없습니다. 그런데도 범위를 벗어난 접근이 일어나지 않는다고 말할 수 있는 근거는 무엇입니까? 그 방식의 대가는 무엇입니까?

::: {.a}
검증기가 로드할 때 모든 경로에서 인덱스 레지스터의 범위를 추적하고, 그 범위가 대상 메모리의 크기 안에 있음을 확인한 프로그램만 받기 때문입니다. 범위 정보는 프로그램 안의 비교문과 산술 연산에서 얻습니다. 대가는 검증기가 증명하지 못하면 실제로 안전한 프로그램도 거부된다는 것입니다. 프로그램 작성자는 검증기가 범위를 추론할 수 있도록 명시적인 비교를 넣어야 합니다. 또한 검증기 자체에 버그가 있으면 그 보장이 깨집니다.
:::
:::

::: {.q}
같은 BPF 오브젝트 파일을 `task_struct`의 배치가 서로 다른 두 커널에 로드했는데 둘 다 올바른 필드를 읽었습니다. 무엇이 이를 가능하게 했습니까?

::: {.a}
컴파일러가 필드 접근 명령어마다 CO-RE 재배치 기록을 남겼기 때문입니다. 기록에는 고정 오프셋이 아니라 구조체의 타입과 접근 경로가 들어 있습니다. 로더는 각 커널이 `/sys/kernel/btf/vmlinux`로 내보이는 BTF에서 이름이 같은 구조체와 필드를 찾아 실제 오프셋을 구하고, 로드 전에 명령어의 오프셋을 그 값으로 고칩니다.
:::
:::

::: {.q}
sched_ext 스케줄러의 `enqueue` 콜백이 일부 태스크를 어떤 큐에도 넣지 않는 버그가 있습니다. 검증기는 이 프로그램을 통과시킵니다. 그 뒤 무슨 일이 일어납니까?

::: {.a}
검증기는 메모리 안전과 종료만 확인하므로 정책의 오류는 잡지 못합니다. 큐에 들어가지 못한 태스크는 실행 가능 상태로 남아 CPU를 받지 못합니다. 워치독의 `check_rq_for_timeouts()`가 런큐의 실행 가능 목록을 돌다가 제한 시간을 넘긴 태스크를 발견하고 `SCX_EXIT_ERROR_STALL`로 스케줄러를 종료시킵니다. 종료 과정에서 모든 태스크의 스케줄링 클래스가 원래대로 돌아가므로, 멈춰 있던 태스크는 fair 클래스에서 다시 실행됩니다.
:::
:::

## 용어 {#terms}

::: {.terms}
eBPF
:   커널 안에서 검증된 프로그램을 실행하는 가상 기계와 그 주변 기반. 이 책에서는 줄여서 BPF라고 쓴다.

검증기 (verifier)
:   BPF 프로그램을 로드할 때 모든 실행 경로를 정적으로 분석해 안전을 확인하는 커널 코드.

tnum
:   값의 각 비트가 0인지, 1인지, 알 수 없는지를 추적하는 검증기의 표현.

맵 (map)
:   BPF 프로그램이 호출 사이에 상태를 두고 유저 공간과 데이터를 주고받는 커널 자료구조.

헬퍼 (helper)
:   BPF 프로그램이 부를 수 있도록 번호를 매겨 고정해 둔 커널 함수.

kfunc
:   BTF로 타입이 기술되어 BPF에 열린 커널 함수. ABI 안정성 약속이 없다.

BTF (BPF type format)
:   구조체와 함수의 타입 정보를 담는 형식. 커널이 자기 타입을 이 형식으로 내보인다.

CO-RE
:   로드할 때 BTF로 구조체 오프셋을 재배치해, 한 번 컴파일한 프로그램을 여러 커널에서 돌리는 방식.

훅 (hook)
:   BPF 프로그램이 붙어 실행되는 커널 안의 지점.

struct_ops
:   커널의 함수 포인터 구조체를 BPF 프로그램으로 채워 서브시스템에 등록하는 기능.

트램펄린 (trampoline)
:   커널의 C 호출과 BPF 프로그램 사이를 잇는, 실행 중에 만든 작은 기계어 조각.
:::
