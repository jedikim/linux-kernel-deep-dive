::: {.lead}
커널은 시간에 대해 두 가지를 알아야 합니다. 지금이 몇 시인지, 그리고 정해 둔 때가 되면 누가 깨워 줄 것인지입니다. 오랫동안 두 질문의 답은 하나였습니다. 1초에 수백 번 울리는 타이머 인터럽트, 곧 틱입니다. 그런데 틱만으로는 마이크로초 단위의 타이머를 만들 수 없고, 할 일이 없는 CPU까지 1초에 수백 번 깨우게 됩니다. 이 장은 틱 하나에 묶여 있던 일들이 어떻게 갈라져 나갔는지, 그리고 v7.3에서 틱이 무엇으로 남았는지를 따라갑니다.
:::

::: {.goals}
- clocksource와 clockevent는 무엇이 다르고, 왜 따로 추상화했는가?
- `jiffies`는 무엇을 세고, 넘침은 어떻게 다루는가?
- v7.3에서 틱은 어디에서 오고, 틱 한 번에 어떤 함수가 불리는가?
- 쉬는 CPU와 태스크 하나만 도는 CPU에서 틱을 멈추면 시간은 누가 관리하는가?
- 타이머 휠과 hrtimer는 왜 자료구조가 다른가?
- `clock_gettime()`은 어떻게 시스템 콜 없이 시각을 읽는가?
:::

## 시간으로 하는 두 가지 일 {#two-jobs}

커널이 시간으로 하는 일은 둘로 나뉩니다.

- **시각 읽기**(timekeeping): 지금이 몇 시인지 아는 일입니다. `clock_gettime()`, 파일의 수정 시각, 스케줄러의 실행 시간 계산이 여기에 기댑니다.
- **이벤트 예약**: 정한 시각이 되면 코드가 실행되게 하는 일입니다. 네트워크 타임아웃, `nanosleep()`, 스케줄러의 틱이 여기에 속합니다.

하드웨어도 둘로 나뉩니다. 계속 올라가는 숫자를 읽게 해 주는 카운터가 있고, 정한 시각에 인터럽트를 거는 타이머 장치가 있습니다. 커널은 앞의 것을 **clocksource**, 뒤의 것을 **clockevent**라는 인터페이스로 감쌉니다. 구조체 이름은 `struct clocksource`와 `struct clock_event_device`입니다.

::: {.fig src="clock-source-event.svg"}
시간 하드웨어의 두 역할. 왼쪽은 읽기만 하고, 오른쪽은 예약을 내려보내고 인터럽트를 올려 받습니다.
:::

x86 PC에서 clocksource로 주로 쓰이는 것은 TSC입니다. CPU 안에 있는 64비트 카운터이고 `rdtsc` 명령어 하나로 읽습니다.

```{.c file="arch/x86/kernel/tsc.c" line="1176"}
static struct clocksource clocksource_tsc = {
	.name			= "tsc",
	.rating			= 300,
	.read			= read_tsc,
	.mask			= CLOCKSOURCE_MASK(64),
	.flags			= CLOCK_SOURCE_IS_CONTINUOUS |
				  CLOCK_SOURCE_CAN_INLINE_READ |
				  CLOCK_SOURCE_MUST_VERIFY |
				  CLOCK_SOURCE_HAS_COUPLED_CLOCK_EVENT,
	.id			= CSID_X86_TSC,
	.vdso_clock_mode	= VDSO_CLOCKMODE_TSC,
	/* ... */
};
```

읽을 곳은 세 군데입니다.

- `.read`가 인터페이스의 전부에 가깝습니다. 호출하면 지금의 사이클 값을 돌려줍니다. 사이클을 나노초로 바꾸는 계산은 코어가 합니다.
- `.rating`은 여러 clocksource 가운데 하나를 고르는 점수입니다. v7.3 소스에서 `jiffies`는 1, PIT는 110, ACPI PM 타이머는 200, HPET은 250, TSC는 300입니다. 커널은 가장 높은 것을 씁니다.
- `CLOCK_SOURCE_MUST_VERIFY`는 검증이 필요하다는 표시입니다. 워치독이 주기적으로 다른 clocksource와 견주어 보고, 어긋나면 불안정하다고 표시한 뒤 다음 순위로 바꿉니다.

clockevent 쪽은 CPU마다 하나씩 있는 Local APIC 타이머입니다. APIC 자체는 [9장](ch09.html)에서 다룹니다.

```{.c file="arch/x86/kernel/apic/apic.c" line="496"}
static struct clock_event_device lapic_clockevent = {
	.name				= "lapic",
	.features			= CLOCK_EVT_FEAT_PERIODIC |
					  CLOCK_EVT_FEAT_ONESHOT | CLOCK_EVT_FEAT_C3STOP
					  | CLOCK_EVT_FEAT_DUMMY,
	/* ... */
	.set_state_periodic		= lapic_timer_set_periodic,
	.set_state_oneshot		= lapic_timer_set_oneshot,
	/* ... */
	.set_next_event			= lapic_next_event,
	.broadcast			= lapic_timer_broadcast,
	/* ... */
};
```

- 모드가 둘입니다. `PERIODIC`은 일정한 간격으로 계속 인터럽트를 겁니다. `ONESHOT`은 한 번만 걸고, 다음 것은 `set_next_event()`로 다시 예약해야 합니다.
- `event_handler`가 초기화 목록에 없습니다. 이 필드는 코어가 채웁니다. 장치 드라이버는 인터럽트가 오면 `evt->event_handler(evt)`를 부르기만 합니다. 여기에 어떤 함수가 걸려 있는지가 뒤에서 볼 틱 모드입니다.
- `C3STOP`은 CPU가 깊은 절전 상태에 들어가면 이 타이머도 멈춘다는 뜻입니다. 그런 CPU는 스스로 깨어날 수 없으므로, 멈추지 않는 다른 장치가 대신 인터럽트를 받아 깨워 줍니다. 이것이 **틱 브로드캐스트**(tick broadcast)입니다. `ARAT` 기능이 있는 CPU에서는 타이머가 멈추지 않으므로 `setup_APIC_timer()`가 이 플래그를 지웁니다.

같은 함수는 CPU가 TSC 데드라인 모드를 지원하면 장치 이름을 `lapic-deadline`으로 바꿉니다. 남은 시간을 세는 대신 "TSC가 이 값에 닿으면 인터럽트를 걸어라"고 MSR에 써 넣는 방식입니다.

::: {.design}
`drivers/clocksource/` 아래에만 드라이버 파일이 백 개 가까이 있습니다. 그런데 코어(`kernel/time/`)가 장치에 요구하는 것은 둘뿐입니다. "지금 값을 읽어 달라"와 "이때 인터럽트를 걸어 달라"입니다. 인터페이스를 장치의 기능 목록이 아니라 **코어가 필요한 최소한**에 맞췄기 때문에, 주기 모드만 되는 낡은 칩과 나노초 단위로 예약되는 최신 칩이 같은 코드 위에서 돕니다. 장치마다 다른 능력은 `features` 비트와 `rating` 점수로 알리고, 무엇을 쓸지는 코어가 고릅니다.
:::

## jiffies와 HZ {#jiffies}

**틱**(tick)은 일정한 간격으로 오는 타이머 인터럽트입니다. 1초에 몇 번 오는지가 `HZ`이고 빌드할 때 정합니다.

```{.kconfig file="kernel/Kconfig.hz" line="6"}
choice
	prompt "Timer frequency"
	default HZ_250
```

선택지는 100, 250, 300, 1000이고 기본값은 250입니다. `HZ`가 크면 타임아웃과 스케줄링의 눈금이 촘촘해지고, 그만큼 인터럽트가 자주 옵니다.

**`jiffies`**는 부팅한 뒤로 틱이 몇 번 지났는지 세는 전역 변수입니다. 실체는 64비트 변수 `jiffies_64`이고, `jiffies`는 그 아래쪽 `unsigned long`만큼을 가리키는 이름입니다. 64비트 시스템에서는 둘이 같습니다.

`jiffies`가 32비트인 시스템에서는 `HZ=1000`일 때 49.7일마다 값이 0으로 돌아갑니다. 그래서 두 시각을 `>`로 직접 비교하면 안 됩니다.

```{.c file="include/linux/jiffies.h" line="123"}
#define time_after(a,b)		\
	(typecheck(unsigned long, a) && \
	 typecheck(unsigned long, b) && \
	 ((long)((b) - (a)) < 0))
/* ... */
/*
 * Have the 32-bit jiffies value wrap 5 minutes after boot
 * so jiffies wrap bugs show up earlier.
 */
#define INITIAL_JIFFIES ((unsigned long)(unsigned int) (-300*HZ))
```

`time_after(a, b)`는 두 값을 빼서 **부호 있는 정수**로 본 뒤 음수인지만 확인합니다. 부호 없는 뺄셈은 넘침이 있어도 두 값의 간격을 맞게 내놓으므로, 간격이 표현 범위의 절반보다 작으면 결과가 맞습니다.

::: {.fig src="jiffies-wrap.svg"}
타임아웃을 건 뒤에 `jiffies`가 넘치는 경우. 단순 비교는 넘치기 전의 큰 값을 "이미 지났다"로 잘못 판정합니다.
:::

`INITIAL_JIFFIES`는 이 버그를 일찍 드러내려는 장치입니다. `jiffies`는 0이 아니라 "32비트 값이 넘치기 5분 전"에서 출발합니다. 넘침을 잘못 다루는 코드는 부팅 5분 뒤에 고장 납니다.

::: {.lab}
`HZ`는 유저 공간에 그대로 보이지 않습니다.

```console
$ getconf CLK_TCK
100
$ grep 'CONFIG_HZ=' /boot/config-$(uname -r)
CONFIG_HZ=250
```

첫 번째 값은 `USER_HZ`입니다. `/proc/stat`이나 `times()`처럼 틱 단위로 시간을 알려 주는 인터페이스의 단위이고, 커널의 `HZ`와 상관없이 100입니다. 내부 구현의 숫자가 유저 공간 인터페이스로 새어 나가면 나중에 바꿀 수 없으므로 둘을 갈라 두었습니다.
:::

## 틱 한 번에 일어나는 일 {#tick}

틱이 오면 커널은 두 종류의 일을 합니다. 시스템 전체에서 한 번만 하면 되는 일(`jiffies`를 올리고 시계를 갱신)과, CPU마다 해야 하는 일(지금 돌던 태스크에 대한 처리)입니다. x86-64에서 고해상도 타이머가 켜진 v7.3 커널의 호출 사슬은 다음과 같습니다.

::: {.fig src="tick-path.svg"}
v7.3의 틱 경로. 틱은 타이머 장치의 주기 인터럽트가 아니라 CPU마다 하나씩 있는 hrtimer의 만료입니다.
:::

눈여겨볼 것은 가운데의 `hrtimer_interrupt()`입니다. 타이머 장치는 원샷 모드로 돌고, 인터럽트의 주인은 틱이 아니라 [고해상도 타이머](#hrtimer)입니다. 틱은 그 위에 얹힌 타이머 하나(`tick_sched` 구조체의 `sched_timer`)일 뿐입니다. 콜백은 이렇게 생겼습니다.

```{.c file="kernel/time/tick-sched.c" line="304"}
static enum hrtimer_restart tick_nohz_handler(struct hrtimer *timer)
{
	struct tick_sched *ts =	container_of(timer, struct tick_sched, sched_timer);
	struct pt_regs *regs = get_irq_regs();
	ktime_t now = ktime_get();

	tick_sched_do_timer(ts, now);

	/* ... */
	if (regs)
		tick_sched_handle(ts, regs);
	else
		ts->next_tick = 0;

	/*
	 * In dynticks mode, tick reprogram is deferred:
	 * - to the idle task if in dynticks-idle
	 * - to IRQ exit if in full-dynticks.
	 */
	if (unlikely(tick_sched_flag_test(ts, TS_FLAG_STOPPED)))
		return HRTIMER_NORESTART;

	hrtimer_forward(timer, now, TICK_NSEC);

	return HRTIMER_RESTART;
}
```

`tick_sched_do_timer()`가 그림의 ①이고 `tick_sched_handle()`이 ②입니다. 마지막 두 줄은 타이머를 `TICK_NSEC`(1/HZ초) 뒤로 다시 맞춥니다. 주기적인 틱은 "매번 스스로를 다시 거는 원샷 타이머"입니다. 틱이 멈춘 상태(`TS_FLAG_STOPPED`)라면 다시 걸지 않습니다. [틱 없는 커널 절](#nohz)에서 봅니다.

### 시스템 전체의 시간

`jiffies`를 올리는 일은 CPU 하나만 맡습니다. 그 번호가 전역 변수 `tick_do_timer_cpu`에 들어 있고, `tick_sched_do_timer()`는 자기가 담당일 때만 아래 함수를 부릅니다.

```{.c file="kernel/time/tick-sched.c" line="57"}
static void tick_do_update_jiffies64(ktime_t now)
{
	unsigned long ticks = 1;
	ktime_t delta, nextp;

	/* ... 락 없이 하는 빠른 검사: 다음 틱 시각 전이면 돌아간다 ... */

	raw_spin_lock(&jiffies_lock);
	/* ... */
	write_seqcount_begin(&jiffies_seq);

	delta = ktime_sub(now, tick_next_period);
	if (unlikely(delta >= TICK_NSEC)) {
		/* Slow path for long idle sleep times */
		s64 incr = TICK_NSEC;

		ticks += ktime_divns(delta, incr);
		/* ... */
	}
	/* ... */

	/* Advance jiffies to complete the 'jiffies_seq' protected job */
	jiffies_64 += ticks;
	/* ... */
	write_seqcount_end(&jiffies_seq);

	calc_global_load();

	raw_spin_unlock(&jiffies_lock);
	update_wall_time();
}
```

`jiffies_64 += ticks`에서 더하는 값이 1이 아닐 수 있다는 점이 중요합니다. 이 함수는 "틱이 한 번 왔다"고 가정하지 않습니다. 지금 시각(`now`)과 마지막으로 갱신한 시각의 차이를 틱 길이로 나누어, 지나간 틱 수만큼 한꺼번에 올립니다. 틱이 한참 오지 않았어도 `jiffies`가 맞게 따라옵니다. `jiffies`의 뜻이 "인터럽트가 온 횟수"에서 "지나간 시간을 틱 단위로 나타낸 값"으로 바뀐 것입니다.

`calc_global_load()`는 `uptime`이 보여 주는 부하 평균을 갱신하고, `update_wall_time()`은 [timekeeper](#timekeeping)를 갱신합니다.

### 이 CPU의 태스크

모든 CPU가 틱마다 하는 일은 `update_process_times()`에 모여 있습니다.

```{.c file="kernel/time/timer.c" line="2468"}
void update_process_times(int user_tick)
{
	struct task_struct *p = current;

	/* Note: this timer irq context must be accounted for as well. */
	account_process_tick(p, user_tick);
	run_local_timers();
	rcu_sched_clock_irq(user_tick);
#ifdef CONFIG_IRQ_WORK
	if (in_hardirq())
		irq_work_tick();
#endif
	sched_tick();
	if (IS_ENABLED(CONFIG_POSIX_TIMERS))
		run_posix_cpu_timers();
}
```

| 호출 | 하는 일 |
|---|---|
| `account_process_tick()` | 끊긴 자리가 유저 모드였는지(`user_tick`)에 따라 현재 태스크의 유저 시간이나 시스템 시간에 틱 하나를 더합니다. |
| `run_local_timers()` | 만료된 [타이머 휠](#wheel) 타이머가 있으면 `TIMER_SOFTIRQ`를 올립니다. 콜백은 softirq에서 실행됩니다([11장](ch11.html)). |
| `rcu_sched_clock_irq()` | 이 CPU가 RCU의 정지 상태를 지났는지 확인합니다([16장](ch16.html)). |
| `sched_tick()` | 현재 태스크가 자기 몫을 다 썼는지 보고 재스케줄을 요청합니다([4장](ch04.html)). |
| `run_posix_cpu_timers()` | "CPU 시간을 N초 쓰면 시그널을 보내라"는 타이머를 검사합니다. |

::: {.old}
많은 자료가 틱 핸들러를 이렇게 그립니다. `do_timer(struct pt_regs *regs)`가 `jiffies_64++`를 하고, `update_process_times(user_mode(regs))`를 부르고, `update_times()`가 `wall_jiffies`와 견주어 벽시계를 틱 수만큼 전진시킨 뒤 `calc_load()`를 부릅니다. 2.6 초기의 구조입니다. 이때는 벽시계가 `jiffies`에서 나왔습니다. 틱을 놓치면 시계가 늦어졌습니다.

v7.3의 `do_timer(unsigned long ticks)`는 `jiffies_64 += ticks`와 `calc_global_load()` 두 줄뿐입니다(`kernel/time/timekeeping.c`). `regs` 인자가 없고 태스크에 대한 일도 하지 않습니다. 부르는 곳도 주기 모드의 `tick_periodic()`과 일부 옛 아키텍처용 코드뿐입니다. 원샷 모드로 넘어간 시스템에서는 앞에서 본 `tick_do_update_jiffies64()`가 같은 일을 직접 합니다. 방향도 뒤집혔습니다. 벽시계가 `jiffies`에서 나오는 것이 아니라, clocksource에서 읽은 시각으로 `jiffies`를 얼마나 올릴지 정합니다.
:::

### 주기 모드에서 원샷 모드로

CPU마다 틱을 만들어 줄 clockevent 장치를 하나 골라 `struct tick_device`에 넣어 둡니다. 필드는 장치 포인터(`evtdev`)와 모드(`TICKDEV_MODE_PERIODIC`, `TICKDEV_MODE_ONESHOT`) 둘입니다.

부팅 직후에는 주기 모드입니다. 장치의 `event_handler`는 `tick_handle_periodic()`이고, 이 함수가 `do_timer(1)`과 `update_process_times()`를 부릅니다. 쓸 만한 clocksource와 원샷이 되는 장치가 확인되면 커널은 `hrtimer_switch_to_hres()`로 모드를 바꿉니다. 이때 `event_handler`가 `hrtimer_interrupt()`로 바뀌고, 틱은 `tick_setup_sched_timer()`가 만드는 hrtimer로 옮겨 갑니다. 그림 8-3은 이 전환이 끝난 뒤의 모습입니다.

## 틱 없는 커널 {#nohz}

주기적인 틱은 낭비가 큽니다. 쉬는 CPU는 깊은 절전 상태로 들어가야 전력을 아끼는데, 1초에 수백 번 깨우면 그럴 수가 없습니다. 계산 작업 하나를 쉬지 않고 돌리는 CPU에서는 틱이 올 때마다 작업이 끊깁니다. 틱 모드는 빌드할 때 `HZ_PERIODIC`, `NO_HZ_IDLE`, `NO_HZ_FULL` 셋 가운데 고릅니다.

::: {.fig src="nohz-timeline.svg"}
같은 CPU에서 세 가지 틱 모드가 인터럽트를 거는 시점. 아래로 갈수록 "필요할 때만" 겁니다.
:::

### 쉬는 CPU

`NO_HZ_IDLE`에서 쉬는 CPU는 idle 루프 안에서 `tick_nohz_idle_stop_tick()`을 부릅니다. 이 함수는 틱이 챙겨야 하는 가장 이른 시각, 곧 타이머 휠에 걸린 타이머 가운데 가장 이른 만료를 구합니다. 그 시각이 한 틱보다 멀면 `sched_timer`를 그 시각으로 옮겨 걸고, 걸린 타이머가 없으면 아예 취소합니다. 틱 핸들러는 `TS_FLAG_STOPPED`가 서 있으면 스스로를 다시 걸지 않으므로, 그때까지 틱은 오지 않습니다.

여기서 문제가 하나 생깁니다. `jiffies`를 올리던 담당 CPU가 잠들면 누가 올릴까요. `tick_nohz_stop_tick()`은 자기가 담당이었으면 `tick_do_timer_cpu`에 `TICK_DO_TIMER_NONE`을 써서 자리를 비웁니다. 그 뒤에 틱을 받은 아무 CPU나 `tick_sched_do_timer()`에서 빈자리를 보고 담당을 넘겨받습니다. 모든 CPU가 잠들어도 괜찮습니다. 누군가 인터럽트로 깨어나면 `tick_irq_enter()`가 먼저 `jiffies`를 따라잡습니다. 앞에서 본 "지나간 틱 수만큼 한꺼번에 올리는" 코드가 이때 쓰입니다.

### 태스크 하나만 도는 CPU

`NO_HZ_FULL`은 한 걸음 더 갑니다. 런큐에 태스크가 하나뿐이면 바꿔 줄 상대가 없으므로 스케줄러 틱이 필요 없습니다. 틱을 멈춰도 되는지는 인터럽트에서 돌아갈 때마다 다시 판단합니다.

```{.c file="kernel/time/tick-sched.c" line="381"}
static bool can_stop_full_tick(int cpu, struct tick_sched *ts)
{
	/* ... */
	if (check_tick_dependency(&tick_dep_mask))
		return false;

	if (check_tick_dependency(&ts->tick_dep_mask))
		return false;

	if (check_tick_dependency(&current->tick_dep_mask))
		return false;

	if (check_tick_dependency(&current->signal->tick_dep_mask))
		return false;

	return true;
}
```

검사하는 것은 **틱 의존성**(tick dependency) 비트입니다. 틱이 필요한 쪽이 자기 비트를 세워 둡니다. 범위는 넷입니다. 시스템 전체, 이 CPU, 현재 태스크, 현재 프로세스입니다. 비트의 종류는 `TICK_DEP_BIT_SCHED`(런큐에 태스크가 둘 이상), `TICK_DEP_BIT_POSIX_TIMER`, `TICK_DEP_BIT_PERF_EVENTS`, `TICK_DEP_BIT_RCU` 등입니다. 네 곳이 모두 비어 있을 때만 틱을 멈춥니다. 멈춰도 되는 조건을 한곳에 나열하지 않고, 틱이 필요한 쪽이 스스로 등록하게 한 구조입니다.

틱이 하던 일은 사라지지 않고 다른 CPU로 옮겨 갑니다. `nohz_full=`에 들지 않은 CPU를 **하우스키핑 CPU**(housekeeping CPU)라고 하는데, `jiffies` 갱신 담당은 이쪽에서만 맡습니다. 틱을 멈춘 CPU의 스케줄러 통계는 워크큐가 1초에 한 번 `sched_tick_remote()`로 대신 갱신하고, RCU 콜백은 커널 스레드로 넘어갑니다(`RCU_NOCB_CPU`). CPU 격리 전반은 [7장](ch07.html)에서 다룹니다.

::: {.warn}
`NO_HZ_FULL`은 공짜가 아닙니다. 틱 없이 CPU 시간을 계산하려면 유저 모드와 커널 모드를 오갈 때마다 시각을 기록해야 하므로 시스템 콜과 인터럽트가 무거워집니다. 유저 모드에서 거의 벗어나지 않는 작업을 특정 CPU에 고정할 때 쓰는 기능이고, `nohz_full=` 부팅 인자를 주지 않으면 `NO_HZ_IDLE`과 똑같이 동작합니다.
:::

## 타이머 휠 {#wheel}

커널 코드가 "나중에 이 함수를 불러 달라"고 예약하는 가장 흔한 방법은 `struct timer_list`입니다. 만료 시각을 `jiffies` 단위로 적습니다.

쓰는 법은 세 단계입니다. `timer_setup(&t, 콜백, 0)`으로 초기화하고, `mod_timer(&t, jiffies + 2 * HZ)`로 2초 뒤에 걸고, `timer_delete_sync(&t)`로 지웁니다. 마지막 함수는 콜백이 다른 CPU에서 돌고 있으면 끝날 때까지 기다립니다. 콜백은 softirq 컨텍스트에서 실행되므로 잠들 수 없습니다.

이 타이머들은 수가 많고, 거의 다 만료되기 전에 취소됩니다. TCP의 재전송 타이머가 그렇습니다. 패킷이 제때 도착하면 쓸모가 없습니다. 그러니 넣고 빼는 연산이 빨라야 합니다. 정렬된 트리에 넣으면 O(log n)이 듭니다. **타이머 휠**(timer wheel)은 만료 시각을 배열 인덱스로 바꿔 O(1)에 넣습니다.

::: {.fig src="timer-wheel.svg"}
타이머 휠의 레벨. 만료가 먼 타이머일수록 폭이 넓은 칸에 들어가고, 그만큼 덜 정확하게 울립니다.
:::

구조는 소스의 주석에 표로 정리되어 있습니다.

```{.c file="kernel/time/timer.c" line="104"}
 * HZ 1000 steps
 * Level Offset  Granularity            Range
 *  0      0         1 ms                0 ms -         63 ms
 *  1     64         8 ms               64 ms -        511 ms
 *  2    128        64 ms              512 ms -       4095 ms (512ms - ~4s)
 *  3    192       512 ms             4096 ms -      32767 ms (~4s - ~32s)
 *  4    256      4096 ms (~4s)      32768 ms -     262143 ms (~32s - ~4m)
```

레벨마다 버킷이 64개 있고, 한 레벨 올라갈 때마다 칸의 폭이 8배가 됩니다. 버킷은 타이머의 연결 리스트입니다. 타이머를 걸 때 만료까지 남은 틱 수로 레벨을 고르고, 다음 함수로 그 레벨 안의 칸을 정합니다.

```{.c file="kernel/time/timer.c" line="524"}
static inline unsigned calc_index(unsigned long expires, unsigned lvl,
				  unsigned long *bucket_expiry)
{

	/*
	 * The timer wheel has to guarantee that a timer does not fire
	 * early. Early expiry can happen due to:
	 * - Timer is armed at the edge of a tick
	 * - Truncation of the expiry time in the outer wheel levels
	 *
	 * Round up with level granularity to prevent this.
	 */
	expires = (expires >> LVL_SHIFT(lvl)) + 1;
	*bucket_expiry = expires << LVL_SHIFT(lvl);
	return LVL_OFFS(lvl) + (expires & LVL_MASK);
}
```

시프트 한 번, 덧셈 한 번, 마스크 한 번입니다. `+ 1`은 올림입니다. 타이머는 요청한 시각보다 일찍 울리면 안 되므로 항상 다음 칸에 넣습니다. 그 대가로 최대 한 칸의 폭만큼 늦을 수 있습니다. 10초 뒤를 요청한 타이머는 레벨 3에 들어가 최대 0.5초쯤 늦게 울립니다.

::: {.design}
이 구조는 **정확도를 버리고 속도를 얻은** 선택입니다. 근거는 쓰임새에 대한 관찰입니다. 소스 주석은 타이머 휠의 주된 용도가 타임아웃이고, 타임아웃은 대부분 만료 전에 취소되며, 만료되었다면 이미 정상 동작이 어긋난 상황이라 조금 늦어도 문제가 없다고 적습니다. 흔한 경우(넣었다가 빼기)를 가장 싸게 만들고, 드문 경우(실제 만료)의 품질을 낮췄습니다. 정확한 만료가 필요한 쓰임새는 다른 도구(hrtimer)로 보냈습니다. 하나의 자료구조로 모든 요구를 만족시키려 하지 않은 것이 요점입니다.
:::

만료 처리는 `TIMER_SOFTIRQ`에서 합니다. 레벨 0은 틱마다, 레벨 1은 8틱마다, 레벨 2는 64틱마다 한 칸씩 차례가 옵니다. 차례가 온 칸의 타이머는 모두 만료된 것이므로 리스트를 통째로 떼어 콜백을 차례로 부릅니다.

::: {.old}
옛 자료의 타이머 휠은 `tv1`부터 `tv5`까지 다섯 배열로 되어 있고, 아래 배열이 한 바퀴 돌 때마다 위 배열의 타이머를 아래로 옮겨 담는 **캐스케이드**(cascade)를 합니다. 정확한 틱에 만료시키기 위한 구조였지만 타이머를 한꺼번에 옮기는 비용에 상한이 없었습니다. v7.3의 휠은 타이머를 옮기지 않습니다. 4.8에서 바뀌었습니다.

API 이름도 달라졌습니다. `init_timer()`와 `setup_timer()`는 4.15에서 `timer_setup()`으로 정리되었고, 콜백의 인자는 `unsigned long data`에서 `struct timer_list *`로 바뀌었습니다. `del_timer()`와 `del_timer_sync()`는 6.15에서 `timer_delete()`와 `timer_delete_sync()`로 완전히 바뀌어 옛 이름이 사라졌습니다. 콜백에서 바깥 구조체를 얻는 `from_timer()`는 v7.3에서 `timer_container_of()`입니다.
:::

틱 없는 커널에서 CPU마다 휠은 셋입니다. 이 CPU에 고정된 타이머용(`BASE_LOCAL`), 어느 CPU에서 만료되어도 되는 타이머용(`BASE_GLOBAL`), 쉬는 CPU를 깨우지 않아도 되는 타이머용(`BASE_DEF`)입니다. 자기 타이머 때문에 깨어나야 하는 CPU는 깊이 잠들 수 없습니다. 그래서 고정되지 않은 타이머는 CPU가 잠들 때 **타이머 마이그레이션 계층**(`kernel/time/timer_migration.c`)에 맡깁니다. CPU들을 8개씩 그룹으로 묶은 트리이고, 그룹마다 깨어 있는 CPU 하나가 잠든 CPU들의 타이머를 대신 만료시킵니다.

## 고해상도 타이머 {#hrtimer}

타이머 휠의 눈금은 틱입니다. `HZ=250`이면 4ms보다 짧은 간격을 표현할 수 없습니다. 오디오 재생, 실시간 제어, `nanosleep()`의 마이크로초 단위 요청에는 모자랍니다. **hrtimer**(high-resolution timer)는 만료 시각을 나노초 단위의 `ktime_t`로 적고, 그 시각에 맞춰 타이머 장치를 직접 예약합니다.

요구가 다르니 자료구조도 다릅니다. hrtimer는 대부분 실제로 만료되고, 만료 순서가 정확해야 합니다. 그래서 만료 시각순으로 정렬한 레드블랙 트리에 넣고, 가장 이른 타이머인 맨 왼쪽 노드를 가리키는 포인터를 따로 둡니다.

::: {.fig src="hrtimer-next-event.svg"}
hrtimer의 한 바퀴. 가장 이른 만료 시각 하나만 장치에 예약하고, 인터럽트가 오면 다음으로 이른 것을 다시 예약합니다.
:::

트리는 CPU마다, 그리고 **클록 베이스**마다 따로 있습니다. 클록은 `CLOCK_MONOTONIC`, `CLOCK_REALTIME`, `CLOCK_BOOTTIME`, `CLOCK_TAI` 넷이고, 타이머를 만들 때 고릅니다. 누군가 벽시계를 한 시간 앞으로 돌리면 `REALTIME` 타이머는 그만큼 일찍 만료되어야 하지만 `MONOTONIC` 타이머는 영향을 받지 않아야 하므로 트리를 섞을 수 없습니다.

타이머 장치가 인터럽트를 걸면 다음 함수가 불립니다. 앞 절에서 본 `event_handler`입니다.

```{.c file="kernel/time/hrtimer.c" line="2220"}
void hrtimer_interrupt(struct clock_event_device *dev)
{
	struct hrtimer_cpu_base *cpu_base = this_cpu_ptr(&hrtimer_bases);
	/* ... */
	raw_spin_lock_irqsave(&cpu_base->lock, flags);
	entry_time = now = hrtimer_update_base(cpu_base);
retry:
	/* ... */
	if (!ktime_before(now, cpu_base->softirq_expires_next)) {
		cpu_base->softirq_expires_next = KTIME_MAX;
		cpu_base->softirq_activated = true;
		raise_timer_softirq(HRTIMER_SOFTIRQ);
	}

	__hrtimer_run_queues(cpu_base, now, flags, HRTIMER_ACTIVE_HARD);

	/* ... */
	now = hrtimer_update_base(cpu_base);
	expires_next = hrtimer_update_next_event(cpu_base);
	cpu_base->hang_detected = false;
	if (expires_next < now) {
		if (++retries < 3) {
			cpu_base->nr_retries++;
			goto retry;
		}
		/* ... */
	}

	hrtimer_interrupt_rearm(cpu_base, expires_next);
	raw_spin_unlock_irqrestore(&cpu_base->lock, flags);
}
```

읽을 곳은 네 군데입니다.

- **콜백이 도는 컨텍스트가 둘입니다.** `HRTIMER_MODE_HARD`로 건 타이머는 여기, hardirq 안에서 바로 실행됩니다. `HRTIMER_MODE_SOFT`로 건 타이머는 `HRTIMER_SOFTIRQ`를 올려 두고 인터럽트가 끝난 뒤 실행됩니다. 클록 베이스가 4개가 아니라 8개인 까닭입니다. `PREEMPT_RT` 커널에서는 `HARD`를 명시하지 않은 타이머가 모두 soft 쪽으로 갑니다.
- **콜백을 부르는 동안에는 락을 풉니다.** `__run_hrtimer()`가 `cpu_base->lock`을 풀고 콜백을 부른 뒤 다시 잡습니다. 콜백이 `HRTIMER_RESTART`를 돌려주면 타이머를 트리에 다시 넣습니다. 틱이 이 방식으로 주기를 만듭니다.
- **`retry`.** 콜백을 실행하는 사이에 다음 타이머의 만료 시각이 지났으면 인터럽트를 다시 받지 않고 한 번 더 돕니다. 핸들러에서 빠져나오지 못하는 일이 없도록 세 번까지만 합니다.
- **마지막 줄의 `hrtimer_interrupt_rearm()`은 장치를 바로 다시 맞추지 않습니다.**

마지막 항목은 최근의 변화입니다. `CONFIG_HRTIMER_REARM_DEFERRED`가 켜진 빌드(x86-64에서는 기본)에서 이 함수는 다음 만료 시각을 적어 두고 스레드 플래그 `TIF_HRTIMER_REARM`만 세웁니다. 장치를 실제로 맞추는 `__hrtimer_rearm_deferred()`는 인터럽트에서 돌아가는 길에, 재스케줄이 끝난 뒤에 불립니다. [6장](ch06.html)에서 본 복귀 경로의 그 자리입니다.

미루는 이유는 스케줄러에 있습니다. 타이머 인터럽트 뒤에는 태스크가 바뀌는 일이 잦고, 스케줄러는 새 태스크의 슬라이스가 끝나는 시각에 맞춰 자기 hrtimer(`hrtick`)를 다시 겁니다. 인터럽트 안에서 장치를 맞추고 곧이어 스케줄러 때문에 또 맞추면 장치에 두 번 써야 합니다. 모든 것이 정해진 뒤에 한 번만 쓰도록 순서를 바꾼 것입니다. 이 옵션이 켜진 v7.3 빌드에서는 스케줄러의 `HRTICK` 기능도 기본으로 켜집니다(`kernel/sched/features.h`).

타이머를 쓰는 쪽의 API는 타이머 휠과 닮았습니다. 틱 자신이 좋은 예입니다. `tick_setup_sched_timer()`는 `hrtimer_setup(&ts->sched_timer, tick_nohz_handler, CLOCK_MONOTONIC, HRTIMER_MODE_ABS_HARD)`로 타이머를 만들고 `hrtimer_start_expires()`로 겁니다. 콜백, 기준 클록, 모드를 한 번에 받습니다. `hrtimer_init()`을 부른 뒤 `timer->function`을 따로 대입하던 예전 방식은 6.15에서 사라졌습니다.

::: {.myth}
"`HZ`가 타이머의 해상도다." 타이머 휠에는 맞고 hrtimer에는 틀립니다. 고해상도 모드에서 `clock_getres(CLOCK_MONOTONIC)`이 돌려주는 값은 `HZ`와 상관없이 1나노초입니다. `HZ=100`인 커널에서도 `nanosleep()`은 마이크로초 단위로 깨워 줍니다. `HZ`가 정하는 것은 `jiffies`를 쓰는 타임아웃의 눈금과 스케줄러 틱의 주기입니다.
:::

## 지금 몇 시인가 {#timekeeping}

clocksource는 사이클 값만 줍니다. 이것을 "1970년부터 몇 나노초"로 바꾸려면 기준점과 환산 비율이 필요합니다. 이 값들을 쥐고 있는 것이 `struct timekeeper`입니다.

계산은 "기준 시각에, 마지막 갱신 뒤로 지나간 사이클을 나노초로 바꿔 더한다"입니다. `cycle_last`는 마지막으로 timekeeper를 갱신했을 때의 사이클 값이고, `mult`와 `shift`는 사이클을 나노초로 바꾸는 비율을 "곱하고 시프트"로 나타낸 것입니다. 나눗셈을 피하려는 표현입니다.

```{.c file="kernel/time/timekeeping.c" line="456"}
static __always_inline u64 timekeeping_cycles_to_ns(const struct tk_read_base *tkr, u64 cycles)
{
	/* Calculate the delta since the last update_wall_time() */
	u64 mask = tkr->mask, delta = (cycles - tkr->cycle_last) & mask;

	/* ... 넘침과 뒤로 간 값 처리 ... */

	return ((delta * tkr->mult) + tkr->xtime_nsec) >> tkr->shift;
}
```

이 식의 값들은 틱마다 `update_wall_time()`이 고칩니다. 그 사이에 다른 CPU가 시각을 읽으면 고치다 만 값을 볼 수 있습니다. 읽는 쪽은 락을 잡지 않고 **시퀀스 카운터**(sequence counter)로 이것을 피합니다.

```{.c file="kernel/time/timekeeping.c" line="992"}
ktime_t ktime_get(void)
{
	struct timekeeper *tk = &tk_core.timekeeper;
	unsigned int seq;
	ktime_t base;
	u64 nsecs;

	/* ... */
	do {
		seq = read_seqcount_begin(&tk_core.seq);
		base = tk->tkr_mono.base;
		nsecs = timekeeping_get_ns(&tk->tkr_mono);

	} while (read_seqcount_retry(&tk_core.seq, seq));

	return ktime_add_ns(base, nsecs);
}
```

쓰는 쪽은 고치기 전후에 카운터를 올립니다. 읽는 쪽은 읽기 전후의 카운터가 같은지 확인하고, 다르면 다시 읽습니다. 읽는 쪽이 공유 메모리에 아무것도 쓰지 않으므로 CPU가 수백 개여도 서로 방해하지 않습니다. 읽기는 매우 잦고 쓰기는 틱마다 한 번뿐이라 이 방식이 잘 맞습니다. seqcount의 내부는 [14장](ch14.html)에서 봅니다.

커널이 내주는 시계는 여러 개이고, 전부 같은 카운터에서 나옵니다. 다른 것은 기준점과 보정뿐입니다.

| 클록 | 뜻 | 벽시계를 고치면 | 절전 중 |
|---|---|---|---|
| `CLOCK_REALTIME` | 1970년부터의 시각(벽시계) | 따라 바뀜 | 흐름 |
| `CLOCK_MONOTONIC` | 부팅 뒤 흐른 시간. 뒤로 가지 않음 | 안 바뀜 | 멈춤 |
| `CLOCK_BOOTTIME` | `MONOTONIC`에 절전 시간을 더한 것 | 안 바뀜 | 흐름 |
| `CLOCK_MONOTONIC_RAW` | NTP 보정을 하지 않은 `MONOTONIC` | 안 바뀜 | 멈춤 |
| `CLOCK_TAI` | 윤초가 없는 국제원자시 | 따라 바뀜 | 흐름 |

`timekeeper`는 `MONOTONIC`을 기본으로 두고 나머지를 오프셋(`offs_real`, `offs_boot`, `offs_tai`)으로 구합니다. NTP는 시계가 조금 빠르거나 느릴 때 시각을 건너뛰게 하지 않고 `mult`를 조금 고쳐 흐르는 속도를 바꿉니다. 그래서 `MONOTONIC`은 뒤로 가지 않습니다. 경과 시간은 `REALTIME`이 아니라 `MONOTONIC`으로 재야 합니다.

### 시스템 콜 없이 시각 읽기

유저 프로그램의 `clock_gettime()`은 대부분 커널에 들어오지 않습니다. 커널은 모든 프로세스의 주소 공간에 작은 공유 라이브러리(**vDSO**)와 읽기 전용 데이터 페이지를 매핑해 둡니다. 데이터 페이지에는 위 식에 필요한 값이 들어 있고, `update_wall_time()`이 timekeeper를 고칠 때마다 `update_vsyscall()`이 이 페이지도 함께 고칩니다.

::: {.fig src="clock-read-path.svg"}
시계를 읽는 두 길. 유저 공간의 길은 커널 모드로 들어가지 않고 끝납니다.
:::

vDSO의 `do_hres()`는 `ktime_get()`과 같은 일을 유저 모드에서 합니다. 시퀀스 카운터를 읽고, `rdtsc`로 TSC를 읽고, 곱하고 시프트하고, 카운터가 바뀌었으면 다시 합니다. `clocksource_tsc`의 `.vdso_clock_mode = VDSO_CLOCKMODE_TSC`가 "이 카운터는 유저 모드에서 읽을 수 있다"는 표시입니다. HPET처럼 이 표시가 없는 clocksource가 선택되면 vDSO는 진짜 시스템 콜로 넘어가고, 시각 읽기가 훨씬 느려집니다. vDSO가 매핑되고 호출되는 방식은 [19장](ch19.html)에서 다룹니다.

::: {.note title="보조 클록"}
v7.3의 `timekeeper_data[]`는 배열입니다. 0번이 지금까지 본 코어 timekeeper이고, `CONFIG_POSIX_AUX_CLOCKS`를 켜면 **보조 클록**(auxiliary clock)용 timekeeper가 최대 8개 붙습니다. 클록 ID는 `CLOCK_AUX`부터입니다. NTP가 다스리는 시스템 시계와 따로 맞출 수 있는 시계이고, 한 기계가 서로 동기화되지 않은 여러 PTP 시간 영역에 걸쳐 있을 때 씁니다. 6.17에서 들어왔고 vDSO로도 읽을 수 있습니다.
:::

## 잠들기 {#sleep}

"일정 시간 기다리기"는 두 타이머 가운데 하나에 얹혀 있습니다. 어느 쪽인지에 따라 정확도가 다릅니다.

| 함수 | 바탕 | 눈금 |
|---|---|---|
| `schedule_timeout(jiffies)` | 타이머 휠 | 틱 |
| `msleep(ms)` | `schedule_timeout()` | 틱 |
| `usleep_range(min, max)` | hrtimer | 마이크로초, 범위 지정 |
| `nanosleep()`, `clock_nanosleep()` | hrtimer | 나노초 + 타이머 슬랙 |
| `udelay(us)`, `ndelay(ns)` | 반복문(잠들지 않음) | 원자적 컨텍스트에서도 됨 |

`schedule_timeout()`은 스택에 `timer_list`를 하나 만들어 걸고 `schedule()`을 부릅니다. 콜백은 `wake_up_process()` 한 줄입니다. `msleep(1)`은 이름과 달리 `HZ=250`에서 4~8ms를 잡니다. 틱 단위로 올림하고, 휠이 한 칸 더 올리기 때문입니다.

드라이버 작성자가 이 표를 외울 필요가 없도록 `fsleep()`이 있습니다.

```{.c file="include/linux/delay.h" line="129"}
static inline void fsleep(unsigned long usecs)
{
	if (usecs <= 10)
		udelay(usecs);
	else if (usecs < USLEEP_RANGE_UPPER_BOUND)
		usleep_range(usecs, usecs + (usecs >> max_slack_shift));
	else
		msleep(DIV_ROUND_UP(usecs, USEC_PER_MSEC));
}
```

10마이크로초 이하는 타이머를 거는 비용이 더 크므로 헛돌며 기다립니다. 그보다 길고 틱 몇 개보다 짧으면 hrtimer를 쓰되 25%의 여유를 줍니다. 충분히 길면 싼 타이머 휠로 갑니다.

여유를 주는 까닭은 인터럽트를 줄이기 위해서입니다. hrtimer는 만료 시각을 범위(가장 이른 시각과 가장 늦은 시각)로 가집니다. 범위가 겹치는 타이머들은 인터럽트 한 번에 함께 처리됩니다. 유저 공간의 `nanosleep()`에는 이 범위가 **타이머 슬랙**(timer slack)으로 붙습니다. 기본값은 50마이크로초이고 `prctl(PR_SET_TIMERSLACK)`으로 바꿉니다. 실시간 정책의 태스크는 슬랙이 0입니다.

::: {.lab}
타이머 하드웨어와 타이머 목록을 봅니다.

```console
$ cd /sys/devices/system/clocksource/clocksource0
$ cat current_clocksource available_clocksource
tsc
tsc hpet acpi_pm

$ grep LOC /proc/interrupts
 LOC:     412345     398211  ...   Local timer interrupts

# grep -E 'Clock Event Device|event_handler' /proc/timer_list | sort | uniq -c
      8 Clock Event Device: lapic-deadline
      8  event_handler:  hrtimer_interrupt
      ...
```

`LOC` 줄을 1초 간격으로 두 번 읽어 차이를 내 보세요. 쉬는 CPU에서는 `HZ`보다 훨씬 작은 값이 나옵니다. 틱이 멈춰 있다는 뜻입니다. `event_handler`가 `hrtimer_interrupt`이면 고해상도 모드이고, `tick_handle_periodic`이면 주기 모드입니다.

어떤 hrtimer가 자주 만료되는지는 추적점으로 셉니다.

```console

^C

@[tick_nohz_handler]: 9214
...
```

`tick_nohz_handler`가 틱이고 `hrtimer_wakeup`이 잠든 태스크를 깨우는 만료입니다. `tracepoint:timer:tick_stop`은 틱을 멈추지 못한 이유(틱 의존성)를 알려 줍니다.

## 정리 {#summary}

- 시간 하드웨어는 두 인터페이스로 추상화됩니다. 카운터를 읽는 clocksource와 인터럽트를 예약하는 clockevent입니다.
- `jiffies`는 틱 단위로 센 경과 시간입니다. 비교는 `time_after()`류로 합니다. v7.3에서는 인터럽트 횟수가 아니라 clocksource로 잰 시간에서 계산됩니다.
- 고해상도 모드에서 틱은 CPU마다 하나씩 있는 hrtimer(`sched_timer`)입니다. 콜백 `tick_nohz_handler()`가 `jiffies` 갱신과 `update_process_times()`를 부릅니다.
- `NO_HZ_IDLE`은 쉬는 CPU의 틱을, `NO_HZ_FULL`은 태스크 하나만 도는 CPU의 틱까지 멈춥니다. 시간 관리 담당은 깨어 있는 CPU로 넘어갑니다.
- 타이머 휠은 대부분 취소되는 타임아웃을 위한 구조입니다. O(1)에 넣고 빼는 대신 먼 타이머는 덜 정확합니다.
- hrtimer는 실제로 만료되는 정밀한 타이머를 위한 구조입니다. 정렬된 트리에서 가장 이른 만료 하나만 장치에 예약합니다.
- 시각은 `기준 + (사이클 차이 × mult) >> shift`로 계산하고, 시퀀스 카운터로 보호합니다. vDSO는 같은 계산을 유저 모드에서 합니다.

## 확인 문제 {#quiz}

::: {.q}
드라이버에 `if (jiffies > dev->deadline)`이라는 코드가 있습니다. 32비트 시스템에서 어떤 상황에 잘못 동작합니까? `INITIAL_JIFFIES`는 이 버그를 찾는 데 어떻게 도움이 됩니까?

::: {.a}
`deadline`을 계산한 덧셈이 넘쳐 작은 값이 된 경우입니다. `jiffies`는 아직 넘치기 전의 큰 값이므로 비교가 곧바로 참이 되어, 시간이 남았는데도 만료로 판정합니다. `time_after(jiffies, dev->deadline)`은 두 값의 차이를 부호 있는 정수로 보므로 맞게 판정합니다. `INITIAL_JIFFIES`는 `jiffies`의 아래 32비트가 부팅 5분 뒤에 넘치도록 잡아 둔 초기값이어서, 이런 코드는 49일 뒤가 아니라 부팅 직후의 시험에서 고장 납니다.
:::
:::

::: {.q}
`NO_HZ_IDLE` 커널에서 모든 CPU가 10초 동안 잠들어 있었습니다. 그동안 틱 인터럽트는 한 번도 오지 않았습니다. 깨어난 뒤 `jiffies`는 어떻게 맞는 값이 됩니까?

::: {.a}
`tick_do_update_jiffies64()`는 지금 시각과 마지막 갱신 시각의 차이를 `TICK_NSEC`로 나눠 그만큼을 한꺼번에 더합니다. 지금 시각은 clocksource에서 읽으므로 인터럽트가 오지 않은 동안에도 흐릅니다. 잠들기 전에 담당 CPU는 `tick_do_timer_cpu`를 `TICK_DO_TIMER_NONE`으로 비워 두고, 처음 깨어난 CPU가 인터럽트 진입 길(`tick_irq_enter()`)에서 `jiffies`를 따라잡습니다.
:::
:::

::: {.q}
TCP 재전송 타이머는 타이머 휠에, `nanosleep()`은 hrtimer에 얹혀 있습니다. 반대로 하면 각각 무엇이 나빠집니까?

::: {.a}
재전송 타이머를 hrtimer에 얹으면, 걸었다가 거의 다 취소되는 타이머를 레드블랙 트리에 O(log n)으로 넣고 빼야 하고, 가장 이른 타이머가 바뀔 때마다 타이머 장치를 다시 예약해야 합니다. 얻는 것은 필요 없는 정밀도입니다. `nanosleep()`을 타이머 휠에 얹으면 눈금이 틱이 되어 `HZ=250`에서 4ms보다 짧은 잠을 표현할 수 없고, 먼 만료는 높은 레벨에 들어가 한 칸의 폭만큼 늦어질 수 있습니다.
:::
:::

::: {.q}
`ktime_get()`은 락을 잡지 않습니다. 다른 CPU가 `update_wall_time()`으로 `mult`와 `cycle_last`를 고치는 도중에 읽어도 틀린 시각을 돌려주지 않는 까닭은 무엇입니까?

::: {.a}
시퀀스 카운터 때문입니다. 쓰는 쪽은 고치기 시작할 때와 끝낼 때 `tk_core.seq`를 올립니다. 읽는 쪽은 `read_seqcount_begin()`으로 카운터를 읽고, 값을 읽어 계산한 뒤, `read_seqcount_retry()`로 카운터가 그대로인지 확인합니다. 그사이에 쓰기가 있었으면 카운터가 달라져 있으므로 반복문을 다시 돕니다. 고치다 만 값으로 계산한 결과는 버려집니다.
:::
:::

## 용어 {#terms}

::: {.terms}
틱 (tick)
:   일정한 간격으로 오는 타이머 인터럽트. 주기는 1/HZ초.

jiffies
:   부팅 뒤 흐른 시간을 틱 단위로 센 전역 변수.

clocksource
:   계속 올라가는 카운터를 읽는 인터페이스. 시각 계산의 바탕.

clockevent
:   정한 시각에 인터럽트를 거는 타이머 장치의 인터페이스(`struct clock_event_device`).

타이머 휠 (timer wheel)
:   `jiffies` 단위 타이머를 만료 시각별 버킷 배열에 담는 자료구조.

hrtimer
:   나노초 단위 만료 시각을 가진 고해상도 타이머.

틱 의존성 (tick dependency)
:   `NO_HZ_FULL`에서 틱을 멈추면 안 되는 이유를 나타내는 비트.

하우스키핑 CPU (housekeeping CPU)
:   틱을 멈춘 CPU들을 대신해 시간 관리와 커널 잡무를 맡는 CPU.

timekeeper
:   사이클 값을 시각으로 바꾸는 기준점과 환산 비율을 담은 구조체.

vDSO
:   커널이 모든 프로세스에 매핑해 주는 작은 공유 라이브러리. 시스템 콜 없이 시각을 읽게 한다.
:::
