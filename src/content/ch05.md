::: {.lead}
"CPU를 공정하게 나눈다"는 말은 쉽지만, 스케줄러는 그것을 비교할 수 있는 숫자로 바꿔야 합니다. CFS는 그 숫자로 가상 실행 시간 하나를 썼습니다. 가장 적게 돈 태스크를 고른다는 규칙은 16년을 버텼지만, "CPU를 많이 쓰지는 않아도 깨어나면 바로 돌아야 한다"는 요구를 담을 자리가 없었습니다. 그 빈자리를 메우던 휴리스틱을 걷어 내고 숫자를 하나 더 들인 것이 EEVDF입니다. 이 장은 그 숫자들이 `kernel/sched/fair.c`에서 어떻게 계산되는지 읽고, fair 클래스 위아래에 놓인 클래스들을 훑습니다.
:::

::: {.goals}
- nice 값은 CPU 시간의 비율로 어떻게 바뀌는가?
- lag, 자격, 가상 데드라인은 각각 무엇이고 코드에서 어떻게 계산되는가?
- fair 클래스의 RB 트리는 무엇으로 정렬되어 있는가?
- slice를 줄이면 무엇이 달라지고 무엇이 그대로인가?
- cgroup 계층은 태스크를 고르는 데 어떻게 반영되는가?
- RT 태스크가 CPU를 독점해도 일반 태스크가 굶지 않는 까닭은 무엇인가?
:::

## 가상 실행 시간 {#vruntime}

CFS(Completely Fair Scheduler)의 출발점은 존재하지 않는 CPU입니다. 태스크 n개를 정말로 동시에, 각각 1/n의 속도로 실행하는 CPU입니다. 실제 CPU는 한 번에 하나만 실행하므로, 스케줄러는 **지금까지 가장 덜 받은 태스크**를 골라 이상에 가까이 갑니다.

태스크마다 받아야 할 몫이 다를 수 있습니다. 몫은 가중치로 정합니다. 가중치가 w인 태스크의 몫은 w를 실행 가능한 모든 태스크의 가중치 합으로 나눈 값입니다. 그러면 "덜 받았다"를 비교하려면 실행 시간을 가중치로 나눠야 합니다. 이 값이 **가상 실행 시간**(virtual runtime), `vruntime`입니다.

```{.c file="kernel/sched/fair.c" line="300"}
/*
 * delta /= w
 */
static inline u64 calc_delta_fair(u64 delta, struct sched_entity *se)
{
	if (se->h_load.weight != NICE_0_LOAD)
		delta = __calc_delta(delta, NICE_0_LOAD, &se->h_load);

	return delta;
}
```

[4장](ch04.html)에서 본 실행 시간 장부가 `delta_exec`을 내놓으면, fair 클래스는 `curr->vruntime += calc_delta_fair(delta_exec, curr)`로 가상 시간을 더합니다. 계산은 `delta × NICE_0_LOAD / weight`입니다. nice 0 태스크의 `vruntime`은 실제 시간과 같은 속도로 흐르고, 가중치가 두 배인 태스크는 절반 속도로 흐릅니다. 가중치의 필드 이름이 `h_load`인 까닭은 [그룹 스케줄링 절](#group)에서 나옵니다.

가중치는 nice 값에서 나옵니다.

```{.c file="kernel/sched/core.c" line="10673"}
const int sched_prio_to_weight[40] = {
 /* -20 */     88761,     71755,     56483,     46273,     36291,
 /* -15 */     29154,     23254,     18705,     14949,     11916,
 /* -10 */      9548,      7620,      6100,      4904,      3906,
 /*  -5 */      3121,      2501,      1991,      1586,      1277,
 /*   0 */      1024,       820,       655,       526,       423,
 /*   5 */       335,       272,       215,       172,       137,
 /*  10 */       110,        87,        70,        56,        45,
 /*  15 */        36,        29,        23,        18,        15,
};
```

이웃한 값의 비가 약 1.25입니다. nice가 1 차이 나는 두 태스크가 CPU 하나를 두고 다투면 55% 대 45%로 나뉩니다. 어느 nice 값에서 출발하든 한 단계의 효과가 같도록 등비수열로 만든 표입니다. nice 0과 nice 5라면 1024 대 335이므로 약 75% 대 25%입니다.

::: {.fig src="vruntime-two-tasks.svg"}
가중치가 3 대 1인 두 태스크. 실제 실행 시간은 3 대 1로 나뉘지만 `vruntime`은 나란히 올라갑니다. 스케줄러의 일은 `vruntime`을 같게 유지하는 것입니다.
:::

CFS의 규칙은 한 줄이었습니다. **`vruntime`이 가장 작은 태스크를 고른다.** 실행 가능한 태스크를 `vruntime` 순서의 RB 트리에 넣어 두고 맨 왼쪽 노드를 꺼냈습니다.

## CFS가 남긴 문제 {#cfs-limit}

`vruntime` 하나는 "얼마나 많이"를 표현합니다. "얼마나 빨리"는 표현하지 못합니다.

오디오 스레드를 생각해 봅시다. 10ms마다 깨어나 0.2ms 일하고 잠듭니다. CPU는 2%만 씁니다. 이 스레드에 필요한 것은 큰 몫이 아니라 깨어난 직후의 CPU입니다. nice를 낮추면 몫이 커질 뿐입니다. 실시간 정책을 주면 되지만 특권이 필요하고, 버그가 나면 시스템을 멈출 수 있습니다.

CFS는 이 틈을 휴리스틱으로 메웠습니다. 잠들었다 깬 태스크의 `vruntime`을 조금 깎아 먼저 돌게 하고, 깨어난 태스크가 현재 태스크를 밀어내려면 `vruntime` 차이가 어느 문턱을 넘어야 한다는 식입니다. 문턱마다 조정값이 붙었습니다. 한 워크로드에 맞추면 다른 워크로드가 나빠졌고, 값의 뜻은 알고리즘이 아니라 경험에서 나왔습니다.

::: {.old}
CFS 시절의 자료는 `sched_latency_ns`, `sched_min_granularity_ns`, `sched_wakeup_granularity_ns` 조정으로 응답성을 다듬는 법을 설명합니다. v7.3에는 이 값들이 없습니다. fair 클래스의 조정값은 `base_slice_ns` 하나이고 `/sys/kernel/debug/sched/` 아래에 있습니다. "RB 트리의 맨 왼쪽 노드가 다음 태스크"라는 설명도 CFS의 것입니다. v7.3의 트리는 정렬 기준이 다르고, 맨 왼쪽이 뽑힌다는 보장이 없습니다.
:::

## EEVDF: lag, 자격, 가상 데드라인 {#eevdf}

EEVDF(Earliest Eligible Virtual Deadline First)는 1995년 논문에 나온 알고리즘이고, [v6.6]{.v}에서 CFS의 자리를 이어받았습니다. `vruntime`과 가중치는 그대로 두고 개념 셋을 더합니다.

**lag**는 받아야 했던 몫과 실제로 받은 몫의 차이입니다. 소스의 주석이 정의를 적어 두었습니다.

```{.c file="kernel/sched/fair.c" line="594"}
 * Fair schedulers conserve lag:
 *
 *   \Sum lag_i = 0
 *
 * Where lag_i is given by:
 *
 *   lag_i = S - s_i = w_i * (V - v_i)
 *
 * Where S is the ideal service time and V is it's virtual time counterpart.
 /* ... */
 *       \Sum v_i * w_i   \Sum v_i * w_i
 *   V = -------------- = --------------
 *          \Sum w_i            W
 *
 * Specifically, this is the weighted average of all entity virtual runtimes.
```

`v_i`는 태스크 i의 `vruntime`입니다. `V`는 이상적인 CPU라면 지금 모든 태스크가 도달해 있을 가상 시각이고, 실행 가능한 태스크들의 `vruntime`을 가중치로 평균한 값입니다. lag가 양수면 덜 받았고, 음수면 더 받았습니다. 모든 태스크의 lag를 더하면 0입니다. 누군가 더 받았다면 누군가는 덜 받은 것입니다.

**자격**(eligibility)은 lag가 0 이상이라는 뜻입니다. `v_i ≤ V`와 같습니다. 제 몫보다 더 받은 태스크는 다른 태스크들이 따라올 때까지 뽑히지 않습니다.

::: {.fig src="lag-meaning.svg"}
가상 시간 축 위의 세 태스크. 평균 `V`보다 왼쪽에 있으면 덜 받은 것(lag > 0)이고 자격이 있습니다. 오른쪽에 있으면 더 받은 것이고 자격이 없습니다.
:::

**가상 데드라인**(virtual deadline)은 "이 태스크의 다음 요청이 끝나 있어야 할 가상 시각"입니다. 요청의 크기가 **slice**입니다.

```{.c file="kernel/sched/fair.c" line="1289"}
static bool update_deadline(struct cfs_rq *cfs_rq, struct sched_entity *se)
{
	if (vruntime_cmp(se->vruntime, "<", se->deadline))
		return false;
	/* ... */
	if (!se->custom_slice)
		se->slice = sysctl_sched_base_slice;

	/*
	 * EEVDF: vd_i = ve_i + r_i / w_i
	 */
	se->deadline = se->vruntime + calc_delta_fair(se->slice, se);
	avg_vruntime(cfs_rq);

	/*
	 * The task has consumed its request, reschedule.
	 */
	return true;
}
```

읽을 곳은 두 군데입니다.

- 데드라인은 `vruntime + slice / weight`입니다. slice가 짧을수록, 가중치가 클수록 데드라인이 가깝습니다.
- `vruntime`이 데드라인에 닿으면 요청 하나를 다 쓴 것입니다. 새 데드라인을 받고 `true`를 반환합니다. 호출한 `update_curr()`는 이것을 보고 재스케줄을 요청합니다([6장](ch06.html)에서 본 `resched_curr_lazy()` 호출이 그 자리입니다).

고르는 규칙은 이름 그대로입니다. **자격 있는 태스크 가운데 가상 데드라인이 가장 이른 것.** 자격이 "얼마나 많이"를 지키고, 데드라인이 "얼마나 빨리"를 정합니다.

### 숫자로 따라가기

태스크 셋이 CPU 하나에서 돕니다. 가중치는 A가 2, B와 C가 1입니다. slice는 A 3ms, B 4ms, C 1ms입니다. 모두 `vruntime` 0에서 시작하고, 뽑힌 태스크는 slice를 다 쓴다고 단순화합니다.

| 단계 | V | A (v, 데드라인) | B (v, 데드라인) | C (v, 데드라인) | 뽑히는 태스크 |
|---|---|---|---|---|---|
| ① | 0 | 0, 1.5 | 0, 4 | 0, 1 | C. 셋 다 자격이 있고 데드라인이 가장 이릅니다. |
| ② | 0.25 | 0, 1.5 | 0, 4 | **1**, 2 | A. C는 자격이 없습니다. |
| ③ | 1 | **1.5**, 3 | 0, 4 | 1, 2 | C. A는 자격이 없고, C가 B보다 이릅니다. |
| ④ | 1.25 | 1.5, 3 | 0, 4 | **2**, 3 | B. 데드라인은 가장 늦지만 혼자 자격이 있습니다. |

A가 3ms 돌면 `vruntime`은 3/2 = 1.5만큼 오릅니다. ②의 `V`는 (2×0 + 1×0 + 1×1) / 4 = 0.25입니다. ③이 CFS와 갈리는 자리입니다. `vruntime`이 가장 작은 것은 B인데 EEVDF는 C를 고릅니다. C는 slice가 짧아 데드라인이 이르기 때문입니다. 그렇다고 C가 더 많이 받는 것은 아닙니다. ④에서 C는 자격을 잃고, 그동안 밀린 B가 4ms를 한 번에 받습니다. 9ms 동안 A는 3ms, B는 4ms, C는 2ms를 받았고 lag는 차례로 +1.5, −1.75, +0.25입니다. 합은 0입니다.

::: {.fig src="eevdf-pick.svg"}
표의 ③ 단계. 자격선 `V`의 왼쪽에 있는 B와 C만 후보이고, 그 가운데 데드라인이 이른 C가 뽑힙니다.
:::

## 트리에서 고르기 {#pick}

"자격 있는 것 중 데드라인이 가장 이른 것"을 빨리 찾으려면 정렬 기준이 둘 필요합니다. 데드라인과 `vruntime`입니다. 트리 하나로 둘을 처리하는 방법이 **증강 RB 트리**(augmented rbtree)입니다.

- 트리(`cfs_rq->tasks_timeline`)는 **데드라인**으로 정렬합니다.
- 각 노드는 자기 서브트리 안의 가장 작은 `vruntime`을 `min_vruntime`에 따로 적어 둡니다. 노드를 넣고 뺄 때 조상들의 값이 함께 갱신됩니다.

::: {.fig src="tree-compare.svg"}
CFS의 트리는 `vruntime`으로 정렬되어 맨 왼쪽이 답이었습니다. EEVDF의 트리는 데드라인으로 정렬하고, 노드마다 서브트리의 최소 `vruntime`을 적어 자격 없는 가지를 통째로 건너뜁니다.
:::

```{.c file="kernel/sched/fair.c" line="1187"}
static struct sched_entity *pick_eevdf(struct cfs_rq *cfs_rq, bool protect)
{
	/* ... */
	if (curr && (!curr->on_rq || !entity_eligible(cfs_rq, curr)))
		curr = NULL;

	if (curr && protect && protect_slice(curr))
		return curr;

	/* Pick the leftmost entity if it's eligible */
	if (se && entity_eligible(cfs_rq, se)) {
		best = se;
		goto found;
	}

	/* Heap search for the EEVD entity */
	while (node) {
		struct rb_node *left = node->rb_left;
		/* ... */
		if (left && vruntime_eligible(cfs_rq,
					__node_2_se(left)->min_vruntime)) {
			node = left;
			continue;
		}

		se = __node_2_se(node);
		/* ... */
		if (entity_eligible(cfs_rq, se)) {
			best = se;
			break;
		}

		node = node->rb_right;
	}
found:
	if (!best || (curr && entity_before(curr, best)))
		best = curr;

	return best;
}
```

`node`는 트리의 루트에서, `se`는 맨 왼쪽 노드에서 시작합니다. 읽을 곳은 네 군데입니다.

- **실행 중인 태스크는 트리 밖에 있습니다.** `cfs_rq->curr`가 따로 가리킵니다. 그래서 트리에서 찾은 답과 `curr`를 마지막에 한 번 더 견줍니다.
- **맨 왼쪽이 자격 있으면 끝입니다.** 데드라인이 가장 이른 노드이므로 더 볼 것이 없습니다. 흔한 경우입니다.
- **아니면 위에서 내려갑니다.** 왼쪽 서브트리의 `min_vruntime`이 자격선 안이면 그 안에 자격 있는 노드가 있고, 왼쪽은 데드라인이 더 이르므로 왼쪽으로 갑니다. 아니면 자기 자신을 보고, 그것도 아니면 오른쪽으로 갑니다. 높이만큼만 내려가므로 O(log n)입니다.
- **`protect_slice()`.** 현재 태스크가 보호받는 구간 안이면 다시 고르지 않고 그대로 둡니다. 다음 절에서 봅니다.

자격 판정은 `V`를 구해 비교하지 않습니다.

```{.c file="kernel/sched/fair.c" line="922"}
static int vruntime_eligible(struct cfs_rq *cfs_rq, u64 vruntime)
{
	struct sched_entity *curr = cfs_rq->curr;
	s64 key, avg = cfs_rq->sum_w_vruntime;
	long load = cfs_rq->sum_weight;

	if (curr && curr->on_rq) {
		unsigned long weight = avg_vruntime_weight(cfs_rq, curr->h_load.weight);

		avg += entity_key(cfs_rq, curr) * weight;
		load += weight;
	}

	key = vruntime_op(vruntime, "-", cfs_rq->zero_vruntime);
	/* ... */
	return avg >= (__int128)key * load;
	/* ... */
}
```

`V`는 나눗셈의 결과라 정밀도를 잃습니다. 그래서 `v ≤ V`의 양변에 가중치 합을 곱해 `Σ(v_i − v0)·w_i ≥ (v − v0)·Σw_i`를 곱셈으로 판정합니다. `cfs_rq`는 좌변의 합(`sum_w_vruntime`)과 가중치 합(`sum_weight`)을 태스크가 트리에 드나들 때마다 갱신해 둡니다. 트리 밖에 있는 `curr`의 몫은 여기서 따로 더합니다. `vruntime`을 그대로 쓰지 않고 기준점 `zero_vruntime`과의 차이로 다루는 것은 64비트 곱셈이 넘치지 않게 하려는 것입니다.

::: {.design}
정렬 기준이 둘이라고 자료구조를 둘 두면, 넣고 뺄 때마다 둘을 맞춰야 하고 어긋날 틈이 생깁니다. 증강 트리는 한 기준으로 정렬하고 다른 기준은 **서브트리의 요약값**으로 얹습니다. 요약값만 보고 가지를 버릴 수 있으면 탐색은 여전히 O(log n)입니다. 커널의 `rbtree_augmented.h`가 이 패턴을 일반화해 두었고, 메모리 관리의 구간 트리도 같은 방식으로 "서브트리 안의 가장 먼 끝점"을 얹습니다.
:::

## slice와 지연 시간 {#slice}

slice는 "한 번에 얼마씩 받겠다"는 요청의 크기입니다. 총량에는 영향이 없습니다. 총량은 가중치가 정합니다. slice가 정하는 것은 **잘게 자주 받을지, 크게 드물게 받을지**입니다.

::: {.fig src="slice-latency.svg"}
CPU를 계속 쓰는 태스크 L이 도는 중에 S가 깨어납니다. S의 slice가 L과 같으면 L의 보호 구간이 끝날 때까지 기다리고, 더 짧으면 깨어나자마자 뽑힙니다. S가 받는 CPU 시간은 같습니다.
:::

기본값은 `sysctl_sched_base_slice`입니다. 소스의 초기값은 0.7ms이고, 부팅 때 CPU 수에 따라 `1 + log2(min(CPU 수, 8))`배가 됩니다. CPU가 8개 이상이면 2.8ms입니다. 태스크마다 다른 값을 주려면 `sched_setattr()`의 `sched_runtime` 필드를 씁니다. 원래 `SCHED_DEADLINE`용이던 필드를 일반 태스크의 slice 요청으로도 쓰게 한 것입니다.

```{.c file="kernel/sched/fair.c" line="6366"}
void __setparam_fair(struct task_struct *p, const struct sched_attr *attr)
{
	struct sched_entity *se = &p->se;

	p->static_prio = NICE_TO_PRIO(attr->sched_nice);
	if (attr->sched_runtime) {
		se->custom_slice = 1;
		se->slice = clamp_t(u64, attr->sched_runtime,
				      NSEC_PER_MSEC/10,   /* HZ=1000 * 10 */
				      NSEC_PER_MSEC*100); /* HZ=100  / 10 */
	} else {
		se->custom_slice = 0;
		se->slice = sysctl_sched_base_slice;
	}
}
```

허용 범위는 0.1ms에서 100ms입니다. 특권이 필요 없습니다. slice를 줄인다고 남의 몫을 빼앗지 않기 때문입니다. 앞 절의 오디오 스레드는 slice를 짧게 요청하면 됩니다.

::: {.myth}
"nice 값을 낮추면 응답이 빨라진다." nice는 가중치, 곧 받는 **양**을 바꿉니다. 양이 늘면 자격을 잃는 일이 줄어 결과적으로 덜 기다리기는 하지만, 그 대가로 다른 태스크의 몫을 가져옵니다. 응답 시간만 필요하다면 바꿀 것은 slice입니다.
:::

뽑힌 태스크가 얼마나 방해받지 않고 도는지는 `kernel/sched/features.h`의 기능 플래그가 정합니다.

| 플래그 | 기본 | 하는 일 |
|---|---|---|
| `RUN_TO_PARITY` | 켜짐 | 뽑힌 태스크는 lag가 0이 되는 지점이나 slice 끝까지 깨우기 선점을 받지 않습니다. |
| `PREEMPT_SHORT` | 켜짐 | 깨어난 태스크의 slice가 현재 태스크보다 짧으면 위의 보호를 풉니다. |
| `PLACE_LAG` | 켜짐 | 잠들 때의 lag를 깨어날 때 되살립니다. |
| `DELAY_DEQUEUE` | 켜짐 | 자격 없는 태스크가 잠들면 큐에서 바로 빼지 않습니다. |

앞의 `pick_eevdf()`에 있던 `protect_slice(curr)`가 이 보호 구간을 확인하는 자리입니다. 보호가 없으면 태스크가 깨어날 때마다 현재 태스크가 끊겨 컨텍스트 스위치만 늘어납니다.

::: {.lab}
fair 클래스의 조정값과 태스크의 상태를 봅니다.

```console
# cat /sys/kernel/debug/sched/base_slice_ns
2800000
# cat /sys/kernel/debug/sched/features
PLACE_LAG PLACE_DEADLINE_INITIAL PLACE_REL_DEADLINE RUN_TO_PARITY PREEMPT_SHORT NO_NEXT_BUDDY ...
# grep -A12 'runnable tasks' /sys/kernel/debug/sched/debug | cut -c1-110
runnable tasks:
 S            task   PID     weight       vruntime   eligible    deadline             slice ...
-------------------------------------------------------------------------------------------
>R            bash  4127    1048576    1203.456789   E    1206.256789      2.800000 ...
```

`eligible` 열은 `E`(자격 있음)나 `N`입니다. `weight` 1048576은 nice 0의 가중치 1024를 64비트 커널이 정밀도를 위해 2^10배 한 값(`NICE_0_LOAD`)입니다. `deadline − vruntime`이 slice와 같다면 방금 새 요청을 받은 것입니다.

slice를 1ms로 줄여 프로그램을 실행합니다. `-T`가 일반 정책에서 slice를 뜻하는 것은 최근 util-linux부터입니다.

```console
$ chrt -o -T 1000000 0 sleep 100 &
$ grep se.slice /proc/$!/sched
se.slice                                     :              1000000
```
:::

## 잠드는 태스크와 lag {#sleep}

태스크가 잠들면 lag를 어떻게 할지가 문제입니다. 잊어버리면 악용할 수 있습니다. slice를 다 쓴 직후에는 lag가 음수입니다. 그때 잠깐 잠들었다 깨는 것으로 빚이 지워진다면, 그런 태스크는 제 몫보다 더 받습니다. 영원히 기억하는 것도 답이 아닙니다. 한 시간 전의 lag는 지금의 경쟁과 상관이 없습니다.

v7.3은 두 장치를 씁니다.

**깨어날 때 lag를 되살립니다.** 큐에서 빠질 때 `se->vlag`에 `V − v`를 적어 두고, 다시 들어올 때 `place_entity()`가 `se->vruntime = V − lag`로 자리를 잡아 줍니다. 덜 받고 잠든 태스크는 `V`보다 왼쪽에서 시작해 곧바로 자격이 있습니다. 적어 두는 lag에는 상한이 있어서(`entity_lag()`, 큐에서 가장 긴 slice에 틱 하나를 더한 만큼) 오래 굶었다고 한없이 보상받지는 않습니다. 새로 만들어진 태스크는 lag 0에서, slice의 절반만 남은 데드라인으로 시작합니다.

**빚이 있는 태스크는 바로 빼지 않습니다.** 이것이 **지연 디큐**(delayed dequeue)입니다.

```{.c file="kernel/sched/fair.c" line="8346"}
static bool __dequeue_task(struct rq *rq, struct task_struct *p, int flags)
{
	/* ... */
	update_curr_eevdf(cfs_rq);
	update_entity_lag(cfs_rq, se);

	if (flags & DEQUEUE_DELAYED) {
		WARN_ON_ONCE(!se->sched_delayed);
	} else {
		bool delay = task_sleep;
		/* ... */
		if (sched_feat(DELAY_DEQUEUE) && delay &&
		    !entity_eligible(cfs_rq, se)) {
			update_load_avg(cfs_rq_of(se), se, UPDATE_UTIL_EST);
			set_delayed(se);
			return false;
		}
	}

	dequeue_hierarchy(p, flags);
	/* ... */
}
```

잠들려는 태스크에 자격이 없으면(`lag < 0`) `sched_delayed` 표시만 하고 `false`를 반환합니다. 태스크는 잠든 상태지만 트리에는 남아 경쟁에 참여합니다. 다른 태스크들이 실행되어 `V`가 이 태스크의 `vruntime`을 따라잡으면 lag가 0이 되고, `pick_eevdf()`가 이 태스크를 뽑습니다. 그 순간 `pick_next_entity()`가 표시를 보고 진짜로 큐에서 뺀 뒤 다시 고릅니다. 빚을 다 갚은 뒤에야 떠나는 셈입니다. 그 전에 깨어나면 표시만 지우고 그대로 경쟁을 이어 갑니다. 4장에서 `dequeue_task()`의 반환형이 `bool`이었던 이유가 이것입니다.

## 그룹 스케줄링 {#group}

지금까지는 태스크끼리 나눴습니다. 컨테이너 둘이 있고 한쪽에 스레드가 100개, 다른 쪽에 1개라면 태스크 단위의 공정함은 100 대 1이 됩니다. **그룹 스케줄링**은 먼저 그룹끼리 나누고, 그룹의 몫을 그 안의 태스크들이 나누게 합니다. 그룹은 cgroup이고, 그룹의 가중치는 `cpu.weight` 파일로 정합니다([22장](ch22.html)).

커널 안에서는 그룹(`struct task_group`)이 CPU마다 자기 `cfs_rq`와, 부모의 큐에서 자기를 대표하는 `sched_entity`를 하나씩 가집니다. 태스크의 `se->parent`를 따라 올라가면 루트에 닿습니다.

v7.3에서 태스크를 고를 때 이 계층은 **가중치를 계산하는 데만** 쓰입니다. 태스크를 고르는 트리는 CPU마다 하나, 루트 `cfs_rq`의 것뿐입니다. 태스크가 큐에 들어올 때 계층을 따라 올라가며 각 단계의 비율을 곱해 실효 가중치를 구합니다.

```{.c file="kernel/sched/fair.c" line="4985"}
/*
 * weight = NICE_0_LOAD;
 * for_each_entity_se(se)
 *   weight = __calc_prop_weight(cfs_rq_of(se), se, weight);
 */
static __always_inline
unsigned long __calc_prop_weight(struct cfs_rq *cfs_rq, struct sched_entity *se,
				 unsigned long weight)
{
	weight *= se->load.weight;
	if (parent_entity(se))
		weight /= cfs_rq->load.weight;
	else
		weight /= NICE_0_LOAD;

	return max(weight, MIN_SHARES);
}
```

단계마다 "이 큐의 전체 가중치 가운데 내 가중치의 비율"을 곱합니다. 그 결과가 `se->h_load`이고, 앞에서 본 `calc_delta_fair()`와 lag 계산이 모두 이 값을 씁니다. CPU 하나에서 가중치가 같은 두 그룹에 nice 0 태스크가 각각 4개와 1개 있으면, 앞 그룹의 태스크는 nice 0 가중치의 1/4을, 뒤 그룹의 태스크는 그대로를 실효 가중치로 받아 같은 트리에서 경쟁합니다. 결과는 그룹별로 절반씩입니다.

::: {.fig src="flat-hierarchy.svg"}
cgroup 계층은 태스크의 실효 가중치 `h_load`를 정합니다. 태스크는 모두 루트 `cfs_rq`의 트리 하나에 들어가고, `pick_eevdf()`는 그 트리만 봅니다.
:::

::: {.old}
v7.2까지의 fair 클래스는 그룹마다 따로 트리를 두고 **위에서 아래로** 골랐습니다. 루트의 트리에서 엔티티를 고르고, 그것이 그룹이면 그 그룹의 트리에서 다시 고르기를 태스크가 나올 때까지 반복했습니다. 옛 자료의 `pick_next_task_fair()`에서 `group_cfs_rq(se)`가 `NULL`이 될 때까지 도는 `do … while` 반복문이 그것입니다. 이 방식에서는 그룹 엔티티도 lag와 데드라인을 가져야 했고, 지연 디큐 같은 기능이 계층의 단계마다 따로 얽혔습니다. [v7.3]{.v}의 `pick_task_fair()`에는 이 반복문이 없습니다. `__enqueue_entity()`는 트리에 들어오는 것이 루트 큐의 태스크인지 `WARN_ON_ONCE`로 확인합니다.
:::

상한을 두는 `cpu.max`는 다른 장치입니다. 주기마다 쿼터를 주고, 다 쓴 그룹의 태스크를 다음 주기까지 세워 둡니다(CFS 대역폭 제어). 비율이 아니라 절대량을 제한합니다.

## 실시간 클래스와 fair_server {#rt-dl}

fair 클래스 위에는 클래스가 둘 있습니다.

**RT 클래스**(`rt.c`)는 가장 단순합니다. 우선순위 100개에 리스트가 하나씩 있고, 비어 있지 않은 리스트를 표시하는 비트맵이 있습니다. 고르기는 비트맵에서 첫 비트를 찾아 그 리스트의 맨 앞을 꺼내는 것입니다. `SCHED_FIFO` 태스크는 스스로 놓거나 더 높은 태스크가 올 때까지 돌고, `SCHED_RR` 태스크는 100ms(`RR_TIMESLICE`)를 쓰면 같은 우선순위의 맨 뒤로 갑니다.

**deadline 클래스**(`deadline.c`)는 태스크가 세 값을 선언합니다. 주기(period)마다 실행 시간(runtime)만큼을 기한(deadline) 안에 달라는 것입니다. 스케줄러는 기한이 가장 이른 태스크를 고르고(EDF), 선언한 실행 시간을 넘긴 태스크는 다음 주기까지 세워 둡니다(CBS). 태스크를 받아들일 때 선언의 합이 CPU 용량을 넘는지 검사하고(`sched_dl_overflow()`), 넘으면 `sched_setattr()`가 `-EBUSY`로 실패합니다.

클래스의 순서는 엄격하므로, RT 태스크가 무한 반복문에 빠지면 그 CPU의 일반 태스크는 영원히 기다립니다. 셸도, 그 태스크를 죽일 `kill`도 돌지 못합니다. v7.3의 해법은 **deadline 서버**입니다. deadline 클래스 안에 태스크가 아닌 엔티티를 하나 두고, 이 엔티티가 뽑히면 **fair 클래스에 태스크를 대신 고르게** 합니다.

```{.c file="kernel/sched/deadline.c" line="2817"}
static struct task_struct *__pick_task_dl(struct rq *rq, struct rq_flags *rf)
{
	/* ... */
	dl_se = pick_next_dl_entity(dl_rq);
	WARN_ON_ONCE(!dl_se);

	if (dl_server(dl_se)) {
		p = dl_se->server_pick_task(dl_se, rf);
		if (!p) {
			dl_server_stop(dl_se);
			goto again;
		}
		rq->dl_server = dl_se;
	} else {
		p = dl_task_of(dl_se);
	}

	return p;
}
```

런큐마다 있는 `rq->fair_server`가 그 엔티티이고, `server_pick_task`는 `pick_task_fair()`를 부릅니다. 기본 설정은 주기 1초에 실행 시간 50ms입니다. deadline 클래스는 RT보다 높으므로, RT 태스크가 CPU를 붙잡고 있어도 일반 태스크는 1초마다 50ms를 받습니다.

::: {.fig src="fair-server.svg"}
RT 태스크가 CPU를 독점할 때. `fair_server`는 deadline 클래스의 엔티티로서 RT 태스크를 밀어내고, 받은 50ms를 fair 클래스의 태스크에 넘깁니다.
:::

서버는 평소에는 나서지 않습니다. 일반 태스크가 제 힘으로 돈 시간도 서버의 예산에서 빼기 때문입니다(`update_curr()`의 `dl_server_update()` 호출). 주기 안에 스스로 50ms를 받았다면 서버는 실행되지 않고, 받지 못한 채 주기의 끝이 다가올 때에만 서버가 실행 가능한 deadline 엔티티가 됩니다. ext 클래스를 위한 `rq->ext_server`도 같은 방식으로 있습니다.

::: {.old}
옛 자료는 이 문제의 해법으로 **RT 스로틀링**을 설명합니다. `sched_rt_runtime_us`의 기본값 950000은 RT 태스크가 1초 중 0.95초만 쓰게 하고, 나머지 0.05초 동안 RT 클래스 전체를 세워 두었습니다. v7.3의 `kernel/sched/rt.c`에서 이 값의 초기값은 1000000, 곧 제한 없음이고, 스로틀링 코드는 RT 그룹 스케줄링(`CONFIG_RT_GROUP_SCHED`)에만 남아 있습니다. 일반 태스크의 보호는 `fair_server`가 맡습니다. 스로틀링은 일반 태스크가 없어도 CPU를 놀렸지만, 서버는 굶는 태스크가 있을 때만 끼어듭니다.
:::

::: {.lab}
`fair_server`의 설정은 CPU별로 debugfs에 있습니다. 단위는 나노초입니다.

```console
# cat /sys/kernel/debug/sched/fair_server/cpu0/runtime
50000000
# cat /sys/kernel/debug/sched/fair_server/cpu0/period
1000000000
```

시험해 보려면 CPU 하나에 `SCHED_FIFO` 무한 반복문을 묶어 두고, 같은 CPU에 묶은 일반 태스크의 CPU 사용률을 봅니다. 5% 근처가 나옵니다.

```console
# taskset -c 3 chrt -f 50 sh -c 'while :; do :; done' &
# taskset -c 3 sh -c 'while :; do :; done' &
# top -b -n 2 -d 3 | grep ' sh$'
```
:::

## sched_ext: BPF로 쓰는 클래스 {#scx}

fair 클래스 바로 아래의 ext 클래스(`kernel/sched/ext/`)는 정책이 비어 있습니다. 정책은 BPF 프로그램이 채웁니다. 커널을 다시 빌드하거나 재부팅하지 않고 스케줄러를 바꿔 끼울 수 있습니다.

구조는 4장에서 본 것의 반복입니다. 뼈대가 `struct sched_class`의 콜백으로 클래스에 묻듯이, ext 클래스는 `struct sched_ext_ops`의 콜백으로 BPF 스케줄러에 묻습니다. 둘 사이의 완충이 **DSQ**(dispatch queue)입니다. CPU는 자기 로컬 DSQ에서만 태스크를 꺼내 실행하고, BPF 스케줄러의 일은 태스크를 알맞은 DSQ에 넣는 것입니다.

::: {.fig src="scx-arch.svg"}
sched_ext의 구조. 깨어난 태스크는 `ops.enqueue()`로 BPF 스케줄러에 넘어가고, CPU가 할 일을 찾을 때 `ops.dispatch()`가 태스크를 그 CPU의 로컬 DSQ로 옮깁니다.
:::

커널 트리에 든 예제 `scx_simple`의 핵심은 두 함수입니다.

```{.c file="tools/sched_ext/scx_simple.bpf.c" line="69"}
void BPF_STRUCT_OPS(simple_enqueue, struct task_struct *p, u64 enq_flags)
{
	stat_inc(1);	/* count global queueing */

	if (fifo_sched) {
		scx_bpf_dsq_insert(p, SHARED_DSQ, SCX_SLICE_DFL, enq_flags);
	} else {
		u64 vtime = p->scx.dsq_vtime;
		/* ... */
		scx_bpf_dsq_insert_vtime(p, SHARED_DSQ, SCX_SLICE_DFL, vtime,
					 enq_flags);
	}
}

void BPF_STRUCT_OPS(simple_dispatch, s32 cpu, struct task_struct *prev)
{
	scx_bpf_dsq_move_to_local(SHARED_DSQ, 0);
}
```

실행 가능해진 태스크를 모든 CPU가 같이 쓰는 DSQ 하나에 가상 시간 순서로 넣고, CPU가 일을 찾으면 그 DSQ의 맨 앞을 가져갑니다. 이 장 앞부분에서 본 CFS의 생각을 전역 큐 하나로 구현한 셈이고, 파일 전체가 160줄 남짓입니다.

BPF 프로그램이 틀릴 수 있으므로 안전장치가 있습니다. BPF 스케줄러가 오류를 내거나, 실행 가능한 태스크를 오래(기본 30초) 돌리지 않거나, 관리자가 `SysRq-S`를 누르면 커널은 BPF 스케줄러를 떼어 내고 모든 태스크를 fair 클래스로 되돌립니다. v7.3에서는 cgroup 하위 트리마다 다른 BPF 스케줄러를 붙이는 하위 스케줄러(`ext/sub.c`)도 지원합니다. BPF 검증기와 `struct_ops`는 [24장](ch24.html)에서 다룹니다.

```console
# cat /sys/kernel/sched_ext/state
enabled
# cat /sys/kernel/sched_ext/root/ops
simple
```

::: {.design}
CFS에서 EEVDF로 가는 데 16년이 걸린 데에는 스케줄러를 바꾸는 비용이 큰 탓도 있습니다. 모든 워크로드가 한 알고리즘을 쓰므로, 어느 하나를 낫게 하는 변경이 다른 것을 나쁘게 하지 않는다는 것을 보여야 합니다. sched_ext는 그 비용 구조를 바꿉니다. 정책을 커널 밖에서 만들고, 특정 워크로드에만 적용하고, 틀리면 자동으로 원래 스케줄러로 돌아옵니다. 핵심 경로를 직접 고치는 대신 **안전하게 실패하는 확장 지점**을 여는 방식입니다. 대가도 문서에 적혀 있습니다. BPF 스케줄러에 주는 인터페이스는 안정성을 보장하지 않습니다.
:::

## 정리 {#summary}

- fair 클래스는 실행 시간을 가중치로 나눈 `vruntime`으로 "얼마나 받았나"를 잽니다. 가중치는 nice 값에서 나오고 한 단계에 약 1.25배입니다.
- EEVDF는 lag(받아야 할 몫 − 받은 몫), 자격(lag ≥ 0), 가상 데드라인(`vruntime + slice/weight`)을 더해 "자격 있는 것 중 데드라인이 가장 이른 것"을 고릅니다.
- 트리는 데드라인으로 정렬하고 서브트리의 최소 `vruntime`을 얹은 증강 RB 트리입니다. 실행 중인 태스크는 트리 밖에 있습니다.
- slice는 총량이 아니라 받는 주기를 정합니다. 짧은 slice는 더 빨리, 더 잘게 받습니다. `sched_setattr()`의 `sched_runtime`으로 태스크마다 정할 수 있습니다.
- 잠드는 태스크의 lag는 보존됩니다. 빚이 있는 태스크는 빚이 갚아질 때까지 큐에 남습니다(지연 디큐).
- v7.3에서 cgroup 계층은 태스크의 실효 가중치만 정하고, 고르기는 CPU마다 트리 하나에서 합니다.
- RT 태스크가 독점해도 `fair_server`가 일반 태스크에 1초마다 50ms를 보장합니다. 옛 RT 스로틀링을 대신합니다.
- sched_ext는 정책을 BPF 프로그램에 맡기는 클래스이고, 문제가 생기면 fair 클래스로 되돌아갑니다.

## 확인 문제 {#quiz}

::: {.q}
nice 0 태스크 둘과 nice 5 태스크 하나가 CPU 하나에서 계속 돕니다. 각자의 CPU 몫은 대략 얼마입니까? nice 5 태스크의 `vruntime`은 실제 시간보다 몇 배 빨리 흐릅니까?

::: {.a}
가중치는 1024, 1024, 335이고 합은 2383입니다. 몫은 약 43%, 43%, 14%입니다. `vruntime`은 `delta × 1024 / weight`만큼 오르므로 nice 5 태스크는 1024/335, 약 3.06배 빨리 흐릅니다. 같은 실제 시간을 돌아도 가상 시간이 빨리 가서 곧 자격을 잃고, 그래서 덜 받게 됩니다.
:::
:::

::: {.q}
가중치가 같은 두 태스크 X(slice 3ms)와 Y(slice 0.5ms)가 있습니다. 오래 지켜보면 누가 CPU를 더 받습니까? Y가 깨어난 직후에는 누가 먼저 뽑힐 가능성이 큽니까?

::: {.a}
받는 양은 같습니다. 양은 가중치가 정하고, 더 받은 쪽은 `vruntime`이 `V`를 넘어 자격을 잃기 때문입니다. 깨어난 직후에는 Y가 먼저 뽑힐 가능성이 큽니다. 데드라인이 `vruntime + slice/weight`이므로 Y의 데드라인이 훨씬 가깝고, 자격이 있는 한 데드라인이 이른 쪽이 뽑힙니다. `PREEMPT_SHORT`가 켜져 있으면 X가 slice 보호를 받는 중이어도 Y가 선점할 수 있습니다.
:::
:::

::: {.q}
`pick_eevdf()`가 트리의 맨 왼쪽 노드를 그냥 돌려주지 않는 까닭은 무엇입니까? 왼쪽 서브트리를 건너뛰어도 되는지는 무엇으로 압니까?

::: {.a}
트리는 데드라인 순서이므로 맨 왼쪽은 데드라인이 가장 이른 태스크지만, 그 태스크에 자격이 없을 수 있습니다. 그때는 자격 있는 것 가운데 데드라인이 가장 이른 것을 찾아야 합니다. 각 노드에는 자기 서브트리의 최소 `vruntime`인 `min_vruntime`이 있습니다. 왼쪽 자식의 `min_vruntime`이 자격선을 넘으면 그 서브트리에는 자격 있는 태스크가 하나도 없으므로 통째로 건너뜁니다.
:::
:::

::: {.q}
slice를 막 다 쓴 태스크가 1ms 동안 잠들었다 깨기를 반복합니다. 지연 디큐가 없다면 이 태스크는 어떤 이득을 봅니까? v7.3은 이것을 어떻게 막습니까?

::: {.a}
slice를 다 쓴 직후에는 lag가 음수입니다. 잠드는 순간 큐에서 빠지면서 그 빚이 사라진다면, 깨어날 때마다 새 태스크처럼 `V` 근처에서 다시 시작해 제 몫보다 더 받습니다. v7.3은 자격 없는 태스크가 잠들 때 `sched_delayed`만 표시하고 트리에 남깁니다. 다른 태스크들이 돌아 `V`가 따라잡을 때까지 이 태스크의 lag는 그대로 계산되고, 그 전에 깨어나면 음수 lag를 그대로 지고 경쟁합니다.
:::
:::

::: {.q}
`SCHED_FIFO` 태스크가 CPU 2에서 무한 반복문을 돌고 있습니다. 같은 CPU의 일반 태스크는 `__pick_next_task()`의 클래스 순회에서 어느 클래스의 `pick_task()`를 통해 선택됩니까?

::: {.a}
deadline 클래스입니다. 일반 태스크가 굶으면 `rq->fair_server`가 deadline 엔티티로 큐에 올라옵니다. 클래스 순회는 stop 다음에 deadline 클래스의 `pick_task_dl()`을 부르고, 뽑힌 엔티티가 서버이므로 `server_pick_task`, 곧 `pick_task_fair()`가 불려 일반 태스크를 돌려줍니다. rt 클래스에는 차례가 가지 않습니다. 서버의 예산 50ms를 다 쓰면 서버는 다음 주기까지 물러나고 RT 태스크가 다시 돕니다.
:::
:::

## 용어 {#terms}

::: {.terms}
가상 실행 시간 (virtual runtime)
:   실제 실행 시간을 가중치로 나눈 값. `se->vruntime`.

가중치 (weight)
:   태스크가 받을 CPU 몫의 상대적 크기. nice 값에서 나온다.

lag
:   이상적인 스케줄러에서 받았을 시간과 실제로 받은 시간의 차이. 양수면 덜 받았다.

자격 (eligibility)
:   lag가 0 이상인 상태. `vruntime`이 가중 평균 `V` 이하라는 것과 같다.

가상 데드라인 (virtual deadline)
:   `vruntime + slice / weight`. 자격 있는 태스크 가운데 이 값이 가장 이른 것이 뽑힌다.

slice
:   태스크가 한 번에 받겠다고 요청하는 실행 시간. 지연 시간을 정하고 총량에는 영향이 없다.

증강 RB 트리 (augmented rbtree)
:   노드마다 서브트리의 요약값을 함께 유지하는 RB 트리.

지연 디큐 (delayed dequeue)
:   lag가 음수인 태스크가 잠들 때 큐에서 바로 빼지 않고 lag가 0이 될 때까지 남겨 두는 것.

그룹 스케줄링 (group scheduling)
:   CPU 시간을 먼저 cgroup 사이에 나누고, 그룹의 몫을 그 안의 태스크가 나누게 하는 것.

deadline 서버 (deadline server)
:   deadline 클래스의 엔티티로 등록되어, 뽑히면 다른 클래스의 태스크를 대신 실행시키는 장치. `fair_server`가 그 예다.

DSQ (dispatch queue)
:   sched_ext에서 커널과 BPF 스케줄러 사이에 놓이는 태스크 큐.
:::
