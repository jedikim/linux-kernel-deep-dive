::: {.lead}
`docker run`으로 띄운 프로세스는 호스트의 `ps`에 그대로 보입니다. PID가 다르게 보이고 파일시스템이 다르게 보일 뿐, 같은 커널 위에서 도는 평범한 태스크입니다. 커널 소스 어디에도 `struct container`는 없습니다. 있는 것은 "이 태스크에게 무엇이 보이는가"를 정하는 네임스페이스와 "이 태스크들이 얼마나 쓸 수 있는가"를 정하는 cgroup입니다. 컨테이너는 유저 공간의 런타임이 이 둘을 엮어 만든 약속입니다. 이 장은 그 두 부품이 `task_struct`에 어떻게 매달려 있는지 읽습니다.
:::

::: {.goals}
- 컨테이너를 이루는 커널 기능은 무엇이고, 각각 무엇을 맡는가?
- 태스크는 자기가 속한 네임스페이스를 어떤 구조체로 가리키는가? `fork()`할 때 그 구조체는 어떻게 되는가?
- 같은 프로세스가 컨테이너 안에서는 PID 1이고 호스트에서는 PID 48213인 것은 어떻게 구현되는가?
- cgroup v2는 왜 트리를 하나만 두는가? "내부 프로세스 금지" 규칙은 코드 어디에 있는가?
- `cpu.max`와 `memory.max`를 넘으면 각각 무슨 일이 일어나는가?
- 컨테이너의 격리는 어디까지이고, 어디서 끝나는가?
:::

## 커널에는 컨테이너가 없다 {#no-container}

컨테이너 런타임이 하는 일을 커널의 눈으로 보면 세 가지입니다.

- **네임스페이스**(namespace): 전역 자원의 **이름표**를 태스크 묶음마다 따로 줍니다. PID, 마운트 트리, 네트워크 장치, 호스트 이름이 그런 자원입니다. 무엇이 *보이는가*를 정합니다.
- **cgroup**(control group): 태스크를 묶어 CPU, 메모리, I/O를 **재고 제한**합니다. 얼마나 *쓰는가*를 정합니다.
- **권한 제한**: capability를 줄이고, seccomp로 시스템 콜을 거르고([19장](ch19.html)), LSM으로 접근을 막습니다. 무엇을 *할 수 있는가*를 정합니다.

::: {.fig src="container-parts.svg"}
컨테이너는 커널 객체가 아니라 세 가지 기능의 조합입니다. 셋은 서로 독립이어서 하나만 쓸 수도 있습니다.
:::

셋은 서로를 모릅니다. 네임스페이스 없이 cgroup만 쓸 수 있고(systemd가 서비스마다 그렇게 합니다), cgroup 없이 네임스페이스만 쓸 수도 있습니다(`unshare` 명령). "컨테이너"라는 단위로 묶는 일은 전부 유저 공간에서 일어납니다.

::: {.myth}
"컨테이너는 가벼운 가상 머신이다." 아닙니다. 가상 머신은 자기 커널을 부팅합니다([23장](ch23.html)). 컨테이너 안의 프로세스는 호스트 커널의 태스크이고, 호스트의 스케줄러가 직접 고르며, 시스템 콜은 호스트 커널이 받습니다. 가벼운 까닭도, 격리가 약한 까닭도 여기 있습니다.
:::

## 네임스페이스와 nsproxy {#namespaces}

v7.3에는 네임스페이스가 여덟 종류 있습니다.

| 종류 | `clone()` 플래그 | 따로 갖는 것 | 도입 |
|---|---|---|---|
| 마운트 | `CLONE_NEWNS` | 마운트 트리 | 2.4.19 |
| UTS | `CLONE_NEWUTS` | 호스트 이름, 도메인 이름 | 2.6.19 |
| IPC | `CLONE_NEWIPC` | System V IPC, POSIX 메시지 큐 | 2.6.19 |
| PID | `CLONE_NEWPID` | 프로세스 ID 번호 공간 | 2.6.24 |
| 네트워크 | `CLONE_NEWNET` | 장치, 주소, 라우팅 표, 포트, 방화벽 규칙 | 2.6.24 |
| 유저 | `CLONE_NEWUSER` | uid·gid와 capability의 범위 | 3.8에 완성 |
| cgroup | `CLONE_NEWCGROUP` | cgroup 트리에서 루트로 보이는 지점 | 4.6 |
| 시간 | `CLONE_NEWTIME` | 단조 시계와 부팅 시계의 기준점 | 5.6 |

태스크는 이 가운데 여섯을 `nsproxy` 하나로 가리킵니다.

```{.c file="include/linux/nsproxy.h" line="32"}
struct nsproxy {
	refcount_t count;
	struct uts_namespace *uts_ns;
	struct ipc_namespace *ipc_ns;
	struct mnt_namespace *mnt_ns;
	struct pid_namespace *pid_ns_for_children;
	struct net 	     *net_ns;
	struct time_namespace *time_ns;
	struct time_namespace *time_ns_for_children;
	struct cgroup_namespace *cgroup_ns;
};
```

포인터를 `task_struct`에 하나씩 두지 않고 `nsproxy`로 한 단 거친 까닭은 `fork()`에 있습니다. 대부분의 `fork()`는 네임스페이스를 하나도 바꾸지 않습니다. 그때는 부모의 `nsproxy`를 함께 가리키고 참조 카운트 하나만 올리면 됩니다.

```{.c file="kernel/nsproxy.c" line="169"}
int copy_namespaces(u64 flags, struct task_struct *tsk)
{
	struct nsproxy *old_ns = tsk->nsproxy;
	struct user_namespace *user_ns = task_cred_xxx(tsk, user_ns);
	struct nsproxy *new_ns;

	if (likely(!(flags & (CLONE_NS_ALL & ~CLONE_NEWUSER)))) {
		if ((flags & CLONE_VM) ||
		    likely(old_ns->time_ns_for_children == old_ns->time_ns)) {
			get_nsproxy(old_ns);
			return 0;
		}
	} else if (!ns_capable(user_ns, CAP_SYS_ADMIN))
		return -EPERM;
	/* ... */
	new_ns = create_new_namespaces(flags, tsk, user_ns, tsk->fs);
	/* ... */
	tsk->nsproxy = new_ns;
	return 0;
}
```

`CLONE_NEW*` 플래그가 하나라도 있으면 `create_new_namespaces()`가 `nsproxy`를 새로 만들고, 종류마다 `copy_*_ns()`를 부릅니다. 플래그가 선 종류는 새 네임스페이스를 만들고, 나머지는 부모 것의 참조만 얻습니다. 그래서 두 태스크가 네트워크 네임스페이스는 함께 쓰고 마운트 네임스페이스는 따로 쓰는 식의 조합이 됩니다.

::: {.fig src="nsproxy-sharing.svg"}
태스크 A와 B는 `nsproxy`를 함께 쓰고, C는 마운트·PID·네트워크만 새로 만든 `nsproxy`를 씁니다. 바꾸지 않은 UTS와 IPC 네임스페이스는 세 태스크가 같은 객체를 가리킵니다.
:::

두 종류는 `nsproxy`에 없습니다. 소스의 주석이 밝히는 대로 PID 네임스페이스는 예외입니다. `nsproxy`의 `pid_ns_for_children`은 "앞으로 만들 자식이 들어갈 곳"이고, 태스크 자신의 PID 네임스페이스는 그 태스크의 `struct pid`에서 나옵니다. 태스크의 PID는 만들어진 뒤에 바뀔 수 없기 때문입니다. 유저 네임스페이스는 자격 증명 `cred`에 있습니다(`task->cred->user_ns`). 권한 판단에 쓰이는 정보이므로 uid, capability와 한곳에 둡니다.

네임스페이스를 다루는 시스템 콜은 셋입니다. `clone()`은 새 네임스페이스 안에 자식을 만들고, `unshare()`는 부르는 태스크 자신을 새 네임스페이스로 옮기고, `setns()`는 이미 있는 네임스페이스에 들어갑니다. `setns()`의 인자는 fd입니다. `/proc/PID/ns/` 아래의 파일을 열거나 pidfd를 넘깁니다. 이 파일들은 [20장](ch20.html)의 nsfs에 속하고, 열어서 쥐고 있는 동안에는 안의 프로세스가 모두 끝나도 네임스페이스가 사라지지 않습니다.

::: {.lab}
셸이 속한 네임스페이스를 보고, 새 PID 네임스페이스에 들어가 봅니다.

```console
$ ls -l /proc/$$/ns
lrwxrwxrwx 1 kim kim 0 ... mnt -> 'mnt:[4026531841]'
lrwxrwxrwx 1 kim kim 0 ... net -> 'net:[4026531840]'
lrwxrwxrwx 1 kim kim 0 ... pid -> 'pid:[4026531836]'
...
$ sudo unshare --fork --pid --mount-proc bash
# ps aux
USER  PID ... COMMAND
root    1 ... bash
root    8 ... ps aux
# readlink /proc/self/ns/pid
pid:[4026532604]
```

대괄호 안의 숫자가 네임스페이스의 식별자입니다. 두 프로세스의 숫자가 같으면 같은 네임스페이스에 있습니다. `unshare` 안에서는 `bash`가 PID 1입니다. 다른 터미널에서 `ps`로 보면 같은 `bash`가 호스트의 PID로 보입니다. `lsns`는 시스템의 네임스페이스를 종류별로 모아 보여 주고, `sudo nsenter -t PID -n ip addr`는 그 프로세스의 네트워크 네임스페이스에 `setns()`로 들어가 명령을 실행합니다.
:::

## PID 네임스페이스 {#pidns}

PID 네임스페이스는 겹쳐집니다. 새 네임스페이스는 만든 쪽의 자식이 되고, 부모 네임스페이스에서는 자식 네임스페이스의 프로세스가 **보입니다**. 반대는 안 됩니다. 그래서 프로세스 하나는 자기가 속한 네임스페이스와 그 조상들 각각에서 번호를 하나씩 갖습니다.

```{.c file="include/linux/pid.h" line="53"}
struct upid {
	int nr;
	struct pid_namespace *ns;
};

struct pid {
	refcount_t count;
	unsigned int level;
	/* ... */
	/* lists of tasks that use this pid */
	struct hlist_head tasks[PIDTYPE_MAX];
	/* ... */
	struct upid numbers[];
};
```

커널 안에서 프로세스의 정체는 숫자가 아니라 `struct pid` 객체입니다. 숫자는 `numbers[]`에 단계별로 들어 있습니다. `numbers[0]`이 최상위 네임스페이스에서의 번호이고, `numbers[level]`이 자기 네임스페이스에서의 번호입니다. `alloc_pid()`는 `fork()` 때 자기 네임스페이스에서 루트까지 거슬러 올라가며 단계마다 빈 번호를 하나씩 받습니다. 번호를 물을 때는 "어느 네임스페이스에서 본 번호인가"를 함께 물어야 합니다.

```{.c file="kernel/pid.c" line="542"}
pid_t pid_nr_ns(struct pid *pid, struct pid_namespace *ns)
{
	struct upid *upid;
	pid_t nr = 0;

	if (pid && ns && ns->level <= pid->level) {
		upid = &pid->numbers[ns->level];
		if (upid->ns == ns)
			nr = upid->nr;
	}
	return nr;
}
```

`ns->level <= pid->level`이 "조상에서만 보인다"는 규칙입니다. 묻는 쪽 네임스페이스가 더 깊거나 계보가 다르면 0이 나옵니다. 컨테이너 안에서 `getppid()`가 0을 돌려주는 경우가 이것입니다. 부모가 바깥에 있어서 안에서는 이름이 없습니다.

::: {.fig src="pidns-nesting.svg"}
PID 네임스페이스의 중첩. 프로세스 하나에 `struct pid`가 하나 있고, 그 안에 단계 수만큼 번호가 있습니다.
:::

네임스페이스에서 처음 만들어진 프로세스가 그 안의 PID 1입니다. 커널은 이 태스크를 `child_reaper`로 기록하고 진짜 `init`처럼 대합니다. 고아가 된 프로세스의 부모가 되고, 핸들러를 달지 않은 시그널은 안에서 보내도 전달되지 않습니다(`SIGNAL_UNKILLABLE`). 이 프로세스가 죽으면 `zap_pid_ns_processes()`가 네임스페이스의 나머지 프로세스를 모두 `SIGKILL`로 끝냅니다. 컨테이너의 첫 프로세스가 끝나면 컨테이너가 끝나는 까닭입니다.

## 마운트와 네트워크 네임스페이스 {#mnt-net}

**마운트 네임스페이스**는 [20장](ch20.html)에서 본 마운트 트리를 통째로 따로 갖게 합니다. 만드는 순간에는 부모의 트리를 복사합니다. 그 뒤로 한쪽에서 하는 `mount()`와 `umount()`는 다른 쪽에 보이지 않습니다. 컨테이너 런타임은 새 네임스페이스 안에서 이미지의 루트 파일시스템을 마운트하고 `pivot_root()`를 부릅니다. 이 시스템 콜은 지정한 마운트를 새 루트로 만들고 옛 루트를 그 아래 한 곳으로 옮깁니다. 런타임이 옛 루트를 언마운트하고 나면 호스트의 파일시스템으로 가는 경로가 트리에서 사라집니다. `chroot()`가 `fs_struct`의 루트 포인터만 바꾸는 것과 다릅니다.

복사만으로는 곤란한 경우가 있습니다. 호스트에 USB 디스크를 꽂았을 때 그 마운트가 다른 네임스페이스에도 나타나야 할까요. 이것을 정하는 것이 **마운트 전파**입니다. 마운트마다 유형이 있습니다. `shared`는 같은 피어 그룹의 마운트끼리 마운트·언마운트 사건을 서로 전합니다. `slave`는 받기만 합니다. `private`은 주지도 받지도 않습니다. `/proc/self/mountinfo`의 `shared:N`과 `master:N`이 이 관계입니다. 컨테이너의 루트는 보통 overlayfs입니다. 읽기 전용인 이미지 층들 위에 쓰기 가능한 층 하나를 겹쳐 하나의 디렉터리 트리로 보이게 합니다.

**네트워크 네임스페이스**는 `struct net`입니다. 네트워크 스택의 전역 상태가 이 구조체 안에 들어 있습니다. 장치 목록, 라우팅 표, 넷필터 규칙, 소켓이 묶이는 포트 공간이 네임스페이스마다 따로입니다. 네트워크 장치 하나는 한 순간에 네임스페이스 하나에만 속합니다. 새로 만든 네임스페이스에는 루프백 장치 하나뿐입니다.

밖과 통하려면 장치를 넣어 주어야 합니다. 흔한 방법이 **veth** 쌍입니다. 가상의 이더넷 케이블로, 한쪽 끝에 넣은 패킷이 다른 쪽 끝에서 나옵니다. 한쪽 끝을 컨테이너의 네임스페이스로 옮기고 다른 쪽 끝을 호스트의 브리지에 꽂으면, 컨테이너의 패킷은 호스트 커널 안에서 장치 둘을 거쳐 [12장](ch12.html)의 수신 경로로 다시 들어갑니다.

::: {.fig src="netns-veth.svg"}
네트워크 네임스페이스 셋. 컨테이너마다 veth의 한쪽 끝을 `eth0`으로 갖고, 다른 쪽 끝은 호스트 네임스페이스의 브리지에 꽂혀 있습니다.
:::

## 유저 네임스페이스와 권한 {#userns}

**유저 네임스페이스**는 uid와 gid를 바꿔 보이게 합니다. `/proc/PID/uid_map`에 "안의 ID 0부터 65536개는 밖의 ID 100000부터"라는 식의 대응표를 한 번 써넣습니다. 안에서 uid 0인 프로세스가 만든 파일은 밖에서 uid 100000의 소유입니다.

중요한 것은 capability와의 관계입니다. 리눅스에서 root의 힘은 `CAP_NET_ADMIN`, `CAP_SYS_ADMIN` 같은 capability로 쪼개져 있고, 커널의 권한 검사는 "이 태스크가 **이 유저 네임스페이스에 대해** 이 capability를 갖는가"를 묻습니다.

```{.c file="security/commoncap.c" line="68"}
static inline int cap_capable_helper(const struct cred *cred,
				     struct user_namespace *target_ns,
				     const struct user_namespace *cred_ns,
				     int cap)
{
	struct user_namespace *ns = target_ns;

	/* ... */
	for (;;) {
		/* Do we have the necessary capabilities? */
		if (likely(ns == cred_ns))
			return cap_raised(cred->cap_effective, cap) ? 0 : -EPERM;

		/* ... */
		if (ns->level <= cred_ns->level)
			return -EPERM;

		/* ... */
		if ((ns->parent == cred_ns) && uid_eq(ns->owner, cred->euid))
			return 0;

		/* ... */
		ns = ns->parent;
	}

	/* We never get here */
}
```

읽을 곳은 세 군데입니다.

- 대상 자원의 네임스페이스(`target_ns`)가 내 네임스페이스와 같으면 내 capability 비트를 봅니다.
- 대상이 내 네임스페이스보다 위거나 같은 높이의 다른 가지면 무조건 거부입니다. 컨테이너 안의 root가 호스트의 자원에 힘을 쓰지 못하는 줄입니다.
- 대상이 내 자손이면 허용합니다. 유저 네임스페이스를 만든 사람은 그 안에 대해 모든 capability를 갖습니다.

다른 네임스페이스들은 저마다 주인 유저 네임스페이스(`user_ns` 필드)를 기록해 둡니다. 네트워크 장치를 설정하려면 그 `struct net`의 주인에 대해 `CAP_NET_ADMIN`이 있어야 합니다. 그래서 일반 사용자가 유저 네임스페이스를 만들고 그 안에서 네트워크 네임스페이스를 만들면, 호스트에서는 아무 권한이 없으면서 자기 네트워크 네임스페이스 안에서는 root처럼 장치를 만들고 방화벽을 고칠 수 있습니다. root 없이 도는 컨테이너가 이렇게 만들어집니다.

::: {.warn}
이 설계는 공격 표면을 넓힙니다. 예전에는 root만 닿을 수 있던 커널 코드(마운트, 넷필터, 여러 소켓 종류)에 일반 사용자가 "자기 네임스페이스 안의 root"로서 닿게 됩니다. 그 코드에 버그가 있으면 호스트 커널이 뚫립니다. 그래서 `user.max_user_namespaces` sysctl을 0으로 두거나 LSM으로 비특권 유저 네임스페이스 생성을 막는 배포판이 있습니다.
:::

## cgroup v2: 하나의 트리 {#cgroup}

cgroup은 태스크를 트리 모양으로 묶고, 묶음마다 자원을 재고 제한합니다. 인터페이스는 파일시스템입니다. `/sys/fs/cgroup` 아래에서 `mkdir`하면 cgroup이 생기고, 파일에 값을 써서 설정합니다. 구현은 sysfs와 같은 kernfs 위에 있습니다.

자원 종류마다 맡는 코드가 따로 있고 이것을 **컨트롤러**라고 합니다. 커널 구조체는 넷입니다.

| 구조체 | 뜻 |
|---|---|
| `struct cgroup` | 트리의 노드 하나. 디렉터리 하나에 대응합니다. |
| `struct cgroup_subsys` | 컨트롤러 하나. 콜백의 묶음입니다. |
| `struct cgroup_subsys_state` (css) | "이 cgroup에서 이 컨트롤러의 상태". 메모리 컨트롤러는 이것을 `struct mem_cgroup`에 품습니다. |
| `struct css_set` | 태스크 하나가 속한 css들의 묶음. 컨트롤러마다 포인터 하나씩입니다. |

`task_struct`가 직접 가리키는 것은 `css_set` 하나입니다(`task->cgroups`).

```{.c file="include/linux/cgroup-defs.h" line="279"}
/*
 * A css_set is a structure holding pointers to a set of
 * cgroup_subsys_state objects. This saves space in the task struct
 * object and speeds up fork()/exit(), since a single inc/dec and a
 * list_add()/del() can bump the reference count on the entire cgroup
 * set for a task.
 */
struct css_set {
	/* ... */
	struct cgroup_subsys_state *subsys[CGROUP_SUBSYS_COUNT];

	/* reference count */
	refcount_t refcount;
	/* ... */
};
```

주석이 이유를 말합니다. 같은 cgroup에 있는 태스크들은 `css_set`을 함께 쓰므로 `fork()`는 참조 카운트 하나만 올립니다. 메모리를 할당하는 빠른 경로에서 "이 태스크의 memcg는 무엇인가"는 `task->cgroups->subsys[memory_cgrp_id]`, 포인터 두 번입니다. `nsproxy`와 같은 발상입니다.

::: {.fig src="css-set.svg"}
태스크는 `css_set`을, `css_set`은 컨트롤러별 css를, css는 cgroup을 가리킵니다. 같은 cgroup의 태스크들은 `css_set` 하나를 함께 씁니다.
:::

v2 트리에는 규칙이 둘 있습니다. 첫째, 컨트롤러는 **위에서 켜 준 것만** 쓸 수 있습니다. 부모의 `cgroup.subtree_control`에 `+memory`를 써야 자식 디렉터리에 `memory.*` 파일이 생깁니다. 둘째, **내부 프로세스 금지**입니다. 루트가 아닌 cgroup은 자식에게 자원을 나눠 주는 일과 프로세스를 직접 담는 일을 함께 하지 못합니다. 프로세스는 잎에만 있습니다. 이 규칙이 없으면 "부모에 직접 든 프로세스"와 "자식 cgroup"이 형제처럼 자원을 다투게 되고, 둘 사이의 몫을 정할 방법이 컨트롤러마다 달라집니다.

```{.c file="kernel/cgroup/cgroup.c" line="2870"}
int cgroup_migrate_vet_dst(struct cgroup *dst_cgrp)
{
	/* v1 doesn't have any restriction */
	if (!cgroup_on_dfl(dst_cgrp))
		return 0;
	/* ... */
	/* apply no-internal-process constraint */
	if (dst_cgrp->subtree_control)
		return -EBUSY;

	return 0;
}
```

`cgroup.procs`에 PID를 쓰면 이 검사를 거쳐 `cgroup_attach_task()`가 불립니다. 옮기는 일은 두 단계입니다. 먼저 컨트롤러마다 `can_attach()`로 거부할 기회를 주고, 모두 통과하면 태스크의 `css_set` 포인터를 바꾼 뒤 `attach()`로 알립니다. 중간에 실패하면 아무것도 바뀌지 않습니다. 컨트롤러가 채우는 콜백 표에 이 짝이 보입니다.

```{.c file="include/linux/cgroup-defs.h" line="784"}
struct cgroup_subsys {
	struct cgroup_subsys_state *(*css_alloc)(struct cgroup_subsys_state *parent_css);
	/* ... */
	int (*can_attach)(struct cgroup_taskset *tset);
	void (*cancel_attach)(struct cgroup_taskset *tset);
	void (*attach)(struct cgroup_taskset *tset);
	int (*can_fork)(struct task_struct *task,
			struct css_set *cset);
	void (*cancel_fork)(struct task_struct *task, struct css_set *cset);
	void (*fork)(struct task_struct *task);
	void (*exit)(struct task_struct *task);
	/* ... */
};
```

`can_*`과 `cancel_*`이 짝을 이룹니다. 여러 컨트롤러 가운데 하나가 거부하면 앞에서 허락한 컨트롤러들에게 취소를 알립니다. 태스크가 cgroup에 들어오는 길은 옮겨 오는 것(`attach`)과 태어나는 것(`fork`) 둘이고, 나가는 길은 `exit`입니다.

::: {.fig src="cgroup-tree.svg"}
cgroup v2 트리. 컨트롤러는 `subtree_control`로 한 단씩 내려 주고, 프로세스는 잎에만 있습니다.
:::

트리의 일부를 덜 신뢰하는 쪽에 맡기는 **위임**도 이 구조에서 나옵니다. 디렉터리와 그 안의 `cgroup.procs`, `cgroup.subtree_control`의 소유자를 바꿔 주면, 받은 쪽은 그 아래에서 자유롭게 cgroup을 만들고 프로세스를 옮기지만 위에서 정한 한도는 넘지 못합니다. systemd가 사용자 세션에 하위 트리를 넘겨주는 방식입니다.

::: {.old}
많은 자료가 `/sys/fs/cgroup/memory/`, `/sys/fs/cgroup/cpu,cpuacct/`처럼 컨트롤러마다 따로 마운트된 트리와 `tasks` 파일, `memory.limit_in_bytes`를 보여 줍니다. cgroup v1입니다. v1에서는 계층을 몇 개든 만들 수 있었고 태스크가 계층마다 다른 위치에 속할 수 있었습니다. v7.3에서도 v1 코드는 남아 있지만 물러나는 중입니다. 메모리 컨트롤러의 v1 인터페이스는 `CONFIG_MEMCG_V1`, cpuset의 v1 인터페이스는 `CONFIG_CPUSETS_V1` 뒤에 있고 둘 다 기본값이 `n`입니다. Kconfig의 설명은 "deprecated"이고 새로 쓰지 말라고 적혀 있습니다. v2에는 `tasks` 파일이 없고 계층은 하나입니다.
:::

::: {.design}
v2의 제약은 v1의 실패에서 나왔습니다. v1은 "컨트롤러마다 원하는 대로 계층을 짜라"는 최대한의 자유를 주었습니다. 결과는 `Documentation/admin-guide/cgroup-v2.rst`가 적은 대로입니다. 대부분의 설정이 컨트롤러마다 계층을 따로 두었고, 유저 공간은 비슷한 트리 여러 개를 똑같이 관리해야 했습니다. 더 큰 문제는 컨트롤러끼리 협력할 수 없다는 것이었습니다. 페이지 캐시의 더티 페이지를 디스크에 쓸 때 그 I/O를 누구에게 과금할지 알려면 메모리 컨트롤러와 io 컨트롤러가 같은 cgroup을 보아야 하는데, 태스크가 두 계층에서 서로 다른 자리에 있으면 답이 없습니다. v2는 자유를 줄여 이 문제를 없앴습니다. 인터페이스에서 선택지를 줄이는 일이 구현과 사용 양쪽을 단순하게 만든 사례입니다.
:::

## 컨트롤러 {#controllers}

v7.3의 `include/linux/cgroup_subsys.h`에는 컨트롤러가 열여섯 개 등록되어 있습니다. 자주 쓰는 것은 다섯입니다.

| 컨트롤러 | 대표 파일 | 하는 일 |
|---|---|---|
| `cpu` | `cpu.weight`, `cpu.max` | CPU 시간을 가중치로 나누고, 주기당 상한을 둡니다. |
| `memory` | `memory.min`·`low`·`high`·`max` | 메모리 사용량을 과금하고, 보호하고, 제한합니다. |
| `io` | `io.weight`, `io.max` | 장치별 I/O를 가중치와 상한으로 조절합니다([21장](ch21.html)). |
| `pids` | `pids.max` | 태스크 수를 제한합니다. |
| `cpuset` | `cpuset.cpus`, `cpuset.mems` | 쓸 수 있는 CPU와 메모리 노드를 고정합니다. |

나머지는 `hugetlb`, `rdma`, `misc`, `dmem`, `perf_event`, `freezer`, `devices`와 v1 전용인 `cpuacct`, `net_cls`, `net_prio`, 그리고 `debug`입니다. v2에서 장치 접근 제어는 파일이 아니라 cgroup에 붙인 BPF 프로그램으로 합니다. cgroup은 BPF의 부착 지점이기도 해서, 소켓 생성이나 패킷 송수신에 cgroup 단위로 프로그램을 걸 수 있습니다([24장](ch24.html)).

### cpu: 가중치와 상한

`cpu.weight`(기본 100)는 **비율**입니다. 형제 cgroup끼리 CPU를 다툴 때의 몫을 정하고, 다투지 않으면 아무 효과가 없습니다. 스케줄러는 cgroup마다 런큐를 두고 cgroup 자체를 스케줄링 단위로 취급합니다([5장](ch05.html)).

`cpu.max`는 **상한**입니다. `50000 100000`이라고 쓰면 100ms 주기마다 50ms까지만 돕니다. CPU가 남아돌아도 그렇습니다. 실행 시간을 깎는 자리가 이것입니다.

```{.c file="kernel/sched/fair.c" line="6901"}
static bool __account_cfs_rq_runtime(struct cfs_rq *cfs_rq, u64 delta_exec)
{
	/* dock delta_exec before expiring quota (as it could span periods) */
	cfs_rq->runtime_remaining -= delta_exec;

	if (likely(cfs_rq->runtime_remaining > 0))
		return false;

	if (cfs_rq->throttled)
		return true;
	/*
	 * throttle_cfs_rq() will try to extend the runtime first
	 * before throttling the hierarchy.
	 */
	return throttle_cfs_rq(cfs_rq);
}
```

cgroup의 런큐는 전역 몫에서 실행 시간을 조금씩 받아 와 쓰고, 다 쓰면 더 받으려 합니다. 주기의 몫이 바닥났으면 **스로틀**됩니다. 다음 주기의 타이머가 몫을 다시 채울 때까지 그 cgroup의 태스크는 돌지 못합니다. `cpu.stat`의 `nr_throttled`와 `throttled_usec`이 그 횟수와 시간입니다.

::: {.old}
스로틀링을 "cgroup의 런큐를 통째로 떼어 내 그 안의 태스크가 즉시 멈춘다"고 설명한 자료가 많습니다. v7.3은 태스크 단위로 합니다. 몫이 바닥나면 `throttle_cfs_rq()`가 계층에 표시만 하고, 각 태스크에는 task_work(`throttle_cfs_rq_work()`)를 걸어 둡니다. 태스크는 **유저 모드로 돌아가는 길에** 스스로 런큐에서 빠집니다. 예전 방식에서는 커널 안에서 락을 쥔 태스크가 스로틀되어, 그 락을 기다리는 다른 cgroup의 태스크까지 한 주기 동안 멈추는 일이 있었습니다.
:::

### memory: 과금과 네 개의 선

메모리 컨트롤러는 페이지를 **할당하는 순간에** 과금합니다. 페이지 폴트로 익명 페이지를 받을 때, 페이지 캐시에 폴리오를 넣을 때, 커널이 그 태스크를 위해 슬랩 객체를 만들 때입니다. 과금 함수가 한도를 집행합니다.

```{.c file="mm/memcontrol.c" line="2645"}
static int try_charge_memcg(struct mem_cgroup *memcg, gfp_t gfp_mask,
			    unsigned int nr_pages)
{
	/* ... */
retry:
	if (consume_stock(memcg, nr_pages))
		return 0;
	/* ... */
		if (page_counter_try_charge(&memcg->memory, batch, &counter))
			goto done_restock;
	/* ... */
	__memcg_memory_event(mem_over_limit, MEMCG_MAX, allow_spinning);
	raised_max_event = true;

	psi_memstall_enter(&pflags);
	nr_reclaimed = try_to_free_mem_cgroup_pages(mem_over_limit, nr_pages,
						    gfp_mask, reclaim_options, NULL);
	psi_memstall_leave(&pflags);
	/* ... */
	if (mem_cgroup_oom(mem_over_limit, gfp_mask,
			   get_order(nr_pages * PAGE_SIZE))) {
		passed_oom = true;
		nr_retries = MAX_RECLAIM_RETRIES;
		goto retry;
	}
	/* ... */
}
```

순서대로 읽으면 이렇습니다. `consume_stock()`은 CPU별로 미리 받아 둔 몫에서 꺼내 쓰는 빠른 길입니다. 없으면 `page_counter_try_charge()`가 이 cgroup과 모든 조상의 카운터를 올려 보고, 어느 하나라도 `memory.max`를 넘으면 실패합니다. 그러면 **그 cgroup 안에서만** 회수를 돌립니다([18장](ch18.html)). 회수로도 자리가 나지 않으면 `mem_cgroup_oom()`이 그 cgroup의 프로세스 가운데 하나를 죽입니다.

| 파일 | 넘거나 밑돌 때 |
|---|---|
| `memory.min` | 사용량이 이 아래면 회수하지 않습니다. 절대 보호입니다. |
| `memory.low` | 이 아래면 다른 곳에 회수할 것이 남아 있는 한 건드리지 않습니다. |
| `memory.high` | 넘으면 할당하는 태스크가 회수 일을 떠맡고 유저 모드 복귀 길에 강제로 잠듭니다. OOM은 없습니다. |
| `memory.max` | 넘을 수 없습니다. 회수로 안 되면 cgroup 안에서 OOM 킬이 일어납니다. |

::: {.fig src="limit-behaviors.svg"}
두 가지 상한이 걸리는 모습. `cpu.max`는 주기마다 실행을 끊고, 메모리는 `high`에서 느려지고 `max`에서 죽습니다.
:::

### pids, 압력, 얼리기

`pids` 컨트롤러는 `fork()` 경로([1장](ch01.html))의 `can_fork()` 콜백으로 구현됩니다. `pids_can_fork()`가 이 cgroup에서 루트까지 카운터를 올려 보고, 어느 단계에서든 `pids.max`를 넘으면 `fork()`가 `EAGAIN`으로 실패합니다. 포크 폭탄이 컨테이너 밖으로 번지지 못하게 하는 장치입니다.

**PSI**(pressure stall information)는 한도가 아니라 측정입니다. "자원이 모자라 태스크가 기다린 시간의 비율"을 CPU, 메모리, I/O별로 냅니다. 시스템 전체는 `/proc/pressure/`에, cgroup별로는 `cpu.pressure`·`memory.pressure`·`io.pressure`에 나옵니다. 앞의 코드에 있던 `psi_memstall_enter()`가 그 계측 지점입니다. 사용량이 한도의 몇 퍼센트인지보다 "모자라서 실제로 얼마나 느려졌는가"가 운영에 쓸모 있는 신호입니다.

`cgroup.freeze`에 1을 쓰면 하위 트리의 모든 프로세스가 멈추고, `cgroup.kill`에 1을 쓰면 모두 `SIGKILL`을 받습니다. 그 사이에 `fork()`로 빠져나가는 프로세스가 없게 커널이 처리합니다. PID를 하나씩 찾아 죽이는 방식으로는 막을 수 없던 경쟁입니다.

::: {.lab}
손으로 cgroup을 만들어 셸을 가둡니다. root 셸에서 합니다.

```console

# mkdir /sys/fs/cgroup/demo
# echo $$ > /sys/fs/cgroup/demo/cgroup.procs
# echo "50000 100000" > /sys/fs/cgroup/demo/cpu.max
# echo 200M > /sys/fs/cgroup/demo/memory.max
# while :; do :; done &
# grep -E 'nr_|throttled' /sys/fs/cgroup/demo/cpu.stat
nr_periods 152
nr_throttled 151
throttled_usec 7391204
# cat /sys/fs/cgroup/demo/memory.events
low 0
high 0
max 0
oom 0
oom_kill 0
...
```

`top`으로 보면 무한 루프가 CPU 50%에서 멈춰 있습니다. `nr_throttled`가 `nr_periods`와 거의 같다는 것은 주기마다 몫을 다 썼다는 뜻입니다. 이 셸에서 200MB 넘게 메모리를 잡는 프로그램을 돌리면 `max`와 `oom_kill`이 올라갑니다. `cat /proc/pressure/cpu`의 `some avg10=`이 최근 10초 동안 누군가 CPU를 기다린 시간의 비율이고, `systemd-cgls`는 트리 전체를 그려 줍니다.
:::

## 컨테이너 조립 {#assembly}

런타임이 컨테이너 하나를 띄울 때 부르는 시스템 콜을 순서대로 늘어놓으면 이 장의 내용이 다 나옵니다.

::: {.fig src="runtime-assembly.svg"}
컨테이너 런타임의 조립 순서. 단계마다 쓰는 커널 기능이 다르고, 마지막 `execve()` 뒤에는 커널에 "컨테이너"라는 흔적이 따로 남지 않습니다.
:::

1. **네임스페이스를 만들며 자식을 만든다.** `clone3()`에 `CLONE_NEWNS | CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWIPC | CLONE_NEWUTS | CLONE_NEWCGROUP`을 줍니다. `CLONE_INTO_CGROUP`과 cgroup 디렉터리의 fd를 함께 주면 자식이 처음부터 그 cgroup에서 태어납니다.
2. **파일시스템을 꾸민다.** 자식이 새 마운트 네임스페이스에서 전파를 `private`으로 바꾸고, overlayfs로 루트를 조립하고, `/proc`과 `/sys`를 새로 마운트한 뒤 `pivot_root()`를 부릅니다.
3. **네트워크를 잇는다.** 부모가 veth 쌍을 만들어 한쪽 끝을 자식의 네트워크 네임스페이스로 옮깁니다.
4. **한도를 건다.** cgroup 디렉터리의 `cpu.max`, `memory.max`, `pids.max`에 값을 씁니다.
5. **권한을 줄인다.** capability를 필요한 것만 남기고, `no_new_privs`를 세우고, seccomp 필터를 올립니다. 이 단계는 되돌릴 수 없으므로 맨 나중에 합니다.
6. **`execve()`.** 여기서부터는 컨테이너 안의 프로그램입니다.

쿠버네티스의 파드는 이 조립을 조금 다르게 합니다. 파드 안의 컨테이너들은 네트워크와 IPC 네임스페이스를 **함께** 쓰고 마운트 네임스페이스는 따로 씁니다. 그래서 한 파드의 컨테이너끼리는 `localhost`로 통신합니다. 네임스페이스를 종류별로 따로 공유할 수 있다는 `nsproxy`의 구조가 그대로 드러나는 자리입니다.

::: {.note title="v7.3의 네임스페이스 관리"}
네임스페이스를 밖에서 들여다보는 수단이 최근에 늘었습니다. 예전에는 시스템의 네임스페이스 목록을 얻으려면 모든 프로세스의 `/proc/PID/ns/`를 훑어야 했고, 프로세스 없이 fd로만 살아 있는 네임스페이스는 찾을 수 없었습니다. 6.19에서 들어온 `listns()` 시스템 콜은 커널이 관리하는 네임스페이스 트리(`kernel/nstree.c`)에서 식별자 목록을 직접 돌려줍니다. nsfs는 파일 핸들도 지원합니다(`nsfs_export_operations`). 네임스페이스를 가리키는 핸들을 저장해 두었다가 나중에 다시 열 수 있습니다.
:::

## 격리의 한계 {#limits}

네임스페이스는 이름을 가리고 cgroup은 양을 제한합니다. 가리지 못하는 것이 하나 있습니다. **커널 자체**입니다. 컨테이너의 프로세스는 호스트와 같은 시스템 콜 테이블로 같은 커널 코드를 실행합니다. 그 코드의 버그 하나가 모든 컨테이너와 호스트의 경계를 한꺼번에 무너뜨립니다. 네임스페이스에 들어가지 않은 전역 상태도 있습니다. 커널 모듈, 여러 sysctl, 실제 시각을 가리키는 시계가 그렇습니다.

경계를 더 두껍게 하는 길은 둘입니다. 하나는 시스템 콜을 호스트 커널에 닿기 전에 가로채는 것입니다. gVisor 같은 샌드박스는 유저 공간에서 커널의 인터페이스를 다시 구현해, 컨테이너가 호스트 커널에 직접 내는 시스템 콜의 종류를 크게 줄입니다. 다른 하나는 컨테이너마다 가상 머신을 띄워 커널을 따로 주는 것입니다. 하드웨어 가상화가 경계가 됩니다. [23장](ch23.html)의 주제입니다.

::: {.design}
"컨테이너"라는 큰 기능을 커널에 넣지 않은 것은 **메커니즘과 정책의 분리**입니다. 커널은 직교하는 작은 메커니즘 여럿을 줍니다. 네임스페이스 여덟 종류, 컨트롤러 여러 개, capability, seccomp가 각각 독립된 스위치입니다. 무엇을 묶어 "컨테이너"라고 부를지는 유저 공간이 정합니다. 덕분에 같은 부품으로 Docker의 컨테이너, 쿠버네티스의 파드, systemd의 서비스, 브라우저의 탭 샌드박스가 서로 다른 조합으로 만들어집니다. 커널에 `struct container`를 넣었다면 그 가운데 하나의 모양으로 굳었을 것입니다. 치르는 값도 분명합니다. 조합을 올바르게 하는 책임이 런타임에 있고, 빠뜨린 스위치 하나가 탈출구가 됩니다.
:::

## 정리 {#summary}

- 커널에는 컨테이너 객체가 없습니다. 네임스페이스(무엇이 보이는가), cgroup(얼마나 쓰는가), 권한 제한(무엇을 할 수 있는가)을 유저 공간이 조합한 것입니다.
- 태스크는 `nsproxy`로 네임스페이스들을 가리킵니다. 네임스페이스를 바꾸지 않는 `fork()`는 `nsproxy`를 공유하고, 하나라도 바꾸면 복사합니다. PID 네임스페이스는 `struct pid`에서, 유저 네임스페이스는 `cred`에서 나옵니다.
- `struct pid`는 네임스페이스 단계마다 번호를 하나씩 갖습니다. 번호는 조상 네임스페이스에서만 보입니다.
- capability는 유저 네임스페이스에 대해 판정됩니다. 네임스페이스를 만든 사람은 그 안에서 전권을 갖고, 밖에 대해서는 아무것도 갖지 못합니다.
- cgroup v2는 트리가 하나입니다. 컨트롤러는 `subtree_control`로 위에서 내려 주고, 프로세스는 잎에만 둡니다. 태스크는 `css_set` 하나로 모든 컨트롤러의 상태에 닿습니다.
- `cpu.max`를 넘으면 다음 주기까지 스로틀되고, `memory.high`를 넘으면 느려지고, `memory.max`를 넘으면 cgroup 안에서 회수와 OOM이 일어납니다.
- 컨테이너는 호스트와 커널을 공유합니다. 그보다 두꺼운 경계가 필요하면 시스템 콜을 가로채는 샌드박스나 가상 머신을 씁니다.

## 확인 문제 {#quiz}

::: {.q}
프로세스가 `unshare(CLONE_NEWPID)`를 부른 뒤 `getpid()`를 부르면 값이 바뀌어 있습니까? 그 뒤 `fork()`로 만든 자식의 PID는 자식에게 얼마로 보입니까?

::: {.a}
바뀌지 않습니다. 태스크의 `struct pid`는 만들어질 때 `numbers[]`가 정해지고 그 뒤로 바뀌지 않습니다. `unshare(CLONE_NEWPID)`는 `nsproxy`의 `pid_ns_for_children`만 새 네임스페이스로 바꿉니다. 그 뒤의 `fork()`에서 `alloc_pid()`가 새 네임스페이스부터 루트까지 번호를 받으므로, 자식은 새 네임스페이스의 첫 프로세스이고 자기에게 PID 1로 보입니다. 부모가 보는 자식의 PID는 부모 네임스페이스에서의 번호입니다.
:::
:::

::: {.q}
일반 사용자가 유저 네임스페이스와 네트워크 네임스페이스를 새로 만들었습니다. 그 안에서 `ip link add`로 장치를 만드는 것은 되는데, 호스트의 `eth0` 설정을 바꾸는 것은 안 됩니다. `cap_capable_helper()`로 설명해 보세요.

::: {.a}
새 유저 네임스페이스 안에서 이 프로세스는 모든 capability를 갖습니다. 새 네트워크 네임스페이스의 주인(`net->user_ns`)은 이 유저 네임스페이스이므로, `CAP_NET_ADMIN` 검사에서 `target_ns == cred_ns`가 되어 capability 비트를 보고 통과합니다. 호스트의 `eth0`은 초기 네트워크 네임스페이스에 속하고 그 주인은 초기 유저 네임스페이스입니다. `target_ns`가 초기 유저 네임스페이스이면 반복문의 둘째 검사 `ns->level <= cred_ns->level`에 걸려 `-EPERM`이 나옵니다. 대상이 내 네임스페이스의 조상이기 때문입니다.
:::
:::

::: {.q}
cgroup v2에서 프로세스가 들어 있는 cgroup `A`의 `cgroup.subtree_control`에 `+memory`를 쓰면 실패합니다. 왜 이런 규칙이 있습니까? 어떻게 해야 `A` 아래에서 메모리를 나눠 줄 수 있습니까?

::: {.a}
내부 프로세스 금지 규칙입니다. `A`가 자식에게 메모리를 나눠 주면서 자기도 프로세스를 직접 담으면, `A`의 프로세스들과 자식 cgroup들이 `A`의 몫을 두고 형제처럼 다투게 되고 그 사이의 분배를 정할 일관된 방법이 없습니다. 프로세스를 잎에만 두면 컨트롤러는 언제나 cgroup끼리만 비교하면 됩니다. 해결은 `A` 아래에 자식 cgroup을 만들어 `A`의 프로세스를 모두 그리로 옮긴 다음 `subtree_control`에 쓰는 것입니다. 반대 방향의 검사가 `cgroup_migrate_vet_dst()`에 있습니다. `subtree_control`이 켜진 cgroup에 프로세스를 넣으려 하면 `-EBUSY`입니다.
:::
:::

::: {.q}
컨테이너에 `memory.max`만 500MB로 걸었더니 한도 근처에서 프로세스가 갑자기 죽습니다. `memory.high`를 450MB로 함께 걸면 무엇이 달라집니까?

::: {.a}
`memory.max`만 있으면 사용량이 500MB에 닿을 때 `try_charge_memcg()`가 cgroup 안에서 회수를 시도하고, 회수할 것이 없으면 곧바로 OOM 킬이 일어납니다. `memory.high`를 450MB로 두면 그 선을 넘은 순간부터 할당하는 태스크가 회수 일을 직접 하고 유저 모드 복귀 길에 강제로 잠듭니다. 메모리를 늘리는 속도가 꺾이므로 500MB에 닿기 전에 시간이 생깁니다. 그 사이에 `memory.events`의 `high`나 `memory.pressure`를 지켜보던 관리 프로세스가 부하를 줄이거나 한도를 올릴 수 있습니다. `high`는 속도를 늦추는 선이고 `max`는 넘지 못하는 벽입니다.
:::
:::

## 용어 {#terms}

::: {.terms}
네임스페이스 (namespace)
:   전역 자원의 이름 공간을 태스크 묶음마다 따로 갖게 하는 커널 기능.

nsproxy
:   태스크가 속한 네임스페이스들의 포인터를 모은 구조체. 조합이 같은 태스크끼리 공유한다.

struct pid
:   프로세스 하나의 커널 안 정체. 네임스페이스 단계마다의 번호를 `numbers[]`에 담는다.

유저 네임스페이스 (user namespace)
:   uid·gid의 대응표와 capability가 미치는 범위를 정하는 네임스페이스.

veth
:   한쪽 끝에 넣은 패킷이 다른 쪽 끝에서 나오는 가상 이더넷 장치 쌍.

cgroup (control group)
:   태스크를 트리로 묶어 자원 사용을 재고 제한하는 커널 기능.

컨트롤러 (controller)
:   cgroup에서 자원 한 종류를 맡는 코드. `cpu`, `memory`, `io`, `pids` 등.

css (cgroup_subsys_state)
:   한 cgroup에서 한 컨트롤러가 갖는 상태 객체.

css_set
:   태스크 하나가 속한 css들의 묶음. 같은 cgroup의 태스크끼리 공유한다.

스로틀 (throttle)
:   주기당 몫을 다 쓴 cgroup의 태스크를 다음 주기까지 실행하지 않는 일.

PSI (pressure stall information)
:   자원이 모자라 태스크가 기다린 시간의 비율을 재는 계측.

위임 (delegation)
:   cgroup 트리의 일부를 덜 신뢰하는 쪽이 관리하도록 소유권을 넘기는 일.
:::
