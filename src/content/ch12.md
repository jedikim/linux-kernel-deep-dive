::: {.lead}
10기가비트 링크는 초당 80만 개가 넘는 풀사이즈 프레임을 실어 나릅니다. 패킷마다 인터럽트를 한 번씩 받으면 CPU는 인터럽트에 들어갔다 나오는 일만 하다가 끝납니다. 반대로 인터럽트를 끄고 장치를 계속 들여다보면 패킷이 드물 때 CPU를 태웁니다. 리눅스의 수신 경로는 이 둘 사이를 부하에 따라 오갑니다. 이 장은 패킷 하나가 NIC에 도착해 `recv()`를 부른 프로그램의 버퍼에 닿을 때까지를 소스로 따라가며, [11장](ch11.html)의 top half와 bottom half가 실제 서브시스템에서 어떻게 쓰이는지 봅니다.
:::

::: {.goals}
- 패킷 하나가 유저 버퍼에 닿기까지 어떤 실행 컨텍스트를 거치는가?
- NAPI는 인터럽트와 폴링을 어떤 조건으로 오가는가?
- softirq 한 번에 처리하는 패킷 수는 무엇으로 제한되는가?
- softirq와 `recv()`를 부른 태스크는 같은 소켓을 어떻게 나눠 쓰는가?
- RSS, RPS, XDP는 각각 수신 경로의 어느 지점에서 무엇을 바꾸는가?
- 패킷이 버려졌을 때 어디서 왜 버려졌는지 어떻게 알아내는가?
:::

## 수신 경로 한눈에 {#overview}

TCP 세그먼트 하나를 받는 길을 먼저 전체로 봅니다. 드라이버는 인텔 기가비트 NIC용 e1000e를 씁니다. 수신 큐가 하나뿐이라 구조가 단순합니다. 큐가 여러 개인 최신 드라이버도 뼈대는 같습니다.

::: {.fig src="rx-journey.svg"}
패킷은 컨텍스트를 세 번 건넙니다. 장치에서 hardirq로, hardirq에서 softirq로, softirq에서 `recv()`를 부른 태스크로.
:::

눈여겨볼 점은 길이의 불균형입니다. hardirq에서 하는 일은 한 단계뿐이고, 프로토콜 처리는 전부 softirq에 있습니다. 프로세스 컨텍스트가 하는 일은 이미 소켓에 쌓인 데이터를 복사해 가는 것뿐입니다. 이 배치는 [11장](ch11.html)의 원칙을 그대로 따른 것입니다. 인터럽트를 끈 채로는 최소한만 하고, 잠들 필요가 없는 무거운 일은 softirq에서 합니다.

## RX 링과 인터럽트 {#rx-ring}

NIC는 받은 프레임을 스스로 메모리에 씁니다. 어디에 쓸지는 드라이버가 미리 알려 둡니다. 그 약속의 장소가 **RX 링**입니다. 디스크립터의 원형 배열이고, 디스크립터마다 버퍼 하나의 DMA 주소가 적혀 있습니다. e1000e의 기본 크기는 256칸입니다.

::: {.fig src="rx-ring.svg"}
RX 링의 한 순간. NIC는 RDH 자리에 패킷을 쓰고 DD(Descriptor Done) 비트를 세웁니다. 드라이버는 `next_to_clean`부터 DD가 선 칸을 거둬 갑니다.
:::

분업은 이렇습니다. 드라이버는 버퍼를 할당해 디스크립터에 주소를 적고 꼬리 레지스터(RDT)를 전진시켜 "여기까지 써도 된다"고 알립니다. NIC는 프레임이 오면 다음 디스크립터의 버퍼에 DMA로 쓰고, 길이와 상태를 디스크립터에 되적고, 인터럽트를 겁니다. 이때까지 CPU는 아무 일도 하지 않았습니다. 드라이버가 버퍼를 대는 속도보다 패킷이 빨리 오면 빈 버퍼가 바닥나고, NIC는 그 뒤의 프레임을 버립니다. `ethtool -S`의 `rx_no_buffer_count`와 `rx_missed_errors`가 이 상황을 셉니다.

::: {.myth}
"인터럽트 핸들러가 패킷을 NIC에서 메모리로 옮긴다." 오래된 그림에 자주 나오는 설명이지만, 지금의 NIC에서는 인터럽트가 걸린 시점에 패킷이 이미 메인 메모리에 있습니다. NIC가 DMA로 직접 썼기 때문입니다. 핸들러가 할 일은 데이터를 옮기는 것이 아니라 "링에 볼 것이 생겼다"는 사실을 전하는 것입니다.
:::

인터럽트를 받는 핸들러는 짧습니다. MSI-X를 쓸 때의 수신 핸들러 전체입니다.

```{.c file="drivers/net/ethernet/intel/e1000e/netdev.c" line="1953"}
static irqreturn_t e1000_intr_msix_rx(int __always_unused irq, void *data)
{
	struct net_device *netdev = data;
	struct e1000_adapter *adapter = netdev_priv(netdev);
	struct e1000_ring *rx_ring = adapter->rx_ring;

	/* Write the ITR value calculated at the end of the
	 * previous interrupt.
	 */
	if (rx_ring->set_itr) {
		u32 itr = rx_ring->itr_val ?
			  1000000000 / (rx_ring->itr_val * 256) : 0;

		writel(itr, rx_ring->itr_register);
		rx_ring->set_itr = 0;
	}

	if (napi_schedule_prep(&adapter->napi)) {
		adapter->total_rx_bytes = 0;
		adapter->total_rx_packets = 0;
		__napi_schedule_irqoff(&adapter->napi);
	}
	return IRQ_HANDLED;
}
```

읽을 곳은 세 군데입니다.

- 링을 건드리지 않습니다. 패킷이 몇 개 왔는지조차 보지 않습니다.
- ITR 레지스터에 쓰는 값은 **인터럽트 병합**(interrupt coalescing) 설정입니다. NIC가 인터럽트를 걸기 전에 얼마나 기다릴지를 정합니다. 기다리는 동안 온 패킷은 인터럽트 하나로 묶입니다. `ethtool -C`로 조절하는 값이 이것입니다.
- `napi_schedule_prep()`이 참이면 `__napi_schedule_irqoff()`를 부릅니다. 뒷일을 softirq에 맡기는 자리입니다.

`__napi_schedule_irqoff()`의 끝은 이렇습니다.

```{.c file="net/core/dev.c" line="5070"}
use_local_napi:
	DEBUG_NET_WARN_ON_ONCE(!list_empty(&napi->poll_list));
	list_add_tail(&napi->poll_list, &sd->poll_list);
	WRITE_ONCE(napi->list_owner, smp_processor_id());
	/* If not called from net_rx_action()
	 * we have to raise NET_RX_SOFTIRQ.
	 */
	if (!sd->in_net_rx_action)
		raise_softirq_irqoff(NET_RX_SOFTIRQ);
```

`sd`는 이 CPU의 `softnet_data`입니다. 네트워크 스택이 CPU마다 하나씩 두는 구조체로, 폴링할 NAPI 인스턴스의 목록 `poll_list`가 여기 있습니다. softirq는 비트 하나로 예약되므로 "무엇을 할지"는 이렇게 CPU별 목록에 따로 걸어 둡니다. 이 장치의 인터럽트는 e1000e가 MSI-X를 설정할 때 켜 둔 자동 마스크 기능으로 이미 막혀 있습니다. 폴링이 끝날 때까지 이 큐는 인터럽트를 걸지 않습니다.

## NAPI: 인터럽트와 폴링 사이 {#napi}

**NAPI**는 방금 본 "인터럽트를 막고 폴링을 예약한다"는 약속에 붙은 이름입니다. 2.4 시절의 "New API"에서 온 이름이고 지금은 약자로서의 뜻이 없습니다.

NAPI 이전의 드라이버는 패킷마다 인터럽트를 받아 핸들러에서 패킷을 꺼냈습니다. 부하가 낮을 때는 문제가 없습니다. 부하가 오르면 인터럽트가 softirq보다 우선하므로, CPU는 패킷을 링에서 꺼내 큐에 쌓는 일만 하고 쌓인 패킷을 처리할 시간을 얻지 못합니다. 큐가 넘쳐 패킷을 버리는데, 버릴 패킷을 꺼내느라 바쁜 상태입니다. 들어오는 양이 늘수록 처리량이 0에 가까워지는 이 현상을 **수신 라이브록**(receive livelock)이라고 합니다.

::: {.fig src="napi-modes.svg"}
NAPI 인스턴스 하나의 상태. 패킷이 드물면 왼쪽에 머물고, 몰려오면 오른쪽에 머뭅니다. 전환을 정하는 것은 타이머가 아니라 "이번 poll에서 링을 다 비웠는가"입니다.
:::

폴링 모드에서는 인터럽트가 오지 않습니다. softirq가 여유 있을 때 링을 훑고, 처리 속도가 따라가지 못하면 패킷은 NIC의 링에서 버려집니다. CPU를 한 사이클도 쓰지 않고 버려지므로 과부하에서도 처리량이 유지됩니다.

`NET_RX_SOFTIRQ`의 핸들러가 폴링 목록을 돕니다.

```{.c file="net/core/dev.c" line="8011"}
static __latent_entropy void net_rx_action(void)
{
	struct softnet_data *sd = this_cpu_ptr(&softnet_data);
	unsigned long time_limit = jiffies +
		usecs_to_jiffies(READ_ONCE(net_hotdata.netdev_budget_usecs));
	struct bpf_net_context __bpf_net_ctx, *bpf_net_ctx;
	int budget = READ_ONCE(net_hotdata.netdev_budget);
	LIST_HEAD(list);
	LIST_HEAD(repoll);
	/* ... */
	for (;;) {
		struct napi_struct *n;
		/* ... */
		n = list_first_entry(&list, struct napi_struct, poll_list);
		budget -= napi_poll(n, &repoll);

		/* If softirq window is exhausted then punt.
		 * Allow this to run for 2 jiffies since which will allow
		 * an average latency of 1.5/HZ.
		 */
		if (unlikely(budget <= 0 ||
			     time_after_eq(jiffies, time_limit))) {
			/* Pairs with READ_ONCE() in softnet_seq_show() */
			WRITE_ONCE(sd->time_squeeze, sd->time_squeeze + 1);
			break;
		}
	}

	local_irq_disable();

	list_splice_tail_init(&sd->poll_list, &list);
	list_splice_tail(&repoll, &list);
	list_splice(&list, &sd->poll_list);
	if (!list_empty(&sd->poll_list))
		__raise_softirq_irqoff(NET_RX_SOFTIRQ);
	/* ... */
}
```

`napi_poll()`은 드라이버의 `poll()`을 부릅니다. e1000e의 것입니다.

```{.c file="drivers/net/ethernet/intel/e1000e/netdev.c" line="2675"}
static int e1000e_poll(struct napi_struct *napi, int budget)
{
	/* ... */
	if (!adapter->msix_entries ||
	    (adapter->rx_ring->ims_val & adapter->tx_ring->ims_val))
		tx_cleaned = e1000_clean_tx_irq(adapter->tx_ring);

	adapter->clean_rx(adapter->rx_ring, &work_done, budget);

	if (!tx_cleaned || work_done == budget)
		return budget;

	/* Exit the polling mode, but don't re-enable interrupts if stack might
	 * poll us due to busy-polling
	 */
	if (likely(napi_complete_done(napi, work_done))) {
		if (adapter->itr_setting & 3)
			e1000_set_itr(adapter);
		if (!test_bit(__E1000_DOWN, &adapter->state)) {
			if (adapter->msix_entries)
				ew32(IMS, adapter->rx_ring->ims_val);
			else
				e1000_irq_enable(adapter);
		}
	}

	return work_done;
}
```

두 코드에 한도가 세 겹으로 있습니다.

| 한도 | v7.3 기본값 | 넘으면 |
|---|---|---|
| `poll()` 한 번의 `budget` | 64 (`NAPI_POLL_WEIGHT`) | `budget`을 그대로 돌려주고 폴링 모드에 남는다 |
| softirq 한 번의 패킷 수 | 300 (`netdev_budget`) | `time_squeeze`를 올리고 softirq를 다시 예약한다 |
| softirq 한 번의 시간 | 2틱 (`netdev_budget_usecs`) | 위와 같다 |

`e1000e_poll()`의 갈림길이 그림 12-3의 두 화살표입니다. `work_done == budget`이면 링에 패킷이 더 있다는 뜻이므로 `budget`을 돌려주고, `net_rx_action()`이 이 인스턴스를 목록 끝에 다시 겁니다. 그보다 적게 처리했으면 링이 비었다는 뜻입니다. `napi_complete_done()`으로 폴링을 끝내고 `IMS` 레지스터에 써서 장치 인터럽트를 다시 켭니다.

`net_rx_action()`이 한도를 넘겨 빠져나오면 `NET_RX_SOFTIRQ`를 다시 세웁니다. 그 뒤는 [11장](ch11.html)에서 본 `handle_softirqs()`의 몫입니다. 2ms와 재시작 10회 안에서는 다시 불리고, 그것도 넘으면 `ksoftirqd`로 넘어갑니다. 네트워크의 한도 위에 softirq 공통의 한도가 한 겹 더 있는 셈입니다.

::: {.design}
NAPI는 타이머도 부하 측정도 없이 적응합니다. 규칙은 하나입니다. "일을 다 끝냈으면 인터럽트를 켜고, 못 끝냈으면 끄고 계속한다." 부하가 낮으면 poll은 매번 링을 비우므로 패킷마다 인터럽트를 받고, 부하가 높으면 poll이 budget을 채우므로 인터럽트 없이 돕니다. 모드를 고르는 정책을 따로 두지 않고, 일이 남았는지라는 사실 하나가 모드를 정하게 한 것입니다. 인터럽트는 지연이 짧고 폴링은 처리량이 높다는 두 성질을 부하에 맞춰 섞는 이 구조는, 스핀하다가 잠드는 뮤텍스([14장](ch14.html))나 블록 계층의 폴링 I/O에도 되풀이됩니다.
:::

`napi_schedule_prep()`도 한 번 봐 둘 만합니다. 이 함수는 `napi->state`의 `NAPI_STATE_SCHED` 비트를 `try_cmpxchg()`로 세우고, 이미 서 있었으면 거짓을 돌려줍니다. 비트를 세운 쪽이 이 NAPI 인스턴스의 소유자가 되고, `napi_complete_done()`이 비트를 내릴 때까지 다른 누구도 `poll()`을 부르지 못합니다. 그래서 `poll()`은 링을 만질 때 락을 잡지 않습니다. 같은 softirq가 여러 CPU에서 동시에 돌 수 있어도, 큐 하나는 한 번에 한 CPU만 폴링합니다.

::: {.old}
옛 자료의 수신 경로는 `do_IRQ()` → 드라이버 핸들러 → `netif_rx()` → CPU별 backlog 큐 → `do_softirq()` → `net_rx_action()` → `netif_receive_skb()`입니다. 핸들러가 패킷마다 skb를 만들어 `netif_rx()`로 큐에 넣는 구조입니다. v7.3의 물리 NIC 드라이버는 핸들러에서 패킷을 건드리지 않습니다. `netif_rx()`와 backlog 큐는 남아 있지만 쓰임이 달라졌습니다. `softnet_data` 안의 `backlog`라는 가짜 NAPI 인스턴스가 그 큐를 폴링하고, 루프백 같은 가상 장치와 뒤에 나올 RPS가 이것을 씁니다. `do_softirq()`와 패킷마다 부르던 `netif_receive_skb()`가 무엇으로 바뀌었는지는 11장과 다음 절에 있습니다.
:::

## skb와 GRO {#skb-gro}

`adapter->clean_rx`가 가리키는 함수가 링에서 패킷을 꺼냅니다.

```{.c file="drivers/net/ethernet/intel/e1000e/netdev.c" line="954"}
	while (staterr & E1000_RXD_STAT_DD) {
		struct sk_buff *skb;

		if (*work_done >= work_to_do)
			break;
		(*work_done)++;
		dma_rmb();	/* read descriptor and rx_buffer_info after status DD */

		skb = buffer_info->skb;
		buffer_info->skb = NULL;
		/* ... */
		dma_unmap_single(&pdev->dev, buffer_info->dma,
				 adapter->rx_buffer_len, DMA_FROM_DEVICE);
		buffer_info->dma = 0;

		length = le16_to_cpu(rx_desc->wb.upper.length);
		/* ... */
		skb_put(skb, length);

		/* Receive Checksum Offload */
		e1000_rx_checksum(adapter, staterr, skb);

		e1000_rx_hash(netdev, rx_desc->wb.lower.hi_dword.rss, skb);

		e1000_receive_skb(adapter, netdev, skb, staterr,
				  rx_desc->wb.upper.vlan);
		/* ... */
	}
```

DD 비트가 선 디스크립터를 `work_to_do`(budget)개까지 돕니다. `dma_rmb()`는 DD를 읽은 뒤에 나머지 필드를 읽도록 순서를 강제하는 메모리 배리어입니다([13장](ch13.html)). NIC가 이미 체크섬을 검증했고 흐름 해시도 계산해 두었으므로, 드라이버는 그 결과를 skb에 옮겨 적기만 합니다.

**`sk_buff`**(줄여서 skb)는 패킷 하나를 나타내는 구조체입니다. 패킷 데이터를 품지 않고 가리킵니다.

::: {.fig src="skb-layout.svg"}
skb는 메타데이터이고 데이터는 따로 있습니다. 헤더를 붙이고 떼는 일은 복사가 아니라 포인터 이동입니다.
:::

포인터 넷이 버퍼 하나의 경계를 가리킵니다. 수신 길에서 계층을 하나 오를 때마다 `data`가 헤더 길이만큼 뒤로 갑니다. 이더넷 헤더를 지나면 IP 헤더가, IP를 지나면 TCP 헤더가 `data` 자리에 옵니다. 버퍼 끝에는 `skb_shared_info`가 붙어 있고, 선형 버퍼에 다 담지 못한 데이터는 그 안의 `frags[]`가 page 조각으로 가리킵니다.

e1000e는 skb를 미리 만들어 링에 걸어 두는 옛 방식을 씁니다. 요즘 드라이버는 page를 링에 걸어 두고 패킷이 온 뒤에 skb를 만들며, page는 **page_pool**이라는 큐별 재활용 풀에서 받습니다. 패킷마다 page를 할당하고 DMA 매핑하는 비용을 없애기 위해서입니다.

### 묶어서 올리기

`e1000_receive_skb()`는 skb를 `napi_gro_receive()`에 넘깁니다. **GRO**(generic receive offload)는 같은 흐름의 연속된 세그먼트를 skb 하나로 합칩니다.

::: {.fig src="gro-merge.svg"}
1448바이트 세그먼트 여섯 개가 skb 둘이 됩니다. 프로토콜 스택에게는 큰 패킷 두 개가 온 것으로 보입니다.
:::

TCP 처리 비용의 대부분은 바이트 수가 아니라 패킷 수에 비례합니다. 헤더 해석, 소켓 조회, 락, 큐 삽입은 패킷마다 한 번씩입니다. GRO는 이 횟수를 줄입니다. 합칠 수 없는 패킷과 합치기를 마친 패킷은 한 개씩 올라가지 않고 목록에 모입니다.

```{.c file="include/net/gro.h" line="537"}
static inline void gro_normal_one(struct gro_node *gro, struct sk_buff *skb,
				  int segs)
{
	list_add_tail(&skb->list, &gro->rx_list);
	gro->rx_count += segs;
	if (gro->rx_count >= READ_ONCE(net_hotdata.gro_normal_batch))
		gro_normal_list(gro);
}
```

`gro_normal_batch`(기본 8)만큼 모이거나 poll이 끝나면 `netif_receive_skb_list_internal()`이 목록째 위로 넘깁니다. IP 계층도 목록을 받는 `ip_list_rcv()`를 갖고 있습니다. 한 패킷이 함수 열 개를 차례로 지나는 대신 패킷 여덟 개가 함수 하나를 지나고 다음 함수로 갑니다. 명령어 캐시가 식지 않고, 간접 호출의 횟수가 줄어듭니다.

## IP와 TCP를 오르다 {#stack}

목록의 skb는 하나씩 `__netif_receive_skb_core()`를 지납니다. 이 함수는 `tcpdump` 같은 패킷 탭에 사본을 주고, tc 훅을 실행하고, `skb->protocol`을 보고 프로토콜 핸들러를 고릅니다. IPv4라면 `ip_rcv()`(목록이면 `ip_list_rcv()`)입니다.

```{.c file="net/ipv4/ip_input.c" line="603"}
int ip_rcv(struct sk_buff *skb, struct net_device *dev, struct packet_type *pt,
	   struct net_device *orig_dev)
{
	struct net *net = dev_net(dev);

	skb = ip_rcv_core(skb, net);
	if (skb == NULL)
		return NET_RX_DROP;

	return NF_HOOK(NFPROTO_IPV4, NF_INET_PRE_ROUTING,
		       net, NULL, skb, dev, NULL,
		       ip_rcv_finish);
}
```

`ip_rcv_core()`가 헤더 길이, 버전, 체크섬을 검사합니다. `NF_HOOK()`은 이 책에서 자주 볼 모양입니다. 넷필터 훅을 실행하고, 훅이 패킷을 통과시키면 마지막 인자의 함수를 이어서 부릅니다. `ip_rcv_finish()`는 라우팅 테이블을 찾아 이 패킷이 로컬로 가는지 다른 곳으로 전달되는지 정합니다. 로컬이면 `ip_local_deliver()`가 `NF_INET_LOCAL_IN` 훅을 거쳐 IP 헤더의 프로토콜 번호에 맞는 핸들러를 부릅니다. TCP면 `tcp_v4_rcv()`입니다.

## 소켓: softirq와 태스크가 만나는 곳 {#socket}

`tcp_v4_rcv()`는 주소와 포트 네 개로 해시 테이블에서 소켓을 찾습니다. 찾은 뒤가 이 장에서 가장 미묘한 자리입니다.

```{.c file="net/ipv4/tcp_ipv4.c" line="2242"}
	sk_incoming_cpu_update(sk);

	bh_lock_sock_nested(sk);
	tcp_segs_in(tcp_sk(sk), skb);
	ret = 0;
	if (!sock_owned_by_user(sk)) {
		ret = tcp_v4_do_rcv(sk, skb);
	} else {
		drop_reason = tcp_add_backlog(sk, skb);
		if (drop_reason)
			goto discard_and_relse;
	}
	bh_unlock_sock(sk);
```

소켓은 두 컨텍스트가 만집니다. 패킷을 넣는 softirq와, `recv()`나 `send()`를 부른 태스크입니다. 태스크는 유저 메모리로 복사하다가 페이지 폴트로 잠들 수 있으므로 스핀락을 쥔 채 일할 수 없습니다. 그렇다고 softirq가 뮤텍스를 기다리며 잠들 수도 없습니다. 소켓 락은 이 문제를 두 층으로 풉니다.

::: {.fig src="socket-handoff.svg"}
소켓 락의 두 층. 스핀락은 큐를 고치는 짧은 순간만 쥐고, "태스크가 쓰는 중"이라는 표시는 플래그로 남깁니다.
:::

- `bh_lock_sock()`은 소켓 안의 스핀락 `sk_lock.slock`입니다. 짧게만 쥡니다.
- `sk_lock.owned`는 "태스크가 이 소켓을 쓰는 중"이라는 플래그입니다. 태스크는 `lock_sock()`에서 스핀락을 잡고 이 플래그를 세운 뒤 스핀락을 풉니다. 그 뒤로는 잠들어도 됩니다.

softirq는 스핀락을 잡고 플래그를 봅니다. 꺼져 있으면 `tcp_v4_do_rcv()`로 TCP 처리를 끝까지 합니다. 순서 번호를 확인하고, 데이터를 `sk_receive_queue`에 넣고, ACK를 준비하고, `sk_data_ready()`로 잠든 읽는 쪽을 깨웁니다. 플래그가 켜져 있으면 TCP 상태를 건드리지 않고 `sk_backlog`에 skb를 걸어 두고 떠납니다. 미뤄 둔 일은 태스크가 소켓을 놓을 때 처리합니다.

```{.c file="net/core/sock.c" line="3864"}
void release_sock(struct sock *sk)
{
	spin_lock_bh(&sk->sk_lock.slock);

	if (unlikely(sk->sk_backlog.tail))
		__release_sock(sk);

	if (sk->sk_prot->release_cb) {
		if (!tcp_release_cb_cond(sk))
			sk->sk_prot->release_cb(sk);
	}
	sock_release_ownership(sk);
	if (unlikely(waitqueue_active(&sk->sk_lock.wq)))
		wake_up(&sk->sk_lock.wq);

	spin_unlock_bh(&sk->sk_lock.slock);
}
```

`__release_sock()`이 backlog의 skb마다 `tcp_v4_do_rcv()`를 부릅니다. softirq가 하려던 일을 태스크가 자기 시간으로 대신하는 것입니다. 급한 쪽(softirq)은 기다리지 않고, 느긋한 쪽(태스크)이 밀린 일을 떠맡습니다. `spin_lock_bh()`가 쓰인 이유는 [13장](ch13.html)의 주제입니다. 태스크가 이 스핀락을 쥔 채 같은 CPU에서 softirq가 끼어들어 같은 락을 잡으려 하면 교착이기 때문입니다.

여정의 마지막은 `tcp_recvmsg()`입니다. `lock_sock()`으로 소켓을 쥐고, `sk_receive_queue`의 skb에서 유저 버퍼로 복사하고, 읽을 것이 없으면 `sk_wait_data()`로 잠들고, `release_sock()`으로 놓습니다. 패킷이 NIC에 도착한 뒤 처음으로 데이터가 복사되는 자리입니다.

## 여러 CPU로 펼치기 {#scaling}

지금까지의 길은 CPU 하나에서 일어났습니다. 링이 하나면 NAPI도 하나이고, 한 번에 한 CPU만 그것을 폴링합니다. 코어가 수십 개여도 수신 처리량은 코어 하나에 묶입니다.

::: {.fig src="rss-rps.svg"}
펼치는 지점이 다릅니다. RSS는 인터럽트 이전에, RPS는 드라이버의 poll 이후에 나눕니다.
:::

**RSS**(receive side scaling)는 NIC가 합니다. 수신 큐를 여러 개 두고, 패킷의 주소와 포트를 해시한 값으로 간접 테이블을 찾아 큐를 고릅니다. 큐마다 MSI-X 벡터와 NAPI 인스턴스가 따로 있고, 벡터의 친화성([10장](ch10.html))이 큐를 CPU에 잇습니다. 같은 연결의 패킷은 해시가 같으므로 늘 같은 큐, 같은 CPU로 갑니다. 연결 안에서 순서가 뒤바뀌지 않고, 그 연결의 소켓이 한 CPU의 캐시에 머뭅니다.

**RPS**(receive packet steering)는 같은 일을 커널이 소프트웨어로 합니다.

```{.c file="net/core/dev.c" line="6516"}
#ifdef CONFIG_RPS
	if (static_branch_unlikely(&rps_needed)) {
		list_for_each_entry_safe(skb, next, head, list) {
			struct rps_dev_flow voidflow, *rflow = &voidflow;
			int cpu = get_rps_cpu(skb->dev, skb, &rflow);

			if (cpu >= 0) {
				/* Will be handled, remove from list */
				skb_list_del_init(skb);
				enqueue_to_backlog(skb, cpu, &rflow->last_qtail);
			}
		}
	}
#endif
```

GRO를 마친 목록이 프로토콜 스택으로 들어가기 직전입니다. `get_rps_cpu()`가 흐름 해시로 대상 CPU를 고르면, skb를 그 CPU의 `softnet_data`에 있는 backlog 큐에 넣고 IPI로 깨웁니다. 앞 절에서 말한 backlog NAPI가 여기서 쓰입니다. **RFS**(receive flow steering)는 한 걸음 더 가서, 해시가 아니라 "이 흐름을 `recv()`하는 태스크가 마지막으로 돈 CPU"를 고릅니다. 송신 쪽에는 CPU마다 쓸 송신 큐를 정하는 **XPS**가 있습니다.

네 기법의 목표는 같습니다. 한 흐름의 일을 한 CPU에 모으고, 서로 다른 흐름을 서로 다른 CPU로 흩습니다. 한 CPU에 모으면 락 경합과 캐시 라인 이동이 줄고, 흩으면 코어를 다 씁니다.

::: {.lab}
수신 큐와 인터럽트가 CPU에 어떻게 걸려 있는지 봅니다. 인터페이스 이름은 `ip -br link`로 확인해 바꿔 넣습니다.

```console
$ ethtool -l eth0                # 큐(채널) 수
$ ethtool -c eth0                # 인터럽트 병합 설정 (rx-usecs 등)
$ grep eth0 /proc/interrupts     # 큐별 IRQ가 어느 CPU에서 몇 번 났는지
$ cat /sys/class/net/eth0/queues/rx-0/rps_cpus
$ ethtool -S eth0 | grep -iE 'miss|drop|no_buffer'
```

softirq 쪽 통계는 `/proc/net/softnet_stat`입니다. 한 줄이 CPU 하나이고 값은 16진수입니다.

```console
$ cat /proc/net/softnet_stat
0002a5f1 00000000 0000001c 00000000 ...
0000c3d2 00000000 00000000 00000000 ...
```

첫째 열은 그 CPU가 처리한 패킷 수, 둘째 열은 backlog 큐가 차서 버린 수, 셋째 열이 `time_squeeze`입니다. 셋째 열이 꾸준히 늘면 `net_rx_action()`이 한도에 걸려 일을 남기고 나온다는 뜻입니다. `sysctl net.core.netdev_budget`을 올리기 전에, 한 CPU에 큐가 몰려 있지 않은지부터 봅니다.

패킷이 어느 태스크의 문맥에서 처리되는지도 볼 수 있습니다. `ksoftirqd`가 많이 나오면 인터럽트 복귀 길에서 다 처리하지 못하고 있다는 뜻입니다.

```console
# bpftrace -e 'tracepoint:net:netif_receive_skb { @[comm] = count(); }'
```
:::

## 더 아래로, 더 한꺼번에 {#xdp}

skb를 만들고 스택을 오르는 비용조차 아까운 경우가 있습니다. DDoS 패킷을 버리는 방화벽은 패킷의 첫 수십 바이트만 보면 되고, 로드 밸런서는 헤더를 고쳐 다시 내보내면 됩니다.

::: {.fig src="hooks.svg"}
수신 경로의 훅. 같은 "버린다"는 결정도 위에서 내릴수록 쌉니다.
:::

**XDP**(express data path)는 그림의 맨 위, 드라이버의 poll 안에서 BPF 프로그램을 실행합니다. skb가 아직 없고, 프로그램은 링의 버퍼를 가리키는 `xdp_buff`만 받습니다. virtio_net 드라이버가 프로그램의 판정을 처리하는 코드입니다.

```{.c file="drivers/net/virtio_net.c" line="1694"}
	act = bpf_prog_run_xdp(xdp_prog, xdp);
	u64_stats_inc(&stats->xdp_packets);

	switch (act) {
	case XDP_PASS:
		return act;

	case XDP_TX:
		u64_stats_inc(&stats->xdp_tx);
		xdpf = xdp_convert_buff_to_frame(xdp);
		/* ... */
		err = virtnet_xdp_xmit(dev, 1, &xdpf, 0);
		/* ... */
		*xdp_xmit |= VIRTIO_XDP_TX;
		return act;

	case XDP_REDIRECT:
		u64_stats_inc(&stats->xdp_redirects);
		err = xdp_do_redirect(dev, xdp, xdp_prog);
		if (err)
			return XDP_DROP;

		*xdp_xmit |= VIRTIO_XDP_REDIR;
		return act;

	default:
		bpf_warn_invalid_xdp_action(dev, xdp_prog, act);
		fallthrough;
	case XDP_ABORTED:
		trace_xdp_exception(dev, xdp_prog, act);
		fallthrough;
	case XDP_DROP:
		return XDP_DROP;
	}
```

판정은 다섯 가지입니다. `XDP_DROP`은 버퍼를 풀에 돌려주고 끝냅니다. `XDP_PASS`는 평소처럼 skb를 만들어 올립니다. `XDP_TX`는 받은 NIC로 되쏩니다. `XDP_REDIRECT`는 다른 NIC, 다른 CPU, 또는 유저 공간의 **AF_XDP** 소켓으로 보냅니다. `XDP_ABORTED`는 프로그램 오류입니다. BPF 프로그램이 어떻게 검증되고 실행되는지는 [24장](ch24.html)에서 다룹니다.

그림의 셋째 단에 있는 tc 훅에도 BPF 프로그램을 붙일 수 있습니다. skb가 만들어진 뒤라 XDP보다 비싸지만, GRO로 합쳐진 패킷을 보고 skb의 메타데이터를 모두 쓸 수 있습니다. 컨테이너 네트워킹 도구들이 이 훅을 많이 씁니다.

수신 경로의 다른 개선들도 방향이 같습니다. 건너뛸 수 있는 단계를 건너뛰고, 한 번 깨어났을 때 많이 처리합니다.

- **busy polling**: `recv()`나 `epoll_wait()`를 부른 태스크가 인터럽트를 기다리지 않고 직접 NAPI poll을 돌립니다. CPU를 써서 지연을 줄입니다.
- **스레드 NAPI**: poll을 softirq 대신 `napi/장치-ID` 커널 스레드에서 돌립니다. 스케줄러가 우선순위와 CPU를 정할 수 있게 됩니다. softirq를 스레드로 옮기는 11장의 흐름과 같은 맥락입니다.
- **IRQ 유예와 중단**: 링을 비운 뒤에도 인터럽트를 바로 켜지 않고 타이머로 한 번 더 폴링하거나(`napi_defer_hard_irqs`, `gro_flush_timeout`), 애플리케이션이 `epoll_wait()`로 데이터를 계속 가져가는 동안 인터럽트를 아예 꺼 둡니다(`irq-suspend-timeout`). 이 값들은 NAPI 인스턴스마다 netlink로 설정합니다.
- **io_uring 제로카피 수신**: NIC가 헤더와 페이로드를 나눠 받게 하고, 페이로드를 유저 메모리에 직접 받습니다. 헤더는 평소처럼 커널 TCP 스택이 처리합니다. 마지막 단계의 복사가 사라집니다.

::: {.design}
이 장에 나온 기법을 세 가지 발상으로 묶을 수 있습니다. 첫째, **적응**입니다. NAPI는 부하에 따라 인터럽트와 폴링을 오갑니다. 둘째, **묶음**입니다. 인터럽트 병합은 인터럽트를, budget은 softirq 실행을, GRO는 패킷을, 목록 수신은 함수 호출을 묶습니다. 고정 비용이 있는 일은 한 번에 여러 개를 하면 싸집니다. 셋째, **일찍 결정하기**입니다. XDP는 버릴 패킷을 skb를 만들기 전에 버립니다. 세 발상 모두 지연 시간을 조금 내주고 처리량을 얻는 거래이고, 그래서 전부 끄거나 조절하는 손잡이가 달려 있습니다. 성능 기능을 넣을 때 "언제 손해인가"를 함께 적고 끌 방법을 주는 것은 커널 네트워크 코드의 일관된 습관입니다.
:::

## 송신 경로와 드롭 추적 {#tx-drops}

송신은 수신을 거꾸로 걷습니다. 대부분 `send()`를 부른 태스크의 문맥에서 일어납니다.

1. `tcp_sendmsg()`가 유저 데이터를 skb에 복사해 소켓의 송신 큐에 넣습니다.
2. `tcp_write_xmit()`이 혼잡 윈도가 허락하는 만큼 꺼내 TCP 헤더를 붙이고 `ip_queue_xmit()`으로 넘깁니다.
3. IP 계층이 경로를 찾고 헤더를 붙이고 넷필터 훅을 거칩니다.
4. `__dev_queue_xmit()`이 장치의 **qdisc**(큐잉 규율)에 넣습니다. 여기서 순서와 속도가 정해집니다.
5. `dev_hard_start_xmit()`이 드라이버의 `ndo_start_xmit()`을 부릅니다. 드라이버는 TX 링에 디스크립터를 채우고 NIC에 알립니다.
6. NIC가 보내고 나면 인터럽트를 걸고, NAPI poll이 보낸 skb를 해제합니다. 앞의 `e1000e_poll()`에서 `e1000_clean_tx_irq()`를 부르던 자리입니다.

수신의 GRO에 대응하는 것이 **TSO/GSO**입니다. TCP는 MSS보다 훨씬 큰 skb 하나를 내려보내고, 쪼개는 일은 NIC(TSO)나 드라이버 직전의 커널 코드(GSO)가 합니다. 스택을 내려가는 횟수가 줄어듭니다. **BQL**(byte queue limits)은 TX 링에 쌓아 둘 바이트 수에 상한을 둡니다. 링이 깊으면 패킷이 qdisc가 아니라 링에서 기다리게 되고, qdisc의 우선순위와 공정성 정책이 힘을 잃기 때문입니다.

### 버려진 패킷 찾기

여정의 모든 단계에서 패킷이 버려질 수 있습니다. 링이 차서, 체크섬이 틀려서, 넷필터 규칙에 걸려서, 소켓이 없어서, 수신 버퍼가 차서입니다. 예전에는 버리는 코드가 모두 `kfree_skb()`를 불러서 어디서 왜 버렸는지 알기 어려웠습니다. 지금은 이유를 함께 넘깁니다.

```{.c file="include/net/dropreason-core.h" line="138"}
enum skb_drop_reason {
	/**
	 * @SKB_NOT_DROPPED_YET: skb is not dropped yet (used for no-drop case)
	 */
	SKB_NOT_DROPPED_YET = 0,
	/** @SKB_CONSUMED: packet has been consumed */
	SKB_CONSUMED,
	/** @SKB_DROP_REASON_NOT_SPECIFIED: drop reason is not specified */
	SKB_DROP_REASON_NOT_SPECIFIED,
	/**
	 * @SKB_DROP_REASON_NO_SOCKET: no valid socket that can be used.
	 * Reason could be one of three cases:
	 * 1) no established/listening socket found during lookup process
	 * 2) no valid request socket during 3WHS process
	 * 3) no valid child socket during 3WHS process
	 */
	SKB_DROP_REASON_NO_SOCKET,
```

v7.3에는 이런 이유가 120개쯤 정의되어 있습니다. `kfree_skb_reason(skb, reason)`은 skb를 해제하면서 `skb:kfree_skb` 추적점에 이유와 호출 위치를 남깁니다. 정상적으로 처리를 마친 skb는 `consume_skb()`로 해제해 이 추적점에 나타나지 않게 합니다.

::: {.lab}
버려지는 패킷을 이유별로 봅니다.

```console
# perf record -e skb:kfree_skb -a -- sleep 10
# perf script | head
  ... skb:kfree_skb: skbaddr=... rx_sk=... protocol=2048 location=tcp_v4_rcv+0x... reason: NO_SOCKET
```

`location`은 버린 함수, `reason`은 위 열거형에서 접두사를 뗀 이름입니다. 닫힌 포트로 온 SYN은 `NO_SOCKET`, 수신 버퍼가 찬 UDP 소켓은 `SOCKET_RCVBUFF`로 나옵니다. `dropwatch -l kas`도 같은 추적점을 씁니다.
:::

## 정리 {#summary}

- NIC는 DMA로 RX 링의 버퍼에 패킷을 쓰고 인터럽트를 겁니다. hardirq 핸들러는 패킷을 건드리지 않고 NAPI를 예약합니다.
- NAPI는 poll이 링을 다 비웠으면 인터럽트를 켜고, budget을 채웠으면 끈 채 계속 폴링합니다. 부하에 따라 두 모드를 저절로 오갑니다.
- softirq 한 번의 수신 처리는 poll당 64개, 전체 300개, 2틱으로 제한되고, 넘으면 `time_squeeze`가 오릅니다.
- skb는 패킷 데이터를 가리키는 메타데이터입니다. GRO와 목록 수신은 패킷을 묶어 스택을 오르는 횟수를 줄입니다.
- 소켓은 스핀락과 소유 플래그의 두 층으로 보호됩니다. 태스크가 소켓을 쥔 동안 온 세그먼트는 backlog에 쌓였다가 `release_sock()`에서 처리됩니다.
- RSS는 NIC에서, RPS는 커널에서 흐름을 CPU로 나눕니다. 한 흐름은 한 CPU에 모읍니다.
- XDP는 skb를 만들기 전에 드라이버 안에서 BPF 프로그램으로 패킷의 운명을 정합니다.
- 패킷을 버리는 코드는 이유를 남기고, `skb:kfree_skb` 추적점으로 볼 수 있습니다.

## 확인 문제 {#quiz}

::: {.q}
패킷이 1초에 100개 오는 서버와 100만 개 오는 서버에서, e1000e의 수신 큐 하나가 1초에 받는 하드웨어 인터럽트 수는 대략 어떻게 다릅니까? 100만 개 쪽이 100만 번이 아닌 이유는 무엇입니까?

::: {.a}
100개 쪽은 인터럽트 병합이 없다면 약 100번입니다. 패킷이 올 때마다 인터럽트가 걸리고, poll이 링을 비운 뒤 `napi_complete_done()`으로 인터럽트를 다시 켜기 때문입니다. 100만 개 쪽은 훨씬 적습니다. 첫 인터럽트 뒤로 장치 인터럽트는 막혀 있고, poll이 매번 budget을 채워 `budget`을 돌려주므로 NAPI는 폴링 모드에 머뭅니다. 링이 비는 순간에만 인터럽트가 다시 켜집니다. 부하가 높을수록 패킷당 인터럽트 수는 0에 가까워집니다.
:::
:::

::: {.q}
`/proc/net/softnet_stat`의 셋째 열이 CPU 0에서만 빠르게 늘고 있습니다. 무슨 일이 일어나고 있고, 무엇을 확인해야 합니까?

::: {.a}
셋째 열은 `time_squeeze`입니다. `net_rx_action()`이 `netdev_budget`(300개)이나 `netdev_budget_usecs`(2틱)에 걸려 폴링 목록에 일을 남긴 채 빠져나온 횟수입니다. CPU 0에만 몰려 있다면 수신 처리가 CPU 0에 집중되어 있다는 뜻입니다. `/proc/interrupts`에서 NIC의 큐별 IRQ가 어느 CPU로 가는지, `ethtool -l`로 큐가 몇 개인지 봅니다. 큐가 하나뿐이면 RPS로, 여러 개인데 친화성이 한 CPU에 몰려 있으면 IRQ 친화성을 펴서 해결합니다. budget을 올리는 것은 그다음입니다.
:::
:::

::: {.q}
`tcp_v4_rcv()`가 `sock_owned_by_user()`가 참일 때 세그먼트를 바로 처리하지 않고 backlog에 넣는 이유는 무엇입니까? 스핀락만으로 소켓을 보호하면 안 됩니까?

::: {.a}
소켓을 쓰는 태스크는 유저 버퍼로 복사하는 도중에 페이지 폴트로 잠들 수 있습니다. 스핀락을 쥔 채로는 잠들 수 없으므로, 태스크는 소켓을 오래 쥐는 동안 스핀락을 쥐고 있을 수 없습니다. 그래서 스핀락은 `owned` 플래그를 세우고 내릴 때와 큐를 고칠 때만 짧게 쥡니다. softirq는 잠들 수 없으므로 태스크가 소켓을 놓기를 기다릴 수도 없습니다. 남는 방법은 일을 backlog에 맡겨 두고 떠나는 것이고, 태스크가 `release_sock()`에서 그 일을 대신합니다.
:::
:::

::: {.q}
같은 TCP 연결의 패킷을 여러 CPU에 고르게 나눠 처리하면 더 빠를 것 같습니다. RSS와 RPS가 그렇게 하지 않고 흐름 단위로 CPU를 고정하는 이유는 무엇입니까?

::: {.a}
첫째, 순서입니다. 한 연결의 세그먼트가 여러 CPU에서 병렬로 스택을 오르면 TCP에 도착하는 순서가 뒤섞이고, TCP는 이것을 손실로 오해해 재전송과 혼잡 제어를 일으킵니다. 둘째, 락과 캐시입니다. 소켓 하나는 어차피 한 번에 한 CPU만 고칠 수 있으므로 여러 CPU가 달려들면 소켓 락에서 줄을 서고, 소켓 구조체의 캐시 라인이 CPU 사이를 오갑니다. 흐름을 해시로 한 CPU에 고정하면 둘 다 피하고, 흐름이 많으면 CPU 전체가 고르게 쓰입니다.
:::
:::

## 용어 {#terms}

::: {.terms}
RX 링 (RX ring)
:   NIC와 드라이버가 수신 버퍼의 주소와 상태를 주고받는 디스크립터의 원형 배열.

NAPI
:   인터럽트를 받으면 장치 인터럽트를 막고 softirq에서 폴링하다가, 링이 비면 인터럽트로 돌아가는 수신 처리 방식.

budget
:   poll 한 번이나 softirq 한 번에 처리할 수 있는 패킷 수의 상한.

수신 라이브록 (receive livelock)
:   패킷마다 걸리는 인터럽트를 처리하느라 정작 패킷을 처리할 시간이 없어 처리량이 무너지는 현상.

softnet_data
:   CPU마다 하나씩 있는 네트워크 스택의 상태. 폴링 목록과 backlog 큐가 들어 있다.

sk_buff
:   패킷 하나의 메타데이터와 데이터 버퍼의 경계 포인터를 담은 구조체. skb라고 줄여 부른다.

GRO (generic receive offload)
:   같은 흐름의 연속된 수신 세그먼트를 큰 skb 하나로 합치는 기능.

소켓 backlog
:   태스크가 소켓을 쥐고 있는 동안 softirq가 처리를 미뤄 둔 skb의 목록.

RSS (receive side scaling)
:   NIC가 패킷의 흐름 해시로 수신 큐를 골라 여러 CPU로 나누는 기능.

RPS (receive packet steering)
:   커널이 흐름 해시로 대상 CPU를 골라 그 CPU의 backlog로 넘기는 기능.

XDP (express data path)
:   드라이버가 skb를 만들기 전에 BPF 프로그램을 실행해 패킷을 버리거나 돌려보내는 훅.

드롭 이유 (drop reason)
:   skb를 버릴 때 함께 기록하는 열거형 값. `skb:kfree_skb` 추적점에 나타난다.
:::
