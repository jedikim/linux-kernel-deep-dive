::: {.lead}
C 함수는 한 번 부르면 한 번 돌아옵니다. `fork()`는 그렇지 않아 보입니다. 한 번 불렀는데 부모 프로세스에서 한 번, 새로 생긴 자식 프로세스에서 한 번 돌아오고, 반환값도 서로 다릅니다. 커널 안에 두 번 반환하는 함수가 있는 것은 아닙니다. 커널은 부모를 본뜬 태스크를 하나 만들고, 그 태스크가 방금 같은 시스템 콜에서 돌아오는 것처럼 보이도록 스택과 레지스터를 꾸며 둡니다. 이 장은 그 꾸밈이 v7.3 소스의 어느 줄에 있는지, 태스크 하나를 만들 때 무엇을 복사하고 무엇을 공유하는지 따라갑니다.
:::

::: {.goals}
- `fork()`가 부모에게는 자식의 PID를, 자식에게는 0을 돌려주는 일은 코드 어디에서 일어나는가?
- `fork`, `vfork`, `clone`, `clone3`는 커널 안에서 무엇이 같고 무엇이 다른가?
- `copy_process()`는 어떤 순서로 태스크를 조립하고, 중간에 실패하면 어떻게 되돌리는가?
- 수 기가바이트를 쓰는 프로세스의 `fork()`가 금방 끝나는 까닭은 무엇인가?
- `vfork()`를 부른 부모는 무엇을 기다리고, 누가 깨우는가?
- 태스크를 끝없이 만들지 못하게 막는 한도는 어디에서 검사하는가?
:::

## 한 번 부르고 두 번 돌아온다 {#returns-twice}

`fork()`는 자신을 부른 프로세스를 복제하는 시스템 콜입니다. 복제가 끝나면 프로세스가 둘이 되고, 둘 다 `fork()` 바로 다음 줄에서 실행을 잇습니다. 둘을 구별하는 것은 반환값뿐입니다.

```{.c name="fork.c"}
#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void)
{
	pid_t pid = fork();

	if (pid == 0) {
		printf("자식: pid=%d 부모=%d\n", getpid(), getppid());
		return 0;
	}
	printf("부모: pid=%d 자식=%d\n", getpid(), pid);
	wait(NULL);
	return 0;
}
```

부모에서는 `pid`에 자식의 PID가, 자식에서는 0이 들어 있습니다. 실패하면 자식은 생기지 않고 부모만 -1을 받습니다.

::: {.fig src="fork-timeline.svg"}
커널에 들어가는 것은 부모 하나입니다. 나오는 것은 둘입니다. 자식은 시스템 콜에 들어간 적이 없지만, 들어갔다 나오는 것처럼 꾸며진 채로 첫 실행을 시작합니다.
:::

"두 번 돌아온다"를 풀어 보면 세 가지 일입니다.

1. 부모는 보통의 시스템 콜처럼 커널에 들어갔다가 나옵니다. 반환값은 새 태스크의 PID입니다.
2. 그 사이에 커널은 부모를 본떠 새 **태스크**(task)를 만듭니다. 태스크는 커널이 스케줄하는 단위이고, 프로세스든 스레드든 커널 안에서는 `struct task_struct` 하나로 표현됩니다. 구조체의 내용은 [2장](ch02.html)에서 봅니다.
3. 자식은 시스템 콜에 들어간 적이 없습니다. 커널은 자식의 커널 스택에 "시스템 콜을 마치고 유저 모드로 돌아가는 중"인 모습을 만들어 두고, 반환값 자리에 0을 써 둡니다. 스케줄러가 자식을 처음 고르면 자식은 그 모습을 따라 유저 모드로 나갑니다.

3번이 이 장의 중심입니다. 먼저 태스크가 만들어지는 길부터 따라갑니다.

## 네 개의 시스템 콜, 하나의 함수 {#kernel-clone}

리눅스에는 태스크를 만드는 시스템 콜이 넷 있습니다. `fork`, `vfork`, `clone`, `clone3`입니다. 넷은 인자를 받는 방식만 다르고, 하는 일은 같습니다. 인자를 `struct kernel_clone_args`에 채워 `kernel_clone()`을 부릅니다.

```{.c file="kernel/fork.c" line="2862"}
SYSCALL_DEFINE0(fork)
{
#ifdef CONFIG_MMU
	struct kernel_clone_args args = {
		.exit_signal = SIGCHLD,
	};

	return kernel_clone(&args);
#else
	/* can not support in nommu mode */
	return -EINVAL;
#endif
}
/* ... */
SYSCALL_DEFINE0(vfork)
{
	struct kernel_clone_args args = {
		.flags		= CLONE_VFORK | CLONE_VM,
		.exit_signal	= SIGCHLD,
	};

	return kernel_clone(&args);
}
```

`fork`는 플래그가 하나도 없습니다. 아무것도 공유하지 않고 전부 복사하라는 뜻입니다. 정한 것은 `exit_signal` 하나로, 자식이 끝나면 부모에게 `SIGCHLD`를 보내라는 뜻입니다. `vfork`는 여기에 플래그 둘을 더합니다. `CLONE_VM`은 주소 공간을 복사하지 말고 같이 쓰라는 뜻이고, `CLONE_VFORK`는 자식이 그 주소 공간에서 손을 뗄 때까지 부모를 재우라는 뜻입니다.

::: {.fig src="clone-family.svg"}
태스크를 만드는 길은 모두 `kernel_clone()`으로 모입니다. 커널 스레드도 같은 길을 씁니다. 차이는 `kernel_clone_args`에 무엇을 적어 넘기느냐뿐입니다.
:::

`clone`은 플래그를 호출하는 쪽이 정합니다. 32비트 플래그 인자의 아래 8비트(`CSIGNAL`)는 `exit_signal`로, 나머지는 `flags`로 갈라 담습니다. `clone3`는 인자를 레지스터가 아니라 구조체로 받습니다. 뒤의 [clone3 절](#clone3)에서 다룹니다.

그림 아래쪽의 `kernel_thread()`는 커널이 자기 일을 시킬 스레드를 만들 때 씁니다. 유저 프로세스와 커널 스레드가 같은 함수로 만들어집니다([2장](ch02.html)).

::: {.note title="C 라이브러리의 fork()는 fork 시스템 콜을 부르지 않는다"}
glibc의 `fork()` 함수는 `clone`을 부릅니다. 넘기는 플래그는 `CLONE_CHILD_SETTID | CLONE_CHILD_CLEARTID | SIGCHLD`입니다. 자식의 스레드 ID를 자식 쪽 메모리에 적어 두려는 플래그 둘이 더해졌을 뿐, 공유하는 자원이 없다는 점은 `fork`와 같습니다. arm64 같은 아키텍처의 64비트 시스템 콜 표(`scripts/syscall.tbl`)에는 `fork`와 `vfork`가 아예 없고 `clone`과 `clone3`만 있습니다.
:::

::: {.lab}
프로그램이 실제로 어떤 시스템 콜로 태스크를 만드는지는 `strace`로 봅니다. `-f`는 새로 생긴 자식까지 따라가라는 옵션입니다.

```console
$ strace -f -e trace=fork,vfork,clone,clone3 ./fork
clone(child_stack=NULL, flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD, child_tidptr=0x7f...) = 41172
...
```

`flags`에 `CLONE_VM`이 없으니 주소 공간을 따로 갖는 프로세스가 생긴 것입니다. 같은 명령을 스레드를 만드는 프로그램에 걸면 `CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD|...`가 붙은 `clone3`가 보입니다.
:::

`kernel_clone()`의 뼈대는 이렇습니다.

```{.c file="kernel/fork.c" line="2727"}
pid_t kernel_clone(struct kernel_clone_args *args)
{
	u64 clone_flags = args->flags;
	struct completion vfork;
	/* ... */
	p = copy_process(NULL, trace, NUMA_NO_NODE, args);
	add_latent_entropy();

	if (IS_ERR(p))
		return PTR_ERR(p);

	/* ... */
	pid = get_task_pid(p, PIDTYPE_PID);
	nr = pid_vnr(pid);
	/* ... */
	if (clone_flags & CLONE_VFORK) {
		p->vfork_done = &vfork;
		init_completion(&vfork);
		get_task_struct(p);
	}

	/* ... */
	wake_up_new_task(p);

	/* ... */
	if (clone_flags & CLONE_VFORK) {
		if (!wait_for_vfork_done(p, &vfork))
			ptrace_event_pid(PTRACE_EVENT_VFORK_DONE, pid);
	}

	put_pid(pid);
	return nr;
}
```

읽을 곳은 세 군데입니다.

- 일은 둘로 나뉩니다. `copy_process()`가 태스크를 **만들고**, `wake_up_new_task()`가 **깨웁니다**. 만드는 동안 새 태스크는 실행될 수 없는 상태로 남아 있습니다.
- 마지막 줄의 `return nr`이 부모가 받는 반환값입니다. `pid_vnr()`은 부모가 속한 PID 네임스페이스에서 본 번호를 돌려줍니다([22장](ch22.html)).
- 자식이 받을 0은 이 함수에 없습니다. 자식은 이 함수에서 돌아오지 않기 때문입니다.

::: {.old}
많은 책과 블로그가 이 함수를 `do_fork()`라고 부릅니다. 이 이름은 `_do_fork()`를 거쳐 v5.10에서 `kernel_clone()`으로 바뀌었습니다. 인자도 달라졌습니다. 예전에는 `clone_flags`, `stack_start`, `stack_size`, `parent_tidptr` 같은 값을 하나씩 넘겼지만, 지금은 `struct kernel_clone_args` 포인터 하나만 넘깁니다.
:::

## copy_process(): 태스크를 조립하는 순서 {#copy-process}

`copy_process()`는 600줄이 넘는 함수지만 하는 일은 한 문장입니다. 부모의 `task_struct`를 통째로 복사한 다음, 그대로 두면 안 되는 부분을 하나씩 고칩니다.

::: {.fig src="copy-process-stages.svg"}
`copy_process()`의 큰 단계. 보라색 묶음은 플래그에 따라 공유하거나 복사하는 자원입니다. 새 태스크는 맨 마지막 단계에 가서야 다른 태스크의 눈에 보입니다.
:::

**플래그 검사.** 함수는 말이 안 되는 플래그 조합부터 거릅니다. `CLONE_THREAD`(같은 스레드 그룹에 넣기)는 `CLONE_SIGHAND`(시그널 핸들러 공유)를 요구하고, `CLONE_SIGHAND`는 `CLONE_VM`을 요구합니다. 주소 공간이 다른데 핸들러 표를 같이 쓰면 핸들러 주소가 한쪽에서는 엉뚱한 곳을 가리키기 때문입니다.

**`dup_task_struct()`.** `task_struct`와 커널 스택을 새로 할당하고 부모의 `task_struct`를 그대로 복사합니다. 이 시점의 자식은 포인터까지 부모와 똑같은 복사본입니다. `mm`, `files`, `fs` 같은 포인터가 부모의 구조체를 그대로 가리킵니다.

**자격 증명과 한도.** `copy_creds()`가 자격 증명을 마련하고, 태스크 수 한도를 넘는지 봅니다. [한도 절](#limits)에서 다시 봅니다.

**`sched_fork()`.** 자식의 상태를 `TASK_NEW`로 둡니다. 이 상태의 태스크는 런큐에 오를 수 없고 시그널로도 깨울 수 없습니다. 조립이 끝나기 전에 누가 실행해 버리는 일을 막는 장치입니다. 우선순위와 스케줄링 클래스도 여기서 정해집니다([4장](ch04.html)).

**자원.** 이제 부모를 가리키고 있는 포인터들을 하나씩 처리합니다.

```{.c file="kernel/fork.c" line="2304"}
	retval = copy_semundo(clone_flags, p);
	if (retval)
		goto bad_fork_cleanup_security;
	retval = copy_files(clone_flags, p, args->no_files);
	if (retval)
		goto bad_fork_cleanup_semundo;
	retval = copy_fs(clone_flags, p,
			 (args->umh ? COPY_FS_UMH : 0) |
			 (args->idle ? COPY_FS_IDLE : 0));
	if (retval)
		goto bad_fork_cleanup_files;
	retval = copy_sighand(clone_flags, p);
	if (retval)
		goto bad_fork_cleanup_fs;
	retval = copy_signal(clone_flags, p);
	if (retval)
		goto bad_fork_cleanup_sighand;
	retval = copy_mm(clone_flags, p);
	if (retval)
		goto bad_fork_cleanup_signal;
	retval = copy_namespaces(clone_flags, p);
	if (retval)
		goto bad_fork_cleanup_mm;
	retval = copy_io(clone_flags, p);
	if (retval)
		goto bad_fork_cleanup_namespaces;
	retval = copy_thread(p, args);
	if (retval)
		goto bad_fork_cleanup_io;
```

`copy_*()` 함수들은 생김새가 같습니다. 해당 플래그가 서 있으면 부모 구조체의 참조 카운트만 올리고 끝냅니다. 없으면 새 구조체를 할당해 내용을 복사하고 자식의 포인터를 그쪽으로 돌립니다. 예를 들어 `copy_files()`는 `CLONE_FILES`가 있으면 `atomic_inc(&oldf->count)` 한 줄이고, 없으면 `dup_fd()`로 파일 디스크립터 표를 복제합니다. 프로세스와 스레드의 차이는 이 함수들이 어느 가지를 타느냐로 정해집니다. 플래그와 구조체의 대응은 [2장](ch02.html)에 표로 정리했습니다.

`copy_namespaces()`만은 방향이 반대입니다. 기본이 공유이고, `CLONE_NEWPID` 같은 `CLONE_NEW*` 플래그가 있을 때 새로 만듭니다.

**`copy_thread()`.** 자식이 처음 실행될 때 쓸 레지스터와 스택을 꾸밉니다. 아키텍처마다 따로 구현합니다. [다음 절](#first-run)의 주제입니다.

**PID.** `alloc_pid()`가 번호를 받습니다. `CLONE_PIDFD`가 있으면 그 PID를 가리키는 파일 디스크립터도 여기서 준비합니다.

**cgroup.** `cgroup_can_fork()`가 cgroup 한도를 확인합니다. 이어 `sched_cgroup_fork()`가 자식을 지금 CPU의 런큐에 일단 배정합니다.

**연결.** 여기까지 온 자식은 완성되었지만 아직 어디에도 연결되어 있지 않습니다. PID로 찾을 수도 없고 부모의 자식 목록에도 없습니다. 마지막 단계에서 `tasklist_lock`을 쓰기로 잡고 한꺼번에 연결합니다. 부모의 `children` 리스트와 전체 태스크 리스트에 넣고, `attach_pid()`로 PID에서 태스크를 찾을 수 있게 합니다. 락을 쥔 뒤 마지막 확인 두 가지(PID 네임스페이스가 닫히는 중인지, 부모에게 치명적 시그널이 와 있는지)를 통과하면 소스에 `/* No more failure paths after this point. */`라는 주석이 나옵니다. 그 아래에는 실패로 끝나는 길이 없습니다. 남에게 보이기 시작한 태스크를 거둬들이기는 훨씬 어렵기 때문에, 실패할 수 있는 일을 모두 앞에 몰아 둔 것입니다.

::: {.key}
`copy_process()`의 순서는 **실패할 수 있는 일을 먼저, 남에게 보이는 일을 맨 나중에**입니다. 태스크는 완성된 뒤에야 시스템에 나타나고, 나타난 뒤에는 생성이 취소되지 않습니다.
:::

### 실패하면 거꾸로 되돌린다

위 인용에서 `goto`의 목적지를 보면 규칙이 있습니다. 어떤 단계가 실패하면 **바로 앞 단계의 정리 라벨**로 갑니다. 라벨들은 함수 끝에 조립의 역순으로 늘어서 있습니다.

```{.c file="kernel/fork.c" line="2613"}
bad_fork_cleanup_namespaces:
	exit_nsproxy_namespaces(p);
bad_fork_cleanup_mm:
	sched_cache_fork_cleanup(p);
	if (p->mm) {
		mm_clear_owner(p->mm, p);
		mmput(p->mm);
	}
bad_fork_cleanup_signal:
	if (!(clone_flags & CLONE_THREAD))
		free_signal_struct(p->signal);
bad_fork_cleanup_sighand:
	__cleanup_sighand(p->sighand);
bad_fork_cleanup_fs:
	exit_fs(p); /* blocking */
bad_fork_cleanup_files:
	exit_files(p); /* blocking */
bad_fork_cleanup_semundo:
	exit_sem(p);
```

`copy_mm()`이 실패하면 `bad_fork_cleanup_signal`로 뛰고, 거기서부터 아래로 흘러내리며 시그널, 핸들러 표, 파일시스템 정보, 파일 표를 차례로 풉니다. `mm`은 만들지 못했으니 풀지 않습니다.

::: {.design}
자원을 여러 개 차례로 얻는 함수에서 중간 실패를 다루는 방법으로, 커널은 `goto`와 역순 라벨을 표준처럼 씁니다. 얻는 순서와 푸는 순서가 거울처럼 마주 보기 때문에, 새 단계를 끼워 넣을 때 고칠 곳이 분명합니다. C에는 예외도 소멸자도 없으므로 이 규율이 없으면 실패 경로마다 정리 코드를 복사해 넣게 되고, 하나를 빠뜨리는 순간 누수가 생깁니다. 라벨 이름은 "어디서 실패했나"가 아니라 "무엇을 정리하나"(`bad_fork_cleanup_mm`)로 짓습니다. 커널은 여기에 범위 기반 정리(`guard()`, `__free()`)를 더해 가고 있습니다. 두 방식의 비교는 [25장](ch25.html)에 있습니다.
:::

## 자식의 첫 실행 {#first-run}

`fork()`가 자식에게 0을 돌려주는 코드는 `copy_thread()`에 있습니다. x86-64의 구현에서 관련된 줄만 추리면 이렇습니다.

```{.c file="arch/x86/kernel/process.c" line="170"}
int copy_thread(struct task_struct *p, const struct kernel_clone_args *args)
{
	u64 clone_flags = args->flags;
	unsigned long sp = args->stack;
	/* ... */
	childregs = task_pt_regs(p);
	fork_frame = container_of(childregs, struct fork_frame, regs);
	frame = &fork_frame->frame;

	frame->bp = encode_frame_pointer(childregs);
	frame->ret_addr = (unsigned long) ret_from_fork_asm;
	p->thread.sp = (unsigned long) fork_frame;
	/* ... */
	frame->bx = 0;
	*childregs = *current_pt_regs();
	childregs->ax = 0;
	if (sp)
		childregs->sp = sp;
	/* ... */
}
```

이 코드를 읽으려면 구조체 두 개를 알아야 합니다.

`struct pt_regs`는 유저 모드에서 커널로 들어올 때 유저 쪽 레지스터를 저장해 두는 틀입니다. 커널 스택의 맨 꼭대기에 놓입니다. 유저 모드로 나갈 때 커널은 이 틀에 담긴 값을 CPU 레지스터에 도로 싣습니다. 시스템 콜의 반환값도 이 틀의 `ax` 칸에 적어 두었다가 그때 함께 실립니다([19장](ch19.html)).

`struct inactive_task_frame`은 실행 중이 아닌 태스크의 스택 포인터가 가리키는 자리에 놓이는 틀입니다. 컨텍스트 스위치는 떠나는 태스크의 레지스터 몇 개를 스택에 밀어 넣고 스택 포인터를 `thread.sp`에 저장한 다음, 들어오는 태스크의 `thread.sp`를 스택 포인터로 삼아 그 레지스터들을 도로 꺼냅니다. 맨 마지막에 꺼내는 것이 `ret_addr`, 곧 "어디로 돌아가 실행을 이을 것인가"입니다([4장](ch04.html)).

::: {.fig src="child-stack.svg"}
`copy_thread()`가 꾸민 자식의 커널 스택과, 그 스택을 따라가는 자식의 첫 실행. 자식은 한 번도 실행된 적이 없지만, 스케줄러가 보기에는 "전에 스위치되어 나갔던 태스크"와 똑같이 생겼습니다.
:::

이제 인용한 코드가 읽힙니다.

- `*childregs = *current_pt_regs()`: 부모의 `pt_regs`를 자식의 스택 꼭대기에 통째로 복사합니다. 부모가 `syscall` 명령어를 실행한 순간의 유저 레지스터입니다. 명령어 포인터, 유저 스택 포인터, 플래그가 다 들어 있습니다. 그래서 자식은 부모와 **같은 유저 주소**에서 실행을 잇습니다.
- `childregs->ax = 0`: 복사본의 반환값 칸만 0으로 고칩니다. **이 한 줄이 자식의 `fork()` 반환값입니다.**
- `frame->ret_addr = ret_from_fork_asm`: 자식이 처음 스위치되어 들어올 때 뛸 주소를 정합니다.
- `p->thread.sp = fork_frame`: 스케줄러가 스택 포인터로 삼을 곳을 이 틀의 시작으로 맞춥니다.

부모 쪽은 따로 손댈 것이 없습니다. 시스템 콜 진입 코드가 모든 시스템 콜에 대해 `regs->ax = x64_sys_call(regs, nr)`로 반환값을 적기 때문입니다(`arch/x86/entry/syscall_64.c`). 부모의 `ax`는 평소의 경로가, 자식의 `ax`는 `copy_thread()`가 채웁니다.

스케줄러가 자식을 처음 고르면 `ret_addr`에 적어 둔 곳에서 실행이 시작됩니다.

```{.asm file="arch/x86/entry/entry_64.S" line="228"}
SYM_CODE_START(ret_from_fork_asm)
	/* ... */
	movq	%rax, %rdi		/* prev */
	movq	%rsp, %rsi		/* regs */
	movq	%rbx, %rdx		/* fn */
	movq	%r12, %rcx		/* fn_arg */
	call	ret_from_fork

	/* ... */
#ifdef CONFIG_X86_FRED
	ALTERNATIVE "jmp swapgs_restore_regs_and_return_to_usermode", \
		    "jmp asm_fred_exit_user", X86_FEATURE_FRED
#else
	jmp	swapgs_restore_regs_and_return_to_usermode
#endif
SYM_CODE_END(ret_from_fork_asm)
```

이 시점에 스택 포인터는 `inactive_task_frame`을 다 꺼내고 `pt_regs`의 시작을 가리킵니다. 그래서 `%rsp`를 그대로 `regs` 인자로 넘깁니다. 어셈블리가 하는 일은 인자 넷을 맞춰 C 함수를 부르는 것뿐입니다.

```{.c file="arch/x86/kernel/process.c" line="151"}
__visible void ret_from_fork(struct task_struct *prev, struct pt_regs *regs,
				     int (*fn)(void *), void *fn_arg)
{
	schedule_tail(prev);

	/* Is this a kernel thread? */
	if (unlikely(fn)) {
		fn(fn_arg);
		/*
		 * A kernel thread is allowed to return here after successfully
		 * calling kernel_execve().  Exit to userspace to complete the
		 * execve() syscall.
		 */
		regs->ax = 0;
	}

	syscall_exit_to_user_mode(regs);
}
```

`schedule_tail()`은 컨텍스트 스위치의 뒷정리입니다. 보통의 태스크는 `schedule()` 안에서 스위치되어 나갔다가 같은 함수 안으로 돌아와 뒷정리를 직접 합니다. 처음 실행되는 자식은 `schedule()`을 부른 적이 없으니 그 뒷부분을 여기서 따로 불러 줍니다. 런큐 락을 풀고 선점을 다시 켜는 일이 들어 있습니다.

`syscall_exit_to_user_mode()`는 모든 시스템 콜이 끝날 때 지나는 출구입니다. 자식은 입구를 지난 적이 없는데 출구로만 나갑니다. 그 뒤 어셈블리 코드가 `pt_regs`를 레지스터에 싣고 유저 모드로 넘어갑니다. `rax`에는 0이 실립니다.

`ret_from_fork()`의 `fn`은 커널 스레드를 위한 가지입니다. 유저 프로세스에서는 `copy_thread()`가 `frame->bx = 0`으로 두었으므로 NULL입니다. 커널 스레드가 이 길을 어떻게 쓰는지는 [2장](ch02.html)에서 봅니다.

## 부모와 자식, 누가 먼저 도는가 {#who-first}

`copy_process()`가 돌려준 자식은 `TASK_NEW` 상태입니다. `wake_up_new_task()`(`kernel/sched/core.c`)가 이것을 실행 가능한 태스크로 바꿉니다. 하는 일은 넷입니다. 상태를 `TASK_RUNNING`으로 바꾸고, `select_task_rq()`에 `WF_FORK` 플래그를 주어 자식이 돌 CPU를 고르고([7장](ch07.html)), `activate_task()`로 그 CPU의 런큐에 넣고, `wakeup_preempt()`로 지금 도는 태스크를 밀어내야 할지 묻습니다.

마지막 질문에 fair 클래스는 이렇게 답합니다.

```{.c file="kernel/sched/fair.c" line="10217"}
	/*
	 * Ignore wakee preemption on WF_FORK as it is less likely that
	 * there is shared data as exec often follow fork.
	 */
	if (wake_flags & WF_FORK)
		goto update;
```

방금 `fork`로 생긴 태스크는 깨어났다는 이유로 현재 태스크를 선점하지 않습니다. 보통의 깨우기에서는 깨운 쪽과 깨어난 쪽이 같은 데이터를 다루는 일이 많아 깨어난 쪽을 빨리 돌리는 것이 이롭지만, `fork` 뒤에는 대개 `exec`가 따라와 그런 이점이 없다는 것이 주석의 설명입니다.

그렇다고 "부모가 먼저"라는 보장이 생기는 것은 아닙니다. 자식이 다른 CPU의 런큐에 놓이면 부모가 `kernel_clone()`에서 빠져나오기도 전에 자식이 유저 코드를 실행할 수 있습니다.

::: {.warn}
`fork()` 뒤에 부모와 자식 중 누가 먼저 실행되는지는 정해져 있지 않습니다. 순서에 기대는 코드는 경쟁 조건입니다. 순서가 필요하면 파이프나 시그널 같은 명시적인 동기화를 써야 합니다.
:::

::: {.old}
예전 자료에는 "리눅스는 자식을 먼저 실행한다. 부모가 먼저 돌며 쓰기 시 복사를 일으키는 낭비를 피하려는 것이다"라는 설명이 자주 나옵니다. 이 동작을 고르는 `kernel.sched_child_runs_first`라는 sysctl도 있었습니다. v7.3의 스케줄러에는 그런 규칙도, 그 sysctl도 없습니다. `WF_FORK` 깨우기는 선점을 일으키지 않을 뿐이고, 순서는 자식이 어느 CPU에 놓이느냐와 그때의 런큐 사정에 달려 있습니다.
:::

## 쓰기 시 복사 {#cow}

`fork`는 주소 공간을 복사합니다. 그런데 수 기가바이트를 쓰는 프로세스의 `fork`도 그만한 메모리를 복사하는 데 걸릴 시간보다 훨씬 빨리 끝납니다. 메모리의 내용은 복사하지 않기 때문입니다.

```{.c file="kernel/fork.c" line="1568"}
static int copy_mm(u64 clone_flags, struct task_struct *tsk)
{
	struct mm_struct *mm, *oldmm;

	/* ... */
	oldmm = current->mm;
	if (!oldmm)
		return 0;

	if (clone_flags & CLONE_VM) {
		mmget(oldmm);
		mm = oldmm;
	} else {
		mm = dup_mm(tsk, current->mm);
		if (!mm)
			return -ENOMEM;
	}

	tsk->mm = mm;
	tsk->active_mm = mm;
	sched_cache_fork(tsk);
	return 0;
}
```

`copy_*()`의 생김새 그대로입니다. `CLONE_VM`이 있으면 `mmget()`으로 참조 카운트만 올리고 부모의 `mm_struct`를 같이 씁니다. 스레드를 만들 때와 `vfork`가 이 가지입니다. 없으면 `dup_mm()`이 새 `mm_struct`를 만듭니다.

`dup_mm()`이 부르는 `dup_mmap()`(`mm/mmap.c`)은 부모의 **VMA**(가상 메모리 영역, 주소 공간의 한 구간을 나타내는 구조체)를 하나씩 돌며 자식 것을 만들고, 구간마다 `copy_page_range()`로 페이지 테이블을 복사합니다. 복사하는 것은 "어느 가상 주소가 어느 물리 페이지에 대응하는가"를 적은 표이지 페이지의 내용이 아닙니다. 표의 항목(PTE) 하나를 복사할 때 이런 일을 합니다.

```{.c file="mm/memory.c" line="1189"}
	/* If it's a COW mapping, write protect it both processes. */
	if (vma_is_cow_mapping(src_vma) && writable) {
		wrprotect_ptes(src_mm, addr, src_pte, nr);
		pte = pte_wrprotect(pte);
	}

	/* If it's a shared mapping, mark it clean in the child. */
	if (src_vma->vm_flags & VM_SHARED)
		pte = pte_mkclean(pte);
	pte = pte_mkold(pte);

	set_ptes(dst_vma->vm_mm, addr, dst_pte, pte, nr);
```

쓸 수 있던 사적(private) 매핑의 항목은 **부모 쪽과 자식 쪽을 모두** 읽기 전용으로 바꿉니다. `wrprotect_ptes()`가 부모의 항목을, `pte_wrprotect()`가 자식에게 줄 항목을 고칩니다. 이제 두 프로세스가 같은 물리 페이지를 읽기 전용으로 함께 가리킵니다.

::: {.fig src="cow.svg"}
`fork` 직후에는 물리 페이지가 하나도 늘지 않습니다. 어느 한쪽이 쓰려는 순간에 그 페이지만 복사됩니다.
:::

그 뒤 어느 쪽이든 그 페이지에 쓰려 하면 CPU가 페이지 폴트를 냅니다. 폴트 핸들러는 VMA를 보고 "원래는 쓸 수 있는 구간"임을 확인한 뒤, 새 페이지를 할당해 내용을 복사하고 폴트를 낸 쪽의 항목만 새 페이지를 가리키게 합니다. 이것이 **쓰기 시 복사**(copy-on-write, COW)입니다. 남은 쪽이 나중에 쓰려 할 때는 그 페이지를 혼자 쓰고 있음을 확인하고 복사 없이 쓰기 권한만 되살립니다. 폴트 처리의 전체 흐름은 [17장](ch17.html)에서 다룹니다.

::: {.myth}
"`fork`는 프로세스의 메모리를 전부 복사하므로 큰 프로세스에서는 쓰면 안 된다." 복사하는 것은 메모리가 아니라 페이지 테이블입니다. 다만 공짜는 아닙니다. 페이지 테이블의 크기는 매핑된 메모리에 비례하므로 큰 프로세스일수록 `fork`가 오래 걸리고, `dup_mmap()`은 그동안 부모의 `mmap_lock`을 쓰기로 쥡니다. `fork` 뒤에 부모가 메모리를 많이 고치면 페이지마다 폴트와 복사가 일어납니다. 스냅숏을 뜨려고 `fork`하는 프로그램이 치르는 비용이 이것입니다.
:::

`copy_page_range()`는 복사를 건너뛰기도 합니다. 파일을 매핑한 구간 가운데 사적인 수정본이 없는 것은 페이지 테이블을 복사하지 않습니다(`vma_needs_copy()`). 자식이 그 주소를 건드릴 때 폴트를 통해 페이지 캐시에서 다시 채울 수 있기 때문입니다.

## vfork와 exec {#vfork-exec}

`fork` 다음에는 대개 `exec`가 옵니다. 이 경우 자식은 방금 복사한 주소 공간을 거의 쓰지 않고 버립니다. 페이지 테이블 복사가 낭비입니다.

`vfork`는 이 낭비를 없앱니다. 주소 공간을 복사하지 않고 부모 것을 빌려 씁니다. 대신 둘이 같은 메모리와 같은 스택에서 동시에 돌면 서로를 망가뜨리므로, 자식이 주소 공간에서 손을 뗄 때까지 부모를 재웁니다.

::: {.fig src="fork-vs-vfork.svg"}
`fork`는 복사 비용을 치르고 부모와 자식이 함께 돕니다. `vfork`는 복사하지 않는 대신 부모가 멈춥니다.
:::

부모가 잠드는 곳은 앞에서 본 `kernel_clone()`의 끝부분입니다. `CLONE_VFORK`가 있으면 스택에 `struct completion`을 하나 만들어 자식의 `vfork_done`에 걸어 두고, 자식을 깨운 뒤 `wait_for_vfork_done()`에서 그 completion을 기다립니다. **completion**은 "어떤 일이 끝났다"는 신호 하나를 기다리는 커널의 동기화 도구입니다([3장](ch03.html)).

깨우는 쪽은 `mm_release()`입니다. 태스크가 `mm`에서 손을 뗄 때 불리는 함수입니다.

```{.c file="kernel/fork.c" line="1503"}
	/*
	 * All done, finally we can wake up parent and return this mm to him.
	 * Also kthread_stop() uses this completion for synchronization.
	 */
	if (tsk->vfork_done)
		complete_vfork_done(tsk);
```

`mm_release()`가 불리는 길은 둘입니다. 자식이 `execve()`에 성공해 새 주소 공간으로 갈아탈 때와 자식이 종료할 때입니다. 어느 쪽이든 자식은 더는 부모의 메모리를 건드리지 않으므로 부모를 깨워도 안전합니다.

::: {.warn}
`vfork()`로 생긴 자식은 부모의 스택 위에서 돕니다. 자식이 `vfork()`를 부른 함수에서 `return`하거나 지역 변수를 고치면 부모의 스택이 깨집니다. 자식이 해도 되는 일은 사실상 `execve()`와 `_exit()`뿐입니다. 그래서 유저 프로그램은 보통 `posix_spawn()`을 씁니다. glibc의 `posix_spawn()`은 `CLONE_VM | CLONE_VFORK`로 `clone`을 부르되 자식에게 따로 마련한 스택을 줍니다. 복사 비용이 없다는 이점은 얻고 스택을 함께 쓰는 위험은 피합니다.
:::

### exec: 태스크는 그대로, 주소 공간만 바꾼다

`execve()`는 새 태스크를 만들지 않습니다. 지금 태스크의 `task_struct`와 PID는 그대로 두고 그 안에서 실행할 프로그램을 바꿉니다. ELF 로더 같은 실행 파일 형식 핸들러가 `begin_new_exec()`(`fs/exec.c`)를 부르면 다음 일이 차례로 일어납니다.

- 스레드 그룹의 다른 스레드를 모두 끝냅니다(`de_thread()`). `exec` 뒤에는 스레드가 하나만 남습니다.
- 파일 디스크립터 표를 남과 공유하고 있었다면 떼어 내고, `O_CLOEXEC`가 붙은 디스크립터를 닫습니다.
- `exec_mmap()`이 `tsk->mm`을 미리 만들어 둔 새 `mm_struct`로 바꿉니다. 이 안에서 앞의 `mm_release()`가 불립니다.
- 등록해 둔 시그널 핸들러를 기본 동작으로 되돌립니다. 예전 프로그램의 핸들러 주소는 새 주소 공간에서 뜻이 없기 때문입니다.

마지막에 핸들러는 `pt_regs`의 명령어 포인터와 스택 포인터를 새 프로그램의 진입점과 새 스택으로 고칩니다. `fork`에서 본 것과 같은 요령입니다. 유저 모드로 돌아가는 길에 실릴 레지스터를 바꿔 놓으면, 돌아간 곳은 새 프로그램의 첫 명령어입니다.

`begin_new_exec()`의 주석은 이 함수를 "돌아올 수 없는 지점"이라고 부릅니다. 이 뒤에 실패하면 돌아갈 예전 프로그램이 없으므로 태스크를 죽이는 수밖에 없습니다. 그래서 파일을 열고 권한을 확인하는, 실패할 만한 일은 모두 이 지점 앞에서 끝냅니다. `copy_process()`와 같은 순서입니다.

태스크가 끝나는 길인 `exit`는 상태 전이와 함께 [3장](ch03.html)에서 다룹니다.

## clone3와 늘어나는 플래그 {#clone3}

`clone`의 플래그 인자는 32비트이고, 그중 8비트는 종료 시그널 번호입니다. 남은 24비트는 다 찼습니다. 인자 수도 레지스터로 넘길 수 있는 한계에 가깝습니다. 그래서 인자를 구조체로 받는 `clone3`가 만들어졌습니다.

```{.c file="include/uapi/linux/sched.h" line="102"}
struct clone_args {
	__aligned_u64 flags;
	__aligned_u64 pidfd;
	__aligned_u64 child_tid;
	__aligned_u64 parent_tid;
	__aligned_u64 exit_signal;
	__aligned_u64 stack;
	__aligned_u64 stack_size;
	__aligned_u64 tls;
	__aligned_u64 set_tid;
	__aligned_u64 set_tid_size;
	__aligned_u64 cgroup;
};
#endif

#define CLONE_ARGS_SIZE_VER0 64 /* sizeof first published struct */
#define CLONE_ARGS_SIZE_VER1 80 /* sizeof second published struct */
#define CLONE_ARGS_SIZE_VER2 88 /* sizeof third published struct */
```

호출은 `clone3(&args, sizeof(args))`입니다. 두 번째 인자가 핵심입니다. 유저 프로그램은 자기가 컴파일될 때 알던 구조체의 크기를 함께 넘기고, 커널은 그 크기를 보고 어느 판의 구조체인지 압니다.

::: {.fig src="clone-args.svg"}
`struct clone_args`는 두 번 뒤로 자랐습니다. 크기가 곧 버전입니다. 오른쪽은 `copy_struct_from_user()`가 크기 차이를 다루는 규칙입니다.
:::

`flags`가 64비트가 되면서 `clone`에는 없는 플래그와 필드가 생겼습니다.

| 플래그·필드 | 하는 일 |
|---|---|
| `CLONE_PIDFD` | 자식을 가리키는 파일 디스크립터(pidfd)를 돌려줍니다. PID는 재사용되지만 pidfd는 그 태스크만 가리킵니다. `clone`에서도 쓸 수 있습니다. |
| `set_tid` | 자식의 PID를 지정합니다. 체크포인트에서 프로세스를 되살릴 때 씁니다. 권한이 필요합니다. |
| `CLONE_CLEAR_SIGHAND` | 자식의 시그널 핸들러를 기본값으로 되돌립니다. |
| `CLONE_INTO_CGROUP` | 자식을 `cgroup` 필드가 가리키는 cgroup에 처음부터 넣습니다. 만든 뒤 옮길 필요가 없습니다. |
| `CLONE_AUTOREAP` | 자식이 끝나면 좀비로 남지 않고 스스로 거둬집니다. 부모가 `wait`를 부를 필요가 없습니다. |
| `CLONE_NNP` | 자식에게 `no_new_privs`를 겁니다. `exec`로 권한이 늘어나지 않게 됩니다. |
| `CLONE_PIDFD_AUTOKILL` | 돌려받은 pidfd가 닫히면 자식에게 `SIGKILL`을 보냅니다. |
| `CLONE_EMPTY_MNTNS` | 루트 마운트 하나만 있는 새 마운트 네임스페이스에서 자식을 시작합니다. |

아래 넷은 v7.1에서 들어왔습니다. `copy_process()`의 첫머리에는 이 플래그들의 조합 규칙이 줄지어 있습니다. 예를 들어 `CLONE_PIDFD_AUTOKILL`은 `CLONE_PIDFD`와 `CLONE_AUTOREAP`를 함께 요구하고, `CLONE_NNP`가 없으면 `CAP_SYS_ADMIN`이 있어야 합니다. pidfd를 닫는 것만으로 자기보다 권한이 높아진 프로세스를 죽일 수 있으면 안 되기 때문입니다.

::: {.design}
시스템 콜은 한번 내놓으면 고칠 수 없습니다. 유저 프로그램이 의존하기 때문입니다. `clone`은 인자가 모자랄 때마다 쓰지 않는 비트를 찾아 뜻을 덧씌웠고, 아키텍처마다 인자 순서가 달라지는 일까지 생겼습니다(`CONFIG_CLONE_BACKWARDS`가 세 가지입니다). `clone3`는 늘어날 것을 전제로 설계했습니다. 규칙은 세 가지입니다. 인자는 구조체로 받고 크기를 함께 받는다. 새 필드는 맨 뒤에만 붙인다. 값 0은 "그 필드가 없던 때와 같은 동작"을 뜻한다. 이 규칙을 지키면 옛 프로그램은 새 커널에서, 새 프로그램은 새 기능을 쓰지 않는 한 옛 커널에서 그대로 돕니다. `copy_struct_from_user()`가 이 규칙을 함수 하나로 구현합니다. 버전 번호를 따로 두지 않고 크기를 버전으로 쓴다는 점이 요령입니다. 시스템 콜 설계는 [19장](ch19.html)에서 다시 다룹니다.
:::

## 태스크 수의 한도 {#limits}

태스크는 메모리를 씁니다. x86-64에서는 커널 스택만 태스크마다 16KB이고 `task_struct`가 더해집니다. 스스로를 끝없이 복제하는 프로그램, 이른바 포크 폭탄 하나가 시스템을 멈추지 못하게 하려면 한도가 필요합니다. `copy_process()`는 세 겹으로 검사합니다.

```{.c file="kernel/fork.c" line="2187"}
	retval = -EAGAIN;
	if (is_rlimit_overlimit(task_ucounts(p), UCOUNT_RLIMIT_NPROC, rlimit(RLIMIT_NPROC))) {
		if (p->real_cred->user != INIT_USER &&
		    !capable(CAP_SYS_RESOURCE) && !capable(CAP_SYS_ADMIN))
			goto bad_fork_cleanup_count;
	}
	current->flags &= ~PF_NPROC_EXCEEDED;

	/*
	 * If multiple threads are within copy_process(), then this check
	 * triggers too late. This doesn't hurt, the check is only there
	 * to stop root fork bombs.
	 */
	retval = -EAGAIN;
	if (data_race(nr_threads >= max_threads))
		goto bad_fork_cleanup_count;
```

| 한도 | 범위 | 보는 곳 | 넘으면 |
|---|---|---|---|
| `RLIMIT_NPROC` | 사용자별 | `ulimit -u` | `EAGAIN`. root와 `CAP_SYS_RESOURCE` 등은 면제 |
| `max_threads` | 시스템 전체 | `/proc/sys/kernel/threads-max` | `EAGAIN`. 면제 없음 |
| `pids.max` | cgroup별 | cgroup의 `pids.max` | `EAGAIN` |

`max_threads`의 기본값은 부팅 때 `set_max_threads()`가 메모리 크기로 정합니다. 모든 태스크의 커널 스택을 합쳐도 메모리의 8분의 1을 넘지 않게 하는 값입니다. 주석이 밝히듯 이 검사는 락 없이 `nr_threads`를 읽으므로 여럿이 동시에 `fork`하면 한도를 조금 넘을 수 있습니다. root의 포크 폭탄을 막는 안전망이라 정확할 필요가 없다는 판단입니다. `data_race()`는 "이 경쟁은 알고 둔 것"이라고 검사 도구에 알리는 표시입니다([27장](ch27.html)).

세 번째 한도는 위 코드가 아니라 `cgroup_can_fork()`에서 걸립니다. pids 컨트롤러가 cgroup에 속한 태스크 수를 세다가 `pids.max`를 넘으면 거절합니다. 컨테이너 하나가 호스트의 PID를 다 써 버리지 못하게 하는 장치입니다([22장](ch22.html)).

PID 번호 자체에도 상한이 있습니다. `/proc/sys/kernel/pid_max`입니다. 커널의 기본값은 32768과 CPU 수 × 1024 가운데 큰 쪽이고, 64비트에서는 4194304까지 올릴 수 있습니다. 번호를 끝까지 쓰면 300부터 다시 돌며 빈 번호를 찾습니다.

::: {.lab}
한도와 현재 값을 확인합니다.

```console
$ cat /proc/sys/kernel/threads-max
126329
$ cat /proc/sys/kernel/pid_max
4194304
$ ulimit -u
63164
$ cat /sys/fs/cgroup/user.slice/pids.max
max
$ grep processes /proc/stat
processes 418233
```

값은 예시입니다. `/proc/stat`의 `processes`는 부팅 뒤 만들어진 태스크의 누계(`total_forks`)입니다.

태스크가 만들어지는 순간은 추적점으로 봅니다. `bpftrace`가 있으면 한 줄입니다.

```console
# bpftrace -e 'tracepoint:sched:sched_process_fork {
    printf("%s(%d) -> %d\n", comm, pid, args.child_pid); }'
bash(3051) -> 41201
make(41201) -> 41202
...

# bpftrace -e 'tracepoint:task:task_newtask { @[args.clone_flags] = count(); }'
```

첫 번째는 `kernel_clone()` 안의 `trace_sched_process_fork()`에, 두 번째는 `copy_process()` 끝의 `trace_task_newtask()`에 걸립니다. 두 번째 명령은 플래그 조합별로 횟수를 세므로, 프로세스와 스레드가 어떤 비율로 만들어지는지 볼 수 있습니다.
:::

## 정리 {#summary}

- `fork`, `vfork`, `clone`, `clone3`와 커널 스레드 생성은 모두 `kernel_clone()`으로 모입니다. 차이는 `struct kernel_clone_args`에 담긴 플래그뿐입니다.
- `kernel_clone()`은 `copy_process()`로 태스크를 만들고 `wake_up_new_task()`로 깨웁니다. 부모가 받는 반환값은 이 함수의 `return nr`입니다. 부모와 자식의 실행 순서는 정해져 있지 않습니다.
- `copy_process()`는 부모의 `task_struct`를 복사한 뒤 자원별 `copy_*()`로 공유하거나 복사합니다. 실패할 수 있는 일을 모두 끝낸 뒤에야 `tasklist_lock`을 쥐고 태스크를 시스템에 연결합니다. 중간에 실패하면 `goto` 라벨을 따라 역순으로 되돌립니다.
- 자식이 받는 0은 `copy_thread()`의 `childregs->ax = 0`입니다. 자식은 `ret_from_fork_asm`에서 첫 실행을 시작해 시스템 콜의 출구로 나갑니다.
- `fork`는 페이지 테이블만 복사하고 쓸 수 있던 항목을 양쪽 모두 읽기 전용으로 바꿉니다. 실제 복사는 쓰기 폴트 때 페이지 단위로 일어납니다.
- `vfork`는 주소 공간을 복사하지 않고, 자식이 `exec`나 `exit`로 `mm`을 놓을 때까지 부모를 completion으로 재웁니다.
- `clone3`는 크기가 딸린 구조체로 인자를 받아, 옛 프로그램을 깨지 않고 필드와 플래그를 늘려 갑니다.

## 확인 문제 {#quiz}

::: {.q}
`fork()`를 부른 프로그램에서 부모는 자식의 PID를, 자식은 0을 받습니다. 두 값은 각각 커널의 어느 코드가 어디에 적습니까?

::: {.a}
부모의 값은 `kernel_clone()`이 돌려준 `nr`입니다. 시스템 콜 진입 코드가 모든 시스템 콜에 대해 하듯이 그 값을 부모의 `pt_regs`의 `ax`에 적습니다(`regs->ax = x64_sys_call(...)`). 자식의 값은 `copy_thread()`가 적습니다. 부모의 `pt_regs`를 자식의 커널 스택 꼭대기에 복사한 뒤 `childregs->ax = 0`으로 고칩니다. 두 태스크 모두 유저 모드로 나갈 때 자기 `pt_regs`의 `ax`가 `rax` 레지스터에 실립니다.
:::
:::

::: {.q}
새로 만든 태스크는 `copy_process()`가 끝날 때까지 `TASK_NEW` 상태이고, 태스크 목록에는 함수의 맨 끝에서야 연결됩니다. 이 두 가지가 각각 막는 문제는 무엇입니까?

::: {.a}
`TASK_NEW`는 조립 중인 태스크가 **실행되는** 것을 막습니다. 이 상태의 태스크는 런큐에 오르지 않고 시그널 같은 외부 사건으로도 깨워지지 않습니다. 연결을 맨 끝으로 미루는 것은 조립 중인 태스크가 남에게 **보이는** 것을 막습니다. PID로 찾을 수 있는 태스크가 생성 도중 실패해 사라지면, 그 사이에 그 태스크를 본 쪽의 처리가 복잡해집니다. 실패할 수 있는 일을 모두 끝낸 뒤에 연결하면 한번 보인 태스크는 반드시 완성된 태스크입니다.
:::
:::

::: {.q}
8GB의 익명 메모리를 쓰는 프로세스가 `fork()`를 부른 뒤, 부모가 그 메모리 전체를 한 번씩 고쳐 씁니다. 자식은 아무것도 하지 않고 잠들어 있습니다. 물리 메모리 사용량은 어떻게 변하고, 왜 그렇습니까?

::: {.a}
`fork` 직후에는 페이지 테이블만큼만 늘어납니다. 부모와 자식이 같은 물리 페이지를 읽기 전용으로 함께 가리키기 때문입니다. 부모가 페이지에 쓸 때마다 쓰기 폴트가 나고, 그 페이지는 자식도 가리키고 있으므로 새 페이지를 할당해 복사합니다. 전체를 다 고치면 8GB가 더 할당되어 합계가 약 16GB가 됩니다. 쓰기 시 복사는 쓰는 쪽이 부모든 자식이든 똑같이 일어납니다. 자식이 먼저 종료했다면 부모는 페이지를 혼자 쓰므로 복사 없이 쓰기 권한만 되살아납니다.
:::
:::

::: {.q}
`vfork()`를 부른 부모는 언제 깨어납니까? 자식이 `execve()`에 실패하고 무한 루프에 빠지면 부모는 어떻게 됩니까?

::: {.a}
자식이 부모의 `mm`에서 손을 뗄 때 깨어납니다. `execve()`가 `exec_mmap()`에서 새 `mm`으로 갈아타거나 자식이 종료할 때 `mm_release()`가 불리고, 그 안의 `complete_vfork_done()`이 부모가 기다리는 completion을 완료시킵니다. `execve()`가 일찍 실패하면 `mm_release()`가 불리지 않으므로 부모는 계속 잠들어 있습니다. 자식이 루프를 돌면 부모는 깨어나지 못합니다. 다만 `wait_for_vfork_done()`은 `TASK_KILLABLE`로 기다리므로 부모를 `SIGKILL`로 죽일 수는 있습니다. 그래서 `vfork` 뒤의 자식은 `execve()`가 실패하면 곧바로 `_exit()`를 불러야 합니다.
:::
:::

::: {.terms}
태스크 (task)
:   커널이 스케줄하는 실행 단위. 프로세스와 스레드 모두 `struct task_struct` 하나로 표현된다.

kernel_clone()
:   태스크를 만드는 모든 길이 모이는 함수. `copy_process()`로 만들고 `wake_up_new_task()`로 깨운다.

copy_process()
:   부모를 본떠 새 태스크를 조립하는 함수. 깨우지는 않는다.

pt_regs
:   유저 모드에서 커널로 들어올 때 유저 레지스터를 저장하는 틀. 커널 스택의 꼭대기에 놓인다.

ret_from_fork
:   새로 만들어진 태스크가 처음 스케줄될 때 실행을 시작하는 곳.

TASK_NEW
:   조립 중인 태스크의 상태. 런큐에 오를 수 없고 외부 사건으로 깨울 수 없다.

쓰기 시 복사 (copy-on-write)
:   페이지를 읽기 전용으로 공유해 두었다가, 쓰려는 순간에 그 페이지만 복사하는 기법.

completion
:   어떤 일이 끝났다는 신호 하나를 기다리는 커널의 동기화 도구. `vfork`에서 부모가 자식을 기다릴 때 쓴다.

pidfd
:   태스크를 가리키는 파일 디스크립터. PID와 달리 재사용으로 다른 태스크를 가리키게 되는 일이 없다.

clone3
:   인자를 크기가 딸린 구조체로 받는 태스크 생성 시스템 콜.
:::
