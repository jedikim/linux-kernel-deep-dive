::: {.lead}
유저 프로그램은 어느 명령어에서든 끊길 수 있습니다. 타이머 인터럽트가 오면 커널이 CPU를 가져가 다른 태스크에 넘깁니다. 그러면 커널 코드는 어떨까요. 시스템 콜을 처리하던 커널 함수 한가운데에서 다른 태스크로 넘어가도 될까요. 리눅스는 이 질문에 "안 된다"로 시작해서 "스케줄러가 정한다"까지 왔습니다. 이 장은 그 판단이 코드 어디에서 내려지는지 따라갑니다.
:::

::: {.goals}
- 커널 모드에서 실행 중인 태스크를 끊어도 되는지는 무엇으로 판단하는가?
- `preempt_count`의 비트는 각각 무엇을 세는가?
- `spin_lock()`은 왜 선점을 끄는가?
- 선점 모델 NONE, VOLUNTARY, FULL, LAZY, RT는 코드에서 어디가 다른가?
- 7.0부터 x86과 arm64에서 NONE과 VOLUNTARY를 고를 수 없게 된 까닭은 무엇인가?
:::

## 유저 선점과 커널 선점 {#user-vs-kernel}

**선점**(preemption)은 실행 중인 태스크가 스스로 양보하지 않았는데 스케줄러가 CPU를 빼앗아 다른 태스크에 주는 일입니다. 태스크가 `read()`에서 데이터를 기다리며 잠드는 것은 선점이 아닙니다. 그것은 자발적인 양보입니다.

선점은 태스크가 끊긴 자리에 따라 둘로 나뉩니다.

- **유저 선점**: 태스크가 유저 모드로 돌아가려는 순간에 일어납니다. 시스템 콜이 끝났거나 인터럽트 처리가 끝나 유저 코드로 복귀하기 직전입니다. 이때 커널은 자기 일을 다 마친 상태이므로 언제나 안전합니다. 리눅스는 처음부터 유저 선점을 했습니다.
- **커널 선점**: 태스크가 커널 모드에서 실행되는 도중에 일어납니다. 시스템 콜을 처리하던 함수 한가운데일 수 있습니다. 커널이 자료구조를 고치던 중이었다면 위험합니다.

::: {.fig src="return-paths.svg"}
인터럽트 처리를 마친 커널은 끊긴 자리가 유저 모드였는지 커널 모드였는지에 따라 다른 길로 돌아갑니다. 커널 선점은 오른쪽 길에서 일어납니다.
:::

그림의 왼쪽 길은 조건이 하나입니다. 다시 스케줄해 달라는 요청이 있으면 `schedule()`을 부릅니다. 오른쪽 길은 조건이 둘입니다. 요청이 있어야 하고, **지금 끊어도 안전해야** 합니다. 커널 선점을 이해한다는 것은 이 두 번째 조건을 이해하는 일입니다.

커널 선점이 없으면 어떻게 될까요. 우선순위가 낮은 태스크가 커널 안에서 긴 반복문을 돌고 있다고 합시다. 그 사이에 오디오 재생 태스크가 깨어나도, 앞의 태스크가 유저 모드로 돌아가거나 스스로 잠들 때까지 기다려야 합니다. 이 기다림이 수십 밀리초가 되면 소리가 끊깁니다. 반대로 커널 선점을 켜면 응답은 빨라지지만 컨텍스트 스위치가 늘고, 커널 곳곳에 "여기서는 끊지 마시오" 표시를 정확히 해 두어야 합니다.

## 두 개의 변수 {#two-variables}

커널 선점 여부는 변수 두 개로 정해집니다.

1. **`preempt_count`**: 지금 끊어도 *되는가*. 0이면 됩니다. 0이 아니면 락을 쥐고 있거나 인터럽트를 처리하는 중이라는 뜻입니다.
2. **`TIF_NEED_RESCHED`**: 지금 끊어야 *하는가*. 이 플래그가 서 있으면 더 급한 태스크가 기다리고 있다는 뜻입니다.

::: {.fig src="two-variables.svg"}
두 조건이 모두 참일 때만 커널 선점이 일어납니다. 한쪽이라도 거짓이면 실행 중인 커널 코드는 계속 갑니다.
:::

`TIF_NEED_RESCHED`는 태스크마다 있는 `thread_info`의 플래그 비트입니다. 스케줄러가 "지금 도는 태스크를 바꿔야겠다"고 판단하면 이 비트를 세웁니다. 판단이 내려지는 곳은 주로 두 군데입니다.

- 태스크가 깨어날 때. 깨어난 태스크가 현재 태스크보다 먼저 돌아야 하면 세웁니다.
- 틱마다. 현재 태스크가 자기 몫의 시간을 다 썼으면 세웁니다.

비트를 세우는 함수가 `resched_curr()`입니다.

```{.c file="kernel/sched/core.c" line="1195"}
static void __resched_curr(struct rq *rq, int tif)
{
	struct task_struct *curr = rq->curr;
	struct thread_info *cti = task_thread_info(curr);
	int cpu;
	/* ... */
	if (cti->flags & ((1 << tif) | _TIF_NEED_RESCHED))
		return;

	cpu = cpu_of(rq);

	trace_sched_set_need_resched_tp(curr, cpu, tif);
	if (cpu == smp_processor_id()) {
		set_ti_thread_flag(cti, tif);
		if (tif == TIF_NEED_RESCHED)
			set_preempt_need_resched();
		return;
	}

	if (set_nr_and_not_polling(cti, tif)) {
		if (tif == TIF_NEED_RESCHED)
			smp_send_reschedule(cpu);
	} else {
		trace_sched_wake_idle_without_ipi(cpu);
	}
}
/* ... */
void resched_curr(struct rq *rq)
{
	__resched_curr(rq, TIF_NEED_RESCHED);
}
```

읽을 곳은 세 군데입니다.

- 이 함수는 **플래그만 세웁니다.** 태스크를 바꾸지 않습니다. 실제 전환은 나중에 누군가 이 플래그를 확인하고 `schedule()`을 부를 때 일어납니다.
- 대상이 다른 CPU에서 도는 태스크라면 `smp_send_reschedule()`로 그 CPU에 인터럽트(IPI)를 보냅니다. 인터럽트를 받은 CPU는 처리를 마치고 돌아가는 길에 플래그를 확인합니다. 그림 6-1의 바로 그 갈림길입니다.
- 인자 `tif`가 있습니다. 예전에는 플래그가 하나였지만 지금은 `TIF_NEED_RESCHED`와 `TIF_NEED_RESCHED_LAZY` 둘 중 하나를 고릅니다. 뒤의 [PREEMPT_LAZY 절](#lazy)에서 다룹니다.

## preempt_count의 비트 {#preempt-count}

`preempt_count`는 단순한 카운터가 아닙니다. 정수 하나를 여러 칸으로 나눠 서로 다른 것을 셉니다.

::: {.fig src="preempt-count-bits.svg"}
v7.3의 `preempt_count` 비트 배치. 어느 칸이든 0이 아니면 선점할 수 없습니다.
:::

```{.c file="include/linux/preempt.h" line="14"}
/*
 * We put the hardirq and softirq counter into the preemption
 * counter. The bitmask has the following meaning:
 *
 * - bits 0-7 are the preemption count (max preemption depth: 256)
 * - bits 8-15 are the softirq count (max # of softirqs: 256)
 * - bits 16-23 are the hardirq disable count (max # of hardirq disable: 256)
 * - bits 24-27 are the hardirq count (max # of hardirqs: 16)
 * - bit 28 is the NMI flag (no nesting count, tracked separately)
 * ...
 */
#define PREEMPT_BITS	8
#define SOFTIRQ_BITS	8
#define HARDIRQ_DISABLE_BITS	8
#define HARDIRQ_BITS	4
#define NMI_BITS	(1 + 3*IS_ENABLED(CONFIG_HAS_SEPARATE_PREEMPT_RESCHED_BITS))
```

| 칸 | 비트 | 올리는 코드 | 뜻 |
|---|---|---|---|
| 선점 카운트 | 0–7 | `preempt_disable()`, `spin_lock()` | 선점을 끈 횟수. 중첩될 수 있어 카운터입니다. |
| softirq 카운트 | 8–15 | `local_bh_disable()`, softirq 진입 | softirq를 실행 중이거나 막아 둔 상태 ([11장](ch11.html)) |
| hardirq 비활성 카운트 | 16–23 | `local_interrupt_disable()` | 인터럽트를 끈 횟수. 중첩을 세기 위한 칸입니다. |
| hardirq 카운트 | 24–27 | `irq_enter()` | 하드웨어 인터럽트 핸들러 안 ([10장](ch10.html)) |
| NMI | 28– | `nmi_enter()` | 마스크할 수 없는 인터럽트 안 |

한 정수에 모아 둔 덕분에 "지금 어떤 컨텍스트인가"를 묻는 질문이 모두 비트 연산 한 번으로 끝납니다.

```{.c file="include/linux/preempt.h" line="154"}
#define in_nmi()		(nmi_count())
#define in_hardirq()		(hardirq_count())
#define in_serving_softirq()	(softirq_count() & SOFTIRQ_OFFSET)
#ifdef CONFIG_PREEMPT_RT
# define in_task()		(!((preempt_count() & (NMI_MASK | HARDIRQ_MASK)) | in_serving_softirq()))
#else
# define in_task()		(!(preempt_count() & (NMI_MASK | HARDIRQ_MASK | SOFTIRQ_OFFSET)))
#endif
/* ... */
#define preemptible()	(preempt_count() == 0 && !irqs_disabled())
```

`preemptible()`이 이 절의 결론입니다. 모든 칸이 0이고 인터럽트가 켜져 있을 때만 끊을 수 있습니다. 인터럽트 핸들러 안에서는 hardirq 칸이 0이 아니므로, 인터럽트 핸들러가 선점당하는 일은 없습니다. 인터럽트 컨텍스트와 태스크 컨텍스트의 차이는 [13장](ch13.html)에서 자세히 봅니다.

::: {.old}
많은 자료가 hardirq 카운트를 비트 16–19에, NMI 카운트를 비트 20–23에 그립니다. v7.3에서는 그 자리에 hardirq 비활성 카운트 8비트가 들어왔고, hardirq 카운트는 24–27로 밀렸습니다. NMI는 중첩 깊이를 따로 떼어 CPU별 변수 `nmi_nesting`에 두고, `preempt_count`에는 "NMI 안"이라는 사실만 남겼습니다. 비트 번호를 외우지 말고 `include/linux/preempt.h`의 주석을 확인하는 편이 안전합니다.
:::

### need_resched를 같은 변수에 접어 넣기

x86에서는 `preempt_count`가 CPU별 변수 `__preempt_count`입니다. 여기에 요령이 하나 있습니다. "끊어야 하는가"를 나타내는 비트를 `preempt_count`의 맨 위 비트에 **뒤집어서** 같이 넣어 둡니다.

```{.c file="arch/x86/include/asm/preempt.h" line="68"}
/*
 * We fold the NEED_RESCHED bit into the preempt count such that
 * preempt_enable() can decrement and test for needing to reschedule with a
 * single instruction.
 *
 * We invert the actual bit, so that when the decrement hits 0 we know we both
 * need to resched (the bit is cleared) and can resched (no preempt count).
 */
/* ... */
static __always_inline bool __preempt_count_dec_and_test(void)
{
	return GEN_UNARY_RMWcc(__pc_dec, __my_cpu_var(__preempt_count), e,
			       __percpu_arg([var]));
}
```

맨 위 비트는 평소에 1입니다. 재스케줄 요청이 오면 0으로 내립니다. 그러면 "카운터가 0이고 요청이 있다"는 두 조건이 "변수 전체가 0이다"라는 조건 하나로 합쳐집니다. `preempt_enable()`은 `dec` 명령어 하나로 카운터를 내리고, 그 결과가 0인지 CPU의 제로 플래그만 보면 됩니다.

::: {.design}
`preempt_enable()`은 커널에서 가장 자주 실행되는 코드에 속합니다. 락을 풀 때마다 불리기 때문입니다. 이런 경로에서는 조건 두 개를 따로 읽고 비교하는 비용도 아깝습니다. 그래서 두 조건을 한 변수에 접어 넣어 명령어 하나로 판정하게 했습니다. 자주 도는 경로일수록 자료의 표현을 바꿔 검사를 싸게 만든다는 발상은 커널 곳곳에 반복해서 나옵니다. 다만 이런 최적화는 읽기 어렵게 만드는 값을 치릅니다. 그래서 위 코드처럼 주석이 구현보다 긴 것이 보통입니다.
:::

## 선점을 끄는 코드 {#disable}

커널 코드가 "여기서는 끊지 마시오"라고 표시하는 방법이 `preempt_disable()`입니다.

```{.c file="include/linux/preempt.h" line="239"}
#define preempt_disable() \
do { \
	preempt_count_inc(); \
	barrier(); \
} while (0)

/* ... */
#define preempt_enable() \
do { \
	barrier(); \
	if (unlikely(preempt_count_dec_and_test())) \
		__preempt_schedule(); \
} while (0)
```

끄는 쪽은 카운터를 올리기만 합니다. 켜는 쪽이 중요합니다. 카운터를 내렸더니 0이 되었고 그 사이에 재스케줄 요청이 와 있었다면, 그 자리에서 바로 스케줄러를 부릅니다. 선점을 꺼 둔 동안 미뤄진 요청이 선점을 다시 켜는 순간 처리되는 구조입니다.

`barrier()`는 컴파일러에게 "이 지점을 넘어 코드를 재배치하지 마시오"라고 알리는 표시입니다. 보호하려는 코드가 최적화 과정에서 카운터 증가보다 앞으로 옮겨지면 안 되기 때문입니다.

### spin_lock()이 선점을 끄는 이유

`preempt_disable()`을 직접 부르는 코드는 많지 않습니다. 대부분은 스핀락을 통해 부릅니다.

```{.c file="include/linux/spinlock_api_smp.h" line="186"}
static inline void __raw_spin_lock(raw_spinlock_t *lock)
	__acquires(lock) __no_context_analysis
{
	preempt_disable();
	spin_acquire(&lock->dep_map, 0, 0, _RET_IP_);
	LOCK_CONTENDED(lock, do_raw_spin_trylock, do_raw_spin_lock);
}
```

첫 줄이 `preempt_disable()`입니다. 락을 잡기도 전에 선점부터 끕니다. 이유는 두 가지입니다.

::: {.fig src="lock-holder-preemption.svg"}
스핀락을 쥔 태스크가 선점당하면, 그 락을 기다리는 다른 CPU는 락 주인이 다시 실행될 때까지 헛돕니다.
:::

**첫째, 락 주인이 선점당하면 기다리는 쪽이 CPU를 태웁니다.** 스핀락은 잠들지 않고 반복문을 돌며 기다립니다. 락 주인이 CPU에서 쫓겨나 있으면 기다리는 쪽은 락이 풀릴 가망이 없는데도 계속 돕니다. 그림의 위쪽이 이 상황입니다. 이것을 **락 주인 선점**(lock holder preemption)이라고 합니다.

**둘째, 같은 CPU 안에서 교착이 생깁니다.** 태스크 A가 락을 쥔 채 선점당하고, 같은 CPU에서 이어 실행된 태스크 B가 같은 락을 잡으려 한다고 합시다. B는 돌면서 기다리고, A는 B가 CPU를 놓아야 실행되는데 B는 놓지 않습니다. 스핀락은 "기다리는 동안 락 주인은 다른 CPU에서 실행 중이다"라는 가정 위에서만 성립합니다.

두 문제 모두 락을 쥔 동안 선점을 꺼서 막습니다. 그래서 스핀락으로 보호되는 구간은 짧아야 하고, 그 안에서 잠들면 안 됩니다. 스핀락과 뮤텍스의 내부는 [14장](ch14.html)에서 다룹니다.

### CPU별 데이터

선점을 끄는 또 하나의 이유는 CPU별 데이터입니다. 커널은 락 경합을 피하려고 CPU마다 따로 두는 변수를 많이 씁니다. 그런데 선점을 켜 둔 채로 CPU 0의 변수를 읽고, 선점당해 CPU 1로 옮겨진 뒤에 값을 쓰면, 읽은 것과 쓴 것이 서로 다른 CPU의 변수가 됩니다. 그래서 CPU별 데이터를 만질 때는 `get_cpu()`와 `put_cpu()`로 감싸 선점을 끕니다.

선점을 끄는 대신 **다른 CPU로 옮겨지는 것만** 막는 방법도 있습니다. `migrate_disable()`입니다. 이 경우 태스크는 선점당할 수 있지만 다시 실행될 때 같은 CPU에서 실행됩니다. 실시간 커널에서 선점을 꺼 두는 구간을 줄이려고 들어온 도구이고, 뒤의 [PREEMPT_RT 절](#rt)에서 다시 나옵니다.

## 선점이 일어나는 자리 {#where}

재스케줄 요청은 플래그일 뿐이라고 했습니다. 그 플래그를 확인하는 자리는 정해져 있습니다.

::: {.fig src="entry-points.svg"}
스케줄러로 들어가는 네 가지 길. 가운데 두 길이 커널 선점이고, 선점 모델에 따라 열리거나 닫힙니다.
:::

**① 유저 모드로 돌아갈 때.** 유저 선점입니다. 모든 선점 모델에서 열려 있습니다.

```{.c file="kernel/entry/common.c" line="42"}
static __always_inline unsigned long __exit_to_user_mode_loop(struct pt_regs *regs,
							      unsigned long ti_work)
{
	/*
	 * Before returning to user space ensure that all pending work
	 * items have been completed.
	 */
	while (ti_work & EXIT_TO_USER_MODE_WORK_LOOP) {

		local_irq_enable();

		if (ti_work & (_TIF_NEED_RESCHED | _TIF_NEED_RESCHED_LAZY)) {
			if (!rseq_grant_slice_extension(ti_work, TIF_SLICE_EXT_DENY))
				schedule();
		}
	/* ... */
	}
/* ... */
}
```

**② 인터럽트를 마치고 커널 코드로 돌아갈 때.** 커널 선점의 대표적인 자리입니다.

```{.c file="kernel/entry/common.c" line="137"}
void raw_irqentry_exit_cond_resched(void)
{
	if (!preempt_count()) {
		/* Sanity check RCU and thread stack */
		rcu_irq_exit_check_preempt();
		if (IS_ENABLED(CONFIG_DEBUG_ENTRY))
			WARN_ON_ONCE(!on_thread_stack());
		if (need_resched() && arch_irqentry_exit_need_resched())
			preempt_schedule_irq();
	}
}
```

앞에서 본 두 조건이 그대로 있습니다. `!preempt_count()`가 "끊어도 되는가"이고 `need_resched()`가 "끊어야 하는가"입니다.

**③ `preempt_enable()`에서 카운터가 0이 될 때.** 선점을 꺼 둔 동안 요청이 와 있었으면 여기서 처리합니다.

```{.c file="kernel/sched/core.c" line="7445"}
static void __sched notrace preempt_schedule_common(void)
{
	do {
		/* ... */
		preempt_disable_notrace();
		preempt_latency_start(1);
		__schedule(SM_PREEMPT);
		preempt_latency_stop(1);
		preempt_enable_no_resched_notrace();

		/*
		 * Check again in case we missed a preemption opportunity
		 * between schedule and now.
		 */
	} while (need_resched());
}
/* ... */
asmlinkage __visible void __sched notrace preempt_schedule(void)
{
	/*
	 * If there is a non-zero preempt_count or interrupts are disabled,
	 * we do not want to preempt the current task. Just return..
	 */
	if (likely(!preemptible()))
		return;
	preempt_schedule_common();
}
```

**④ 스스로 양보할 때.** 태스크가 잠들면서 `schedule()`을 부르거나, 긴 반복문 중간에 `cond_resched()`를 부르는 경우입니다. 이것은 선점이 아니라 자발적 양보입니다.

### SM_PREEMPT가 구분하는 것

②와 ③은 `__schedule(SM_PREEMPT)`를, ①과 ④는 `__schedule(SM_NONE)`을 부릅니다. 이 인자는 태스크가 **왜** 스케줄러에 들어왔는지 알려 줍니다.

태스크가 잠들 때는 보통 이렇게 합니다. 먼저 자기 상태를 `TASK_INTERRUPTIBLE`로 바꾸고, 조건을 한 번 더 확인하고, `schedule()`을 부릅니다. 스케줄러는 상태가 `TASK_RUNNING`이 아닌 태스크를 런큐에서 뺍니다. 그런데 상태를 바꾼 직후, `schedule()`을 부르기 전에 선점당하면 어떻게 될까요. 스케줄러가 이 태스크를 런큐에서 빼 버리면 아직 조건 확인도 못 한 태스크가 영영 잠들 수 있습니다.

그래서 `SM_PREEMPT`로 들어온 경우에는 태스크 상태가 무엇이든 런큐에서 빼지 않습니다. 선점당한 태스크는 여전히 실행 가능한 태스크입니다. 태스크 상태와 대기 큐는 [3장](ch03.html), `__schedule()`의 전체 흐름은 [4장](ch04.html)에서 봅니다.

## 선점 모델 {#models}

그림 6-5의 가운데 두 길을 얼마나 열어 둘지가 **선점 모델**입니다. 커널을 빌드할 때 고릅니다.

::: {.fig src="models-timeline.svg"}
태스크 C가 커널 모드에서 실행되는 도중에 태스크 D가 깨어났을 때, D가 CPU를 받는 시점이 선점 모델마다 다릅니다.
:::

| 모델 | Kconfig | 커널 코드가 끊기는 자리 | 겨냥한 용도 |
|---|---|---|---|
| NONE | `PREEMPT_NONE` | 스스로 잠들 때, `cond_resched()` | 처리량이 중요한 서버 |
| VOLUNTARY | `PREEMPT_VOLUNTARY` | 위에 더해 `might_sleep()` 자리 | 데스크톱 |
| FULL | `PREEMPT` | `preempt_count`가 0인 모든 자리 | 지연 시간이 중요한 데스크톱·임베디드 |
| LAZY | `PREEMPT_LAZY` | FULL과 같지만 일반 태스크는 틱 하나만큼 미룸 | FULL의 응답성과 NONE의 처리량 사이 |
| RT | `PREEMPT_RT` | 스핀락을 쥔 구간까지 포함 | 실시간 보장이 필요한 시스템 |

NONE과 VOLUNTARY에는 그림 6-5의 ②와 ③이 없습니다. 대신 커널 코드 곳곳에 `cond_resched()`가 심어져 있습니다. 긴 반복문을 도는 코드가 "혹시 양보할 일이 있으면 지금 하겠다"고 스스로 확인하는 자리입니다. VOLUNTARY는 `might_sleep()`도 같은 확인 자리로 씁니다. `might_sleep()`은 원래 "이 함수는 잠들 수 있으니 원자적 컨텍스트에서 부르지 마시오"라는 디버깅용 표시인데, 잠들어도 되는 자리라면 양보해도 되는 자리이기 때문입니다.

### PREEMPT_DYNAMIC: 부팅할 때 고르기

배포판은 커널 바이너리 하나로 서버와 데스크톱을 모두 지원하고 싶어 합니다. `PREEMPT_DYNAMIC`은 선점 모델을 부팅 인자 `preempt=`로 고르게 해 줍니다. 구현은 소스의 주석에 표로 정리되어 있습니다.

```{.c file="kernel/sched/core.c" line="7938"}
 * NONE:
 *   cond_resched               <- __cond_resched
 *   might_resched              <- RET0
 *   preempt_schedule           <- NOP
 *   preempt_schedule_notrace   <- NOP
 *   irqentry_exit_cond_resched <- NOP
 *   dynamic_preempt_lazy       <- false
 *
 * VOLUNTARY:
 *   cond_resched               <- __cond_resched
 *   might_resched              <- __cond_resched
 *   preempt_schedule           <- NOP
 *   preempt_schedule_notrace   <- NOP
 *   irqentry_exit_cond_resched <- NOP
 *   dynamic_preempt_lazy       <- false
 *
 * FULL:
 *   cond_resched               <- RET0
 *   might_resched              <- RET0
 *   preempt_schedule           <- preempt_schedule
 *   preempt_schedule_notrace   <- preempt_schedule_notrace
 *   irqentry_exit_cond_resched <- irqentry_exit_cond_resched
 *   dynamic_preempt_lazy       <- false
 *
 * LAZY:
 *   cond_resched               <- RET0
 *   might_resched              <- RET0
 *   preempt_schedule           <- preempt_schedule
 *   preempt_schedule_notrace   <- preempt_schedule_notrace
 *   irqentry_exit_cond_resched <- irqentry_exit_cond_resched
 *   dynamic_preempt_lazy       <- true
```

이 표가 선점 모델의 정의입니다. 모델의 차이는 함수 다섯 개와 스위치 하나를 켜고 끄는 것이 전부입니다. NONE에서 `preempt_schedule`이 `NOP`라는 것은 `preempt_enable()`이 스케줄러를 부르지 않는다는 뜻이고, FULL에서 `cond_resched`가 `RET0`이라는 것은 어차피 어디서든 끊을 수 있으니 자발적 확인이 필요 없다는 뜻입니다.

::: {.design}
모델을 실행 중에 고르게 하려면 가장 단순한 방법은 전역 변수를 읽어 `if`로 가르는 것입니다. 그런데 이 분기는 `preempt_enable()`과 인터럽트 복귀 경로에 놓입니다. 초당 수백만 번 도는 자리입니다. 그래서 커널은 **스태틱 콜**(static call)을 씁니다. 함수 호출 명령어의 목적지 주소를 부팅 때 직접 고쳐 써서, 실행 중에는 분기도 간접 호출도 없이 보통의 직접 호출과 같은 비용만 듭니다. 설정 가능성과 성능을 맞바꾸지 않고, 코드를 고쳐 쓰는 복잡함으로 둘 다 얻은 사례입니다. 스태틱 콜을 지원하지 않는 아키텍처는 같은 일을 스태틱 키로 합니다. 이 기법은 [25장](ch25.html)에서 다시 봅니다.
:::

::: {.lab}
실행 중인 커널의 선점 모델을 확인합니다.

```console
$ uname -v
#1 SMP PREEMPT_DYNAMIC Sun Oct 18 ...

$ sudo dmesg | grep -i 'dynamic preempt'
[    0.041] Dynamic Preempt: lazy

$ sudo cat /sys/kernel/debug/sched/preempt
full (lazy)
```

마지막 파일에서 괄호로 묶인 것이 현재 모델입니다. 이 파일에 `full`을 쓰면 재부팅 없이 바뀝니다. x86이나 arm64의 v7.x 커널에서는 목록에 `none`과 `voluntary`가 나오지 않습니다. 까닭은 다음 절에 있습니다.

빌드할 때 고른 값은 `grep PREEMPT /boot/config-$(uname -r)`로 봅니다.
:::

## PREEMPT_LAZY: 스케줄러가 정하는 선점 {#lazy}

오랫동안 선택지는 NONE, VOLUNTARY, FULL 셋이었습니다. 셋 다 불만이 있었습니다.

- **FULL은 너무 성급합니다.** 일반 태스크 하나가 깨어났다는 이유만으로, 커널 안에서 뮤텍스를 쥐고 일하던 태스크를 즉시 끊습니다. 그 뮤텍스를 기다리던 다른 태스크들은 락 주인이 다시 실행될 때까지 함께 밀립니다. 컨텍스트 스위치도 늘어납니다. 처리량이 중요한 서버에서 FULL이 꺼려진 이유입니다.
- **NONE과 VOLUNTARY는 `cond_resched()`에 기댑니다.** 지연 시간이 "누군가 그 반복문에 `cond_resched()`를 넣었는가"에 달려 있습니다. 긴 지연이 보고될 때마다 `cond_resched()`를 하나씩 더 심는 방식으로 수십 년을 버텼고, 그 수는 계속 늘었습니다. 어디에 넣어야 하는지는 원칙이 아니라 경험으로 정해졌습니다.

`PREEMPT_LAZY`의 발상은 **요청을 두 단계로 나누는 것**입니다.

- `TIF_NEED_RESCHED`: 지금 당장 바꿔 달라. 커널 코드 안이라도 끊습니다.
- `TIF_NEED_RESCHED_LAZY`: 급하지 않으니 적당한 때에 바꿔 달라. 커널 코드는 끊지 않고, 유저 모드로 돌아갈 때 처리합니다.

누가 어느 쪽을 쓰는지는 스케줄링 클래스가 정합니다. 일반 태스크를 다루는 fair 클래스는 느긋한 쪽을, 실시간 클래스(RT, deadline)는 급한 쪽을 씁니다.

```{.c file="kernel/sched/core.c" line="1259"}
static __always_inline int get_lazy_tif_bit(void)
{
	if (dynamic_preempt_lazy())
		return TIF_NEED_RESCHED_LAZY;

	return TIF_NEED_RESCHED;
}

void resched_curr_lazy(struct rq *rq)
{
	__resched_curr(rq, get_lazy_tif_bit());
}
```

fair 클래스에서 현재 태스크가 자기 몫을 다 썼을 때 부르는 코드를 보면 `resched_curr()`가 아니라 `resched_curr_lazy()`입니다.

```{.c file="kernel/sched/fair.c" line="2223"}
static void update_curr(struct cfs_rq *cfs_rq)
{
	/* ... */
	if (resched || !protect_slice(curr)) {
		resched_curr_lazy(rq);
		clear_buddies(cfs_rq, curr);
	}
}
```

그런데 느긋한 요청을 받은 태스크가 커널 안에서 유저 모드로 돌아가지 않고 계속 돌면 어떻게 될까요. 기한이 있습니다. **다음 틱**입니다.

```{.c file="kernel/sched/core.c" line="5782"}
void sched_tick(void)
{
	/* ... */
	if (dynamic_preempt_lazy() && tif_test_bit(TIF_NEED_RESCHED_LAZY))
		resched_curr(rq);

	donor->sched_class->task_tick(rq, donor, 0);
	/* ... */
}
```

틱이 왔는데 느긋한 요청이 아직 남아 있으면 급한 요청으로 올립니다. 그러면 이 틱 인터럽트에서 돌아가는 길(그림 6-5의 ②)에 태스크가 끊깁니다.

::: {.fig src="lazy-flow.svg"}
PREEMPT_LAZY에서 일반 태스크가 깨어났을 때. 현재 태스크는 최대 한 틱 동안 커널 안의 일을 마칠 기회를 얻습니다. 실시간 태스크가 깨어나면 기다리지 않고 바로 끊습니다.
:::

정리하면 LAZY는 이렇게 동작합니다.

- 실시간 태스크가 깨어나면 FULL과 똑같이 즉시 끊습니다. 응답성은 그대로입니다.
- 일반 태스크가 깨어나면 현재 태스크에게 최대 한 틱(`HZ=1000`이면 1ms)을 줍니다. 그 사이에 쥐고 있던 락을 풀고 유저 모드로 돌아가면 거기서 바뀝니다. 락 주인 선점이 줄어듭니다.
- 지연 시간의 상한이 `cond_resched()`가 심어진 위치가 아니라 틱 주기로 정해집니다. `cond_resched()`가 필요 없어집니다.

### 7.0에서 NONE과 VOLUNTARY가 사라진 까닭

LAZY가 NONE과 VOLUNTARY가 하던 일을 대신할 수 있다면, 선택지를 줄일 수 있습니다. v7.0에서 그렇게 되었습니다.

```{.kconfig file="kernel/Kconfig.preempt" line="17"}
choice
	prompt "Preemption Model"
	default PREEMPT_LAZY if ARCH_HAS_PREEMPT_LAZY
	default PREEMPT_NONE

config PREEMPT_NONE
	bool "No Forced Preemption (Server)"
	depends on !PREEMPT_RT
	depends on ARCH_NO_PREEMPT
	# ...

config PREEMPT_VOLUNTARY
	bool "Voluntary Kernel Preemption (Desktop)"
	depends on !ARCH_HAS_PREEMPT_LAZY
	depends on !ARCH_NO_PREEMPT
	# ...
```

`depends on` 줄을 읽으면 됩니다. NONE은 선점을 아예 지원하지 않는 아키텍처(`ARCH_NO_PREEMPT`)에서만, VOLUNTARY는 LAZY를 지원하지 않는 아키텍처에서만 고를 수 있습니다. v7.3에서 LAZY를 지원하는 아키텍처는 x86, arm64, riscv, s390, powerpc, loongarch입니다. 이 아키텍처들에서는 FULL, LAZY, RT만 남았고 기본값은 LAZY입니다.

이 변화의 목적지는 커널 소스에서 `cond_resched()`를 걷어 내는 것입니다. 선점 모델이 하나의 메커니즘으로 모이면, 곳곳에 흩어진 자발적 양보 지점과 그것을 둘러싼 "여기에도 넣어야 하나"라는 판단이 사라집니다.

::: {.note title="기본값을 바꾼 대가"}
기본값이 바뀌자 회귀 보고가 나왔습니다. v7.0 무렵, LAZY가 기본값이 된 뒤 PostgreSQL 벤치마크의 성능이 절반으로 떨어졌다는 보고가 메일링 리스트에 올라왔습니다. 보고자는 PostgreSQL이 유저 공간에서 쓰는 자체 스핀락의 경합이 크게 늘었다고 했습니다. 락을 쥔 스레드가 선점당해 나머지가 헛도는, 앞에서 본 락 주인 선점이 유저 공간에서 일어난다는 해석이었습니다.

스케줄러 메인테이너는 기본값을 되돌리는 대신 같은 릴리스에 들어간 **타임 슬라이스 연장**을 쓰라고 권했습니다. 유저 프로그램이 짧은 임계 구역에 들어가며 "잠깐만 끊지 말아 달라"고 표시해 두면, 커널이 유저 모드 복귀 길에서 선점을 잠깐 미뤄 주는 기능입니다. 미루는 시간은 기본 5마이크로초이고 50마이크로초까지 늘릴 수 있습니다. 앞의 `__exit_to_user_mode_loop()`에 있던 `rseq_grant_slice_extension()`이 그 자리입니다.

그런데 PostgreSQL 개발자가 재현해 보니 조건이 하나 더 있었습니다. 문제는 100GB쯤 되는 버퍼 풀을 huge page 없이 쓸 때만 나타났고, huge page를 켜면 사라졌습니다. huge page가 없으면 TLB 미스와 페이지 폴트가 늘어 임계 구역이 길어지고, 그만큼 임계 구역 안에서 선점당할 가능성이 커진 것입니다. 유저 공간 스핀락을 쓰지 않아도 같은 현상이 났으므로 타임 슬라이스 연장은 이 경우의 답이 아니었습니다. 기본값은 되돌려지지 않았습니다.

볼 것은 둘입니다. 커널 내부의 선택지를 줄인 결정이 유저 공간 프로그램의 성능 특성을 바꿀 수 있다는 점, 그리고 처음의 그럴듯한 진단이 재현 실험에서 뒤집혔다는 점입니다. 경과는 LWN의 [The 7.0 scheduler regression that wasn't](https://lwn.net/Articles/1067029/)에 정리되어 있습니다. 커널이 회귀를 어떻게 다루는지는 [26장](ch26.html)에서 봅니다.
:::

## PREEMPT_RT: 스핀락을 쥔 구간도 끊는 커널 {#rt}

FULL에서도 끊을 수 없는 구간이 남습니다. 스핀락을 쥔 구간, 인터럽트 핸들러, softirq입니다. 이 구간의 길이가 곧 최악의 지연 시간입니다. 공장 로봇이나 오디오 장비처럼 "100마이크로초 안에 반드시 반응한다"는 보장이 필요한 시스템에는 이것도 깁니다.

`PREEMPT_RT`는 그 남은 구간을 끊을 수 있게 만듭니다. 방법은 **끊을 수 없는 것들을 끊을 수 있는 것으로 바꿔치기**하는 것입니다.

| 대상 | 일반 커널 | PREEMPT_RT |
|---|---|---|
| `spinlock_t` | 돌면서 기다림, 선점 끔 | 잠들 수 있는 락(`rt_mutex` 기반), 선점 유지 |
| `raw_spinlock_t` | 돌면서 기다림, 선점 끔 | 그대로. 정말 끊기면 안 되는 곳에만 씁니다. |
| 인터럽트 핸들러 | 인터럽트 컨텍스트에서 실행 | 커널 스레드에서 실행 ([11장](ch11.html)) |
| softirq | 인터럽트 복귀 길에 실행 | 선점 가능한 태스크 컨텍스트에서 실행 |

RT 커널의 `spin_lock()`은 이렇게 생겼습니다.

```{.c file="kernel/locking/spinlock_rt.c" line="46"}
static __always_inline void __rt_spin_lock(spinlock_t *lock)
{
	rtlock_might_resched();
	rtlock_lock(&lock->lock);
	rcu_read_lock();
	migrate_disable();
}
```

앞에서 본 `__raw_spin_lock()`과 견주어 보면 `preempt_disable()`이 없습니다. 대신 `migrate_disable()`이 있습니다. 락을 쥔 태스크는 선점당할 수 있고, 다만 다른 CPU로 옮겨지지 않습니다. 락을 기다리는 쪽은 돌지 않고 잠듭니다. 그래서 락 주인 선점으로 CPU를 태우는 일도, 같은 CPU 안의 교착도 생기지 않습니다. 락을 쥔 낮은 우선순위 태스크 때문에 높은 우선순위 태스크가 오래 기다리는 문제는 우선순위 상속으로 풉니다. [15장](ch15.html)의 주제입니다.

이 설계에서 주목할 점은 드라이버 코드가 바뀌지 않았다는 것입니다. 수만 군데의 `spin_lock()` 호출은 그대로이고, 그 뜻만 빌드 설정에 따라 달라집니다. 대신 20년에 걸쳐 "여기는 정말 돌면서 기다려야 한다"는 자리를 찾아 `raw_spinlock_t`로 바꾸는 작업이 필요했습니다.

::: {.myth}
"실시간 커널은 더 빠른 커널이다." 아닙니다. PREEMPT_RT는 평균 처리량을 내주고 최악의 지연 시간을 줄입니다. 스핀락이 잠드는 락이 되면서 락 하나의 비용은 오히려 늘어납니다. 실시간의 뜻은 "빠르다"가 아니라 "기한을 넘기지 않는다"입니다.
:::

## 지연 시간과 처리량 {#tradeoff}

선점 모델은 결국 하나의 축 위에서 자리를 고르는 일입니다. 한쪽 끝은 처리량, 다른 쪽 끝은 최악의 지연 시간입니다.

| | NONE | VOLUNTARY | LAZY | FULL | RT |
|---|---|---|---|---|---|
| 커널 선점 | 없음 | 없음 | 있음 | 있음 | 있음 |
| 일반 태스크가 기다리는 최대 시간 | 양보 지점까지 | 양보 지점까지 | 약 한 틱 | 선점 불가 구간 | 선점 불가 구간 |
| 선점 불가 구간 | 커널 코드 전체 | 커널 코드 전체 | 락·IRQ 구간 | 락·IRQ 구간 | raw 락·저수준 코드만 |
| 컨텍스트 스위치 | 적음 | 적음 | 중간 | 많음 | 가장 많음 |

선점을 더 허용할수록 급한 태스크는 빨리 실행되지만, 전체가 단위 시간에 처리하는 일은 줄어드는 경향이 있습니다. 컨텍스트 스위치 자체의 비용, 캐시가 식는 비용, 락 주인이 끊겨 다른 태스크가 밀리는 비용 때문입니다. LAZY는 "실시간 태스크에게는 FULL처럼, 일반 태스크에게는 NONE에 가깝게"라는 절충입니다.

::: {.lab}
선점이 꺼져 있던 가장 긴 구간을 `ftrace`로 잽니다. 커널이 `CONFIG_PREEMPT_TRACER`로 빌드되어 있어야 합니다.

```console
# cd /sys/kernel/tracing
# echo preemptoff > current_tracer
# echo 1 > tracing_on
# sleep 10
# cat tracing_max_latency
217
# cat trace | head -30
```

`tracing_max_latency`는 마이크로초 단위이고, `trace`에는 그 구간이 어느 함수에서 시작해 어디서 끝났는지가 남습니다. `irqsoff`는 인터럽트가 꺼져 있던 구간을, `preemptirqsoff`는 둘 중 하나라도 꺼져 있던 구간을 잽니다.

유저 공간에서 본 지연은 `cyclictest`나 `rtla timerlat`으로 잽니다.

```console
# rtla timerlat top -d 30s
```
:::

## 정리 {#summary}

- 커널 선점은 두 조건이 모두 참일 때 일어납니다. `preempt_count`가 0이고(끊어도 된다), 재스케줄 요청이 있을 때(끊어야 한다)입니다.
- `preempt_count`는 선점 끔, softirq, hardirq 비활성, hardirq, NMI를 한 정수의 칸으로 나눠 셉니다. 실행 컨텍스트를 묻는 매크로는 모두 이 정수를 봅니다.
- `spin_lock()`은 락을 잡기 전에 선점부터 끕니다. 락 주인 선점과 같은 CPU 안의 교착을 막기 위해서입니다.
- 재스케줄 요청은 플래그일 뿐이고, 확인하는 자리는 유저 모드 복귀, 인터럽트 복귀, `preempt_enable()`, 자발적 양보 넷입니다.
- 선점 모델은 이 자리들 가운데 어느 것을 열어 둘지를 정합니다. `PREEMPT_DYNAMIC`은 스태틱 콜로 부팅 때 고르게 합니다.
- `PREEMPT_LAZY`는 요청을 급한 것과 느긋한 것으로 나눕니다. 일반 태스크의 요청은 유저 모드 복귀나 다음 틱까지 미룹니다. v7.0부터 주요 아키텍처의 기본값입니다.
- `PREEMPT_RT`는 `spinlock_t`를 잠들 수 있는 락으로 바꿔 락 구간까지 선점할 수 있게 합니다.

## 확인 문제 {#quiz}

::: {.q}
인터럽트 핸들러 안에서 `resched_curr()`가 불려 `TIF_NEED_RESCHED`가 섰습니다. 태스크 전환은 언제 일어납니까? 핸들러 안에서 바로 일어나지 않는 이유는 무엇입니까?

::: {.a}
핸들러가 끝나고 인터럽트에서 복귀하는 길에 일어납니다. 핸들러 안에서는 `preempt_count`의 hardirq 칸이 0이 아니므로 `preemptible()`이 거짓입니다. `resched_curr()`는 플래그만 세우고, 복귀 길의 `raw_irqentry_exit_cond_resched()`(커널로 복귀)나 `__exit_to_user_mode_loop()`(유저로 복귀)가 그 플래그를 확인합니다.
:::
:::

::: {.q}
`spin_lock()`으로 보호되는 구간 안에서 `kmalloc(size, GFP_KERNEL)`을 부르면 안 되는 이유를 `preempt_count`로 설명해 보세요.

::: {.a}
`GFP_KERNEL` 할당은 메모리가 부족하면 잠들 수 있습니다. 잠든다는 것은 `schedule()`을 부른다는 뜻입니다. 그런데 `spin_lock()`이 `preempt_count`를 올려 둔 상태이므로 지금은 다른 태스크로 넘어가면 안 되는 구간입니다. 락을 쥔 채 잠들면 그 락을 기다리는 다른 CPU가 한없이 돕니다. 디버그 옵션을 켠 커널은 이때 "scheduling while atomic" 경고를 냅니다. RT 커널에서는 `spinlock_t`가 잠들 수 있는 락이 되므로 사정이 달라지지만, `raw_spinlock_t` 구간에서는 여전히 안 됩니다.
:::
:::

::: {.q}
PREEMPT_LAZY 커널에서 일반 태스크 A가 커널 모드로 긴 작업을 하고 있습니다. (1) 일반 태스크 B가 깨어난 경우와 (2) `SCHED_FIFO` 태스크 R이 깨어난 경우, A는 각각 언제 CPU를 내줍니까?

::: {.a}
(1) fair 클래스가 `resched_curr_lazy()`를 불러 `TIF_NEED_RESCHED_LAZY`만 섭니다. A는 계속 실행하다가 유저 모드로 돌아가는 길에 내주거나, 그 전에 틱이 오면 `sched_tick()`이 요청을 `TIF_NEED_RESCHED`로 올려 그 틱 인터럽트의 복귀 길에 내줍니다. 최대 한 틱쯤 걸립니다. (2) RT 클래스는 `resched_curr()`를 불러 `TIF_NEED_RESCHED`를 바로 세웁니다. A가 `preempt_count` 0인 자리에 있으면 즉시, 선점을 꺼 둔 구간이면 그 구간이 끝나는 `preempt_enable()`에서 내줍니다.
:::
:::

::: {.q}
x86에서 `PREEMPT_NEED_RESCHED` 비트를 뒤집어서 `preempt_count`에 넣어 두는 이유는 무엇입니까?

::: {.a}
"카운터가 0이다"와 "재스케줄 요청이 있다"를 한 번에 판정하기 위해서입니다. 요청이 있을 때 비트가 0이 되도록 뒤집어 두면, 두 조건이 모두 참일 때 변수 전체가 0이 됩니다. `preempt_enable()`은 카운터를 내리는 `dec` 명령어의 제로 플래그만 보면 되므로, 가장 자주 도는 경로가 명령어 하나와 조건 분기 하나로 끝납니다.
:::
:::

## 용어 {#terms}

::: {.terms}
선점 (preemption)
:   실행 중인 태스크가 양보하지 않았는데 스케줄러가 CPU를 빼앗아 다른 태스크에 주는 일.

커널 선점 (kernel preemption)
:   태스크가 커널 모드에서 실행되는 도중에 일어나는 선점.

preempt_count
:   선점 끔, softirq, hardirq, NMI의 중첩 깊이를 한 정수에 나눠 담은 카운터. 0일 때만 선점할 수 있다.

TIF_NEED_RESCHED
:   현재 태스크를 바꿔야 한다는 요청을 나타내는 스레드 플래그.

TIF_NEED_RESCHED_LAZY
:   급하지 않은 재스케줄 요청. 유저 모드 복귀나 다음 틱에 처리한다.

선점 모델 (preemption model)
:   커널 코드를 어느 자리에서 끊을 수 있게 할지에 대한 빌드·부팅 설정.

락 주인 선점 (lock holder preemption)
:   락을 쥔 태스크가 선점당해, 그 락을 기다리는 쪽이 헛되이 기다리게 되는 현상.

스태틱 콜 (static call)
:   호출 명령어의 목적지를 실행 중에 고쳐 써서, 간접 호출 없이 호출 대상을 바꾸는 기법.

cond_resched()
:   재스케줄 요청이 있으면 양보하는 자발적 확인 지점.
:::
