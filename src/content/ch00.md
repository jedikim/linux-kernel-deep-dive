::: {.lead}
리눅스 커널은 C로 쓴 프로그램 하나입니다. 부팅할 때 메모리에 올라가 전원이 꺼질 때까지 그 자리에 있습니다. 그런데 보통의 프로그램과 달리 `main()`에서 시작해 차례로 흘러가지 않습니다. 대부분의 시간 동안 커널 코드는 실행되지 않고, 누군가 부를 때만 실행됩니다. 이 책은 그 프로그램의 v7.3 소스를 읽습니다. 이 장에서는 커널이 언제 실행되는지, 소스가 어떻게 놓여 있는지, 무엇으로 읽는지를 봅니다.
:::

::: {.goals}
- 커널 코드는 언제, 누구의 자격으로 실행되는가?
- 부팅한 커널은 어떤 순서로 자기 자신을 준비하는가?
- 9만 개가 넘는 소스 파일은 어떻게 나뉘어 있고 어디부터 읽어야 하는가?
- 버전 번호 7.3은 무엇을 뜻하는가?
- 커널의 C는 보통의 C 프로그램과 무엇이 다른가?
:::

## 커널은 불려야 실행된다 {#entry}

셸에서 `ls`를 실행하면 CPU는 `ls`의 코드를 실행합니다. 커널의 코드가 아닙니다. 커널 코드가 CPU에서 실행되는 것은 다음 세 경우뿐입니다.

::: {.fig src="three-doors.svg"}
커널로 들어오는 문은 셋입니다. 앞의 둘은 실행 중인 태스크가 일으키고, 셋째는 하드웨어가 일으킵니다.
:::

1. **시스템 콜**(system call). 태스크가 커널에 일을 요청합니다. `read()`, `fork()`, `mmap()` 같은 것입니다. [19장](ch19.html)에서 다룹니다.
2. **예외**(exception). CPU가 명령어를 실행하다 문제를 만납니다. 아직 물리 메모리가 붙지 않은 주소를 읽으면 페이지 폴트가 납니다. [17장](ch17.html)에서 다룹니다.
3. **인터럽트**(interrupt). 장치가 CPU에 신호를 보냅니다. 타이머가 만료되었거나, 네트워크 카드에 패킷이 도착했거나, 디스크가 읽기를 마쳤을 때입니다. [9장](ch09.html)과 [10장](ch10.html)에서 다룹니다.

세 경우 모두 CPU는 하던 일을 멈추고, 권한 수준을 올리고, 커널이 미리 등록해 둔 주소로 건너뜁니다. 커널은 일을 처리한 뒤 원래 자리로 돌아갑니다. [6장](ch06.html)의 그림 6-1이 이 돌아가는 길을 그린 것입니다.

여기서 중요한 성질 하나가 나옵니다. **커널에는 자기만의 실행 흐름이 따로 없습니다.** 시스템 콜을 처리하는 커널 코드는 그 시스템 콜을 부른 태스크의 자격으로, 그 태스크의 커널 스택 위에서 실행됩니다. 커널 소스 어디에나 나오는 `current`는 "지금 이 코드를 실행하게 만든 태스크"를 가리키는 포인터입니다([2장](ch02.html)). 인터럽트를 처리하는 코드는 우연히 그때 CPU를 쓰고 있던 태스크를 잠깐 밀어내고 실행됩니다. 인터럽트는 그 태스크와 아무 상관이 없습니다.

예외가 하나 있습니다. 커널이 스스로 만든 태스크인 **커널 스레드**입니다. `kworker`, `ksoftirqd`, `kswapd` 같은 것들로, 유저 공간이 없고 커널 코드만 실행합니다. `ps`에서 대괄호로 묶여 보이는 것들입니다.

::: {.myth}
"커널은 백그라운드에서 계속 도는 프로세스다." 아닙니다. 커널은 프로세스가 아니고, 스케줄되는 대상도 아닙니다. 커널은 프로세스들이 부르는 코드와 데이터의 모음입니다. 스케줄러조차 따로 도는 스레드가 아니라, 실행 중이던 태스크가 `schedule()` 함수를 부르는 것입니다([4장](ch04.html)).
:::

## 부팅: 커널이 자기를 준비하는 순서 {#boot}

커널이 부르기를 기다리는 상태가 되려면 먼저 준비가 필요합니다. 펌웨어와 부트로더가 커널 이미지를 메모리에 올리면, 어셈블리로 된 아키텍처별 진입 코드를 거쳐 C 함수 `start_kernel()`에 닿습니다. 이 함수는 길지만 구조는 단순합니다. 서브시스템의 초기화 함수를 **의존 순서대로** 하나씩 부릅니다.

```{.c file="init/main.c" line="987"}
void start_kernel(void)
{
	/* ... */
	local_irq_disable();
	/* ... */
	trap_init();
	mm_core_init();
	/* ... */
	/*
	 * Set up the scheduler prior starting any interrupts (such as the
	 * timer interrupt). Full topology setup happens at smp_init()
	 * time - but meanwhile we still have a functioning scheduler.
	 */
	sched_init();
	/* ... */
	early_irq_init();
	init_IRQ();
	tick_init();
	rcu_init_nohz();
	timers_init();
	srcu_init();
	hrtimers_init();
	softirq_init();
	vdso_setup_data_pages();
	timekeeping_init();
	time_init();
	/* ... */
	local_irq_enable();
	/* ... */
	fork_init();
	/* ... */
	vfs_caches_init();
	/* ... */
	cgroup_init();
	/* ... */
	rest_init();
/* ... */
}
```

::: {.fig src="start-kernel.svg"}
`start_kernel()`이 부르는 초기화 함수와 그것을 다루는 장. 이 함수의 호출 순서가 곧 서브시스템 사이의 의존 관계입니다.
:::

읽을 곳은 세 군데입니다.

- **순서에 이유가 있습니다.** 스케줄러(`sched_init`)는 인터럽트를 켜기 전에 준비됩니다. 소스의 주석대로, 타이머 인터럽트가 오면 스케줄러가 불리기 때문입니다. 메모리 할당자(`mm_core_init`)는 거의 모든 것보다 앞섭니다. 뒤에 오는 초기화 함수들이 메모리를 할당하기 때문입니다.
- **인터럽트는 한참 뒤에 켜집니다.** 함수 첫머리의 `local_irq_disable()`부터 `local_irq_enable()`까지, 커널은 인터럽트가 꺼진 채로 준비합니다. 인터럽트를 받을 자료구조(`early_irq_init`, `init_IRQ`)와 그 뒤처리(`softirq_init`), 시간(`timekeeping_init`)이 모두 갖춰진 다음에야 켭니다.
- **마지막 줄이 `rest_init()`입니다.** 여기서 처음으로 태스크를 만듭니다.

```{.c file="init/main.c" line="681"}
static noinline void __ref __noreturn rest_init(void)
{
	struct kernel_clone_args init_args = {
		.flags		= (CLONE_VM | CLONE_UNTRACED),
		.fn		= kernel_init,
		.fn_arg		= NULL,
	};
	/* ... */
	pid = kernel_clone(&init_args);
	/* ... */
	pid = kernel_thread(kthreadd, NULL, NULL, CLONE_FS | CLONE_FILES);
	/* ... */
	/*
	 * The boot idle thread must execute schedule()
	 * at least once to get things moving:
	 */
	schedule_preempt_disabled();
	/* Call into cpu_idle with preempt disabled */
	cpu_startup_entry(CPUHP_ONLINE);
}
```

`kernel_clone()`은 `fork()`가 부르는 바로 그 함수입니다([1장](ch01.html)). 첫 호출이 PID 1을 만듭니다. 이 태스크가 `kernel_init()`을 실행하다가 유저 공간의 `/sbin/init`(대개 systemd)을 실행하면서 첫 유저 프로세스가 됩니다. 둘째 호출이 PID 2인 `kthreadd`를 만듭니다. 이후의 모든 커널 스레드는 `kthreadd`의 자식입니다. 지금까지 `start_kernel()`을 실행해 온 흐름 자신은 PID 0, 곧 **idle 태스크**가 되어 할 일이 없을 때 CPU를 쉬게 합니다.

::: {.lab}
부팅의 흔적은 돌아가는 시스템에 남아 있습니다.

```console
$ ps -o pid,ppid,comm -p 1,2
    PID    PPID COMMAND
      1       0 systemd
      2       0 kthreadd

$ cat /proc/version
Linux version 7.3.2-arch1-1 (...) (gcc (GCC) ...) #1 SMP PREEMPT_DYNAMIC ...

$ sudo dmesg | head -3
[    0.000000] Linux version 7.3.2-arch1-1 ...
[    0.000000] Command line: BOOT_IMAGE=/vmlinuz-linux root=...
```

PID 1과 2의 부모가 모두 0입니다. `dmesg`의 첫 줄은 `start_kernel()`의 `pr_notice("%s", linux_banner)`가 찍은 것입니다.
:::

## 지도 {#map}

준비를 마친 커널은 아래와 같은 모습입니다. 상자를 누르면 그 장으로 갑니다.

::: {.fig src="kernel-map.svg" .plain}
유저 공간과 하드웨어 사이의 커널. 세로 방향은 요청이 내려가는 길이고, 가운데의 동시성은 모든 서브시스템에 걸쳐 있습니다.
:::

그림을 위에서 아래로 읽으면 요청 하나가 지나가는 길이 됩니다. 유저 프로그램이 `read()`를 부르면 시스템 콜 인터페이스를 지나 VFS로, 파일시스템과 페이지 캐시로, 블록 계층으로, 디스크 드라이버로 내려갑니다. 디스크가 읽기를 마치면 인터럽트가 아래에서 위로 올라와 잠들어 있던 태스크를 깨웁니다.

그림을 가로로 읽으면 커널이 관리하는 자원이 됩니다. CPU 시간(태스크와 스케줄러), 메모리, 저장장치, 네트워크입니다. 가운데를 가로지르는 동시성은 자원이 아니라 규칙입니다. 여러 CPU가 같은 자료구조를 동시에 만지는 커널에서, 어떤 코드도 이 규칙을 피할 수 없습니다.

## 소스 트리 {#tree}

v7.3의 소스는 파일 96,080개입니다. 최상위 디렉터리별로 세면 아래와 같습니다.

::: {.fig src="tree-files.svg"}
최상위 디렉터리별 파일 수(v7.3). 스케줄러, 메모리 관리, VFS 같은 핵심부는 전체의 작은 부분입니다.
:::

파일의 40%가 `drivers/`에 있습니다. 커널 소스의 대부분은 장치 드라이버와 아키텍처별 코드입니다. 이 책이 주로 읽는 곳은 그림에서 색이 다른 디렉터리들입니다.

| 디렉터리 | 내용 | 이 책에서 |
|---|---|---|
| `kernel/` | 태스크, 스케줄러(`sched/`), 락(`locking/`), 시간(`time/`), IRQ(`irq/`), RCU(`rcu/`), cgroup, BPF | 1–16장, 22장, 24장 |
| `mm/` | 메모리 관리 | 17–18장 |
| `fs/` | VFS와 파일시스템들 | 20장 |
| `block/`, `io_uring/` | 블록 계층, io_uring | 21장 |
| `net/` | 네트워크 스택 | 12장 |
| `arch/x86/` | x86의 진입 코드, 인터럽트, 페이지 테이블, KVM | 9장, 19장, 23장 |
| `include/linux/` | 커널 내부 헤더. 구조체 정의는 대부분 여기 있습니다. | 전체 |
| `include/uapi/` | 유저 공간에 공개하는 헤더. 한 번 내보내면 바꿀 수 없습니다. | 19장 |
| `init/` | `start_kernel()` | 이 장 |
| `lib/` | 커널이 스스로 갖춘 라이브러리(문자열, 자료구조) | 25장 |
| `rust/` | Rust 지원과 추상화 계층 | 27장 |
| `Documentation/` | 문서. [docs.kernel.org](https://docs.kernel.org/)에 그대로 실립니다. | 전체 |
| `scripts/`, `tools/` | 빌드·검사 스크립트, 유저 공간 도구와 테스트 | 26–28장 |

함수를 찾을 때는 이름으로 짐작하는 것이 가장 빠릅니다. 스케줄러 코드는 `kernel/sched/`에, 그 구조체는 `include/linux/sched.h`에 있습니다. 아키텍처에 따라 달라지는 부분은 `arch/<아키텍처>/` 아래에 같은 이름으로 있습니다. 예를 들어 페이지 폴트의 공통 처리는 `mm/memory.c`에, x86의 진입부는 `arch/x86/mm/fault.c`에 있습니다.

::: {.design}
아키텍처 20여 종과 드라이버 수만 개를 한 저장소에 두는 것은 의도된 선택입니다. 내부 인터페이스를 바꾸는 사람이 그 인터페이스를 쓰는 모든 코드를 같은 커밋에서 함께 고칠 수 있기 때문입니다. 그래서 커널은 내부 API를 고정하지 않고도 계속 고쳐 나갈 수 있습니다. 대신 저장소 밖에 있는 코드는 이 혜택을 받지 못합니다. 이 원칙과 그 결과는 [26장](ch26.html)에서 봅니다.
:::

## 버전 {#version}

소스 트리 맨 위의 `Makefile`은 버전으로 시작합니다.

```{.makefile file="Makefile" line="1"}
# SPDX-License-Identifier: GPL-2.0
VERSION = 7
PATCHLEVEL = 3
SUBLEVEL = 0
EXTRAVERSION =
NAME = Baby Opossum Posse
```

::: {.fig src="version-anatomy.svg"}
`uname -r`이 보여 주는 버전 문자열의 구성과, 메인라인에서 안정 버전이 갈라져 나오는 모습.
:::

- 메인라인은 9–10주마다 새 버전을 냅니다. v7.3은 2026년 10월 18일에 나왔습니다.
- 앞의 두 숫자가 릴리스를 가리킵니다. 숫자에 뜻은 없습니다. 7.0은 6.19 다음 버전일 뿐이고, 큰 변화가 있어서 7이 된 것이 아닙니다.
- 세 번째 숫자는 안정 버전입니다. 릴리스 뒤에 발견된 버그 수정만 모아 7.3.1, 7.3.2로 나옵니다.
- 그 뒤의 꼬리는 배포판이 붙입니다.

::: {.old}
"둘째 숫자가 짝수면 안정 버전, 홀수면 개발 버전"이라는 설명은 2.4와 2.5 시절까지의 규칙입니다. 2.6부터는 개발 전용 버전이 따로 없습니다. 새 기능은 릴리스 직후 2주 동안의 머지 윈도에 메인라인으로 바로 들어가고, 그 뒤 7주쯤 수정만 받다가 다음 버전이 됩니다. `2.6.x.y`처럼 숫자가 넷이던 표기도 3.0에서 사라졌습니다.
:::

이 책의 코드 인용은 모두 v7.3 태그의 것입니다. 코드 블록 머리의 파일 경로를 누르면 그 태그의 해당 줄이 열립니다. 인용 중간의 `/* ... */`는 줄였다는 표시입니다. 릴리스가 만들어지는 과정은 [26장](ch26.html)에서 다룹니다.

## 커널의 C는 무엇이 다른가 {#kernel-c}

커널 소스는 C로 쓰여 있지만, 유저 공간에서 쓰던 C와는 환경이 다릅니다.

| | 유저 공간 프로그램 | 커널 |
|---|---|---|
| 표준 라이브러리 | libc | 없음. `printk`, `kmalloc`, 문자열 함수를 `lib/`에 직접 갖춤 |
| 언어 표준 | 보통 표준 C | GNU C(`-std=gnu11`)와 컴파일러 확장 |
| 스택 | 수 MB, 자라남 | x86-64에서 16KB, 고정 |
| 잘못된 포인터 | 그 프로세스만 죽음(SIGSEGV) | 시스템 전체가 멈출 수 있음(oops, panic) |
| 메모리 할당 실패 | 드묾 | 언제든 실패할 수 있고 반드시 확인 |
| 부동소수점 | 자유롭게 사용 | 원칙적으로 쓰지 않음 |
| 동시성 | 스레드를 만들 때만 | 언제나. 모든 CPU가 같은 코드와 데이터를 실행 |
| 실행 중 끊김 | 신경 쓰지 않아도 됨 | 인터럽트와 선점을 직접 고려 |
| 잠들기 | 언제든 | 컨텍스트에 따라 금지 |

아래 두 줄이 가장 큰 차이입니다. 커널 함수 하나를 읽을 때는 "이 코드가 실행되는 동안 무엇이 끼어들 수 있는가", "여기서 잠들어도 되는가"를 늘 물어야 합니다. 그 답을 정하는 것이 실행 컨텍스트이고 [6장](ch06.html)과 [13장](ch13.html)의 주제입니다.

커널 소스에는 매크로도 많습니다. `SYSCALL_DEFINE3(read, ...)`, `list_for_each_entry(...)`, `DEFINE_PER_CPU(...)` 같은 것들은 처음에는 낯설지만 종류가 많지 않습니다. C로 객체지향과 제네릭을 흉내 내는 이 관용구들은 [25장](ch25.html)에서 모아서 봅니다.

v6.1부터는 Rust도 커널의 두 번째 언어입니다. v7.3 소스에는 `.c` 파일이 37,383개, `.rs` 파일이 496개 있습니다. [27장](ch27.html)에서 다룹니다.

## 읽는 순환 {#loop}

커널 소스를 읽는 일은 한 방향으로 흐르지 않습니다. 질문에서 시작해서, 코드를 찾고, 읽고, 돌아가는 시스템에서 확인하고, 왜 그렇게 되었는지 역사를 찾는 순환입니다.

::: {.fig src="reading-loop.svg"}
소스를 읽는 순환. 이 책의 각 장도 같은 순서로 쓰여 있습니다.
:::

**찾기.** 소스 트리가 있으면 `git grep`이 가장 빠릅니다. 없으면 [elixir.bootlin.com](https://elixir.bootlin.com/linux/v7.3/source)에서 식별자를 누르며 따라갑니다.

```console
$ git grep -n 'void sched_tick' kernel/
kernel/sched/core.c:5782:void sched_tick(void)

$ git grep -n 'struct task_struct {' include/
include/linux/sched.h:...:struct task_struct {
```

**확인하기.** 커널은 자기 상태를 파일로 내보입니다. `/proc`과 `/sys` 아래의 파일들은 디스크에 있지 않고, 읽는 순간 커널 함수가 내용을 만들어 냅니다([20장](ch20.html)). 실행 흐름을 보려면 추적 도구를 씁니다.

| 도구 | 볼 수 있는 것 |
|---|---|
| `/proc`, `/sys` | 태스크, 메모리, 인터럽트, 스케줄러의 현재 상태와 통계 |
| `ftrace` (`/sys/kernel/tracing`) | 어떤 커널 함수가 어떤 순서로 불렸는가 |
| `bpftrace` | 특정 지점에 조건과 집계를 붙여 관찰 ([24장](ch24.html)) |
| `perf` | CPU 시간이 어디에 쓰였는가, 이벤트 횟수 |

이 책의 '직접 확인하기' 상자는 이 도구들을 씁니다. 커널을 직접 빌드해 가상 머신에서 부팅하는 방법은 [28장](ch28.html)에 있습니다.

**역사 찾기.** 커널의 코드 한 줄에는 대개 그 줄을 넣은 커밋이 있고, 커밋 메시지에는 이유가 적혀 있고, 그 패치를 두고 벌어진 토론이 메일링 리스트 보관소([lore.kernel.org](https://lore.kernel.org/))에 남아 있습니다. `git blame`으로 커밋을 찾고, 커밋의 `Link:` 태그로 토론을 찾습니다. 큰 변화는 [LWN.net](https://lwn.net/Kernel/)이 기사로 정리합니다. "왜 이렇게 짰는가"의 답은 대부분 기록되어 있습니다.

::: {.lab}
시스템 전체에서 어떤 프로그램이 시스템 콜을 가장 많이 부르는지 5초 동안 셉니다. 첫째 문으로 들어오는 발걸음을 세는 것입니다.

```console
$ sudo bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); } interval:s:5 { exit(); }'
Attaching 2 probes...

@[sshd]: 214
@[systemd-journal]: 388
@[bpftrace]: 1543
@[Xorg]: 9120
...
```

셋째 문은 `/proc/interrupts`에서 봅니다. 숫자는 부팅 뒤 각 CPU가 받은 인터럽트 횟수입니다.

```console
$ head -4 /proc/interrupts
           CPU0       CPU1       CPU2       CPU3
  1:          0          0        918          0  IR-IO-APIC   1-edge      i8042
  8:          0          0          0          0  IR-IO-APIC   8-edge      rtc0
  9:          0       4107          0          0  IR-IO-APIC   9-fasteoi   acpi
```
:::

## 정리 {#summary}

- 커널 코드는 시스템 콜, 예외, 인터럽트로 불릴 때 실행됩니다. 커널은 프로세스가 아닙니다.
- 시스템 콜과 예외를 처리하는 커널 코드는 그것을 일으킨 태스크의 자격으로 실행됩니다. `current`가 그 태스크입니다.
- `start_kernel()`은 서브시스템을 의존 순서대로 초기화하고, 마지막에 PID 1과 PID 2를 만든 뒤 idle 태스크가 됩니다.
- 소스의 대부분은 드라이버와 아키텍처 코드입니다. 핵심부는 `kernel/`, `mm/`, `fs/`, `net/`, `block/`에 있습니다.
- 버전 번호에는 뜻이 없습니다. 메인라인은 9–10주마다 나오고, 세 번째 숫자는 버그 수정만 담은 안정 버전입니다.
- 커널의 C에는 libc가 없고, 스택이 작고, 모든 코드가 동시에 실행될 수 있으며, 컨텍스트에 따라 잠들 수 없습니다.

## 확인 문제 {#quiz}

::: {.q}
태스크 A가 `read()` 시스템 콜로 커널에 들어와 있는 동안 네트워크 카드의 인터럽트가 왔습니다. 인터럽트 핸들러가 실행되는 동안 `current`는 누구를 가리킵니까? 이 인터럽트는 A와 관계가 있습니까?

::: {.a}
`current`는 여전히 A를 가리킵니다. 인터럽트는 그 순간 CPU를 쓰고 있던 태스크를 밀어내고 실행되기 때문입니다. 하지만 인터럽트는 A와 관계가 없습니다. 패킷은 다른 태스크의 것일 수 있습니다. 그래서 인터럽트 핸들러는 `current`의 자원(주소 공간, 파일)을 쓰면 안 되고, `current`를 대신해 잠들어서도 안 됩니다.
:::
:::

::: {.q}
`start_kernel()`에서 `sched_init()`이 `local_irq_enable()`보다 앞에 있어야 하는 이유는 무엇입니까?

::: {.a}
인터럽트를 켜면 타이머 인터럽트가 올 수 있고, 타이머 인터럽트의 처리 경로는 스케줄러를 부릅니다. 런큐와 스케줄링 클래스가 준비되지 않은 상태에서 그 코드가 실행되면 초기화되지 않은 자료구조를 만지게 됩니다.
:::
:::

::: {.q}
커널의 스택이 16KB로 고정되어 있다는 사실은 커널 코드를 쓰는 방식에 어떤 제약을 줍니까?

::: {.a}
큰 배열이나 구조체를 지역 변수로 둘 수 없고, 깊은 재귀를 쓸 수 없습니다. 큰 버퍼는 `kmalloc()`으로 힙에서 할당합니다. 호출이 깊어질 수 있는 경로(파일시스템 위에 파일시스템이 쌓이는 경우 등)는 스택 사용량을 따로 관리합니다.
:::
:::

::: {.q}
어떤 배포판의 `uname -r`이 `6.12.48-1-lts`를 출력합니다. 이 커널에 v7.0에서 들어간 기능이 있을까요? 보안 수정은 어떻습니까?

::: {.a}
기능은 없습니다. 6.12는 메인라인 릴리스이고, 세 번째 숫자 48은 그 뒤에 나온 안정 버전의 횟수입니다. 안정 버전에는 새 기능이 들어가지 않습니다. 대신 이후 메인라인에서 고쳐진 버그와 보안 수정 가운데 6.12에도 해당하는 것이 옮겨져 있습니다.
:::
:::

## 용어 {#terms}

::: {.terms}
커널 (kernel)
:   하드웨어를 직접 다루는 권한을 가진 운영체제의 핵심 프로그램.

시스템 콜 (system call)
:   유저 프로그램이 커널에 일을 요청하는 진입점.

예외 (exception)
:   CPU가 명령어를 실행하다 스스로 일으키는 사건. 페이지 폴트가 대표적이다.

인터럽트 (interrupt)
:   장치가 CPU에 보내는 신호. 실행 중인 코드와 무관하게 도착한다.

커널 스레드 (kernel thread)
:   유저 공간 없이 커널 코드만 실행하는 태스크.

current
:   지금 이 CPU에서 실행 중인 태스크의 `task_struct`를 가리키는 포인터.

메인라인 (mainline)
:   리누스 토르발스가 관리하는 저장소. 새 기능이 들어가는 곳.

안정 버전 (stable release)
:   메인라인 릴리스에 버그 수정만 더한 버전. 세 번째 숫자로 구분한다.

idle 태스크 (idle task)
:   실행할 태스크가 없을 때 CPU를 쉬게 하는 PID 0 태스크.
:::
