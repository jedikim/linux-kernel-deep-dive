::: {.lead}
락을 잡으려는데 이미 누가 쥐고 있습니다. 할 수 있는 일은 둘뿐입니다. 풀릴 때까지 제자리에서 돌거나, CPU를 내주고 잠들거나. 스핀락은 앞의 길이고 뮤텍스는 뒤의 길입니다. 그런데 v7.3의 스핀락은 줄을 세우고, 뮤텍스는 잠들기 전에 한동안 돕니다. 두 락의 내부를 열어 보면 "돌 것인가 잠들 것인가"라는 물음에 커널이 얼마나 세밀하게 답하고 있는지 보입니다.
:::

::: {.goals}
- 스핀락과 뮤텍스는 무엇을 기준으로 고르는가?
- `spin_lock()` 한 줄은 어떤 층을 거쳐 어떤 원자 연산이 되는가?
- qspinlock은 4바이트에 무엇을 담고, 대기자는 왜 락이 아니라 자기 노드를 보며 도는가?
- 뮤텍스의 `owner` 워드에는 무엇이 들어 있고, 세 경로는 각각 언제 타는가?
- PREEMPT_RT에서는 어떤 락이 무엇으로 바뀌는가?
- `guard(mutex)`와 `__guarded_by()`는 어떤 실수를 막으려는 것인가?
:::

## 돌 것인가 잠들 것인가 {#spin-or-sleep}

**스핀락**(spinlock)은 락이 풀릴 때까지 반복문을 돌며 기다립니다. **뮤텍스**(mutex)는 기다리는 태스크를 대기 목록에 넣고 `schedule()`을 불러 CPU를 다른 태스크에 넘깁니다. 둘 다 한 번에 한 태스크만 임계 구역에 들이는 **상호 배제**(mutual exclusion) 락이고, 다른 점은 기다리는 방법입니다.

::: {.fig src="spin-vs-sleep.svg"}
같은 락을 두 가지 방법으로 기다릴 때 CPU 1이 쓰는 시간. 잠들었다 깨어나는 데는 컨텍스트 스위치가 두 번 듭니다.
:::

고르는 기준은 두 가지입니다.

**첫째, 잠들어도 되는 컨텍스트인가.** 인터럽트 핸들러와 softirq에는 돌아올 태스크가 없으므로 잠들 수 없습니다. 선점을 꺼 둔 구간도 마찬가지입니다. 이런 곳에서는 선택지가 스핀락뿐입니다. 실행 컨텍스트의 종류와 컨텍스트별로 쓸 수 있는 락은 [13장](ch13.html)에서 다뤘습니다.

**둘째, 락을 얼마나 오래 쥐는가.** 잠들고 깨어나려면 컨텍스트 스위치를 두 번 해야 하고, 그동안 캐시도 식습니다. 임계 구역이 리스트에 노드 하나를 끼우는 정도라면 그 비용이 임계 구역보다 큽니다. 반대로 임계 구역 안에서 디스크 I/O를 기다린다면 도는 쪽은 그 시간 내내 CPU 하나를 태웁니다.

| | 스핀락 | 뮤텍스 |
|---|---|---|
| 기다리는 방법 | 돈다 | 잠든다 (그 전에 잠깐 돌 수 있다) |
| 쓸 수 있는 곳 | 모든 컨텍스트 | 잠들 수 있는 태스크 컨텍스트 |
| 쥔 채로 잠들기 | 안 됨 | 됨 |
| 쥔 동안 선점 | 꺼짐 | 켜짐 |
| 경합이 없을 때 비용 | 원자 연산 한 번 | 원자 연산 한 번 |

마지막 줄이 중요합니다. 경합이 없으면 둘의 비용은 같습니다. 차이는 경합이 생겼을 때 나타나고, 이 장의 대부분은 그 느린 경로 이야기입니다.

## 스핀락의 층 {#layers}

`spin_lock(&lock)`은 한 줄이지만 네 층을 거칩니다. 층마다 맡은 일이 다릅니다.

::: {.fig src="spinlock-layers.svg"}
`spin_lock()`이 원자 연산이 되기까지. 맨 위 층에서 빌드 설정에 따라 길이 갈립니다.
:::

```{.c file="include/linux/spinlock.h" line="344"}
static __always_inline void spin_lock(spinlock_t *lock)
	__acquires(lock) __no_context_analysis
{
	raw_spin_lock(&lock->rlock);
}
```

일반 커널에서 `spinlock_t`는 `raw_spinlock_t` 하나를 감싼 구조체입니다. 굳이 두 타입으로 나눈 까닭은 PREEMPT_RT입니다. RT 커널에서 `spinlock_t`는 잠드는 락으로 바뀌고 `raw_spinlock_t`는 도는 락으로 남습니다. [6장](ch06.html)에서 본 대로입니다. 코드를 쓰는 사람은 타입 이름으로 "여기는 RT에서도 반드시 돌아야 한다"는 뜻을 밝힙니다.

두 번째 층이 선점을 끕니다. [6장](ch06.html)에서 `__raw_spin_lock()`을 읽었으니 여기서는 인터럽트까지 끄는 변형을 봅니다.

```{.c file="include/linux/spinlock_api_smp.h" line="148"}
static inline unsigned long __raw_spin_lock_irqsave(raw_spinlock_t *lock)
	__acquires(lock) __no_context_analysis
{
	unsigned long flags;

	local_irq_save(flags);
	preempt_disable();
	spin_acquire(&lock->dep_map, 0, 0, _RET_IP_);
	LOCK_CONTENDED(lock, do_raw_spin_trylock, do_raw_spin_lock);
	return flags;
}
```

순서를 읽습니다. 인터럽트를 끄고, 선점을 끄고, lockdep에 알리고, 그다음에야 락을 잡습니다. 락을 쥔 채 인터럽트가 들어와 그 핸들러가 같은 락을 잡으려 하면 같은 CPU 안에서 교착이 생기기 때문에, 인터럽트 핸들러와 함께 쓰는 락은 이렇게 인터럽트부터 막습니다. `LOCK_CONTENDED`는 `CONFIG_LOCK_STAT`이 꺼져 있으면 `do_raw_spin_lock(lock)` 한 줄로 펼쳐집니다.

변형은 "락을 쥔 동안 무엇이 끼어들지 못하게 할 것인가"로 나뉩니다.

| 함수 | 락 앞에서 하는 일 | 이 락을 함께 쓰는 상대 |
|---|---|---|
| `spin_lock()` | `preempt_disable()` | 태스크 컨텍스트끼리 |
| `spin_lock_bh()` | softirq 카운트를 올림 | softirq |
| `spin_lock_irq()` | `local_irq_disable()` | 인터럽트 핸들러. 인터럽트가 켜져 있었음이 확실할 때 |
| `spin_lock_irqsave()` | `local_irq_save(flags)` | 인터럽트 핸들러. 호출 시점의 상태를 모를 때 |
| `spin_lock_irq_disable()` | `local_interrupt_disable()` | 인터럽트 핸들러. 중첩을 세어 준다 |
| `spin_trylock()` | 위와 같고, 실패하면 되돌림 | 기다리지 않고 포기할 때 |

다섯째 줄은 v7.3에 있는 새 변형입니다. `_irq`는 풀 때 인터럽트를 무조건 켜므로, 이미 인터럽트가 꺼진 자리에서 부르면 바깥 구간의 보호가 깨집니다. `_irqsave`는 안전하지만 `flags` 변수를 호출자가 들고 다녀야 합니다. 새 변형은 그 상태를 CPU별 변수와 `preempt_count`의 한 칸에 맡깁니다.

```{.c file="include/linux/interrupt_rc.h" line="58"}
static inline void local_interrupt_disable(void)
{
	int new_count;
	unsigned long flags;

	WARN_ON_ONCE(in_nmi());

	local_irq_save(flags);
	new_count = hardirq_disable_enter();

	if ((new_count & HARDIRQ_DISABLE_MASK) == HARDIRQ_DISABLE_OFFSET)
		_local_interrupt_save_state(flags);
}
```

`hardirq_disable_enter()`는 `preempt_count`의 비트 16–23, [6장](ch06.html)의 "hardirq 비활성 카운트" 칸을 1 올립니다. 카운트가 0에서 1이 되는 맨 바깥 호출만 원래 인터럽트 상태를 저장하고, `local_interrupt_enable()`은 카운트가 0으로 돌아올 때만 그 상태를 복원합니다. 선점을 `preempt_disable()`로 겹쳐 끌 수 있듯이 인터럽트도 겹쳐 끌 수 있게 한 것입니다.

## qspinlock: 줄을 서는 스핀락 {#qspinlock}

맨 아래 층 `arch_spin_lock()`이 실제로 도는 곳입니다. x86과 arm64는 `ARCH_USE_QUEUED_SPINLOCKS`를 켜고, 이때 `arch_spin_lock()`은 `queued_spin_lock()`입니다. 이 구현을 **qspinlock**이라고 부릅니다.

### 왜 줄을 세우는가

가장 단순한 스핀락은 워드 하나를 0에서 1로 바꾸는 데 성공할 때까지 원자 연산을 되풀이합니다. 문제가 둘 있습니다. 누가 다음에 잡을지 정해져 있지 않아 굶는 CPU가 생깁니다. 그리고 기다리는 CPU 전부가 같은 워드를 읽고 쓰므로 그 워드가 든 캐시 라인이 CPU 사이를 끝없이 오갑니다. CPU가 많을수록 락을 쥔 쪽도 자기 임계 구역의 데이터를 캐시에서 빼앗겨 느려집니다. 캐시 라인이 CPU 사이를 오가는 비용은 [13장](ch13.html)에서 다뤘습니다.

::: {.fig src="ticket-vs-queue.svg"}
대기자가 셋일 때 락 워드의 캐시 라인을 읽는 CPU. 티켓 락은 공정하지만 여전히 모두가 한 워드를 봅니다.
:::

::: {.old}
많은 자료가 리눅스 스핀락을 **티켓 락**(ticket lock)으로 설명합니다. 락 워드를 `next`와 `owner` 두 칸으로 나누고, 잡으려는 CPU는 `next`를 1 올리며 번호표를 받아 `owner`가 자기 번호가 될 때까지 돕니다. 2.6.25(2008)에서 x86에 들어와 공정성 문제를 풀었습니다. 그러나 대기자 전원이 `owner`를 지켜보는 구조는 그대로였고, 4.2(2015)에서 x86의 기본 구현이 qspinlock으로 바뀌었습니다. v7.3에도 티켓 락은 `include/asm-generic/ticket_spinlock.h`에 남아 있습니다. qspinlock은 8비트·16비트 단위의 원자 연산이 잘 맞물려야 하므로, 그 조건을 갖추지 못한 아키텍처는 이 범용 티켓 락을 씁니다.
:::

qspinlock의 바탕은 **MCS 락**입니다. 대기자마다 자기 노드를 하나씩 갖고, 노드를 연결 리스트로 이어 줄을 섭니다. 각 대기자는 락 워드가 아니라 **자기 노드의 `locked` 필드**만 보며 돕니다. 앞사람이 락을 넘겨줄 때 뒷사람 노드의 `locked`에 1을 써 줍니다. 캐시 라인은 한 번에 한 CPU로만 옮겨 갑니다.

### 4바이트에 접어 넣기

원래의 MCS 락은 꼬리 노드를 가리키는 포인터(8바이트)가 필요합니다. 그런데 그때까지의 스핀락은 4바이트였고, 스핀락을 품은 수많은 구조체가 그 크기에 맞춰져 있었습니다. qspinlock은 포인터 대신 **CPU 번호**를 넣어 이 문제를 풉니다.

```{.c file="include/asm-generic/qspinlock_types.h" line="51"}
/*
 * Bitfields in the atomic value:
 *
 * When NR_CPUS < 16K
 *  0- 7: locked byte
 *  8-15: pending byte
 * 16-17: tail index
 * 18-31: tail cpu (+1)
 *
 * When NR_CPUS >= 16K
 *  0- 7: locked byte
 *     8: pending
 *  9-10: tail index
 * 11-31: tail cpu (+1)
 */
```

::: {.fig src="qspinlock-word.svg"}
qspinlock의 락 워드와, 주인 하나에 대기자 넷이 붙은 순간. 락 워드를 직접 지켜보는 CPU는 pending 하나와 대기열 머리 하나뿐입니다.
:::

노드는 동적으로 할당하지 않습니다. CPU마다 네 개씩 미리 둡니다(`qnodes[_Q_MAX_NODES]`). 네 개인 까닭은 스핀락을 기다리는 도중에 끼어들 수 있는 컨텍스트가 태스크, softirq, hardirq, NMI 넷뿐이기 때문입니다. 그래서 꼬리는 "CPU 번호 + 그 CPU의 몇 번째 노드(2비트)"로 적을 수 있습니다. 노드 하나는 16바이트이고 네 개가 64바이트 캐시 라인 하나에 꼭 맞습니다.

### 세 가지 길

```{.c file="include/asm-generic/qspinlock.h" line="108"}
static __always_inline void queued_spin_lock(struct qspinlock *lock)
{
	int val = 0;

	if (likely(atomic_try_cmpxchg_acquire(&lock->val, &val, _Q_LOCKED_VAL)))
		return;

	queued_spin_lock_slowpath(lock, val);
}
```

**① 경합 없음.** 워드 전체가 0이면 `cmpxchg` 한 번으로 `locked`를 1로 만들고 끝납니다. 풀 때는 `locked` 바이트에 0을 쓰는 것이 전부입니다.

**② 두 번째로 온 CPU.** 주인만 있고 대기자가 없으면, 큐 노드를 건드리지 않고 `pending` 비트만 세운 뒤 `locked`가 0이 되기를 기다립니다. 대기자가 하나뿐일 때 노드의 캐시 라인까지 끌어오는 비용을 아끼려는 지름길입니다.

**③ 세 번째부터.** `pending`도 차 있으면 줄을 섭니다.

```{.c file="kernel/locking/qspinlock.c" line="236"}
pv_queue:
	node = this_cpu_ptr(&qnodes[0].mcs);
	idx = node->count++;
	tail = encode_tail(smp_processor_id(), idx);
	/* ... */
	node = grab_mcs_node(node, idx);
	/* ... */
	node->locked = 0;
	node->next = NULL;
	/* ... */
	old = xchg_tail(lock, tail);
	next = NULL;

	/*
	 * if there was a previous node; link it and wait until reaching the
	 * head of the waitqueue.
	 */
	if (old & _Q_TAIL_MASK) {
		prev = decode_tail(old, qnodes);

		/* Link @node into the waitqueue. */
		WRITE_ONCE(prev->next, node);

		pv_wait_node(node, prev);
		arch_mcs_spin_lock_contended(&node->locked);
		/* ... */
	}
	/* ... */
	val = atomic_cond_read_acquire(&lock->val, !(VAL & _Q_LOCKED_PENDING_MASK));
```

읽을 곳은 세 군데입니다.

- `xchg_tail()`이 락 워드의 꼬리 칸을 자기 것으로 바꾸고 예전 꼬리를 돌려받습니다. 줄 서기는 이 원자적 교환 한 번입니다.
- 앞사람이 있으면 그 노드의 `next`에 자기를 잇고 `arch_mcs_spin_lock_contended(&node->locked)`에서 돕니다. 보는 메모리는 **자기 CPU의 노드**입니다.
- 줄의 맨 앞에 서면 그제야 락 워드를 보며 `locked`와 `pending`이 모두 0이 되기를 기다립니다. 락을 얻은 뒤에는 다음 노드의 `locked`에 1을 써서 머리 자리를 넘겨줍니다.

::: {.deep title="가상 머신에서의 스핀락"}
줄을 서는 락은 가상 머신에서 약점이 있습니다. 하이퍼바이저가 줄 중간의 vCPU를 물리 CPU에서 내려 버리면, 그 뒤의 vCPU는 락이 풀려도 차례가 오지 않습니다. [6장](ch06.html)의 락 주인 선점이 대기자에게 일어나는 셈입니다. 커널은 두 가지로 대응합니다. `CONFIG_PARAVIRT_SPINLOCKS`가 켜져 있으면 느린 경로를 `__pv_queued_spin_lock_slowpath()`로 바꿔, 한동안 돌아도 차례가 오지 않는 vCPU는 `pv_wait()` 하이퍼콜로 멈추고 락을 넘겨주는 쪽이 `pv_kick()`으로 깨웁니다. 이 기능을 쓸 수 없는 하이퍼바이저에서는 x86의 `virt_spin_lock()`이 줄 서기를 건너뛰고 단순한 test-and-set 락으로 돌아갑니다. 소스 주석이 이유를 적어 두었습니다. 공정한 락은 락 주인 선점 문제가 심각하다는 것입니다.
:::

## 읽는 쪽이 많을 때: rwlock과 seqlock {#rw-seq}

읽기만 하는 코드끼리는 서로 막을 이유가 없습니다. **rwlock**(`rwlock_t`)은 읽는 쪽 여럿 또는 쓰는 쪽 하나를 들입니다. v7.3의 구현은 qrwlock입니다. 32비트 `cnts`의 아래 9비트가 쓰는 쪽의 상태이고 그 위가 읽는 쪽의 수입니다. `read_lock()`은 `cnts`에 `_QR_BIAS`(1 << 9)를 더하고, 쓰는 쪽 비트가 서 있지 않으면 통과합니다.

rwlock의 한계는 읽는 쪽도 락 워드에 **쓴다**는 점입니다. 읽는 CPU가 많으면 `cnts`가 든 캐시 라인이 그 사이를 오갑니다. 임계 구역이 짧을수록 이 비용이 두드러져서, 읽기가 압도적으로 많은 데이터에는 rwlock 대신 [16장](ch16.html)의 RCU를 씁니다.

**seqlock**은 방향이 다릅니다. 읽는 쪽은 락을 잡지 않고 그냥 읽은 뒤, 읽는 사이에 쓰기가 끼어들었는지 확인해서 끼어들었으면 다시 읽습니다.

::: {.fig src="seqlock-retry.svg"}
쓰는 쪽은 앞뒤로 카운터를 1씩 올립니다. 읽는 쪽은 시작과 끝의 카운터가 같고 짝수일 때만 읽은 값을 믿습니다.
:::

```{.c file="kernel/time/timekeeping.c" line="992"}
ktime_t ktime_get(void)
{
	struct timekeeper *tk = &tk_core.timekeeper;
	unsigned int seq;
	ktime_t base;
	u64 nsecs;

	WARN_ON(timekeeping_suspended);

	do {
		seq = read_seqcount_begin(&tk_core.seq);
		base = tk->tkr_mono.base;
		nsecs = timekeeping_get_ns(&tk->tkr_mono);

	} while (read_seqcount_retry(&tk_core.seq, seq));

	return ktime_add_ns(base, nsecs);
}
```

현재 시각을 읽는 함수입니다. 커널 곳곳에서 매우 자주 불리지만 공유 메모리에 아무것도 쓰지 않습니다. 시각을 고치는 쪽은 틱 주기로 드물게 실행되므로 다시 읽는 일은 드뭅니다. 시간 관리의 나머지는 [8장](ch08.html)에 있습니다.

seqlock에는 조건이 있습니다. 읽는 쪽은 쓰는 도중의 어중간한 값을 볼 수 있으므로, 그 값으로 포인터를 따라가거나 하면 안 됩니다. 정수 몇 개처럼 "읽고 나서 버려도 되는" 데이터에만 맞습니다. 쓰는 쪽끼리는 따로 락으로 직렬화해야 하고, `seqlock_t`는 그 스핀락을 함께 묶은 타입입니다.

## 뮤텍스 {#mutex}


필드는 넷입니다. `owner`가 락의 상태 전부를 담고, `first_waiter`가 잠든 대기자들의 목록을 가리키고, `wait_lock`이 그 목록을 지키고, `osq`가 돌며 기다리는 대기자의 줄입니다. `context_lock_struct`와 `__guarded_by`는 [뒤의 절](#guard)에서 다룹니다.

### owner: 포인터와 플래그를 한 워드에

::: {.fig src="mutex-owner-bits.svg"}
`owner` 워드. `task_struct`는 캐시 라인 크기 이상으로 정렬되므로 포인터의 아래 세 비트는 언제나 0이고, 그 자리에 플래그를 둡니다.
:::

```{.c file="kernel/locking/mutex.h" line="24"}
/*
 * @owner: contains: 'struct task_struct *' to the current lock owner,
 * NULL means not owned. Since task_struct pointers are aligned at
 * at least L1_CACHE_BYTES, we have low bits to store extra state.
 *
 * Bit0 indicates a non-empty waiter list; unlock must issue a wakeup.
 * Bit1 indicates unlock needs to hand the lock to the top-waiter
 * Bit2 indicates handoff has been done and we're waiting for pickup.
 */
#define MUTEX_FLAG_WAITERS	0x01
#define MUTEX_FLAG_HANDOFF	0x02
#define MUTEX_FLAG_PICKUP	0x04

#define MUTEX_FLAGS		0x07
```

"누가 쥐고 있는가"와 "기다리는 태스크가 있는가"를 한 워드에 두면 둘을 **원자 연산 한 번에** 함께 읽고 고칠 수 있습니다. 따로 두었다면 주인을 확인한 뒤 대기자 유무를 확인하는 사이에 상태가 바뀌는 경우를 전부 따져야 합니다.

::: {.old}
옛 자료는 뮤텍스를 `count` 필드로 설명합니다. 1이면 풀림, 0이면 잠김, 음수면 대기자 있음이고, 주인은 디버그용 필드에 따로 적었습니다. v7.3에는 `count`가 없습니다. `owner` 워드 하나가 주인과 상태를 함께 담습니다. 대기 목록도 달라졌습니다. 예전의 `struct list_head wait_list` 대신 첫 대기자를 가리키는 포인터 `first_waiter` 하나만 둡니다.
:::

### 세 경로

::: {.fig src="mutex-paths.svg"}
`mutex_lock()`은 싼 방법부터 차례로 시도합니다.
:::

**① 빠른 경로.**

```{.c file="kernel/locking/mutex.c" line="153"}
static __always_inline bool __mutex_trylock_fast(struct mutex *lock)
	__cond_acquires(true, lock)
{
	unsigned long curr = (unsigned long)current;
	unsigned long zero = 0UL;

	MUTEX_WARN_ON(lock->magic != lock);

	if (atomic_long_try_cmpxchg_acquire(&lock->owner, &zero, curr))
		return true;

	return false;
}

/* ... */
void __sched mutex_lock(struct mutex *lock)
{
	might_sleep();

	if (!__mutex_trylock_fast(lock))
		__mutex_lock_slowpath(lock);
}
```

`owner`가 정확히 0일 때만 성공합니다. 플래그가 하나라도 서 있으면 실패하므로, 대기자가 있는 락을 새로 온 태스크가 이 길로 가로채지는 못합니다. 풀 때도 대칭입니다. `owner`가 플래그 없이 `current`와 같으면 `cmpxchg` 한 번으로 0을 만들고 끝납니다.

**② 낙관적 스핀.** 빠른 경로가 실패했다고 바로 잠들지 않습니다. 주인이 **지금 다른 CPU에서 실행 중**이라면 곧 락을 풀 가능성이 높습니다. 그 짧은 시간을 위해 컨텍스트 스위치 두 번을 치르는 것은 손해입니다.

```{.c file="kernel/locking/mutex.c" line="384"}
static noinline
bool mutex_spin_on_owner(struct mutex *lock, struct task_struct *owner,
			 struct ww_acquire_ctx *ww_ctx, struct mutex_waiter *waiter)
{
	bool ret = true;

	lockdep_assert_preemption_disabled();

	while (__mutex_owner(lock) == owner) {
		/* ... */
		barrier();

		/*
		 * Use vcpu_is_preempted to detect lock holder preemption issue.
		 */
		if (!owner_on_cpu(owner) || need_resched()) {
			ret = false;
			break;
		}
		/* ... */
		cpu_relax();
	}

	return ret;
}
```

도는 조건이 반복문에 그대로 적혀 있습니다. 주인이 바뀌지 않았고, 그 주인이 CPU 위에 있고(`owner->on_cpu`), 나에게 재스케줄 요청이 오지 않은 동안입니다. 주인이 잠들거나 선점당하면 기다려도 소용이 없으니 멈추고, 내가 양보해야 할 처지가 되어도 멈춥니다. 이 판단은 `owner` 워드에 주인의 포인터가 들어 있기에 가능합니다.

도는 태스크가 여럿이면 다시 스핀락의 캐시 라인 문제가 생깁니다. 그래서 스핀하려는 태스크는 먼저 `osq_lock()`으로 줄을 섭니다. **OSQ**(optimistic spin queue)는 뮤텍스용으로 다듬은 MCS 락이고, 줄의 맨 앞 하나만 `owner`를 보며 돕니다. qspinlock과 다른 점은 줄 중간에서도 빠져나올 수 있다는 것입니다. 재스케줄 요청을 받은 태스크는 줄을 떠나 느린 경로로 갑니다.

::: {.myth}
"뮤텍스를 못 잡으면 태스크는 잠든다." 절반만 맞습니다. `CONFIG_MUTEX_SPIN_ON_OWNER`가 켜진 SMP 커널에서 뮤텍스는 주인이 실행 중인 동안 스핀락처럼 돕니다. 커널 문서도 뮤텍스를 "사실상 혼합형"이라고 부릅니다. 임계 구역이 짧은 뮤텍스는 대부분 한 번도 잠들지 않고 주인이 바뀝니다.
:::

**③ 느린 경로.** 스핀으로도 얻지 못하면 `wait_lock`을 잡고 대기 목록 끝에 서서 잠듭니다.

```{.c file="kernel/locking/mutex.c" line="695"}
	for (;;) {
		bool first;

		/* ... */
		if (__mutex_trylock(lock))
			break;

		/* ... 시그널 확인 ... */
		raw_spin_unlock_irqrestore_wake(&lock->wait_lock, flags, &wake_q);

		schedule_preempt_disabled();

		first = lock->first_waiter == &waiter;

		raw_spin_lock_irqsave(&lock->wait_lock, flags);
		/* ... */
		set_current_state(state);
		/* ... */
		if (__mutex_trylock_or_handoff(lock, first))
			break;
		/* ... */
	}
```

잠들기 전에 한 번, 깨어난 뒤에 한 번 다시 시도합니다. 깨어났다고 락이 내 것은 아닙니다. unlock은 `owner`에서 주인을 지우고 첫 대기자를 깨울 뿐이어서, 대기자가 실제로 실행되기 전에 뒤늦게 온 다른 태스크가 스핀하다가 먼저 잡을 수 있습니다. 이미 CPU 위에 있는 태스크가 바로 일하는 편이 처리량에 좋으므로 이 가로채기는 일부러 허용합니다.

대신 굶주림을 막는 장치가 있습니다. 깨어난 첫 대기자가 또 실패하면 `__mutex_trylock_or_handoff()`가 `MUTEX_FLAG_HANDOFF`를 세웁니다. 이 플래그를 본 unlock은 `owner`를 0으로 만들지 않고, 첫 대기자의 포인터와 `MUTEX_FLAG_PICKUP`을 써 넣습니다. 그 순간부터 락은 그 대기자만 가져갈 수 있습니다. 평소에는 가로채기로 처리량을 얻고, 누군가 밀리기 시작하면 차례를 지키는 방식입니다.

::: {.design}
이 구현에는 다른 소프트웨어에도 통하는 원칙이 둘 있습니다.

**흔한 경우를 가장 싸게.** 대부분의 락은 대부분의 시간에 경합이 없습니다. 그래서 잡기와 풀기가 각각 `cmpxchg` 한 번이고, 대기 목록과 스핀락과 스케줄러는 그 한 번이 실패했을 때만 등장합니다. 느린 경로는 아예 다른 함수로 떼어 빠른 경로의 레지스터 압박과 코드 크기를 줄였습니다.

**정렬 덕에 남는 비트를 쓴다.** 포인터의 아래 비트가 언제나 0이라면 거기에 상태를 실을 수 있고, 그러면 포인터와 상태를 한 번의 원자 연산으로 함께 바꿀 수 있습니다. 락 없이 일관성을 얻는 가장 흔한 방법입니다. rwsem의 `owner`, 페이지 테이블 항목의 플래그 비트, 태그 붙은 포인터가 모두 같은 발상입니다.
:::

### 뮤텍스의 규칙

뮤텍스는 세마포어보다 규칙이 엄격하고, 그 덕에 위의 최적화가 가능합니다.

- 잡은 태스크만 풀 수 있습니다. `owner`가 뜻을 가지려면 그래야 합니다.
- 재귀적으로 잡을 수 없습니다.
- 인터럽트 컨텍스트에서 쓸 수 없습니다. 잠들 수 있기 때문입니다.
- 쥔 채로 태스크가 종료하면 안 됩니다.

`CONFIG_DEBUG_MUTEXES`를 켜면 이 규칙을 실행 중에 검사합니다.

::: {.warn}
`mutex_unlock()`은 `owner`를 풀어 준 뒤에도 뮤텍스 구조체를 더 만질 수 있습니다. 대기자를 깨우려고 `wait_lock`을 잡기 때문입니다. 그래서 "뮤텍스를 풀자마자 다른 태스크가 그 뮤텍스가 든 객체를 해제한다"는 코드는 해제된 메모리를 건드릴 수 있습니다. 객체의 수명은 뮤텍스가 아니라 참조 카운트로 지켜야 합니다. `spin_unlock()`에는 이 문제가 없습니다.
:::

## 그 밖의 잠드는 락 {#others}

| 락 | 무엇인가 | v7.3에서의 쓰임 |
|---|---|---|
| `struct semaphore` | 카운터와 대기 목록. `down()`이 카운터를 내리고 0이면 잠든다 | 주인이 없어 다른 태스크가 `up()`할 수 있다. 콘솔 락 `console_sem` 등 몇 군데에 남았다 |
| `struct rw_semaphore` | 읽는 쪽 여럿 또는 쓰는 쪽 하나. 잠든다 | `mmap_lock`([17장](ch17.html)), inode의 `i_rwsem` |
| `struct percpu_rw_semaphore` | 읽는 쪽이 CPU별 카운터만 건드리는 rwsem | CPU 핫플러그 락, 파일시스템 동결 |
| `struct completion` | "끝났다"는 사건 하나를 기다린다 | 스레드 시작·종료 기다리기, I/O 완료 |

**세마포어**는 뮤텍스가 생기기 전에 그 역할까지 맡았습니다. 지금 새 코드에서 상호 배제에는 뮤텍스를, "어떤 일이 끝나기를 기다린다"에는 completion을 씁니다. 세마포어는 주인이 없어서 낙관적 스핀도, [15장](ch15.html)의 우선순위 상속도 적용할 수 없습니다.

**rwsem**은 뮤텍스와 같은 기법을 씁니다. `count` 워드에 쓰는 쪽 비트, 대기자 비트, 핸드오프 비트, 읽는 쪽 수를 함께 담고, `owner`로 낙관적 스핀을 하고, OSQ로 줄을 세웁니다. **percpu-rwsem**은 읽는 쪽 비용을 더 줄입니다. 읽는 쪽은 자기 CPU의 카운터만 올리고, 쓰는 쪽이 모든 CPU의 카운터를 더해 0이 되기를 기다립니다. 쓰기가 아주 드문 락에 맞습니다.

## local_lock과 PREEMPT_RT의 치환 {#rt}

CPU별 데이터는 락 없이 `preempt_disable()`이나 `local_irq_disable()`만으로 보호해 왔습니다. 다른 CPU는 그 데이터를 건드리지 않으니 같은 CPU 안의 끼어들기만 막으면 되기 때문입니다. 이 방식의 문제는 **무엇을 보호하려고 선점을 껐는지 코드에 남지 않는다**는 것입니다. `local_lock`은 그 구간에 이름을 붙입니다.

```{.c file="mm/mlock.c" line="242"}
void mlock_folio(struct folio *folio)
{
	struct folio_batch *fbatch;

	local_lock(&mlock_fbatch.lock);
	fbatch = this_cpu_ptr(&mlock_fbatch.fbatch);
	/* ... */
	folio_get(folio);
	if (!folio_batch_add(fbatch, mlock_lru(folio)) ||
	    !folio_may_be_lru_cached(folio) || lru_cache_disabled())
		mlock_folio_batch(fbatch);
	local_unlock(&mlock_fbatch.lock);
}
```

일반 커널에서 `local_lock()`은 `preempt_disable()`입니다. `local_lock_t` 구조체는 lockdep을 켜지 않으면 크기가 0입니다. 달라지는 것은 읽는 사람과 도구가 얻는 정보입니다. 이 구간이 `mlock_fbatch`를 보호한다는 사실이 코드에 적히고, lockdep이 그 규칙을 검사할 수 있습니다.

PREEMPT_RT에서는 뜻이 바뀝니다. `local_lock()`이 `migrate_disable()`과 CPU별 `spinlock_t` 획득이 됩니다. 선점은 켜 둔 채, 같은 CPU에서 같은 구간에 들어오려는 다른 태스크만 막습니다. 이름을 붙여 둔 덕분에 가능한 치환입니다. 이름 없는 `preempt_disable()`은 무엇을 보호하는지 알 수 없어 RT에서도 선점을 끌 수밖에 없습니다.

::: {.fig src="rt-mapping.svg"}
`Documentation/locking/locktypes.rst`가 정리한 치환. PREEMPT_RT는 주인이 있는 락을 거의 전부 `rt_mutex` 위로 옮깁니다.
:::

오른쪽 열이 대부분 보라색인 이유는 [15장](ch15.html)에서 밝혀집니다. 실시간 커널은 락을 쥔 태스크에게 기다리는 태스크의 우선순위를 빌려줄 수 있어야 하고, 그러려면 락마다 주인이 누구인지 알아야 합니다. 세마포어가 그대로인 것은 주인이 없기 때문입니다.

RT에서 rwlock과 rwsem은 공정성이 달라집니다. 쓰는 쪽은 자기 우선순위를 읽는 쪽 여럿에게 한꺼번에 빌려줄 수 없으므로, 우선순위가 낮은 읽는 쪽이 선점당한 채 락을 쥐고 있으면 쓰는 쪽이 굶을 수 있습니다. `kernel/locking/rwbase_rt.c`의 머리 주석이 이 절충을 설명합니다.

## 범위로 잡는 락과 컴파일러의 검사 {#guard}

락에서 가장 흔한 버그는 내부 구현이 아니라 쓰는 쪽에 있습니다. 오류 경로에서 unlock을 빠뜨리는 것, 락 없이 보호 대상에 손대는 것입니다. v7.3에는 두 실수를 컴파일러가 막게 하는 장치가 있습니다.

### guard(): 범위를 벗어나면 풀린다

```{.c file="kernel/irq/irqdesc.c" line="891"}
int __ref __irq_alloc_descs(int irq, unsigned int from, unsigned int cnt, int node,
			    struct module *owner, const struct irq_affinity_desc *affinity)
{
	int start;

	if (!cnt)
		return -EINVAL;
	/* ... */
	guard(mutex)(&sparse_irq_lock);

	start = irq_find_free_area(from, cnt);
	if (irq >=0 && start != irq)
		return -EEXIST;

	if (start + cnt > total_nr_irqs) {
		if (!irq_expand_nr_irqs(start + cnt))
			return -ENOMEM;
	}
	return alloc_descs(start, cnt, node, affinity, owner);
}
```

`guard(mutex)(&sparse_irq_lock)` 뒤로 `return`이 세 번 나오지만 `mutex_unlock()`은 한 번도 없습니다. `guard()`는 지역 변수를 하나 선언하면서 락을 잡고, 그 변수에 컴파일러의 `cleanup` 속성을 붙입니다. 변수가 범위를 벗어나는 모든 경로에 컴파일러가 unlock 호출을 넣습니다. 예전 방식이라면 함수 끝에 `unlock:` 레이블을 두고 오류마다 `goto unlock`으로 뛰어야 했고, 새 오류 경로를 추가하면서 그 `goto`를 빠뜨리는 것이 흔한 버그였습니다.

락마다 어떤 함수가 짝인지는 헤더에 한 줄로 선언합니다.

```{.c file="include/linux/mutex.h" line="253"}
DEFINE_LOCK_GUARD_1(mutex, struct mutex, mutex_lock(_T->lock), mutex_unlock(_T->lock))
DEFINE_LOCK_GUARD_1_COND(mutex, _try, mutex_trylock(_T->lock))
DEFINE_LOCK_GUARD_1_COND(mutex, _intr, mutex_lock_interruptible(_T->lock), _RET == 0)
```

`spinlock`, `spinlock_irqsave`, `raw_spinlock`, `rwsem_read`, `rcu`, `preempt`에도 같은 선언이 있습니다. 함수 전체가 아니라 블록 하나만 감싸려면 `scoped_guard (spinlock_irqsave, &lock) { ... }`를 씁니다. 이 기반은 6.5(2023)에 들어왔고, v7.3의 `kernel/` 아래에는 `guard(mutex)`만 220곳이 넘습니다. `cleanup.h`의 나머지(`__free()`, `CLASS()`)는 [25장](ch25.html)에서 다룹니다.

### 락 문맥 분석

앞의 `struct mutex` 정의에 낯선 표시가 둘 있었습니다.

- `context_lock_struct(mutex)`: 이 구조체가 "잡고 푸는 대상"임을 컴파일러에 알립니다.
- `first_waiter __guarded_by(&wait_lock)`: 이 필드는 `wait_lock`을 쥔 상태에서만 읽고 쓸 수 있다는 선언입니다.

함수에도 붙습니다. `spin_lock()`의 `__acquires(lock)`은 "이 함수는 돌아올 때 `lock`을 쥐고 있다", `__must_hold(&lock->wait_lock)`은 "부르는 쪽이 이미 쥐고 있어야 한다"입니다. Clang은 이 표시를 따라 함수의 모든 경로에서 어떤 락이 쥐어져 있는지 계산하고, 락 없이 `first_waiter`를 만지는 코드나 락을 쥔 채 빠져나가는 경로를 **컴파일할 때** 경고합니다. 커널은 이 기능을 **문맥 분석**(context analysis)이라고 부릅니다. Clang의 Thread Safety Analysis를 커널 락 타입에 맞춘 것입니다.

7.0(2026)에 들어온 기능이고 아직 선택 사항입니다. `CONFIG_WARN_CONTEXT_ANALYSIS`를 켜고(v7.3 문서 기준 Clang 23 이상), 디렉터리의 `Makefile`에 `CONTEXT_ANALYSIS := y`를 적은 곳만 검사합니다. v7.3에서 `kernel/locking/mutex.c`, `kernel/sched/core.c`, `kernel/futex/`, `block/` 등이 켜 두었습니다. `__no_context_analysis`는 락 구현 내부처럼 분석이 따라갈 수 없는 함수에 붙이는 예외 표시입니다.

::: {.design}
락 규칙을 지키게 하는 방법은 세 단계로 발전했습니다. 처음에는 주석이었습니다("이 필드는 `foo_lock`으로 보호됨"). 다음은 실행 중 검사인 lockdep([27장](ch27.html))으로, 실제로 그 경로를 타야만 잡힙니다. 지금은 컴파일러가 타지 않은 경로까지 검사합니다. 규칙을 사람이 읽는 글에서 도구가 읽는 선언으로 옮길수록 리뷰어의 주의력에 덜 기대게 됩니다. 한편 도입 방식도 눈여겨볼 만합니다. 수천만 줄을 한꺼번에 바꾸지 않고, 옛 표기와 함께 쓸 수 있게 한 뒤 서브시스템이 하나씩 옮겨 가게 했습니다.
:::

## 경합을 재는 법 {#measure}

락이 느린지는 재 보아야 압니다. v7.3의 락 느린 경로에는 `lock:contention_begin`과 `lock:contention_end` 트레이스포인트가 심어져 있습니다. 앞에서 읽은 `queued_spin_lock_slowpath()`와 `__mutex_lock_common()`에도 `trace_contention_begin()` 호출이 있습니다. 디버그 빌드가 아니어도 쓸 수 있습니다.

::: {.lab}
시스템 전체에서 5초 동안 경합이 심한 락을 봅니다. `-b`는 BPF로 커널 안에서 집계하라는 옵션입니다.

```console
# perf lock contention -a -b sleep 5
 contended   total wait     max wait     avg wait         type   caller

       318      2.41 ms     61.20 us      7.58 us     spinlock   ...
        12      1.87 ms    410.33 us    155.83 us        mutex   ...
```

`type`이 락의 종류, `caller`가 기다린 자리입니다. 값은 예시입니다. 뮤텍스의 `avg wait`가 수 마이크로초라면 낙관적 스핀으로 끝났을 가능성이 높고, 수백 마이크로초를 넘으면 잠들었다 깨어난 것으로 볼 수 있습니다.

`bpftrace`로 기다린 시간의 분포를 직접 그릴 수도 있습니다.

```console
# bpftrace -e '
  tracepoint:lock:contention_begin { @t[tid] = nsecs; }
  tracepoint:lock:contention_end /@t[tid]/ {
      @wait_ns = hist(nsecs - @t[tid]); delete(@t[tid]);
  }'
```

락 클래스별 누적 통계는 `/proc/lock_stat`에 있습니다. `CONFIG_LOCK_STAT`으로 빌드한 커널에서만 나오고 lockdep을 함께 켜므로 느립니다. `/proc/lockdep_stats`는 lockdep이 추적하는 락 클래스와 의존 관계의 수를 보여 줍니다.
:::

경합이 확인되면 고치는 방향은 대개 정해져 있습니다. 임계 구역을 줄이거나, 락 하나를 여럿으로 쪼개거나, 읽는 쪽을 락 밖으로 빼거나(seqlock, RCU), 데이터를 CPU별로 나눕니다.

::: {.design}
리눅스의 락 역사는 굵은 락을 잘게 쪼갠 역사입니다. SMP를 처음 지원했을 때 커널에는 락이 하나였습니다. **BKL**(big kernel lock)을 쥔 CPU만 커널 코드를 실행했습니다. 구현은 쉬웠지만 CPU가 늘어도 커널 안에서는 한 번에 하나만 일했습니다. 그 뒤 십수 년에 걸쳐 서브시스템마다, 자료구조마다, 마지막에는 해시 버킷과 객체마다 락을 따로 두는 방향으로 바뀌었고, BKL은 2.6.39(2011)에서 완전히 사라졌습니다.

배울 점은 순서입니다. 굵은 락 하나로 **먼저 맞게** 만들고, 측정으로 병목이 드러난 곳부터 쪼갰습니다. 락을 쪼갤 때마다 락 순서 규칙이 늘고 교착 가능성이 생기므로, 측정 없이 미리 쪼갠 락은 비용만 치르기 쉽습니다.
:::

## 정리 {#summary}

- 스핀락은 돌며 기다리고 뮤텍스는 잠들어 기다립니다. 잠들 수 없는 컨텍스트이거나 임계 구역이 컨텍스트 스위치보다 짧으면 스핀락을 씁니다.
- `spin_lock()`은 `spinlock_t` → `raw_spinlock_t` → `arch_spinlock_t` 층을 내려갑니다. 변형(`_bh`, `_irq`, `_irqsave`, `_irq_disable`)은 락을 쥔 동안 무엇을 막을지를 정합니다.
- qspinlock은 4바이트에 `locked`, `pending`, 꼬리(CPU 번호와 노드 인덱스)를 담습니다. 세 번째 이후의 대기자는 CPU별 MCS 노드로 줄을 서고 자기 노드만 보며 돕니다.
- seqlock은 읽는 쪽이 아무것도 쓰지 않고, 쓰기가 끼어들었으면 다시 읽습니다.
- 뮤텍스의 `owner` 워드는 주인의 포인터와 플래그 셋을 함께 담습니다. 경합이 없으면 `cmpxchg` 한 번, 주인이 실행 중이면 낙관적 스핀, 그래도 안 되면 대기 목록에서 잠듭니다. 핸드오프가 굶주림을 막습니다.
- PREEMPT_RT는 `spinlock_t`, `rwlock_t`, `mutex`, `rw_semaphore`, `local_lock_t`를 `rt_mutex` 기반 구현으로 바꾸고 `raw_spinlock_t`만 도는 락으로 남깁니다.
- `guard()`는 unlock을 컴파일러에 맡기고, 문맥 분석 주석은 "이 필드는 이 락으로 보호된다"는 규칙을 컴파일러가 검사하게 합니다.

## 확인 문제 {#quiz}

::: {.q}
CPU가 64개인 기계에서 한 스핀락에 대기자가 40개 붙었습니다. 티켓 락과 qspinlock에서, 주인이 락을 풀 때 락 워드의 캐시 라인을 새로 가져와야 하는 CPU는 각각 몇 개쯤입니까?

::: {.a}
티켓 락에서는 대기자 40개 전부가 `owner` 칸을 읽으며 돌고 있으므로, unlock이 그 칸을 쓰는 순간 40개의 캐시 사본이 모두 무효가 되고 전부 다시 가져옵니다. 그중 하나만 자기 차례임을 확인하고 나머지 39개는 헛일을 합니다. qspinlock에서는 락 워드를 보며 도는 CPU가 `pending` 하나와 대기열 머리 하나, 많아야 둘입니다. 나머지 38개는 자기 CPU의 `qnodes` 노드만 읽고 있으므로 unlock의 영향을 받지 않습니다. 머리가 락을 얻은 뒤 다음 노드의 `locked`에 1을 쓸 때 그 노드의 캐시 라인 하나가 한 CPU로 옮겨 갈 뿐입니다.
:::
:::

::: {.q}
`mutex_spin_on_owner()`는 주인의 `on_cpu`가 0이 되면 스핀을 그만둡니다. 이 판단이 스핀락에는 필요 없고 뮤텍스에는 필요한 이유는 무엇입니까?

::: {.a}
스핀락은 쥔 동안 선점이 꺼져 있고 잠들 수도 없으므로, 주인은 언제나 어떤 CPU 위에서 실행 중입니다(가상 머신에서 vCPU가 내려가는 경우는 예외이고, 그래서 PV 스핀락이 있습니다). 뮤텍스는 쥔 채로 잠들거나 선점당할 수 있습니다. 주인이 CPU에서 내려가 있으면 언제 돌아와 락을 풀지 알 수 없으므로, 도는 것은 CPU 낭비입니다. 그래서 주인이 실행 중일 때만 "곧 풀릴 것"이라는 낙관이 성립하고, `owner` 워드에 든 `task_struct` 포인터로 그 상태를 확인합니다.
:::
:::

::: {.q}
뮤텍스의 빠른 경로는 `owner == 0`일 때만 성공합니다. 그런데 느린 경로에서 깨어난 대기자가 락을 "또 놓칠" 수 있는 까닭은 무엇이고, 이 일이 반복되지 않게 하는 장치는 무엇입니까?

::: {.a}
unlock의 느린 경로는 `owner`에서 주인 포인터를 지우고(플래그는 남깁니다) 첫 대기자를 깨웁니다. 깨어난 대기자가 실제로 CPU를 받아 `__mutex_trylock()`을 부르기까지는 시간이 걸립니다. 그 사이에 `mutex_lock()`을 부른 다른 태스크는 빠른 경로에서는 실패하지만(WAITERS 플래그 때문에 `owner`가 0이 아닙니다), 이어지는 `__mutex_trylock()`이나 낙관적 스핀에서 주인 칸이 비어 있는 것을 보고 락을 가져갑니다. 반복을 막는 장치가 핸드오프입니다. 깨어난 첫 대기자가 실패하면 `MUTEX_FLAG_HANDOFF`를 세우고, 다음 unlock은 주인 칸에 그 대기자의 포인터와 `MUTEX_FLAG_PICKUP`을 써 넣어 다른 태스크가 가로챌 수 없게 합니다.
:::
:::

::: {.q}
다음 코드는 일반 커널에서는 문제가 없지만 PREEMPT_RT 커널에서는 버그입니다. 이유를 설명하고 고쳐 보세요: `raw_spin_lock(&a); spin_lock(&b); ...`

::: {.a}
PREEMPT_RT에서 `spin_lock(&b)`는 `rt_mutex` 기반의 잠드는 락입니다. 경합이 있으면 `schedule()`을 부릅니다. 그런데 `raw_spin_lock(&a)`가 선점을 꺼 둔 상태이므로 잠들 수 없는 구간에서 잠들려 하는 것이 됩니다. 일반 커널에서는 둘 다 도는 락이라 드러나지 않습니다. 고치는 방법은 두 가지입니다. 바깥 락이 정말로 인터럽트·스케줄러 같은 저수준 코드용이 아니라면 `a`를 `spinlock_t`로 바꿉니다. 저수준 코드가 맞다면 안쪽 `b`도 `raw_spinlock_t`로 하고 임계 구역을 아주 짧게 유지합니다. lockdep의 `CONFIG_PROVE_RAW_LOCK_NESTING`이 이런 중첩을 일반 커널에서도 잡아 줍니다.
:::
:::

::: {.q}
`guard(mutex)(&m);`을 함수 맨 위가 아니라 `if` 블록 안에 쓰면 락은 언제 풀립니까? 이 성질이 문제가 되는 경우를 하나 들어 보세요.

::: {.a}
`guard()`가 선언하는 변수의 범위는 그 `if` 블록이므로, 블록의 닫는 중괄호에서(또는 그 안의 `return`, `break`, `goto`에서) 풀립니다. 함수 끝까지 쥐고 있을 것이라 생각하고 블록 뒤에서 보호 대상에 접근하면 락 없이 접근하게 됩니다. 반대로 한 함수 안에서 `guard()` 여러 개와 `__free()` 변수를 섞어 쓸 때는 선언의 역순으로 정리되므로, 선언 순서가 곧 unlock 순서입니다. 락을 풀기 전에 해제되어야 할 자원이 락보다 먼저 선언되어 있으면 순서가 뒤바뀝니다.
:::
:::

## 용어 {#terms}

::: {.terms}
스핀락 (spinlock)
:   락이 풀릴 때까지 반복문을 돌며 기다리는 락. 쥔 동안 선점이 꺼진다.

뮤텍스 (mutex)
:   기다리는 태스크를 재우는 상호 배제 락. 잡은 태스크만 풀 수 있다.

qspinlock
:   4바이트 락 워드와 CPU별 MCS 노드로 대기자를 줄 세우는 스핀락 구현.

MCS 락 (MCS lock)
:   대기자마다 자기 노드를 갖고, 그 노드만 보며 도는 큐 방식 스핀락.

티켓 락 (ticket lock)
:   번호표를 받아 자기 번호가 불릴 때까지 도는 공정한 스핀락. qspinlock 이전의 x86 구현.

낙관적 스핀 (optimistic spinning)
:   락 주인이 CPU에서 실행 중인 동안은 잠들지 않고 도는 뮤텍스·rwsem의 중간 경로.

OSQ (optimistic spin queue)
:   낙관적 스핀을 하려는 태스크를 한 줄로 세우는, 중간에 빠져나올 수 있는 MCS 락.

핸드오프 (handoff)
:   unlock이 락을 풀지 않고 첫 대기자에게 직접 넘기는 일. 대기자의 굶주림을 막는다.

seqlock
:   읽는 쪽이 락을 잡지 않고 읽은 뒤, 순번 카운터로 쓰기가 끼어들었는지 확인해 다시 읽는 락.

local_lock
:   CPU별 데이터를 보호하는 구간에 이름을 붙인 락. 일반 커널에서는 선점·인터럽트 끄기, RT에서는 CPU별 락.

guard()
:   범위를 벗어날 때 컴파일러가 unlock을 넣어 주는 범위 기반 락 매크로.

문맥 분석 (context analysis)
:   어떤 락을 쥔 상태에서만 접근할 수 있는지를 선언하고 컴파일러가 검사하게 하는 기능.
:::
