::: {.lead}
`counter++` 한 줄은 혼자 실행될 때는 틀릴 수가 없습니다. 커널에서는 혼자 실행된다는 보장이 없습니다. 다른 CPU가 같은 줄을 동시에 실행하고, 인터럽트가 그 줄의 한가운데에 끼어들고, 스케줄러가 태스크를 중간에 끊습니다. 그 결과로 생기는 버그는 백만 번에 한 번 나타나고 재현되지 않습니다. 이 장은 락의 종류를 나열하기 전에 먼저 묻습니다. 지금 이 코드는 어떤 상황에서 실행되고 있고, 누가 끼어들 수 있는가. 이 질문에 답할 수 있으면 어떤 보호가 필요한지는 따라 나옵니다.
:::

::: {.goals}
- 커널에서 같은 데이터에 동시에 접근하게 만드는 원인은 무엇 무엇인가?
- 태스크, softirq, hardirq, NMI 컨텍스트는 서로를 끊을 수 있는가?
- 원자적 컨텍스트란 무엇이고, 거기서 잠들면 커널은 어떻게 알아채는가?
- CPU별 데이터와 원자 연산은 락과 무엇이 다른가?
- 두 컨텍스트가 데이터를 나눠 쓸 때 `spin_lock()`, `_bh`, `_irqsave` 가운데 무엇을 써야 하는가?
- 락을 잡았는데도 값이 어긋날 수 있는 메모리 순서 문제와 거짓 공유란 무엇인가?
:::

## 동시성은 어디서 오는가 {#sources}

커널 코드가 만지는 데이터에 다른 실행 흐름이 끼어드는 길은 넷입니다.

- **여러 CPU.** 두 CPU가 같은 순간에 같은 함수를 실행합니다. 흉내가 아닌 진짜 병렬입니다.
- **선점.** CPU가 하나여도 스케줄러가 커널 코드 중간에서 태스크를 바꿉니다([6장](ch06.html)). 바뀐 태스크가 같은 데이터를 만지면 결과는 두 CPU가 동시에 만진 것과 같습니다.
- **hardirq.** 인터럽트는 어느 명령어 사이에든 끼어들어 핸들러를 실행합니다([10장](ch10.html)).
- **softirq.** 인터럽트에서 돌아가는 길이나 `local_bh_enable()`에서 실행됩니다([11장](ch11.html)). 태스크가 보기에는 인터럽트처럼 끼어듭니다.

여기에 **NMI**(마스크할 수 없는 인터럽트)가 있습니다. 인터럽트를 꺼 둔 구간까지 끊고 들어옵니다. 워치독과 성능 카운터 샘플링이 쓰고, 일반 드라이버 코드는 NMI 안에서 돌 일이 없습니다. 다만 NMI 핸들러를 쓰는 사람은 "무엇을 끊었는지 알 수 없다"는 조건에서 일해야 합니다.

리눅스가 처음 SMP를 지원한 2.0은 이 문제를 가장 단순하게 풀었습니다. 커널 전체에 락 하나를 두어 한 번에 한 CPU만 커널 코드를 실행하게 했습니다. 올바르지만 CPU를 늘려도 커널 안의 일은 빨라지지 않습니다. 그 뒤 30년은 그 큰 락을 자료구조마다의 작은 락으로 쪼개고, 락 없이 되는 곳에서는 락을 없애 온 역사입니다. 쪼갤수록 "이 데이터에 누가 끼어들 수 있는가"를 정확히 알아야 했습니다.

## 경쟁 조건의 해부 {#anatomy}

**경쟁 조건**(race condition)은 결과가 실행 순서에 따라 달라지는 상황입니다. 가장 작은 예가 카운터 증가입니다.

::: {.fig src="interleave.svg"}
`counter++`의 세 단계가 두 CPU에서 엇갈린 모습. 각 CPU는 자기 일을 올바르게 했지만 결과는 틀렸습니다.
:::

C의 한 문장은 CPU에게 하나의 동작이 아닙니다. 메모리에서 읽고, 레지스터에서 더하고, 메모리에 씁니다. x86 컴파일러가 이것을 `incl counter` 명령어 하나로 만들어도 사정은 같습니다. 명령어 하나 안에서 읽기와 쓰기가 따로 일어나고, 그 사이에 다른 CPU의 쓰기가 들어올 수 있습니다.

패턴은 셋으로 정리됩니다.

- **읽고 고쳐 쓰기.** 위의 카운터, 플래그 비트 켜기, 리스트의 `head` 갱신. 읽은 값이 쓰는 시점에는 낡아 있습니다.
- **여러 필드를 함께 고치기.** 리스트에 노드를 넣으려면 포인터 둘을 고쳐야 합니다. 하나만 고쳐진 순간에 다른 쪽이 리스트를 따라가면 깨진 구조를 봅니다.
- **확인하고 나서 쓰기.** `if (!list_empty(q))` 다음 줄에서 첫 노드를 꺼내는 코드는, 검사와 사용 사이에 다른 쪽이 그 노드를 가져가면 빈 리스트를 꺼냅니다.

셋 다 해법의 모양은 같습니다. 엇갈리면 안 되는 구간, 곧 **임계 구역**(critical section)을 정하고, 그 구간에는 한 번에 하나만 들어가게 합니다. 어려운 것은 구간을 정하는 일이 아니라 "누가 들어올 수 있는가"를 빠짐없이 아는 일입니다.

::: {.lab}
경쟁 조건은 유저 공간에서도 똑같이 일어납니다. 스레드 둘이 카운터 셋을 천만 번씩 올립니다.

```{.c name="race.c"}
#include <pthread.h>
#include <stdatomic.h>
#include <stdio.h>

#define N 10000000

static volatile long plain;
static atomic_long atom;
static long locked;
static pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;

static void *work(void *arg)
{
	for (long i = 0; i < N; i++)
		plain++;			/* 읽기, 더하기, 쓰기 */
	for (long i = 0; i < N; i++)
		atomic_fetch_add(&atom, 1);	/* 쪼개지지 않는 연산 하나 */
	for (long i = 0; i < N; i++) {
		pthread_mutex_lock(&m);
		locked++;
		pthread_mutex_unlock(&m);
	}
	return NULL;
}

int main(void)
{
	pthread_t a, b;

	pthread_create(&a, NULL, work, NULL);
	pthread_create(&b, NULL, work, NULL);
	pthread_join(a, NULL);
	pthread_join(b, NULL);
	printf("plain  %ld\natomic %ld\nmutex  %ld\n",
	       plain, atomic_load(&atom), locked);
	return 0;
}
```

```console
$ gcc -O2 -pthread race.c -o race && ./race
plain  10023673
atomic 20000000
mutex  20000000
```

`plain`은 실행할 때마다 다른 값이 나오고 2천만에 못 미칩니다. 위는 한 번의 실행 예이고, 증가의 절반 가까이가 사라졌습니다. `volatile`을 빼면 컴파일러가 반복문 전체를 덧셈 한 번으로 바꿔 경쟁이 가려집니다. 버그가 사라진 것이 아니라 드물어진 것이고, 걸리면 한 스레드 몫인 천만이 통째로 사라집니다. `time ./race`로 세 방식의 시간도 견주어 보세요. 올바른 두 방식이 훨씬 느립니다. 이 장의 뒷부분은 그 값을 줄이는 이야기입니다.
:::

## 실행 컨텍스트 {#contexts}

커널 코드는 넷 가운데 한 **실행 컨텍스트**(execution context)에서 돕니다. 컨텍스트가 할 수 있는 일을 정합니다.

| 컨텍스트 | 누구의 문맥인가 | 잠들기 | 유저 메모리 | 쓸 수 있는 락 | 확인 |
|---|---|---|---|---|---|
| 태스크 | `current`가 실제 주인. 시스템 콜, 커널 스레드 | 가능 | 가능 | 전부 | `in_task()` |
| softirq | 끊긴 태스크나 `ksoftirqd`를 빌림 | 불가 | 불가 | 스핀락 | `in_serving_softirq()` |
| hardirq | 끊긴 태스크를 빌림 | 불가 | 불가 | 스핀락 | `in_hardirq()` |
| NMI | 무엇이든 끊고 들어옴 | 불가 | 불가 | 기다리지 않는 것만 | `in_nmi()` |

아래 세 컨텍스트가 잠들 수 없는 이유는 같습니다. `schedule()`은 `current`를 재웠다가 나중에 이어서 실행하는 함수인데, 이 컨텍스트들에서 `current`는 우연히 끊긴 남의 태스크입니다. 재울 주체가 없습니다. 유저 메모리 접근도 페이지 폴트로 잠들 수 있어 같은 이유로 막힙니다.

::: {.fig src="context-matrix.svg"}
한 CPU 안에서 누가 누구를 끊는가. 아래 행일수록 끊기지 않고, 오른쪽 열일수록 막기 어렵습니다.
:::

이 표가 락 규칙의 뿌리입니다. 읽는 법은 이렇습니다. 태스크 컨텍스트 코드가 softirq와 데이터를 나눠 쓴다면, 태스크 행의 softirq 칸이 "끊는다"이므로 태스크 쪽에서 `local_bh_disable()`로 막아야 합니다. 반대로 softirq 쪽은 태스크 칸이 "못 끊는다"이므로 막을 것이 없습니다. softirq가 도는 동안 같은 CPU의 태스크는 실행되지 않습니다.

컨텍스트를 묻는 매크로는 [6장](ch06.html)에서 본 `preempt_count`의 칸을 읽습니다.

```{.c file="include/linux/preempt.h" line="146"}
/*
 * Macros to retrieve the current execution context:
 *
 * in_nmi()		- We're in NMI context
 * in_hardirq()		- We're in hard IRQ context
 * in_serving_softirq()	- We're in softirq context
 * in_task()		- We're in task context
 */
#define in_nmi()		(nmi_count())
#define in_hardirq()		(hardirq_count())
#define in_serving_softirq()	(softirq_count() & SOFTIRQ_OFFSET)
/* ... */
/*
 * The following macros are deprecated and should not be used in new code:
 * in_softirq()   - We have BH disabled, or are processing softirqs
 * in_interrupt() - We're in NMI,IRQ,SoftIRQ context or have BH disabled
 */
#define in_softirq()		(softirq_count())
#define in_interrupt()		(irq_count())
```

::: {.old}
옛 자료는 "인터럽트 컨텍스트인가"를 `in_interrupt()`로 묻고, 그 결과로 `GFP_ATOMIC`과 `GFP_KERNEL`을 고르는 코드를 예로 듭니다. v7.3의 헤더는 `in_interrupt()`와 `in_softirq()`를 새 코드에 쓰지 말라고 적어 두었습니다. 이 둘은 softirq를 실행 중일 때뿐 아니라 태스크가 `local_bh_disable()`을 한 구간에서도 참이 되어, "지금 인터럽트 안인가"라는 질문에 틀린 답을 줍니다. 정확한 질문에는 `in_hardirq()`, `in_serving_softirq()`, `in_task()`를 씁니다. 더 나은 방법은 묻지 않는 것입니다. 함수가 실행 중에 컨텍스트를 알아내 동작을 바꾸면, 스핀락을 쥔 호출자처럼 매크로로는 보이지 않는 제약을 놓칩니다. 잠들어도 되는지는 호출자가 인자로 알려 주는 것이 커널의 관례입니다.
:::

## 원자적 컨텍스트 {#atomic}

잠들 수 없는 상태를 통틀어 **원자적 컨텍스트**(atomic context)라고 부릅니다. softirq, hardirq, NMI 안이 그렇고, 태스크 컨텍스트라도 다음 구간은 원자적입니다.

- 스핀락을 쥔 구간. `spin_lock()`이 선점을 끕니다.
- `preempt_disable()`, `local_bh_disable()`로 막은 구간.
- 인터럽트를 끈 구간.

공통점은 `preempt_count`가 0이 아니거나 인터럽트가 꺼져 있다는 것입니다. 이런 구간에서 잠들면 락을 쥔 채 CPU를 떠나게 되고, 그 락을 기다리는 쪽은 끝없이 돕니다.

커널은 이 실수를 두 군데에서 잡습니다. 첫째는 잠들 수 있는 함수의 입구입니다. `mutex_lock()`, `kmalloc(GFP_KERNEL)`, `copy_from_user()` 같은 함수는 첫머리에 `might_sleep()`을 둡니다. 이번 호출에서 실제로 잠들지 않더라도, 잠들면 안 되는 자리에서 불렸으면 경고합니다.

```{.c file="kernel/sched/core.c" line="9241"}
	pr_err("BUG: sleeping function called from invalid context at %s:%d\n",
	       file, line);
	pr_err("in_atomic(): %d, irqs_disabled(): %d, non_block: %d, pid: %d, name: %s\n",
	       in_atomic(), irqs_disabled(), current->non_block_count,
	       current->pid, current->comm);
	pr_err("preempt_count: %x, expected: %x\n", preempt_count(),
	       offsets & MIGHT_RESCHED_PREEMPT_MASK);
```

둘째는 `schedule()` 자신입니다. 들어왔는데 `preempt_count`가 기대값이 아니면 "BUG: scheduling while atomic"을 찍습니다. 첫째 검사는 `CONFIG_DEBUG_ATOMIC_SLEEP`을 켠 커널에서만 동작합니다. 드물게만 잠드는 경로의 버그는 둘째 검사로는 몇 달에 한 번 걸리지만, 첫째 검사는 그 함수를 지나갈 때마다 걸립니다. 개발용 커널에 이 옵션을 켜 두는 이유입니다.

::: {.lab}
`dmesg`에서 이 경고를 만나면 세 줄을 읽습니다.

```console
BUG: sleeping function called from invalid context at kernel/locking/mutex.c:...
in_atomic(): 1, irqs_disabled(): 0, non_block: 0, pid: 1234, name: mydrv_worker
preempt_count: 1, expected: 0
```

첫 줄의 파일과 줄 번호는 잠들 수 있는 함수(여기서는 뮤텍스)의 위치입니다. 버그가 있는 곳은 그 함수를 부른 쪽이고, 아래에 이어지는 스택 추적에서 찾습니다. 둘째 줄이 원인을 가릅니다. `in_atomic(): 1`이고 `irqs_disabled(): 0`이면 스핀락이나 `preempt_disable()` 구간 안이고, `irqs_disabled(): 1`이면 인터럽트를 끈 구간입니다. 셋째 줄의 `preempt_count`를 6장의 비트 배치로 읽으면 더 좁혀집니다. `1`은 선점 칸 하나(스핀락 하나), `100`은 softirq를 실행하는 중, `200`은 `local_bh_disable()`입니다. lockdep을 켠 커널은 쥐고 있는 락의 목록도 함께 찍습니다.
:::

## 도구의 사다리 {#ladder}

보호 수단은 여럿이고 값이 다릅니다. 싼 것부터 봅니다.

::: {.fig src="ladder.svg"}
아래로 갈수록 막는 범위가 넓고 값도 큽니다. 스핀락의 softirq와 hardirq 칸은 `spin_lock_bh()`, `spin_lock_irqsave()`로 채웁니다.

### CPU별 데이터

가장 싼 방법은 공유하지 않는 것입니다. **CPU별 데이터**(per-CPU data)는 변수를 CPU 수만큼 만들어 각 CPU가 자기 것만 고치게 합니다. 다른 CPU와 겨룰 일이 없으니 락도 없습니다. [11장](ch11.html)의 softirq pending 비트맵이 그렇습니다.

```{.c file="include/linux/interrupt.h" line="528"}
#define local_softirq_pending()	(__this_cpu_read(local_softirq_pending_ref))
#define set_softirq_pending(x)	(__this_cpu_write(local_softirq_pending_ref, (x)))
#define or_softirq_pending(x)	(__this_cpu_or(local_softirq_pending_ref, (x)))
```

남는 문제는 같은 CPU 안의 끼어들기입니다. 읽고 고쳐 쓰는 도중에 선점당해 다른 CPU로 옮겨지면 남의 변수에 쓰게 됩니다. `this_cpu_inc()` 같은 `this_cpu_*` 연산은 이것을 명령어 하나로 풉니다. x86에서는 세그먼트 레지스터를 기준으로 "이 CPU의 변수"를 가리키는 `inc` 명령어 하나가 됩니다. 인터럽트도 선점도 명령어 중간에는 끼어들지 못하므로, 주소 계산과 증가 사이에 틈이 없습니다. 값을 치르는 곳은 읽을 때입니다. 전체 합을 알려면 모든 CPU의 값을 더해야 하고, 그 합은 더하는 사이에도 바뀌는 근삿값입니다. 통계 카운터에는 충분하고, 정확한 값이 필요한 참조 카운트에는 맞지 않습니다.

### 원자 연산

변수 하나를 여러 CPU가 정확히 나눠 써야 하면 **원자 연산**(atomic operation)을 씁니다. `atomic_t`에 대한 x86의 증가입니다.

```{.c file="arch/x86/include/asm/atomic.h" line="51"}
static __always_inline void arch_atomic_inc(atomic_t *v)
{
	asm_inline volatile(LOCK_PREFIX "incl %0"
		     : "+m" (v->counter) :: "memory");
}
```

`LOCK_PREFIX`가 전부입니다. 이 접두사가 붙은 명령어는 읽기와 쓰기 사이에 다른 CPU가 그 메모리를 건드리지 못하게 합니다. 앞의 `race.c`에서 `atomic_fetch_add()`가 한 일입니다. 종류는 넷쯤 됩니다.

- `atomic_t`, `atomic_long_t`: 더하기, 빼기, 교환.
- `set_bit()`, `test_and_set_bit()`: 비트 하나. 태스크릿의 `TASKLET_STATE_RUN`이 이것으로 락 노릇을 했습니다.
- `cmpxchg()`, `try_cmpxchg()`: "값이 내가 읽은 그대로면 새 값으로 바꾼다." 실패하면 다시 읽고 재시도합니다.
- `refcount_t`: 참조 카운트 전용입니다. 넘치면 0으로 돌아가는 대신 포화값에 붙어 움직이지 않습니다. 카운트 넘침을 해제 후 사용 버그로 바꾸는 공격을 막습니다.

`cmpxchg` 반복문의 실제 모습입니다. [12장](ch12.html)에서 NAPI의 소유권을 잡던 함수입니다.

```{.c file="net/core/dev.c" line="6824"}
bool napi_schedule_prep(struct napi_struct *n)
{
	unsigned long new, val = READ_ONCE(n->state);

	do {
		if (unlikely(val & NAPIF_STATE_DISABLE))
			return false;
		new = val | NAPIF_STATE_SCHED;
		/* ... */
	} while (!try_cmpxchg(&n->state, &val, new));

	return !(val & NAPIF_STATE_SCHED);
}
```

읽은 값 `val`로 새 값 `new`를 계산하고, 그 사이에 `n->state`가 바뀌지 않았을 때만 써넣습니다. 바뀌었으면 `try_cmpxchg()`가 `val`을 현재 값으로 고쳐 주고 반복문이 다시 돕니다. 락 없이 "읽고 고쳐 쓰기"를 안전하게 만드는 기본형입니다. 돌려주는 값이 "내가 비트를 세웠는가"이므로, 참을 받은 쪽 하나만 다음 단계로 갑니다.

원자 연산은 변수 하나만 지킵니다. 두 변수를 함께 고쳐야 하거나, 확인과 사용 사이를 묶어야 하면 락이 필요합니다. 그리고 싸지 않습니다. 여러 CPU가 같은 변수를 두드리면 그 변수가 든 캐시 라인이 CPU 사이를 오갑니다([캐시 라인 절](#cacheline)).

### 이 CPU에서 끼어드는 것 막기

그림의 가운데 세 줄은 락이 아닙니다. 그림 13-2의 "막는 방법" 줄 그대로, 같은 CPU에서 끼어드는 것을 한 단계씩 막습니다. 다른 CPU는 막지 못하므로 CPU별 데이터를 지킬 때만 단독으로 쓰입니다. 여러 CPU가 나눠 쓰는 데이터라면 이것들을 스핀락과 겹칩니다. 스핀락의 변형이 그 조합입니다.

```{.c file="include/linux/spinlock_api_smp.h" line="148"}
static inline unsigned long __raw_spin_lock_irqsave(raw_spinlock_t *lock)
	__acquires(lock) __no_context_analysis
{
	unsigned long flags;

	local_irq_save(flags);
	preempt_disable();
	spin_acquire(&lock->dep_map, 0, 0, _RET_IP_);
	LOCK_CONTENDED(lock, do_raw_spin_trylock, do_raw_spin_lock);
	return flags;
}
/* ... */
static inline void __raw_spin_lock_bh(raw_spinlock_t *lock)
	__acquires(lock) __no_context_analysis
{
	__local_bh_disable_ip(_RET_IP_, SOFTIRQ_LOCK_OFFSET);
	spin_acquire(&lock->dep_map, 0, 0, _RET_IP_);
	LOCK_CONTENDED(lock, do_raw_spin_trylock, do_raw_spin_lock);
}
```

순서를 봅니다. 끼어들 수 있는 것을 **먼저** 막고 그다음에 락을 잡습니다. 락을 잡은 뒤에 인터럽트를 끄면 그 사이에 인터럽트가 들어와 같은 락을 잡으려 할 수 있습니다.

`local_irq_save(flags)`는 인터럽트가 이미 꺼져 있었는지를 `flags`에 담아 두었다가 복원합니다. 호출자가 변수를 들고 다녀야 하고, 짝이 어긋나면 인터럽트가 엉뚱한 때 켜집니다. v7.3에는 횟수를 세는 방식이 추가되어 있습니다.

```{.c file="include/linux/interrupt_rc.h" line="58"}
static inline void local_interrupt_disable(void)
{
	int new_count;
	unsigned long flags;

	WARN_ON_ONCE(in_nmi());

	local_irq_save(flags);
	new_count = hardirq_disable_enter();

	if ((new_count & HARDIRQ_DISABLE_MASK) == HARDIRQ_DISABLE_OFFSET)
		_local_interrupt_save_state(flags);
}
```

`preempt_disable()`이 중첩 횟수를 세듯, `preempt_count`의 hardirq 비활성 칸으로 인터럽트를 끈 횟수를 셉니다. 맨 바깥에서 끌 때만 원래 상태를 CPU별 변수에 저장하고, 횟수가 0으로 돌아올 때 복원합니다. 이 위에 `spin_lock_irq_disable()`이 있습니다. `flags`를 들고 다닐 필요가 없어, 스코프가 끝날 때 자동으로 풀리는 가드나 Rust의 락 타입과 맞물리기 쉽습니다.

### 락

사다리의 아래쪽이 락입니다. 스핀락은 기다리는 동안 CPU를 쥐고 돌고, 뮤텍스는 잠듭니다. 스핀락은 어느 컨텍스트에서나 쓸 수 있지만 쥔 채 잠들 수 없고, 뮤텍스는 쥔 채 잠들 수 있지만 태스크 컨텍스트에서만 씁니다. 내부는 [14장](ch14.html)에서 봅니다. 읽기가 압도적으로 많은 데이터에는 읽는 쪽이 아무것도 기다리지 않는 RCU([16장](ch16.html))와 seqlock이 있습니다.

::: {.design}
동시성 설계의 첫 질문은 "어떤 락을 걸까"가 아니라 "공유를 없앨 수 있는가"입니다. 커널의 뜨거운 경로가 CPU별로 쪼개져 있는 것은 우연이 아닙니다. 런큐, softirq pending, 네트워크의 `softnet_data`, 슬랩의 CPU별 캐시, 통계 카운터가 모두 그렇습니다. 락은 올바름을 주지만 확장성을 주지 않습니다. CPU가 64개여도 락 하나를 지나는 일은 한 번에 하나씩입니다. 공유하지 않는 데이터는 CPU 수만큼 빨라집니다. 유저 공간에서도 같습니다. 스레드별 할당 캐시, 샤드로 나눈 해시 테이블, 코어당 이벤트 루프 하나라는 구조가 모두 이 발상입니다.
:::

## 어떤 락을 고를까 {#which-lock}

데이터를 만지는 컨텍스트가 정해지면 필요한 최소한의 보호도 정해집니다.

::: {.fig src="lock-table.svg"}
행과 열은 같은 데이터를 만지는 두 쪽입니다. 커널 문서 `Documentation/kernel-hacking/locking.rst`의 표를 세 컨텍스트로 줄인 것입니다.
:::

규칙은 셋으로 줄일 수 있습니다.

1. **끊길 수 있는 쪽이 막습니다.** 태스크와 softirq가 나눠 쓰면 태스크 쪽이 `spin_lock_bh()`를 씁니다. softirq 쪽은 태스크에게 끊기지 않으므로 `spin_lock()`이면 됩니다. [12장](ch12.html)의 소켓 락에서 태스크는 `spin_lock_bh()`를, `tcp_v4_rcv()`는 `bh_lock_sock()`(평범한 `spin_lock()`)을 쓰던 것이 이 규칙입니다.
2. **잠들어야 하면 뮤텍스이고, 그러면 그 데이터는 태스크 컨텍스트에서만 만질 수 있습니다.** 인터럽트 핸들러가 그 데이터를 고쳐야 한다면 고치는 일을 워크큐로 넘깁니다([11장](ch11.html)). 락의 선택이 코드를 어느 컨텍스트에서 돌릴지를 정하는 셈입니다.
3. **확신이 없으면 `spin_lock_irqsave()`입니다.** 어느 컨텍스트에서 불려도 안전합니다. 대신 인터럽트가 꺼지는 시간이 생기므로, 꼭 필요한 곳에만 씁니다.

같은 softirq끼리도 락이 필요하다는 점을 빠뜨리기 쉽습니다. softirq는 같은 CPU에서는 중첩되지 않지만 다른 CPU에서 동시에 돕니다. 표의 가운데 칸이 "락 없음"이 아니라 `spin_lock()`인 이유입니다.

::: {.myth}
"CPU가 하나면 락이 필요 없다." 다른 CPU는 없어도 선점과 인터럽트는 있습니다. 단일 CPU용으로 빌드한 커널에서 `spin_lock()`은 실제 락 없이 `preempt_disable()`만 남고, `spin_lock_irqsave()`는 인터럽트 끄기만 남습니다. 보호가 사라지는 것이 아니라 "다른 CPU" 몫만 빠집니다. 락을 올바르게 건 코드는 CPU가 몇 개든 그대로 올바릅니다.
:::

::: {.note}
`PREEMPT_RT` 커널에서는 `spinlock_t`가 잠드는 락이 되고 인터럽트 핸들러가 스레드에서 돌기 때문에, 이 표의 일부가 달라집니다. `spin_lock_irqsave()`가 실제로는 인터럽트를 끄지 않습니다. 코드를 고칠 필요는 없지만, "스핀락을 쥐었으니 선점되지 않는다"는 가정에 기댄 코드는 깨집니다. [14장](ch14.html)에서 다룹니다.
:::

## 교착 {#deadlock}

락은 경쟁 조건을 없애는 대신 새 버그를 들여옵니다. **교착**(deadlock)입니다. 커널에서 흔한 모양은 둘입니다.

::: {.fig src="irq-deadlock.svg"}
한 CPU 안의 교착. 락을 쥔 코드를 끊고 들어온 핸들러가 같은 락을 기다립니다.
:::

첫째는 자기 자신과의 교착입니다. 태스크가 `spin_lock()`으로 락을 쥔 상태에서 인터럽트가 오고, 핸들러가 같은 락을 잡으려 합니다. 핸들러는 락이 풀리기를 기다리며 돌고, 락을 풀 태스크는 핸들러가 끝나야 실행됩니다. 다른 CPU가 도울 방법도 없습니다. 앞 절의 규칙 1이 막으려는 것이 이 상황입니다. 스핀락은 재귀적이지 않으므로, 락을 쥔 함수가 같은 락을 잡는 함수를 부르는 것도 같은 교착입니다.

::: {.fig src="abba.svg"}
두 락을 서로 다른 순서로 잡는 두 경로. 기다림이 고리를 이루면 아무도 나아가지 못합니다.
:::

둘째는 **락 순서**(lock ordering)의 역전입니다. 해법은 규율입니다. 함께 잡는 락에는 순서를 정하고 모든 경로가 지킵니다. 순서는 보통 자료구조의 포함 관계를 따르고, 같은 종류의 락 둘을 잡아야 하면 주소가 작은 쪽을 먼저 잡는 식으로 정합니다.

사람이 수만 개의 락 순서를 기억할 수는 없습니다. **lockdep**이 대신합니다. 락을 잡을 때마다 "A를 쥔 채 B를 잡았다"는 관계를 기록하고, 언젠가 반대 순서가 한 번이라도 나타나면 실제로 교착이 일어나지 않았어도 경고합니다. 인터럽트 핸들러에서 잡힌 적이 있는 락을 인터럽트를 켠 채 잡는 것도 같은 방식으로 잡습니다. 자세한 것은 [27장](ch27.html)입니다.

::: {.design}
락은 코드를 보호하지 않습니다. 데이터를 보호합니다. "이 함수는 락을 잡는다"가 아니라 "이 필드는 이 락을 쥐고 만진다"로 적어야 합니다. 커널의 큰 구조체는 필드마다 이 규칙을 주석으로 답니다. 워크큐가 좋은 예입니다.

```{.c file="kernel/workqueue.c" line="151"}
 * Structure fields follow one of the following exclusion rules.
 *
 * I: Modifiable by initialization/destruction paths and read-only for
 *    everyone else.
 *
 * P: Preemption protected.  Disabling preemption is enough and should
 *    only be modified and accessed from the local cpu.
 *
 * L: pool->lock protected.  Access with pool->lock held.
```

그리고 구조체 정의에서 필드마다 `/* L: list of pending works */`처럼 글자를 붙입니다. 주석은 낡을 수 있으므로 코드로도 적습니다. `lockdep_assert_held(&pool->lock)` 한 줄은 "이 함수는 이 락을 쥔 채 불려야 한다"는 계약을 실행할 때 검사합니다. 불변식을 사람이 읽는 형태와 기계가 검사하는 형태 둘 다로 남기는 것은 동시성 코드가 아니어도 통하는 습관입니다.
:::

## 순서가 바뀐다 {#ordering}

지금까지는 명령어가 쓰인 순서대로 실행된다고 가정했습니다. 락 없이 공유 변수를 읽고 쓰는 코드에서는 이 가정이 두 번 깨집니다.

**컴파일러가 바꿉니다.** 컴파일러는 다른 스레드가 없다고 보고 최적화합니다. 변수를 한 번 읽어 레지스터에 두고 계속 쓰기도 하고, 반대로 한 번 읽으라고 쓴 변수를 두 번 읽기도 합니다. 둘째 경우가 위험합니다. 값을 검사한 뒤 쓰는 사이에 다시 읽으면 검사한 값과 쓰는 값이 달라집니다.

```{.c file="include/asm-generic/rwonce.h" line="43"}
#ifndef __READ_ONCE
#define __READ_ONCE(x)	(*(const volatile __unqual_scalar_typeof(x) *)&(x))
#endif

#define READ_ONCE(x)							\
({									\
	compiletime_assert_rwonce_type(x);				\
	__READ_ONCE(x);							\
})
```

`READ_ONCE()`는 `volatile` 캐스트를 거쳐 읽어서 컴파일러가 "정확히 한 번" 읽게 합니다. `WRITE_ONCE()`는 쓰기 쪽의 짝입니다. 락 없이 접근하는 공유 변수에는 이 둘을 붙이는 것이 규칙이고, 그 자체로 "여기는 일부러 락 없이 읽는다"는 표시가 됩니다. 앞에서 본 워크큐와 NAPI 코드에 `READ_ONCE()`가 여러 번 나온 것이 이것입니다.

**CPU가 바꿉니다.** CPU는 쓰기를 곧바로 캐시에 반영하지 않고 **스토어 버퍼**(store buffer)에 넣어 둔 채 다음 명령어로 넘어갑니다.

::: {.fig src="store-buffer.svg"}
두 CPU가 각자 쓰고 나서 상대의 변수를 읽습니다. 코드 순서로는 불가능해 보이는 "둘 다 0"이 나옵니다.
:::

x86은 이 한 가지 재배치만 허용합니다. 쓰기 뒤의 읽기가 쓰기보다 먼저 보일 수 있습니다. arm64 같은 약한 순서의 아키텍처는 독립된 읽기끼리, 쓰기끼리도 순서를 바꿉니다. 순서를 강제하는 명령이 **메모리 배리어**(memory barrier)이고, 두 아키텍처의 정의를 나란히 놓으면 차이가 보입니다.

```{.c file="arch/x86/include/asm/barrier.h" line="53"}
#define __smp_mb()	asm volatile("lock addl $0,-4(%%" _ASM_SP ")" ::: "memory", "cc")

#define __smp_rmb()	dma_rmb()
#define __smp_wmb()	barrier()
```

```{.c file="arch/arm64/include/asm/barrier.h" line="126"}
#define __smp_mb()	dmb(ish)
#define __smp_rmb()	dmb(ishld)
#define __smp_wmb()	dmb(ishst)
```

x86에서 `smp_rmb()`와 `smp_wmb()`는 컴파일러만 막는 `barrier()`입니다. CPU가 이미 그 순서를 지키기 때문입니다. arm64에서는 셋 다 실제 명령어입니다. x86에서만 테스트한 락 없는 코드가 arm64에서 깨지는 이유입니다.

스토어 버퍼 문제는 커널의 가장 기본적인 자리에 있습니다. 잠드는 쪽은 "상태를 바꾸고 조건을 확인"하고, 깨우는 쪽은 "조건을 세우고 상태를 확인"합니다. 그림 13-7과 같은 모양입니다. 둘 다 상대의 쓰기를 못 보면 깨움을 놓칩니다.

```{.c file="include/linux/sched.h" line="247"}
#define set_current_state(state_value)					\
	do {								\
		debug_normal_state_change((state_value));		\
		trace_set_current_state(state_value);			\
		smp_store_mb(current->__state, (state_value));		\
	} while (0)
```

`smp_store_mb()`는 쓰고 나서 완전한 배리어를 칩니다. 태스크 상태를 쓴 것이 다른 CPU에 보이게 된 뒤에야 조건을 읽습니다. [3장](ch03.html)의 잠들기 순서가 지켜지는 것은 이 한 줄 덕분입니다.

::: {.warn}
배리어를 직접 쓰는 코드는 드물어야 합니다. 락을 잡고 푸는 동작, 원자 연산, RCU의 API에는 필요한 배리어가 이미 들어 있습니다. 락으로 보호한 데이터는 메모리 순서를 걱정할 필요가 없습니다. 락 없는 알고리즘을 직접 쓰기로 했다면 `Documentation/memory-barriers.txt`를 읽고, `tools/memory-model`의 리눅스 커널 메모리 모델로 검증하고, 락 없이 접근하는 변수를 찾아 주는 KCSAN([27장](ch27.html))을 켜고 돌려야 합니다. 대부분은 그 수고보다 락이 쌉니다.
:::

## 캐시 라인 {#cacheline}

올바르게 동기화한 코드가 느린 이유는 대개 캐시입니다. CPU는 메모리를 **캐시 라인** 단위로 가져옵니다. x86-64와 arm64에서 64바이트입니다. 한 CPU가 어떤 라인에 쓰려면 그 라인을 독점해야 하고, 다른 CPU의 캐시에 있던 사본은 무효가 됩니다. 다음에 그 CPU가 같은 라인을 만지면 다시 가져와야 합니다.

여러 CPU가 원자 연산으로 카운터 하나를 올리면, 연산 하나하나는 정확하지만 라인이 CPU 사이를 계속 오갑니다. 이것을 **캐시 라인 바운싱**이라고 합니다. 락 변수도 메모리의 한 워드이므로 마찬가지입니다. 경합이 없어도, 여러 CPU가 번갈아 잡기만 해도 락이 든 라인이 오갑니다.

::: {.fig src="false-sharing.svg"}
거짓 공유. 두 CPU는 서로 다른 필드를 쓰지만 캐시는 라인 단위로만 봅니다.
:::

**거짓 공유**(false sharing)는 논리적으로는 공유하지 않는데 물리적으로 같은 라인에 놓여 생기는 바운싱입니다. 코드를 읽어서는 보이지 않습니다. 커널은 뜨거운 구조체의 필드 배치를 직접 관리합니다. [12장](ch12.html)의 `softnet_data`입니다.

```{.c file="include/linux/netdevice.h" line="3636"}
	/* written and read only by owning cpu: */
	struct netdev_xmit xmit;
#ifdef CONFIG_RPS
	/* input_queue_head should be written by cpu owning this struct,
	 * and only read by other cpus. Worth using a cache line.
	 */
	unsigned int		input_queue_head ____cacheline_aligned_in_smp;

	/* Elements below can be accessed between CPUs for RPS/RFS */
	call_single_data_t	csd ____cacheline_aligned_in_smp;
	struct softnet_data	*rps_ipi_next;
	unsigned int		cpu;
```

주석이 필드를 "누가 쓰고 누가 읽는가"로 나눕니다. 자기 CPU만 쓰는 것, 자기가 쓰고 남이 읽는 것, 다른 CPU가 쓰는 것을 서로 다른 라인에 둡니다. `____cacheline_aligned_in_smp`는 그 필드를 새 캐시 라인의 시작에 맞춥니다. [6장](ch06.html)의 `DECLARE_PER_CPU_CACHE_HOT`은 반대 방향의 같은 배려입니다. 함께 쓰이는 CPU별 변수를 한 라인에 모아 캐시 미스를 줄입니다.

::: {.lab}
거짓 공유는 `perf c2c`로 찾습니다. 같은 캐시 라인을 여러 CPU가 건드려 생긴 캐시 미스를 라인별로 모아 줍니다.

```console
# perf c2c record -a -- sleep 10
# perf c2c report --stdio
```

보고서의 맨 위에 오는 라인이 가장 많이 오간 라인입니다. 라인 안의 오프셋별로 어느 코드가 읽고 썼는지 나오므로, 서로 다른 오프셋을 서로 다른 CPU가 쓰고 있으면 거짓 공유입니다.

락 경합은 `/proc/lock_stat`으로 봅니다. `CONFIG_LOCK_STAT`으로 빌드한 커널에서만 있고, 락별로 경합 횟수와 기다린 시간, 쥐고 있던 시간이 나옵니다. 배포판 커널에는 보통 꺼져 있습니다. 그럴 때는 `perf lock contention -a -b -- sleep 10`이 BPF로 락 경합 추적점을 모아 비슷한 정보를 줍니다.
:::

## 정리 {#summary}

- 커널의 동시성은 여러 CPU, 선점, hardirq, softirq에서 옵니다. 경쟁 조건은 읽고 고쳐 쓰기, 여러 필드 고치기, 확인 후 사용의 세 모양으로 나타납니다.
- 실행 컨텍스트는 태스크, softirq, hardirq, NMI 넷이고, 뒤의 것이 앞의 것을 끊습니다. 태스크 컨텍스트만 잠들 수 있습니다.
- `preempt_count`가 0이 아니거나 인터럽트가 꺼진 상태가 원자적 컨텍스트입니다. 거기서 잠들면 `might_sleep()`과 `schedule()`의 검사가 잡습니다.
- 보호 수단은 값이 다릅니다. 공유를 없애는 CPU별 데이터가 가장 싸고, 원자 연산, 같은 CPU의 끼어들기 막기, 스핀락, 잠드는 락 순으로 무거워집니다.
- 락을 고르는 규칙은 "끊길 수 있는 쪽이 막는다"입니다. 태스크와 softirq는 `spin_lock_bh()`, hardirq가 끼면 `spin_lock_irqsave()`입니다.
- 교착은 같은 CPU에서 인터럽트가 같은 락을 잡거나, 두 경로가 락을 반대 순서로 잡을 때 생깁니다.
- 락 없이 공유 변수를 만지는 코드는 컴파일러와 CPU의 재배치를 직접 다뤄야 합니다. `READ_ONCE()`와 메모리 배리어가 그 도구입니다.
- 올바른 코드도 캐시 라인을 다투면 느립니다. 거짓 공유는 필드 배치로 풉니다.

## 확인 문제 {#quiz}

::: {.q}
타이머 콜백(softirq)과 `ioctl()` 경로(태스크)가 같은 연결 리스트를 고칩니다. 각각 어떤 락 함수를 써야 하고, 양쪽이 다른 이유는 무엇입니까? `ioctl()` 쪽이 `spin_lock()`만 쓰면 어떤 일이 생깁니까?

::: {.a}
`ioctl()` 쪽은 `spin_lock_bh()`, 타이머 콜백은 `spin_lock()`입니다. 태스크는 softirq에게 끊길 수 있으므로 락을 잡기 전에 softirq를 막아야 하고, softirq는 같은 CPU의 태스크에게 끊기지 않으므로 막을 것이 없습니다. `ioctl()`이 `spin_lock()`만 쓰면, 락을 쥔 채 인터럽트가 들어오고 그 복귀 길에 타이머 softirq가 실행되어 같은 락을 잡으려 합니다. softirq는 락이 풀리기를 기다리며 돌고, 락을 쥔 태스크는 softirq가 끝나야 실행되므로 그 CPU는 멈춥니다. 다른 CPU에서 콜백이 도는 경우에는 정상적으로 기다렸다 지나가므로, 이 버그는 타이머가 같은 CPU에서 만료될 때만 나타납니다.
:::
:::

::: {.q}
`this_cpu_inc(stat)`은 선점도 인터럽트도 끄지 않고 안전합니다. 그런데 `x = this_cpu_read(stat); this_cpu_write(stat, x + 1);`은 안전하지 않습니다. 차이는 무엇입니까?

::: {.a}
`this_cpu_inc()`는 "이 CPU의 변수를 찾아 1을 더한다"가 명령어 하나입니다. 선점과 인터럽트는 명령어 사이에서만 일어나므로 끼어들 틈이 없습니다. 둘째 코드는 연산 둘이고 그 사이에 틈이 있습니다. 읽은 뒤 인터럽트 핸들러가 같은 변수를 올리면 그 증가가 덮어써집니다. 읽은 뒤 선점당해 다른 CPU로 옮겨지면, 이전 CPU에서 읽은 값에 1을 더해 새 CPU의 변수에 쓰게 됩니다. 연산 하나하나가 원자적이어도 묶음은 원자적이지 않습니다. 둘째 형태가 필요하면 `preempt_disable()`이나 `local_irq_save()`로 구간을 감싸야 합니다.
:::
:::

::: {.q}
인터럽트 핸들러 안에서 `kmalloc(size, GFP_KERNEL)`을 불렀습니다. 대부분은 문제없이 동작하다가 메모리가 모자란 날 시스템이 이상해집니다. `CONFIG_DEBUG_ATOMIC_SLEEP`을 켠 커널에서는 무엇이 달라집니까?

::: {.a}
`GFP_KERNEL` 할당은 여유 메모리가 있으면 잠들지 않고 돌아오므로 평소에는 드러나지 않습니다. 메모리가 모자라면 회수를 기다리며 `schedule()`을 부르고, hardirq 컨텍스트에서 잠들려 한 것이므로 "scheduling while atomic"이 찍히거나 더 나쁜 일이 생깁니다. 디버그 옵션을 켜면 할당 함수 입구의 `might_sleep()` 계열 검사가 실제로 잠드는지와 상관없이 매번 실행됩니다. `preempt_count`의 hardirq 칸이 0이 아니므로 첫 호출에서 "sleeping function called from invalid context"와 스택 추적이 찍힙니다. 드물게 터지는 버그를 항상 터지는 경고로 바꿔 줍니다.
:::
:::

::: {.q}
잠드는 쪽이 `current->__state = TASK_INTERRUPTIBLE; if (!cond) schedule();`을, 깨우는 쪽이 `cond = 1; wake_up_process(t);`를 실행합니다. 상태를 쓰는 데 평범한 대입을 쓰면 x86에서도 깨움을 놓칠 수 있습니다. 어떤 순서로 그렇게 됩니까?

::: {.a}
잠드는 CPU의 `__state` 쓰기와 깨우는 CPU의 `cond` 쓰기가 각자의 스토어 버퍼에 머무는 동안, 양쪽이 상대의 변수를 읽습니다. 잠드는 쪽은 `cond`를 0으로 읽어 `schedule()`로 가고, 깨우는 쪽은 태스크 상태를 아직 `TASK_RUNNING`으로 읽어 깨울 필요가 없다고 판단합니다. 그 뒤 버퍼가 비워지면 태스크는 잠든 상태이고 깨워 줄 쪽은 이미 지나갔습니다. `set_current_state()`는 `smp_store_mb()`로 상태 쓰기 뒤에 완전한 배리어를 넣어, 쓰기가 다른 CPU에 보인 뒤에야 `cond`를 읽게 합니다. 깨우는 쪽에도 대응하는 배리어가 있어서, 둘 중 적어도 하나는 상대의 쓰기를 봅니다.
:::
:::

::: {.q}
스레드 넷이 각자 자기 카운터만 올리는데, 카운터를 `long counters[4]` 배열에 두었더니 스레드를 늘릴수록 느려집니다. 원인과 해법은 무엇이고, 어떻게 확인합니까?

::: {.a}
`long` 넷은 32바이트라 한 캐시 라인에 들어갑니다. 스레드들은 서로 다른 원소를 쓰지만 CPU는 라인 단위로 독점권을 주고받으므로, 한 스레드가 쓸 때마다 다른 세 CPU의 캐시에서 그 라인이 무효가 됩니다. 거짓 공유입니다. 해법은 원소마다 캐시 라인 크기로 정렬해 서로 다른 라인에 놓는 것입니다. 커널이라면 CPU별 변수나 `____cacheline_aligned_in_smp`를 씁니다. 확인은 `perf c2c`로 합니다. 한 라인의 서로 다른 오프셋에 서로 다른 CPU의 쓰기가 몰려 있으면 거짓 공유입니다.
:::
:::

## 용어 {#terms}

::: {.terms}
경쟁 조건 (race condition)
:   결과가 여러 실행 흐름의 실행 순서에 따라 달라지는 상황.

임계 구역 (critical section)
:   한 번에 한 실행 흐름만 들어가야 올바른 코드 구간.

실행 컨텍스트 (execution context)
:   코드가 태스크, softirq, hardirq, NMI 가운데 어떤 상황에서 실행되는지. 할 수 있는 일을 정한다.

원자적 컨텍스트 (atomic context)
:   잠들면 안 되는 상태. `preempt_count`가 0이 아니거나 인터럽트가 꺼져 있다.

CPU별 데이터 (per-CPU data)
:   CPU마다 따로 두어 다른 CPU와 공유하지 않는 변수.

원자 연산 (atomic operation)
:   다른 CPU가 중간 상태를 볼 수 없게 한 번에 끝나는 읽고 고쳐 쓰기.

교착 (deadlock)
:   실행 흐름들이 서로가 쥔 락을 기다려 아무도 나아가지 못하는 상태.

락 순서 (lock ordering)
:   여러 락을 함께 잡을 때 모든 경로가 따르는 정해진 순서.

스토어 버퍼 (store buffer)
:   CPU가 쓰기를 캐시에 반영하기 전에 잠시 담아 두는 곳. 쓰기와 읽기의 순서가 바뀌어 보이는 원인.

메모리 배리어 (memory barrier)
:   앞뒤 메모리 접근의 순서가 다른 CPU에 그대로 보이도록 강제하는 명령.

데이터 경쟁 (data race)
:   락이나 원자 연산 없이 같은 변수에 동시에 접근하고 그 가운데 하나 이상이 쓰기인 경우.

거짓 공유 (false sharing)
:   서로 다른 변수가 같은 캐시 라인에 놓여, 공유하지 않는데도 라인이 CPU 사이를 오가는 현상.
:::
