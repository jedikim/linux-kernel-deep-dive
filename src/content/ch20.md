::: {.lead}
`cat /etc/hostname`과 `cat /proc/uptime`은 같은 시스템 콜을 부릅니다. `openat()`, `read()`, `close()`입니다. 그런데 앞의 파일은 디스크 블록에 들어 있고, 뒤의 파일은 어디에도 저장되어 있지 않습니다. 읽는 순간 커널이 값을 계산해 글자로 만듭니다. 파이프와 소켓도 같은 `read()`로 읽습니다. 이 차이를 가리는 층이 VFS입니다. 이 장은 fd 번호 하나가 커널 안에서 어떤 객체를 거쳐 실제 구현에 닿는지 따라갑니다.
:::

::: {.goals}
- fd 번호는 커널 안에서 어떤 구조체들을 거쳐 inode에 닿는가?
- `open("/home/kim/notes.txt")`는 문자열을 어떻게 dentry로 바꾸는가? 그 과정이 대부분 락 없이 끝나는 까닭은 무엇인가?
- 같은 `read()`가 ext4 파일, 파이프, `/proc` 파일에서 다르게 동작하는 것은 코드 어디에서 갈리는가?
- `write()`가 돌아온 뒤 데이터는 어디에 있고, 언제 디스크로 가는가?
- 마운트는 무엇과 무엇을 잇는가? 마운트 시스템 콜은 왜 여러 개로 나뉘었는가?
- `/proc`과 `/sys`의 파일 내용은 누가 만드는가?
:::

## 네 개의 객체 {#objects}

**VFS**(virtual filesystem switch)는 시스템 콜과 개별 파일시스템 사이에 놓인 층입니다. 유저 공간에는 모든 파일시스템이 같은 시스템 콜에 같은 방식으로 답하게 하고, 파일시스템 쪽에는 "이 함수들을 채워 넣으면 된다"는 틀을 줍니다.

::: {.fig src="vfs-layers.svg"}
시스템 콜에서 장치까지의 층. VFS는 경로 탐색, fd 관리, 캐시처럼 모든 파일시스템에 공통인 일을 맡고, 파일시스템마다 다른 일은 ops 테이블을 거쳐 넘깁니다.
:::

VFS는 파일시스템을 네 종류의 객체로 봅니다.

| 객체 | 나타내는 것 | ops 테이블 |
|---|---|---|
| `super_block` | 마운트된 파일시스템 하나 | `super_operations` |
| `inode` | 파일 하나. 종류, 권한, 크기를 담고 이름은 없습니다. | `inode_operations` |
| `dentry` | 이름 하나. 부모 디렉터리와 이름을 inode에 잇습니다. | `dentry_operations` |
| `file` | 열린 파일 하나. 읽기·쓰기 위치와 플래그를 담습니다. | `file_operations` |

객체가 넷으로 나뉜 까닭은 수명과 개수가 서로 다르기 때문입니다.

- **이름과 파일은 별개입니다.** 하드 링크는 dentry 둘이 inode 하나를 가리키는 것입니다.
- **파일과 열린 파일은 별개입니다.** 같은 파일을 두 번 `open()`하면 `file`이 둘 생기고 읽기 위치도 따로 움직입니다. `dup()`이나 `fork()`로 복제한 fd는 같은 `file`을 가리키므로 위치를 함께 씁니다.
- **dentry와 inode는 캐시입니다.** 닫은 뒤에도 메모리에 남아 다음 탐색을 빠르게 합니다. `file`은 마지막 참조가 사라지면 없어집니다.

::: {.fig src="object-chain.svg"}
태스크에서 슈퍼블록까지. fd 3과 4는 같은 파일을 따로 열어 `file`이 둘이고, 두 `file`은 같은 dentry와 inode를 가리킵니다.
:::

`struct file`의 정의에서 이 사슬이 그대로 보입니다.

```{.c file="include/linux/fs.h" line="1255"}
struct file {
	spinlock_t			f_lock;
	fmode_t				f_mode;
	const struct file_operations	*f_op;
	struct address_space		*f_mapping;
	void				*private_data;
	struct inode			*f_inode;
	/* ... */
	union {
		const struct path	f_path;
		struct path		__f_path;
	};
	/* ... */
	loff_t				f_pos;
	/* ... */
	file_ref_t			f_ref;
	/* ... */
} __randomize_layout
```

읽을 곳은 네 군데입니다.

- `f_op`가 이 파일에 대한 `read()`, `write()`, `mmap()`의 실제 구현을 가리킵니다.
- `f_path`는 `struct path`, 곧 `(vfsmount, dentry)` 쌍입니다. 같은 dentry가 여러 마운트 지점에서 보일 수 있으므로 dentry만으로는 위치가 정해지지 않습니다.
- `f_pos`가 읽기·쓰기 위치입니다. inode가 아니라 `file`에 있으므로 여는 쪽마다 따로 갖습니다.
- `f_mapping`은 이 파일의 페이지 캐시입니다([18장](ch18.html)).

태스크 쪽에는 fd 테이블인 `files_struct`와, 루트·현재 디렉터리를 담은 `fs_struct`가 있습니다. 스레드끼리 이 둘을 공유할지는 `clone()`의 `CLONE_FILES`, `CLONE_FS` 플래그가 정합니다([2장](ch02.html)).

## fd에서 struct file까지 {#fd}

fd는 배열 인덱스입니다. `files_struct`가 가리키는 `fdtable`에 `struct file *` 배열 `fd[]`가 있고, `read(3, ...)`은 `fd[3]`을 꺼내는 일로 시작합니다. `ksys_read()`의 첫 줄 `CLASS(fd_pos, f)(fd)`를 따라가면 `__fget_light()`에 닿습니다.

```{.c file="fs/file.c" line="1180"}
static inline struct fd __fget_light(unsigned int fd, fmode_t mask)
{
	struct files_struct *files = current->files;
	struct file *file;

	/* ... */
	if (likely(atomic_read_acquire(&files->count) == 1)) {
		file = files_lookup_fd_raw(files, fd);
		if (!file || unlikely(file->f_mode & mask))
			return EMPTY_FD;
		return BORROWED_FD(file);
	} else {
		file = __fget_files(files, fd, mask);
		if (!file)
			return EMPTY_FD;
		return CLONED_FD(file);
	}
}
```

길이 둘로 갈립니다.

- **fd 테이블을 혼자 쓰는 경우**(`files->count == 1`). 시스템 콜을 처리하는 동안 다른 누구도 이 fd를 닫을 수 없으므로 참조 카운트를 올리지 않고 포인터를 빌려 씁니다.
- **fd 테이블을 여럿이 쓰는 경우.** 다른 스레드가 같은 순간에 `close(3)`을 부를 수 있습니다. `__fget_files()`는 RCU 읽기 구간([16장](ch16.html)) 안에서 `fd[]`를 읽고, `file_ref_get()`으로 참조를 얻은 다음, 그 칸이 여전히 같은 `file`을 가리키는지 **다시 확인**합니다.

다시 확인하는 까닭은 `file`의 슬랩 캐시가 `SLAB_TYPESAFE_BY_RCU`이기 때문입니다. 이 캐시에서는 해제된 메모리가 유예 기간을 기다리지 않고 곧바로 다른 `file`로 재사용될 수 있습니다. 포인터를 읽은 뒤 참조를 얻기 전에 그 `file`이 닫히고 같은 자리에 다른 파일이 열렸을 수 있습니다. 참조를 얻은 뒤 테이블을 한 번 더 읽어 같은 포인터인지 보면 이 경우가 걸러집니다.

::: {.old}
많은 자료가 `struct file`의 참조 카운트를 `atomic_long_t f_count`로 설명하고 `fget()`이 `atomic_long_inc_not_zero()`를 부른다고 씁니다. v7.3에서 이 필드는 `file_ref_t f_ref`입니다. 6.13에서 바뀌었습니다. 참조가 하나일 때 값이 0이고, 마지막 참조가 사라지면 음수 영역으로 넘어갑니다. 그래서 "죽은 파일이 아니면 올리기"가 비교 교환 반복 없이 덧셈 한 번과 부호 검사로 끝납니다.
:::

::: {.lab}
셸이 연 fd와 그 뒤의 객체를 봅니다.

```console
$ ls -l /proc/$$/fd
lrwx------ 1 kim kim 64 ... 0 -> /dev/pts/3
...
$ cat /proc/$$/fdinfo/0
pos:    0
flags:  02
mnt_id: 27
ino:    6
$ cat /proc/sys/fs/file-nr
3328    0       9223372036854775807
```

`fdinfo`의 `pos`는 `f_pos`, `flags`는 `f_flags`(8진수), `mnt_id`와 `ino`는 `f_path`의 마운트와 inode입니다. `file-nr`의 첫 값은 시스템 전체의 `struct file` 개수입니다. `strace -e trace=openat cat /etc/hostname`을 돌리면 `cat` 하나가 뜨는 데에도 `openat()`이 여러 번 불리는 것이 보입니다.
:::

## 경로 탐색: 문자열을 dentry로 {#lookup}

`open()`, `openat()`, `openat2()`는 모두 `do_sys_openat2()`로 모입니다. 마지막 줄은 `FD_ADD(how->flags, do_file_open(dfd, name, &op))`입니다. `do_file_open()`이 `struct file`을 만들어 돌려주면 `FD_ADD`가 빈 fd 번호를 잡아 테이블에 꽂습니다.

```{.c file="fs/namei.c" line="5018"}
struct file *do_file_open(int dfd, struct filename *pathname,
		const struct open_flags *op)
{
	struct nameidata nd;
	int flags = op->lookup_flags;
	struct file *filp;

	if (IS_ERR(pathname))
		return ERR_CAST(pathname);
	set_nameidata(&nd, dfd, pathname, NULL);
	filp = path_openat(&nd, op, flags | LOOKUP_RCU);
	if (unlikely(filp == ERR_PTR(-ECHILD)))
		filp = path_openat(&nd, op, flags);
	if (unlikely(filp == ERR_PTR(-ESTALE)))
		filp = path_openat(&nd, op, flags | LOOKUP_REVAL);
	restore_nameidata();
	return filp;
}
```

`path_openat()`을 최대 세 번 부릅니다. 이 세 번의 시도는 [다음 절](#rcu-walk)에서 보고, 먼저 한 번의 시도가 하는 일입니다.

탐색의 현재 위치는 `struct nameidata`의 `path`, 곧 `(mnt, dentry)` 쌍입니다. `path_init()`이 출발점을 정합니다. 경로가 `/`로 시작하면 태스크의 루트(`fs->root`), 아니면 현재 디렉터리나 `dfd`입니다. 그다음 `link_path_walk()`가 경로를 `/`로 끊어 가며 성분마다 같은 일을 되풀이합니다.

1. `may_lookup()`: 현재 디렉터리에 탐색(실행) 권한이 있는지 봅니다.
2. `hash_name()`: 다음 `/`까지의 이름을 잘라 해시를 계산합니다.
3. `lookup_fast()`: **dcache**(dentry 캐시)에서 `(부모 dentry, 이름)`으로 자식을 찾습니다. 전역 해시 테이블 조회 한 번입니다.
4. 없으면 `lookup_slow()`: 디렉터리 inode의 락을 공유 모드로 잡고 파일시스템의 `i_op->lookup()`을 부릅니다. 파일시스템이 디스크에서 디렉터리를 읽어 dentry를 채웁니다.
5. `step_into()`: 찾은 dentry가 마운트 지점이거나 심볼릭 링크인지 보고 현재 위치를 옮깁니다.

::: {.fig src="path-walk.svg"}
`/home/kim/notes.txt`를 따라가는 길. `/home`에 다른 파일시스템이 마운트되어 있으면 dentry를 찾은 뒤 마운트 해시를 한 번 더 조회해 그 파일시스템의 루트 dentry로 건너갑니다.
:::

세 가지 특별한 경우가 있습니다.

**없는 이름도 캐시합니다.** `lookup()`이 디스크에서 이름을 찾지 못하면 inode 포인터가 `NULL`인 dentry를 dcache에 남깁니다. **음성 dentry**(negative dentry)입니다. 셸이 `PATH`를 차례로 뒤질 때처럼 "없다"는 답이 많은 탐색에서 디스크를 다시 읽지 않게 합니다.

**마운트 지점을 건넙니다.** dentry에 `DCACHE_MOUNTED` 플래그가 서 있으면 `__lookup_mnt()`가 `(현재 마운트, 이 dentry)`를 키로 마운트 해시를 조회합니다. 자식 마운트가 있으면 현재 위치를 `(자식 마운트, 그 루트 dentry)`로 바꿉니다. 위치를 dentry 하나가 아니라 쌍으로 기억하는 까닭이 여기 있습니다.

**심볼릭 링크를 따라갑니다.** 남은 경로를 `nd->stack`에 밀어 두고 링크의 내용을 새 경로처럼 걷습니다. 한 번의 탐색에서 따라갈 수 있는 링크는 `MAXSYMLINKS`, 40개까지입니다.

마지막 성분까지 오면 `do_open()`이 권한을 확인하고 `vfs_open()`을 부릅니다.

경로 탐색은 보안 경계이기도 합니다. 컨테이너 런타임이 컨테이너의 루트 아래에서 파일을 열 때, 그 안의 심볼릭 링크가 `../../..`을 가리키면 호스트의 파일이 열립니다. `openat2()`는 `resolve` 필드로 탐색 자체를 제한합니다. `RESOLVE_BENEATH`는 `dfd` 밖으로 나가는 탐색을 거부하고, `RESOLVE_IN_ROOT`는 `dfd`를 루트처럼 취급합니다. `RESOLVE_NO_SYMLINKS`와 `RESOLVE_NO_XDEV`는 심볼릭 링크나 마운트 지점을 만나면 실패하게 합니다.

dcache와 inode 캐시는 메모리가 남는 한 계속 자랍니다. 메모리가 모자라면 [18장](ch18.html)의 회수 코드가 슈퍼블록마다 등록된 **슈링커**(shrinker) `super_cache_scan()`을 부릅니다. 참조가 0인 dentry를 LRU에서 먼저 버리고 그다음에 inode를 버립니다. dentry가 inode를 붙들고 있기 때문입니다.

## RCU-walk와 ref-walk {#rcu-walk}

경로 탐색은 커널에서 가장 자주 도는 코드에 속하고, 모든 절대 경로는 루트 dentry에서 출발합니다. 지나가는 dentry마다 락을 잡고 참조 카운트를 올리면 모든 CPU가 루트 dentry의 같은 캐시 라인에 쓰기를 하게 됩니다. 캐시 라인이 CPU 사이를 오가는 비용이 탐색 비용을 압도합니다([13장](ch13.html)). 그래서 탐색에는 두 가지 방식이 있습니다.

- **ref-walk**: 성분마다 dentry의 `d_lock`을 잡고 참조 카운트를 올립니다. 느리지만 중간에 잠들 수 있습니다.
- **RCU-walk**: 시작할 때 `rcu_read_lock()`을 한 번 부르고, 끝날 때까지 **어떤 dentry에도 쓰지 않습니다.**

참조 없이 dentry를 읽으면 그 사이에 이름이 바뀌거나 지워질 수 있습니다. RCU는 메모리 해제를 막아 주지만 내용이 바뀌는 것은 막지 않습니다. 그래서 dentry마다 순서 카운터 `d_seq`가 있습니다. 읽기 전에 값을 적어 두고, 읽은 내용을 쓰기 직전에 값이 그대로인지 확인합니다. seqcount의 원리는 [14장](ch14.html)에 있습니다.

```{.c file="fs/namei.c" line="1843"}
static struct dentry *lookup_fast(struct nameidata *nd)
{
	struct dentry *dentry, *parent = nd->path.dentry;
	int status = 1;

	/* ... */
	if (nd->flags & LOOKUP_RCU) {
		dentry = __d_lookup_rcu(parent, &nd->last, &nd->next_seq);
		if (unlikely(!dentry)) {
			if (!try_to_unlazy(nd))
				return ERR_PTR(-ECHILD);
			return NULL;
		}

		/* ... */
		if (read_seqcount_retry(&parent->d_seq, nd->seq))
			return ERR_PTR(-ECHILD);
		/* ... */
	} else {
		dentry = __d_lookup(parent, &nd->last);
		/* ... */
	}
	/* ... */
	return dentry;
}
```

읽을 곳은 세 군데입니다.

- `__d_lookup_rcu()`는 자식 dentry와 함께 그 `d_seq` 값을 `nd->next_seq`에 돌려줍니다. 부모의 seq를 확인하고 자식의 seq를 받아 두는 식으로 검증이 사슬처럼 이어집니다.
- `-ECHILD`는 "RCU-walk로는 못 하겠다"는 신호입니다. `do_file_open()`이 이 값을 받으면 처음부터 ref-walk로 다시 합니다.
- dcache에 없으면 `try_to_unlazy()`를 부릅니다. 지금 서 있는 dentry와 마운트에 참조를 얻어 RCU-walk를 ref-walk로 **도중에 전환**합니다. 디스크를 읽으려면 잠들어야 하고, RCU 읽기 구간에서는 잠들 수 없기 때문입니다. 성공하면 그 자리에서 이어 갑니다.

::: {.fig src="rcu-vs-ref-walk.svg"}
같은 경로를 두 방식으로 걸을 때 dentry마다 일어나는 일. RCU-walk는 읽기와 검증만 하고, 마지막 dentry에서만 참조를 얻습니다.
:::

마지막 dentry에는 어차피 참조가 필요합니다. `file`이 그것을 붙들어야 하기 때문입니다. 그래서 RCU-walk도 끝에서 한 번 `try_to_unlazy()`를 거칩니다. 세 번째 시도인 `LOOKUP_REVAL`은 NFS 같은 네트워크 파일시스템을 위한 것입니다. `-ESTALE`이 나오면 캐시된 dentry를 믿지 않고 성분마다 서버에 다시 확인하며 걷습니다.

::: {.design}
RCU-walk는 **낙관적인 빠른 길과 확실한 느린 길**을 짝지은 설계입니다. 빠른 길은 "아무도 중간에 바꾸지 않았을 것"이라고 가정하되, 가정이 깨졌는지 값싸게 검증할 수단(`d_seq`)을 갖습니다. 깨졌으면 고쳐 쓰려 하지 않고 느린 길로 통째로 넘깁니다. 이름 변경과의 경쟁, 캐시 미스, 잠들어야 하는 파일시스템은 전부 `-ECHILD` 한 줄로 포기합니다. 올바름은 느린 길이 책임지고, 빠른 길은 흔한 경우만 빠르게 하면 됩니다.
:::

## file_operations: read()가 갈리는 자리 {#fops}

`vfs_open()`이 부르는 `do_dentry_open()`에서 `file`에 ops 테이블이 붙습니다. 핵심은 `f->f_op = fops_get(inode->i_fop);` 한 줄입니다. inode의 `i_fop`는 그 inode를 만든 파일시스템이 채워 둔 것입니다. ext4는 디스크에서 일반 파일의 inode를 읽어 올 때 `inode->i_fop = &ext4_file_operations`를 대입합니다. 그 뒤로 이 `file`에 대한 모든 연산은 `f_op`를 거칩니다.

```{.c file="fs/read_write.c" line="554"}
ssize_t vfs_read(struct file *file, char __user *buf, size_t count, loff_t *pos)
{
	/* ... */
	if (file->f_op->read)
		ret = file->f_op->read(file, buf, count, pos);
	else if (file->f_op->read_iter)
		ret = new_sync_read(file, buf, count, pos);
	else
		ret = -EINVAL;
	/* ... */
	return ret;
}
```

`vfs_read()`는 대상이 무엇인지 묻지 않습니다. 열린 모드를 확인하고 함수 포인터를 부를 뿐입니다. 세 파일시스템의 테이블을 나란히 놓으면 이렇습니다.

```{.c file="fs/ext4/file.c" line="1035"}
const struct file_operations ext4_file_operations = {
	.llseek		= ext4_llseek,
	.read_iter	= ext4_file_read_iter,
	.write_iter	= ext4_file_write_iter,
	/* ... */
	.mmap_prepare	= ext4_file_mmap_prepare,
	.open		= ext4_file_open,
	.release	= ext4_release_file,
	.fsync		= ext4_sync_file,
	/* ... */
};
```

```{.c file="fs/pipe.c" line="1340"}
static const struct file_operations pipeanon_fops = {
	.open		= fifo_open,
	.read_iter	= anon_pipe_read,
	.write_iter	= anon_pipe_write,
	.poll		= pipe_poll,
	.unlocked_ioctl	= pipe_ioctl,
	.release	= pipe_release,
	/* ... */
};
```

```{.c file="fs/proc/inode.c" line="566"}
static const struct file_operations proc_iter_file_ops = {
	.llseek		= proc_reg_llseek,
	.read_iter	= proc_reg_read_iter,
	.write		= proc_reg_write,
	/* ... */
	.open		= proc_reg_open,
	.release	= proc_reg_release,
};
```

::: {.fig src="fops-dispatch.svg"}
`vfs_read()`까지는 한 길이고 `f_op->read_iter`에서 갈립니다. ext4는 페이지 캐시에서, 파이프는 커널 안의 링 버퍼에서 읽고, procfs는 읽는 순간 내용을 만들어 냅니다.
:::

세 테이블에서 눈여겨볼 것은 **비어 있는 칸**입니다. 파이프에는 `.llseek`도 `.fsync`도 `.mmap`도 없습니다. `do_dentry_open()`은 `llseek`이 없는 파일에서 `FMODE_LSEEK`을 지우고, `vfs_llseek()`은 이 비트가 없으면 `-ESPIPE`를 돌려줍니다. 구현하지 않은 연산에 무엇을 답할지는 VFS가 정하므로, 파일시스템은 자기에게 뜻이 있는 연산만 채웁니다.

::: {.design}
`file_operations`는 C로 쓴 인터페이스입니다. 호출하는 쪽과 구현하는 쪽이 함수 포인터의 구조체 하나로만 이어집니다. 새 파일시스템을 넣을 때 VFS를 고치지 않고, VFS에 넣은 개선(RCU-walk, 폴리오 전환)은 모든 파일시스템에 한꺼번에 돌아갑니다. 치르는 값은 테이블의 칸이나 인자를 바꿀 때 수십 개 파일시스템을 함께 고쳐야 한다는 것입니다. `Documentation/filesystems/porting.rst`가 그 기록입니다. ops 테이블 패턴은 [25장](ch25.html)에서 다시 봅니다.
:::

## 읽기: 페이지 캐시를 거치는 길 {#read}

ext4의 `read_iter`는 `generic_file_read_iter()`를 거쳐 `filemap_read()`로 갑니다. 여기서부터는 `mm/filemap.c`, 곧 디스크 파일시스템들이 함께 쓰는 코드입니다. `filemap_read()`는 반복문 하나입니다. `filemap_get_pages()`로 필요한 범위의 폴리오를 한 묶음 얻고, `copy_folio_to_iter()`로 유저 버퍼에 복사하고, 폴리오를 놓습니다. 디스크와 만나는 곳은 `filemap_get_pages()` 안입니다.

```{.c file="mm/filemap.c" line="2686"}
static int filemap_get_pages(struct kiocb *iocb, size_t count,
		struct folio_batch *fbatch, bool need_uptodate)
{
	/* ... */
	filemap_get_read_batch(mapping, index, last_index - 1, fbatch);
	if (!folio_batch_count(fbatch)) {
		DEFINE_READAHEAD(ractl, filp, &filp->f_ra, mapping, index);

		/* ... */
		page_cache_sync_ra(&ractl, last_index - index);
		/* ... */
		filemap_get_read_batch(mapping, index, last_index - 1, fbatch);
	}
	/* ... */
	folio = fbatch->folios[folio_batch_count(fbatch) - 1];
	if (folio_test_readahead(folio)) {
		err = filemap_readahead(iocb, filp, mapping, folio, last_index);
		/* ... */
	}
	if (!folio_test_uptodate(folio)) {
		/* ... */
		err = filemap_update_page(iocb, mapping, count, folio,
					  need_uptodate);
		/* ... */
	}
	/* ... */
}
```

세 가지 경우가 이 함수에 다 들어 있습니다.

- **캐시에 있다.** `filemap_get_read_batch()`가 페이지 캐시(xarray)에서 폴리오를 찾아옵니다. RCU로 보호되며 락을 잡지 않습니다. 디스크 I/O도 없습니다.
- **캐시에 없다.** `page_cache_sync_ra()`가 폴리오를 할당해 페이지 캐시에 넣고, 파일시스템의 `a_ops->readahead()`를 불러 디스크 읽기를 겁니다. 요청한 범위의 뒤쪽까지 **미리 읽습니다**(readahead). 폴리오는 I/O가 끝날 때까지 잠겨 있고, `filemap_update_page()`가 그 락이 풀리기를 기다립니다. 태스크가 `read()` 안에서 잠드는 곳입니다.
- **미리 읽은 창의 끝에 닿았다.** 미리 읽기는 창의 한 폴리오에 표시(`PG_readahead`)를 해 둡니다. 읽기가 그 폴리오에 닿으면 `filemap_readahead()`가 다음 창을 비동기로 읽기 시작합니다. 순차 읽기가 이어지는 동안에는 유저가 데이터를 소비하는 사이에 다음 데이터가 도착합니다.

::: {.fig src="read-path.svg"}
`read()`가 페이지 캐시를 거치는 길. 캐시에 있으면 복사만 하고 돌아갑니다. 없으면 미리 읽기가 폴리오를 만들고 블록 계층에 읽기를 요청합니다.
:::

페이지 캐시를 거치지 않는 길도 있습니다. `O_DIRECT`로 연 파일은 유저 버퍼의 페이지를 고정해 그대로 블록 계층에 넘깁니다. 자체 캐시를 가진 데이터베이스가 이중 캐싱을 피하려고 씁니다. `mmap()`은 반대로 복사를 없앱니다. 페이지 캐시의 폴리오가 유저의 페이지 테이블에 직접 매핑됩니다([17장](ch17.html)).

## 쓰기와 writeback {#write}

ext4에서 버퍼를 거치는 `write()`는 `generic_perform_write()`에 닿습니다.

```{.c file="mm/filemap.c" line="4346"}
ssize_t generic_perform_write(struct kiocb *iocb, struct iov_iter *i)
{
	/* ... */
	do {
		/* ... */
		balance_dirty_pages_ratelimited(mapping);
		/* ... */
		status = a_ops->write_begin(iocb, mapping, pos, bytes,
						&folio, &fsdata);
		/* ... */
		copied = copy_folio_from_iter_atomic(folio, offset, bytes, i);
		flush_dcache_folio(folio);

		status = a_ops->write_end(iocb, mapping, pos, bytes, copied,
						folio, fsdata);
		/* ... */
	} while (iov_iter_count(i));
	/* ... */
}
```

`write_begin()`이 폴리오를 준비하고, 유저 데이터를 폴리오에 복사하고, `write_end()`가 폴리오에 **더티**(dirty) 표시를 합니다. 그리고 돌아옵니다. 디스크에는 아무것도 쓰지 않았습니다. ext4의 기본 설정에서는 어느 블록에 쓸지조차 이때 정하지 않고 공간만 예약해 둡니다(지연 할당).

::: {.myth}
"`write()`가 성공했으니 데이터는 디스크에 있다." 아닙니다. 데이터는 페이지 캐시에 있고, 그 뒤에 전원이 나가면 사라집니다. 디스크에 닿았다는 보장은 `fsync()`나 `fdatasync()`가 성공해야 얻습니다. 쓰기 도중의 I/O 오류도 `write()`가 아니라 나중의 `fsync()`가 돌려줍니다.
:::

더티 폴리오를 디스크로 보내는 일이 **writeback**입니다. 하는 주체는 장치마다 있는 플러셔입니다. 저장 장치 하나(`backing_dev_info`)에 `bdi_writeback`이 붙어 있고, 그 안의 지연 워크가 `writeback`이라는 워크큐에서 실행됩니다([11장](ch11.html)). `ps`에 보이는 `kworker/u16:2-flush-259:0` 같은 이름이 이 워커입니다. 워크 함수 `wb_workfn()`이 부르는 `wb_do_writeback()`은 세 가지를 차례로 확인합니다.

| 계기 | 코드 | 조건 (기본값) |
|---|---|---|
| 명시적 요청 | `get_next_work_item()` | `sync()`, 메모리 회수 등이 넣은 작업 |
| 오래된 데이터 | `wb_check_old_data_flush()` | 5초마다 깨어나, 더티가 된 지 30초 넘은 inode를 씁니다. |
| 더티가 너무 많음 | `wb_check_background_flush()` | 더티 페이지가 쓸 수 있는 메모리의 10%를 넘으면 그 아래로 내려갈 때까지 씁니다. |

숫자는 `vm.dirty_writeback_centisecs`(500), `vm.dirty_expire_centisecs`(3000), `vm.dirty_background_ratio`(10)의 기본값입니다.

플러셔가 쓰는 프로세스를 따라잡지 못하면 더티 페이지가 메모리를 채웁니다. 이것을 막는 장치가 앞의 코드에 있던 `balance_dirty_pages_ratelimited()`입니다. 더티 페이지가 배경 임계값과 상한(`vm.dirty_ratio`, 기본 20%)의 중간을 넘으면 `balance_dirty_pages()`가 **쓰는 태스크를 `write()` 안에서 잠깐 재웁니다.** 한 번에 최대 200ms(`MAX_PAUSE`)이고, 더티 페이지가 상한에 가까울수록 길어집니다. 빠른 쓰기가 디스크의 속도로 늦춰지는 자리입니다.

::: {.fig src="writeback-pipeline.svg"}
`write()`에서 디스크까지. 더티 페이지의 양에 따라 플러셔가 깨어나고(10%), 그래도 늘면 쓰는 태스크가 느려집니다(15%부터). `fsync()`는 임계값을 기다리지 않고 해당 파일을 바로 내보냅니다.
:::

`fsync(fd)`는 `vfs_fsync_range()`를 거쳐 `f_op->fsync`를 부릅니다. ext4라면 그 파일의 더티 폴리오를 내보내고 끝나기를 기다린 다음, 저널을 커밋하고, 장치의 쓰기 캐시를 비우는 명령까지 보냅니다. 플러셔가 쓰는 길은 `do_writepages()`가 부르는 `a_ops->writepages()`이고, 거기서 만들어진 bio가 [21장](ch21.html)의 블록 계층으로 내려갑니다.

::: {.lab}
더티 페이지가 쌓였다가 빠지는 것을 봅니다.

```console
$ sysctl vm.dirty_background_ratio vm.dirty_ratio
vm.dirty_background_ratio = 10
vm.dirty_ratio = 20
$ dd if=/dev/zero of=/var/tmp/big bs=1M count=2000 &
$ watch -n 0.5 "grep -E '^(Dirty|Writeback):' /proc/meminfo"
Dirty:            812344 kB
Writeback:         40960 kB
```

`Dirty`는 아직 내보내지 않은 양, `Writeback`은 지금 장치로 나가고 있는 양입니다. `dd`가 끝난 뒤에도 `Dirty`가 한동안 남았다가 줄어듭니다. 어느 프로세스가 `read()`를 많이 부르는지는 VFS의 입구에 탐침을 걸어 셉니다.

```console
# bpftrace -e 'kprobe:vfs_read { @[comm] = count(); }'
```
:::

::: {.old}
예전 자료에는 `pdflush`나 `bdflush`라는 커널 스레드가 더티 페이지를 내보내고, 파일시스템은 `address_space_operations`의 `writepage()`와 `readpage()`를 구현한다고 나옵니다. v7.3에는 그 스레드도, 그 두 콜백도 없습니다. 플러셔는 장치별 `bdi_writeback`의 워크이고, 콜백은 폴리오 단위의 `read_folio()`와 범위 단위의 `readahead()`, `writepages()`입니다.
:::

## 마운트 {#mount}

파일시스템 구현은 자기를 `struct file_system_type`으로 등록합니다. ext4의 것입니다.

```{.c file="fs/ext4/super.c" line="7543"}
static struct file_system_type ext4_fs_type = {
	.owner			= THIS_MODULE,
	.name			= "ext4",
	.init_fs_context	= ext4_init_fs_context,
	.parameters		= ext4_param_specs,
	.kill_sb		= ext4_kill_sb,
	.fs_flags		= FS_REQUIRES_DEV | FS_ALLOW_IDMAP | FS_MGTIME |
				  FS_LBS,
};
```

`register_filesystem()`이 이것을 `/proc/filesystems`에 보이는 전역 목록에 넣습니다.

마운트는 두 단계입니다. 첫 단계는 **슈퍼블록을 만드는 것**입니다. `init_fs_context()`가 `struct fs_context`를 준비하고, 옵션이 하나씩 `parse_param()`으로 들어오고, `get_tree()`가 장치에서 디스크의 슈퍼블록을 읽어 `super_block`과 루트 dentry를 만듭니다. 둘째 단계는 그것을 **디렉터리 트리의 한 곳에 붙이는 것**입니다. 붙인 자리 하나가 `struct mount`이고, 핵심 필드는 `mnt_parent`(부모 마운트), `mnt_mountpoint`(부모 안에서 덮은 dentry), `mnt.mnt_root`(이 마운트의 루트 dentry), `mnt.mnt_sb`(슈퍼블록)입니다.

::: {.fig src="mount-tree.svg"}
마운트 트리. 슈퍼블록 하나가 여러 `mount`로 붙을 수 있습니다(바인드 마운트). 새 마운트 API는 슈퍼블록을 만드는 단계와 트리에 붙이는 단계를 서로 다른 시스템 콜로 나눕니다.
:::

슈퍼블록과 `mount`가 별개이므로 슈퍼블록 하나가 여러 곳에 붙을 수 있습니다. 컨테이너가 호스트의 디렉터리를 자기 트리에 끼워 넣는 바인드 마운트가 그것입니다. 마운트 트리 전체는 마운트 네임스페이스에 속하므로 태스크마다 다른 트리를 볼 수 있습니다. 네임스페이스와 마운트 전파는 [22장](ch22.html)에서 다룹니다.

`mount(2)`는 두 단계를 한 번에 합니다. 옵션은 문자열 하나로 넘기고, 실패하면 `errno` 하나만 돌아옵니다. 옵션 열 개 가운데 무엇이 틀렸는지 알려면 `dmesg`를 뒤져야 했습니다. 5.2에서 들어온 시스템 콜들은 단계를 나눕니다.

| 시스템 콜 | 하는 일 |
|---|---|
| `fsopen("ext4", …)` | 파일시스템 종류를 골라 `fs_context`를 만들고 fd로 돌려줍니다. |
| `fsconfig(fd, FSCONFIG_SET_STRING, …)` | 옵션을 하나씩 넣습니다. 오류 메시지는 그 fd에서 `read()`로 읽습니다. |
| `fsconfig(fd, FSCONFIG_CMD_CREATE, …)` | 슈퍼블록을 만듭니다(`get_tree()`). |
| `fsmount(fd, …)` | 아직 어디에도 붙지 않은 마운트를 만들어 fd로 돌려줍니다. |
| `move_mount(mfd, "", AT_FDCWD, "/mnt", …)` | 그 마운트를 트리에 붙입니다. |

붙이기 전의 마운트를 fd로 쥐고 속성을 다 맞춘 뒤에 한 번에 보이게 할 수 있습니다. 예전 `mount(2)`도 그대로 동작합니다. 내부에서 `do_new_mount()`가 `fs_context`를 만들어 같은 길을 탑니다.

같은 계열의 `mount_setattr()`는 **idmapped 마운트**를 만듭니다. 마운트 하나에 uid·gid 변환표(`struct mnt_idmap`)를 붙여, 그 마운트를 거쳐 볼 때만 파일의 소유자가 다르게 보이게 합니다. 경로 탐색의 권한 검사가 이 변환표를 인자로 받습니다. 같은 디렉터리를 uid 범위가 다른 여러 컨테이너에 `chown` 없이 나눠 줄 때 씁니다. 읽는 쪽에는 `listmount()`와 `statmount()`가 있습니다. 글자로 된 `/proc/self/mountinfo`를 해석하는 대신 마운트 정보를 구조체로 받습니다.

::: {.old}
파일시스템 작성법을 다룬 글은 대개 `file_system_type`에 `.mount = myfs_mount`를 채우고 그 안에서 `mount_bdev()`나 `mount_nodev()`를 부르라고 합니다. v7.3의 `struct file_system_type`에는 `mount` 필드가 없습니다. `Documentation/filesystems/porting.rst`의 표현으로는 "`->get_sb()` and `->mount()` are gone"입니다. 모든 파일시스템이 `init_fs_context`와 `fs_context_operations`(`parse_param`, `get_tree`, `reconfigure`)로 옮겨 갔습니다.
:::

::: {.lab}
마운트 트리를 봅니다.

```console
$ findmnt
TARGET     SOURCE         FSTYPE OPTIONS
/          /dev/nvme0n1p2 ext4   rw,relatime
├─/sys     sysfs          sysfs  rw,nosuid,nodev,noexec,relatime
...
$ head -2 /proc/self/mountinfo
29 1 259:2 / / rw,relatime shared:1 - ext4 /dev/nvme0n1p2 rw
30 29 0:22 / /sys rw,nosuid,nodev,noexec,relatime shared:7 - sysfs sysfs rw
```

`mountinfo`의 첫 두 열이 `struct mount`의 `mnt_id`와 부모의 `mnt_id`입니다. `-`의 앞은 `mount`의 속성이고 뒤의 세 칸(종류, 장치, 옵션)은 `super_block`의 속성입니다.
:::

## 디스크 위의 구조로 가는 길 {#on-disk}

VFS와 페이지 캐시는 "파일의 몇 번째 바이트"로 말하고, 블록 계층은 "장치의 몇 번째 섹터"로 말합니다. 둘 사이의 번역이 파일시스템의 본업입니다. 번역을 묻는 방식에 두 세대가 있습니다.

**버퍼 헤드**(buffer head)는 블록 하나마다 `struct buffer_head`를 두고 페이지에 줄줄이 매답니다. 블록마다 "이 블록은 장치의 어디인가"를 따로 묻습니다. **iomap**은 범위로 묻습니다. "파일의 이 위치부터 이만큼은 어디인가"를 물으면 파일시스템이 연속된 구간 하나로 답합니다.

```{.c file="include/linux/iomap.h" line="130"}
struct iomap {
	u64			addr; /* disk offset of mapping, bytes */
	loff_t			offset;	/* file offset of mapping, bytes */
	u64			length;	/* length of mapping, bytes */
	/* ... */
	struct block_device	*bdev;	/* block device for I/O */
	/* ... */
};
```

"파일의 `offset`부터 `length`바이트는 `bdev`의 `addr`에 있다"는 문장 하나입니다. 파일시스템은 `iomap_ops`의 `iomap_begin()`으로 이 구조체를 채워 주기만 하고, 폴리오를 돌며 bio를 만드는 반복문은 `fs/iomap/`의 공용 코드가 맡습니다. 블록별 상태도 폴리오마다 비트맵 하나로 줄었습니다. `Documentation/filesystems/iomap/operations.rst`는 블록당 부담을 "two bits vs. 104 bytes"로 견줍니다. 범위로 다루는 방식은 4KB보다 큰 폴리오와도 맞물립니다.

v7.3에서 버퍼를 거치는 I/O까지 iomap으로 하는 파일시스템은 XFS, GFS2, zonefs, erofs, exfat, 두 NTFS 드라이버, FUSE입니다. ext4는 직접 I/O에 iomap을 쓰지만 버퍼 쓰기는 아직 버퍼 헤드를 거칩니다(`ext4_block_write_begin()`).

파일 하나를 늘리려면 블록 비트맵, inode, 데이터 블록을 고쳐야 하고, 그 중간에 전원이 나가면 구조가 어긋납니다. ext4(jbd2)와 XFS는 **저널링**으로 막습니다. 고칠 내용을 저널 영역에 먼저 적고 커밋 표시를 쓴 다음 제자리에 반영합니다. btrfs는 **쓰기 시 복사**(copy-on-write)로 막습니다. 있는 블록을 덮어쓰지 않고 새 자리에 쓴 뒤 마지막에 루트 포인터 하나를 바꿉니다.

::: {.note title="v7.3의 fs/ 디렉터리"}
bcachefs는 트리에 없습니다. 6.18에서 소스가 빠졌고 `MAINTAINERS`에는 "Externally maintained" 항목만 남았습니다. NTFS 드라이버는 둘입니다. 기존의 `fs/ntfs3/`에 더해 7.1에서 `fs/ntfs/`가 들어왔습니다. 처음부터 iomap과 폴리오 위에 쓴 읽기·쓰기 드라이버입니다.
:::

## 파일이 아닌 파일 {#pseudo}

저장 장치 없이 `file_operations`만 구현한 파일시스템도 많습니다. 커널이 자기 상태를 내보이거나 설정을 받는 창구로 씁니다.

| 파일시스템 | 마운트 위치 | 내용 |
|---|---|---|
| procfs | `/proc` | 프로세스별 정보, 커널 통계, sysctl(`/proc/sys/`) |
| sysfs | `/sys` | 장치 모델. 커널 객체 하나가 디렉터리, 속성 하나가 파일입니다. |
| tmpfs | `/dev/shm`, `/run` | 페이지 캐시에만 있는 파일. 메모리가 모자라면 스왑으로 갑니다. |
| debugfs, tracefs | `/sys/kernel/debug`, `/sys/kernel/tracing` | 디버깅 정보, ftrace 제어 |
| cgroup2, bpffs | `/sys/fs/cgroup`, `/sys/fs/bpf` | cgroup 트리([22장](ch22.html)), BPF 객체([24장](ch24.html)) |
| pidfs, nsfs | (마운트되지 않음) | pidfd와 네임스페이스 fd 뒤의 inode |

이 책의 "직접 확인하기"가 읽는 `/proc` 파일들은 디스크에 없습니다. `/proc/softirqs`의 구현이 이것입니다.

```{.c file="fs/proc/softirqs.c" line="11"}
static int show_softirqs(struct seq_file *p, void *v)
{
	int i, j;

	seq_puts(p, "                    ");
	for_each_possible_cpu(i)
		seq_printf(p, "CPU%-8d", i);
	seq_putc(p, '\n');

	for (i = 0; i < NR_SOFTIRQS; i++) {
		seq_printf(p, "%12s:", softirq_to_name[i]);
		for_each_possible_cpu(j)
			seq_put_decimal_ull_width(p, " ", kstat_softirqs_cpu(i, j), 10);
		seq_putc(p, '\n');
	}
	return 0;
}
```

같은 파일의 초기화 함수가 `proc_create_single("softirqs", 0, NULL, show_softirqs)`로 이름과 `show` 콜백을 등록합니다. 누군가 이 파일을 `read()`하면 그림 20-5의 길로 `seq_read_iter()`가 불립니다. **seq_file**은 "글자를 찍어 내는 콜백"과 "유저가 임의의 크기로 나눠 읽는 `read()`" 사이를 맞춰 주는 도우미입니다. 커널 버퍼를 잡고, `show()`를 불러 채우고, 넘치면 버퍼를 키워 다시 부르고, 유저가 요청한 만큼 잘라 복사합니다. 내용이 읽는 순간에 만들어지므로 `ls -l`에 나오는 크기는 0입니다.

sysfs와 cgroup2는 **kernfs**라는 공용 뼈대 위에 있습니다. 디렉터리 트리와 dentry·inode 관리는 kernfs가 하고, sysfs는 "kobject 하나에 디렉터리 하나, 속성 하나에 값 하나"라는 규칙을 얹습니다.

::: {.design}
"모든 것이 파일"은 **재사용 전략**입니다. 커널 객체를 fd로 내보이면 이미 있는 장치가 전부 따라옵니다. 권한 검사, 프로세스 종료 때의 정리, `fork()`로의 상속, 유닉스 소켓으로 넘기기, `epoll`·io_uring으로 기다리기가 그렇습니다. 그래서 새 기능은 새 ID 체계 대신 fd로 나옵니다. eventfd, timerfd, pidfd, 마운트 컨텍스트, BPF 맵, io_uring 인스턴스가 모두 fd입니다. PID 숫자는 재사용되어 엉뚱한 프로세스를 가리킬 수 있지만 pidfd는 `struct file`이 대상을 붙들고 있으므로 그럴 수 없습니다.
:::

## 정리 {#summary}

- VFS는 파일시스템을 `super_block`, `inode`, `dentry`, `file` 네 객체로 봅니다. 이름, 파일, 열린 파일은 수명과 개수가 달라서 따로 있습니다.
- fd는 `fdtable`의 배열 인덱스입니다. 조회는 RCU로 락 없이 하고, fd 테이블을 혼자 쓰는 프로세스는 참조 카운트도 올리지 않습니다.
- 경로 탐색은 성분마다 dcache를 조회합니다. 위치는 `(마운트, dentry)` 쌍입니다. 먼저 dentry에 쓰지 않는 RCU-walk로 시도하고, 안 되면 ref-walk로 넘어갑니다.
- `open()` 때 inode의 `i_fop`가 `file->f_op`로 복사됩니다. 그 뒤의 `read()`·`write()`는 이 테이블에서 갈립니다.
- 디스크 파일의 `read()`는 페이지 캐시에서 복사하고, `write()`는 페이지 캐시에 쓰고 더티 표시만 한 채 돌아옵니다. 더티 페이지는 장치별 플러셔가 내보내고, 너무 많으면 쓰는 태스크가 늦춰집니다.
- 마운트는 슈퍼블록 만들기와 트리에 붙이기의 두 단계이고, 새 마운트 API는 둘을 별개의 시스템 콜로 나눕니다.

## 확인 문제 {#quiz}

::: {.q}
프로세스가 같은 파일을 `open()`으로 두 번 열어 fd 3과 4를 얻고, `dup(3)`으로 fd 5를 얻었습니다. fd 3으로 100바이트를 읽은 뒤 fd 4와 fd 5로 각각 `read()`를 하면 어느 위치부터 읽힙니까?

::: {.a}
fd 4는 0부터, fd 5는 100부터 읽힙니다. `open()`은 부를 때마다 `struct file`을 새로 만들고, 읽기 위치 `f_pos`는 `file`에 있습니다. fd 3과 4는 서로 다른 `file`을 가리키므로 위치가 따로 움직입니다. `dup()`은 `fdtable`의 새 칸에 같은 `file` 포인터를 넣고 참조 카운트(`f_ref`)만 올립니다. fd 3과 5는 `f_pos`를 함께 씁니다.
:::
:::

::: {.q}
RCU-walk 도중에 dcache에 없는 이름을 만났습니다. 커널은 어떻게 합니까? 처음부터 다시 시작하지 않아도 되는 까닭은 무엇입니까?

::: {.a}
`lookup_fast()`가 `try_to_unlazy()`를 부릅니다. 지금 서 있는 dentry와 마운트에 참조를 얻고, 그 dentry의 `d_seq`가 처음 읽은 값과 같은지 확인한 다음 RCU 읽기 구간을 벗어납니다. 성공하면 여기까지 걸어온 위치가 유효하고 참조도 쥐고 있으므로, 그 자리에서 ref-walk로 이어 가며 `lookup_slow()`로 디스크를 읽습니다. 실패하면 `-ECHILD`가 돌아가 처음부터 다시 걷습니다.
:::
:::

::: {.q}
프로그램이 `write()`로 1GB를 연달아 씁니다. 처음에는 `write()`가 빠르게 돌아오다가 어느 순간부터 느려집니다. 무슨 일이 일어난 것입니까?

::: {.a}
처음에는 페이지 캐시에 복사만 하므로 메모리 복사 속도로 돌아옵니다. 더티 페이지가 `vm.dirty_background_ratio`(10%)를 넘으면 플러셔가 깨어나지만 쓰는 쪽은 아직 느려지지 않습니다. 더티 페이지가 배경 임계값과 `vm.dirty_ratio`(20%)의 중간을 넘으면, `generic_perform_write()`가 매번 부르는 `balance_dirty_pages_ratelimited()`가 쓰는 태스크를 잠깐씩 재웁니다. 이때부터 `write()`의 속도는 플러셔가 디스크로 내보내는 속도에 맞춰집니다.
:::
:::

::: {.q}
파이프의 fd에 `lseek()`을 부르면 `ESPIPE`가 나옵니다. 파이프 코드에는 이 오류를 돌려주는 줄이 없습니다. 어디서 나옵니까?

::: {.a}
`pipeanon_fops`에는 `.llseek`이 없습니다. `do_dentry_open()`은 파일을 열 때 `FMODE_LSEEK`을 세웠다가 `f_op->llseek`이 `NULL`이면 지웁니다. `lseek()`이 부르는 `vfs_llseek()`은 이 비트가 없으면 `f_op`를 부르지 않고 `-ESPIPE`를 돌려줍니다. 구현되지 않은 연산의 기본 동작을 VFS가 정하는 예입니다.
:::
:::

## 용어 {#terms}

::: {.terms}
VFS (virtual filesystem switch)
:   시스템 콜과 개별 파일시스템 사이에서 공통 객체와 ops 테이블을 정의하는 층.

inode
:   파일 하나의 속성과 데이터 위치를 담는 객체. 이름은 갖지 않는다.

dentry
:   디렉터리 안의 이름 하나를 inode에 잇는 객체. 경로 탐색의 캐시 단위다.

dcache (dentry cache)
:   `(부모 dentry, 이름)`으로 dentry를 찾는 전역 해시 테이블과 LRU.

음성 dentry (negative dentry)
:   "이 이름은 없다"는 탐색 결과를 캐시한, inode 포인터가 `NULL`인 dentry.

file_operations
:   열린 파일에 대한 `read`, `write`, `mmap` 등의 구현을 담은 함수 포인터 구조체.

RCU-walk
:   dentry에 락을 잡거나 참조를 올리지 않고 `d_seq` 검증만으로 진행하는 경로 탐색 방식.

writeback
:   페이지 캐시의 더티 폴리오를 저장 장치로 내보내는 일.

미리 읽기 (readahead)
:   순차 읽기를 예상해 요청보다 뒤쪽 범위까지 페이지 캐시에 올려 두는 일.

iomap
:   파일의 범위를 장치의 연속 구간으로 번역하는 인터페이스와 그 위의 공용 I/O 코드.

seq_file
:   글자를 찍는 `show` 콜백으로 가상 파일의 `read()`를 구현하게 해 주는 도우미.
:::
