RCU

읽는 쪽이 아무것도 기다리지 않는 동기화

Linux v7.3 기준약 50분
읽는 소스security/device_cgroup.cinclude/linux/rcupdate.hkernel/rcu/tree_plugin.hkernel/rcu/Kconfiginclude/linux/rculist.hkernel/rcu/tree.hkernel/rcu/tree.cnet/core/neighbour.c

라우팅 테이블, PID 표, 디렉터리 캐시는 쉴 새 없이 읽히고 가끔 고쳐집니다. 이런 데이터에 읽기-쓰기 락을 걸면, 아무도 쓰지 않는데도 읽는 CPU끼리 락 워드를 두고 다툽니다. RCU는 읽는 쪽이 락을 잡지도, 기다리지도, 공유 메모리에 쓰지도 않게 합니다. 대신 한 가지 어려운 질문을 떠안습니다. 누군가 아직 읽고 있을지 모르는 옛 데이터를 언제 지워도 되는가.

이 장에서 답하는 질문
  • rwlock의 읽기는 왜 CPU가 늘수록 느려지고, RCU의 읽기는 왜 그렇지 않은가?
  • rcu_read_lock(), rcu_dereference(), rcu_assign_pointer()는 각각 무엇으로 펼쳐지는가?
  • 유예 기간은 무엇을 기다리고, 커널은 그것이 끝났음을 어떻게 아는가?
  • 선점 가능한 커널에서 읽기 구간 안의 태스크가 선점당하면 어떻게 추적하는가?
  • call_rcu()로 맡긴 콜백은 누가, 언제 실행하는가?
  • RCU로 찾은 객체를 읽기 구간 밖에서도 쓰려면 무엇이 더 필요한가?

16.1읽기가 압도적으로 많을 때#

14장에서 본 rwlock은 읽는 쪽 여럿을 동시에 들입니다. 그런데 read_lock()은 락 워드의 읽는 쪽 수를 원자 연산으로 1 올립니다. 읽기인데도 공유 메모리에 씁니다. 그 워드가 든 캐시 라인은 읽는 CPU가 바뀔 때마다 그 CPU로 옮겨 가야 합니다. 임계 구역이 포인터 몇 번 따라가는 정도로 짧으면, 락을 잡고 푸는 비용이 본래 하려던 일보다 커집니다. CPU가 많을수록 더 나빠집니다.

RCU(read-copy-update)의 출발점은 이것입니다. 읽는 쪽은 공유 메모리에 아무것도 쓰지 않는다. 그러면 읽는 쪽을 막을 방법도 없으므로, 고치는 쪽이 방식을 바꿔야 합니다.

  1. 고칠 객체를 복사해서 복사본을 고칩니다. 원본은 건드리지 않습니다.
  2. 객체를 가리키던 포인터를 복사본으로 바꿔 끼웁니다. 포인터 하나를 쓰는 것은 원자적이므로, 읽는 쪽은 옛것 전체를 보거나 새것 전체를 봅니다. 고치다 만 모습은 보지 않습니다.
  3. 원본을 해제합니다. 다만 바꿔 끼우기 전에 원본을 집어 든 읽는 쪽이 아직 그것을 쓰고 있을 수 있습니다. 그들이 모두 끝날 때까지 기다린 뒤에 해제합니다.

이름의 read, copy, update가 이 순서입니다. 1과 2는 쉽습니다. RCU의 구현은 거의 전부 3, 곧 "모두 끝났다"를 읽는 쪽에 비용을 지우지 않고 알아내는 일입니다.

16.2세 가지 동작: 읽기, 게시, 회수#

동작 함수 하는 일
읽기 rcu_read_lock() / rcu_read_unlock() 읽기 구간의 시작과 끝을 표시
rcu_dereference(p) RCU로 보호되는 포인터를 읽기
게시 rcu_assign_pointer(p, v) 새 객체를 읽는 쪽에 보이게 하기
회수 synchronize_rcu() 지금 진행 중인 읽기 구간이 모두 끝날 때까지 잠들기

kfree_rcu(ptr, field) 그때가 되면 kfree(ptr) 해 달라고 맡기기

실제 코드를 봅니다. cgroup v1의 장치 컨트롤러는 "이 cgroup이 접근할 수 있는 장치" 목록을 리스트로 갖고, 장치 파일에 접근할 때마다 그 리스트를 훑습니다. 읽기는 매우 잦고 고치는 일은 관리자가 설정을 바꿀 때뿐입니다.

security/device_cgroup.cv7.3
static int devcgroup_legacy_check_permission(short type, u32 major, u32 minor,
                    short access)
{
    struct dev_cgroup *dev_cgroup;
    bool rc;

    rcu_read_lock();
    dev_cgroup = task_devcgroup(current);
    if (dev_cgroup->behavior == DEVCG_DEFAULT_ALLOW)
        /* Can't match any of the exceptions, even partially */
        rc = !match_exception_partial(&dev_cgroup->exceptions,
                          type, major, minor, access);
    else
        /* Need to match completely one exception to be allowed */
        rc = match_exception(&dev_cgroup->exceptions, type, major,
                     minor, access);
    rcu_read_unlock();

    if (!rc)
        return -EPERM;

    return 0;
}

읽는 쪽은 rcu_read_lock()과 rcu_read_unlock() 사이에서 리스트를 훑습니다. match_exception() 안의 순회는 list_for_each_entry_rcu()입니다. 락을 기다리는 곳이 없습니다.

security/device_cgroup.cv7.3
/*
 * called under devcgroup_mutex
 */
static void dev_exception_rm(struct dev_cgroup *dev_cgroup,
                 struct dev_exception_item *ex)
{
    struct dev_exception_item *walk, *tmp;

    lockdep_assert_held(&devcgroup_mutex);

    list_for_each_entry_safe(walk, tmp, &dev_cgroup->exceptions, list) {
        if (walk->type != ex->type)
            continue;
        if (walk->major != ex->major)
            continue;
        if (walk->minor != ex->minor)
            continue;

        walk->access &= ~ex->access;
        if (!walk->access) {
            list_del_rcu(&walk->list);
            kfree_rcu(walk, rcu);
        }
    }

읽을 곳은 세 군데입니다.

  • 고치는 쪽끼리는 여전히 락이 필요합니다. 주석대로 이 함수는 devcgroup_mutex를 쥔 채 불립니다. RCU는 읽는 쪽과 고치는 쪽 사이만 풉니다.
  • list_del_rcu()는 노드를 리스트에서 떼어 내지만, 그 노드를 지나던 읽는 쪽이 길을 잃지 않게 합니다.
  • kfree_rcu(walk, rcu)는 지금 해제하지 않습니다. rcu는 구조체 안에 넣어 둔 struct rcu_head 필드의 이름입니다. 그 필드를 써서 "유예 기간 뒤에 해제할 것" 목록에 올립니다.
핵심

RCU가 보장하는 것은 하나입니다. 읽기 구간 안에서 rcu_dereference()로 얻은 포인터는 그 읽기 구간이 끝날 때까지 해제되지 않습니다. 최신 데이터를 본다는 보장은 없습니다. 읽는 쪽은 방금 리스트에서 빠진 노드를 볼 수 있습니다.

16.3매크로를 펼쳐 보면#

게시와 읽기

include/linux/rcupdate.hv7.3
#define rcu_assign_pointer(p, v)                          \
context_unsafe(                               \
    uintptr_t _r_a_p__v = (uintptr_t)(v);                     \
    rcu_check_sparse(p, __rcu);                       \
                                          \
    if (__builtin_constant_p(v) && (_r_a_p__v) == (uintptr_t)NULL)        \
        WRITE_ONCE((p), (typeof(p))(_r_a_p__v));              \
    else                                      \
        smp_store_release(&p, RCU_INITIALIZER((typeof(p))_r_a_p__v)); \
)

rcu_assign_pointer()는 smp_store_release()로 끝납니다. 새 객체의 필드를 채운 쓰기들이 포인터 쓰기보다 먼저 다른 CPU에 보이도록 순서를 강제합니다. 이것이 없으면 읽는 쪽이 포인터는 새것인데 내용은 아직 초기화되지 않은 객체를 볼 수 있습니다. 메모리 순서와 배리어는 13장에서 다뤘습니다.

include/linux/rcupdate.hv7.3
#define __rcu_dereference_check(p, local, c, space) \
({ \
    /* Dependency order vs. p above. */ \
    typeof(*p) *local = (typeof(*p) *__force)READ_ONCE(p); \
    RCU_LOCKDEP_WARN(!(c), "suspicious rcu_dereference_check() usage"); \
    rcu_check_sparse(p, space); \
    ((typeof(*p) __force __kernel *)(local)); \
})

rcu_dereference()의 알맹이는 READ_ONCE() 한 번입니다. 컴파일러가 포인터를 두 번 읽어 그사이 값이 바뀌는 일을 막습니다. 나머지는 검사입니다. RCU_LOCKDEP_WARN은 읽기 구간 밖에서 불렀을 때 lockdep이 경고하게 하고, rcu_check_sparse는 포인터가 __rcu로 선언되어 있는지 정적 검사 도구가 확인하게 합니다. 두 매크로는 기계어보다 문서로서의 역할이 큽니다. 어느 포인터가 RCU 규칙을 따르는지 코드에 표시해 둡니다.

rcu_read_lock()은 무엇을 하는가

구현이 둘입니다. 먼저 선점 불가 RCU입니다.

include/linux/rcupdate.hv7.3
static inline void __rcu_read_lock(void)
{
    preempt_disable();
}

static inline void __rcu_read_unlock(void)
{
    if (IS_ENABLED(CONFIG_RCU_STRICT_GRACE_PERIOD))
        rcu_read_unlock_strict();
    preempt_enable();
}

선점을 끄는 것이 전부입니다. 읽는 쪽이 누구인지 어디에도 적지 않습니다. 그래도 되는 까닭은 유예 기간 절에서 밝혀집니다. 다음은 선점 가능한 RCU입니다.

kernel/rcu/tree_plugin.hv7.3
static void rcu_preempt_read_enter(void)
{
    WRITE_ONCE(current->rcu_read_lock_nesting, READ_ONCE(current->rcu_read_lock_nesting) + 1);
}

/* ... */
void __rcu_read_lock(void)
{
    rcu_preempt_read_enter();
    /* ... */
    barrier();  /* critical section after entry code. */
}

이쪽은 선점을 끄지 않습니다. task_struct의 중첩 카운터를 1 올릴 뿐입니다. 이 카운터는 그 태스크만 건드리므로 원자 연산도 아니고 공유 메모리도 아닙니다. 읽기 구간 안에서 선점당할 수 있고, 그래서 읽기 구간이 길어도 실시간 태스크의 지연이 늘지 않습니다.

어느 쪽이 쓰이는지는 Kconfig가 정합니다.

kernel/rcu/Kconfigv7.3
config PREEMPT_RCU
    bool
    default y if (PREEMPT || PREEMPT_RT || PREEMPT_DYNAMIC)
    select TREE_RCU

PREEMPT_DYNAMIC으로 빌드한 커널은 선점 가능한 RCU를 씁니다. 배포판 커널이 대개 이 경우입니다. 6장의 PREEMPT_LAZY만 고르고 PREEMPT_DYNAMIC을 끈 빌드는 이 조건에 걸리지 않습니다. 커널은 선점 가능한데 RCU 읽기 구간은 preempt_disable()로 선점을 막는 조합이 됩니다.

예전 자료와 다른 점

많은 자료가 "rcu_read_lock()은 아무 코드도 만들지 않는다"고 씁니다. 선점을 지원하지 않는 커널에서는 맞는 말이었습니다. 그런 빌드에서는 preempt_disable()이 명령어를 하나도 만들지 않았기 때문입니다. v7.3의 x86과 arm64에는 그런 빌드가 없습니다. 6장에서 본 대로 NONE과 VOLUNTARY 선택지가 사라졌고, 선점 카운터가 항상 있습니다. rcu_read_lock()은 선점 카운터나 태스크의 중첩 카운터 가운데 하나를 올립니다. 달라지지 않은 것은 핵심입니다. 어느 구현이든 다른 CPU와 공유하는 메모리에는 쓰지 않습니다.

리스트에서 떼어 내기

include/linux/rculist.hv7.3
static inline void list_del_rcu(struct list_head *entry)
{
    __list_del_entry(entry);
    entry->prev = LIST_POISON2;
}

보통의 list_del()은 떼어 낸 노드의 next와 prev를 모두 독 값으로 덮어써서 잘못된 접근을 드러냅니다. list_del_rcu()는 prev만 덮어씁니다. next는 그대로 둡니다.

RCU 리스트 순회는 앞으로만 갑니다. next만 살아 있으면 읽는 쪽은 안전합니다.

16.4유예 기간과 정지 상태#

유예 기간(grace period)은 "시작하는 순간에 읽기 구간 안에 있던 읽는 쪽이 모두 빠져나갈 때까지"의 시간입니다. 유예 기간이 한 번 지나면, 그 전에 리스트에서 떼어 낸 객체를 보고 있는 읽는 쪽은 없습니다. 유예 기간이 시작된 뒤에 들어온 읽는 쪽은 기다리지 않습니다. 그들은 떼어 낸 객체를 찾을 길이 없기 때문입니다.

커널은 읽는 쪽을 하나하나 세지 않습니다. 대신 CPU마다 정지 상태(quiescent state)를 지났는지 봅니다. 정지 상태는 "이 CPU가 지금 읽기 구간 밖에 있음이 확실한 순간"입니다.

선점 불가 RCU에서는 정지 상태를 찾기 쉽습니다. 읽기 구간은 선점이 꺼진 구간이므로, 그 안에서는 컨텍스트 스위치가 일어나지 않습니다. 뒤집으면 컨텍스트 스위치가 일어났다면 그 CPU는 읽기 구간 밖에 있었습니다. 유저 모드에서 실행 중이거나 idle인 CPU도 커널의 읽기 구간 안일 수 없습니다. 스케줄러와 틱 핸들러가 이 사건들을 RCU에 알립니다. 이것이 앞에서 미뤄 둔 답입니다. 읽는 쪽이 아무 표시도 남기지 않아도 되는 까닭은, 스케줄러가 어차피 하는 일에서 필요한 정보가 나오기 때문입니다.

읽기 구간 안에서 선점당한 태스크

선점 가능한 RCU에서는 이 논리가 깨집니다. 읽기 구간 안의 태스크가 선점당하면, 그 CPU에서는 컨텍스트 스위치가 일어났는데도 읽기 구간이 끝나지 않았습니다. 읽는 쪽이 CPU가 아니라 태스크를 따라다닙니다.

kernel/rcu/tree_plugin.hv7.3
void rcu_note_context_switch(bool preempt)
{
    struct task_struct *t = current;
    struct rcu_data *rdp = this_cpu_ptr(&rcu_data);
    struct rcu_node *rnp;
    /* ... */
    if (rcu_preempt_depth() > 0 &&
        !t->rcu_read_unlock_special.b.blocked) {

        /* Possibly blocking in an RCU read-side critical section. */
        rnp = rdp->mynode;
        raw_spin_lock_rcu_node(rnp);
        t->rcu_read_unlock_special.b.blocked = true;
        t->rcu_blocked_node = rnp;
        /* ... */
        rcu_preempt_ctxt_queue(rnp, rdp);
    } else {
        rcu_preempt_deferred_qs(t);
    }
    /* ... */
    rcu_qs();
    /* ... */
}

스케줄러에 들어올 때 불리는 함수입니다. 중첩 카운터가 0보다 크면, 곧 읽기 구간 안에서 CPU를 내주는 것이면, 태스크를 rcu_node의 blkd_tasks 리스트에 올립니다. 그런 다음에야 CPU의 정지 상태를 보고합니다(rcu_qs()). CPU는 풀려나지만 태스크가 리스트에 남아 유예 기간을 붙잡습니다. 태스크가 다시 실행되어 가장 바깥의 rcu_read_unlock()에 이르면, rcu_read_unlock_special에 표시가 있는 것을 보고 리스트에서 자기를 뺍니다.

읽기 구간의 빠른 경로는 여전히 카운터 증감뿐입니다. 공유 자료구조를 건드리는 비용은 읽기 구간 안에서 선점당하는 드문 경우에만 치릅니다.

그 태스크의 우선순위가 낮아 오래 실행되지 못하면 유예 기간도 끝나지 않고, 해제를 기다리는 메모리가 쌓입니다. CONFIG_RCU_BOOST는 유예 기간을 오래 막고 있는 태스크의 우선순위를 올립니다. 15장의 rt_mutex를 빌려 쓰는 방식입니다.

16.5Tree RCU: 정지 상태를 모으는 트리#

유예 기간을 끝내려면 "모든 CPU가 정지 상태를 지났는가"를 알아야 합니다. CPU마다 비트 하나를 두고 지나간 CPU가 자기 비트를 지우면 됩니다. 문제는 그 비트맵을 지키는 락입니다. CPU가 수백 개면 모든 CPU가 유예 기간마다 전역 락 하나를 잡게 됩니다. 읽는 쪽의 경합을 없애려고 만든 장치가 스스로 경합을 만듭니다.

Tree RCU는 비트맵을 트리로 나눕니다.

kernel/rcu/tree.hv7.3
struct rcu_node {
    raw_spinlock_t __private lock;  /* Root rcu_node's lock protects */
                    /*  some rcu_state fields as well as */
                    /*  following. */
    unsigned long gp_seq;   /* Track rsp->gp_seq. */
    /* ... */
    unsigned long qsmask;   /* CPUs or groups that need to switch in */
                /*  order for current grace period to proceed.*/
                /*  In leaf rcu_node, each bit corresponds to */
                /*  an rcu_data structure, otherwise, each */
                /*  bit corresponds to a child rcu_node */
                /*  structure. */
    /* ... */
    unsigned long grpmask;  /* Mask to apply to parent qsmask. */
                /*  Only one bit will be set in this mask. */
    /* ... */
    struct rcu_node *parent;
    struct list_head blkd_tasks;
                /* Tasks blocked in RCU read-side critical */
                /*  section.  Tasks are placed at the head */
                /*  of this list and age towards the tail. */
    struct list_head *gp_tasks;
                /* Pointer to the first task blocking the */
                /*  current grace period, or NULL if there */
                /*  is no such task. */
    /* ... */
} ____cacheline_internodealigned_in_smp;

qsmask가 "아직 정지 상태를 보고하지 않은 것들"입니다. 잎에서는 비트 하나가 CPU 하나이고, 안쪽 노드에서는 비트 하나가 자식 노드 하나입니다. 앞 절의 blkd_tasks도 여기 있습니다.

kernel/rcu/tree.cv7.3
static void rcu_report_qs_rnp(unsigned long mask, struct rcu_node *rnp,
                  unsigned long gps, unsigned long flags)
    __releases(rnp->lock)
{
    /* ... */
    /* Walk up the rcu_node hierarchy. */
    for (;;) {
        /* ... */
        WRITE_ONCE(rnp->qsmask, rnp->qsmask & ~mask);
        /* ... */
        if (rnp->qsmask != 0 || rcu_preempt_blocked_readers_cgp(rnp)) {

            /* Other bits still set at this level, so done. */
            raw_spin_unlock_irqrestore_rcu_node(rnp, flags);
            return;
        }
        rnp->completedqs = rnp->gp_seq;
        mask = rnp->grpmask;
        if (rnp->parent == NULL) {

            /* No more levels.  Exit loop holding root lock. */

            break;
        }
        raw_spin_unlock_irqrestore_rcu_node(rnp, flags);
        rnp_c = rnp;
        rnp = rnp->parent;
        raw_spin_lock_irqsave_rcu_node(rnp, flags);
        oldmask = READ_ONCE(rnp_c->qsmask);
    }
    /* ... */
    rcu_report_qs_rsp(flags); /* releases rnp->lock. */
}

자기 비트를 지우고, 이 노드에 다른 비트가 남아 있거나 읽기 구간 안에서 선점당한 태스크가 남아 있으면 거기서 끝냅니다. 노드가 비었을 때만 부모로 올라가 이 노드의 비트(grpmask)를 지웁니다. 잎 하나에 CPU가 16개라면 16번의 보고 가운데 15번은 잎의 락만 잡고 끝납니다. 뿌리까지 올라가는 것은 유예 기간마다 한 번, 마지막 CPU뿐입니다.

유예 기간을 시작하고 끝내는 일은 전용 커널 스레드가 맡습니다. ps에 rcu_preempt(선점 불가 RCU에서는 rcu_sched)로 보이는 스레드입니다.

kernel/rcu/tree.cv7.3
static int __noreturn rcu_gp_kthread(void *unused)
{
    rcu_bind_gp_kthread();
    for (;;) {

        /* Handle grace-period start. */
        for (;;) {
            /* ... */
            swait_event_idle_exclusive(rcu_state.gp_wq,
                     READ_ONCE(rcu_state.gp_flags) &
                     RCU_GP_FLAG_INIT);
            /* ... */
            if (rcu_gp_init())
                break;
            /* ... */
        }

        /* Handle quiescent-state forcing. */
        rcu_gp_fqs_loop();

        /* Handle grace-period end. */
        WRITE_ONCE(rcu_state.gp_state, RCU_GP_CLEANUP);
        rcu_gp_cleanup();
        WRITE_ONCE(rcu_state.gp_state, RCU_GP_CLEANED);
    }
}

세 단계입니다. rcu_gp_init()은 트리를 훑으며 모든 qsmask를 온라인 CPU로 채웁니다. rcu_gp_fqs_loop()는 보고를 기다리다가, 일정 시간이 지나도 보고하지 않는 CPU를 직접 살핍니다. idle이거나 유저 모드에 머무는 CPU는 스스로 보고하러 오지 않습니다. 틱조차 꺼져 있을 수 있습니다(8장). 그런 CPU는 깨우지 않고, 유예 기간 스레드가 그 CPU의 상태 카운터를 읽어 대신 보고합니다. 커널 안에서 오래 버티는 CPU에는 재스케줄을 요청합니다. rcu_gp_cleanup()은 유예 기간 번호(gp_seq)를 올려 끝을 알립니다.

유예 기간은 짧아도 틱 몇 번, 곧 밀리초 단위의 시간이 걸립니다. 기다릴 수 없는 호출자를 위해 synchronize_rcu_expedited()가 있습니다. 모든 CPU에 IPI를 보내 정지 상태를 재촉합니다. 빠르지만 다른 CPU의 일을 끊으므로 흔한 경로에서는 쓰지 않습니다.

설계 노트

"모두에게서 응답을 모은다"는 작업을 트리로 나누는 기법입니다. 각 참가자는 자기 그룹의 락만 잡고, 그룹이 끝났을 때만 한 단계 위로 올라갑니다. 락 하나를 다투는 참가자 수가 전체 CPU 수가 아니라 팬아웃으로 묶입니다. 캐시 지역성도 따라옵니다. 같은 잎에 속한 CPU들만 그 잎의 캐시 라인을 만집니다. 락 경합을 줄이는 방법이 "락을 더 빠르게"가 아니라 "대부분의 일이 좁은 범위에서 끝나게"인 사례입니다.

16.6콜백의 일생#

synchronize_rcu()는 유예 기간이 끝날 때까지 호출자를 재웁니다. 잠들 수 없는 곳이나 기다리기 싫은 곳에서는 call_rcu()로 콜백을 맡깁니다.

콜백 리스트는 CPU마다 따로 있어, call_rcu()는 보통 인터럽트만 끄고 자기 CPU의 리스트 끝에 붙입니다. 리스트 하나를 포인터 네 개로 구간을 나눕니다. 유예 기간이 시작되면 그 전에 들어온 콜백이 WAIT으로, 끝나면 DONE으로 넘어갑니다. 콜백마다 "어느 유예 기간을 기다리는가"를 따로 적지 않고 구간 경계만 옮기므로, 콜백이 수만 개여도 유예 기간이 바뀔 때 드는 비용은 일정합니다.

DONE 구간의 콜백은 기본적으로 그 CPU의 RCU_SOFTIRQ에서 실행됩니다(11장). PREEMPT_RT에서는 softirq 대신 CPU별 스레드 rcuc/N이 맡습니다. 지연에 민감한 CPU에서 콜백 실행을 아예 걷어 낼 수도 있습니다. 부팅 인자 rcu_nocbs=로 지정한 CPU의 콜백은 rcuop/N 스레드가 대신 실행하고, 그 스레드는 다른 CPU에 배치할 수 있습니다.

콜백이 kfree() 한 줄뿐인 경우가 많아서 kfree_rcu()가 따로 있습니다. v7.3의 구현은 mm/slab_common.c에 있고, 해제할 포인터를 CPU별 배열에 모았다가 유예 기간 뒤에 묶음으로 슬랩 할당자에 돌려줍니다.

v7.3에는 급하지 않은 콜백을 더 미루는 장치도 있습니다. CONFIG_RCU_LAZY를 켜면 콜백을 떼어 낸 CPU에서는 call_rcu()로 맡긴 콜백을 위해 유예 기간을 바로 시작하지 않고, 몇 초 동안 모으거나 메모리가 부족해질 때까지 기다립니다. idle에 가까운 기기에서 유예 기간 스레드가 깨어나는 횟수를 줄여 전력을 아끼려는 것입니다. 깨우기처럼 미루면 안 되는 콜백은 call_rcu_hurry()를 씁니다.

주의

call_rcu()는 메모리를 나중에 해제합니다. 객체를 만드는 속도가 유예 기간이 도는 속도보다 빠르면 해제를 기다리는 메모리가 쌓입니다. 유저가 시스템 콜을 반복해 그런 객체를 마음대로 만들 수 있는 경로라면 메모리 고갈 공격이 됩니다. 커널은 CPU의 콜백이 일정 수(기본 10000개)를 넘으면 한 번에 실행하는 콜백 수의 제한을 풀어 따라잡지만, 근본적인 해법은 만드는 쪽에 상한을 두는 것입니다.

16.7변종: SRCU와 Tasks RCU#

RCU의 읽기 구간에서는 잠들 수 없습니다. 선점 불가 구현에서는 선점이 꺼져 있고, 선점 가능 구현에서도 스스로 잠드는 것은 금지입니다. 읽기 구간 하나가 길어지면 시스템 전체의 유예 기간이 늦어지기 때문입니다. 이 제약이 맞지 않는 곳을 위해 변종이 있습니다.

SRCU(sleepable RCU)는 읽기 구간에서 잠들 수 있습니다. 대신 쓰는 곳마다 struct srcu_struct를 따로 둡니다. 유예 기간이 도메인별로 돌아가므로, 한 도메인의 느린 읽는 쪽이 다른 도메인을 늦추지 않습니다. 읽는 쪽은 CPU별 카운터를 올리고 메모리 배리어를 한 번 실행합니다. 보통의 RCU보다 비싸지만 여전히 공유 캐시 라인에는 쓰지 않습니다. srcu_read_lock()이 돌려주는 인덱스를 srcu_read_unlock()에 넘겨야 합니다.

Tasks RCU는 읽기 구간 표시가 아예 없습니다. ftrace와 BPF는 실행 중에 트램펄린이라는 작은 코드 조각을 만들어 함수 진입점에 끼워 넣습니다. 트램펄린을 해제하려면 그 안을 실행 중인 태스크가 없음을 알아야 하는데, 트램펄린 안에 rcu_read_lock()을 넣을 수는 없습니다. 태스크가 트램펄린의 첫 명령어에 닿기 직전이나 마지막 명령어를 막 지난 순간도 보호해야 하기 때문입니다. Tasks RCU는 "모든 태스크가 자발적으로 컨텍스트 스위치를 한 번씩 했다"를 유예 기간으로 삼습니다. 선점당한 태스크는 트램펄린 안에 멈춰 있을 수 있으므로 선점은 치지 않습니다.

Tasks Trace RCU는 잠들 수 있는 BPF 프로그램을 위한 것입니다. v7.3에서는 SRCU의 빠른 읽기 경로 위에 얇게 구현되어 있습니다.

예전 자료와 다른 점

옛 자료에는 RCU가 셋으로 나옵니다. rcu_read_lock()의 RCU, softirq를 끈 구간이 읽기 구간인 RCU-bh, 선점을 끈 구간이 읽기 구간인 RCU-sched입니다. 유예 기간도 synchronize_rcu(), synchronize_rcu_bh(), synchronize_sched()로 따로였고, 짝을 잘못 맞추면 버그였습니다. Documentation/RCU/checklist.rst에 따르면 4.20부터 커널은 한 가지 RCU만 구현합니다. rcu_read_lock_bh()와 rcu_read_lock_sched()는 남아 있지만 기다리는 쪽은 synchronize_rcu() 하나입니다. 소스 주석은 한 걸음 더 나아가, v5.0부터는 선점·인터럽트·softirq를 끈 모든 구간이 그대로 RCU 읽기 구간이라고 적습니다.

16.8함정과 패턴#

RCU는 락보다 규칙이 적어 보이지만, 어기면 드러나지 않는 버그가 됩니다.

  • 읽기 구간에서 잠들지 않습니다. GFP_KERNEL 할당, 뮤텍스, 유저 메모리 접근이 모두 해당합니다. 필요하면 SRCU를 쓰거나, 다음에 나오는 참조 카운트로 객체를 붙잡고 읽기 구간을 나옵니다.
  • 포인터는 한 번만 읽습니다. rcu_dereference()의 결과를 지역 변수에 받아 그것만 씁니다. 같은 포인터를 두 번 읽으면 그사이 다른 객체로 바뀌어 있을 수 있습니다.
  • 고치는 쪽끼리는 락을 잡습니다. 앞의 devcgroup_mutex처럼.
  • 읽는 쪽은 옛 데이터를 볼 수 있습니다. 삭제가 "즉시 모든 읽는 쪽에 보여야" 하는 데이터에는 RCU가 맞지 않습니다.
  • 읽기 구간을 나오면 포인터는 무효입니다.

찾기는 RCU로, 붙잡기는 참조 카운트로

마지막 규칙 때문에, RCU로 찾은 객체를 오래 쓰려면 읽기 구간 안에서 참조 카운트를 올려야 합니다.

net/core/neighbour.cv7.3
struct neighbour *neigh_lookup(struct neigh_table *tbl, const void *pkey,
                   struct net_device *dev)
{
    struct neighbour *n;

    NEIGH_CACHE_STAT_INC(tbl, lookups);

    rcu_read_lock();
    n = __neigh_lookup_noref(tbl, pkey, dev);
    if (n) {
        if (!refcount_inc_not_zero(&n->refcnt))
            n = NULL;
        NEIGH_CACHE_STAT_INC(tbl, hits);
    }

    rcu_read_unlock();
    return n;
}

refcount_inc()가 아니라 refcount_inc_not_zero()인 점을 봅니다. RCU는 객체의 메모리가 해제되지 않았음을 보장할 뿐입니다. 객체는 이미 마지막 참조가 내려가 해제를 기다리는 중일 수 있습니다. 카운트가 0인 객체는 죽은 객체이므로 되살리면 안 됩니다. 0이 아닐 때만 올리고, 실패하면 못 찾은 것으로 칩니다. 참조 카운트 일반은 25장에 있습니다.

객체를 아주 자주 만들고 없애는 경우에는 유예 기간마다 메모리가 묶이는 것이 부담입니다. 슬랩 캐시에 SLAB_TYPESAFE_BY_RCU를 주면 객체가 아니라 슬랩 페이지의 해제만 유예 기간 뒤로 미룹니다. 해제된 객체의 자리는 곧바로 같은 타입의 다른 객체로 재사용될 수 있습니다. 읽는 쪽은 메모리가 그 타입이라는 것만 믿을 수 있으므로, 참조를 잡은 뒤 "내가 찾던 그 객체가 맞는가"를 반드시 다시 확인해야 합니다. struct file이 이렇게 관리됩니다(fs/file.c의 __get_file_rcu()).

rcu_preempt가 유예 기간 스레드입니다. rcuc/N이 보이면 콜백을 softirq가 아니라 스레드로 실행하는 설정이고, rcuog/N과 rcuop/N이 보이면 콜백을 떼어 낸 CPU가 있는 것입니다. /proc/softirqs의 RCU 줄은 CPU별로 RCU softirq가 실행된 횟수입니다.

유예 기간이 rcu_cpu_stall_timeout(기본 21초, /sys/module/rcupdate/parameters/)을 넘도록 끝나지 않으면 커널이 정지 경고(stall warning)를 냅니다.

출력
rcu: INFO: rcu_preempt detected stalls on CPUs/tasks:
rcu:    2-....: (3 GPs behind) idle=06c4/0/0x0 softirq=1453/1455 fqs=0
rcu:    (detected by 32, t=2603 jiffies, g=7075, q=625 ncpus=64)

형식은 Documentation/RCU/stallwarn.rst의 예를 v7.3의 출력 형식에 맞춘 것입니다. 맨 앞의 숫자가 정지 상태를 보고하지 않는 CPU이고(P1234처럼 나오면 읽기 구간 안에서 선점당한 태스크의 PID), t=는 유예 기간이 시작된 뒤 지난 jiffies, q=는 밀려 있는 콜백 수입니다. 이어서 그 CPU의 스택이 찍힙니다. 대부분의 원인은 그 스택에 있습니다. 인터럽트나 선점을 끈 채 도는 반복문입니다.

설계 노트

RCU에서 배울 것은 두 가지 뒤집기입니다.

비용을 뒤집었습니다. 보통의 락은 읽기와 쓰기에 비슷한 비용을 물립니다. RCU는 읽기를 거의 0으로 만들고, 그 값을 쓰기(복사)와 회수(유예 기간)에 몰았습니다. 읽기가 수천 배 많은 데이터에서는 이 교환이 압도적으로 유리합니다. 동기화 기법을 고를 때 먼저 볼 것은 읽기와 쓰기의 비율입니다.

질문을 뒤집었습니다. "지금 누가 이 객체를 보고 있는가"는 읽는 쪽이 표시를 남겨야 답할 수 있습니다. RCU는 "모든 CPU가 한 번씩 읽기 구간 밖에 있었는가"로 바꿔 물었고, 그 답은 스케줄러가 이미 아는 사건들에서 나옵니다. 유저 공간의 대응물인 에포크 기반 회수나 해저드 포인터는 읽는 쪽이 에포크 번호나 포인터를 어딘가에 적어야 합니다. 커널의 RCU가 그 비용조차 없앨 수 있었던 것은 스케줄러를 직접 쥐고 있기 때문입니다.

정리#

  • rwlock은 읽는 쪽도 락 워드에 쓰므로 캐시 라인이 CPU 사이를 오갑니다. RCU의 읽는 쪽은 공유 메모리에 쓰지 않습니다.
  • 고치는 쪽은 복사본을 고쳐 rcu_assign_pointer()로 게시하고, 유예 기간이 지난 뒤 옛 객체를 해제합니다. 고치는 쪽끼리는 여전히 락이 필요합니다.
  • rcu_read_lock()은 선점 불가 RCU에서 preempt_disable(), 선점 가능한 RCU에서 태스크별 중첩 카운터 증가입니다.
  • 유예 기간은 모든 CPU가 정지 상태(컨텍스트 스위치, idle, 유저 모드)를 한 번씩 지나면 끝납니다. 선점 가능한 RCU는 읽기 구간 안에서 선점당한 태스크를 rcu_node의 blkd_tasks에 올려 따로 기다립니다.
  • Tree RCU는 정지 상태 보고를 rcu_node 트리의 qsmask로 모읍니다. 대부분의 보고는 잎의 락만 잡고 끝납니다.
  • 콜백은 CPU별 구간 리스트에 쌓였다가 RCU_SOFTIRQ, rcuc, rcuop 가운데 하나에서 실행됩니다.
  • 읽기 구간에서 잠들어야 하면 SRCU를, 표시할 수 없는 코드를 보호하려면 Tasks RCU를 씁니다.
  • RCU로 찾은 객체를 읽기 구간 밖에서 쓰려면 refcount_inc_not_zero()로 붙잡습니다.

확인 문제#

고치는 쪽이 rcu_assign_pointer() 대신 그냥 gp = new;라고 쓰면 어떤 일이 생길 수 있습니까? x86에서는 잘 드러나지 않는 까닭도 설명해 보세요.

답 보기

new의 필드를 채우는 쓰기와 gp에 포인터를 쓰는 쓰기 사이에 순서 보장이 없어집니다. 컴파일러나 CPU가 순서를 바꾸면, 다른 CPU의 읽는 쪽이 새 포인터를 읽고 따라갔는데 필드는 아직 초기화 전인 값을 볼 수 있습니다. rcu_assign_pointer()의 smp_store_release()는 앞선 쓰기들이 포인터 쓰기보다 먼저 보이도록 합니다. x86은 쓰기끼리의 순서를 하드웨어가 지켜 주므로 smp_store_release()가 컴파일러 재배치만 막으면 되는 보통의 쓰기가 됩니다. arm64 같은 약한 순서의 아키텍처에서는 실제 명령어가 달라지고 버그도 실제로 나타납니다.

선점 불가 RCU에서 "컨텍스트 스위치는 정지 상태"가 성립하는 이유를 rcu_read_lock()의 구현으로 설명하고, 선점 가능한 RCU에서는 왜 성립하지 않는지 말해 보세요.

답 보기

선점 불가 RCU의 rcu_read_lock()은 preempt_disable()입니다. 읽기 구간 안에서는 선점이 꺼져 있고 스스로 잠드는 것도 금지이므로, 읽기 구간 도중에는 컨텍스트 스위치가 일어날 수 없습니다. 따라서 어떤 CPU에서 컨텍스트 스위치가 일어났다면 그 순간 그 CPU는 읽기 구간 밖에 있었습니다. 선점 가능한 RCU의 rcu_read_lock()은 태스크의 rcu_read_lock_nesting만 올리고 선점은 켜 둡니다. 읽기 구간 안의 태스크가 선점당하면 CPU는 다른 태스크로 넘어가지만 읽기 구간은 끝나지 않았습니다. 그래서 rcu_note_context_switch()가 중첩 카운터를 확인해, 0보다 크면 그 태스크를 rcu_node의 blkd_tasks에 올린 다음에야 CPU의 정지 상태를 보고합니다.

CPU 64개짜리 시스템에서 유예 기간 하나 동안 뿌리 rcu_node의 락은 정지 상태 보고 때문에 몇 번쯤 잡힙니까? 기본 팬아웃(잎 16, 안쪽 64)을 가정합니다.

답 보기

잎이 4개이고 뿌리 아래에 바로 달립니다. 각 CPU의 보고는 잎의 락을 잡고 자기 비트를 지웁니다. 잎의 qsmask가 0이 아니면 거기서 돌아가므로, 잎마다 16번의 보고 가운데 마지막 한 번만 뿌리로 올라갑니다. 따라서 뿌리의 락은 정지 상태 보고로는 네 번쯤 잡힙니다. 트리가 없다면 64번 모두 전역 락 하나를 잡았을 것입니다. 유예 기간 스레드가 시작과 끝에서 잡는 것은 따로입니다.

neigh_lookup()에서 refcount_inc_not_zero()가 실패하는 것은 어떤 순간입니까? 그때 n이 가리키는 메모리를 읽어도 안전한 이유는 무엇입니까?

답 보기

다른 CPU가 그 이웃 항목의 마지막 참조를 내려 카운트가 0이 된 뒤, 해시 테이블에서 떼어 내고 해제를 맡긴 순간입니다. 읽는 쪽은 떼어 내기 전에 포인터를 집었거나, 리스트에서 막 빠진 노드를 지나고 있었습니다. 메모리가 안전한 이유는 RCU입니다. 해제는 유예 기간 뒤로 미뤄지고, 이 읽는 쪽은 그 유예 기간이 시작되기 전부터 읽기 구간 안에 있었으므로 rcu_read_unlock()까지는 해제되지 않습니다. 그래서 카운트 필드를 읽고 0임을 확인하는 것까지는 안전합니다. 다만 객체로서는 이미 죽었으므로 참조를 올려 되살리면 안 되고, 못 찾은 것으로 처리합니다.

모듈이 call_rcu()로 콜백을 맡겨 둔 채 언로드되면 어떤 일이 생깁니까? 무엇으로 막습니까? kfree_rcu()만 쓰는 모듈은 왜 이 문제가 없습니까?

답 보기

콜백 함수는 모듈의 코드 영역에 있습니다. 모듈이 언로드되어 그 메모리가 해제된 뒤에 유예 기간이 끝나면, RCU가 사라진 주소로 점프합니다. 언로드 경로에서 rcu_barrier()를 불러, 이미 맡긴 콜백이 모두 실행될 때까지 기다려야 합니다. synchronize_rcu()로는 부족합니다. 유예 기간이 끝났다는 것과 콜백이 실행되었다는 것은 다르기 때문입니다. kfree_rcu()는 콜백 함수가 모듈이 아니라 커널 본체에 있고 해제할 포인터만 넘기므로, 모듈이 사라져도 실행할 코드는 남아 있습니다.
