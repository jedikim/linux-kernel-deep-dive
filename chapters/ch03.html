태스크의 상태와 대기

잠들고, 깨어나고, 죽고, 거둬지기까지

Linux v7.3 기준약 55분
읽는 소스include/linux/sched.hfs/proc/array.ckernel/sched/core.cinclude/linux/wait.hkernel/sched/wait.cinclude/linux/sched/signal.hkernel/hung_task.ckernel/exit.c

태스크는 대부분의 시간을 기다리며 보냅니다. 키 입력을, 디스크를, 네트워크 패킷을, 다른 태스크가 쥔 락을 기다립니다. 기다리는 동안에는 CPU를 쓰면 안 되고, 기다리던 일이 일어나면 단 한 번도 놓치지 않고 깨어나야 합니다. 이 두 요구 사이에 틈이 있습니다. "잠들까 말까" 살피는 순간과 실제로 잠드는 순간 사이에 깨우는 신호가 지나가 버리면 태스크는 영영 깨어나지 못합니다. 이 장은 태스크의 상태가 어떤 값으로 표현되는지, 커널이 그 틈을 어떻게 메우는지, 그리고 태스크가 마지막으로 잠드는 종료의 과정을 따라갑니다.

이 장에서 답하는 질문
  • __state의 값들은 ps가 보여 주는 R, S, D, T, Z와 어떻게 대응하는가?
  • 잠드는 코드는 왜 상태를 먼저 바꾸고, 그다음에 조건을 확인하고, 그다음에 schedule()을 부르는가?
  • wake_up()은 대기 큐에서 누구를 몇이나 깨우는가?
  • kill -9로도 죽지 않는 프로세스는 왜 생기고, TASK_KILLABLE은 무엇을 고쳤는가?
  • 좀비는 무엇을 쥐고 있고, 누가 언제 거두는가?
  • 부모가 먼저 죽은 태스크는 누구의 자식이 되는가?

3.1상태는 비트 묶음이다#

태스크의 상태는 task_struct의 두 필드에 나뉘어 있습니다. __state는 실행할 수 있는지를, exit_state는 종료가 어디까지 진행되었는지를 나타냅니다. 값은 include/linux/sched.h에 한 줄로 이어 정의되어 있습니다.

include/linux/sched.hv7.3
/* Used in tsk->__state: */
#define TASK_RUNNING            0x00000000
#define TASK_INTERRUPTIBLE      0x00000001
#define TASK_UNINTERRUPTIBLE        0x00000002
#define __TASK_STOPPED          0x00000004
#define __TASK_TRACED           0x00000008
/* Used in tsk->exit_state: */
#define EXIT_DEAD           0x00000010
#define EXIT_ZOMBIE         0x00000020
#define EXIT_TRACE          (EXIT_ZOMBIE | EXIT_DEAD)
/* Used in tsk->__state again: */
#define TASK_PARKED         0x00000040
#define TASK_DEAD           0x00000080
#define TASK_WAKEKILL           0x00000100
#define TASK_WAKING         0x00000200
#define TASK_NOLOAD         0x00000400
#define TASK_NEW            0x00000800
#define TASK_RTLOCK_WAIT        0x00001000
#define TASK_FREEZABLE          0x00002000
/* ... */
#define TASK_FROZEN         0x00008000
/* ... */
/* Convenience macros for the sake of set_current_state: */
#define TASK_KILLABLE           (TASK_WAKEKILL | TASK_UNINTERRUPTIBLE)
#define TASK_STOPPED            (TASK_WAKEKILL | __TASK_STOPPED)
#define TASK_TRACED         __TASK_TRACED

#define TASK_IDLE           (TASK_UNINTERRUPTIBLE | TASK_NOLOAD)

읽을 곳은 세 군데입니다.

  • 값이 1, 2, 4, 8처럼 비트 하나씩입니다. 순서를 매긴 번호가 아니라 겹쳐 쓸 수 있는 플래그입니다.
  • TASK_RUNNING만 0입니다. "잠들 이유가 하나도 없다"는 뜻입니다. 나머지 비트는 저마다 실행하지 못하는 이유 하나를 가리킵니다.
  • 아래쪽의 TASK_KILLABLE과 TASK_IDLE은 비트 둘을 묶은 이름입니다. TASK_WAKEKILL, TASK_NOLOAD, TASK_FREEZABLE은 혼자 쓰이지 않고 다른 상태에 붙어 성질을 바꾸는 수식 비트입니다.

ps와 /proc/<pid>/status가 보여 주는 한 글자는 이 비트에서 나옵니다.

fs/proc/array.cv7.3
static const char * const task_state_array[] = {

    /* states in TASK_REPORT: */
    "R (running)",      /* 0x00 */
    "S (sleeping)",     /* 0x01 */
    "D (disk sleep)",   /* 0x02 */
    "T (stopped)",      /* 0x04 */
    "t (tracing stop)", /* 0x08 */
    "X (dead)",     /* 0x10 */
    "Z (zombie)",       /* 0x20 */
    "P (parked)",       /* 0x40 */

    /* states beyond TASK_REPORT: */
    "I (idle)",     /* 0x80 */
};

__state와 exit_state를 합쳐 가장 높은 비트 하나를 고른 뒤 이 표에서 찾습니다. 유저 공간에 내보내는 글자는 아홉 가지뿐이어서 몇몇은 뭉뚱그려집니다. TASK_KILLABLE은 D로, TASK_IDLE은 따로 I로, 얼어 있는 TASK_FROZEN은 D로 보입니다.

예전 자료와 다른 점

교과서의 프로세스 상태도는 생성, 준비, 실행, 대기, 종료의 다섯 칸입니다. 리눅스를 설명하는 글도 R, S, D, T, Z 다섯을 하나씩의 상태로 그리곤 합니다. v7.3의 실제 모습은 두 가지가 다릅니다. 첫째, "준비"와 "실행"을 가르는 상태값이 없습니다. 런큐에서 차례를 기다리는 태스크도, 지금 CPU를 쓰는 태스크도 TASK_RUNNING입니다. 둘을 가르는 것은 상태가 아니라 on_rq(런큐에 있는가)와 on_cpu(CPU에서 도는 중인가)라는 별도의 필드입니다. 둘째, 상태는 다섯 개의 칸이 아니라 열여섯 개 남짓의 비트이고 조합됩니다. 필드 이름도 바뀌었습니다. 예전 자료의 task->state는 v5.14에서 __state가 되었습니다. 밑줄 둘은 "직접 읽고 쓰지 말고 READ_ONCE()나 전용 매크로를 거치라"는 표시입니다.

3.2상태 사이를 오가는 길#

상태가 바뀌는 길을 한 장에 모으면 이렇습니다.

길은 넷으로 나뉩니다.

  • 만들어져서 런큐로. copy_process()가 만든 태스크는 TASK_NEW이고, wake_up_new_task()가 TASK_RUNNING으로 바꿔 런큐에 넣습니다(1장).
  • 잠들었다 깨어나기. 태스크가 스스로 상태를 바꾸고 schedule()을 불러 런큐에서 빠집니다. 다른 누군가가 try_to_wake_up()으로 되돌려 놓습니다. 이 장의 대부분이 이 길 이야기입니다.
  • 멈췄다 풀리기. SIGSTOP이나 디버거가 태스크를 세우고, SIGCONT나 디버거가 다시 풉니다.
  • 죽어서 거둬지기. do_exit()를 거쳐 좀비가 되고, 부모가 wait4()로 거둡니다.

TASK_RUNNING 안에서 "대기"와 "실행" 사이를 오가는 것은 상태 전이가 아닙니다. 스케줄러가 다음 태스크를 고르거나 현재 태스크를 선점하는 일이고, __state는 그대로입니다(4장, 6장). 반대쪽에도 예외가 있습니다. v7.3의 fair 클래스는 잠든 태스크를 런큐에서 곧바로 빼지 않고 다음에 뽑힐 차례까지 남겨 두기도 합니다(5장). 그래도 그 태스크가 실행되지는 않습니다.

3.3잠드는 순서#

커널 코드가 "어떤 조건이 참이 될 때까지 기다린다"를 구현하는 표준 모양이 있습니다. set_current_state()의 주석에 그대로 적혀 있습니다.

include/linux/sched.hv7.3
/*
 * set_current_state() includes a barrier so that the write of current->__state
 * is correctly serialised wrt the caller's subsequent test of whether to
 * actually sleep:
 *
 *   for (;;) {
 *  set_current_state(TASK_UNINTERRUPTIBLE);
 *  if (CONDITION)
 *     break;
 *
 *  schedule();
 *   }
 *   __set_current_state(TASK_RUNNING);

순서는 셋입니다. ① 자기 상태를 "잠듦"으로 바꾼다. ② 조건을 확인한다. ③ 조건이 거짓이면 schedule()을 부른다. 직관과는 반대입니다. 조건부터 보고, 거짓이면 그때 상태를 바꾸고 자는 편이 자연스러워 보입니다. 그렇게 하면 안 되는 이유가 깨움 분실(lost wakeup)입니다.

깨우는 쪽이 하는 일은 "조건을 참으로 만들고, 그 태스크가 잠든 상태면 TASK_RUNNING으로 되돌린다"입니다. 왼쪽 그림에서는 깨우는 쪽이 왔을 때 A가 아직 TASK_RUNNING이어서 되돌릴 것이 없습니다. 그 뒤에 A가 잠들면 다시 깨워 줄 사람이 없습니다. 오른쪽에서는 A가 이미 "잠듦"이라고 적어 두었으므로 깨우는 쪽이 그것을 TASK_RUNNING으로 고칩니다. A가 그 뒤에 schedule()을 불러도 상태가 TASK_RUNNING이므로 런큐에서 빠지지 않습니다.

상태를 바꾼 것만으로는 잠든 것이 아닙니다. 태스크를 실제로 런큐에서 빼는 것은 schedule()이고, 그때 __state를 봅니다.

kernel/sched/core.cv7.3
static bool try_to_block_task(struct rq *rq, struct task_struct *p,
                  unsigned long *task_state_p, bool should_block)
{
    unsigned long task_state = *task_state_p;

    WARN_ON_ONCE(p->is_blocked);

    if (signal_pending_state(task_state, p)) {
        WRITE_ONCE(p->__state, TASK_RUNNING);
        *task_state_p = TASK_RUNNING;
        clear_task_blocked_on(p, NULL);

        return false;
    }

    p->is_blocked = 1;
    /* ... */
    block_task(rq, p, task_state);
    return true;
}

__schedule()은 현재 태스크의 __state가 0이 아니고 선점으로 들어온 것이 아닐 때 이 함수를 부릅니다. block_task()가 런큐에서 빼는 일을 합니다. 그 앞의 signal_pending_state()는 뒤의 시그널 절에서 다시 봅니다.

"선점으로 들어온 것이 아닐 때"라는 조건이 중요합니다. ①과 ③ 사이에서 태스크가 선점당하면 스케줄러는 상태가 무엇이든 태스크를 런큐에 그대로 둡니다. 그러지 않으면 조건을 확인하기도 전에 잠들어 버리기 때문입니다. 6장의 SM_PREEMPT가 이 구분입니다.

참고 · 순서만으로는 모자란다: 메모리 배리어

set_current_state()는 단순한 대입이 아니라 smp_store_mb()입니다. 상태를 쓴 다음 메모리 배리어를 실행해, 그 쓰기가 뒤따르는 조건 읽기보다 먼저 다른 CPU에 보이도록 합니다. 깨우는 쪽도 대칭으로 조건을 쓴 뒤 배리어를 치고 상태를 읽습니다. 배리어가 없으면 CPU가 쓰기를 버퍼에 잠시 쥐고 있는 동안 양쪽이 서로의 옛 값을 읽어, 소스의 순서가 옳아도 깨움을 놓칠 수 있습니다. 메모리 순서는 13장에서 다룹니다. 조건과 깨움이 같은 락으로 보호될 때는 배리어 없는 __set_current_state()를 써도 됩니다.

3.4대기 큐#

깨우려면 누가 기다리는지 알아야 합니다. 같은 사건을 기다리는 태스크들을 매달아 두는 리스트가 대기 큐(wait queue)입니다.

include/linux/wait.hv7.3
struct wait_queue_entry {
    unsigned int        flags;
    void            *private;
    wait_queue_func_t   func;
    struct list_head    entry;
};

struct wait_queue_head {
    spinlock_t      lock;
    struct list_head    head;
};

머리(wait_queue_head)는 기다릴 대상 쪽에 있습니다. 소켓, 파이프, 터미널 같은 구조체 안에 들어 있습니다. 항목(wait_queue_entry)은 기다리는 쪽이 자기 커널 스택에 만들어 매답니다. private은 보통 기다리는 태스크를 가리키고, func는 깨울 때 불릴 함수입니다.

앞 절의 잠드는 순서를 대기 큐와 엮은 것이 wait_event() 계열 매크로입니다. 속은 이 매크로 하나입니다.

include/linux/wait.hv7.3
#define ___wait_event(wq_head, condition, state, exclusive, ret, cmd)       \
({                                      \
    __label__ __out;                            \
    struct wait_queue_entry __wq_entry;                 \
    long __ret = ret;   /* explicit shadow */               \
                                        \
    init_wait_entry(&__wq_entry, exclusive ? WQ_FLAG_EXCLUSIVE : 0);    \
    for (;;) {                              \
        long __int = prepare_to_wait_event(&wq_head, &__wq_entry, state);\
                                        \
        if (condition)                          \
            break;                          \
                                        \
        if (___wait_is_interruptible(state) && __int) {         \
            __ret = __int;                      \
            goto __out;                     \
        }                               \
                                        \
        cmd;                                \
                                        \
        if (condition)                          \
            break;                          \
    }                                   \
    finish_wait(&wq_head, &__wq_entry);                 \
__out:  __ret;                                  \
})

앞에서 본 세 단계가 그대로 있습니다. prepare_to_wait_event()가 항목을 큐에 매달고 set_current_state(state)를 부릅니다(①). 이어 condition을 확인하고(②), 거짓이면 cmd, 곧 schedule()을 실행합니다(③). 깨어나면 루프의 처음으로 돌아가 조건을 다시 봅니다. 깨어났다고 조건이 참이라는 보장은 없기 때문입니다. 다른 태스크가 먼저 채 갔을 수도 있고, 다른 이유로 깨워졌을 수도 있습니다. wait_event(wq, cond)는 이 매크로를 TASK_UNINTERRUPTIBLE과 schedule()로 부른 것이고, wait_event_interruptible()은 TASK_INTERRUPTIBLE로 부른 것입니다.

설계 노트

잠드는 순서는 한 줄만 어긋나도 "백만 번에 한 번 멈추는" 버그가 됩니다. 그런 규약을 호출하는 사람마다 손으로 쓰게 두면 누군가는 틀립니다. 커널은 규약 전체를 wait_event(wq, 조건) 한 줄로 감쌌습니다. 호출하는 쪽은 "무엇을 기다리는가"만 쓰고, "어떤 순서로 잠드는가"는 매크로가 맡습니다. 조건을 인자로 받아 루프 안에서 다시 평가한다는 점도 설계의 일부입니다. 틀리기 쉬운 순서가 있으면 문서로 경고하기 전에 그 순서를 한곳에 가두어, 틀릴 수 없는 인터페이스를 만드는 편이 낫습니다. 락을 쥐고 푸는 순서를 감싼 guard()도 같은 발상입니다(25장).

누구를 깨우는가

깨우는 쪽은 wake_up(&wq)을 부릅니다. 속은 리스트를 도는 반복문입니다.

kernel/sched/wait.cv7.3
static int __wake_up_common(struct wait_queue_head *wq_head, unsigned int mode,
            int nr_exclusive, int wake_flags, void *key)
{
    wait_queue_entry_t *curr, *next;

    lockdep_assert_held(&wq_head->lock);

    curr = list_first_entry(&wq_head->head, wait_queue_entry_t, entry);

    if (&curr->entry == &wq_head->head)
        return nr_exclusive;

    list_for_each_entry_safe_from(curr, next, &wq_head->head, entry) {
        unsigned flags = curr->flags;
        int ret;

        ret = curr->func(curr, mode, wake_flags, key);
        if (ret < 0)
            break;
        if (ret && (flags & WQ_FLAG_EXCLUSIVE) && !--nr_exclusive)
            break;
    }

    return nr_exclusive;
}

항목마다 func를 부르고, 배타 대기자를 nr_exclusive개 깨우면 멈춥니다. wake_up()은 이 값을 1로, wake_up_all()은 0(제한 없음)으로 넘깁니다. 배타 대기자는 큐의 뒤쪽에 넣으므로, wake_up() 한 번은 비배타 대기자 전부와 배타 대기자 하나를 깨웁니다.

배타 대기(exclusive wait)가 있는 까닭은 떼로 깨어나는 문제입니다. 워커 스레드 백 개가 같은 리스닝 소켓에서 accept()를 기다린다고 합시다. 연결 하나가 들어왔을 때 백 개를 다 깨우면, 하나만 연결을 얻고 아흔아홉은 조건을 다시 확인한 뒤 도로 잠듭니다. 아흔아홉 번의 컨텍스트 스위치가 낭비입니다. accept()는 배타로 기다리므로(inet_csk_wait_for_connect()) 연결 하나에 하나만 깨어납니다.

func가 함수 포인터라는 점도 쓸모가 있습니다. 기본값인 default_wake_function()은 태스크를 깨우지만, epoll은 여기에 자기 콜백을 걸어 "깨우는 대신 준비 목록에 넣기"를 합니다. 대기 큐가 "사건이 생기면 불러 주는 콜백 목록"으로도 쓰이는 것입니다.

대기 큐보다 단순한 도구도 있습니다. 1장의 vfork에서 본 completion은 "한 번 끝난다"는 사건 전용입니다. 카운터 하나와 단순 대기 큐(swait) 하나로 되어 있고, complete()가 카운터를 올린 뒤 깨우므로 wait_for_completion()이 나중에 불려도 놓치지 않습니다.

3.5깨우는 쪽#

default_wake_function()이 부르는 것이 try_to_wake_up()입니다. 잠든 태스크를 깨우는 길은 모두 이 함수로 모입니다. 주석은 하는 일을 한 줄로 적습니다. @state & @p->state이면 @p->state = TASK_RUNNING.

kernel/sched/core.cv7.3
int try_to_wake_up(struct task_struct *p, unsigned int state, int wake_flags)
{
    guard(preempt)();
    int cpu, success = 0;
    /* ... */
    scoped_guard (raw_spinlock_irqsave, &p->pi_lock) {
        /* ... */
        smp_mb__after_spinlock();

        if (!ttwu_state_match(p, state, &success))
            break;

        trace_sched_waking(p);
        /* ... */
        smp_rmb();
        if (READ_ONCE(p->on_rq) && ttwu_runnable(p, wake_flags))
            break;
        /* ... */
        WRITE_ONCE(p->__state, TASK_WAKING);
        /* ... */
        cpu = select_task_rq(p, p->wake_cpu, &wake_flags);
        /* ... */
        ttwu_queue(p, cpu, wake_flags);
    }
    /* ... */
}

읽을 곳은 네 군데입니다.

  • 인자 state는 "어떤 잠을 깨울 것인가"의 마스크입니다. wake_up()은 TASK_NORMAL(S와 D)을 넘깁니다. 태스크의 __state와 겹치는 비트가 없으면 ttwu_state_match()가 거짓을 돌려주고 아무 일도 하지 않습니다. 이미 깨어 있는 태스크를 깨워도 해가 없는 이유입니다.
  • p->on_rq가 아직 1이면 태스크는 상태만 바꿨을 뿐 런큐에서 빠지지 않았습니다. 앞의 그림 3-3 오른쪽이 이 경우입니다. ttwu_runnable()이 상태만 TASK_RUNNING으로 되돌리고 끝냅니다.
  • 런큐에서 빠진 태스크라면 select_task_rq()로 깨울 CPU를 고릅니다. 잠들기 전의 CPU일 수도 있고 다른 CPU일 수도 있습니다(7장).
  • ttwu_queue()가 그 CPU의 런큐에 넣고 TASK_RUNNING으로 바꿉니다.

깨운다는 것은 런큐에 넣는다는 뜻이지 CPU를 준다는 뜻이 아닙니다. 깨어난 태스크가 언제 실제로 도는지는 스케줄러가 정합니다. 그리고 이 함수는 인터럽트 핸들러에서도 불립니다. 디스크가 읽기를 마쳤다는 인터럽트, 패킷이 도착했다는 인터럽트가 기다리던 태스크를 깨우는 것이 바로 이 길입니다. 그래서 pi_lock은 인터럽트를 끄고 잡는 스핀락입니다.

3.6시그널이 깨우는 잠, 깨우지 못하는 잠#

잠에는 두 가지가 있습니다. TASK_INTERRUPTIBLE(S)은 기다리던 사건이 오거나 시그널이 오면 깨어납니다. TASK_UNINTERRUPTIBLE(D)은 기다리던 사건이 올 때까지 무슨 일이 있어도 잡니다.

시그널을 보내는 쪽은 대상 태스크에 TIF_SIGPENDING 플래그를 세우고 wake_up_state()를 부릅니다. 넘기는 마스크는 TASK_INTERRUPTIBLE이고, 치명적 시그널이면 TASK_WAKEKILL이 더해집니다. D로 잠든 태스크는 이 마스크에 걸리지 않으므로 깨어나지 않습니다. 잠드는 쪽에서는 앞에서 본 try_to_block_task()와 prepare_to_wait_event()가 이 함수로 "이미 와 있는 시그널"을 확인합니다.

include/linux/sched/signal.hv7.3
static inline int signal_pending_state(unsigned int state, struct task_struct *p)
{
    if (!(state & (TASK_INTERRUPTIBLE | TASK_WAKEKILL)))
        return 0;
    if (!signal_pending(p))
        return 0;

    return (state & TASK_INTERRUPTIBLE) || __fatal_signal_pending(p);
}

시그널에 깨어난 커널 코드는 하던 일을 접고 -ERESTARTSYS를 들고 유저 모드 쪽으로 나갑니다. 나가는 길에 시그널 핸들러가 실행되고, 그 뒤 시스템 콜을 다시 걸지 EINTR로 실패시킬지가 정해집니다. 다시 거는 방법은 1장에서 본 요령입니다. pt_regs의 명령어 포인터를 2바이트 뒤로 물려(regs->ip -= 2) syscall 명령어를 한 번 더 실행하게 합니다.

그렇다면 왜 D가 있을까요. 하던 일을 중간에 접을 수 없는 코드가 있기 때문입니다. 파일시스템이 디스크 블록 여러 개를 고치는 도중이라면, 시그널이 왔다고 반쯤 고친 채 돌아갈 수는 없습니다. 그런 곳은 D로 기다립니다. 대신 값을 치릅니다. 기다리던 사건이 끝내 오지 않으면, 예컨대 저장 장치가 응답을 멈추면, 그 태스크는 kill -9로도 죽지 않습니다. SIGKILL도 시그널이기 때문입니다.

TASK_KILLABLE이 이 문제를 줄였습니다. D에 TASK_WAKEKILL 비트를 더한 것으로, 보통 시그널은 무시하되 태스크를 죽일 시그널에는 깨어납니다. 위 함수의 마지막 줄이 그 판정입니다. 치명적 시그널을 받은 태스크는 유저 코드로 돌아가지 않고 곧 죽을 것이므로, 커널 코드는 "이어 갈 수 있게 되돌리기"가 아니라 "쥔 것을 놓고 빠져나오기"만 하면 됩니다. 되돌리기보다 훨씬 쉬운 일이라, 예전에는 D로만 기다릴 수 있던 많은 자리가 TASK_KILLABLE로 바뀌었습니다.

잠의 종류 ps 보통 시그널 SIGKILL 부하 평균에 포함 hung task 검사
TASK_INTERRUPTIBLE S 깨운다 깨운다 아니오 안 함
TASK_UNINTERRUPTIBLE D 못 깨운다 못 깨운다 예 한다
TASK_KILLABLE D 못 깨운다 깨운다 예 안 함
TASK_IDLE I 못 깨운다 못 깨운다 아니오 안 함

표의 오른쪽 두 열이 D 상태의 부작용입니다.

흔한 오해

"load average는 CPU 사용률이다." 리눅스의 부하 평균은 실행 가능한 태스크 수에 D 상태로 잠든 태스크 수를 더해 평균한 값입니다(kernel/sched/loadavg.c). CPU는 한가한데 디스크나 NFS가 막혀 태스크 수십 개가 D로 쌓이면 부하 평균은 수십이 됩니다. 부하 평균이 높을 때는 ps에서 R이 많은지 D가 많은지부터 봐야 합니다. 일감을 기다리며 쉬는 커널 스레드가 이 숫자를 부풀리지 않도록 만든 것이 TASK_NOLOAD 비트와 TASK_IDLE입니다.

D로 너무 오래 잠든 태스크는 커널이 알려 줍니다. khungtaskd라는 커널 스레드가 주기적으로 태스크를 훑습니다.

kernel/hung_task.cv7.3
static bool task_is_hung(struct task_struct *t, unsigned long timeout)
{
    unsigned long switch_count = t->nvcsw + t->nivcsw;
    unsigned int state = READ_ONCE(t->__state);

    /*
     * skip the TASK_KILLABLE tasks -- these can be killed
     * skip the TASK_IDLE tasks -- those are genuinely idle
     * skip the TASK_FROZEN task -- it reasonably stops scheduling by freezer
     */
    if (!(state & TASK_UNINTERRUPTIBLE) ||
        (state & (TASK_WAKEKILL | TASK_NOLOAD | TASK_FROZEN)))
        return false;
    /* ... */
}

수식 비트가 붙지 않은 순수한 D이고, 컨텍스트 스위치 횟수가 hung_task_timeout_secs(기본 120초) 동안 그대로이면 "task ... blocked for more than 120 seconds"라는 메시지와 함께 스택을 찍습니다. 이 메시지는 대개 디스크나 네트워크 저장소가 응답하지 않거나, 락을 쥔 태스크가 멈췄다는 신호입니다.

3.7멈춤, 주차, 얼림#

잠과 닮았지만 "조건을 기다리는" 것이 아닌 상태들이 있습니다. 누가 풀어 줄 때까지 서 있는 상태입니다.

  • 멈춤(T). SIGSTOP이나 셸의 Ctrl-Z를 받은 태스크는 TASK_STOPPED가 됩니다. SIGCONT를 보내는 쪽이 wake_up_state(t, __TASK_STOPPED)로 풉니다. TASK_STOPPED에는 TASK_WAKEKILL이 들어 있어서, 멈춘 프로세스도 SIGKILL로는 죽습니다.
  • 추적 멈춤(t). gdb나 strace 같은 추적 도구가 ptrace로 붙은 태스크는 중단점이나 시스템 콜 경계에서 TASK_TRACED로 섭니다. 추적 도구가 계속하라고 할 때까지입니다.
  • 주차(P). CPU별 커널 스레드는 자기 CPU가 꺼질 때 종료하는 대신 TASK_PARKED로 서 있다가, CPU가 다시 켜지면 이어서 돕니다.
  • 얼림. 시스템을 절전 상태로 보낼 때 프리저가 태스크들을 TASK_FROZEN으로 만듭니다. 잠들 때 TASK_FREEZABLE을 붙여 둔 태스크는 깨울 필요 없이 그 자리에서 얼릴 수 있습니다.

이 상태들은 조건 루프를 돌지 않으므로 set_current_state() 대신 set_special_state()로 들어갑니다. 이 매크로는 pi_lock을 쥐고 상태를 씁니다. 앞에서 본 것처럼 깨우는 쪽은 뒤늦게 TASK_RUNNING을 덮어쓸 수 있는데, 조건 루프가 없는 코드는 그 덮어쓰기를 "한 바퀴 더 돌면 그만"으로 넘길 수 없기 때문입니다.

3.8종료와 좀비#

태스크는 exit()를 부르거나 치명적 시그널을 받아 끝납니다. 어느 쪽이든 do_exit()(kernel/exit.c)로 옵니다. 만들 때의 copy_process()를 거꾸로 돌린 것과 비슷합니다.

do_exit()의 순서는 이렇습니다.

  1. exit_signals()로 PF_EXITING을 세웁니다. 이 태스크는 더는 시그널을 받지 않습니다.
  2. exit_mm(), exit_files(), exit_fs() 등으로 자원을 놓습니다. 참조 카운트를 내리고, 마지막 사용자였다면 해제합니다. 주소 공간이 여기서 사라집니다.
  3. exit_notify()로 가족에게 알립니다.
  4. do_task_dead()가 __state를 TASK_DEAD로 바꾸고 마지막 schedule()을 부릅니다. 이 호출은 돌아오지 않습니다.
kernel/exit.cv7.3
static void exit_notify(struct task_struct *tsk, int group_dead)
{
    bool autoreap;
    struct task_struct *p, *n;
    LIST_HEAD(dead);

    write_lock_irq(&tasklist_lock);
    forget_original_parent(tsk, &dead);
    /* ... */
    tsk->exit_state = EXIT_ZOMBIE;

    if (unlikely(tsk->ptrace)) {
        /* ... */
    } else if (thread_group_leader(tsk)) {
        autoreap = thread_group_empty(tsk) &&
               do_notify_parent(tsk, tsk->exit_signal);
    } else {
        autoreap = true;
        /* untraced sub-thread */
        do_notify_pidfd(tsk);
    }

    if (autoreap) {
        tsk->exit_state = EXIT_DEAD;
        list_add(&tsk->ptrace_entry, &dead);
    }
    /* ... */
    write_unlock_irq(&tasklist_lock);

    list_for_each_entry_safe(p, n, &dead, ptrace_entry) {
        list_del_init(&p->ptrace_entry);
        release_task(p);
    }
}

읽을 곳은 세 군데입니다.

  • forget_original_parent()가 먼저입니다. 죽는 태스크의 자식들에게 새 부모를 찾아 줍니다. 아래에서 봅니다.
  • exit_state = EXIT_ZOMBIE. 이 순간부터 태스크는 좀비(zombie)입니다. do_notify_parent()가 부모에게 exit_signal(보통 SIGCHLD)을 보내고 부모의 wait 대기 큐를 깨웁니다.
  • autoreap이 참이면 좀비 단계를 건너뛰고 곧바로 release_task()로 갑니다. 스레드 그룹의 리더가 아닌 스레드가 그렇고, 부모가 SIGCHLD를 무시하도록 해 둔 경우와 1장의 CLONE_AUTOREAP로 만든 자식이 그렇습니다.

좀비가 남는 이유는 부모에게 전할 것이 있기 때문입니다. 종료 코드와 그동안 쓴 자원의 통계입니다. 부모가 wait4()나 waitid()로 물어 올 때까지 누군가 그것을 들고 있어야 하고, PID도 그때까지는 다른 태스크에 다시 배정되면 안 됩니다. 좀비는 task_struct와 PID, 그리고 거기 딸린 작은 구조체 몇 개만 쥐고 있습니다. 주소 공간도 파일도 없고, 커널 스택도 마지막 컨텍스트 스위치 직후에 놓습니다. 그러니 좀비 하나는 메모리를 거의 쓰지 않습니다. 문제가 되는 것은 PID와 태스크 수 한도입니다.

부모가 wait4()를 부르면 wait_task_zombie()가 exit_state를 EXIT_ZOMBIE에서 EXIT_DEAD로 바꾸고(여러 스레드가 동시에 거두지 못하도록 cmpxchg로), 종료 코드를 읽어 내고, release_task()를 부릅니다. release_task()는 PID를 반납하고 태스크를 모든 리스트에서 뗍니다. task_struct 메모리는 그 뒤에도 조금 더 남습니다.

kernel/exit.cv7.3
void put_task_struct_rcu_user(struct task_struct *task)
{
    if (refcount_dec_and_test(&task->rcu_users))
        call_rcu(&task->rcu, delayed_put_task_struct);
}

rcu_users는 2로 시작합니다. 하나는 release_task()가, 하나는 죽은 태스크에서 스위치되어 나온 직후의 스케줄러(finish_task_switch())가 내립니다. 둘 다 내려간 뒤에도 곧바로 해제하지 않고 call_rcu()에 맡깁니다. 커널 곳곳에 락 없이 task_struct를 읽는 코드가 있기 때문입니다. getppid()가 real_parent를 따라갈 때, kill()이 PID로 태스크를 찾을 때가 그렇습니다. 그런 읽기가 모두 끝났음이 보장되는 시점, 곧 RCU 유예 기간이 지난 뒤에야 메모리를 풉니다(16장).

설계 노트

task_struct 하나를 없애는 데 단계가 넷입니다. 자원은 do_exit()에서, 스택은 마지막 스위치에서, 이름(PID)은 release_task()에서, 메모리는 RCU 콜백에서 풀립니다. 번거로워 보이지만 각 단계는 "이것을 아직 쓰는 쪽이 누구인가"에 대한 답입니다. 스택은 죽는 태스크 자신이 마지막 순간까지 쓰므로 스스로 풀 수 없고, 종료 코드는 부모가 읽어야 하며, 구조체 메모리는 락 없이 읽는 쪽이 남아 있을 수 있습니다. 여럿이 함께 쓰는 객체의 해제는 한 번의 free()가 아니라, 사용자 부류마다 하나씩 참조를 거둬 가는 과정으로 설계해야 합니다. 그 설계가 틀리면 해제 후 사용(use-after-free)이 됩니다.

부모가 먼저 죽으면

부모가 자식보다 먼저 끝나면 자식은 고아가 됩니다. 고아에게도 종료를 거둬 줄 부모가 있어야 하므로, forget_original_parent()가 새 부모를 정합니다. 찾는 순서는 주석에 적혀 있습니다.

kernel/exit.cv7.3
/*
 * When we die, we re-parent all our children, and try to:
 * 1. give them to another thread in our thread group, if such a member exists
 * 2. give it to the first ancestor process which prctl'd itself as a
 *    child_subreaper for its children (like a service manager)
 * 3. give it to the init process (PID 1) in our pid namespace
 */

2번의 서브리퍼(subreaper)는 prctl(PR_SET_CHILD_SUBREAPER)로 "내 자손 가운데 고아가 생기면 내가 맡겠다"고 등록한 프로세스입니다. 서비스 관리자가 자기가 띄운 서비스의 손자, 증손자까지 놓치지 않으려고 씁니다. 3번의 init은 그 PID 네임스페이스의 PID 1입니다. 컨테이너 안이라면 컨테이너의 첫 프로세스입니다. 이 프로세스가 wait()를 부르지 않는 프로그램이면 컨테이너 안에 좀비가 쌓입니다. 컨테이너에 작은 init 프로그램을 넣으라고들 하는 이유입니다.

직접 확인하기

좀비를 직접 만들어 봅니다.

zombie.cC
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(void)
{
    pid_t pid = fork();

    if (pid == 0)
        exit(42);   /* 자식: 곧바로 끝난다 */

    printf("자식 %d를 거두지 않고 30초 기다립니다\n", pid);
    sleep(30);      /* 부모: wait()를 부르지 않는다 */
    return 0;
}
터미널
$ gcc -o zombie zombie.c
$ ./zombie &
자식 41533을 거두지 않고 30초 기다립니다
$ ps -o pid,ppid,stat,rss,comm --ppid $!
    PID    PPID STAT   RSS COMMAND
  41533   41532 Z        0 zombie <defunct>
$ grep -E 'State|VmRSS' /proc/41533/status
State:  Z (zombie)

RSS가 0이고 VmRSS 줄이 없습니다. 주소 공간이 이미 없기 때문입니다. 좀비에게 kill -9를 보내도 사라지지 않습니다. 이미 죽은 태스크라 시그널을 받을 주체가 없습니다. 없애려면 부모가 wait()를 부르거나 부모가 끝나야 합니다. 30초 뒤 부모가 끝나면 좀비는 init이나 서브리퍼에게 넘어가 곧 거둬집니다.

정리#

  • 태스크의 상태는 __state와 exit_state 두 필드의 비트입니다. TASK_RUNNING은 0이고, 나머지 비트는 실행하지 못하는 이유를 하나씩 나타내며 조합됩니다.
  • "실행 중"과 "실행 대기"는 상태값이 아니라 on_cpu와 on_rq로 구분됩니다.
  • 잠드는 순서는 상태를 바꾸고, 조건을 확인하고, schedule()을 부르는 것입니다. 순서가 바뀌면 깨움을 놓칩니다. wait_event() 계열 매크로가 이 순서를 감쌉니다.
  • 대기 큐는 기다리는 태스크의 항목을 잇는 리스트입니다. wake_up()은 비배타 대기자 전부와 배타 대기자 하나를 깨웁니다.
  • 깨운다는 것은 try_to_wake_up()이 상태를 TASK_RUNNING으로 되돌리고 런큐에 넣는 일입니다.
  • S는 시그널에 깨어나고 D는 깨어나지 않습니다. TASK_KILLABLE은 치명적 시그널에만 깨어납니다. D 상태의 태스크는 부하 평균에 포함됩니다.
  • 종료한 태스크는 부모가 wait로 거둘 때까지 task_struct와 PID만 쥔 좀비로 남습니다. task_struct 메모리는 RCU 유예 기간 뒤에 풀립니다.
  • 고아는 같은 스레드 그룹의 스레드, 가장 가까운 서브리퍼, PID 네임스페이스의 init 순서로 새 부모를 얻습니다.

확인 문제#

다음 코드는 flag가 참이 될 때까지 기다리려는 것입니다. 무엇이 잘못되었고, 어떤 순서로 실행될 때 문제가 드러납니까?

C
while (!flag) {
    set_current_state(TASK_INTERRUPTIBLE);
    schedule();
}
답 보기

조건 확인(!flag)이 상태 변경보다 앞에 있습니다. 태스크가 !flag를 참으로 본 직후, set_current_state()를 부르기 전에 다른 CPU가 flag = true로 바꾸고 wake_up_process()를 부르면, 그때 이 태스크는 아직 TASK_RUNNING이므로 깨움은 아무 일도 하지 않습니다. 이어서 태스크가 상태를 TASK_INTERRUPTIBLE로 바꾸고 schedule()을 부르면 런큐에서 빠지고, 다시 깨워 줄 쪽이 없습니다. 고치려면 set_current_state()를 루프의 맨 앞에 두고 그 뒤에 flag를 확인해야 합니다. wait_event_interruptible(wq, flag)를 쓰면 이 순서가 보장됩니다.

ps에서 어떤 프로세스가 D 상태로 몇 분째 머물러 있고 kill -9에도 반응하지 않습니다. 이 프로세스의 __state는 무엇이고, SIGKILL이 듣지 않는 이유는 무엇입니까? 같은 D로 보이는데 kill -9가 듣는 프로세스는 무엇이 다릅니까?

답 보기

__state는 TASK_UNINTERRUPTIBLE(0x2)입니다. SIGKILL을 보내면 커널은 TIF_SIGPENDING을 세우고 wake_up_state()를 부르는데, 넘기는 마스크는 TASK_INTERRUPTIBLE에 TASK_WAKEKILL을 더한 것입니다. TASK_UNINTERRUPTIBLE과는 겹치는 비트가 없으므로 try_to_wake_up()의 상태 확인에서 걸러집니다. 시그널은 대기 상태로 남아 있다가 태스크가 다른 이유로 깨어나 유저 모드로 나가려 할 때 처리됩니다. kill -9가 듣는 D는 TASK_KILLABLE입니다. TASK_WAKEKILL 비트가 있어 마스크와 겹치고, signal_pending_state()도 치명적 시그널이면 참을 돌려줍니다. ps가 둘을 모두 D로 보여 주는 것은 TASK_WAKEKILL이 보고용 비트(TASK_REPORT)에 들어 있지 않기 때문입니다.

워커 스레드 32개가 한 대기 큐에서 wait_event_interruptible_exclusive()로 일감을 기다립니다. 일감 하나가 들어와 wake_up()이 한 번 불렸습니다. 몇 개의 스레드가 깨어납니까? 깨어난 스레드가 일감을 꺼내려다 실패할 수도 있습니까?

답 보기

하나입니다. 32개 모두 배타 대기자이므로 __wake_up_common()은 첫 항목의 func를 불러 깨우고 nr_exclusive가 0이 되어 멈춥니다. 다만 깨어난 스레드가 일감을 얻는다는 보장은 없습니다. 깨움은 런큐에 넣는 것일 뿐이라, 그 스레드가 실제로 돌기 전에 마침 깨어 있던 다른 스레드가 일감을 먼저 가져갈 수 있습니다. 그래서 wait_event 매크로는 깨어난 뒤 조건을 다시 확인하고, 거짓이면 다시 잠듭니다. "깨어났다"와 "조건이 참이다"는 별개입니다.

좀비 프로세스 천 개가 쌓인 서버가 있습니다. 메모리는 거의 줄지 않았는데 새 프로세스가 fork: Resource temporarily unavailable로 실패하기 시작했습니다. 좀비가 쥐고 있는 것과 쥐고 있지 않은 것으로 이 현상을 설명해 보세요.

답 보기

좀비는 do_exit()에서 주소 공간, 파일, 네임스페이스 참조를 이미 놓았고 커널 스택도 마지막 스위치 뒤에 놓았습니다. 남은 것은 task_struct와 struct pid, 그리고 종료 코드와 통계뿐입니다. 그래서 좀비 하나가 쓰는 메모리는 task_struct 하나 남짓입니다. 그러나 좀비도 태스크 하나로 셉니다. release_task()가 불리기 전까지 사용자별 RLIMIT_NPROC 계수, cgroup의 pids.current, PID 번호가 그대로 잡혀 있습니다. fork()가 돌려준 EAGAIN은 1장에서 본 이 한도들 가운데 하나에 걸린 것입니다. 해결은 좀비를 죽이는 것이 아니라(이미 죽었습니다) 부모가 wait()를 부르게 하거나 부모를 끝내 고아로 만들어 init이 거두게 하는 것입니다.

스레드 넷으로 된 프로세스에서 메인 스레드가 아닌 스레드 하나가 pthread_exit()로 끝났습니다. 이 스레드는 좀비가 됩니까? 반대로 메인 스레드만 pthread_exit()로 끝나고 나머지 셋이 계속 돌면 ps에는 어떻게 보입니까?

답 보기

리더가 아닌 스레드는 좀비로 남지 않습니다. exit_notify()에서 thread_group_leader()가 거짓이므로 autoreap이 참이 되고, exit_state가 곧바로 EXIT_DEAD가 되어 release_task()로 넘어갑니다. 스레드의 종료를 기다리는 pthread_join()은 커널의 wait가 아니라 CLONE_CHILD_CLEARTID와 futex로 구현되기 때문에 좀비가 필요 없습니다. 메인 스레드(그룹 리더)만 끝난 경우는 다릅니다. 리더는 EXIT_ZOMBIE가 되지만 thread_group_empty()가 거짓이라 부모에게 알리지 않고, 나머지 스레드가 모두 끝날 때까지 좀비로 남습니다. 리더의 task_struct가 스레드 그룹의 PID(tgid)를 대표하기 때문입니다. ps에는 그 프로세스가 Zl처럼 좀비이면서 다중 스레드인 상태로 보이고, 나머지 스레드는 ps -L에서 정상적으로 돕니다.

용어#

__state
태스크가 실행 가능한지, 어떤 이유로 잠들었는지를 나타내는 task_struct의 비트 필드.
TASK_RUNNING
실행 중이거나 런큐에서 실행을 기다리는 상태. 값은 0.
깨움 분실lost wakeup
조건 확인과 잠들기 사이에 깨움이 지나가, 태스크가 깨워 줄 이 없이 잠드는 경쟁 조건.
대기 큐wait queue
같은 사건을 기다리는 태스크의 항목을 이은 리스트. wait_queue_head와 wait_queue_entry로 이루어진다.
배타 대기exclusive wait
wake_up() 한 번에 하나만 깨어나도록 표시한 대기. 떼로 깨어나는 낭비를 막는다.
try_to_wake_up
태스크의 상태를 TASK_RUNNING으로 되돌리고 런큐에 넣는 함수. 모든 깨움이 여기로 모인다.
TASK_KILLABLE
보통 시그널에는 깨어나지 않고 치명적 시그널에만 깨어나는 잠. TASK_WAKEKILL | TASK_UNINTERRUPTIBLE.
TASK_IDLE
부하 평균에 넣지 않는 시그널 불가 잠. 일감을 기다리는 커널 스레드가 쓴다.
completion
"한 번 끝난다"는 사건을 기다리는 도구. 카운터와 단순 대기 큐로 이루어진다.
좀비zombie
종료했지만 부모가 아직 거두지 않은 태스크. task_struct와 PID만 남아 있다.
서브리퍼subreaper
자손 가운데 생긴 고아를 init 대신 떠맡겠다고 등록한 프로세스.
부하 평균load average
실행 가능한 태스크 수와 D 상태 태스크 수를 더해 지수 평균한 값.
