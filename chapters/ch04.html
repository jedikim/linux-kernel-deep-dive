스케줄러의 뼈대

런큐, 스케줄링 클래스, __schedule()과 컨텍스트 스위치

Linux v7.3 기준약 55분
읽는 소스kernel/sched/sched.hinclude/asm-generic/vmlinux.lds.hkernel/sched/core.carch/x86/entry/entry_64.Skernel/sched/fair.c

CPU는 한 번에 태스크 하나만 실행합니다. 실행하고 싶은 태스크는 수백 개입니다. 누구를 먼저, 얼마나 오래 돌릴지는 정책의 문제이고, 정책은 용도마다 다릅니다. 오디오 스레드와 컴파일 작업에 같은 규칙을 쓸 수는 없습니다. 그런데 "지금 도는 태스크를 내리고 다른 태스크를 올리는" 절차는 정책이 무엇이든 같습니다. 리눅스 스케줄러는 이 둘을 갈라 놓았습니다. 이 장은 정책이 꽂히는 틀, 곧 스케줄러의 뼈대를 읽습니다.

이 장에서 답하는 질문
  • CPU마다 하나씩 있는 런큐에는 무엇이 들어 있는가?
  • 스케줄링 클래스는 몇 개이고, 클래스 사이의 우선순위는 어디에서 정해지는가?
  • SCHED_FIFO, nice 값, prio 숫자는 서로 어떤 관계인가?
  • 틱이 하는 일과 __schedule()이 하는 일은 어떻게 다른가?
  • 컨텍스트 스위치에서 실제로 저장되고 복원되는 것은 무엇인가?
  • switch_to()는 왜 인자가 셋인가?

4.1뼈대와 정책#

스케줄러가 하는 일은 둘로 나뉩니다.

  • 고르는 일: 실행할 수 있는 태스크 가운데 다음에 누구를 돌릴지 정합니다. 정책입니다.
  • 바꾸는 일: 지금 도는 태스크의 상태를 저장하고 고른 태스크의 상태를 복원합니다. 메커니즘입니다.

코드도 이 경계를 따라 나뉘어 있습니다. kernel/sched/core.c가 뼈대입니다. 언제 스케줄러에 들어가는지, 런큐 락을 어떻게 잡는지, 컨텍스트 스위치를 어떻게 하는지가 여기 있습니다. "누구를 고를지"는 스케줄링 클래스라는 모듈이 답하고, 뼈대는 정해진 인터페이스로 묻기만 합니다.

클래스는 파일 하나씩을 차지합니다. fair.c, rt.c, deadline.c, idle.c, stop_task.c와 ext/ 디렉터리입니다. 이 장은 뼈대인 core.c와 sched.h를 읽습니다. 자료구조 둘(런큐와 클래스), 정책과 우선순위, 실행 경로 둘(틱과 __schedule()), 컨텍스트 스위치 순서입니다.

4.2런큐: CPU마다 하나#

런큐(runqueue)는 한 CPU에서 실행을 기다리는 태스크를 모아 둔 자료구조입니다. 타입은 struct rq이고, CPU별 변수 runqueues로 CPU마다 하나씩 있습니다. cpu_rq(cpu)가 특정 CPU의 런큐를, this_rq()가 지금 CPU의 런큐를 돌려줍니다.

런큐를 CPU마다 두는 이유는 락입니다. 큐가 하나뿐이면 모든 CPU의 모든 스케줄링이 락 하나를 두고 다툽니다. 큐와 락을 CPU마다 따로 두면 각 CPU는 대부분의 시간에 자기 락만 잡습니다. 대가로, 한 CPU에 태스크가 몰리고 옆 CPU는 노는 일이 없도록 큐 사이의 균형을 따로 맞춰야 합니다(7장).

kernel/sched/sched.hv7.3
struct rq {
    /* ... */
    unsigned int        nr_running;
    /* ... */
#ifdef CONFIG_SCHED_PROXY_EXEC
    struct task_struct __rcu    *donor;  /* Scheduling context */
    struct task_struct __rcu    *curr;   /* Execution context */
#else
    union {
        struct task_struct __rcu *donor; /* Scheduler context */
        struct task_struct __rcu *curr;  /* Execution context */
    };
#endif
    struct task_struct  *idle;
    /* ... */
    /* runqueue lock: */
    raw_spinlock_t      __lock;
    /* ... */
    struct cfs_rq       cfs;
    struct rt_rq        rt;
    struct dl_rq        dl;
#ifdef CONFIG_SCHED_CLASS_EXT
    struct scx_rq       scx;
    struct sched_dl_entity  ext_server;
#endif
    /* ... */
    struct sched_dl_entity  fair_server;
    /* ... */
    struct task_struct  *stop;
    /* ... */
    u64         clock_task ____cacheline_aligned;
    /* ... */
    u64         clock;
    /* ... */
} __no_randomize_layout;

읽을 곳은 다섯 군데입니다.

  • nr_running: 이 CPU에서 실행 가능한 태스크의 수입니다. 모든 클래스를 합친 값입니다.
  • curr와 donor: curr는 지금 이 CPU에서 실제로 실행 중인 태스크이고, donor는 스케줄러가 돌 차례라고 뽑은 태스크입니다. 보통은 같은 태스크이고, CONFIG_SCHED_PROXY_EXEC를 끄면 union으로 아예 같은 메모리가 됩니다. 둘이 갈라지는 것은 뽑힌 태스크가 뮤텍스를 기다리는 중이어서 그 차례를 빌려 락 주인을 대신 실행할 때입니다(15장). 이 장에서는 같은 태스크로 봅니다.
  • idle과 stop: CPU마다 하나씩 있는 특별한 태스크입니다. idle은 돌릴 태스크가 없을 때 도는 swapper/N이고, stop은 다른 모든 것을 제치고 돌아야 하는 migration/N입니다.
  • cfs, rt, dl, scx: 클래스별 하위 큐입니다. 런큐는 큐 하나가 아니고, 클래스마다 자기에게 맞는 자료구조를 가집니다. fair는 RB 트리, RT는 우선순위별 리스트 배열, deadline은 데드라인 순서의 RB 트리입니다.
  • __lock: 런큐 락입니다. 런큐를 고치는 코드는 반드시 이 락을 쥡니다. raw_spinlock_t이므로 RT 커널에서도 잠들지 않는 락입니다(6장). 이름 앞의 밑줄은 직접 쓰지 말고 rq_lock() 같은 함수를 거치라는 뜻입니다. 코어 스케줄링을 켜면 SMT 형제 CPU들이 락 하나를 같이 쓰기 때문입니다.

clock과 clock_task는 런큐가 따로 가진 시계이고 시간 장부 절에서 봅니다. 태스크 쪽에서는 p->on_rq가 "런큐에 들어 있다"를, p->on_cpu가 "지금 CPU에서 실행 중이다"를 나타냅니다. 실행 중인 태스크도 런큐에 들어 있는 태스크입니다. 런큐에서 빠지는 것은 잠들 때입니다.

설계 노트

struct rq의 정의에는 배치에 대한 주석이 눈에 띕니다. 맨 앞의 nr_running부터 idle까지는 "부하 분산 코드가 락 없이 한꺼번에 읽으므로 캐시 라인 하나에 모았다"고 적혀 있고, 락과 시계들은 각각 다른 캐시 라인에 있습니다. 필드를 뜻이 가까운 것끼리가 아니라 같이 읽히는 것끼리 묶은 것입니다. 여러 CPU가 서로의 런큐를 쉴 새 없이 들여다보는 코드에서는 필드가 어느 캐시 라인에 놓이느냐가 성능을 가릅니다(13장).

4.3스케줄링 클래스#

스케줄링 클래스(scheduling class)는 정책 하나를 구현한 모듈입니다. 실체는 함수 포인터 표 struct sched_class입니다.

kernel/sched/sched.hv7.3
struct sched_class {
    /* ... */
    void (*enqueue_task) (struct rq *rq, struct task_struct *p, int flags);
    /* ... */
    bool (*dequeue_task) (struct rq *rq, struct task_struct *p, int flags);
    /* ... */
    void (*wakeup_preempt)(struct rq *rq, struct task_struct *p, int flags);
    /* ... */
    struct task_struct *(*pick_task)(struct rq *rq, struct rq_flags *rf);
    /* ... */
    void (*task_tick)(struct rq *rq, struct task_struct *p, int queued);
    /* ... */
};

뼈대는 태스크의 p->sched_class 포인터를 따라가 이 함수들을 부릅니다.

콜백 뼈대가 부르는 때
enqueue_task / dequeue_task 태스크가 실행 가능해질 때 / 잠들거나 다른 CPU로 옮겨질 때
pick_task 다음에 돌릴 태스크를 물을 때
wakeup_preempt 깨어난 태스크가 현재 태스크를 밀어내야 하는지 물을 때
task_tick 틱마다
select_task_rq 깨울 태스크를 어느 CPU에 넣을지 물을 때 (7장)

v7.3에는 클래스가 여섯 개 있습니다.

클래스 누가 쓰나
stop CPU마다 하나인 migration/N. 태스크 강제 이동처럼 무엇보다 먼저 해야 하는 일
deadline 기한이 있는 태스크. 기한이 가장 이른 것부터
rt 고정 우선순위 실시간 태스크
fair 일반 태스크. 대부분이 여기입니다
ext BPF 스케줄러가 맡은 태스크
idle CPU마다 하나인 idle 태스크

클래스 사이에는 엄격한 순서가 있습니다. 위 클래스에 실행 가능한 태스크가 하나라도 있으면 아래 클래스의 태스크는 돌지 못합니다. RT 태스크 하나가 무한 반복문을 돌면 그 CPU의 일반 태스크는 원칙적으로 영원히 기다립니다. 실제로는 이것을 막는 안전장치(fair_server)가 있고 5장에서 다룹니다.

순서는 링커가 정한다

클래스의 순서는 C 코드가 아니라 링커 스크립트에 적혀 있습니다.

include/asm-generic/vmlinux.lds.hv7.3
#define SCHED_DATA              \
    STRUCT_ALIGN();             \
    __sched_class_highest = .;      \
    *(__stop_sched_class)           \
    *(__dl_sched_class)         \
    *(__rt_sched_class)         \
    *(__fair_sched_class)           \
    *(__ext_sched_class)            \
    *(__idle_sched_class)           \
    __sched_class_lowest = .;

각 클래스는 DEFINE_SCHED_CLASS() 매크로로 정의되고, 이 매크로는 인스턴스를 자기 이름의 섹션(__fair_sched_class 등)에 넣습니다. 링커가 그 섹션들을 위 순서대로 이어 붙이면, 여섯 개의 struct sched_class가 메모리에 우선순위 순서로 나란히 놓입니다. 사실상 배열입니다.

그래서 "A 클래스가 B 클래스보다 높은가"를 묻는 sched_class_above(a, b)는 ((a) < (b)), 곧 포인터 비교 한 번입니다. "높은 클래스부터 차례로"를 뜻하는 for_each_class()는 __sched_class_highest에서 시작해 포인터를 하나씩 올리는 반복문입니다.

클래스의 크기는 제각각입니다. 가장 단순한 stop 클래스는 119줄짜리 stop_task.c가 전부이고, pick_task_stop()은 rq->stop이 실행 가능하면 그것을, 아니면 NULL을 돌려줄 뿐입니다. 같은 표를 fair 클래스는 15,000줄이 넘는 fair.c로 채웁니다.

예전 자료와 다른 점

옛 자료는 스케줄링 클래스를 next 포인터로 이어진 연결 리스트로 설명합니다. 각 클래스 정의의 첫 줄이 .next = &rt_sched_class 같은 식이었습니다. v7.3의 struct sched_class에는 next가 없고, 순서는 링커 스크립트가 정합니다. 콜백 이름도 바뀌었습니다. 옛 자료의 pick_next_task는 pick_task로, check_preempt_curr는 wakeup_preempt로 읽으면 됩니다.

DEFINE_SCHED_CLASS() 위의 주석은 아직도 "섹션이 거꾸로 놓이니 조심하라"고 적고 있지만, 위에서 본 대로 v7.3의 링커 스크립트는 높은 클래스부터 놓습니다. 주석과 코드가 어긋날 때는 코드가 맞습니다.

설계 노트

__schedule()은 fair 클래스가 RB 트리를 쓰는지, RT 클래스가 비트맵을 쓰는지 모릅니다. pick_task()를 부를 뿐입니다. 그래서 새 정책을 넣는 일의 대부분이 "표 하나를 더 채우는 일"이 됩니다. deadline 클래스와 ext 클래스가 그렇게 자기 파일을 가진 클래스로 들어왔고, fair 클래스의 알고리즘이 통째로 바뀌었을 때도(5장) 뼈대의 구조는 그대로였습니다. 함수 포인터 표는 커널이 C로 다형성을 구현하는 표준 방법이고, 25장에서 파일시스템·드라이버의 같은 패턴과 함께 다시 봅니다. 이 인터페이스는 고정된 것도 아닙니다. 콜백은 필요하면 바뀌고, 바꾸는 사람이 모든 구현을 함께 고칩니다(26장).

4.4정책과 우선순위#

유저 프로그램은 클래스를 직접 고르지 않습니다. 스케줄링 정책(scheduling policy)을 고릅니다. 정책은 sched_setattr()나 sched_setscheduler() 시스템 콜로 정하고, 커널이 정책을 클래스로 옮깁니다.

정책 값 클래스 뜻
SCHED_NORMAL 0 fair 기본값. 유저 공간 헤더의 이름은 SCHED_OTHER입니다.
SCHED_FIFO 1 rt 고정 우선순위. 양보하거나 더 높은 태스크가 올 때까지 돕니다.
SCHED_RR 2 rt FIFO와 같되, 같은 우선순위끼리는 타임 슬라이스로 돌아가며 돕니다.
SCHED_BATCH 3 fair 일반 태스크와 같되, 깨어났을 때 현재 태스크를 밀어내지 않습니다.
SCHED_IDLE 5 fair 아주 낮은 가중치의 일반 태스크. idle 클래스와는 다릅니다.
SCHED_DEADLINE 6 deadline 주기마다 정해진 실행 시간을 기한 안에 받습니다.
SCHED_EXT 7 ext BPF 스케줄러가 맡습니다.

대응을 정하는 함수는 짧습니다.

kernel/sched/core.cv7.3
const struct sched_class *__setscheduler_class(int policy, int prio)
{
    if (dl_prio(prio))
        return &dl_sched_class;

    if (rt_prio(prio))
        return &rt_sched_class;

#ifdef CONFIG_SCHED_CLASS_EXT
    if (task_should_scx(policy))
        return &ext_sched_class;
#endif

    return &fair_sched_class;
}

읽을 곳은 두 군데입니다.

  • deadline과 rt는 정책이 아니라 prio 값으로 판정합니다. 일반 태스크가 RT 태스크가 기다리는 락을 쥐고 있으면 우선순위 상속으로 prio가 잠시 RT 범위로 올라가고, 그동안은 클래스도 rt가 됩니다(15장).
  • ext는 조건부입니다. BPF 스케줄러가 올라와 있지 않으면 task_should_scx()가 거짓이고, SCHED_EXT 태스크는 fair 클래스에서 돕니다. 반대로 BPF 스케줄러가 "전부 맡겠다"고 올라오면 SCHED_NORMAL 태스크까지 ext 클래스로 옮겨집니다.

prio 숫자

task_struct에는 우선순위 필드가 넷 있습니다.

필드 뜻
static_prio nice 값에서 나온 값. 120 + nice이므로 100–139
rt_priority 실시간 우선순위. 1–99이고 클수록 높습니다. 일반 태스크는 0
normal_prio 정책과 위 두 값으로 계산한 "원래" 우선순위
prio 스케줄러가 실제로 쓰는 값. 보통 normal_prio와 같고, 우선순위 상속 중에만 다릅니다

normal_prio를 계산하는 __normal_prio()(kernel/sched/syscalls.c)는 세 갈래입니다. deadline 정책이면 MAX_DL_PRIO - 1, 실시간 정책이면 MAX_RT_PRIO - 1 - rt_priority, 그 밖에는 NICE_TO_PRIO(nice)입니다.

MAX_DL_PRIO는 0, MAX_RT_PRIO는 100입니다. 그래서 커널 안의 prio는 작을수록 높은 하나의 축이 됩니다.

유저 공간의 rt_priority 99가 커널의 prio 0이고, nice 0이 prio 120입니다. 커널 코드에서 prio를 비교하는 조건문은 "작은 쪽이 이긴다"로 읽어야 합니다.

이 축은 클래스를 가르는 데와 RT 클래스 안에서 쓰입니다. fair 클래스 안에서는 prio를 직접 비교하지 않습니다. nice 값을 가중치로 바꿔 CPU 시간의 비율을 정합니다. 5장의 내용입니다.

직접 확인하기

태스크의 정책과 우선순위를 봅니다.

터미널
$ ps -eo pid,cls,rtprio,ni,comm | head -4
    PID CLS RTPRIO  NI COMMAND
      1  TS      -   0 systemd
      2  TS      -   0 kthreadd
     18  FF     99   - migration/0

CLS 열의 TS는 SCHED_NORMAL, FF는 SCHED_FIFO입니다. migration/0은 stop 클래스의 태스크지만 유저 공간에는 SCHED_FIFO 99로 보이게 해 두었습니다. 이제 정책을 바꿔 봅니다. 실시간 정책은 root이거나 CAP_SYS_NICE가 있어야 줄 수 있습니다.

4.5틱: 주기적 스케줄러#

스케줄러 코드가 실행되는 길은 둘입니다. 타이머 인터럽트가 주기적으로 부르는 sched_tick()과, 태스크를 실제로 바꾸는 __schedule()입니다. 앞의 것을 주기적 스케줄러, 뒤의 것을 주 스케줄러라고 부르기도 합니다.

틱은 태스크를 바꾸지 않습니다. 장부를 갱신하고, 바꿔야 하면 표시만 합니다.

kernel/sched/core.cv7.3
void sched_tick(void)
{
    /* ... */
    /* scheduler accounting goes to the donor task */
    struct task_struct *curr, *donor;
    /* ... */
    rq_lock(rq, &rf);
    curr = rq->curr;
    donor = rq->donor;
    /* ... */
    update_rq_clock(rq);
    /* ... */
    donor->sched_class->task_tick(rq, donor, 0);
    /* ... */
    rq_unlock(rq, &rf);
    /* ... */
    if (!scx_switched_all()) {
        rq->idle_balance = idle_cpu(cpu);
        sched_balance_trigger(rq);
    }
}

읽을 곳은 네 군데입니다.

  • 이 함수는 타이머 인터럽트 핸들러 안에서, 인터럽트가 꺼진 채로 불립니다. 여기서 schedule()을 부를 수는 없습니다(6장의 preempt_count).
  • 런큐 락을 잡고 런큐 시계를 갱신합니다.
  • 현재 태스크의 클래스에 일을 넘깁니다. fair 클래스(task_tick_fair())는 실행 시간을 장부에 더하고, 자기 몫을 다 썼으면 재스케줄 요청 플래그를 세웁니다. RT 클래스(task_tick_rt())는 SCHED_RR 태스크의 타임 슬라이스를 하나 깎고, 0이 되면 큐 맨 뒤로 보낸 뒤 플래그를 세웁니다. SCHED_FIFO 태스크는 장부만 갱신합니다.
  • 끝에서 sched_balance_trigger()가 부하 분산을 할 때가 되었는지 확인합니다(7장).

플래그가 어디서 확인되는지는 6장이, 틱이 어떻게 만들어지고 놀고 있는 CPU에서 어떻게 멈추는지는 8장이 다룹니다.

예전 자료와 다른 점

이 함수의 이름은 오랫동안 scheduler_tick()이었습니다. v6.10에서 스케줄러 함수 이름을 sched_ 접두사로 통일하면서 sched_tick()이 되었습니다.

옛 교재는 틱의 일을 "현재 태스크의 타임 슬라이스 카운터를 1 줄이고, 0이 되면 need_resched를 세운다"고 설명합니다. v7.3에서 틱마다 카운터를 깎는 것은 SCHED_RR 태스크뿐입니다. 일반 태스크에는 깎을 카운터가 없습니다. fair 클래스는 나노초 시계로 잰 실행 시간으로 판단하고, 틱은 그 판단을 다시 해 보는 계기일 뿐입니다.

틱에만 기대면 선점의 정밀도가 틱 주기(HZ=1000이면 1ms)에 묶입니다. 그래서 태스크의 몫이 끝나는 시각에 고해상도 타이머를 따로 거는 HRTICK 기능이 있고, 이 타이머도 같은 task_tick()을 부릅니다.

4.6__schedule(): 주 스케줄러#

태스크를 바꾸는 함수는 __schedule() 하나입니다. 이 함수로 들어오는 계기는 소스의 주석이 세 가지로 정리해 두었습니다.

  1. 명시적으로 잠들 때. 뮤텍스, 세마포어, 대기 큐에서 기다리는 코드가 schedule()을 부릅니다(3장).
  2. 재스케줄 요청 플래그가 확인될 때. 인터럽트에서 돌아가는 길, 유저 모드로 돌아가는 길, preempt_enable()에서입니다(6장).
  3. 깨우기는 계기가 아닙니다. 깨우는 쪽은 태스크를 런큐에 넣고 필요하면 플래그를 세울 뿐이고, 전환은 2번 경로로 일어납니다.
kernel/sched/core.cv7.3
static void __sched notrace __schedule(int sched_mode)
{
    /* ... */
    rq = cpu_rq(cpu);
    prev = rq->curr;
    /* ... */
    local_irq_disable();
    /* ... */
    rq_lock(rq, &rf);
    /* ... */
    update_rq_clock(rq);
    /* ... */
    switch_count = &prev->nivcsw;
    /* ... */
    preempt = sched_mode == SM_PREEMPT;
    /* ... */
    prev_state = READ_ONCE(prev->__state);
    if (sched_mode == SM_IDLE) {
        /* ... */
    } else if (!preempt && prev_state) {
        /* ... */
        try_to_block_task(rq, prev, &prev_state,
                  !task_is_blocked(prev));
        switch_count = &prev->nvcsw;
    }

pick_again:
    /* ... */
    next = pick_next_task(rq, &rf);
    /* ... */
picked:
    clear_tsk_need_resched(prev);
    clear_preempt_need_resched();
    /* ... */

앞 절반입니다.

  • 인터럽트를 끄고 런큐 락을 잡습니다. 여기부터 컨텍스트 스위치가 끝날 때까지 이 CPU의 런큐는 다른 누구도 고치지 못합니다. 호출하는 쪽이 이미 선점을 꺼 두었으므로(schedule()의 preempt_disable()), 이 시점의 preempt_count는 락까지 합쳐 2입니다.
  • 잠드는 태스크를 큐에서 뺍니다. 조건은 두 가지입니다. 선점으로 들어온 것이 아니고(!preempt), 태스크 상태가 TASK_RUNNING(값 0)이 아닐 것(prev_state). 스스로 schedule()을 부른 태스크가 미리 상태를 TASK_INTERRUPTIBLE 등으로 바꿔 두었다면 여기서 런큐를 떠납니다. 선점당한 태스크는 상태가 무엇이든 큐에 남습니다. 그 이유는 6장에서 봤습니다.
  • 다음 태스크를 고르고(pick_next_task(), 다음 절), 재스케줄 요청을 지웁니다.

try_to_block_task()에는 예외가 둘 있습니다. 시그널로 깰 수 있는 상태로 잠들려는 태스크에 시그널이 이미 와 있으면, 큐에서 빼지 않고 상태를 TASK_RUNNING으로 되돌립니다. 그리고 클래스가 "지금은 빼지 않겠다"고 할 수 있습니다. dequeue_task()의 반환형이 bool인 이유입니다. fair 클래스는 받은 CPU 시간이 제 몫보다 많은 태스크가 잠들 때, 그 빚이 갚아질 때까지 큐에 남겨 둡니다. 지연 디큐(delayed dequeue)라고 하고 5장에서 다룹니다.

kernel/sched/core.cv7.3
    is_switch = prev != next;
    if (likely(is_switch)) {
        rq->nr_switches++;
        /* ... */
        RCU_INIT_POINTER(rq->curr, next);
        /* ... */
        ++*switch_count;
        /* ... */
        trace_sched_switch(preempt, prev, next, prev_state);

        /* Also unlocks the rq: */
        rq = context_switch(rq, prev, next, &rf);
    } else {
        /* ... */
        raw_spin_rq_unlock_irq(rq);
    }
    /* ... */
}

뒤 절반입니다.

  • 고른 태스크가 지금 태스크와 같으면 락을 풀고 돌아갑니다. 요청은 왔지만 다시 따져 보니 현재 태스크가 여전히 최선인 경우입니다.
  • 다르면 rq->curr를 새 태스크로 바꾸고, 컨텍스트 스위치 횟수를 올리고, sched_switch 트레이스포인트를 찍고, context_switch()를 부릅니다.
  • switch_count는 앞에서 정해 둔 포인터입니다. 스스로 잠든 경우는 nvcsw(자발적 전환), 그 밖에는 nivcsw(비자발적 전환)를 가리킵니다. /proc/PID/status의 voluntary_ctxt_switches와 nonvoluntary_ctxt_switches가 이 두 값입니다.
  • 주석대로 context_switch()가 런큐 락을 풉니다. 락은 이 함수가 잡았는데 푸는 것은 다른 함수이고, 뒤에서 보듯 다른 태스크입니다.

schedule()은 이 함수를 감싼 래퍼입니다. 잠들러 가는 길이면 먼저 모아 둔 블록 I/O 요청을 내보내고(sched_submit_work()), 선점을 끄고 __schedule(SM_NONE)을 부르고, 돌아온 뒤에도 재스케줄 요청이 남아 있으면 반복합니다.

4.7다음 태스크 고르기#

kernel/sched/core.cv7.3
static inline struct task_struct *
__pick_next_task(struct rq *rq, struct rq_flags *rf)
    __must_hold(__rq_lockp(rq))
{
    /* ... */
    if (scx_enabled())
        goto restart;

    /* ... */
    if (likely(!sched_class_above(rq->donor->sched_class, &fair_sched_class) &&
           rq->nr_running == rq->cfs.h_nr_queued)) {

        p = pick_task_fair(rq, rf);
        if (unlikely(p == RETRY_TASK))
            goto restart;

        /* Assume the next prioritized class is idle_sched_class */
        if (!p)
            p = pick_task_idle(rq, rf);

        put_prev_set_next_task(rq, rq->donor, p);
        return p;
    }

restart:
    prev_balance(rq, rf);

    for_each_active_class(class) {
        p = class->pick_task(rq, rf);
        if (unlikely(p == RETRY_TASK))
            goto restart;
        if (p) {
            put_prev_set_next_task(rq, rq->donor, p);
            return p;
        }
    }

    BUG(); /* The idle class should always have a runnable task. */
}

읽을 곳은 세 군데입니다.

  • 빠른 길. 런큐의 실행 가능한 태스크 수(nr_running)가 fair 클래스의 태스크 수(cfs.h_nr_queued)와 같으면, 다른 클래스에는 태스크가 없다는 뜻입니다. 그러면 클래스를 차례로 돌지 않고 fair 클래스에 바로 묻습니다. 대부분의 시스템이 대부분의 시간에 이 길로 갑니다. 다만 방금까지 돌던 태스크가 fair보다 높은 클래스였다면 이 길을 쓰지 않습니다. 그 클래스가 다른 CPU에서 일거리를 끌어올 기회(prev_balance())를 줘야 하기 때문입니다.
  • 일반적인 길. 높은 클래스부터 pick_task()를 부르고, 처음으로 태스크를 내놓는 클래스에서 멈춥니다. 그림 4-2의 순회입니다. for_each_active_class는 ext 클래스가 꺼져 있으면 건너뛰고, ext가 일반 태스크를 전부 맡았으면 fair를 건너뜁니다.
  • BUG(). 반복문이 끝까지 가는 일은 없습니다. idle 클래스의 pick_task_idle()은 언제나 rq->idle을 돌려주기 때문입니다. "돌릴 태스크가 없다"는 경우를 따로 처리하는 대신, 아무것도 하지 않는 태스크를 하나 둔 것입니다.

고른 뒤에는 put_prev_set_next_task()가 이전 태스크의 클래스에 put_prev_task()를, 새 태스크의 클래스에 set_next_task()를 불러 각자의 장부를 정리하게 합니다.

4.8컨텍스트 스위치#

컨텍스트 스위치(context switch)는 CPU가 실행하는 태스크를 바꾸는 일입니다. 바꿔야 하는 것은 둘입니다. 주소 공간과 CPU 상태(레지스터와 스택)입니다.

kernel/sched/core.cv7.3
context_switch(struct rq *rq, struct task_struct *prev,
           struct task_struct *next, struct rq_flags *rf)
    __releases(__rq_lockp(rq))
{
    /* ... */
    if (!next->mm) {                // to kernel
        enter_lazy_tlb(prev->active_mm, next);

        next->active_mm = prev->active_mm;
        if (prev->mm)               // from user
            mmgrab_lazy_tlb(prev->active_mm);
        else
            prev->active_mm = NULL;
    } else {                    // to user
        /* ... */
        switch_mm_irqs_off(prev->active_mm, next->mm, next);
        /* ... */
    }
    /* ... */
    prepare_lock_switch(rq, next, rf);

    /* Here we just switch the register state and the stack. */
    switch_to(prev, next, prev);
    barrier();

    return finish_task_switch(prev);
}

주소 공간

next->mm이 NULL이면 커널 스레드입니다. 커널 스레드는 유저 주소 공간이 없고, 커널 주소 공간은 모든 페이지 테이블에 똑같이 들어 있습니다. 그래서 페이지 테이블을 바꾸지 않고 직전 태스크의 것을 빌려 씁니다. active_mm이 빌린 주소 공간을 가리킵니다. TLB도 그대로 남으므로, 유저 태스크 → 커널 스레드 → 같은 유저 태스크로 돌아오는 흔한 경우에 주소 공간 전환이 한 번도 일어나지 않습니다. 이것을 lazy TLB라고 합니다.

next가 유저 태스크면 switch_mm_irqs_off()가 페이지 테이블 기준 레지스터(x86의 CR3)를 새 태스크의 것으로 바꿉니다. 페이지 테이블은 17장에서 봅니다.

레지스터와 스택

switch_to()는 아키텍처마다 구현이 다릅니다. x86-64에서는 어셈블리 함수 __switch_to_asm을 부릅니다.

arch/x86/entry/entry_64.Sv7.3
SYM_FUNC_START(__switch_to_asm)
    /* ... */
    pushq   %rbp
    pushq   %rbx
    pushq   %r12
    pushq   %r13
    pushq   %r14
    pushq   %r15

    /* switch stack */
    movq    %rsp, TASK_threadsp(%rdi)
    movq    TASK_threadsp(%rsi), %rsp
    /* ... */
    /* restore callee-saved registers */
    popq    %r15
    popq    %r14
    popq    %r13
    popq    %r12
    popq    %rbx
    popq    %rbp

    jmp __switch_to
SYM_FUNC_END(__switch_to_asm)

앞의 pushq 여섯 줄이 저장하는 것은 호출 규약에서 callee-saved로 정한 레지스터입니다. 핵심은 가운데 두 줄입니다. 지금 스택 포인터를 prev->thread.sp에 저장하고, next->thread.sp를 스택 포인터에 넣습니다. 이 두 명령어 사이에서 CPU가 딛고 선 커널 스택이 바뀝니다.

저장하는 레지스터가 여섯 개뿐인 이유가 있습니다.

  • __switch_to_asm은 C 코드에서 보통의 함수 호출로 불립니다. 호출 규약에 따라 나머지 레지스터는 호출한 쪽이 이미 챙겼습니다. 호출된 함수가 보존할 책임이 있는 레지스터(callee-saved)만 저장하면 됩니다.
  • 유저 모드의 레지스터는 이 태스크가 커널에 들어올 때 커널 스택 맨 위의 pt_regs에 이미 저장되었습니다(19장).
  • 복귀 주소도 따로 저장하지 않습니다. call 명령어가 스택에 넣어 두었습니다.

그래서 전환의 직접 비용은 작습니다. 큰 것은 간접 비용입니다. 새 태스크의 데이터는 캐시에 없고, 주소 공간이 바뀌면 TLB도 다시 채워야 합니다.

마지막 줄은 call이 아니라 jmp입니다. __switch_to()가 ret을 실행하면 새 스택에 있는 복귀 주소로 돌아갑니다. 그 주소는 next가 예전에 __switch_to_asm을 부른 바로 다음 줄입니다. next의 입장에서는 오래전에 부른 함수가 이제야 반환된 것입니다.

__switch_to()(arch/x86/kernel/process_64.c)는 스택에 담기지 않는 CPU 상태를 바꿉니다.

  • switch_fpu()는 prev의 부동소수점·벡터 레지스터를 메모리에 저장하고 TIF_NEED_FPU_LOAD 플래그를 세웁니다. next의 것은 여기서 복원하지 않고, next가 유저 모드로 돌아가기 직전에야 복원합니다. 커널 안에서만 돌다가 다시 전환되는 태스크는 복원 비용을 치르지 않습니다.
  • 스레드 로컬 저장소가 쓰는 FS·GS 베이스를 바꿉니다.
  • CPU별 변수 current_task에 next를 씁니다. current 매크로가 읽는 변수이므로, 이 줄부터 current가 next를 가리킵니다(2장).
  • 끝에서 prev_p를 반환합니다. 이 값이 뒤에서 쓰입니다.

세 번째 태스크

switch_to(prev, next, prev)는 인자가 셋입니다. x86에서 switch_to(prev, next, last)는 last = __switch_to_asm(prev, next)로 펼쳐지는 매크로입니다(arch/x86/include/asm/switch_to.h). 반환값을 세 번째 인자에 넣는데, context_switch()는 그 자리에 prev를 넘겼습니다. 즉 스위치에서 돌아오면 지역 변수 prev가 덮어써집니다. 왜 그래야 할까요.

태스크 A가 context_switch(rq, A, B)를 불러 B로 넘어갔다고 합시다. A의 커널 스택에는 지역 변수 prev = A, next = B가 남은 채로 얼어붙습니다. 나중에 어떤 태스크 C가 context_switch(rq, C, A)를 부르면 A가 다시 실행됩니다. A는 자기 스택에서 깨어나므로 지역 변수는 예전 그대로입니다. 그런데 A가 뒷정리해 줘야 할 직전 태스크는 C이고, A의 스택에는 C에 대한 정보가 없습니다.

그 정보를 실어 나르는 것이 반환값입니다. C가 부른 __switch_to(C, A)는 C를 반환합니다. 반환값은 레지스터(%rax)에 실리고, 레지스터는 스택이 바뀌어도 그대로입니다. A의 스택 위에서 실행이 재개될 때 %rax에는 C가 들어 있고, 매크로가 그 값을 prev에 넣습니다.

뒷정리

finish_task_switch(prev)는 새 태스크의 스택 위에서 직전 태스크의 뒷정리를 합니다.

  • prev->on_cpu를 0으로 내립니다. 이 순간부터 prev는 다른 CPU에서 깨어나 실행될 수 있습니다. 스위치가 끝나기 전에 내리면 한 태스크가 두 CPU에서 같은 스택으로 실행됩니다.
  • 런큐 락을 풉니다. 이 락은 prev가 __schedule()에서 잡은 것입니다. 잡은 태스크와 푸는 태스크가 다른, 커널에서 드문 경우입니다.
  • prev가 TASK_DEAD였다면 여기서 task_struct의 참조를 놓습니다. 죽는 태스크는 자기 스택 위에서 자기 스택을 해제할 수 없으므로, 마지막 정리는 다음 태스크가 대신 해 줍니다(3장).

갓 만들어진 태스크는 __switch_to_asm을 부른 적이 없습니다. 그래서 fork 때 커널이 새 태스크의 스택을 "마치 부른 적이 있는 것처럼" 꾸며 둡니다. 복귀 주소 자리에 ret_from_fork_asm을 넣어 두면, 첫 스위치의 ret이 그리로 가고, 거기서 schedule_tail()이 같은 finish_task_switch()를 부릅니다(1장).

설계 노트

잠든 태스크는 모두 같은 자리에서 멈춰 있습니다. CPU를 쥐고 있지 않은 태스크는 예외 없이 __switch_to_asm의 스택 교체 지점에 서 있습니다. 시스템 콜에서 잠들었든, 인터럽트 복귀 길에 선점당했든, 방금 fork로 만들어졌든 같습니다. 그래서 스위치 코드는 "이 태스크가 어디서 멈췄나"를 구분하지 않고 20줄 남짓한 어셈블리 하나로 끝납니다. 태스크마다 다른 사정은 그 태스크의 커널 스택에 함수 호출 사슬로 쌓여 있고 ret이 차례로 풀어 줍니다. 경우의 수를 코드로 나열하는 대신 모든 경우를 한 가지 모양으로 만든 것입니다.

4.9시간 장부#

스케줄러의 모든 판단은 "누가 얼마나 돌았나"에서 시작합니다. 그 장부의 바탕은 런큐가 가진 시계입니다.

시계 뜻
rq->clock 이 CPU의 나노초 시계. update_rq_clock()이 갱신합니다.
rq->clock_task 위에서 인터럽트 처리 시간과 하이퍼바이저에 빼앗긴 시간을 뺀 것(해당 빌드 옵션이 켜져 있을 때). 태스크가 실제로 일한 시간만 흐릅니다.
rq->clock_pelt CPU의 속도에 맞춰 늘이고 줄인 것. 부하 추적(PELT)이 씁니다(7장).

시계는 저절로 흐르지 않습니다. __schedule()과 sched_tick()의 앞머리에 있던 update_rq_clock()처럼, 런큐 락을 잡은 코드가 명시적으로 갱신합니다. 한 번의 락 구간 안의 모든 계산은 같은 "지금"을 씁니다.

태스크의 실행 시간은 이 시계의 차이로 잽니다.

kernel/sched/fair.cv7.3
static s64 update_se(struct rq *rq, struct sched_entity *se)
{
    u64 now = rq_clock_task(rq);
    s64 delta_exec;

    delta_exec = now - se->exec_start;
    if (unlikely(delta_exec <= 0))
        return delta_exec;

    se->exec_start = now;
    if (entity_is_task(se)) {
        struct task_struct *running = rq->curr;
        /* ... */
        running->se.sum_exec_runtime += delta_exec;
        /* ... */
    }
    /* ... */
    return delta_exec;
}

exec_start는 "마지막으로 장부를 적은 시각"입니다. 지금 시각과의 차이를 sum_exec_runtime에 더합니다. 이 계산은 틱마다, 그리고 태스크가 큐에 들어가고 나갈 때마다 일어나므로, 틱 사이에 태스크가 여러 번 바뀌어도 각자 돈 시간이 나노초 단위로 나뉩니다.

clock_gettime(CLOCK_THREAD_CPUTIME_ID)가 돌려주는 값이 sum_exec_runtime입니다. 각 클래스는 delta_exec을 받아 자기 방식으로 가공합니다. fair 클래스는 가중치로 나눠 vruntime에 더하고, deadline 클래스는 남은 실행 예산에서 뺍니다.

태스크 하나의 장부를 봅니다.

터미널

시스템 전체의 컨텍스트 스위치는 vmstat 1의 cs 열로, 누가 누구로 바뀌는지는 __schedule()에 있던 sched_switch 트레이스포인트로 봅니다.

정리#

  • 스케줄러는 뼈대(core.c)와 정책(스케줄링 클래스)으로 나뉩니다. 뼈대는 언제, 어떻게 바꿀지를 맡고 클래스는 누구를 고를지를 맡습니다.
  • 런큐 struct rq는 CPU마다 하나이고, 그 안에 클래스별 하위 큐가 따로 있습니다. 런큐를 고치려면 런큐 락을 쥡니다.
  • 클래스는 stop, deadline, rt, fair, ext, idle 여섯 개입니다. 순서는 링커 스크립트가 정하고, 높은 클래스에 태스크가 있으면 낮은 클래스는 돌지 못합니다.
  • 유저 공간은 정책(SCHED_*)을 고르고 커널이 클래스로 옮깁니다. 커널 안의 prio는 작을수록 높고, −1은 deadline, 0–99는 RT, 100–139는 nice −20…19입니다.
  • 틱(sched_tick())은 장부를 갱신하고 플래그를 세울 뿐입니다. 태스크를 바꾸는 것은 __schedule()입니다.
  • __schedule()은 런큐 락을 잡고, 잠드는 태스크를 큐에서 빼고, 클래스에 다음 태스크를 묻고, 다르면 컨텍스트 스위치를 합니다.
  • 컨텍스트 스위치는 주소 공간 전환과 커널 스택 전환입니다. x86-64에서 직접 저장하는 것은 callee-saved 레지스터 여섯 개와 스택 포인터입니다. 잠든 태스크는 모두 __switch_to_asm 안의 같은 자리에 멈춰 있고, 깨어난 태스크가 직전 태스크의 뒷정리를 합니다.

확인 문제#

SCHED_FIFO 우선순위 50인 태스크 하나가 CPU 0에서 무한 반복문을 돌고 있습니다. 같은 CPU의 nice −20 일반 태스크는 __pick_next_task()에서 왜 선택되지 않습니까? 빠른 길과 일반적인 길 가운데 어느 쪽으로 갑니까?

답 보기

런큐에 RT 태스크가 있으므로 rq->nr_running이 rq->cfs.h_nr_queued보다 큽니다. 빠른 길의 조건이 거짓이 되어 일반적인 길로 갑니다. 클래스 순회는 stop, deadline, rt 순서로 pick_task()를 부르고, rt 클래스가 FIFO 태스크를 내놓는 순간 반환합니다. nice 값은 fair 클래스 안에서만 뜻이 있습니다. (실제로는 fair_server가 일반 태스크에 최소한의 시간을 보장합니다. 5장.)

태스크가 set_current_state(TASK_INTERRUPTIBLE)을 한 직후 인터럽트가 와서 선점당했습니다. __schedule()은 이 태스크를 런큐에서 뺍니까? 코드의 어느 조건이 그것을 정합니까?

답 보기

빼지 않습니다. 인터럽트 복귀 길의 선점은 __schedule(SM_PREEMPT)로 들어오므로 preempt가 참입니다. 큐에서 빼는 try_to_block_task()는 !preempt && prev_state일 때만 불립니다. 태스크는 상태가 TASK_INTERRUPTIBLE인 채로 런큐에 남고, 다시 실행되면 하려던 조건 확인과 schedule() 호출을 이어서 합니다.

__switch_to_asm이 %rax, %rcx, %rdx 같은 레지스터를 저장하지 않아도 되는 이유는 무엇입니까? 유저 모드에서 쓰던 %rax는 어디에 있습니까?

답 보기

__switch_to_asm은 C 코드에서 보통의 함수로 호출됩니다. 호출 규약에서 %rax, %rcx, %rdx 등은 호출한 쪽이 보존할 책임이 있으므로 컴파일러가 이미 챙겼습니다. 호출된 함수가 책임지는 %rbp, %rbx, %r12–%r15만 저장하면 됩니다. 유저 모드의 %rax는 이 태스크가 커널에 들어올 때 커널 스택 맨 위의 pt_regs에 저장되었습니다.

context_switch()의 마지막 줄 finish_task_switch(prev)에서 prev는 이 함수가 인자로 받은 그 prev입니까?

답 보기

아닐 수 있습니다. switch_to(prev, next, prev)는 __switch_to_asm의 반환값을 prev에 대입합니다. 이 태스크가 다시 실행될 때 반환값 레지스터에는 방금 이 태스크로 전환해 준 태스크가 들어 있으므로, 스위치 뒤의 prev는 CPU를 넘겨준 상대입니다. finish_task_switch()는 그 태스크의 on_cpu를 내리고, 그 태스크가 잡아 둔 런큐 락을 풉니다.

용어#

런큐runqueue
한 CPU에서 실행 가능한 태스크를 담는 자료구조. struct rq이고 CPU마다 하나다.
스케줄링 클래스scheduling class
스케줄링 정책 하나를 구현한 함수 포인터 표. struct sched_class.
스케줄링 정책scheduling policy
유저 공간이 태스크에 지정하는 SCHED_NORMAL, SCHED_FIFO 같은 값. 커널이 클래스로 옮긴다.
prio
스케줄러가 쓰는 태스크의 우선순위. 작을수록 높다. 0–99는 RT, 100–139는 일반 태스크.
틱tick
주기적인 타이머 인터럽트. 스케줄러에서는 sched_tick()을 부른다.
컨텍스트 스위치context switch
CPU가 실행하는 태스크를 바꾸는 일. 주소 공간, 커널 스택, 레지스터를 바꾼다.
rq->curr, rq->donor
이 CPU에서 지금 실행 중인 태스크와, 스케줄러가 돌 차례라고 뽑은 태스크. 프록시 실행이 아니면 같다.
lazy TLB
커널 스레드로 전환할 때 페이지 테이블을 바꾸지 않고 직전 태스크의 것을 빌려 쓰는 최적화.
자발적 전환voluntary context switch
태스크가 스스로 잠들어 일어난 전환. nvcsw로 센다. 그 밖의 전환은 nivcsw.
