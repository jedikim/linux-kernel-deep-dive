인터럽트 하드웨어

PIC에서 APIC·MSI로, IDT에서 FRED로

Linux v7.3 기준약 50분
읽는 소스arch/x86/include/asm/irq_vectors.harch/x86/kernel/i8259.carch/x86/include/asm/apic.harch/x86/include/asm/io_apic.harch/x86/kernel/apic/apic.carch/x86/kernel/idt.carch/x86/include/asm/idtentry.harch/x86/entry/entry_64.S

키보드를 누르거나 패킷이 도착하면 그 사실이 CPU에 닿아야 합니다. CPU는 프로그램을 실행하느라 바쁘고, 장치는 수백 개이고, CPU도 여러 개입니다. 장치 하나가 선 하나를 올리던 방식은 CPU가 하나이던 시절의 것입니다. 이 장은 신호가 장치에서 출발해 커널의 첫 명령어에 닿기까지 거치는 하드웨어를 따라갑니다. 인터럽트 컨트롤러가 PIC에서 APIC과 MSI로, CPU의 진입 방식이 IDT에서 FRED로 바뀐 까닭도 함께 봅니다.

이 장에서 답하는 질문
  • CPU는 실행 중인 프로그램을 언제, 어떻게 끊고 핸들러로 넘어가는가?
  • 예외와 인터럽트는 무엇이 다르고, 벡터 번호는 어떻게 나뉘어 있는가?
  • 8259 PIC의 구조는 왜 멀티프로세서에 맞지 않았고, APIC은 무엇을 바꾸었는가?
  • MSI는 핀 없이 어떻게 인터럽트를 전달하는가?
  • IDT로 진입할 때 CPU가 하는 일과 커널 진입 코드가 하는 일은 어디서 갈리는가?
  • FRED는 IDT 방식의 어떤 문제를 하드웨어에서 없앴는가?

9.1폴링과 인터럽트#

장치가 일을 마쳤는지 CPU가 아는 방법은 둘입니다. 폴링(polling)은 CPU가 장치의 상태 레지스터를 주기적으로 읽어 확인하는 방식입니다. 일이 없을 때도 읽어야 하고, 읽는 주기만큼 반응이 늦습니다. 인터럽트(interrupt)는 장치가 신호를 보내 CPU가 하던 일을 멈추게 하는 방식입니다.

CPU가 신호를 받아들이는 시점은 정해져 있습니다. 명령어 하나를 끝낼 때마다 요청이 있는지 확인합니다.

요청을 받아들이면 CPU는 세 가지를 합니다. 어떤 인터럽트인지 나타내는 벡터(vector) 번호를 얻고, 돌아올 자리를 스택에 저장하고, 벡터에 해당하는 핸들러 주소로 점프합니다. x86에는 RFLAGS 레지스터에 IF 비트가 있어서, 이 비트가 0이면 CPU는 요청이 있어도 받지 않고 다음 명령어로 갑니다. cli와 sti 명령어가 이 비트를 끄고 켭니다. 커널의 local_irq_disable()이 하는 일이 이것입니다.

폴링이 사라진 것은 아닙니다. 패킷이 초당 수십만 개씩 오면 패킷마다 인터럽트를 받는 비용이 더 큽니다. 그래서 네트워크 스택은 첫 인터럽트만 받고 나머지는 폴링으로 걷어 갑니다(12장).

9.2예외와 인터럽트#

CPU의 실행 흐름을 끊는 사건은 출처에 따라 나뉩니다.

  • 예외(exception)는 CPU가 명령어를 실행하다가 스스로 일으킵니다. 0으로 나누거나, 매핑되지 않은 주소를 읽은 경우입니다. 같은 명령어를 같은 상태에서 실행하면 언제나 같은 자리에서 생깁니다.
  • 인터럽트는 CPU 바깥에서 옵니다. 실행 중인 명령어와 상관없이 아무 때나 옵니다. IF 비트로 막을 수 있는 것과 막을 수 없는 NMI(non-maskable interrupt)가 있습니다. NMI는 하드웨어 오류 통지와 워치독처럼 인터럽트가 꺼져 있어도 닿아야 하는 일에 씁니다.
  • 소프트웨어 인터럽트는 프로그램이 int n 명령어로 일부러 일으킵니다. 32비트 시스템 콜의 int 0x80이 대표적입니다. 커널의 softirq(11장)와는 이름만 비슷하고 다른 것입니다.

예외는 돌아오는 자리에 따라 다시 셋으로 나뉩니다.

종류 저장되는 RIP 예
폴트(fault) 예외를 일으킨 명령어. 원인을 고친 뒤 다시 실행합니다. 페이지 폴트(#PF), 일반 보호 오류(#GP)
트랩(trap) 다음 명령어 브레이크포인트(#BP)
어보트(abort) 믿을 수 없음. 이어 갈 수 없습니다. 이중 폴트(#DF), 머신 체크(#MC)

이 모든 사건에 0부터 255까지의 벡터 번호가 붙습니다. 리눅스가 256개를 나눠 쓰는 방식은 헤더의 주석에 있습니다.

arch/x86/include/asm/irq_vectors.hv7.3
 *  Vectors   0 ...  31 : system traps and exceptions - hardcoded events
 *  Vectors  32 ... 127 : device interrupts
 *  Vector  128         : legacy int80 syscall interface
 *  Vectors 129 ... FIRST_SYSTEM_VECTOR-1 : device interrupts
 *  Vectors FIRST_SYSTEM_VECTOR ... 255   : special interrupts

0–31은 인텔이 예외용으로 정해 둔 번호입니다. 맨 뒤의 시스템 벡터는 커널이 자기 용도로 고정해 둔 것으로, Local APIC 타이머(8장)와 CPU끼리 주고받는 IPI가 여기에 있습니다. v7.3에서 FIRST_SYSTEM_VECTOR는 0xeb입니다. 그 사이, FIRST_EXTERNAL_VECTOR(0x20)부터의 200개 남짓이 장치 인터럽트 몫입니다.

200개는 장치 수에 견주어 적어 보이지만, 장치 벡터는 CPU마다 따로 배정합니다(arch/x86/kernel/apic/vector.c). CPU 0의 벡터 0x41과 CPU 1의 벡터 0x41은 서로 다른 장치의 것일 수 있습니다. 쓸 수 있는 벡터는 CPU 수만큼 늘어납니다. 배정 방식은 10장에서 봅니다.

9.38259 PIC#

장치는 많고 CPU의 인터럽트 입력은 하나입니다. 그 사이에서 요청을 모으고, 순서를 정하고, 어떤 장치인지 번호로 알려 주는 칩이 인터럽트 컨트롤러입니다. PC의 첫 컨트롤러는 인텔 8259A, 흔히 PIC(programmable interrupt controller)라고 부르는 칩입니다.

PIC에는 장치의 선(IRQ 선)이 8개 들어옵니다. 요청은 내부 레지스터 셋을 차례로 거칩니다.

  • IMR(interrupt mask register): 선마다 1비트. 1이면 그 선의 요청을 막습니다. 커널이 특정 IRQ를 끄는 수단입니다.
  • IRR(interrupt request register): 요청이 들어왔지만 아직 CPU에 넘기지 못한 선을 기억합니다.
  • ISR(in-service register): CPU가 받아 가서 처리 중인 선을 기억합니다. 이 비트가 서 있는 동안 PIC은 그보다 우선순위가 낮은 요청을 CPU에 올리지 않습니다.

IRR에 있는 요청 가운데 우선순위가 가장 높은 것을 골라 INTR 선을 올리면, CPU가 INTA로 응답하고, PIC이 데이터 버스에 벡터 번호를 실어 줍니다. 벡터 번호는 "기준값 + 선 번호"입니다. 기준값은 초기화할 때 커널이 써 넣습니다.

arch/x86/kernel/i8259.cv7.3
static void init_8259A(int auto_eoi)
{
    /* ... */
    outb(0xff, PIC_MASTER_IMR); /* mask all of 8259A-1 */

    /*
     * outb_pic - this has to work on a wide range of PC hardware.
     */
    outb_pic(0x11, PIC_MASTER_CMD); /* ICW1: select 8259A-1 init */

    /* ICW2: 8259A-1 IR0-7 mapped to ISA_IRQ_VECTOR(0) */
    outb_pic(ISA_IRQ_VECTOR(0), PIC_MASTER_IMR);

    /* 8259A-1 (the master) has a slave on IR2 */
    outb_pic(1U << PIC_CASCADE_IR, PIC_MASTER_IMR);
    /* ... */
}

읽을 곳은 세 군데입니다.

  • 모든 접근이 outb()입니다. PIC의 레지스터는 포트 0x20과 0x21에 있습니다. 포트 I/O는 마지막 절에서 봅니다.
  • ICW2에 써 넣는 ISA_IRQ_VECTOR(0)이 기준값입니다. 값은 0x30이므로 IRQ 1(키보드)은 벡터 0x31이 됩니다.
  • 선이 8개로는 모자라서 PIC을 하나 더 달았습니다. 둘째 PIC의 출력을 첫째의 2번 선에 연결합니다. 이것이 캐스케이드(cascade)이고, IRQ 2가 비어 있고 IRQ가 0–15까지 있는 이유입니다.

핸들러가 끝나면 커널은 PIC에 EOI(end of interrupt)를 보내 ISR 비트를 지웁니다. 이것을 빠뜨리면 그 선과 그보다 낮은 선의 인터럽트가 다시는 오지 않습니다.

이 구조에는 한계가 뚜렷합니다. INTR 선이 하나라서 CPU 하나에만 전달할 수 있습니다. 선이 15개뿐이라 장치들이 선을 나눠 써야 합니다. 우선순위가 선 번호로 고정되어 있습니다.

예전 자료와 다른 점

많은 교재가 "장치 → PIC → CPU"를 인터럽트의 기본 그림으로 그립니다. 지금의 x86 PC에서 PIC은 호환성을 위해 칩셋 안에 남아 있을 뿐이고, IO-APIC이 있는 시스템에서 커널은 옛 IRQ를 IO-APIC 쪽으로 옮기면서 PIC 쪽 선을 마스크합니다. 드라이버 arch/x86/kernel/i8259.c는 v7.3에도 있습니다. /proc/interrupts의 장치 줄에 XT-PIC이 보인다면 IO-APIC 없이 PIC으로 받고 있다는 뜻입니다. IMR, IRR, ISR, EOI라는 개념은 그대로 Local APIC으로 이어졌으므로 알아 둘 가치가 있습니다.

9.4APIC#

APIC(advanced PIC)은 컨트롤러를 둘로 쪼갰습니다. CPU마다 하나씩 붙는 Local APIC과, 장치 쪽에 있는 IO-APIC입니다. 둘 사이는 선이 아니라 메시지로 이어집니다.

Local APIC

Local APIC은 CPU 안에 들어 있고 세 가지 일을 합니다.

  • 받기. 자기 앞으로 온 메시지를 받아 IRR에 적고, 우선순위를 따져 CPU 코어에 인터럽트를 겁니다. PIC의 IRR·ISR·EOI가 여기에 벡터 256개 크기로 들어 있습니다. 우선순위는 벡터 번호의 위쪽 4비트이고, 태스크 우선순위 레지스터(TPR)보다 낮은 것은 보류합니다.
  • 자기 CPU만의 인터럽트 만들기. 타이머, 성능 카운터 넘침, 온도 경고 같은 것입니다. 각각 어떤 벡터로 전달할지를 LVT(local vector table) 레지스터에 적어 둡니다.
  • 보내기. 인터럽트 명령 레지스터(ICR)에 목적지와 벡터를 쓰면 다른 CPU의 Local APIC으로 메시지가 갑니다. 이것이 IPI(inter-processor interrupt)입니다. 다른 CPU를 재스케줄시키거나(6장) TLB를 비우게 할 때 씁니다.

레지스터에 접근하는 방법은 두 세대가 있습니다. xAPIC은 물리 주소 0xfee00000부터 4KB에 레지스터를 매핑합니다. x2APIC은 같은 레지스터를 MSR 0x800번대로 옮기고 APIC ID를 8비트에서 32비트로 늘렸습니다. APIC ID가 8비트를 넘는 큰 시스템은 x2APIC이어야 합니다. EOI를 보내는 두 함수를 나란히 놓으면 차이가 보입니다.

arch/x86/include/asm/apic.hv7.3
static inline void native_apic_mem_eoi(void)
{
    native_apic_mem_write(APIC_EOI, APIC_EOI_ACK);
}
/* ... */
static inline void native_apic_msr_eoi(void)
{
    native_wrmsrq(APIC_BASE_MSR + (APIC_EOI >> 4), APIC_EOI_ACK);
}

같은 EOI 레지스터(0xb0)에 0을 쓰는 일인데, 앞의 것은 메모리 쓰기이고 뒤의 것은 MSR 쓰기입니다. 커널의 나머지 코드는 apic_eoi()만 부르고, 어느 쪽으로 갈지는 부팅 때 스태틱 콜(25장)로 정해집니다. PIC의 EOI가 "몇 번 선을 끝냈다"고 알려 주는 것과 달리 Local APIC의 EOI에는 번호가 없습니다. ISR에서 우선순위가 가장 높은 비트가 지워집니다.

IO-APIC

IO-APIC에는 장치의 인터럽트 선이 핀으로 들어옵니다. 핀마다 리다이렉션 테이블 항목이 하나씩 있고, 커널이 여기에 "이 핀의 요청을 어떤 메시지로 바꿀지"를 써 넣습니다.

arch/x86/include/asm/io_apic.hv7.3
struct IO_APIC_route_entry {
    union {
        struct {
            u64 vector          :  8,
                delivery_mode       :  3,
                dest_mode_logical   :  1,
                delivery_status     :  1,
                active_low      :  1,
                irr         :  1,
                is_level        :  1,
                masked          :  1,
                reserved_0      : 15,
                reserved_1      : 17,
                virt_destid_8_14    :  7,
                destid_0_7      :  8;
        };
        /* ... */
    };
} __attribute__ ((packed));

64비트 한 항목에 핀 하나의 설정이 모두 들어 있습니다. PIC에서는 칩 전체에 하나뿐이던 벡터 기준값이 핀마다 따로 있고, PIC에는 없던 목적지가 생겼습니다. vector는 벡터 번호, destid는 목적지 APIC ID, masked는 마스크입니다. is_level과 active_low는 선의 신호 방식입니다. 에지 트리거(edge-triggered)는 전압이 바뀌는 순간을, 레벨 트리거(level-triggered)는 전압이 유지되는 동안을 요청으로 봅니다. 이 차이를 커널이 어떻게 다루는지는 10장에서 봅니다.

delivery_mode는 목적지를 고르는 방식입니다. 한 CPU를 지정하는 고정(fixed) 방식과, 여러 후보 가운데 우선순위가 가장 낮은 CPU에게 하드웨어가 알아서 보내는 방식(lowest priority)이 있습니다. 예전 자료는 앞의 것을 정적 분배, 뒤의 것을 동적 분배라고 부릅니다. v7.3의 x86 코드는 고정 방식만 씁니다. 어느 CPU가 받을지는 하드웨어가 아니라 커널이 친화성 설정에 따라 정해서 써 넣습니다(10장).

9.5MSI와 MSI-X#

IO-APIC의 핀은 결국 선입니다. 장치가 늘면 선이 모자라고, 선을 나눠 쓰면 핸들러들이 "내 장치인가"를 일일이 확인해야 합니다. MSI(message signaled interrupts)는 선을 없앱니다. 장치가 정해진 주소에 정해진 값을 쓰는 것이 곧 인터럽트입니다.

어떤 주소에 어떤 값을 쓸지는 커널이 정해서 장치에 알려 줍니다. x86에서 그 값을 만드는 함수입니다.

arch/x86/kernel/apic/apic.cv7.3
void __irq_msi_compose_msg(struct irq_cfg *cfg, struct msi_msg *msg,
               bool dmar)
{
    memset(msg, 0, sizeof(*msg));

    msg->arch_addr_lo.base_address = X86_MSI_BASE_ADDRESS_LOW;
    msg->arch_addr_lo.dest_mode_logical = apic->dest_mode_logical;
    msg->arch_addr_lo.destid_0_7 = cfg->dest_apicid & 0xFF;

    msg->arch_data.delivery_mode = APIC_DELIVERY_MODE_FIXED;
    msg->arch_data.vector = cfg->vector;
    /* ... */
}

주소의 위쪽 12비트는 0xfee로 고정입니다. Local APIC이 있는 바로 그 주소 영역입니다. 주소의 가운데에 목적지 APIC ID가, 데이터에 벡터 번호가 들어갑니다. IO-APIC의 리다이렉션 항목에 있던 정보가 주소와 데이터 한 쌍으로 옮겨 온 셈입니다. 장치가 이 주소에 쓰면 메모리에 저장되지 않고 목적지 CPU의 Local APIC에 메시지로 전달됩니다.

MSI에는 두 판이 있습니다. 처음의 MSI는 장치당 주소·데이터 한 쌍에 연속된 벡터 최대 32개입니다. MSI-X는 장치의 메모리 영역에 표를 두고 항목마다 주소·데이터·마스크를 따로 가집니다. 최대 2048개이고 항목마다 다른 CPU로 보낼 수 있습니다. NVMe SSD와 서버용 네트워크 카드는 이것으로 큐마다 벡터를 하나씩 두고, 큐를 CPU에 하나씩 짝지어 줍니다.

주소의 목적지 칸은 8비트뿐입니다. 더 큰 APIC ID로 보내려면, 그리고 장치가 엉뚱한 벡터를 쏘지 못하게 하려면 인터럽트 리매핑(interrupt remapping)이 필요합니다. 장치는 주소에 CPU 번호가 아니라 표의 인덱스를 싣고, IOMMU가 그 표를 찾아 실제 목적지와 벡터로 바꿉니다. 표는 커널만 고칠 수 있습니다.

PCI Express 장치는 MSI나 MSI-X 지원이 필수입니다. 그래서 요즘 PC에서 IO-APIC 핀을 쓰는 것은 키보드 컨트롤러, 직렬 포트, ACPI 이벤트 같은 옛 장치 몇 개뿐입니다.

9.6IDT와 진입 스텁#

메시지가 Local APIC에 닿고 CPU가 벡터 번호를 얻은 다음부터는 CPU와 커널의 일입니다. 벡터로 핸들러 주소를 찾는 표가 IDT(interrupt descriptor table)입니다. 256칸이고 한 칸을 게이트(gate)라고 합니다.

리눅스는 게이트를 표로 선언해 둡니다.

arch/x86/kernel/idt.cv7.3
/* Interrupt gate */
#define INTG(_vector, _addr)                \
    G(_vector, _addr, DEFAULT_STACK, GATE_INTERRUPT, DPL0, __KERNEL_CS)

/* System interrupt gate */
#define SYSG(_vector, _addr)                \
    G(_vector, _addr, DEFAULT_STACK, GATE_INTERRUPT, DPL3, __KERNEL_CS)
/* ... */
#define ISTG(_vector, _addr, _ist)          \
    G(_vector, _addr, _ist + 1, GATE_INTERRUPT, DPL0, __KERNEL_CS)
arch/x86/kernel/idt.cv7.3
static const __initconst struct idt_data def_idts[] = {
    INTG(X86_TRAP_DE,       asm_exc_divide_error),
    ISTG(X86_TRAP_NMI,      asm_exc_nmi, IST_INDEX_NMI),
    /* ... */
    INTG(X86_TRAP_GP,       asm_exc_general_protection),
    /* ... */
    ISTG(X86_TRAP_DF,       asm_exc_double_fault, IST_INDEX_DF),
    /* ... */
    SYSG(X86_TRAP_OF,       asm_exc_overflow),
};

게이트의 종류는 셋이고 차이는 인자 둘입니다.

  • DPL: 유저 프로그램이 int n 명령어로 이 벡터를 직접 부를 수 있는지를 정합니다. SYSG(DPL 3)는 int3, into, int 0x80에만 씁니다. 나머지는 DPL 0이어서, 유저 프로그램이 int 14로 가짜 페이지 폴트를 만들려 하면 #GP가 납니다.
  • IST 번호: 0이 아니면 CPU가 무조건 TSS의 ist[n]에 적힌 전용 스택으로 갈아탑니다. 커널 스택이 망가진 상태에서도 처리해야 하는 예외에 씁니다. v7.3에서는 #DF, NMI, #DB, #MC, #VC 다섯입니다.
예전 자료와 다른 점

교재는 게이트를 인터럽트 게이트와 트랩 게이트로 나누고, 예외는 트랩 게이트(진입할 때 IF를 그대로 둠)로, 인터럽트는 인터럽트 게이트(IF를 0으로 만듦)로 건다고 설명합니다. 하드웨어의 구분은 그대로이지만 v7.3의 idt.c에는 트랩 게이트가 없습니다. 위 매크로에서 보듯 모든 게이트가 GATE_INTERRUPT입니다. 예외든 인터럽트든 인터럽트가 꺼진 채로 진입하고, 켜도 되는 시점은 C 코드가 정합니다. 진입 직후의 몇 명령어 동안 인터럽트가 끼어들 수 있으면 따져야 할 경우가 너무 많아지기 때문입니다.

스택과 프레임

CPU는 게이트를 읽은 뒤 스택을 고릅니다. 유저 모드에서 왔으면 TSS의 sp0에 적힌 커널 스택으로 바꿉니다. 유저 스택은 믿을 수 없기 때문입니다. 커널 모드에서 왔고 IST 지정이 없으면 쓰던 스택을 그대로 씁니다. 그리고 그 스택에 SS, RSP, RFLAGS, CS, RIP를 쌓습니다. 일부 예외에서는 오류 코드도 쌓습니다.

여기까지가 CPU의 몫이고 남은 것은 전부 소프트웨어가 합니다. 장치 인터럽트의 진입점은 벡터마다 하나씩 있는 작은 스텁입니다.

arch/x86/include/asm/idtentry.hv7.3
    .align IDT_ALIGN
SYM_CODE_START(irq_entries_start)
    vector=FIRST_EXTERNAL_VECTOR
    .rept NR_EXTERNAL_VECTORS
    UNWIND_HINT_IRET_REGS
0 :
    ENDBR
    .byte   0x6a, vector
    jmp asm_common_interrupt
    /* Ensure that the above is IDT_ALIGN bytes max */
    .fill 0b + IDT_ALIGN - ., 1, 0xcc
    vector = vector+1
    .endr
SYM_CODE_END(irq_entries_start)

.rept가 같은 코드를 벡터 수만큼 찍어 냅니다. 스텁이 하는 일은 자기 벡터 번호를 스택에 넣고(0x6a는 push imm8의 기계어) 공통 진입점으로 뛰는 것뿐입니다. CPU는 핸들러에게 벡터 번호를 알려 주지 않습니다. 어느 스텁으로 들어왔는지가 유일한 정보이므로 스텁이 벡터마다 따로 있어야 합니다.

공통 진입점은 먼저 error_entry를 부릅니다.

arch/x86/entry/entry_64.Sv7.3
SYM_CODE_START(error_entry)
    /* ... */
    PUSH_AND_CLEAR_REGS save_ret=1
    ENCODE_FRAME_POINTER 8

    testb   $3, CS+8(%rsp)
    jz  .Lerror_kernelspace

    /*
     * We entered from user mode or we're pretending to have entered
     * from user mode due to an IRET fault.
     */
    swapgs
    FENCE_SWAPGS_USER_ENTRY
    /* We have user CR3.  Change to kernel CR3. */
    SWITCH_TO_KERNEL_CR3 scratch_reg=%rax
    /* ... */
    leaq    8(%rsp), %rdi           /* arg0 = pt_regs pointer */
    /* Put us onto the real thread stack. */
    jmp sync_regs
  • PUSH_AND_CLEAR_REGS가 범용 레지스터를 모두 스택에 넣습니다. CPU가 쌓은 다섯 칸과 합쳐 struct pt_regs가 됩니다.
  • testb $3, CS+8(%rsp)는 저장된 CS의 아래 두 비트를 봅니다. 3이면 유저 모드에서 온 것입니다. CPU는 "어디서 왔는지"를 따로 알려 주지 않으므로 프레임을 보고 알아냅니다.
  • 유저 모드에서 왔으면 swapgs로 GS 베이스를 커널의 CPU별 데이터 쪽으로 바꾸고, CR3를 커널 페이지 테이블로 바꿉니다. 이 두 줄 전에는 커널의 CPU별 변수도, 커널 메모리의 대부분도 쓸 수 없습니다.

swapgs는 정확히 한 번 해야 합니다. 커널에서 왔는데 하면 GS가 유저 것이 되고, 유저에서 왔는데 빠뜨려도 마찬가지입니다. NMI처럼 swapgs 직전이나 직후에 끼어들 수 있는 사건은 CS만으로 판단할 수 없어서 MSR을 직접 읽어 확인하는 별도 경로(paranoid_entry)를 탑니다. x86 진입 코드가 어려운 까닭의 대부분이 여기에 있습니다.

레지스터 저장이 끝나면 C 함수로 넘어갑니다. 장치 인터럽트는 common_interrupt()이고, 그 뒤는 10장의 주제입니다.

설계 노트

idtentry.h는 C와 어셈블리 양쪽에서 포함됩니다. DECLARE_IDTENTRY_IRQ(X86_TRAP_OTHER, common_interrupt) 같은 한 줄이 C에서는 함수 선언이 되고, 어셈블리에서는 진입 스텁을 찍어 내는 매크로 호출이 됩니다. 진입점 수십 개의 목록이 한곳에만 있으므로, 벡터를 하나 더할 때 C 선언과 어셈블리 스텁이 어긋날 수 없습니다. 같은 정보를 두 군데에 손으로 적어야 하는 구조라면, 한 번 적고 두 가지로 펼치는 방법을 먼저 찾는 것이 커널의 관행입니다.

9.7FRED#

IDT 방식은 16비트 시절의 설계를 64비트까지 끌고 온 것입니다. 앞 절에서 본 문제를 다시 꼽으면 이렇습니다. CPU는 유저에서 왔는지 커널에서 왔는지를 알려 주지 않습니다. GS 전환은 소프트웨어의 책임입니다. IST 스택은 같은 예외가 겹치면 앞의 프레임을 덮어씁니다. 복귀 명령어 iret은 NMI 차단을 무조건 풀어서, NMI 처리 중에 예외가 나면 NMI가 겹칠 수 있습니다. 커널은 이것들을 수십 년 동안 어셈블리 코드로 막아 왔습니다.

FRED(flexible return and event delivery)는 인텔이 이 진입·복귀 과정을 새로 정의한 것입니다. FRED가 켜지면 CPU는 IDT를 쓰지 않습니다.

진입점은 둘뿐입니다.

arch/x86/entry/entry_64_fred.Sv7.3
SYM_CODE_START_NOALIGN(asm_fred_entrypoint_user)
    FRED_ENTER
    call    fred_entry_from_user
SYM_INNER_LABEL(asm_fred_exit_user, SYM_L_GLOBAL)
    FRED_EXIT
1:  ERETU
    /* ... */
SYM_CODE_END(asm_fred_entrypoint_user)

/* ... */
    .org asm_fred_entrypoint_user + 256, 0xcc
SYM_CODE_START_NOALIGN(asm_fred_entrypoint_kernel)
    FRED_ENTER
    call    fred_entry_from_kernel
    FRED_EXIT
    ERETS
SYM_CODE_END(asm_fred_entrypoint_kernel)

링 3에서 일어난 사건은 첫째 진입점으로, 링 0에서 일어난 사건은 거기서 256바이트 뒤의 둘째 진입점으로 옵니다. error_entry에 있던 testb $3도 swapgs도 없습니다. 어디서 왔는지는 진입점이 말해 주고, GS는 CPU가 바꿉니다. 복귀 명령어도 둘입니다. ERETU는 유저로, ERETS는 커널로 돌아갑니다.

무슨 사건인지는 프레임에서 읽습니다.

arch/x86/entry/entry_fred.cv7.3
__visible noinstr void fred_entry_from_user(struct pt_regs *regs)
{
    unsigned long error_code = regs->orig_ax;

    /* Invalidate orig_ax so that syscall_get_nr() works correctly */
    regs->orig_ax = -1;

    switch (regs->fred_ss.type) {
    case EVENT_TYPE_EXTINT:
        return fred_extint(regs);
    case EVENT_TYPE_NMI:
        if (likely(regs->fred_ss.vector == X86_TRAP_NMI))
            return fred_exc_nmi(regs);
        break;
    case EVENT_TYPE_HWEXC:
        return fred_hwexc(regs, error_code);
    /* ... */
    case EVENT_TYPE_OTHER:
        return fred_other(regs);
    default: break;
    }

    return fred_bad_type(regs, error_code);
}

CPU는 프레임의 SS 칸 남는 비트에 사건의 종류(type)와 벡터(vector)를 적어 줍니다. 커널은 switch 두 단계로 핸들러를 찾습니다. 장치 인터럽트(EVENT_TYPE_EXTINT)는 fred_extint()를 거쳐 IDT 방식과 똑같은 common_interrupt()에 닿습니다. 시스템 콜도 같은 진입점으로 들어와 EVENT_TYPE_OTHER로 분류됩니다(19장). 벡터별 스텁 200여 개가 C의 switch 문 하나로 바뀌었습니다.

IST는 스택 레벨 0–3으로 바뀌었습니다. 사건마다 레벨을 정해 두면 CPU는 현재 레벨보다 높을 때만 스택을 갈아탑니다. v7.3은 #DB에 1, NMI와 #MC에 2, #DF에 3을 줍니다. 같은 레벨의 사건이 겹치면 갈아타지 않고 쓰던 스택에 이어 쌓으므로 덮어쓰는 일이 없습니다.

참고 · FRED를 쓰려면

CPU가 지원해야 하고(/proc/cpuinfo의 fred 플래그), 커널이 CONFIG_X86_FRED로 빌드되어 있어야 합니다. 두 조건이 맞으면 v7.3은 FRED를 켭니다. 끄려면 부팅 인자 fred=off를 줍니다. 커널 지원은 6.9에서 들어왔지만 처음에는 fred=on을 줘야 켜졌고, 실제 CPU에서 검증된 뒤인 7.1에서 기본값이 뒤집혔습니다. FRED를 실은 CPU로는 인텔의 Panther Lake 세대가 있습니다.

설계 노트

FRED에서 눈여겨볼 것은 커널 쪽 변경의 크기입니다. 예외와 인터럽트의 C 핸들러(exc_page_fault(), common_interrupt() 등)는 대부분 그대로 쓰입니다. NMI, #DB, #MC처럼 스택과 얽힌 몇 개만 FRED용 변형이 따로 있습니다. 2020년에 진입 코드를 정리하면서 "어셈블리는 pt_regs를 만들어 C 함수를 부르는 데까지만 하고, 나머지는 전부 C로 쓴다"는 경계를 그어 두었기 때문입니다. FRED는 그 경계의 아래쪽만 갈아 끼웠습니다. 하드웨어에 가까운 층을 얇게 유지하면 하드웨어가 바뀔 때 고칠 곳도 얇습니다.

9.8ARM은 어떻게 다른가#

같은 문제를 arm64는 다르게 풉니다. 견주어 보면 x86의 방식이 유일한 답이 아님을 알 수 있습니다.

CPU의 진입점부터 다릅니다. arm64의 예외 벡터 테이블은 256칸이 아니라 16칸입니다. 사건의 종류 넷(동기 예외, IRQ, FIQ, 오류)과 온 곳 넷의 조합입니다. 모든 장치 인터럽트가 "IRQ" 한 칸으로 들어옵니다. FRED가 뒤늦게 도달한 구조와 닮았습니다.

어떤 장치인지는 커널이 인터럽트 컨트롤러 GIC(generic interrupt controller)에 물어서 알아냅니다. 핸들러는 먼저 GIC의 레지스터를 읽어(gic_read_iar()) 인터럽트 번호를 받습니다. 번호는 대역으로 뜻이 갈립니다.

drivers/irqchip/irq-gic-v3.cv7.3
static enum gic_intid_range __get_intid_range(irq_hw_number_t hwirq)
{
    switch (hwirq) {
    case 0 ... 15:
        return SGI_RANGE;
    case 16 ... 31:
        return PPI_RANGE;
    case 32 ... 1019:
        return SPI_RANGE;
    /* ... */
    case 8192 ... GENMASK(23, 0):
        return LPI_RANGE;
    default:
        return __INVALID_RANGE__;
    }
}
GIC 뜻 x86에서 견줄 만한 것
SGI (0–15) 소프트웨어가 다른 CPU에 보내는 인터럽트 IPI
PPI (16–31) CPU마다 따로 있는 장치의 인터럽트(타이머 등) Local APIC의 LVT
SPI (32–1019) 여러 CPU가 공유하는 장치의 선 IO-APIC 핀
LPI (8192–) 메시지로 오는 인터럽트 MSI

GICv3의 구성도 대응이 됩니다. SPI를 어느 CPU로 보낼지 정하는 디스트리뷰터는 IO-APIC에, CPU마다 있는 리디스트리뷰터는 Local APIC에 해당합니다. MSI를 LPI로 바꿔 주는 ITS는 인터럽트 리매핑과 하는 일이 비슷합니다. 하드웨어가 이렇게 달라도 드라이버가 쓰는 request_irq()는 같습니다. 그 차이를 흡수하는 층이 다음 장의 주제입니다.

9.9장치 레지스터와 I/O 주소#

인터럽트는 "무슨 일이 생겼다"는 신호일 뿐입니다. 무슨 일인지 알고 장치에 명령을 내리려면 장치의 레지스터를 읽고 써야 합니다. 장치는 보통 데이터, 상태, 제어 레지스터를 내놓습니다. CPU에서 이 레지스터에 닿는 길은 둘입니다.

포트 I/O는 메모리와 분리된 x86의 별도 주소 공간입니다. 16비트 주소(64KB)이고 in, out 명령어로만 접근합니다. PIC, 키보드 컨트롤러 같은 PC의 오래된 장치가 여기에 있습니다. MMIO(memory-mapped I/O)는 장치 레지스터를 물리 주소 공간의 한 구역에 배치합니다. 보통의 메모리 접근 명령어로 읽고 쓰지만, 그 주소 뒤에는 RAM이 아니라 장치가 있습니다. Local APIC(0xfee00000)과 IO-APIC(0xfec00000)이 그렇고, 요즘 장치는 거의 다 이 방식입니다.

PCI 장치는 자기 레지스터가 어디에 놓일지를 스스로 정하지 않습니다. 장치마다 설정 공간(configuration space)이라는 표준 형식의 작은 영역이 있고, 그 안의 BAR(base address register)에 펌웨어나 커널이 주소를 배정해 써 넣습니다. MSI와 MSI-X의 설정도 설정 공간의 기능 목록(capability)에 있습니다. 드라이버는 배정된 주소를 받아 커널 가상 주소로 매핑합니다.

drivers/net/ethernet/intel/e1000e/netdev.cv7.3
    mmio_start = pci_resource_start(pdev, 0);
    mmio_len = pci_resource_len(pdev, 0);

    err = -EIO;
    adapter->hw.hw_addr = ioremap(mmio_start, mmio_len);
drivers/net/ethernet/intel/e1000e/e1000.hv7.3
static inline u32 __er32(struct e1000_hw *hw, unsigned long reg)
{
    return readl(hw->hw_addr + reg);
}

#define er32(reg)   __er32(hw, E1000_##reg)

pci_resource_start(pdev, 0)이 BAR 0에 배정된 물리 주소입니다. ioremap()이 이것을 커널 페이지 테이블에 매핑하고, 그 뒤로 er32(ICR)은 "매핑한 주소 + 0xc0에서 32비트를 읽어라"가 됩니다. e1000e의 인터럽트 핸들러는 이 한 줄로 인터럽트의 원인을 읽고, 읽는 동작 자체가 장치의 원인 비트를 지웁니다.

주의

ioremap()이 돌려준 주소를 포인터처럼 *addr로 읽으면 안 됩니다. 컴파일러는 그것이 메모리라고 가정하고 읽기를 합치거나 없애거나 순서를 바꿀 수 있습니다. 장치 레지스터는 읽을 때마다 값이 다르고, 읽는 것만으로 상태가 바뀝니다. readl()과 writel()은 정확한 폭의 접근이 한 번 일어나도록 만들어져 있습니다. 반환 타입에 붙은 __iomem 표시는 정적 검사 도구가 이런 직접 접근을 잡아내게 합니다(27장).

가상 머신 안에서는 이 장의 하드웨어가 전부 소프트웨어입니다. 하이퍼바이저가 가상 APIC을 흉내 내고, 게스트가 APIC 레지스터에 쓰면 그것을 가로채 처리합니다. 벡터 목록에 있던 POSTED_INTR_VECTOR는 CPU가 하이퍼바이저를 거치지 않고 게스트에 인터럽트를 넣어 주는 기능의 흔적입니다. 23장에서 다룹니다.

정리#

  • CPU는 명령어의 경계에서 인터럽트 요청을 확인하고, 벡터 번호로 핸들러를 찾습니다. 예외는 CPU가 스스로, 인터럽트는 바깥에서 일으킵니다.
  • 8259 PIC은 요청을 모아 INTR 선 하나로 CPU 하나에 전달합니다. IMR·IRR·ISR·EOI라는 개념은 여기서 나왔습니다.
  • APIC은 CPU마다 Local APIC, 장치 쪽에 IO-APIC을 두고 메시지로 잇습니다. 핀마다 벡터와 목적지 CPU를 따로 정할 수 있습니다.
  • MSI는 장치가 0xfee… 주소에 벡터를 쓰는 것으로 인터럽트를 겁니다. MSI-X는 장치 하나에 벡터를 여럿 두어 큐마다 CPU를 짝지을 수 있게 합니다.
  • IDT 방식에서 CPU는 스택을 고르고 다섯 칸을 쌓는 데까지만 합니다. 어디서 왔는지 가리기, swapgs, CR3 전환, 레지스터 저장은 커널의 어셈블리 코드가 합니다.
  • FRED는 진입점을 둘로 줄이고, 사건의 종류와 벡터를 프레임에 실어 주고, GS 전환과 스택 레벨을 CPU가 맡습니다.
  • 장치 레지스터는 포트 I/O나 MMIO로 접근합니다. MMIO 주소는 ioremap()으로 매핑하고 readl()·writel()로만 건드립니다.

확인 문제#

인터럽트 핸들러가 PIC이나 Local APIC에 EOI를 보내지 않고 끝나면 어떤 일이 생깁니까? 컨트롤러의 어떤 레지스터 때문입니까?

답 보기

ISR(in-service register)에 그 인터럽트의 비트가 남습니다. 컨트롤러는 ISR에 서 있는 것과 우선순위가 같거나 낮은 요청을 CPU에 올리지 않으므로, 그 인터럽트와 그보다 낮은 인터럽트가 다시는 전달되지 않습니다. 요청은 IRR에 쌓인 채 기다립니다. EOI가 ISR 비트를 지워야 다음 요청이 올라갑니다.

NVMe SSD가 큐 8개에 MSI-X 벡터를 하나씩 쓰고 있습니다. 핀 인터럽트 하나를 쓰는 경우와 견주어, 완료 인터럽트를 처리하는 경로에서 달라지는 점을 두 가지 설명해 보세요.

답 보기

첫째, 어느 큐의 완료인지가 벡터로 구분됩니다. 핀 하나라면 핸들러가 장치 레지스터를 읽어 어느 큐인지 알아내야 하고, 선을 다른 장치와 나눠 쓴다면 다른 장치의 핸들러까지 불립니다. 둘째, 벡터마다 목적지 CPU를 따로 정할 수 있습니다. 큐 n의 인터럽트를 그 큐에 요청을 넣은 CPU로 보내면, 완료 처리가 요청을 보낸 CPU의 캐시가 따뜻한 자리에서 일어나고 CPU 사이의 락 경합도 줄어듭니다.

IDT 방식의 진입 코드는 testb $3, CS+8(%rsp)로 무엇을 판단합니까? 그 결과에 따라 swapgs를 하는 이유는 무엇이고, FRED에서는 이 검사가 왜 필요 없습니까?

답 보기

저장된 CS의 아래 두 비트(권한 레벨)로 끊긴 자리가 유저 모드였는지 커널 모드였는지를 판단합니다. 유저 모드였다면 GS 베이스가 유저의 값이므로 swapgs로 커널의 CPU별 데이터 쪽으로 바꿔야 하고, 커널 모드였다면 이미 커널 값이므로 바꾸면 안 됩니다. FRED에서는 CPU가 온 곳에 따라 서로 다른 진입점으로 보내 주고 GS 베이스도 CPU가 바꾸므로, 소프트웨어가 판단할 것이 없습니다.

v7.3의 IDT에서 페이지 폴트(#PF)의 게이트는 INTG로, 오버플로(#OF)의 게이트는 SYSG로 선언되어 있습니다. 유저 프로그램이 int $14를 실행하면 어떻게 됩니까? into는 왜 다릅니까?

답 보기

INTG는 DPL이 0입니다. 유저 모드(권한 레벨 3)에서 int n으로 DPL 0인 게이트를 부르면 CPU가 거부하고 일반 보호 오류(#GP)를 냅니다. 그래서 유저 프로그램이 가짜 페이지 폴트를 만들어 커널의 페이지 폴트 핸들러를 속일 수 없습니다. SYSG는 DPL이 3이어서 유저 모드의 명령어가 직접 일으킬 수 있습니다. into, int3, int 0x80처럼 유저 프로그램이 쓰라고 만든 벡터에만 이렇게 합니다.

용어#

벡터vector
예외와 인터럽트를 구분하는 0–255의 번호. CPU가 핸들러를 찾는 인덱스.
예외exception
CPU가 명령어를 실행하다가 스스로 일으키는 사건. 폴트, 트랩, 어보트로 나뉜다.
NMI
IF 비트로 막을 수 없는 인터럽트.
EOI
인터럽트 처리가 끝났음을 컨트롤러에 알리는 신호. ISR 비트를 지운다.
Local APIC
CPU마다 있는 인터럽트 컨트롤러. 메시지를 받아 CPU에 전달하고 타이머와 IPI를 맡는다.
IO-APIC
장치의 인터럽트 핀을 받아 리다이렉션 테이블에 따라 메시지로 바꾸는 컨트롤러.
IPI
한 CPU가 다른 CPU에 보내는 인터럽트.
MSI / MSI-X
장치가 정해진 주소에 쓰기를 하여 인터럽트를 거는 방식. MSI-X는 장치당 최대 2048개.
인터럽트 리매핑interrupt remapping
IOMMU가 장치의 인터럽트 메시지를 표에 따라 검사하고 목적지를 바꿔 주는 기능.
IDT
벡터 번호로 핸들러 주소를 찾는 256칸짜리 표.
IST
특정 예외에서 CPU가 무조건 갈아타는 전용 스택의 목록.
FRED
IDT 전달과 iret 복귀를 대체하는 x86의 새 진입·복귀 방식.
