멀티코어 스케줄링

어느 CPU에서 깨울 것인가, 언제 옮길 것인가

Linux v7.3 기준약 50분
읽는 소스kernel/sched/topology.ckernel/sched/fair.ckernel/sched/pelt.ckernel/sched/cpufreq_schedutil.c

CPU가 하나라면 스케줄러의 질문은 "다음에 누구를 돌릴까" 하나입니다. CPU가 여럿이면 질문이 하나 더 생깁니다. "이 태스크를 어디에서 돌릴까." 놀고 있는 CPU로 보내면 당장은 빨리 돌지만, 방금까지 쓰던 캐시를 버리게 됩니다. 캐시가 따뜻한 CPU에서 기다리게 하면 그 사이 다른 CPU가 놉니다. 코어마다 크기가 다르고 메모리가 노드마다 흩어진 하드웨어에서는 답이 더 복잡해집니다. 이 장은 그 판단이 내려지는 두 자리, 깨울 때와 균형을 맞출 때를 따라갑니다.

이 장에서 답하는 질문
  • 스케줄러는 CPU들의 배치(SMT, 캐시, 소켓, NUMA)를 어떤 자료구조로 알고 있는가?
  • 깨어난 태스크가 들어갈 CPU는 어떤 순서로 정해지는가?
  • "부하"와 "이용률"은 어떻게 재는가?
  • 부하 분산은 언제 일어나고, 어떤 태스크는 옮기지 않는가?
  • 크기가 다른 코어, NUMA, 공유 캐시는 배치에 각각 어떻게 반영되는가?

7.1두 번의 결정#

런큐는 CPU마다 하나입니다(4장). 태스크는 한 번에 런큐 하나에만 들어 있고, 그 런큐의 CPU에서만 실행됩니다. 그래서 "어디에서 돌릴까"는 "어느 런큐에 넣을까"와 같은 말입니다. 이 결정은 두 번 내려집니다.

  • 깨울 때. 잠들었던 태스크가 깨어나거나 새 태스크가 만들어질 때, 넣을 런큐를 고릅니다. 태스크가 아직 어느 큐에도 없으므로 옮기는 비용이 없습니다. 가장 싸고 가장 자주 일어나는 결정입니다.
  • 균형을 맞출 때. 이미 런큐에 있는 태스크를 다른 런큐로 옮깁니다. 깨울 때의 결정은 그 순간의 정보로 내린 것이라 시간이 지나면 어긋납니다. 한 CPU에 태스크가 쌓이고 옆 CPU가 놀면 부하 분산(load balancing)이 바로잡습니다.

두 결정 모두 같은 긴장 위에 있습니다. 태스크를 퍼뜨리면 놀고 있는 CPU가 줄고, 모아 두면 캐시와 메모리가 가까이 있습니다. 어느 쪽이 나은지는 CPU들이 서로 얼마나 가까운지에 달려 있습니다. 스케줄러가 그 거리를 아는 방법부터 봅니다.

7.2스케줄 도메인#

CPU들은 평평하게 놓여 있지 않습니다. 한 코어의 두 하드웨어 스레드(SMT)는 연산 장치를 같이 쓰고, 한 칩의 코어들은 마지막 단계 캐시(LLC, 보통 L3)를 같이 쓰고, 소켓이 다르면 메모리까지 멀어집니다. 스케줄러는 이 구조를 스케줄 도메인(scheduling domain)의 계층으로 가지고 있습니다.

kernel/sched/topology.cv7.3
static struct sched_domain_topology_level default_topology[] = {
#ifdef CONFIG_SCHED_SMT
    SDTL_INIT(tl_smt_mask, cpu_smt_flags, SMT),
#endif

#ifdef CONFIG_SCHED_CLUSTER
    SDTL_INIT(tl_cls_mask, cpu_cluster_flags, CLS),
#endif

#ifdef CONFIG_SCHED_MC
    SDTL_INIT(tl_mc_mask, cpu_core_flags, MC),
#endif
    SDTL_INIT(tl_pkg_mask, NULL, PKG),
    { NULL, },
};

아래에서 위로 SMT(같은 코어), CLS(L2 등을 같이 쓰는 클러스터), MC(같은 LLC), PKG(같은 패키지)입니다. NUMA 머신에서는 그 위에 노드 사이의 거리마다 NUMA 단계가 더 쌓입니다. 하드웨어에 없는 단계나 아래 단계와 범위가 같은 단계는 만들어지지 않습니다.

자료구조는 둘입니다.

  • struct sched_domain: CPU마다, 단계마다 하나씩 있습니다. rq->sd가 가장 아래 도메인을 가리키고 sd->parent로 올라갑니다. 범위(span), 성질을 나타내는 플래그(SD_SHARE_LLC, SD_NUMA 등), 균형 주기 같은 매개변수를 가집니다.
  • struct sched_group: 한 도메인을 나눈 조각입니다. 그림의 MC 도메인은 코어 네 개가 그룹 네 개이고, NUMA 도메인은 소켓 둘이 그룹 둘입니다. 부하 분산은 같은 도메인 안의 그룹끼리 견줍니다.

자주 쓰는 도메인은 CPU별 포인터로 따로 꺼내 둡니다. sd_llc는 이 CPU가 LLC를 같이 쓰는 가장 넓은 도메인이고, 깨울 CPU를 찾는 범위가 됩니다.

토폴로지를 확인합니다.

터미널

  0    0      0    0 0:0:0:0          yes
  1    0      0    1 1:1:1:0          yes
...

core_cpus_list가 SMT 형제이고, index3/shared_cpu_list가 L3를 같이 쓰는 CPU, 곧 MC 도메인의 범위입니다. 커널이 실제로 만든 도메인은 debugfs에 있습니다. 디렉터리가 비어 있으면 먼저 verbose를 켭니다.

7.3깨울 CPU 고르기#

태스크를 깨우는 try_to_wake_up()은 클래스의 select_task_rq() 콜백으로 CPU를 묻습니다. fair 클래스의 답은 이렇습니다.

kernel/sched/fair.cv7.3
select_task_rq_fair(struct task_struct *p, int prev_cpu, int wake_flags)
{
    /* ... */
    if (wake_flags & WF_TTWU) {
        record_wakee(p);
        /* ... */
        if (!is_rd_overutilized(this_rq()->rd)) {
            new_cpu = find_energy_efficient_cpu(p, prev_cpu);
            if (new_cpu >= 0)
                return new_cpu;
            new_cpu = prev_cpu;
        }

        want_affine = !wake_wide(p) && cpumask_test_cpu(cpu, p->cpus_ptr);
    }

    for_each_domain(cpu, tmp) {
        /* ... */
        if (want_affine && (tmp->flags & SD_WAKE_AFFINE) &&
            cpumask_test_cpu(prev_cpu, sched_domain_span(tmp))) {
            if (cpu != prev_cpu)
                new_cpu = wake_affine(tmp, p, cpu, prev_cpu, sync);

            sd = NULL; /* Prefer wake_affine over balance flags */
            break;
        }
        /* ... */
    }

    /* Slow path */
    if (unlikely(sd))
        return sched_balance_find_dst_cpu(sd, p, cpu, prev_cpu, sd_flag);

    /* Fast path */
    if (wake_flags & WF_TTWU)
        return select_idle_sibling(p, prev_cpu, new_cpu);

    return new_cpu;
}

prev_cpu는 태스크가 마지막으로 돌았던 CPU이고, cpu는 지금 깨우는 코드가 돌고 있는 CPU입니다. 읽을 곳은 네 군데입니다.

  • 에너지 경로. 크기가 다른 코어가 섞인 시스템에서 여유가 있을 때는 find_energy_efficient_cpu()가 먼저 답합니다. 뒤의 절에서 봅니다.
  • 후보를 둘로 줄입니다. wake_affine()은 prev_cpu와 cpu 가운데 하나를 고릅니다. 깨우는 쪽과 깨어나는 쪽은 데이터를 주고받는 사이일 가능성이 크므로, 깨우는 CPU 쪽으로 당겨 오는 것이 이득일 수 있습니다. 다만 서버 하나가 클라이언트 수십 개를 깨우는 식이면 한 CPU에 몰리므로, wake_wide()가 그런 관계를 가려내 당기지 않습니다.
  • 빠른 길. 일반적인 깨우기는 select_idle_sibling()으로 끝납니다. 고른 후보 CPU의 LLC 안에서 놀고 있는 CPU를 찾습니다.
  • 느린 길. fork와 exec에서는 도메인을 위에서부터 내려가며 가장 한가한 그룹과 CPU를 찾습니다. 새 태스크는 따뜻한 캐시가 없으므로 넓게 찾을 가치가 있습니다.

select_idle_sibling()의 순서는 싼 것부터입니다. 후보 CPU가 놀고 있으면 그것, prev_cpu가 같은 캐시 안에서 놀고 있으면 그것, 최근에 썼던 CPU(recent_used_cpu)가 놀고 있으면 그것입니다. 다 아니면 LLC 도메인을 훑습니다. 어디에도 없으면 원래 후보를 돌려주고, 태스크는 그 런큐에서 차례를 기다립니다.

kernel/sched/fair.cv7.3
static int select_idle_cpu(struct task_struct *p, struct sched_domain *sd, bool has_idle_core, int target)
{
    /* ... */
    if (sched_feat(SIS_UTIL) && sd->shared) {
        /* ... */
        nr = READ_ONCE(sd->shared->nr_idle_scan) + 1;
        /* overloaded LLC is unlikely to have idle cpu/core */
        if (nr == 1)
            return -1;
    }
    /* ... */
    for_each_cpu_wrap(cpu, cpus, target + 1) {
        if (has_idle_core) {
            i = select_idle_core(p, cpu, cpus, &idle_cpu);
            if ((unsigned int)i < nr_cpumask_bits)
                return i;

        } else {
            if (--nr <= 0)
                return -1;
            idle_cpu = __select_idle_cpu(cpu, p);
            if ((unsigned int)idle_cpu < nr_cpumask_bits)
                break;
        }
    }
    /* ... */
}

훑기는 target의 다음 CPU에서 시작해 한 바퀴 돕니다. SMT가 있고 통째로 빈 코어가 있다고 표시되어 있으면(has_idle_core) 형제까지 비어 있는 코어를 먼저 찾습니다. 형제가 바쁜 코어의 빈 스레드는 연산 장치를 나눠 써야 하기 때문입니다. 눈여겨볼 것은 nr입니다.

설계 노트

LLC를 훑는 일은 CPU 수에 비례하는 비용이 듭니다. 코어가 수십 개인 칩에서 깨울 때마다 전부 훑으면 탐색이 실행보다 비싸집니다. 그래서 select_idle_cpu()는 훑을 CPU 수에 상한을 둡니다. LLC의 이용률이 높을수록 상한(nr_idle_scan)이 줄고, 포화 상태면 위 코드의 nr == 1에 걸려 아예 훑지 않습니다. 놀고 있는 CPU가 있을 가망이 없기 때문입니다. 최선을 찾는 탐색에 예산을 두고, 예산을 그 탐색이 성공할 확률에 맞추는 방식입니다. 깨우기는 가장 뜨거운 경로이므로 "조금 덜 좋은 CPU를 빨리 고르는 것"이 "가장 좋은 CPU를 늦게 고르는 것"보다 낫습니다.

7.4부하를 재는 법: PELT#

"바쁜 CPU", "작은 태스크"를 말하려면 재는 방법이 있어야 합니다. 런큐에 있는 태스크 수는 좋은 척도가 아닙니다. 1%만 쓰는 태스크 열 개와 100%를 쓰는 태스크 하나는 다릅니다. 스케줄러는 PELT(Per-Entity Load Tracking)로 태스크마다 최근의 행동을 추적합니다.

kernel/sched/pelt.cv7.3
 * We can represent the historical contribution to runnable average as the
 * coefficients of a geometric series.  To do this we sub-divide our runnable
 * history into segments of approximately 1ms (1024us); label the segment that
 * occurred N-ms ago p_N, with p_0 corresponding to the current period, e.g.
 /* ... */
 * Let u_i denote the fraction of p_i that the entity was runnable.
 *
 * We then designate the fractions u_i as our co-efficients, yielding the
 * following representation of historical load:
 *   u_0 + u_1*y + u_2*y^2 + u_3*y^3 + ...
 *
 * We choose y based on the with of a reasonably scheduling period, fixing:
 *   y^32 = 0.5

시간을 약 1ms 구간으로 자르고, 구간마다 태스크가 활동한 비율을 구해, 오래된 구간일수록 작은 가중치로 더합니다. 가중치는 32ms마다 절반이 됩니다. 과거 전체를 저장할 필요가 없습니다. 구간이 넘어갈 때 기존 합에 y를 곱하고 새 구간을 더하면 됩니다.

struct sched_avg에는 같은 방식으로 구한 신호가 셋 있습니다.

신호 무엇의 비율인가 쓰는 곳
util_avg 실행 중이었던 시간. 0–1024 CPU가 얼마나 찼는지, 주파수 선택
runnable_avg 실행 중이거나 기다린 시간 경쟁이 있는지
load_avg 위에 가중치를 곱한 것 부하 분산에서 그룹끼리 견줄 때

태스크의 값은 런큐(cfs_rq->avg)로 합산됩니다. 1024는 "가장 큰 CPU를 최고 주파수로 꽉 채운 양"입니다. 느린 코어나 낮은 주파수에서 돈 시간은 그만큼 줄여 셉니다. 4장에서 본 rq->clock_pelt가 그 환산을 맡습니다. 그래서 이용률은 CPU가 달라도 서로 견줄 수 있는 값이 됩니다.

감쇠에는 부작용이 있습니다. 오래 잠든 태스크는 util_avg가 0에 가까워져, 깨어난 직후에는 작은 태스크로 보입니다. util_est는 잠들기 직전의 이용률을 따로 기억해 둔 값이고, 배치와 주파수 결정은 둘 가운데 큰 쪽을 씁니다.

이 신호의 가장 직접적인 소비자가 CPU 주파수 조절기 schedutil입니다.

kernel/sched/cpufreq_schedutil.cv7.3
 * If the utilization is frequency-invariant, choose the new frequency to be
 * proportional to it, that is
 *
 * next_freq = C * max_freq * util / max
 /* ... */
 * Take C = 1.25 for the frequency tipping point at (util / max) = 0.8.

이용률에 25%의 여유를 얹어 주파수를 고릅니다. 이용률이 용량의 80%에 닿으면 최고 주파수가 됩니다. 스케줄러가 이용률을 갱신할 때 조절기를 직접 부르므로, 따로 표본을 뜨는 조절기보다 빨리 반응합니다.

설계 노트

PELT 신호는 한 곳에서 만들어 여러 결정이 같이 씁니다. 깨울 CPU, 부하 분산, 주파수, 뒤에 나올 에너지 계산이 모두 같은 util_avg를 봅니다. 결정마다 따로 재면 서로 어긋납니다. 스케줄러가 "이 CPU는 한가하다"며 태스크를 보냈는데 주파수 조절기는 "바쁘다"며 주파수를 올리는 식입니다. 측정을 하나로 모으면 그 측정이 틀릴 때 모두 같이 틀리지만, 고칠 곳도 하나입니다.

예전 자료와 다른 점

옛 자료는 CPU의 부하를 "런큐 길이"나 그것을 틱마다 평균한 cpu_load[] 배열로 설명합니다. v7.3에서 부하 분산이 보는 값은 PELT의 load_avg, util_avg, runnable_avg입니다. uptime이 보여 주는 load average는 이것과 다른 값입니다. 실행 가능하거나 중단할 수 없는 대기 상태에 있는 태스크 수를 1분, 5분, 15분으로 평균한 것이고 스케줄링 판단에는 쓰이지 않습니다.

7.5부하 분산#

부하 분산은 세 가지 계기로 일어납니다.

계기 누가 하나 진입점
주기적 틱을 받은 CPU 자신 sched_tick() → sched_balance_trigger() → SCHED_SOFTIRQ
막 한가해질 때 런큐가 비려는 CPU pick_task_fair() → sched_balance_newidle()
틱이 멈춘 CPU 대신 깨워진 한가한 CPU 하나 nohz_balancer_kick() → nohz_idle_balance()

주기적인 경우, 틱은 때가 되었는지만 보고 softirq를 올립니다(11장).

kernel/sched/fair.cv7.3
void sched_balance_trigger(struct rq *rq)
{
    /* ... */
    if (time_after_eq(jiffies, rq->next_balance))
        raise_softirq(SCHED_SOFTIRQ);

    nohz_balancer_kick(rq);
}

softirq 핸들러 sched_balance_softirq()는 sched_balance_domains()를 부르고, 이 함수가 자기 CPU의 도메인을 아래에서 위로 올라가며 주기가 찬 도메인마다 sched_balance_rq()를 부릅니다. 주기는 도메인이 넓을수록 깁니다. 가까운 CPU 사이는 자주, 먼 CPU 사이는 드물게 맞춥니다. 멀리 옮길수록 잃는 것이 많기 때문입니다.

kernel/sched/fair.cv7.3
static int sched_balance_rq(int this_cpu, struct rq *this_rq,
            struct sched_domain *sd, enum cpu_idle_type idle,
            int *continue_balancing)
{
    /* ... */
redo:
    if (!should_we_balance(&env)) {
        *continue_balancing = 0;
        goto out_balanced;
    }
    /* ... */
    group = sched_balance_find_src_group(&env);
    if (!group) {
        schedstat_inc(sd->lb_nobusyg[idle]);
        goto out_balanced;
    }

    busiest = sched_balance_find_src_rq(&env, group);
    if (!busiest) {
        schedstat_inc(sd->lb_nobusyq[idle]);
        goto out_balanced;
    }
    /* ... */
        cur_ld_moved = detach_tasks(&env);
    /* ... */
        if (cur_ld_moved) {
            attach_tasks(&env);
            ld_moved += cur_ld_moved;
        }
    /* ... */
}

읽을 곳은 네 군데입니다.

  • 끌어오기만 합니다. 이 함수는 this_cpu로 태스크를 가져올 뿐, 남에게 밀어내지 않습니다. 각 CPU가 자기 쪽으로만 당기므로 두 CPU가 같은 태스크를 서로 밀어내는 일이 없습니다.
  • should_we_balance(). 한 그룹에서 한 CPU만 그 그룹을 대표해 균형을 맞춥니다. 놀고 있는 CPU가 있으면 그 CPU가 맡습니다. 같은 일을 여럿이 하지 않게 합니다.
  • 가장 바쁜 그룹, 그 안의 가장 바쁜 런큐. sched_balance_find_src_group()은 도메인의 그룹마다 통계를 모아 상태(enum group_type)를 매깁니다. 여유 있음(group_has_spare), 꽉 참(group_fully_busy), 들어맞지 않는 태스크가 있음(group_misfit_task), 과부하(group_overloaded) 등이고, 뒤쪽일수록 먼저 덜어 줘야 할 그룹입니다. 자기 그룹보다 충분히 바쁜 그룹이 있을 때만 그 그룹을 돌려줍니다. "충분히"의 문턱이 도메인의 imbalance_pct입니다. 차이가 작으면 옮기는 비용이 더 큽니다.
  • 떼어서 붙입니다. detach_tasks()가 바쁜 런큐의 락을 쥐고 태스크를 떼어 내고, 락을 푼 뒤 attach_tasks()가 자기 런큐에 붙입니다. 두 런큐의 락을 동시에 쥐지 않습니다.

모든 태스크를 옮길 수 있는 것은 아닙니다.

kernel/sched/fair.cv7.3
int can_migrate_task(struct task_struct *p, struct lb_env *env)
{
    /* ... */
    /*
     * We do not migrate tasks that are:
     * 1) delayed dequeued unless we migrate load, or
     * 2) target cfs_rq is in throttled hierarchy, or
     * 3) cannot be migrated to this CPU due to cpus_ptr, or
     * 4) running (obviously), or
     * 5) are cache-hot on their current CPU, or
     * 6) are blocked on mutexes (if SCHED_PROXY_EXEC is enabled)
     */
    /* ... */
    if (!hot || env->sd->nr_balance_failed > env->sd->cache_nice_tries) {
        if (hot)
            p->sched_task_hot = 1;
        return 1;
    }

    schedstat_inc(p->stats.nr_failed_migrations_hot);
    return 0;
}

3번이 친화성, 5번이 캐시입니다. task_hot()은 태스크가 마지막으로 실행된 지 sysctl_sched_migration_cost(기본 0.5ms)가 지나지 않았으면 캐시가 따뜻하다고 봅니다. 그런 태스크는 건너뛰되, 균형 시도가 거듭 실패하면(nr_balance_failed) 따뜻해도 옮깁니다. 4번도 예외가 있습니다. 바쁜 런큐에 실행 중인 태스크 하나뿐이라 뗄 것이 없는데도 불균형이 이어지면, 그 CPU의 stop 클래스 태스크(4장)를 깨워 실행 중인 태스크를 강제로 밀어냅니다. 액티브 밸런싱입니다.

막 한가해지는 CPU의 균형(sched_balance_newidle())은 가장 효과가 큽니다. 어차피 놀 CPU이므로 끌어오면 바로 이득입니다. 다만 곧 깨어날 태스크가 있다면 헛일이므로, 이 CPU가 평균적으로 한가했던 시간(avg_idle)이 균형 작업에 드는 시간보다 짧으면 시도하지 않습니다.

이미 잠든 CPU는 틱이 멈춰 있어(8장) 스스로 주기적 균형을 하지 못합니다. 바쁜 CPU의 틱이 이것을 알아채면(nohz_balancer_kick()) 잠든 CPU 하나를 깨워, 그 CPU가 잠든 CPU들 모두의 몫으로 균형을 맞추게 합니다.

예전 자료와 다른 점

옛 자료의 함수 이름은 v7.3 소스에서 찾을 수 없습니다. v6.10부터 부하 분산 함수들이 sched_balance_ 접두사로 정리되었습니다.

옛 이름 v7.3
trigger_load_balance() sched_balance_trigger()
run_rebalance_domains(), rebalance_domains() sched_balance_softirq(), sched_balance_domains()
load_balance() sched_balance_rq()
find_busiest_group(), find_busiest_queue() sched_balance_find_src_group(), sched_balance_find_src_rq()
idle_balance() sched_balance_newidle()

도메인 이름도 바뀌었습니다. 옛 자료의 DIE 도메인이 v7.3의 PKG입니다.

7.6친화성과 실시간 태스크#

CPU 친화성(CPU affinity)은 태스크가 실행될 수 있는 CPU의 집합입니다. task_struct의 cpus_ptr가 가리키는 비트마스크이고, sched_setaffinity() 시스템 콜이나 taskset 명령으로 정합니다. 앞에서 본 두 결정 모두 이 마스크 안에서만 고릅니다. select_task_rq_fair()와 can_migrate_task()에 p->cpus_ptr 검사가 있었습니다. 커널 코드가 잠깐 CPU를 옮기지 못하게 하는 migrate_disable()(6장)도 같은 장치를 씁니다. 그런 태스크가 CPU를 내줄 때 이 마스크를 현재 CPU 하나로 좁혀 둡니다.

RT 클래스는 균형의 기준이 다릅니다. fair 클래스는 부하를 고르게 하려 하지만, RT 클래스의 목표는 시스템 전체에서 우선순위가 가장 높은 N개의 태스크가 N개의 CPU에서 도는 것입니다. 그래서 주기를 기다리지 않습니다. RT 태스크가 깨어났는데 자기 CPU에 더 높은 태스크가 돌고 있으면, 우선순위가 더 낮은 태스크를 돌리는 CPU를 찾아 그쪽으로 밀어냅니다(push_rt_task()). 반대로 CPU의 우선순위가 내려가면 다른 CPU에서 기다리는 RT 태스크를 끌어옵니다(pull_rt_task()). deadline 클래스도 같은 구조입니다.

직접 확인하기

태스크가 CPU를 옮겨 다니는 것을 봅니다.

터미널
$ taskset -cp $$
pid 4127's current affinity list: 0-15
$ perf stat -e migrations,context-switches -- make -j8
...
             1,204      migrations
            98,331      context-switches
$ grep se.nr_migrations /proc/$$/sched
se.nr_migrations                             :                   37

taskset -c 0-3 명령으로 범위를 좁혀 실행하면 migrations가 줄어듭니다. 어느 CPU에서 누가 돌았는지는 perf sched record로 기록한 뒤 perf sched map으로 봅니다. 도메인별 균형 시도와 성공 횟수는 /proc/schedstat의 domain 줄에 쌓입니다.

7.7크기가 다른 CPU#

스마트폰과 최근의 노트북 칩은 빠른 코어와 느리지만 전력을 덜 쓰는 코어를 섞습니다. 스케줄러는 CPU마다 용량(capacity)을 가집니다. 가장 큰 코어가 1024이고 작은 코어는 그보다 작습니다. arm64에서는 /sys/devices/system/cpu/cpuN/cpu_capacity로 볼 수 있습니다. 앞 절에서 본 대로 이용률도 같은 눈금이므로 둘을 직접 견줄 수 있습니다.

kernel/sched/fair.cv7.3
/*
 * The margin used when comparing utilization with CPU capacity.
 *
 * (default: ~20%)
 */
#define fits_capacity(cap, max) ((cap) * 1280 < (max) * 1024)

태스크의 이용률이 CPU 용량의 80% 아래면 "들어맞는다"고 봅니다. 이 판정에서 세 가지가 나옵니다.

  • misfit. 작은 코어에서 도는 태스크의 이용률이 그 코어에 들어맞지 않게 되면 런큐에 misfit_task_load가 표시되고, 부하 분산이 그 태스크를 큰 코어로 올립니다.
  • EAS(Energy Aware Scheduling). 시스템에 여유가 있는 동안은 깨울 때 find_energy_efficient_cpu()가 먼저 답합니다. 태스크가 들어맞는 CPU들을 후보로 놓고, 에너지 모델(주파수별 전력 표)로 각 후보에 태스크를 놓았을 때 시스템이 쓸 에너지를 추정해 가장 적은 쪽을 고릅니다. 어느 CPU든 80%를 넘겨 과이용 상태가 되면(rd->overutilized) 이 경로를 끄고 보통의 분산으로 돌아갑니다. 꽉 찬 시스템에서는 처리량이 먼저입니다.
  • uclamp. 이용률은 과거의 관찰이라 틀릴 수 있습니다. sched_setattr()의 sched_util_min과 sched_util_max로 태스크의 이용률을 "적어도 이만큼", "많아야 이만큼"으로 보게 할 수 있습니다. 화면을 그리는 스레드는 아래를 받쳐 큰 코어와 높은 주파수를 얻고, 백그라운드 작업은 위를 눌러 작은 코어에 머뭅니다.

7.8NUMA 균형#

소켓이 여럿인 서버에서는 메모리도 소켓마다 나뉘어 있습니다(NUMA 노드). 다른 노드의 메모리를 읽는 것은 자기 노드의 메모리보다 느립니다. 태스크와 그 태스크의 메모리가 다른 노드에 있으면 손해입니다. 자동 NUMA 균형(automatic NUMA balancing)은 둘을 가까이 붙입니다.

스케줄러는 태스크가 어느 노드의 메모리를 쓰는지 모릅니다. 그래서 물어봅니다.

  1. 틱이 주기적으로 task_numa_work()를 예약합니다. 이 함수는 태스크의 주소 공간 일부를 일부러 접근 불가로 바꿔 둡니다.
  2. 태스크가 그 페이지를 건드리면 페이지 폴트가 납니다(NUMA 힌트 폴트). 실제 오류가 아니므로 커널은 권한을 되돌려 주고, task_numa_fault()가 "이 태스크가 어느 노드의 페이지를 건드렸다"를 기록합니다.
  3. 기록이 쌓이면 task_numa_placement()가 폴트가 가장 많은 노드를 선호 노드(numa_preferred_nid)로 정합니다.
  4. 태스크를 선호 노드의 CPU로 옮기려 하고(task_numa_migrate()), 폴트가 난 페이지가 다른 노드에 있으면 페이지를 태스크 쪽으로 옮깁니다.

부하 분산도 이 정보를 씁니다. can_migrate_task()는 태스크를 선호 노드에서 멀어지게 하는 이동을 캐시가 따뜻한 태스크처럼 꺼립니다. 페이지 폴트와 페이지 이동은 17장과 18장에서 다룹니다. sysctl kernel.numa_balancing으로 켜고 끄며, 노드별 메모리 분포는 numastat -p PID로 봅니다.

7.9캐시 인지 스케줄링#

지금까지의 분산은 부하를 고르게 하는 것이 목표였습니다. LLC가 여럿인 머신에서는 이것이 손해가 될 수 있습니다. 한 프로세스의 스레드들은 같은 데이터를 만집니다. 스레드들이 여러 LLC에 흩어지면, 한 스레드가 고친 캐시 라인을 다른 LLC의 스레드가 읽을 때마다 캐시 사이를 건너야 합니다. v7.2에 들어온 캐시 인지 스케줄링(CONFIG_SCHED_CACHE)은 같은 프로세스의 스레드를 한 LLC에 모으려 합니다.

방법은 NUMA 균형과 닮았습니다. 프로세스마다 "어느 CPU에서 얼마나 돌았나"를 감쇠 평균으로 쌓아 두고(account_mm_sched()), 주기적으로 그 합이 가장 큰 LLC를 그 프로세스의 선호 LLC로 정합니다. 그러고 나서 부하 분산이 태스크를 옮길지 판단할 때 이 선호를 끼워 넣습니다.

kernel/sched/fair.cv7.3
static enum llc_mig can_migrate_llc(int src_cpu, int dst_cpu,
                    unsigned long tsk_util,
                    bool to_pref)
{
    /* ... */
    if (!fits_llc_capacity(dst_util, dst_cap) &&
        !fits_llc_capacity(src_util, src_cap))
        return mig_unrestricted;

    if (to_pref) {
        /* ... */
        if (!fits_llc_capacity(dst_util, dst_cap) &&
            util_greater(dst_util, src_util))
            return mig_forbid;
    } else {
        /* ... */
        if (fits_llc_capacity(src_util, src_cap) ||
            !util_greater(src_util, dst_util))
            return mig_forbid;
    }
    return mig_llc;
}

읽을 곳은 세 군데입니다.

  • 양쪽이 다 바쁘면 손을 뗍니다(mig_unrestricted). 두 LLC의 이용률이 모두 문턱(기본 50%)을 넘으면 캐시보다 부하가 급합니다. 보통의 분산에 맡깁니다.
  • 선호 LLC로 가는 이동은 허용하되, 그 LLC가 이미 문턱을 넘었고 출발지보다 20% 넘게 바쁘면 막습니다.
  • 선호 LLC에서 나가는 이동은 막되, 선호 LLC가 문턱을 넘었고 도착지보다 20% 넘게 바쁘면 허용합니다.

모으지 않는 경우도 정해져 있습니다. 스레드가 하나뿐인 프로세스, 활동 중인 스레드가 LLC의 코어 수에 견주어 너무 많은 프로세스, 쓰는 메모리가 LLC 크기를 넘는 프로세스입니다. 모아 봐야 캐시에 다 들어가지 않기 때문입니다. LLC가 하나뿐인 머신에서는 기능 자체가 꺼집니다. 조정값은 /sys/kernel/debug/sched/llc_balancing/ 아래에 있습니다.

설계 노트

이 기능은 깨울 CPU를 고르는 뜨거운 경로를 건드리지 않고, 드물게 도는 부하 분산의 판단에만 끼어듭니다. 그리고 선호를 규칙이 아니라 한쪽으로 기운 저울로 넣었습니다. 20%와 50%라는 여유는 이력 현상을 만듭니다. 조금 기울었다고 옮기고 다시 돌아오는 왕복을 막는 것입니다. 서로 당기는 목표(부하의 균형, 캐시의 가까움)를 한 시스템에 넣을 때 커널이 반복해서 쓰는 방법입니다. 한쪽을 기본으로 두고, 다른 쪽은 문턱을 넘을 때만 이기게 합니다.

7.10격리와 코어 스케줄링#

분산을 하지 말아야 할 때도 있습니다.

CPU 격리. 지연 시간에 민감한 워크로드는 CPU 몇 개를 통째로 차지하고 다른 것이 끼어들지 않기를 바랍니다. 부팅 인자 isolcpus=는 지정한 CPU를 스케줄 도메인에서 빼서 부하 분산의 대상이 되지 않게 하고, nohz_full=은 그 CPU에서 태스크 하나만 돌 때 틱까지 멈춥니다(8장). 격리되지 않은 나머지를 하우스키핑 CPU라고 부르고, 묶이지 않은 커널 스레드와 타이머 같은 잡무가 그쪽으로 갑니다. 실행 중에 같은 일을 하려면 cgroup의 cpuset에서 cpuset.cpus.partition에 isolated를 씁니다(22장).

코어 스케줄링. SMT 형제는 연산 장치와 캐시를 같이 쓰므로, 한쪽에서 도는 코드가 다른 쪽의 데이터를 부채널로 엿볼 수 있는 취약점이 여러 번 발견되었습니다. SMT를 끄면 안전하지만 처리량을 잃습니다. 코어 스케줄링은 태스크에 쿠키를 붙이고(prctl(PR_SCHED_CORE, ...)), 한 코어의 형제들이 같은 쿠키의 태스크만 동시에 돌리게 합니다. 맞는 짝이 없으면 형제 하나를 일부러 놀립니다. 이를 위해 형제들의 런큐가 락 하나를 같이 쓰고 다음 태스크를 함께 고릅니다. 4장에서 런큐 락을 rq_lock()으로 감싸 쓰던 이유입니다.

정리#

  • 태스크의 CPU는 깨울 때 한 번 정해지고, 부하 분산이 나중에 바로잡습니다. 두 결정 모두 "퍼뜨릴 것인가, 모을 것인가"를 저울질합니다.
  • 스케줄 도메인은 CPU 사이의 거리를 SMT, MC, PKG, NUMA의 계층으로 나타냅니다. 가까운 단계일수록 자주 균형을 맞춥니다.
  • 깨울 때는 후보를 prev_cpu와 깨우는 CPU로 줄이고, 그 LLC 안에서 놀고 있는 CPU를 찾습니다. 탐색에는 상한이 있습니다.
  • PELT는 태스크의 최근 활동을 32ms 반감기의 감쇠 합으로 추적합니다. util_avg는 배치와 주파수 선택에, load_avg는 분산에 쓰입니다.
  • 부하 분산은 끌어오기입니다. 가장 바쁜 그룹의 가장 바쁜 런큐에서, 친화성이 허락하고 캐시가 식은 태스크를 가져옵니다.
  • 코어 크기가 다르면 용량과 이용률을 견주어 들어맞는 CPU를 고르고, 여유가 있을 때는 에너지 모델로 고릅니다.
  • NUMA 균형은 힌트 폴트로 태스크가 쓰는 메모리의 위치를 알아내 태스크와 페이지를 서로 가까이 옮깁니다.
  • 캐시 인지 스케줄링은 한 프로세스의 스레드를 한 LLC에 모으는 쪽으로 부하 분산을 기울입니다.

확인 문제#

16코어 머신에서 make -j4를 돌리는데 컴파일러 프로세스들이 CPU를 자주 옮겨 다닙니다. fork로 만들어진 직후의 배치와, 디스크 I/O에서 깨어날 때의 배치는 select_task_rq_fair()의 어느 길로 갑니까?

답 보기

fork와 exec는 느린 길입니다. 도메인에 SD_BALANCE_FORK, SD_BALANCE_EXEC가 서 있어 sd가 잡히고, sched_balance_find_dst_cpu()가 넓은 범위에서 가장 한가한 CPU를 찾습니다. 새 태스크는 캐시가 식어 있으므로 멀리 가도 잃을 것이 없습니다. I/O에서 깨어나는 것은 빠른 길입니다. wake_affine()이 prev_cpu와 깨우는 CPU 가운데 하나를 고르고, select_idle_sibling()이 그 CPU의 LLC 안에서 놀고 있는 CPU를 찾습니다. 16코어가 LLC 하나를 같이 쓴다면 놀고 있는 CPU가 많으므로 깨어날 때마다 다른 CPU로 갈 수 있습니다.

100ms 동안 CPU를 꽉 채워 쓰던 태스크가 64ms 동안 잠들었다 깨어났습니다. 깨어난 직후의 util_avg는 잠들기 전의 대략 몇 분의 일입니까? 스케줄러가 이 태스크를 작은 태스크로 오해하지 않게 하는 장치는 무엇입니까?

답 보기

PELT의 반감기가 32ms이므로 64ms 뒤에는 약 4분의 1입니다. 이 값만 보면 큰 태스크가 작아 보여, 작은 코어에 놓이거나 낮은 주파수를 받을 수 있습니다. util_est가 잠들기 직전의 이용률을 기억하고 있고, task_util_est()는 util_avg와 util_est 가운데 큰 값을 돌려주므로 배치와 주파수 결정은 잠들기 전의 크기를 봅니다.

sched_balance_rq()가 가장 바쁜 런큐를 찾았는데 태스크를 하나도 옮기지 못하는 경우를 can_migrate_task()의 조건으로 세 가지 들어 보세요. 그 뒤에 무슨 일이 일어납니까?

답 보기
  1. 태스크들의 cpus_ptr에 이 CPU가 없는 경우(친화성). (2) 런큐의 태스크가 지금 실행 중인 것 하나뿐인 경우. (3) 남은 태스크가 모두 방금 실행되어 캐시가 따뜻한 경우. 실패하면 도메인의 nr_balance_failed가 올라갑니다. 이 값이 cache_nice_tries를 넘으면 다음 시도에서는 따뜻한 태스크도 옮기고, 그래도 안 되면 바쁜 CPU의 stop 태스크를 깨워 실행 중인 태스크를 밀어내는 액티브 밸런싱을 합니다. 친화성 때문이라면 같은 그룹의 다른 CPU로 대신 옮기는 길을 찾습니다.

EAS는 왜 시스템이 과이용 상태가 되면 꺼집니까?

답 보기

EAS는 "태스크를 어디에 놓아도 필요한 만큼의 CPU 시간을 받는다"는 가정 위에서 에너지만 비교합니다. 그리고 PELT의 이용률이 태스크의 실제 요구를 나타낸다고 믿습니다. CPU가 꽉 차면 태스크는 원하는 만큼 돌지 못하므로 이용률이 요구보다 작게 측정되고, 그 숫자로 한 에너지 추정은 틀립니다. 그때는 에너지를 아끼는 것보다 놀고 있는 용량을 찾아 처리량을 지키는 것이 먼저이므로, 보통의 부하 분산과 select_idle_sibling() 경로로 돌아갑니다.

스레드 4개가 같은 해시 테이블을 읽고 쓰는 프로세스가 LLC 둘(각 16 CPU)인 머신에서 돕니다. 다른 부하는 없습니다. 캐시 인지 스케줄링이 꺼져 있을 때와 켜져 있을 때 스레드의 배치는 어떻게 다릅니까?

답 보기

꺼져 있으면 부하 분산이 두 LLC의 부하를 고르게 하려 하므로 스레드가 2개씩 나뉘는 쪽으로 갑니다. 한 LLC의 스레드가 고친 캐시 라인을 다른 LLC의 스레드가 읽을 때마다 캐시 미스가 납니다. 켜져 있으면 프로세스가 가장 많이 돈 LLC가 선호 LLC가 되고, can_migrate_llc()가 그쪽으로 가는 이동은 허용하고 나가는 이동은 막습니다. 스레드 4개의 이용률은 16 CPU인 LLC의 문턱(50%)에 못 미치므로 한 LLC에 모입니다. 다른 LLC는 비지만, 이 프로세스에는 그 편이 빠릅니다.

용어#

부하 분산load balancing
런큐 사이에 태스크를 옮겨 CPU들의 부하를 맞추는 일.
스케줄 도메인scheduling domain
하드웨어 자원을 같이 쓰는 CPU들의 범위. SMT, MC, PKG, NUMA 단계로 계층을 이룬다.
LLClast level cache
CPU들이 같이 쓰는 가장 바깥 단계의 캐시. 보통 L3.
PELTper-entity load tracking
태스크와 런큐의 최근 활동을 지수 감쇠 합으로 추적하는 방식.
이용률utilization
태스크가 실제로 실행된 시간의 비율. 0–1024로 나타내고 CPU 용량과 같은 눈금이다.
util_est
태스크가 잠들기 직전의 이용률을 기억해 둔 값.
CPU 친화성CPU affinity
태스크가 실행될 수 있는 CPU의 집합. p->cpus_ptr.
용량capacity
CPU의 상대적 처리 능력. 가장 큰 코어가 1024.
EASenergy aware scheduling
에너지 모델로 태스크를 놓을 CPU를 고르는 깨우기 경로.
NUMA 힌트 폴트NUMA hinting fault
태스크가 어느 노드의 메모리를 쓰는지 알아내려고 커널이 일부러 일으키는 페이지 폴트.
캐시 인지 스케줄링cache aware scheduling
같은 프로세스의 스레드를 한 LLC에 모으도록 부하 분산을 기울이는 기능.
코어 스케줄링core scheduling
SMT 형제가 같은 쿠키의 태스크만 동시에 실행하게 하는 기능.
