27.1여러 겹의 방어#

한 가지 검사로 모든 버그를 잡을 수는 없습니다. 컴파일러는 타입이 안 맞는 대입을 잡지만 락 순서는 모릅니다. 테스트는 돌려 본 경로만 봅니다. 그래서 커널은 성질이 다른 검사를 여러 겹으로 둡니다. 앞 겹이 놓친 것을 뒤 겹이 잡습니다.

같은 버그라도 왼쪽에서 잡힐수록 쌉니다. 컴파일 오류는 작성자가 그 자리에서 고칩니다. 운영 환경에서 터진 메모리 오염은 보고, 재현, 이등분, 수정, 백포트를 거칩니다. 이 장에 나오는 도구의 역사는 검사를 왼쪽으로 옮겨 온 역사입니다.

누가 버그를 찾는지도 달라졌습니다. v7.3에서 Reported-by 태그가 붙은 커밋은 1,411개였고, 그 절반 가까이가 사람이 아니라 자동화된 시스템의 보고였습니다. 퍼저 syzbot이 15.3%, 빌드 봇인 kernel test robot이 5.7%, LLM으로 패치를 검토하는 Sashiko가 19.4%입니다.

27.2컴파일할 때 잡는다#

경고와 컴파일 시점 단언

커널은 경고 없이 빌드되는 것을 목표로 합니다. 기본 수준보다 엄한 검사는 make W=1로 켭니다.

컴파일러에게 직접 조건을 검사시킬 수도 있습니다. BUILD_BUG_ON(조건)과 static_assert(조건)은 조건이 어긋나면 빌드를 실패시킵니다.

mm/kfence/core.cv7.3
static const char *const counter_names[] = {
    [KFENCE_COUNTER_ALLOCATED]  = "currently allocated",
    [KFENCE_COUNTER_ALLOCS]     = "total allocations",
    /* ... */
};
static_assert(ARRAY_SIZE(counter_names) == KFENCE_COUNTER_COUNT);

열거형에 항목을 더하고 이름 배열을 고치는 것을 잊으면 컴파일이 되지 않습니다. "두 곳을 같이 고쳐야 한다"는 주석을 다는 대신, 어긋날 수 없게 만든 것입니다.

sparse: 타입에 뜻을 더하기

C의 타입은 char *가 유저 공간 주소인지 커널 주소인지 구분하지 못합니다. sparse는 커널이 붙인 주석을 읽어 그 구분을 검사하는 정적 분석기입니다.

include/linux/compiler_types.hv7.3
#ifdef __CHECKER__
/* address spaces */
# define __kernel   __attribute__((address_space(0)))
# define __user     __attribute__((noderef, address_space(__user)))
# define __iomem    __attribute__((noderef, address_space(__iomem)))
# define __percpu   __attribute__((noderef, address_space(__percpu)))
# define __rcu      __attribute__((noderef, address_space(__rcu)))

__user가 붙은 포인터는 다른 주소 공간에 속하고(address_space), 직접 역참조할 수 없습니다(noderef). 시스템 콜 인자로 받은 포인터를 copy_from_user() 없이 읽으면 sparse가 경고합니다(19장). __rcu는 rcu_dereference()를 거치지 않은 접근을(16장), __bitwise로 만든 __le32와 __be32는 엔디언이 섞이는 것을 잡습니다. 보통의 컴파일러로 빌드할 때는 이 매크로들이 사라집니다. make C=1은 다시 컴파일되는 파일에, C=2는 모든 파일에 sparse를 돌립니다.

컨텍스트 분석: 락 규칙을 컴파일러가 검사한다

"이 필드는 이 락을 쥐고 만져야 한다"는 규칙은 오랫동안 주석이었습니다. v7.3에서는 그것을 컴파일러가 검사하는 주석으로 쓸 수 있습니다.

kernel/kcov.cv7.3
    refcount_t      refcount;
    /* The lock protects mode, size, area and t. */
    spinlock_t      lock;
    enum kcov_mode      mode __guarded_by(&lock);
    /* Size of arena (in long's). */
    unsigned int        size __guarded_by(&lock);
    /* Coverage buffer shared with user space. */
    void            *area __guarded_by(&lock);
    /* Task for which we collect coverage, or NULL. */
    struct task_struct  *t __guarded_by(&lock);

둘째 줄의 주석과 __guarded_by(&lock)는 같은 말을 합니다. 차이는 뒤의 것을 Clang이 읽는다는 점입니다. lock을 잡지 않은 채 mode를 읽거나 쓰는 코드는 경고를 받습니다. 함수에는 __must_hold(락), __acquires(락), __releases(락)을 붙여 "이 락을 쥔 채 불러야 한다", "이 함수가 락을 잡는다"를 밝힙니다. 6장에서 인용한 __raw_spin_lock()의 __acquires(lock)이 그것입니다.

이 기능은 컨텍스트 분석(context analysis)이라고 부르며, CONFIG_WARN_CONTEXT_ANALYSIS와 Clang 23 이상이 필요합니다. 트리 전체에 한꺼번에 켜지 않습니다. 준비된 파일만 Makefile에서 하나씩 켭니다. v7.3의 kernel/sched/Makefile에는 CONTEXT_ANALYSIS_core.o := y와 CONTEXT_ANALYSIS_fair.o := y가 있습니다. 스케줄러의 두 핵심 파일이 이 검사를 받으며 빌드됩니다.

예전 자료와 다른 점

예전 자료는 "__acquires()와 __releases()는 sparse가 락의 짝을 검사하는 데 쓰는 주석"이라고 설명합니다. v7.3의 Documentation/dev-tools/sparse.rst에는 락 검사에 대한 절이 없습니다. 이 주석들은 이제 include/linux/compiler-context-analysis.h에서 Clang의 속성으로 정의되고, sparse가 하던 락 문맥 추적은 Clang의 컨텍스트 분석이 넘겨받았습니다. 이 문서는 v7.0부터 실려 있습니다. sparse는 함수 안에서 락과 언락의 개수가 맞는지만 보았지만, 새 분석은 어느 데이터가 어느 락에 묶여 있는지까지 봅니다.

설계 노트

버그를 막는 수단에는 강도의 순서가 있습니다.

  1. 주석: "이 필드는 락을 쥐고 만질 것". 읽는 사람이 지켜야 합니다.
  2. 런타임 단언: lockdep_assert_held(&lock). 그 경로가 실행되어야 잡힙니다.
  3. 정적 검사: __guarded_by(&lock). 컴파일할 때 모든 경로에서 잡힙니다.
  4. 타입: 락을 잡아야만 데이터에 닿는 참조를 얻는 구조. 틀린 코드를 쓸 수 없습니다(Rust 절).

커널의 품질 작업은 규칙을 이 사다리의 위쪽으로 올리는 일입니다. 올릴수록 검사는 일찍, 빠짐없이 이루어지지만 표현할 수 있는 코드의 꼴이 좁아집니다. 컨텍스트 분석 문서도 조건에 따라 락을 잡고 푸는 복잡한 흐름은 제약을 받는다고 밝힙니다. 그래서 한 번에 다 올리지 않고 파일 단위로 옮깁니다.

27.3lockdep: 일어나지 않은 교착을 찾는다#

교착은 시험으로 찾기 어렵습니다. 두 CPU가 정확히 나쁜 순서로 맞물려야 일어나기 때문입니다. lockdep은 다른 길을 택합니다. 교착이 일어나기를 기다리지 않고, 락을 잡는 순서를 기록해 두었다가 모순되는 순서가 한 번이라도 관찰되면 보고합니다.

lockdep이 다루는 단위는 락 하나하나가 아니라 락 클래스입니다. 아이노드가 백만 개 있어도 "아이노드의 락"은 클래스 하나입니다. 락을 잡을 때마다 lockdep은 "지금 쥐고 있는 클래스 → 새로 잡는 클래스"라는 간선을 그래프에 더합니다. 새 간선이 순환을 만들면 교착 가능성이 있다는 뜻입니다. 문서는 이것을 이렇게 표현합니다.

Documentation/locking/lockdep-design.rstv7.3
I.e. complex multi-CPU and multi-task locking scenarios do not have to
occur in practice to prove a deadlock: only the simple 'component'
locking chains have to occur at least once (anytime, in any
task/context) for the validator to be able to prove correctness. [...]

문서는 CPU가 셋 넘게 있어야 나는 교착도 CPU 하나짜리 시스템에서 찾아낼 수 있다고 덧붙입니다. 각 순서가 한 번씩만 실행되면 됩니다. 시험해야 할 것이 "모든 타이밍의 조합"에서 "모든 락 순서를 한 번씩"으로 줄어듭니다.

lockdep은 순서만 보지 않습니다. 락마다 "인터럽트 핸들러 안에서 잡힌 적이 있는가", "인터럽트를 켠 채 잡힌 적이 있는가"를 기록합니다. 인터럽트 핸들러에서 잡는 락을 다른 곳에서 인터럽트를 켠 채 잡았다면, 그 사이에 인터럽트가 와서 같은 락을 다시 잡으려 할 수 있습니다. 13장의 "어떤 락을 쓸지 고르는 표"를 어긴 코드가 이 검사에 걸립니다.

보고서는 정해진 틀로 나옵니다.

kernel/locking/lockdep.cv7.3
    pr_warn("======================================================\n");
    pr_warn("WARNING: possible circular locking dependency detected\n");
    print_kernel_ident();
    pr_warn("------------------------------------------------------\n");
    pr_warn("%s/%d is trying to acquire lock:\n",
        curr->comm, task_pid_nr(curr));
    print_lock(check_src);

    pr_warn("\nbut task is already holding lock:\n");

    print_lock(check_tgt);
    pr_warn("\nwhich lock already depends on the new lock.\n\n");

"잡으려는 락", "이미 쥔 락", "그런데 쥔 락이 이미 새 락에 의존한다"는 세 문장이 뼈대입니다. 그 뒤에 각 간선이 처음 기록된 때의 콜 스택과, 그림 27-2의 오른쪽처럼 두 CPU가 맞물리는 시나리오가 표로 따라옵니다.

비용이 커서 운영 환경에는 켜지 않습니다. 같은 순서의 락 묶음은 해시로 기억해 두고 한 번만 검사하는 방법으로 개발·시험용 커널에서 쓸 만한 속도를 냅니다. 첫 번째 문제를 보고한 뒤에는 스스로 꺼집니다.

27.4메모리 검사기: KASAN과 KFENCE#

C에는 배열의 끝을 넘는 접근이나 해제한 메모리를 쓰는 접근을 막는 장치가 없습니다. 그런 접근은 그 자리에서 죽지 않고, 한참 뒤에 전혀 다른 곳에서 증상을 냅니다. 메모리 검사기는 잘못된 접근을 일어난 그 순간에 잡습니다.

KASAN: 모든 접근을 검사한다

KASAN(Kernel Address Sanitizer)은 메모리의 모든 바이트에 대해 "접근해도 되는가"를 따로 적어 둡니다. 그 기록이 섀도 메모리(shadow memory)입니다. 메모리 8바이트마다 섀도 1바이트가 대응합니다.

include/linux/kasan.hv7.3
static inline void *kasan_mem_to_shadow(const void *addr)
{
    return (void *)((unsigned long)addr >> KASAN_SHADOW_SCALE_SHIFT)
        + KASAN_SHADOW_OFFSET;
}

주소를 3비트 밀고 상수를 더하면 섀도의 주소입니다. 컴파일러가 모든 메모리 접근 앞에 이 섀도 바이트를 확인하는 코드를 끼워 넣습니다. 섀도 값 00은 8바이트 전부 접근 가능, 1부터 7까지의 N은 앞의 N바이트만 가능, 음수는 접근 불가입니다. 음수의 값으로 까닭을 구분합니다. mm/kasan/kasan.h에서 0xFC는 슬랩 객체 사이의 레드존(redzone), 0xFB는 해제된 객체입니다.

할당자와의 협력이 나머지를 채웁니다. 객체를 할당하면 그 범위의 섀도를 열고, 객체 사이는 레드존으로 닫아 둡니다. 해제하면 섀도를 닫고 객체를 한동안 격리소(quarantine)에 두어 재사용을 늦춥니다. 해제된 메모리가 곧바로 다른 용도로 쓰이면 해제 후 사용을 구분할 수 없기 때문입니다.

대가는 메모리의 8분의 1과 실행 속도입니다. 이 방식(Generic KASAN)은 디버깅용이고 x86_64를 비롯한 여덟 아키텍처에서 됩니다. arm64에는 포인터의 위쪽 비트에 꼬리표를 두는 두 방식이 더 있습니다. 그 가운데 하드웨어의 메모리 태깅(MTE)을 쓰는 방식은 운영 환경에서도 쓸 수 있다고 문서는 적습니다.

KFENCE: 표본만 검사한다

KASAN은 너무 무거워서 운영 환경에 켤 수 없습니다. 그런데 어떤 버그는 운영 환경의 부하에서만 드러납니다. KFENCE는 그 틈을 메웁니다.

방법은 표본 추출입니다. 기본값으로 100밀리초마다 kmalloc() 하나를 골라 특별한 풀에서 내줍니다. 이 풀의 객체는 페이지의 왼쪽 끝이나 오른쪽 끝에 붙어 있고, 이웃 페이지는 매핑이 막혀 있습니다. 객체의 끝을 넘으면 페이지 폴트가 나고, KFENCE가 그 폴트를 받아 보고서를 냅니다. 해제된 객체의 페이지도 막아 두므로 해제 후 사용도 폴트가 됩니다.

검사 코드를 끼워 넣지 않고 MMU에게 검사를 맡긴 것입니다. 풀은 기본 255개 객체, 4KB 페이지 기준 2MiB이고, 문서의 표현으로 성능 부담은 0에 가깝습니다. 대신 어떤 접근이 검사받을지는 운에 달렸습니다. KFENCE의 설계 근거는 기계의 수입니다. 한 대에서는 드물게 걸리지만, 수만 대에서 몇 달을 돌리면 드문 경로의 버그도 걸립니다.

설계 노트

검사기에는 두 가지 비용 모형이 있습니다.

전수 검사(lockdep, KASAN)는 모든 사건을 봅니다. 한 번 실행된 경로의 버그는 반드시 잡지만 느립니다. 그래서 개발자의 장비와 CI에서 돌립니다. 약점은 범위입니다. 시험에서 실행되지 않은 경로는 보지 못합니다.

표본 검사(KFENCE, 그리고 감시 지점을 무작위로 두는 KCSAN)는 일부만 봅니다. 한 번의 실행에서 잡을 확률은 낮지만 싸므로 어디에나, 오래 켜 둘 수 있습니다. 범위는 실제 운영 부하 전체입니다.

둘은 경쟁하지 않습니다. 앞의 것은 "시험이 닿는 곳을 깊게", 뒤의 것은 "시험이 닿지 않는 곳을 얕고 넓게" 봅니다. 검사 도구를 고를 때 물을 것은 "얼마나 정확한가"만이 아니라 "얼마나 많은 실행에 켜 둘 수 있는가"입니다.

27.5테스트: KUnit과 kselftest#

검사기는 "실행 중에 나쁜 일이 생기면 알려 주는" 도구입니다. 무엇을 실행할지는 테스트가 정합니다. 커널의 테스트 틀은 둘입니다.

KUnit은 커널 안에서 도는 단위 테스트입니다. 테스트 코드가 커널의 일부이므로 유저 공간에 드러나지 않는 내부 함수를 직접 부릅니다. 25장의 내장 리스트를 시험하는 코드입니다.

lib/tests/list-test.cv7.3
static void list_test_list_add(struct kunit *test)
{
    struct list_head a, b;
    LIST_HEAD(list);

    list_add(&a, &list);
    list_add(&b, &list);

    /* should be [list] -> b -> a */
    KUNIT_EXPECT_PTR_EQ(test, list.next, &b);
    KUNIT_EXPECT_PTR_EQ(test, b.prev, &list);
    KUNIT_EXPECT_PTR_EQ(test, b.next, &a);
}

KUNIT_EXPECT_*는 실패해도 테스트를 계속하고, KUNIT_ASSERT_*는 그 자리에서 그 테스트를 끝냅니다. 테스트 함수들은 kunit_case 배열로 묶여 kunit_suite가 되고, kunit_test_suites()로 등록됩니다. 실행은 래퍼 스크립트가 맡습니다.

터미널
$ ./tools/testing/kunit/kunit.py run
$ ./tools/testing/kunit/kunit.py run --arch=x86_64

첫 명령은 커널을 유저 모드 리눅스(UML)로 빌드해 보통의 프로세스로 실행합니다. 가상 머신도 root 권한도 필요 없습니다. 둘째는 QEMU에서 x86_64 커널로 돌립니다.

kselftest는 커널 밖에서 도는 테스트입니다. tools/testing/selftests/ 아래의 유저 공간 프로그램과 스크립트가 시스템 콜, /proc, /sys를 통해 커널을 시험합니다. v7.3에는 futex, rseq, cgroup, sched_ext, bpf, rcutorture 등 125개의 디렉터리가 있습니다. 문서는 새 시스템 콜에는 kselftest가 따라와야 한다고 적습니다.

26장의 호환성 경계와 겹쳐 보면 뜻이 분명해집니다. kselftest는 약속한 면을 지키는 테스트이고, KUnit은 그 안쪽을 마음 놓고 고치기 위한 테스트입니다. 이 밖에 파일시스템의 xfstests, 블록 계층의 blktests처럼 트리 밖에서 관리되는 서브시스템별 테스트 묶음이 있습니다.

테스트와 검사기는 곱해서 씁니다. KASAN과 lockdep을 켠 커널에서 테스트를 돌리면, 테스트가 확인하는 결과값 말고도 그 경로에서 일어난 모든 잘못된 접근과 락 순서가 함께 검사됩니다.

참고 · 모델 검사와 런타임 검증

가능한 모든 경우를 따지는 도구도 일부 영역에 쓰입니다. tools/memory-model/의 리눅스 커널 메모리 모델(LKMM)은 13장의 메모리 순서 규칙을 형식 언어로 적은 것으로, 몇 줄짜리 동시성 코드 조각이 가질 수 있는 모든 실행 순서를 도구로 열거합니다. Documentation/trace/rv/의 런타임 검증(RV)은 "태스크를 깨우는 일은 언제나 선점이 꺼진 상태에서 일어난다" 같은 명세를 오토마타로 적고, 실행 중인 커널의 추적 이벤트가 그 명세를 벗어나는지 지켜봅니다.

27.6퍼저와 봇#

사람이 쓴 테스트는 사람이 떠올린 경우만 시험합니다. 퍼저(fuzzer)는 입력을 기계로 만들어 냅니다. 커널에서 가장 큰 몫을 하는 것이 syzkaller와, 그것을 계속 돌리며 결과를 보고하는 syzbot입니다.

syzkaller의 입력은 시스템 콜의 나열입니다. 무작위 바이트를 던지면 대부분 첫 인자 검사에서 튕겨 나오므로, 시스템 콜의 꼴을 기술한 언어가 있습니다. syzkaller 문서의 예입니다.

출력
open(file filename, flags flags[open_flags], mode flags[open_mode]) fd
read(fd fd, buf buffer[out], count len[buf])
close(fd fd)

open이 fd를 돌려주고 read가 fd를 받는다는 관계가 적혀 있으므로, 퍼저는 "열고, 읽고, 닫는" 뜻이 통하는 프로그램을 만듭니다. 만든 프로그램은 가상 머신 안의 커널에서 실행합니다. 그 커널에는 KASAN, lockdep 같은 검사기가 켜져 있습니다. 퍼저는 입력을 만들고, 잘못을 알아채는 일은 앞 절들의 검사기가 합니다.

어느 프로그램이 쓸모 있는지는 커버리지로 판단합니다. 커널의 KCOV가 그 정보를 줍니다.

Documentation/dev-tools/kcov.rstv7.3
KCOV collects and exposes kernel code coverage information in a form suitable
for coverage-guided fuzzing. Coverage data of a running kernel is exported via
the ``kcov`` debugfs file. Coverage collection is enabled on a task basis, and
thus KCOV can capture precise coverage of a single system call.

태스크 단위로 "이 시스템 콜이 커널의 어느 코드를 지나갔는가"를 알려 줍니다. 전에 못 가 본 코드에 닿은 프로그램은 보관했다가 조금씩 바꿔 다시 씁니다. 앞에서 __guarded_by의 예로 본 struct kcov가 이 기능의 자료구조입니다.

충돌이 나면 syzbot은 다음 일을 사람 없이 합니다.

  1. 로그에서 충돌을 일으킨 프로그램을 찾아 가장 작은 재현기로 줄입니다. 가능하면 C 프로그램으로 바꿉니다.
  2. 재현기로 이등분을 돌려 원인 커밋을 찾습니다.
  3. 충돌 보고서, 커널 설정, 재현기를 묶어 해당 메일링 리스트에 보냅니다. 상태는 공개 대시보드 syzkaller.appspot.com에 올립니다.
  4. 수정 패치의 커밋 메시지에는 Reported-by: syzbot+해시@syzkaller.appspotmail.com을 넣습니다. 이 해시로 syzbot이 버그와 수정을 잇습니다.
  5. 수정 커밋이 시험하는 모든 트리에 닿을 때까지 지켜본 뒤에 버그를 닫습니다. 같은 충돌이 다시 나면 새 버그로 엽니다.

개발자는 메일 답장으로 syzbot에게 일을 시킬 수 있습니다. 패치를 붙여 #syz test라고 답하면 그 패치를 적용한 커널에서 재현기를 돌려 결과를 알려 줍니다.

패치를 받아 돌려 보는 봇들

퍼저 말고도 여러 시스템이 공개된 패치와 트리를 지켜봅니다.

  • kernel test robot: Intel이 운영하는 0-day 시험 서비스입니다. 메일링 리스트의 패치와 개발 트리를 여러 아키텍처와 설정으로 빌드하고, 빌드 오류와 성능 저하를 작성자에게 답장으로 알립니다.
  • KernelCI: 여러 기관의 시험 장비를 묶어 업스트림 커널을 시험하는 리눅스 재단 프로젝트입니다.
  • linux-next와 안정 rc: 통합된 트리 자체가 시험 대상입니다. 안정 릴리스의 rc는 공개된 뒤 여러 곳에서 시험 결과가 Tested-by:로 돌아옵니다(26장).
  • regzbot: 보고된 회귀가 고쳐질 때까지 추적합니다(26장).
  • Sashiko: 2026년 3월에 발표된, LLM으로 메일링 리스트의 패치를 검토하는 시스템입니다. v7.3에서 Reported-by 태그의 19.4%가 이 도구의 것이었습니다.

어느 것도 병합의 관문이 아닙니다. 결과는 메일로 돌아오고, 판단은 메인테이너가 합니다.

설계 노트

이 구조의 분업은 분명합니다. 기계는 찾고, 줄이고, 원인 커밋을 가리킵니다. 사람은 이해하고 고칩니다.

기계가 잘하는 일은 넓게 뒤지는 것, 같은 일을 지치지 않고 되풀이하는 것, 수백 가지 설정을 빌드하는 것입니다. syzbot이 재현기를 최소화하고 이등분까지 해 주면, 개발자가 받는 것은 "이 스무 줄짜리 프로그램을 돌리면 이 커밋부터 이 경고가 난다"입니다. 디버깅에서 가장 시간이 드는 재현과 범위 좁히기가 끝난 상태입니다.

이 분업이 성립하려면 조건이 있습니다. 검사기가 잘못을 그 자리에서 기계가 읽을 수 있는 꼴로 알려야 하고(KASAN 보고서의 정해진 형식), 역사가 이등분 가능해야 하며(26장), 보고와 수정을 잇는 표식이 커밋에 남아야 합니다(Reported-by, Closes). 자동화는 도구 하나가 아니라 이 규약들의 합입니다.

27.7하드닝: 버그가 있어도 덜 위험하게#

앞의 도구들은 버그를 찾습니다. 그래도 남는 버그가 있습니다. 하드닝(hardening)은 남은 버그가 공격에 쓰이기 어렵게 만드는 장치들입니다. 운영 커널에 켜 두는 것이므로 싸야 합니다. kernel/configs/hardening.config가 기본 묶음을 모아 둔 설정 조각입니다.

kernel/configs/hardening.configv7.3
# Basic kernel memory permission enforcement.
CONFIG_STRICT_KERNEL_RWX=y
CONFIG_STRICT_MODULE_RWX=y
CONFIG_VMAP_STACK=y

# Kernel image and memory ASLR.
CONFIG_RANDOMIZE_BASE=y
CONFIG_RANDOMIZE_MEMORY=y

# Randomize allocator freelists, harden metadata.
CONFIG_SLAB_FREELIST_RANDOM=y
CONFIG_SLAB_FREELIST_HARDENED=y
갈래 옵션 막는 것
메모리 권한 STRICT_KERNEL_RWX 코드는 쓸 수 없고, 데이터는 실행할 수 없음
스택 VMAP_STACK, STACKPROTECTOR_STRONG 스택이 넘치면 보호 페이지에서 폴트, 복귀 주소 앞의 카나리 값 확인
무작위화 RANDOMIZE_BASE(KASLR), SLAB_FREELIST_RANDOM 커널과 객체의 주소를 예측하기 어렵게 함
경계 검사 FORTIFY_SOURCE, UBSAN_BOUNDS, HARDENED_USERCOPY 크기를 아는 버퍼를 넘는 memcpy(), 배열 인덱스, 유저 복사
초기화 INIT_STACK_ALL_ZERO, INIT_ON_ALLOC_DEFAULT_ON 초기화하지 않은 변수로 옛 데이터가 새는 것
제어 흐름 CFI, x86의 X86_KERNEL_IBT 덮어쓴 함수 포인터로 엉뚱한 코드를 실행하는 것
표본 검사 KFENCE 앞 절 참고

마지막에서 둘째 줄을 자세히 봅니다. 25장에서 본 대로 커널은 file_operations 같은 함수 포인터 표로 다형성을 구현합니다. 공격자가 메모리 오염 버그로 그 포인터 하나를 덮어쓸 수 있다면 원하는 코드로 실행을 돌릴 수 있습니다. 제어 흐름 무결성(CFI)은 간접 호출의 목적지를 제한합니다.

arch/x86/include/asm/cfi.hv7.3
 * kCFI:
 *
 * __cfi_foo:
 *   movl $0x12345678, %eax
 *              # 11 nops when CONFIG_CALL_PADDING
 * foo:
 *   endbr64            # when IBT
 *   ... code here ...
 *   ret
 *
 * [...]
 * indirect call:
 *   lea foo(%rip), %r11
 *   ...
 *   movl $(-0x12345678), %r10d
 *   addl -4(%r11), %r10d   # -15 when CONFIG_CALL_PADDING
 *   jz   1f
 *   ud2
 * 1:call *%r11

읽을 곳은 둘입니다. 함수 foo 바로 앞에 그 함수의 타입(인자와 반환값의 꼴)에서 계산한 해시가 놓입니다. 간접 호출을 하는 쪽은 목적지 주소의 바로 앞 4바이트를 읽어 자기가 기대하는 해시와 더해 보고, 0이 아니면 ud2로 트랩을 냅니다. 포인터를 덮어쓰더라도 타입이 같은 함수로만 뛸 수 있습니다. IBT는 CPU가 하는 더 거친 검사로, 간접 분기가 endbr64 명령어가 아닌 곳에 떨어지면 폴트를 냅니다.

같은 생각이 자료형에도 적용됩니다. refcount_t는 참조 카운터가 넘치면 0으로 돌아가는 대신 한 값에 붙어 버립니다. 객체는 영영 해제되지 않지만 해제 후 사용보다는 누수가 낫다는 판단입니다. 구조체 끝의 가변 길이 배열에는 __counted_by(필드)를 붙여 "이 배열의 길이는 저 필드에 있다"고 컴파일러에 알립니다. 그러면 컴파일러의 경계 검사가 그 길이를 쓸 수 있습니다. 스택의 가변 길이 배열은 아예 금지입니다.

27.8Rust: 틀린 코드를 쓸 수 없게#

지금까지의 도구는 C로 쓴 코드를 바깥에서 검사합니다. Rust는 방향이 다릅니다. 메모리 안전과 데이터 경쟁에 관한 규칙을 언어의 타입 시스템에 넣어, 어긴 코드가 컴파일되지 않게 합니다. 앞의 사다리에서 맨 위 칸입니다.

커널의 Rust 지원은 v6.1에 실험으로 들어왔습니다. 2025년 12월의 메인테이너 서밋은 그 실험이 성공으로 끝났다고 결론 냈고, v6.19 문서까지 있던 "The Rust experiment" 절은 v7.0 문서에서 빠졌습니다. v7.3 트리에는 .rs 파일이 496개 있습니다. rust/ 아래의 공통 코드가 369개, 드라이버가 102개입니다. 드라이버 가운데 큰 것은 NVIDIA GPU용 nova-core와 안드로이드의 Binder이고, Arm Mali GPU 드라이버 tyr, 블록 장치 rnull, 이더넷 PHY 드라이버 둘이 있습니다. 지원 아키텍처는 x86_64, arm64, arm, riscv, loongarch, s390, um 일곱이고, 컴파일러는 Rust 1.85.0 이상이 필요합니다.

가장 작은 모듈은 이렇게 생겼습니다.

samples/rust/rust_minimal.rsv7.3
struct RustMinimal {
    numbers: KVec<i32>,
}

impl kernel::Module for RustMinimal {
    fn init(_module: &'static ThisModule) -> Result<Self> {
        pr_info!("Rust minimal sample (init)\n");
        /* ... */

        let mut numbers = KVec::new();
        numbers.push(72, GFP_KERNEL)?;
        numbers.push(108, GFP_KERNEL)?;
        numbers.push(200, GFP_KERNEL)?;

        Ok(RustMinimal { numbers })
    }
}

impl Drop for RustMinimal {
    fn drop(&mut self) {
        pr_info!("My numbers are {:?}\n", self.numbers);
        pr_info!("Rust minimal sample (exit)\n");
    }
}

C 모듈과 견주어 읽을 곳은 세 군데입니다.

  • init의 반환형이 Result<Self>입니다. 초기화가 성공하면 모듈의 상태를 담은 값을 돌려주고, 실패하면 오류를 돌려줍니다. 초기화하다 만 상태가 존재할 수 없습니다.
  • push(72, GFP_KERNEL)?. 할당이 실패할 수 있다는 사실이 타입에 있습니다. 끝의 ?는 실패하면 그 오류를 들고 함수를 빠져나갑니다. 반환값 검사를 빼먹으면 컴파일되지 않습니다. GFP_KERNEL을 넘기는 것은 18장의 C 할당자와 같습니다.
  • exit 함수가 없습니다. 모듈이 내려갈 때 RustMinimal 값이 버려지면서 drop이 불리고, KVec의 메모리도 그때 해제됩니다. 25장의 guard()가 흉내 낸 것이 이 동작입니다.

안전한 추상화라는 층

커널의 Rust 코드는 C 코어 위에 얹혀 있습니다. 스핀락은 여전히 C의 spin_lock()입니다. 그 사이를 rust/kernel/의 추상화 층이 잇습니다.

rust/kernel/sync/lock/spinlock.rsv7.3
    #[inline]
    unsafe fn lock(ptr: *mut Self::State) -> Self::GuardState {
        // SAFETY: The safety requirements of this function ensure that `ptr` points to valid
        // memory, and that it has been initialised before.
        unsafe { bindings::spin_lock(ptr) }
    }

C 함수를 부르는 일은 컴파일러가 검증할 수 없으므로 unsafe 블록에 들어갑니다. 커널의 규칙은 모든 unsafe 블록 앞에 // SAFETY: 주석으로 왜 이 호출이 안전한지를 적는 것입니다. 리뷰어는 그 주석이 참인지를 봅니다. 이 층 위에서 드라이버가 쓰는 인터페이스는 이렇습니다.

rust/kernel/sync/lock.rsv7.3
impl<T: ?Sized, B: Backend> Lock<T, B> {
    /// Acquires the lock and gives the caller access to the data protected by it.
    #[inline]
    pub fn lock(&self) -> Guard<'_, T, B> {
        // SAFETY: The constructor of the type calls `init`, so the existence of the object proves
        // that `init` was called.
        let state = unsafe { B::lock(self.state.get()) };
        // SAFETY: The lock was just acquired.
        unsafe { Guard::new(self, state) }
    }

Lock<T, B>는 락과 그 락이 보호하는 데이터 T를 한 덩어리로 쌉니다. 데이터에 닿는 길은 lock()이 돌려주는 Guard뿐이고, Guard가 버려질 때 락이 풀립니다. C에서 __guarded_by로 검사하던 규칙이 여기서는 타입의 구조입니다. 락을 잡지 않고 데이터를 만지는 코드, 락을 풀고 나서 데이터의 참조를 쥐고 있는 코드는 쓸 수 없습니다.

Rust가 컴파일 시점으로 옮기는 것과 옮기지 못하는 것을 나누면 이렇습니다.

막는 것 못 막는 것
해제 후 사용, 이중 해제 논리 오류. 잘못된 값을 "안전하게" 쓰는 코드

정리#

  • 커널의 품질은 성질이 다른 여러 겹의 검사로 지킵니다. 같은 버그는 일찍 잡힐수록 쌉니다.
  • 컴파일 시점에는 경고, static_assert, sparse, Clang의 컨텍스트 분석, Coccinelle이 있습니다. __guarded_by는 "이 락을 쥐고 만질 것"이라는 주석을 컴파일러가 읽게 만든 것입니다.
  • lockdep은 락 클래스 사이의 순서를 그래프로 기록합니다. 모순되는 순서가 각각 한 번씩만 실행되어도 교착 가능성을 보고합니다.
  • KASAN은 섀도 메모리로 모든 접근을 검사하고, KFENCE는 보호 페이지로 일부 할당만 검사합니다. 앞의 것은 시험용, 뒤의 것은 운영용입니다.
  • KUnit은 커널 안에서 내부 함수를, kselftest는 유저 공간에서 드러난 인터페이스를 시험합니다.
  • syzbot은 커버리지를 길잡이로 시스템 콜 프로그램을 만들고, 충돌이 나면 재현기 최소화와 이등분까지 한 뒤 보고합니다.
  • 하드닝은 남은 버그가 악용되기 어렵게 합니다. kCFI는 간접 호출의 목적지를 타입이 같은 함수로 제한합니다.
  • Rust는 메모리 안전과 데이터 경쟁의 규칙을 타입으로 옮깁니다. unsafe는 추상화 층에 모으고 // SAFETY: 주석으로 근거를 남깁니다.

확인 문제#

시험 장비는 CPU가 하나뿐이고, 시험 스크립트는 기능 X와 기능 Y를 차례로 한 번씩 실행합니다. X는 락 A를 쥔 채 B를 잡고, Y는 B를 쥔 채 A를 잡습니다. 이 시험에서 교착이 일어납니까? lockdep은 무엇을 보고합니까?

답 보기

교착은 일어나지 않습니다. X와 Y가 겹쳐 실행되지 않았기 때문입니다. 그래도 lockdep은 보고합니다. X가 실행될 때 "A → B" 간선이 그래프에 기록되고, Y가 B를 쥔 채 A를 잡으려는 순간 "B → A" 간선이 순환을 만들기 때문입니다. lockdep이 검사하는 것은 실제로 일어난 교착이 아니라 관찰된 순서들 사이의 모순입니다. 다만 X와 Y 가운데 하나라도 시험에서 실행되지 않았다면 lockdep도 알 수 없습니다.

KASAN이 켜진 커널에서 p = kmalloc(20, GFP_KERNEL) 뒤에 p[20] = 0을 실행했습니다. KASAN은 이 쓰기가 잘못되었음을 어떻게 압니까? 같은 코드가 KFENCE만 켜진 커널에서는 왜 대부분 잡히지 않습니까?

답 보기

KASAN은 할당할 때 그 객체의 섀도 바이트를 00 00 04로 적어 둡니다. 앞의 16바이트는 전부, 셋째 묶음은 앞의 4바이트만 접근할 수 있다는 뜻입니다. p[20]은 셋째 묶음의 다섯째 바이트입니다. 컴파일러가 쓰기 앞에 끼워 넣은 검사가 섀도 값 4를 보고 범위 밖임을 알아챕니다. KFENCE는 계측 없이 보호 페이지에 기댑니다. 이 할당이 표본으로 뽑혀 KFENCE 풀에서 나온 경우에만, 객체 바로 옆의 보호 페이지를 건드려 폴트가 납니다. 기본 설정으로 100밀리초에 할당 하나만 뽑히므로 대부분의 할당은 보통의 슬랩에서 나오고, 그 경우 넘친 바이트는 조용히 이웃 메모리에 쓰입니다.

syzbot이 KASAN의 해제 후 사용 보고서와 C 재현기를 보내왔습니다. 이등분 결과는 석 달 전에 들어간 커밋을 가리킵니다. 수정 패치의 커밋 메시지에 들어가야 할 태그를 26장의 규칙으로 꼽아 보세요. 각각 어떤 도구가 읽습니까?

kCFI가 켜진 커널에서 공격자가 메모리 오염 버그로 file_operations의 read 포인터를 덮어쓸 수 있게 되었습니다. 이 포인터를 임의의 커널 함수 주소로 바꾸면 어떻게 됩니까? kCFI가 막지 못하는 경우는 무엇입니까?

답 보기

read를 간접 호출하는 코드는 목적지 주소 바로 앞의 4바이트를 읽어, read 함수 포인터의 타입에서 계산한 해시와 견줍니다. 덮어쓴 주소가 타입이 다른 함수이거나 함수의 시작이 아닌 곳이면 해시가 맞지 않아 ud2 트랩이 납니다. 막지 못하는 것은 타입이 정확히 같은 다른 함수로 바꾸는 경우입니다. 해시는 함수의 타입만 보기 때문입니다. 또 kCFI는 간접 호출만 검사하므로, 스택의 복귀 주소를 덮어쓰는 공격은 스택 카나리나 섀도 스택 같은 다른 장치가 맡습니다.

용어#

sparse
__user, __rcu, __bitwise 같은 커널의 타입 주석을 검사하는 정적 분석기.
컨텍스트 분석context analysis
__guarded_by, __must_hold 주석으로 락 규칙을 컴파일 시점에 검사하는 Clang의 기능.
lockdep
락 클래스 사이의 획득 순서를 기록해 교착 가능성을 찾는 런타임 검사기.
락 클래스lock class
락 규칙이 같은 락들의 묶음. lockdep이 다루는 단위.
섀도 메모리shadow memory
KASAN이 메모리 8바이트마다 1바이트씩 두는 접근 가능 여부의 기록.
레드존redzone
객체 사이에 두는 접근 금지 영역. 경계를 넘는 접근을 드러낸다.
KFENCE
일부 할당만 보호 페이지 사이에 두어 검사하는, 운영 환경용 메모리 검사기.
KUnit
커널 안에서 실행되는 단위 테스트 틀.
kselftest
유저 공간에서 커널의 인터페이스를 시험하는 테스트 모음.
퍼저fuzzer
입력을 기계로 만들어 프로그램의 버그를 찾는 도구.
제어 흐름 무결성control flow integrity
간접 호출과 복귀의 목적지를 제한해, 덮어쓴 포인터로 엉뚱한 코드가 실행되는 것을 막는 기법.
