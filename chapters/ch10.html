커널의 IRQ 계층

irq_desc에서 핸들러까지, 여러 CPU가 같은 IRQ를 만날 때

Linux v7.3 기준약 55분
읽는 소스include/linux/irqdesc.hkernel/irq/irqdesc.cinclude/linux/irq.hkernel/irq/chip.ckernel/irq/internals.harch/x86/include/asm/idtentry.harch/x86/kernel/irq.ckernel/irq/handle.c

CPU가 커널에 건네주는 것은 벡터 번호 하나입니다. 그 숫자에서 "이 NVMe 장치의 3번 큐가 일을 마쳤다"까지 가려면 여러 질문에 답해야 합니다. 어느 장치인가. 그 장치의 드라이버가 등록한 함수는 무엇인가. 컨트롤러에는 언제 어떤 응답을 보내야 하는가. 처리하는 도중에 같은 인터럽트가 다른 CPU에 또 오면 어떻게 하는가. 그리고 이 답은 APIC을 쓰는 PC에서도, GIC을 쓰는 ARM 보드에서도 같은 드라이버 코드로 통해야 합니다. 이 장은 그 사이를 메우는 커널의 IRQ 계층을 읽습니다.

이 장에서 답하는 질문
  • 하드웨어 IRQ 번호, 리눅스 IRQ 번호, 벡터는 각각 무엇이고 누가 이어 주는가?
  • irq_desc 안의 irq_chip, 플로 핸들러, irqaction은 각각 무엇을 책임지는가?
  • 벡터 번호에서 드라이버의 핸들러까지 v7.3은 어떤 함수를 거치는가?
  • 같은 IRQ가 두 CPU에 잇달아 오면 핸들러는 어떻게 한 번에 하나만 실행되는가?
  • 여러 장치가 IRQ 하나를 나눠 쓸 때 커널은 누구의 인터럽트인지 어떻게 아는가?
  • 인터럽트가 어느 CPU로 갈지는 누가, 무엇을 근거로 정하는가?

10.1번호가 셋이다#

인터럽트 하나에는 번호가 셋 붙습니다. 이 셋을 섞으면 그 뒤의 코드가 읽히지 않습니다.

  • 하드웨어 IRQ 번호(hwirq): 인터럽트 컨트롤러 안에서의 번호입니다. IO-APIC이라면 핀 번호, MSI-X라면 장치의 표에서 몇 번째 항목인지, GIC이라면 INTID입니다. 컨트롤러마다 0부터 따로 셉니다.
  • 리눅스 IRQ 번호: 커널이 인터럽트마다 붙이는 시스템 전체에서 유일한 번호입니다. 드라이버가 request_irq()에 넘기는 값이고 /proc/interrupts의 첫 열입니다. 하드웨어와는 아무 관계가 없는, irq_desc를 찾는 열쇠일 뿐입니다.
  • 벡터: x86 CPU가 인터럽트를 구분하는 번호입니다(9장). CPU마다 따로 배정합니다.

hwirq와 리눅스 IRQ 번호를 이어 주는 것이 irq_domain입니다. 컨트롤러 하나가 도메인 하나를 만들고, 그 안에서 hwirq를 리눅스 IRQ 번호로 바꾸는 표를 가집니다.

요즘 하드웨어에서는 인터럽트 하나가 컨트롤러를 여럿 거칩니다. x86에서 MSI-X 인터럽트는 장치의 MSI-X 표, IOMMU의 리매핑 표, CPU의 벡터를 차례로 지납니다. 커널은 이 경로를 도메인 계층으로 그대로 본뜹니다. 장치에 가까운 쪽이 자식이고 CPU에 가까운 쪽이 부모입니다. 인터럽트를 하나 할당하면 계층의 각 도메인이 자기 몫의 자원(표의 한 칸, 벡터 하나)을 잡고 자기 irq_data를 채웁니다. 친화성을 바꾸는 것 같은 요청은 자식에서 부모로 차례로 내려갑니다.

흔한 오해

"IRQ 번호는 하드웨어의 인터럽트 선 번호다." PIC 하나가 전부이던 시절에는 맞았습니다. IRQ 1은 PIC의 1번 선이고 벡터는 거기에 상수를 더한 값이었습니다. 지금 /proc/interrupts에 보이는 142는 커널이 할당한 순서에 가까운 숫자이고, 재부팅하면 달라질 수 있습니다. 하드웨어 쪽 번호는 같은 줄의 컨트롤러 이름 뒤에 따로 나옵니다. x86에서 0–15번만은 호환성 때문에 옛 ISA IRQ 번호와 같게 맞춰 둡니다.

10.2irq_desc#

리눅스 IRQ 번호 하나에 struct irq_desc 하나가 대응합니다. 이 인터럽트에 대해 커널이 아는 모든 것이 여기에 있습니다.

include/linux/irqdesc.hv7.3
struct irq_desc {
    struct irq_common_data  irq_common_data;
    struct irq_data     irq_data;
    struct irqstat __percpu *kstat_irqs;
    irq_flow_handler_t  handle_irq;
    struct irqaction    *action;    /* IRQ action list */
    unsigned int        status_use_accessors;
    unsigned int        core_internal_state__do_not_mess_with_it;
    unsigned int        depth;      /* nested irq disables */
    unsigned int        wake_depth; /* nested wake enables */
    /* ... */
    unsigned int        irq_count;  /* For detecting broken IRQs */
    unsigned int        irqs_unhandled;
    /* ... */
    raw_spinlock_t      lock;
    /* ... */
    struct mutex        request_mutex;
    /* ... */
    const char      *name;
    /* ... */
} ____cacheline_internodealigned_in_smp;

필드는 네 무리로 읽으면 됩니다.

  • 하드웨어 쪽: irq_data에는 리눅스 IRQ 번호(irq), hwirq, 그리고 이 인터럽트를 맡은 컨트롤러의 조작 함수 묶음인 irq_chip 포인터가 있습니다. irq_common_data에는 도메인 계층의 모든 irq_data가 함께 보는 값, 곧 상태 비트와 친화성 마스크가 있습니다.
  • 처리 방법: handle_irq는 이 인터럽트가 왔을 때 부를 함수입니다. 플로 핸들러(flow handler)라고 합니다.
  • 드라이버 쪽: action은 드라이버가 등록한 핸들러들의 연결 리스트입니다.
  • 동시성: lock은 이 구조체를 지키는 스핀락, depth는 disable_irq()가 중첩된 횟수, 이름이 긴 core_internal_state__do_not_mess_with_it은 코어만 쓰는 상태 비트입니다. request_mutex는 등록과 해제를 직렬화합니다.

kstat_irqs는 CPU별 횟수입니다. /proc/interrupts의 숫자가 여기서 나옵니다.

irq_desc는 배열이 아니라 트리에 들어 있습니다.

kernel/irq/irqdesc.cv7.3
static struct maple_tree sparse_irqs = MTREE_INIT_EXT(sparse_irqs,
                    MT_FLAGS_ALLOC_RANGE |
                    MT_FLAGS_LOCK_EXTERN |
                    MT_FLAGS_USE_RCU,
                    sparse_irq_lock);
/* ... */
struct irq_desc *irq_to_desc(unsigned int irq)
{
    return mtree_load(&sparse_irqs, irq);
}

리눅스 IRQ 번호는 드문드문 쓰입니다. CPU가 수백 개이고 장치마다 큐가 수백 개인 서버에서는 번호가 수만까지 가지만 실제로 쓰이는 것은 일부입니다. 그래서 필요할 때 할당해서 메이플 트리(17장)에 번호를 키로 넣습니다. MT_FLAGS_USE_RCU가 있으므로 찾는 쪽은 락 없이 읽습니다.

예전 자료와 다른 점

옛 자료는 irq_desc[NR_IRQS]라는 전역 배열을 그리고, IRQ 번호를 인덱스로 씁니다. v7.3에서 x86과 arm64는 CONFIG_SPARSE_IRQ를 쓰므로 배열이 없습니다. 디스크립터를 담는 자료구조는 래딕스 트리를 거쳐 6.5에서 메이플 트리가 되었고, 번호의 상한도 빌드 때 정한 값에서 INT_MAX로 풀렸습니다. 구조체 안도 달라졌습니다. 옛 판에 있던 status 한 워드는 뒤에서 볼 두 곳으로 갈라졌고, kstat_irqs는 정수 배열에서 struct irqstat로 바뀌었습니다.

10.3칩과 플로#

인터럽트 하나를 처리하려면 컨트롤러와 몇 가지를 주고받아야 합니다. 받았다고 알리고(ack), 필요하면 막고(mask), 다시 열고(unmask), 끝났다고 알립니다(eoi). 무엇을 하는지는 컨트롤러마다 다릅니다. IO-APIC의 마스크는 리다이렉션 항목의 비트 하나를 쓰는 일이고, PIC의 마스크는 포트 0x21에 쓰는 일입니다. 이 부분이 struct irq_chip입니다.

include/linux/irq.hv7.3
struct irq_chip {
    const char  *name;
    unsigned int    (*irq_startup)(struct irq_data *data);
    void        (*irq_shutdown)(struct irq_data *data);
    void        (*irq_enable)(struct irq_data *data);
    void        (*irq_disable)(struct irq_data *data);

    void        (*irq_ack)(struct irq_data *data);
    void        (*irq_mask)(struct irq_data *data);
    void        (*irq_mask_ack)(struct irq_data *data);
    void        (*irq_unmask)(struct irq_data *data);
    void        (*irq_eoi)(struct irq_data *data);

    int     (*irq_set_affinity)(struct irq_data *data, const struct cpumask *dest, bool force);
    /* ... */
    int     (*irq_set_type)(struct irq_data *data, unsigned int flow_type);
    /* ... */
};

어떤 순서로 하는지는 컨트롤러가 아니라 신호의 방식이 정합니다. 에지 트리거와 레벨 트리거는 순서가 달라야 합니다.

레벨 트리거의 플로 핸들러는 그림 그대로입니다.

kernel/irq/chip.cv7.3
void handle_level_irq(struct irq_desc *desc)
{
    guard(raw_spinlock)(&desc->lock);
    mask_ack_irq(desc);

    if (!irq_can_handle(desc))
        return;

    kstat_incr_irqs_this_cpu(desc);
    handle_irq_event(desc);

    cond_unmask_irq(desc);
}

막고, 드라이버의 핸들러들을 부르고(handle_irq_event()), 엽니다. mask_ack_irq()와 cond_unmask_irq()는 안에서 desc->irq_data.chip의 콜백을 부릅니다. 이 함수에는 IO-APIC이나 GIC이라는 말이 없습니다. guard(raw_spinlock)은 함수를 빠져나갈 때 락을 자동으로 푸는 표기입니다(14장).

코어가 제공하는 플로 핸들러는 몇 개뿐입니다.

플로 핸들러 순서 v7.3의 x86에서 쓰는 곳
handle_edge_irq() ack → 핸들러 → (그사이 또 왔으면 반복) MSI, MSI-X, IO-APIC의 에지 핀
handle_level_irq() mask·ack → 핸들러 → unmask 8259 PIC
handle_fasteoi_irq() 핸들러 → eoi IO-APIC의 레벨 핀
handle_percpu_irq() ack → 핸들러 → eoi, 락 없음 CPU마다 따로 오는 인터럽트

/proc/interrupts에서 hwirq 뒤에 붙는 -edge, -fasteoi가 이 이름입니다.

설계 노트

Documentation/core-api/genericirq.rst는 이 구조가 나온 까닭을 적어 두었습니다. 처음의 리눅스는 __do_IRQ()라는 함수 하나가 모든 종류의 인터럽트를 처리했고, 칩마다 다른 동작은 ->ack, ->end 같은 콜백으로 갈랐습니다. 그러자 "언제 무엇을 부르는가"라는 흐름의 논리와 "레지스터에 무엇을 쓰는가"라는 하드웨어의 논리가 콜백 안에서 뒤섞였습니다. i386에는 같은 IO-APIC을 두고 에지용 타입과 레벨용 타입이 따로 있었습니다. 해법은 축을 둘로 나누는 것이었습니다. 흐름은 플로 핸들러 몇 개로, 하드웨어는 irq_chip으로 나누면, 칩 M개와 흐름 N개를 M+N개의 코드로 덮습니다. 변하는 이유가 다른 것을 한 함수에 두지 않는다는 원칙의 사례입니다.

10.4상태 비트#

IRQ마다 상태가 있습니다. 꺼져 있는가, 마스크되어 있는가, 지금 어느 CPU에서 처리 중인가, 처리 중에 또 왔는가. v7.3은 이 비트들을 두 곳에 나눠 둡니다.

include/linux/irq.hv7.3
enum {
    IRQD_TRIGGER_MASK       = 0xf,
    IRQD_SETAFFINITY_PENDING    = BIT(8),
    /* ... */
    IRQD_LEVEL          = BIT(13),
    IRQD_WAKEUP_STATE       = BIT(14),
    IRQD_IRQ_DISABLED       = BIT(16),
    IRQD_IRQ_MASKED         = BIT(17),
    IRQD_IRQ_INPROGRESS     = BIT(18),
    /* ... */
    IRQD_AFFINITY_MANAGED       = BIT(21),
    /* ... */
};
kernel/irq/internals.hv7.3
enum {
    IRQS_AUTODETECT     = 0x00000001,
    IRQS_SPURIOUS_DISABLED  = 0x00000002,
    IRQS_POLL_INPROGRESS    = 0x00000008,
    IRQS_ONESHOT        = 0x00000020,
    IRQS_REPLAY     = 0x00000040,
    IRQS_WAITING        = 0x00000080,
    IRQS_PENDING        = 0x00000200,
    /* ... */
};

두 열거형은 정의된 파일부터 다릅니다. IRQD_*는 공개 헤더 include/linux/irq.h에 있고 irq_common_data.state_use_accessors에 저장됩니다. 칩 드라이버가 알아야 하는 상태입니다. IRQS_*는 kernel/irq/ 디렉터리 안의 internals.h에 있고 desc->core_internal_state__do_not_mess_with_it에 저장됩니다. 플로 핸들러와 코어만 쓰는 상태입니다.

예전 자료와 다른 점

옛 자료는 irq_desc[irq].status에 IRQ_DISABLED, IRQ_PENDING, IRQ_INPROGRESS, IRQ_WAITING이 함께 있다고 설명하고, 드라이버나 아키텍처 코드가 이 필드를 직접 읽고 고치는 예를 보여 줍니다. v7.3에는 이 이름들이 없습니다. 대응은 이렇습니다.

옛 비트 v7.3 뜻
IRQ_DISABLED IRQD_IRQ_DISABLED disable_irq()로 꺼 둔 상태
IRQ_INPROGRESS IRQD_IRQ_INPROGRESS 어느 CPU가 핸들러를 실행 중
IRQ_PENDING IRQS_PENDING 처리하지 못한 요청이 남아 있음
IRQ_WAITING IRQS_WAITING 아직 한 번도 오지 않음(자동 탐지용)

코어 밖의 코드가 상태 워드를 직접 고치지 못하게 하려는 것이 나눈 이유입니다.

설계 노트

C에는 private이 없습니다. 커널은 세 겹으로 같은 효과를 냅니다. 첫째는 이름입니다. state_use_accessors와 core_internal_state__do_not_mess_with_it은 필드 이름이 곧 경고문입니다. 이 필드를 직접 건드리는 패치는 리뷰에서 눈에 띌 수밖에 없습니다. 코어 안에서는 #define istate core_internal_state__do_not_mess_with_it으로 짧게 줄여 씁니다. 둘째는 접근자의 위치입니다. 읽는 함수 irqd_irq_inprogress()는 공개 헤더에 있고, 쓰는 함수 irqd_set()은 kernel/irq/internals.h에만 있습니다. 그 파일의 첫 주석은 "kernel/irq/ 밖에서는 이 파일을 포함하지 말라"입니다. 셋째는 정적 검사입니다. state_use_accessors에 붙은 __private 표시는 ACCESS_PRIVATE() 매크로를 거치지 않은 접근을 sparse가 잡아내게 합니다(27장). 언어가 주지 않는 캡슐화를 관례와 도구로 세운 것입니다.

10.5벡터에서 핸들러까지#

이제 인터럽트 하나를 따라갑니다. 9장은 진입 스텁이 pt_regs를 만들고 C 함수를 부르는 데서 끝났습니다.

common_interrupt()는 DEFINE_IDTENTRY_IRQ 매크로로 정의됩니다. 매크로가 함수의 겉을 만들고, 개발자가 쓴 본문은 그 안에서 불립니다.

arch/x86/include/asm/idtentry.hv7.3
#define DEFINE_IDTENTRY_IRQ(func)                   \
static void __##func(struct pt_regs *regs, u32 vector);         \
                                    \
__visible noinstr void func(struct pt_regs *regs,           \
                unsigned long error_code)           \
{                                   \
    irqentry_state_t state = irqentry_enter(regs);          \
    u32 vector = (u32)(u8)error_code;               \
                                    \
    kvm_set_cpu_l1tf_flush_l1d();                                   \
    instrumentation_begin();                    \
    run_irq_on_irqstack_cond(__##func, regs, vector);       \
    instrumentation_end();                      \
    irqentry_exit(regs, state);                 \
}                                   \
                                    \
static noinline void __##func(struct pt_regs *regs, u32 vector)
  • irqentry_enter()와 irqentry_exit()가 처리를 감쌉니다. 뒤의 것이 6장에서 본 복귀 갈림길입니다. 재스케줄 요청과 시그널이 여기서 처리됩니다.
  • run_irq_on_irqstack_cond()는 CPU마다 하나씩 있는 IRQ 스택으로 갈아탄 뒤 본문을 부릅니다. 태스크의 커널 스택은 크기가 정해져 있으므로, 깊은 시스템 콜 도중에 인터럽트가 와도 넘치지 않게 하려는 것입니다. 이 매크로는 본문 앞뒤로 irq_enter_rcu()와 irq_exit_rcu()도 부릅니다. 앞의 것이 preempt_count의 hardirq 칸을 올리고, 뒤의 것이 내린 다음 밀린 softirq를 실행합니다(11장).

본문은 짧습니다.

arch/x86/kernel/irq.cv7.3
static __always_inline bool call_irq_handler(int vector, struct pt_regs *regs)
{
    struct irq_desc *desc = __this_cpu_read(vector_irq[vector]);

    if (likely(!IS_ERR_OR_NULL(desc))) {
        handle_irq(desc, regs);
        return true;
    }
    /* ... */
}

/* ... */
DEFINE_IDTENTRY_IRQ(common_interrupt)
{
    struct pt_regs *old_regs = set_irq_regs(regs);

    /* entry code tells RCU that we're not quiescent.  Check it. */
    RCU_LOCKDEP_WARN(!rcu_is_watching(), "IRQ failed to wake up RCU");

    if (unlikely(!call_irq_handler(vector, regs)))
        apic_eoi();

    set_irq_regs(old_regs);
}

vector_irq는 CPU별 배열입니다. 256칸이고 칸마다 irq_desc 포인터가 들어 있습니다. 벡터에서 디스크립터를 찾는 일은 배열 읽기 한 번입니다. x86-64에서 handle_irq()는 desc->handle_irq(desc), 곧 플로 핸들러를 부르는 것이 전부입니다. 여기서부터는 아키텍처와 상관없는 코드입니다.

플로 핸들러는 칩과 응답을 주고받은 뒤 handle_irq_event()를 부릅니다.

kernel/irq/handle.cv7.3
irqreturn_t handle_irq_event(struct irq_desc *desc)
{
    irqreturn_t ret;

    desc->istate &= ~IRQS_PENDING;
    irqd_set(&desc->irq_data, IRQD_IRQ_INPROGRESS);
    raw_spin_unlock(&desc->lock);

    ret = handle_irq_event_percpu(desc);

    raw_spin_lock(&desc->lock);
    irqd_clear(&desc->irq_data, IRQD_IRQ_INPROGRESS);
    return ret;
}

이 함수는 desc->lock을 쥔 채로 불립니다. "처리 중" 표시를 세우고, 락을 풀고, 드라이버의 핸들러들을 부르고, 다시 락을 잡아 표시를 내립니다. 락을 푸는 이유는 다음 절에서 봅니다. 핸들러를 실제로 부르는 반복문은 한 단계 더 안에 있습니다.

kernel/irq/handle.cv7.3
irqreturn_t __handle_irq_event_percpu(struct irq_desc *desc)
{
    irqreturn_t retval = IRQ_NONE;
    unsigned int irq = desc->irq_data.irq;
    struct irqaction *action;

    for_each_action_of_desc(desc, action) {
        irqreturn_t res;

        /* ... */
        trace_irq_handler_entry(irq, action);
        /* ... */
            res = action->handler(irq, action->dev_id);
        /* ... */
        trace_irq_handler_exit(irq, action, res);

        if (WARN_ONCE(!irqs_disabled(),"irq %u handler %pS enabled interrupts\n",
                  irq, action->handler))
            local_irq_disable();

        /* ... IRQ_WAKE_THREAD면 스레드를 깨운다 ... */

        retval |= res;
    }

    return retval;
}

action 사슬에 달린 핸들러를 모두 부릅니다. 선을 나눠 쓰는 경우 어느 장치가 걸었는지 커널은 모르기 때문입니다. 핸들러가 돌려준 값을 OR로 모읍니다. 가운데의 WARN_ONCE는 규칙 하나를 말해 줍니다. 핸들러는 인터럽트가 꺼진 채로 불리고, 켜서 돌아오면 안 됩니다.

예전 자료와 다른 점

옛 자료의 경로는 do_IRQ() → __do_IRQ() → handle_IRQ_event()입니다. do_IRQ()는 irq_desc[] 배열을 IRQ 번호로 찾고, __do_IRQ() 하나가 모든 종류의 인터럽트를 처리하며, handle_IRQ_event()는 등록할 때 SA_INTERRUPT 플래그를 주지 않은 핸들러에 대해서는 local_irq_enable()로 인터럽트를 켠 뒤에 핸들러를 부릅니다. 느린 핸들러가 다른 인터럽트를 오래 막지 않게 하려는 배려였습니다.

v7.3에는 이 함수들이 없습니다. x86의 do_IRQ()는 5.8에서 common_interrupt()가 되었고, __do_IRQ()는 플로 핸들러들로 대체되었습니다. 핸들러는 예외 없이 인터럽트가 꺼진 채로 실행됩니다. 2010년에 그렇게 바뀌면서 SA_INTERRUPT와 그 뒤를 이은 IRQF_DISABLED는 뜻을 잃고 사라졌습니다. 핸들러 도중에 인터럽트가 겹쳐 들어오면 스택이 얼마나 깊어질지 알 수 없다는 것이 이유였습니다. 오래 걸리는 일은 인터럽트를 켜고 계속하는 것이 아니라 스레드나 softirq로 넘깁니다(11장).

10.6같은 IRQ를 두 CPU가 만날 때#

핸들러가 실행되는 CPU에서는 인터럽트가 꺼져 있습니다. 그런데 다른 CPU는 사정이 다릅니다. 장치가 인터럽트를 또 걸었고, 그 사이에 친화성이 바뀌었거나 컨트롤러가 다른 CPU를 골랐다면, 같은 IRQ가 다른 CPU에 도착합니다. 드라이버의 핸들러는 자기가 두 CPU에서 동시에 실행될 수 있다고 가정하고 쓰이지 않았습니다.

에지 트리거의 플로 핸들러가 이 문제를 푸는 코드입니다.

kernel/irq/chip.cv7.3
void handle_edge_irq(struct irq_desc *desc)
{
    guard(raw_spinlock)(&desc->lock);

    if (!irq_can_handle(desc)) {
        desc->istate |= IRQS_PENDING;
        mask_ack_irq(desc);
        return;
    }

    kstat_incr_irqs_this_cpu(desc);

    /* Start handling the irq */
    desc->irq_data.chip->irq_ack(&desc->irq_data);

    do {
        if (unlikely(!desc->action)) {
            mask_irq(desc);
            return;
        }

        /*
         * When another irq arrived while we were handling
         * one, we could have masked the irq.
         * Reenable it, if it was not disabled in meantime.
         */
        if (unlikely(desc->istate & IRQS_PENDING)) {
            if (!irqd_irq_disabled(&desc->irq_data) &&
                irqd_irq_masked(&desc->irq_data))
                unmask_irq(desc);
        }

        handle_irq_event(desc);

    } while ((desc->istate & IRQS_PENDING) && !irqd_irq_disabled(&desc->irq_data));
}

인터럽트를 받은 CPU는 세 가지 경우 가운데 하나를 만납니다.

① 아무도 처리하고 있지 않다. irq_can_handle()이 참입니다. 칩에 ack를 보내고 반복문으로 들어가 handle_irq_event()를 부릅니다. 이 함수가 IRQD_IRQ_INPROGRESS를 세우고 락을 풉니다.

② 다른 CPU가 처리하고 있다. irq_can_handle()은 IRQD_IRQ_INPROGRESS가 서 있는 것을 보고 거짓을 돌려줍니다. 이 CPU는 핸들러를 부르지 않습니다. IRQS_PENDING만 세우고, 같은 인터럽트가 더 오지 않게 마스크한 뒤 곧바로 돌아갑니다. 핸들러가 끝나기를 기다리지 않습니다.

③ 처리하던 CPU가 끝내려고 한다. handle_irq_event()에서 돌아온 CPU는 락을 쥔 채 while 조건을 봅니다. IRQS_PENDING이 서 있으면 처리하는 사이에 요청이 또 왔다는 뜻입니다. 반복문의 처음으로 돌아가 마스크를 풀고 핸들러를 한 번 더 부릅니다. IRQS_PENDING이 없을 때 비로소 빠져나갑니다.

결과적으로 한 IRQ의 핸들러는 언제나 한 CPU에서, 차례로 실행됩니다. 늦게 온 CPU는 일을 넘기고 떠나고, 먼저 온 CPU가 남의 몫까지 처리합니다.

이렇게 직렬화하는 데는 까닭이 있습니다. 같은 장치의 핸들러를 두 CPU에서 동시에 돌려 봐야 어차피 둘은 같은 장치 레지스터와 같은 드라이버 자료구조를 건드립니다. 드라이버가 자기 락으로 다시 줄을 세워야 하고, 캐시 라인은 두 CPU 사이를 오갑니다. 코어가 미리 줄을 세우면 드라이버는 "내 핸들러는 자기 자신과 겹쳐 실행되지 않는다"고 가정하고 짧게 쓸 수 있습니다.

handle_irq_event()가 핸들러를 부르는 동안 desc->lock을 푸는 것도 이 구조에 필요합니다. 락을 쥔 채로 핸들러를 부르면 ②의 CPU는 PENDING을 세우려고 락을 기다리며 핸들러가 끝날 때까지 헛돌게 됩니다. 락은 상태 비트를 읽고 쓰는 수십 나노초만 지키고, 핸들러끼리 겹치지 않게 하는 일은 INPROGRESS 비트가 맡습니다. 긴 구간은 플래그로, 플래그는 짧은 락으로 지키는 방식입니다. 드라이버가 핸들러 안에서 disable_irq_nosync()처럼 같은 디스크립터의 락이 필요한 함수를 부를 수 있는 것도 이 덕분입니다.

레벨 트리거에는 PENDING 반복문이 없습니다. 마스크를 풀었을 때 선이 아직 올라가 있으면 컨트롤러가 인터럽트를 다시 걸어 주기 때문입니다. 에지는 지나가면 그만이라서 소프트웨어가 "왔었다"는 사실을 기억해 두어야 합니다.

더 깊이v7.3의 예외: 친화성이 막 옮겨 온 CPU는 기다린다

②에는 예외가 하나 있습니다. irq_can_handle() 안의 irq_can_handle_pm()은, 이 IRQ의 목적지가 방금 이 CPU로 바뀌었는데 예전 목적지 CPU가 아직 핸들러를 실행 중이라면 PENDING을 세우지 않습니다. 대신 락을 풀고 IRQD_IRQ_INPROGRESS가 내려갈 때까지 짧게 헛돌며 기다렸다가 자기가 처리합니다(irq_wait_on_inprogress()). 소스 주석이 이유를 적어 두었습니다. 장치가 인터럽트를 매우 빠르게 걸면 예전 CPU는 핸들러를 마칠 때마다 PENDING을 발견해 반복문을 빠져나오지 못하고, 친화성을 옮겼는데도 처리는 계속 예전 CPU에서 일어납니다. 가상 머신에서 실제로 관찰된 현상입니다. 인터럽트를 한 CPU로만 보내는 칩의 에지 인터럽트에만 적용됩니다.

10.7드라이버가 쓰는 API#

드라이버는 지금까지 본 구조를 몰라도 됩니다. 함수 몇 개만 씁니다.

drivers/net/ethernet/intel/e1000e/netdev.cv7.3
static int e1000_request_irq(struct e1000_adapter *adapter)
{
    struct net_device *netdev = adapter->netdev;
    int err;

    if (adapter->msix_entries) {
        err = e1000_request_msix(adapter);
        if (!err)
            return err;
        /* ... */
    }
    if (adapter->flags & FLAG_MSI_ENABLED) {
        err = request_irq(adapter->pdev->irq, e1000_intr_msi, 0,
                  netdev->name, netdev);
        if (!err)
            return err;
        /* ... */
    }

    err = request_irq(adapter->pdev->irq, e1000_intr, IRQF_SHARED,
              netdev->name, netdev);
    if (err)
        e_err("Unable to allocate interrupt, Error: %d\n", err);

    return err;
}

request_irq(irq, handler, flags, name, dev_id)는 irqaction을 하나 만들어 그 IRQ의 action 사슬에 답니다. 해제는 free_irq()이고, 장치가 떨어질 때 자동으로 해제되는 devm_request_irq()도 있습니다. 이 드라이버는 MSI-X, MSI, 핀 인터럽트 순으로 시도합니다. 눈여겨볼 것은 마지막 호출의 IRQF_SHARED입니다. 핀 인터럽트는 다른 장치와 선을 나눠 쓸 수 있으므로 이 플래그를 줍니다. MSI에는 주지 않습니다.

공유 IRQ에서 지켜야 할 약속이 둘 있습니다.

  • dev_id가 유일해야 합니다. 핸들러가 불릴 때 두 번째 인자로 돌아오는 값이고, free_irq(irq, dev_id)가 사슬에서 어느 irqaction을 뗄지 찾는 열쇠입니다. 보통 장치 구조체의 포인터를 줍니다.
  • 핸들러는 먼저 자기 장치가 맞는지 확인해야 합니다. 사슬의 핸들러가 모두 불리기 때문입니다. e1000e의 e1000_intr()은 장치의 원인 레지스터를 읽어 값이 0이면 IRQ_NONE을 돌려주고 끝냅니다.

핸들러의 반환값은 셋입니다.

값 뜻
IRQ_NONE 내 장치의 인터럽트가 아니었다
IRQ_HANDLED 처리했다
IRQ_WAKE_THREAD 급한 일만 했다. 나머지를 할 스레드를 깨워 달라

사슬의 모든 핸들러가 IRQ_NONE을 돌려주면 주인 없는 인터럽트입니다. 한두 번은 흔한 일이지만 계속되면 고장입니다. 레벨 트리거 선을 아무도 달래지 않으면 인터럽트가 끝없이 다시 걸려 시스템이 멈춥니다. 코어는 이것을 셉니다. 인터럽트 10만 번 가운데 99,900번 넘게 주인이 없으면 irq N: nobody cared라는 메시지와 함께 그 IRQ를 꺼 버립니다(kernel/irq/spurious.c).

IRQ를 잠시 꺼 두는 함수는 중첩됩니다.

kernel/irq/manage.cv7.3
void __disable_irq(struct irq_desc *desc)
{
    if (!desc->depth++)
        irq_disable(desc);
}

depth가 0에서 1이 될 때만 실제로 끄고, enable_irq()는 1에서 0이 될 때만 켭니다. 서로 모르는 두 코드가 같은 IRQ를 껐다 켜도 먼저 켠 쪽이 나중 쪽의 구간을 깨뜨리지 않습니다. disable_irq()는 끈 뒤에 다른 CPU에서 실행 중인 핸들러가 끝나기를 기다립니다. 그래서 핸들러가 잡는 락을 쥔 채로 부르면 교착됩니다. 기다리지 않는 판이 disable_irq_nosync()입니다.

request_threaded_irq()는 핸들러를 둘 받습니다. 첫째는 지금까지처럼 hardirq 컨텍스트에서 불리고, IRQ_WAKE_THREAD를 돌려주면 둘째가 irq/9-acpi 같은 이름의 커널 스레드에서 불립니다. 스레드에서는 잠들 수 있고 뮤텍스를 쓸 수 있습니다. 레벨 트리거 인터럽트라면 스레드가 장치를 달랠 때까지 선을 막아 두어야 하는데, 이것을 요청하는 플래그가 IRQF_ONESHOT입니다. 스레드 IRQ와, 보통의 핸들러까지 스레드로 돌리는 강제 스레드화는 11장에서 다른 지연 처리 수단과 함께 다룹니다.

10.8어느 CPU가 받는가#

IRQ마다 친화성(affinity) 마스크가 있습니다. 이 인터럽트를 받아도 되는 CPU의 집합입니다.

터미널
# cat /proc/irq/142/smp_affinity_list
0-7
# cat /proc/irq/142/effective_affinity_list
3
# echo 2 > /proc/irq/142/smp_affinity_list

smp_affinity_list는 허용된 집합이고 effective_affinity_list는 그 가운데 실제로 받는 CPU입니다. x86의 벡터 도메인은 인터럽트를 한 번에 CPU 하나로만 보내므로 뒤의 것은 언제나 하나입니다. 파일에 쓰면 irq_chip의 irq_set_affinity()가 도메인 계층을 따라 불리고(칩에 따라서는 다음 인터럽트가 올 때까지 미뤄집니다), x86에서는 새 CPU에서 벡터를 하나 받아 그 CPU의 vector_irq[]에 디스크립터를 적은 뒤, MSI 메시지나 IO-APIC 항목의 목적지를 고쳐 씁니다. 옛 CPU의 벡터는 새 벡터로 첫 인터럽트가 온 것을 확인한 다음에 돌려줍니다. 그 사이에 옛 경로로 출발한 인터럽트를 잃지 않기 위해서입니다.

허용된 CPU가 여럿이면 벡터 할당기가 고릅니다.

kernel/irq/matrix.cv7.3
static unsigned int matrix_find_best_cpu(struct irq_matrix *m,
                    const struct cpumask *msk)
{
    unsigned int cpu, best_cpu, maxavl = 0;
    struct cpumap *cm;

    best_cpu = UINT_MAX;

    for_each_cpu(cpu, msk) {
        cm = per_cpu_ptr(m->maps, cpu);

        if (!cm->online || cm->available <= maxavl)
            continue;

        best_cpu = cpu;
        maxavl = cm->available;
    }
    return best_cpu;
}

기준은 "남은 벡터가 가장 많은 CPU"입니다. 부하가 아니라 벡터 수입니다. 실제 부하에 따라 인터럽트를 옮기는 일은 커널이 하지 않고, 유저 공간의 irqbalance 데몬이 /proc/interrupts를 읽고 smp_affinity에 써서 합니다. 9장에서 본 것처럼 하드웨어의 동적 분배 기능도 쓰지 않습니다. 인터럽트가 CPU 사이를 옮겨 다니면 핸들러가 쓰는 데이터의 캐시가 매번 식기 때문에, 한자리에 두고 필요할 때만 옮기는 쪽이 낫다는 판단입니다.

관리형 친화성

NVMe나 서버용 네트워크 카드는 CPU 수만큼 큐를 만들고 큐마다 MSI-X 벡터를 하나씩 둡니다. 이런 장치는 친화성을 유저 공간에 맡기지 않습니다. 드라이버가 pci_alloc_irq_vectors_affinity()로 벡터를 할당하면 코어가 큐들을 CPU에 고르게 펼치고 마스크를 고정합니다. 이것이 관리형 친화성(managed affinity)입니다.

관리형 IRQ는 /proc/irq/N/smp_affinity에 써도 바뀌지 않습니다. CPU가 꺼질 때의 동작도 다릅니다. 보통의 IRQ는 꺼지는 CPU에서 남은 CPU로 옮겨집니다(irq_migrate_all_off_this_cpu()). 관리형 IRQ는 마스크에 든 CPU가 모두 꺼지면 옮기지 않고 그대로 꺼 둡니다. 그 큐에 요청을 넣을 CPU가 없으니 인터럽트도 올 일이 없습니다.

이렇게 하는 까닭은 벡터 수입니다. 장치 벡터는 CPU당 200개 남짓입니다. 큐 128개짜리 장치가 둘이면 인터럽트가 256개입니다. CPU 128개에 펼쳐져 있을 때는 CPU마다 둘씩이라 문제가 없지만, 절전에 들어가며 CPU 하나만 남기고 모두 끄면 256개가 한 CPU로 몰려 벡터가 모자랍니다. 관리형은 옮기지 않으므로 이 문제가 생기지 않습니다. 같은 이유로 x86은 보통의 MSI 인터럽트에도 예약 모드를 씁니다. 장치가 벡터를 할당만 하고 request_irq()를 부르지 않은 동안에는 실제 벡터를 주지 않고, 전체 수량에서 하나를 빼 두기만 합니다(IRQD_CAN_RESERVE).

정리#

  • 인터럽트에는 번호가 셋 있습니다. 컨트롤러 안의 hwirq, 커널이 붙이는 리눅스 IRQ 번호, CPU가 보는 벡터입니다. irq_domain 계층이 이들을 잇습니다.
  • irq_desc는 IRQ 하나의 모든 것입니다. 하드웨어 조작은 irq_chip, 순서는 플로 핸들러, 장치별 처리는 irqaction 사슬이 맡습니다.
  • 상태 비트는 칩 드라이버도 읽는 IRQD_*와 코어만 쓰는 IRQS_*로 나뉘어 있고, 이름과 접근자와 정적 검사로 지켜집니다.
  • x86-64에서 벡터는 CPU별 vector_irq[]로 irq_desc가 되고, 플로 핸들러와 handle_irq_event()를 거쳐 드라이버의 핸들러에 닿습니다. 핸들러는 인터럽트가 꺼진 채로 실행됩니다.
  • 한 IRQ의 핸들러는 한 번에 한 CPU에서만 돕니다. 늦게 온 CPU는 IRQS_PENDING만 세우고 떠나고, 처리하던 CPU가 이어서 처리합니다. desc->lock은 핸들러를 부르는 동안 풀려 있습니다.
  • 공유 IRQ에서는 사슬의 핸들러가 모두 불리고, 각자 자기 장치인지 확인해 IRQ_NONE이나 IRQ_HANDLED를 돌려줍니다.
  • 어느 CPU가 받을지는 친화성 마스크와 벡터 할당기가 정합니다. 멀티큐 장치의 관리형 IRQ는 커널이 CPU에 펼치고 유저 공간은 바꿀 수 없습니다.

확인 문제#

/proc/interrupts에 16: ... IO-APIC 16-fasteoi ehci_hcd:usb1, i801_smbus라는 줄이 있습니다. 이 IRQ에 인터럽트가 한 번 오면 드라이버의 핸들러는 몇 개 불립니까? 커널은 어느 장치가 건 것인지 어떻게 압니까?

답 보기

둘 다 불립니다. 두 장치가 IO-APIC의 16번 핀을 나눠 쓰고 있고, irq_desc의 action 사슬에 irqaction이 둘 달려 있습니다. __handle_irq_event_percpu()는 사슬을 처음부터 끝까지 돌며 핸들러를 모두 부릅니다. 커널은 어느 장치인지 모릅니다. 각 핸들러가 자기 장치의 상태 레지스터를 읽어 보고, 자기 것이 아니면 IRQ_NONE을, 맞으면 처리한 뒤 IRQ_HANDLED를 돌려줍니다.

handle_irq_event()는 드라이버의 핸들러를 부르기 전에 desc->lock을 풉니다. 락을 쥔 채로 부르면 어떤 문제가 생깁니까? 락을 풀었는데도 핸들러가 두 CPU에서 동시에 실행되지 않는 까닭은 무엇입니까?

답 보기

락을 쥔 채로 부르면, 그 사이에 같은 IRQ를 받은 다른 CPU가 desc->lock을 얻으려고 핸들러가 끝날 때까지 인터럽트를 끈 채 헛돕니다. 핸들러 안에서 같은 디스크립터의 락이 필요한 함수(disable_irq_nosync() 등)를 부르면 교착됩니다. 락을 풀기 전에 IRQD_IRQ_INPROGRESS를 세워 두기 때문에 동시 실행은 일어나지 않습니다. 다른 CPU의 플로 핸들러는 락을 잡고 이 비트를 본 뒤 핸들러를 부르지 않고 IRQS_PENDING만 세우고 돌아갑니다.

에지 트리거 인터럽트에서, CPU 0이 핸들러를 실행하는 동안 CPU 1에 같은 IRQ가 도착했습니다. 이 두 번째 인터럽트는 결국 누가, 언제 처리합니까? handle_edge_irq()의 코드로 설명해 보세요.

답 보기

CPU 0이 처리합니다. CPU 1은 irq_can_handle()이 거짓이므로 desc->istate |= IRQS_PENDING을 하고 mask_ack_irq()로 마스크한 뒤 돌아갑니다. CPU 0은 handle_irq_event()에서 돌아와 while ((desc->istate & IRQS_PENDING) && ...) 조건을 보고 반복문을 다시 돕니다. 반복문 처음에서 마스크되어 있으면 unmask_irq()로 풀고, handle_irq_event()를 한 번 더 부릅니다. 이 함수가 IRQS_PENDING을 지우므로, 그 사이에 또 오지 않았다면 다음 조건 검사에서 빠져나갑니다.

레벨 트리거 선을 쓰는 장치의 드라이버가 핸들러에서 장치의 인터럽트 원인을 지우지 않고 IRQ_HANDLED를 돌려줍니다. 어떤 일이 생깁니까? IRQ_NONE을 돌려주었다면 무엇이 달라집니까?

답 보기

장치가 선을 내리지 않았으므로, handle_level_irq()가 마지막에 마스크를 푸는 순간 인터럽트가 다시 걸립니다. 핸들러가 끝없이 다시 불리고 그 CPU는 다른 일을 하지 못합니다. IRQ_HANDLED를 돌려주면 코어는 정상 처리로 보므로 막을 방법이 없습니다. IRQ_NONE을 돌려주었다면 코어의 가짜 인터럽트 감지가 셉니다. 10만 번 가운데 99,900번 넘게 주인이 없으면 "nobody cared"를 출력하고 그 IRQ를 꺼서 시스템이 멈추는 것을 막습니다. 다만 같은 선을 쓰는 다른 장치도 함께 인터럽트를 잃습니다.

CPU 64개짜리 서버에서 NVMe 장치의 큐 인터럽트는 /proc/irq/N/smp_affinity에 써도 바뀌지 않는데, 같은 서버의 직렬 포트 인터럽트는 바뀝니다. 왜 다릅니까? 그리고 CPU 하나를 오프라인으로 만들면 두 인터럽트는 각각 어떻게 됩니까?

답 보기

NVMe 큐 인터럽트는 관리형 친화성(IRQD_AFFINITY_MANAGED)입니다. 드라이버가 벡터를 할당할 때 커널이 큐들을 CPU에 펼쳐 마스크를 정했고, 큐와 CPU의 짝이 블록 계층의 큐 배치와 맞물려 있으므로 유저 공간이 바꾸지 못하게 합니다. 직렬 포트는 보통의 IRQ라서 바꿀 수 있습니다. CPU가 꺼지면 직렬 포트 인터럽트는 친화성 마스크에 남은 CPU로(없으면 켜져 있는 아무 CPU로) 옮겨지고 새 벡터를 받습니다. NVMe 큐 인터럽트는 마스크에 다른 CPU가 남아 있으면 그쪽으로 가고, 그 CPU가 마지막이었다면 옮기지 않고 꺼 둡니다. CPU가 다시 켜지면 되살립니다.

용어#

hwirq
인터럽트 컨트롤러 안에서의 인터럽트 번호. 핀 번호나 표의 인덱스.
irq_domain
컨트롤러 하나의 hwirq를 리눅스 IRQ 번호에 대응시키는 객체. 여러 겹으로 계층을 이룬다.
irq_desc
리눅스 IRQ 번호 하나에 대한 모든 정보를 담은 구조체.
irq_chip
인터럽트 컨트롤러를 조작하는 콜백 묶음. mask, unmask, ack, eoi, 친화성 설정 등.
플로 핸들러flow handler
신호 방식에 맞춰 칩 콜백과 드라이버 핸들러를 정해진 순서로 부르는 함수.
irqaction
드라이버가 등록한 핸들러 하나를 나타내는 구조체. 공유 IRQ에서는 사슬로 이어진다.
공유 IRQshared IRQ
여러 장치가 인터럽트 선 하나를 나눠 쓰는 것. IRQF_SHARED로 등록한다.
가짜 인터럽트spurious interrupt
어느 핸들러도 자기 것이라고 하지 않은 인터럽트.
친화성affinity
인터럽트를 받아도 되는 CPU의 집합. 실제로 받는 CPU는 유효 친화성이라고 한다.
관리형 친화성managed affinity
커널이 멀티큐 장치의 인터럽트를 CPU에 펼쳐 고정하는 방식. 유저 공간에서 바꿀 수 없다.
IRQ 스택IRQ stack
인터럽트 처리에 쓰는 CPU별 전용 스택.
