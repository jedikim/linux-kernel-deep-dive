시스템 콜

유저에서 커널로 들어오는 정문

Linux v7.3 기준약 55분
읽는 소스arch/x86/entry/entry_64.Sarch/x86/entry/syscall_64.cinclude/linux/entry-common.harch/x86/entry/syscalls/syscall_64.tblfs/read_write.carch/x86/include/asm/syscall_wrapper.hinclude/linux/uaccess.harch/x86/include/asm/uaccess_64.h

유저 프로그램은 혼자서는 파일 하나 열지 못합니다. 디스크도, 네트워크도, 다른 프로세스도 CPU가 유저 모드에서는 건드리지 못하게 막아 두었기 때문입니다. 무엇이든 하려면 커널에 부탁해야 하고, 그 부탁이 드나드는 문이 시스템 콜입니다. 이 문은 쉴 새 없이 열리므로 빨라야 하고, 문밖에서 오는 값은 하나도 믿을 수 없으므로 꼼꼼해야 하며, 한 번 내준 번호와 인자는 수십 년 뒤의 프로그램도 그대로 쓰므로 바꿀 수 없습니다. 세 요구가 진입 코드, 유저 메모리 접근 함수, 인터페이스 설계 규칙에 각각 어떻게 새겨져 있는지 봅니다.

이 장에서 답하는 질문
  • syscall 명령어 한 번에 CPU가 하는 일과 커널이 하는 일은 어디서 나뉘는가?
  • 시스템 콜 번호는 어디에 적혀 있고, v7.3에서는 어떻게 함수 호출로 바뀌는가?
  • SYSCALL_DEFINE3(read, ...) 한 줄은 어떤 함수들로 펼쳐지는가?
  • 커널은 유저가 준 포인터를 어떻게 읽고, 그 포인터가 엉터리면 어떻게 되는가?
  • clock_gettime()은 왜 커널에 들어오지 않고도 답을 얻는가?
  • 새 시스템 콜에 flags 인자와 구조체 크기를 넣으라고 하는 까닭은 무엇인가?

19.1경계를 넘는 방법#

x86 CPU에는 권한 수준이 있습니다. 유저 프로그램은 링 3에서, 커널은 링 0에서 돕니다. 링 3에서는 I/O 포트, 제어 레지스터, 인터럽트 설정을 건드리는 명령어가 예외를 일으키고, 페이지 테이블의 USER 비트가 꺼진 메모리에는 접근하지 못합니다(17장). 링 3의 코드가 링 0으로 넘어가는 길은 CPU가 정해 둔 몇 가지뿐이고, 어느 길이든 도착 지점은 커널이 미리 등록해 둔 주소입니다. 유저가 커널의 아무 주소로나 뛰어들 수는 없습니다.

시스템 콜(system call)은 그 길 가운데 프로그램이 스스로 부르는 것입니다. x86에는 역사적으로 세 가지 명령어가 있었습니다.

명령어 쓰이는 곳 방식
int $0x80 32비트 프로그램 소프트웨어 인터럽트. 가장 오래되고 가장 느립니다.
sysenter 32비트 프로그램 (Intel) 전용 MSR에 적어 둔 주소로 곧장 진입
syscall 64비트 프로그램 MSR LSTAR에 적어 둔 주소로 곧장 진입

64비트 프로그램이 쓰는 것은 syscall 하나입니다. 커널은 부팅할 때 wrmsrq(MSR_LSTAR, entry_SYSCALL_64)로 도착 주소를 CPU에 알려 둡니다. 호출 규약도 정해져 있습니다. 번호는 rax에, 인자는 순서대로 rdi, rsi, rdx, r10, r8, r9에 넣고, 결과는 rax로 받습니다. 인자는 최대 여섯 개입니다.

직접 확인하기

C 라이브러리의 래퍼를 거치지 않고 번호로 직접 부를 수 있습니다.

rawcall.cC
#define _GNU_SOURCE
#include <stdio.h>
#include <unistd.h>
#include <sys/syscall.h>

int main(void)
{
    long pid = syscall(SYS_getpid);

    printf("%ld %d\n", pid, getpid());
    return 0;
}

SYS_getpid는 x86-64에서 39입니다. strace ./rawcall로 보면 getpid()가 두 번 찍힙니다. getpid()라는 C 함수는 이 번호를 rax에 넣고 syscall 명령어를 실행하는 몇 줄짜리 래퍼입니다.

다른 아키텍처도 모양은 같습니다. arm64는 svc 명령어를 쓰고 번호를 x8에, 인자를 x0–x5에 넣습니다. 새 x86 CPU의 FRED는 syscall을 포함해 유저 모드에서 오는 모든 진입을 진입점 하나와 스택 프레임 형식 하나로 통일합니다(9장). FRED에서도 C 코드에 들어오면 아래에서 볼 do_syscall_64()로 합류합니다.

19.2entry_SYSCALL_64: 처음 서른 줄#

syscall 명령어가 하는 일은 놀랄 만큼 적습니다. 돌아갈 주소(rip)를 rcx에, 플래그를 r11에 복사하고, 권한을 링 0으로 올리고, LSTAR의 주소로 뜁니다. 스택은 바꾸지 않습니다. 메모리에 아무것도 저장하지 않습니다. 그래서 커널 코드의 첫 명령어는 유저의 스택 포인터를 쥔 채, 쓸 수 있는 레지스터가 하나도 없는 상태에서 시작합니다.

arch/x86/entry/entry_64.Sv7.3
SYM_CODE_START(entry_SYSCALL_64)
    UNWIND_HINT_ENTRY
    ENDBR

    swapgs
    /* tss.sp2 is scratch space. */
    movq    %rsp, PER_CPU_VAR(cpu_tss_rw + TSS_sp2)
    SWITCH_TO_KERNEL_CR3 scratch_reg=%rsp
    movq    PER_CPU_VAR(cpu_current_top_of_stack), %rsp

SYM_INNER_LABEL(entry_SYSCALL_64_safe_stack, SYM_L_GLOBAL)
    ANNOTATE_NOENDBR

    /* Construct struct pt_regs on stack */
    pushq   $__USER_DS              /* pt_regs->ss */
    pushq   PER_CPU_VAR(cpu_tss_rw + TSS_sp2)   /* pt_regs->sp */
    pushq   %r11                    /* pt_regs->flags */
    pushq   $__USER_CS              /* pt_regs->cs */
    pushq   %rcx                    /* pt_regs->ip */
SYM_INNER_LABEL(entry_SYSCALL_64_after_hwframe, SYM_L_GLOBAL)
    pushq   %rax                    /* pt_regs->orig_ax */

    PUSH_AND_CLEAR_REGS rax=$-ENOSYS

    /* IRQs are off. */
    movq    %rsp, %rdi
    /* Sign extend the lower 32bit as syscall numbers are treated as int */
    movslq  %eax, %rsi

    /* clobbers %rax, make sure it is after saving the syscall nr */
    IBRS_ENTER
    UNTRAIN_RET
    CLEAR_BRANCH_HISTORY

    call    do_syscall_64       /* returns with IRQs disabled */

순서대로 읽습니다.

  • swapgs. gs 세그먼트의 베이스를 유저 값에서 커널 값으로 바꿉니다. 커널의 gs는 이 CPU의 CPU별 데이터 영역을 가리킵니다. 이 한 줄이 있어야 다음 줄의 PER_CPU_VAR()가 동작합니다.
  • 스택 바꾸기. 유저의 rsp를 CPU별 임시 칸에 치워 두고, 현재 태스크의 커널 스택 꼭대기를 rsp에 넣습니다. 그 사이의 SWITCH_TO_KERNEL_CR3는 KPTI가 켜진 시스템에서 페이지 테이블을 커널용으로 바꿉니다.
  • pt_regs 쌓기. 유저의 레지스터를 전부 커널 스택에 밀어 넣습니다. 쌓인 모양이 struct pt_regs와 일치합니다. PUSH_AND_CLEAR_REGS는 저장한 뒤 레지스터를 0으로 지웁니다. 유저가 넣어 둔 값이 커널 코드의 추측 실행에 쓰이지 않게 하려는 것입니다.
  • 완화책. IBRS_ENTER, UNTRAIN_RET, CLEAR_BRANCH_HISTORY는 Spectre 계열 공격의 대응입니다. 유저 모드에서 학습시킨 분기 예측기 상태가 커널 안의 분기에 영향을 주지 못하게 합니다. CPU에 따라 아무 명령어도 아닌 것으로 바뀝니다.

pt_regs가 이 장의 중심에 있는 자료구조입니다. 시스템 콜의 인자는 regs->di, regs->si에 있고, 번호는 regs->orig_ax에 있으며, 반환값은 regs->ax에 써 두면 복귀할 때 rax로 되돌아갑니다. ptrace가 다른 프로세스의 레지스터를 읽고 고치는 것도, 시그널 핸들러에서 돌아온 뒤 원래 하던 일을 잇는 것도 모두 이 구조체를 통해서입니다.

19.3진입에서 복귀까지#

어셈블리가 부르는 C 함수는 짧습니다.

arch/x86/entry/syscall_64.cv7.3
__visible noinstr bool do_syscall_64(struct pt_regs *regs, long nr)
{
    if (likely(syscall_enter_from_user_mode_randomize_stack(regs, &nr))) {
        instrumentation_begin();

        if (!do_syscall_x64(regs, nr))
            do_syscall_x32(regs, nr);

        instrumentation_end();
    }
    syscall_exit_to_user_mode(regs);
    /* ... */
    /* SYSRET requires RCX == RIP and R11 == EFLAGS */
    if (unlikely(regs->cx != regs->ip || regs->r11 != regs->flags))
        return false;
    /* ... */
    /* Use SYSRET to exit to userspace */
    return true;
}

세 단계입니다. 진입 작업을 하고, 시스템 콜 함수를 부르고, 복귀 작업을 합니다. 진입과 복귀 작업은 x86만의 코드가 아니라 include/linux/entry-common.h와 kernel/entry/에 있는 공용 코드이고, 여러 아키텍처가 같이 씁니다.

진입 쪽 매크로 syscall_enter_from_user_mode_randomize_stack()은 이름대로 세 가지를 합니다. 커널에 들어왔음을 RCU와 컨텍스트 추적에 알리고, 커널 스택에 시스템 콜마다 달라지는 임의의 오프셋을 더하고(CONFIG_RANDOMIZE_KSTACK_OFFSET. 스택의 위치를 맞혀야 하는 공격을 어렵게 합니다), 인터럽트를 켠 뒤, 이 태스크에 걸려 있는 진입 작업이 있으면 처리합니다. 작업의 순서가 중요합니다.

include/linux/entry-common.hv7.3
static __always_inline long syscall_trace_enter(struct pt_regs *regs, unsigned long work,
                        long syscall)
{
    /* ... */
    /* Handle ptrace */
    if (work & (SYSCALL_WORK_SYSCALL_TRACE | SYSCALL_WORK_SYSCALL_EMU)) {
        if (!arch_ptrace_report_syscall_permit_entry(regs) ||
            (work & SYSCALL_WORK_SYSCALL_EMU))
            return false;

        /* ptrace might have changed work flags */
        work = READ_ONCE(current_thread_info()->syscall_work);
    }

    /* Do seccomp after ptrace, to catch any tracer changes. */
    if (work & SYSCALL_WORK_SECCOMP) {
        if (!__seccomp_permit_syscall())
            return false;
    }

    if (unlikely(work & SYSCALL_WORK_SYSCALL_TRACEPOINT))
        trace_syscall_enter(regs);
    /* ... */
    return true;
}

ptrace가 먼저, seccomp가 그다음입니다. 주석이 이유를 말합니다. 추적하는 쪽(디버거)은 멈춰 있는 태스크의 레지스터를 고쳐 시스템 콜 번호나 인자를 바꿀 수 있습니다. seccomp가 먼저 검사하면 허용된 호출로 통과한 뒤 금지된 호출로 바꿔치기할 수 있으므로, 검사는 바뀐 뒤의 값에 대해 해야 합니다. 대부분의 태스크는 syscall_work가 0이어서 이 함수 전체를 건너뜁니다.

복귀 쪽 syscall_exit_to_user_mode()는 감사와 추적점, ptrace의 종료 보고를 처리하고, 인터럽트를 끈 뒤, 유저 모드로 돌아가기 전의 마지막 점검을 합니다. 재스케줄 요청이 있으면 여기서 schedule()을 부르고, 대기 중인 시그널이 있으면 여기서 전달합니다. 6장에서 본 __exit_to_user_mode_loop()가 이 자리입니다.

마지막 반환값은 어셈블리에게 주는 답입니다. sysret 명령어는 rcx의 주소로, r11의 플래그로 돌아가는 빠른 복귀입니다. 그런데 시스템 콜 도중 pt_regs가 고쳐졌다면(시그널 핸들러로 가게 되었거나, ptrace가 레지스터를 바꿨거나, execve()로 새 프로그램이 되었거나) 그 조건이 깨집니다. 그때는 false를 돌려주고 어셈블리는 느리지만 무엇이든 복원할 수 있는 iret을 씁니다.

19.4번호에서 함수로#

번호와 함수의 짝은 텍스트 파일 하나에 적혀 있습니다.

arch/x86/entry/syscalls/syscall_64.tblv7.3
0   common  read            sys_read
1   common  write           sys_write
2   common  open            sys_open
3   common  close           sys_close

v7.3의 이 표에서 64비트 프로그램이 쓰는 줄은 0번 read부터 472번 fchroot까지 386개이고, 그 가운데 실제 함수가 연결된 것은 370개입니다. 나머지는 예전에 번호만 받고 구현이 사라진 자리입니다. 번호는 다시 쓰지 않습니다. 2번이 open이라는 사실은 정적으로 링크된 30년 전의 바이너리가 믿고 있는 약속이기 때문입니다.

빌드할 때 scripts/syscalltbl.sh가 이 표를 __SYSCALL(0, sys_read) 꼴의 줄이 나열된 헤더로 바꿉니다. 디스패치 코드는 그 헤더를 __SYSCALL의 정의를 바꿔 가며 세 번 포함합니다.

arch/x86/entry/syscall_64.cv7.3
#define __SYSCALL(nr, sym) case nr: return __x64_##sym(regs);

/* The unsigned int @nr argument is intentional as it creates denser code */
static noinline long x64_sys_call(const struct pt_regs *regs, unsigned int nr)
{
    switch (nr) {
    #include <asm/syscalls_64.h>
    default: return __x64_sys_ni_syscall(regs);
    }
}
/* ... */
static __always_inline bool do_syscall_x64(struct pt_regs *regs, unsigned long nr)
{
    if (likely(nr < NR_syscalls)) {
        nr = array_index_nospec(nr, NR_syscalls);
        regs->ax = x64_sys_call(regs, (unsigned int)nr);
        return true;
    }
    return false;
}

읽을 곳은 세 군데입니다.

  • 디스패치는 switch 문입니다. 헤더의 각 줄이 case 0: return __x64_sys_read(regs);로 펼쳐집니다. 함수 포인터 배열을 색인해 간접 호출하는 것이 아니라, 컴파일러가 만든 분기와 직접 호출입니다.
  • 없는 번호는 default로 가서 __x64_sys_ni_syscall()이 -ENOSYS를 돌려줍니다.
  • array_index_nospec()은 범위 검사 뒤에 한 번 더 번호를 눌러 줍니다. 까닭은 유저 메모리 절에서 봅니다.
예전 자료와 다른 점

거의 모든 자료가 시스템 콜 디스패치를 sys_call_table[nr](regs) 한 줄, 곧 함수 포인터 표의 간접 호출로 설명합니다. v7.3의 x86에서는 그렇지 않습니다. sys_call_table[]은 남아 있지만 위에 붙은 주석대로 "더 이상 시스템 콜에 쓰이지 않고" 추적 코드가 함수 주소를 알아내는 데만 씁니다. 2024년에 나온 6.9에서 바뀌었습니다. 유저가 고른 번호로 간접 분기를 하는 자리는 분기 예측기를 속이는 Spectre 계열 공격(BHI)의 좋은 표적이고, 간접 분기를 보호하는 완화책은 느립니다. switch로 바꾸면 컴파일러가 직접 호출을 만들 수 있습니다. 이 표를 덮어써서 시스템 콜을 가로채던 옛 루트킷과 일부 보안 모듈의 수법도 함께 통하지 않게 되었습니다. arm64는 v7.3에서도 sys_call_table[]을 array_index_nospec()과 함께 색인합니다.

아키텍처마다 표가 따로 있고 번호도 다릅니다. read는 x86-64에서 0번, arm64에서 63번입니다. 이 차이는 역사의 흔적입니다. 새로 생기는 아키텍처는 scripts/syscall.tbl 하나를 같이 쓰고, 모든 아키텍처에서 424번 이후의 새 시스템 콜은 같은 번호를 받습니다.

19.5SYSCALL_DEFINE가 펼쳐지는 모습#

표의 sys_read는 소스 어디에도 그 이름으로 정의되어 있지 않습니다. 시스템 콜의 본체는 매크로로 씁니다.

fs/read_write.cv7.3
SYSCALL_DEFINE3(read, unsigned int, fd, char __user *, buf, size_t, count)
{
    return ksys_read(fd, buf, count);
}

3은 인자의 수이고, 타입과 이름을 쉼표로 번갈아 적습니다. x86에서 이 매크로는 함수 셋을 만듭니다.

arch/x86/include/asm/syscall_wrapper.hv7.3
#define __SYSCALL_DEFINEx(x, name, ...)                 \
    static long __se_sys##name(__MAP(x,__SC_LONG,__VA_ARGS__)); \
    static inline long __do_sys##name(__MAP(x,__SC_DECL,__VA_ARGS__));\
    __X64_SYS_STUBx(x, name, __VA_ARGS__)               \
    __IA32_SYS_STUBx(x, name, __VA_ARGS__)              \
    static long __se_sys##name(__MAP(x,__SC_LONG,__VA_ARGS__))  \
    {                               \
        long ret = __do_sys##name(__MAP(x,__SC_CAST,__VA_ARGS__));\
        __MAP(x,__SC_TEST,__VA_ARGS__);             \
        __PROTECT(x, ret,__MAP(x,__SC_ARGS,__VA_ARGS__));   \
        return ret;                     \
    }                               \
    static inline long __do_sys##name(__MAP(x,__SC_DECL,__VA_ARGS__))
  • __x64_sys_read(const struct pt_regs *regs). switch가 부르는 함수입니다. regs->di, regs->si, regs->dx를 꺼내 다음 함수에 넘깁니다. 인자가 셋인 시스템 콜은 레지스터 셋만 읽습니다. 유저가 r10, r8, r9에 넣어 둔 값은 본체에 닿지 않습니다.
  • __se_sys_read(long, long, long). 인자를 모두 long으로 받아 선언된 타입으로 변환합니다. 32비트 값의 윗비트에 쓰레기가 남아 있어도 여기서 잘립니다. __SC_TEST는 long보다 큰 타입을 인자로 쓰면 빌드가 깨지게 합니다.
  • __do_sys_read(unsigned int fd, char __user *buf, size_t count). 중괄호 안의 본문입니다. inline이므로 실제로는 위 함수에 합쳐집니다.

매크로는 SYSCALL_METADATA도 만듭니다. 인자의 이름과 타입을 문자열로 담은 표이고, 추적점 syscalls:sys_enter_read가 fd, buf, count를 이름 붙여 보여 줄 수 있는 것이 이 덕분입니다.

설계 노트

시스템 콜이 370개이면 "레지스터에서 인자를 꺼내 타입을 맞추고 추적 정보를 등록하는" 코드도 370번 필요합니다. 손으로 쓰면 그 가운데 몇 개는 틀립니다. 2009년에는 일부 64비트 아키텍처에서 32비트 인자의 부호 확장이 빠져 있던 것이 보안 문제(CVE-2009-0029)로 드러났고, 인자를 감싸는 래퍼를 매크로로 만들어 내는 방식이 그 대응으로 들어왔습니다. 매크로로 생성하면 규칙이 한곳에 있고, 규칙을 바꿀 때도 한곳만 고칩니다. 2018년에 x86이 "인자를 레지스터로 직접 받는" 방식에서 "pt_regs 포인터 하나만 받는" 방식으로 바꿨을 때, 수백 개의 시스템 콜 본체는 한 줄도 고치지 않았습니다. 반복되는 경계 코드를 생성하고 검사를 생성기에 넣는 것은 커널 밖에서도 통하는 방법입니다. 대가는 grep sys_read로 정의를 찾을 수 없다는 것입니다. SYSCALL_DEFINE.*read로 찾아야 합니다.

19.6유저 메모리 접근#

read()의 둘째 인자 buf는 유저가 준 주소입니다. 커널은 그 값을 믿을 수 없습니다. 매핑되지 않은 주소일 수도 있고, 커널 영역의 주소를 넣어 커널이 제 손으로 자기 메모리를 덮어쓰게 하려는 것일 수도 있습니다. 그래서 타입에 __user가 붙은 포인터는 직접 역참조하지 않고 정해진 함수로만 다룹니다. __user는 평소에는 아무 뜻이 없고, 정적 검사 도구 sparse로 빌드할 때 "다른 주소 공간의 포인터"로 취급되어 직접 역참조하는 코드를 잡아냅니다.

include/linux/uaccess.hv7.3
static inline __must_check unsigned long
_inline_copy_from_user(void *to, const void __user *from, unsigned long n)
{
    unsigned long res = n;
    might_fault();
    if (should_fail_usercopy())
        goto fail;
    if (can_do_masked_user_access())
        from = mask_user_address(from);
    else {
        if (!access_ok(from, n))
            goto fail;
        /* ... */
        barrier_nospec();
    }
    instrument_copy_from_user_before(to, from, n);
    res = raw_copy_from_user(to, from, n);
    instrument_copy_from_user_after(to, from, n, res);
    if (likely(!res))
        return 0;
fail:
    memset(to + (n - res), 0, res);
    return res;
}

copy_from_user()의 본체입니다. 세 가지를 합니다.

주소가 유저 영역인지 확인합니다. 고전적인 방법은 access_ok()로 from + n이 유저 주소의 상한을 넘지 않는지 비교하는 것입니다. x86-64는 그 대신 mask_user_address()를 씁니다. 비교하고 분기하는 대신, 주소가 상한보다 크면 조건부 이동 명령어로 상한값으로 바꿔 버립니다. 분기가 없으므로 CPU가 잘못 추측해 커널 주소를 읽는 일이 없고, 바뀐 주소는 매핑되지 않은 자리라 폴트로 끝납니다.

복사합니다. raw_copy_from_user()는 x86-64에서 이렇게 생겼습니다.

arch/x86/include/asm/uaccess_64.hv7.3
static __always_inline __must_check unsigned long
copy_user_generic(void *to, const void *from, unsigned long len)
{
    stac();
    /* ... */
    asm volatile(
        "1:\n\t"
        ALTERNATIVE("rep movsb",
                "call rep_movs_alternative", ALT_NOT(X86_FEATURE_FSRM))
        "2:\n"
        _ASM_EXTABLE_UA(1b, 2b)
        :"+c" (len), "+D" (to), "+S" (from), ASM_CALL_CONSTRAINT
        : : "memory", "rax");
    clac();
    return len;
}

복사 자체는 rep movsb 한 줄입니다. 그 앞뒤의 stac()과 clac()은 SMAP을 잠깐 풉니다. SMAP은 커널 모드에서 유저 페이지에 접근하면 폴트를 내는 CPU 기능입니다. 커널이 버그로 유저 포인터를 역참조하는 사고를 하드웨어가 막아 줍니다. 정말로 유저 메모리를 읽어야 하는 이 몇 줄에서만 플래그 하나(AC)를 세워 허용합니다. 짝이 되는 SMEP은 커널 모드에서 유저 페이지의 코드를 실행하지 못하게 합니다.

폴트에 대비합니다. 주소가 유저 영역이어도 매핑되어 있지 않을 수 있습니다. _ASM_EXTABLE_UA(1b, 2b)가 그 대비입니다. "1번 레이블의 명령어에서 폴트가 나면 2번 레이블로 가라"는 한 쌍을 예외 테이블이라는 별도의 섹션에 적어 둡니다.

rep movsb가 폴트를 내면 17장의 페이지 폴트 핸들러가 돕니다. 주소가 VMA 안이면 평소처럼 페이지를 채우고 같은 명령어를 다시 실행합니다. 복사하는 코드는 폴트가 났는지도 모릅니다. VMA 밖이면 커널 코드에 시그널을 보낼 수는 없으므로 fixup_exception()이 예외 테이블에서 폴트 난 명령어의 주소를 찾고, regs->ip를 짝지어진 주소로 바꿉니다. 실행은 2:에서 이어지고, rcx에는 못 다 복사한 바이트 수가 남아 있습니다. 그것이 반환값이 되고, 호출한 쪽은 0이 아니면 -EFAULT를 돌려줍니다. 정상 경로에는 검사 명령어가 하나도 없고, 비용은 드물게 일어나는 실패 쪽이 다 집니다.

주의

유저 메모리는 복사한 뒤에만 믿을 수 있습니다. 유저의 구조체에서 길이 필드를 get_user()로 읽어 검사한 다음 같은 구조체를 다시 copy_from_user()로 읽으면, 그 사이에 다른 스레드가 길이를 바꿔 놓을 수 있습니다. 검사한 값과 쓰는 값이 달라지는 이중 읽기(double fetch) 버그입니다. 한 번에 커널 버퍼로 복사하고, 검사도 사용도 그 사본으로 합니다.

추측 실행은 범위 검사도 믿지 못하게 만들었습니다. if (nr < NR_syscalls)를 통과하지 못한 값이라도 CPU가 분기를 잘못 예측하면 그 뒤의 코드가 잠깐 실행되고, 흔적이 캐시에 남습니다(Spectre v1). array_index_nospec(nr, NR_syscalls)는 nr이 범위 밖이면 분기 없이 0으로 만드는 마스크 연산입니다. 유저가 준 값으로 배열을 색인하는 곳마다 범위 검사 뒤에 이것이 붙습니다.

19.7반환값과 재시작#

시스템 콜 함수는 long 하나를 돌려줍니다. 0 이상이면 성공이고, −1에서 −4095(MAX_ERRNO) 사이면 오류 번호의 부호를 바꾼 것입니다. C 라이브러리의 래퍼가 이 범위의 값을 보면 부호를 뒤집어 errno에 넣고 −1을 돌려줍니다. errno는 커널이 아니라 C 라이브러리가 만든 변수입니다.

유저에게 보이지 않는 오류 번호도 있습니다. read()가 데이터를 기다리며 잠든 사이에 시그널이 오면, 태스크는 깨어나 -ERESTARTSYS(512)를 들고 시스템 콜에서 빠져나옵니다(3장). 이 값은 유저 모드에 닿기 전에 처리됩니다.

arch/x86/kernel/signal.cv7.3
static void
handle_signal(struct ksignal *ksig, struct pt_regs *regs)
{
    /* ... */
    /* Are we from a system call? */
    if (syscall_get_nr(current, regs) != -1) {
        /* If so, check system call restarting.. */
        switch (syscall_get_error(current, regs)) {
        case -ERESTART_RESTARTBLOCK:
        case -ERESTARTNOHAND:
            regs->ax = -EINTR;
            break;

        case -ERESTARTSYS:
            if (!(ksig->ka.sa.sa_flags & SA_RESTART)) {
                regs->ax = -EINTR;
                break;
            }
            fallthrough;
        case -ERESTARTNOINTR:
            regs->ax = regs->orig_ax;
            regs->ip -= 2;
            break;
        }
    }
    /* ... */
}

시그널 핸들러를 SA_RESTART 없이 등록했다면 유저는 EINTR을 봅니다. SA_RESTART가 있으면 두 줄이 시스템 콜을 다시 걸어 둡니다. regs->ax에 원래 번호(orig_ax)를 되돌려 넣고, regs->ip를 2 줄입니다. syscall 명령어의 길이가 2바이트이므로, 핸들러가 끝나고 돌아가면 프로그램은 같은 syscall 명령어를 한 번 더 실행합니다. pt_regs에 orig_ax가 따로 있는 까닭이 이것입니다. ax는 반환값으로 덮였기 때문입니다.

19.8커널에 들어오지 않는 시스템 콜: vDSO#

시스템 콜은 보통의 함수 호출보다 훨씬 비쌉니다. 모드 전환, 레지스터 저장과 복원에 더해, KPTI가 켜져 있으면 CR3를 두 번 바꾸고, 진입할 때마다 분기 예측기를 다독이는 완화책이 돕니다. 로그 한 줄마다 시각을 찍는 프로그램에게 clock_gettime()의 이 비용은 큽니다.

vDSO(virtual dynamic shared object)는 커널이 모든 프로세스의 주소 공간에 매핑해 주는 작은 공유 라이브러리입니다. 코드는 커널 소스에서 빌드되지만 유저 모드에서 실행됩니다. 커널은 그 옆에 읽기 전용 데이터 페이지를 매핑하고, 틱마다 현재 시각을 계산하는 데 필요한 값을 거기에 갱신합니다(8장).

lib/vdso/gettimeofday.cv7.3
static __always_inline
bool do_hres(const struct vdso_time_data *vd, const struct vdso_clock *vc,
         clockid_t clk, struct __kernel_timespec *ts)
{
    u64 sec, ns;
    u32 seq;
    /* ... */
    do {
        if (vdso_read_begin_timens(vc, &seq))
            return do_hres_timens(vd, vc, clk, ts);

        if (!vdso_get_timestamp(vd, vc, clk, &sec, &ns))
            return false;
    } while (vdso_read_retry(vc, seq));

    vdso_set_timespec(ts, sec, ns);

    return true;
}

락이 없습니다. 커널이 데이터를 고치는 동안 순번을 홀수로 만들어 두므로, 읽는 쪽은 순번을 읽고, 값을 읽고, 순번이 그대로인지 확인해 달라졌으면 다시 읽습니다. 14장의 seqlock과 같은 방법입니다. vdso_get_timestamp()는 CPU의 타임스탬프 카운터를 유저 모드에서 직접 읽어 마지막 갱신 이후 흐른 시간을 더합니다. vDSO가 처리할 수 없는 경우(시계 종류를 지원하지 않거나 클럭 소스를 유저 모드에서 읽을 수 없을 때)에는 false가 돌아오고 진짜 시스템 콜로 넘어갑니다.

v7.3의 x86-64 vDSO가 내보내는 것은 clock_gettime, gettimeofday, time, clock_getres, getcpu, getrandom 등입니다. getrandom은 6.11에 들어왔습니다. 난수 생성기의 상태를 프로세스 쪽 메모리에 두되, 커널이 그 메모리를 fork()나 메모리 압박 때 지워 버릴 수 있게 표시해 두는 방식입니다.

직접 확인하기

vDSO가 어디에 매핑되어 있는지, 시각을 읽는 호출이 정말 시스템 콜을 건너뛰는지 확인합니다.

터미널
$ grep -E 'vdso|vvar' /proc/self/maps
7ffc3a5f2000-7ffc3a5f6000 r--p 00000000 00:00 0   [vvar]
7ffc3a5f6000-7ffc3a5f8000 r-xp 00000000 00:00 0   [vdso]

$ strace -c date > /dev/null
% time     seconds  usecs/call     calls    errors syscall
...

strace -c의 표에 clock_gettime은 나오지 않습니다. date는 시각을 읽었지만 커널에 들어오지 않았기 때문입니다. 시스템 전체에서 누가 시스템 콜을 많이 부르는지는 추적점으로 셉니다.

터미널
# bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }'
# perf trace -s sleep 1

vDSO로 옮길 수 없는 시스템 콜의 비용은 횟수를 줄여서 낮춥니다. readv()·sendmmsg()처럼 여러 건을 한 번에 넘기는 호출이 그렇고, 요청과 완료를 공유 메모리의 링에 쌓아 두고 한 번의 진입으로 처리하는 io_uring이 그 끝에 있습니다(21장).

19.9문 앞의 검문소: seccomp와 ptrace#

진입 작업의 두 손님을 조금 더 봅니다.

seccomp는 프로세스가 스스로에게 거는 시스템 콜 필터입니다. 필터는 작은 BPF 프로그램이고, 입력은 시스템 콜 번호, 아키텍처, 명령어 주소, 인자 여섯 개를 담은 struct seccomp_data입니다. 포인터 인자는 값만 볼 수 있고 가리키는 내용은 읽지 못합니다. 필터의 반환값이 처분을 정합니다.

반환값 처분
SECCOMP_RET_ALLOW 통과
SECCOMP_RET_ERRNO 시스템 콜을 실행하지 않고 지정한 오류를 돌려줌
SECCOMP_RET_TRAP SIGSYS를 보냄
SECCOMP_RET_USER_NOTIF 태스크를 멈추고 감독 프로세스에 알림. 감독 쪽이 대신 처리하고 결과를 정함
SECCOMP_RET_KILL_PROCESS 프로세스를 죽임

한 번 건 필터는 풀 수 없고 fork()와 execve()를 넘어 이어집니다. 컨테이너 런타임, 브라우저의 렌더러 프로세스, systemd의 서비스 격리가 이것으로 "이 프로세스가 부를 수 있는 시스템 콜"의 목록을 좁힙니다. 커널의 공격 표면은 시스템 콜 전체이므로, 쓰지 않는 문을 닫아 두는 것입니다.

ptrace는 한 프로세스가 다른 프로세스를 멈추고 들여다보는 장치입니다. strace는 대상에 PTRACE_SYSCALL을 걸어 둡니다. 그러면 대상의 syscall_work에 SYSCALL_WORK_SYSCALL_TRACE가 서고, 대상은 시스템 콜에 들어올 때와 나갈 때마다 멈춰 strace를 깨웁니다. strace는 대상의 pt_regs를 읽어 번호와 인자를 출력하고 대상을 다시 보냅니다. 시스템 콜 한 번에 컨텍스트 스위치가 네 번 끼어드는 셈이라, strace를 붙인 프로그램은 눈에 띄게 느려집니다. 운영 중인 시스템에서는 추적점이나 perf trace가 낫습니다.

19.10새 시스템 콜을 설계하는 법#

시스템 콜은 한 번 릴리스에 들어가면 영원히 지원해야 합니다. 번호만이 아니라 인자의 뜻, 구조체의 배치, 오류 번호까지입니다(26장). 고칠 수 없다면 처음부터 늘릴 자리를 마련해 두어야 합니다. Documentation/process/adding-syscalls.rst는 지난 실수에서 얻은 규칙을 적어 둔 문서입니다. 문서는 dup2/dup3, pipe/pipe2, renameat/renameat2를 "그렇게 하지 않아서 뒤따라 생긴 시스템 콜"의 예로 듭니다.

flags 인자를 두고, 모르는 비트는 거절한다. v7.3에서 가장 번호가 큰 시스템 콜이 본보기입니다.

fs/open.cv7.3
SYSCALL_DEFINE2(fchroot, int, fd, unsigned int, flags)
{
    struct path path;
    int error;

    if (flags)
        return -EINVAL;
    /* ... */
}

지금은 쓰는 플래그가 하나도 없는데도 인자를 두고, 0이 아니면 -EINVAL입니다. 거절이 핵심입니다. 모르는 비트를 조용히 무시하면, 프로그램들이 쓰레기 값을 넣은 채로 굳어져 나중에 그 비트에 뜻을 줄 수 없게 됩니다. open()의 플래그가 이 실수를 했습니다.

인자가 많으면 크기를 실은 구조체로 받는다. 구조체에 필드를 덧붙일 수 있게, 유저가 자기가 아는 구조체의 크기를 함께 넘깁니다.

include/linux/uaccess.hv7.3
static __always_inline __must_check int
copy_struct_from_user(void *dst, size_t ksize, const void __user *src,
              size_t usize)
{
    size_t size = min(ksize, usize);
    size_t rest = max(ksize, usize) - size;
    /* ... */
    /* Deal with trailing bytes. */
    if (usize < ksize) {
        memset(dst + size, 0, rest);
    } else if (usize > ksize) {
        int ret = check_zeroed_user(src + size, rest);
        if (ret <= 0)
            return ret ?: -E2BIG;
    }
    /* Copy the interoperable parts of the struct. */
    if (copy_from_user(dst, src, size))
        return -EFAULT;
    return 0;
}

옛 프로그램이 새 커널을 부르면(usize < ksize) 모자란 뒷부분을 0으로 채웁니다. 새 필드는 0이 "예전과 같은 동작"을 뜻하도록 설계합니다. 새 프로그램이 옛 커널을 부르면(usize > ksize) 커널이 모르는 뒷부분이 전부 0인지 확인하고, 아니면 -E2BIG입니다. 어느 방향으로 버전이 어긋나도 동작합니다. clone3()와 openat2()가 이 함수로 인자를 받습니다.

커널 객체는 파일 디스크립터로 가리킨다. 새 종류의 핸들을 만들지 않습니다. fd는 poll()로 기다릴 수 있고, 다른 프로세스에 넘길 수 있고, 닫으면 정리된다는 의미가 이미 정해져 있습니다. PID 대신 pidfd를 쓰는 최근의 API가 이 규칙을 따른 것입니다. fd를 새로 돌려준다면 O_CLOEXEC에 해당하는 플래그도 함께 받습니다.

경로를 받는다면 *at() 꼴로 만든다. 기준 디렉터리의 fd를 함께 받으면 "현재 디렉터리"라는 프로세스 전역 상태에 기대지 않아도 됩니다.

open()의 역사가 이 규칙들의 요약입니다. open(path, flags, mode)은 기준 디렉터리를 정할 수 없어 2.6.16에 openat(dfd, path, flags, mode)가 생겼습니다. openat()은 모르는 플래그를 거절하지 않고 인자를 더 붙일 자리도 없어, 경로 해석을 제한하는 옵션(RESOLVE_BENEATH 등)을 넣으려 했을 때 또 새 번호가 필요했습니다. 5.6의 openat2(dfd, path, how, size)는 구조체 open_how와 그 크기를 받고, 모르는 플래그를 거절합니다. 세 번호 모두 v7.3의 표에 살아 있습니다(2, 257, 437).

설계 노트

이 규칙들은 "내보낸 인터페이스는 못 바꾼다"는 전제 하나에서 나옵니다. 못 바꾼다면 두 가지를 처음부터 넣어야 합니다. 하나는 늘릴 자리(쓰지 않는 플래그 비트, 크기가 실린 구조체)이고, 다른 하나는 엄격한 거절(모르는 입력은 오류)입니다. 뒤쪽이 덜 직관적이지만 더 중요합니다. 관대한 인터페이스는 잘못된 입력에 의존하는 사용자를 만들고, 그 사용자가 생기는 순간 그 잘못된 입력도 지켜야 할 약속이 됩니다. 네트워크 프로토콜, 파일 형식, 라이브러리 API처럼 양쪽을 동시에 고칠 수 없는 모든 경계에 같은 규칙이 통합니다.

정리#

  • 64비트 x86의 시스템 콜은 syscall 명령어로 들어옵니다. CPU는 rip와 플래그를 레지스터에 옮기고 뛸 뿐이고, 스택 전환과 레지스터 저장은 entry_SYSCALL_64가 합니다.
  • 유저의 레지스터는 커널 스택에 struct pt_regs로 쌓입니다. 인자 읽기, 반환값 쓰기, ptrace, 재시작이 모두 이 구조체를 통합니다.
  • do_syscall_64()는 공용 진입 작업(ptrace, seccomp, 추적), 디스패치, 공용 복귀 작업(스케줄, 시그널)의 세 단계입니다.
  • v7.3의 x86은 번호를 switch 문으로 함수에 연결합니다. 표는 syscall_64.tbl이고 번호는 다시 쓰지 않습니다.
  • SYSCALL_DEFINEn은 pt_regs에서 인자를 꺼내는 함수, 타입을 맞추는 함수, 본체를 만들어 냅니다.
  • 유저 메모리는 copy_from_user() 계열로만 읽습니다. 주소를 유저 영역으로 누르고, SMAP을 잠깐 풀고, 폴트는 예외 테이블로 복구합니다.
  • vDSO는 일부 시스템 콜을 유저 모드에서 끝냅니다.
  • 새 시스템 콜에는 flags와 크기가 실린 구조체를 넣고 모르는 입력은 거절합니다. 한 번 내보내면 바꿀 수 없기 때문입니다.

확인 문제#

entry_SYSCALL_64의 첫 명령어가 swapgs여야 하는 까닭은 무엇입니까? 이 명령어 전에 커널이 할 수 없는 일은 무엇입니까?

답 보기

syscall 명령어는 스택도 바꾸지 않고 레지스터도 저장하지 않으므로, 진입 직후에는 유저의 rsp를 쥐고 있고 자유롭게 쓸 레지스터가 없습니다. 커널 스택의 위치는 CPU별 변수에 있고, CPU별 변수는 gs 베이스를 기준으로 접근합니다. swapgs로 gs를 커널 값으로 바꾸기 전에는 CPU별 데이터에 접근할 수 없으므로, 유저의 rsp를 치워 둘 곳도 커널 스택 주소를 읽을 곳도 없습니다.

x86-64에서 존재하지 않는 번호 9999로 syscall을 부르면 -ENOSYS가 돌아옵니다. v7.3의 코드에서 이 값이 만들어질 수 있는 자리 두 곳을 찾아보세요.

답 보기

첫째, 어셈블리 진입 코드의 PUSH_AND_CLEAR_REGS rax=$-ENOSYS가 pt_regs->ax를 미리 -ENOSYS로 채워 둡니다. do_syscall_x64()는 nr < NR_syscalls가 거짓이면 아무것도 하지 않으므로(x32 범위에도 들지 않으면) 이 값이 그대로 유저에게 돌아갑니다. 9999가 이 경우입니다. 둘째, 번호가 범위 안이지만 표에 함수가 없는 경우에는 x64_sys_call()의 default가 __x64_sys_ni_syscall()을 불러 -ENOSYS를 돌려줍니다.

인자가 둘인 시스템 콜을 부르면서 rdx, r10에 임의의 값을 넣어 두었습니다. 이 값은 시스템 콜 본체(__do_sys_*)에 전달됩니까? 어느 코드가 그것을 정합니까?

답 보기

전달되지 않습니다. SYSCALL_DEFINE2가 만든 __x64_sys_*() 스텁은 SC_X86_64_REGS_TO_ARGS로 regs->di와 regs->si만 꺼내 __se_sys_*()에 넘깁니다. 나머지 레지스터 값은 pt_regs에 저장되어 있을 뿐 어떤 함수의 인자로도 쓰이지 않습니다. 게다가 진입 코드의 PUSH_AND_CLEAR_REGS가 실제 레지스터를 0으로 지웠으므로, 추측 실행으로도 그 값이 커널 코드에 흘러들지 않습니다.

copy_from_user(kbuf, ubuf, 4096)에서 ubuf의 앞 100바이트만 매핑되어 있고 그 뒤는 어떤 VMA에도 속하지 않습니다. 반환값은 얼마이고, kbuf의 내용은 어떻게 됩니까?

답 보기

100바이트를 복사한 뒤 rep movsb가 폴트를 냅니다. 주소가 VMA 밖이므로 페이지 폴트 핸들러는 fixup_exception()으로 가고, 예외 테이블이 가리키는 2: 레이블에서 실행이 이어집니다. rcx에 남은 3996이 반환값입니다. _inline_copy_from_user()는 res가 0이 아니므로 memset(to + (n - res), 0, res)로 kbuf의 나머지 3996바이트를 0으로 채웁니다. 커널 스택이나 힙에 있던 이전 내용이 유저에게 새어 나가지 않게 하려는 것입니다. 호출한 쪽은 보통 반환값이 0이 아니면 -EFAULT를 돌려줍니다.

openat2()를 아는 새 프로그램이 open_how에 커널이 모르는 새 필드를 채워 옛 커널을 불렀습니다. 커널은 어떻게 반응하고, 이 동작이 "조용히 무시"보다 나은 까닭은 무엇입니까?

답 보기

usize > ksize이므로 copy_struct_from_user()가 check_zeroed_user()로 커널이 모르는 뒷부분을 검사하고, 0이 아닌 바이트가 있으므로 -E2BIG를 돌려줍니다. 프로그램은 이 커널이 그 기능을 지원하지 않는다는 것을 알고 다른 방법을 쓸 수 있습니다. 조용히 무시했다면 프로그램은 요청이 받아들여졌다고 믿습니다. 그 필드가 "이 디렉터리 밖으로 나가지 마라" 같은 보안 제약이었다면, 제약 없이 파일이 열리는 사고가 됩니다.

용어#

시스템 콜system call
유저 프로그램이 커널에 일을 요청하는 진입 수단. 번호로 구분한다.
pt_regs
커널 진입 시점의 유저 레지스터를 커널 스택에 저장한 구조체.
swapgs
gs 세그먼트 베이스를 유저 값과 커널 값 사이에서 맞바꾸는 x86-64 명령어.
진입 작업 / 복귀 작업entry / exit work
시스템 콜 본체 앞뒤에서 공용 코드가 처리하는 일. ptrace, seccomp, 추적, 스케줄, 시그널 전달.
SYSCALL_DEFINEn
시스템 콜 본체와 그 래퍼, 추적용 메타데이터를 함께 만들어 내는 매크로.
__user
유저 공간 주소임을 표시하는 포인터 주석. sparse가 직접 역참조를 잡아낸다.
SMAP
커널 모드에서 유저 페이지에 접근하면 폴트를 내는 CPU 기능. stac/clac으로 잠깐 푼다.
예외 테이블exception table
폴트가 나도 되는 커널 명령어의 주소와, 폴트 시 이어서 실행할 주소의 쌍을 모아 둔 표.
vDSO
커널이 모든 프로세스에 매핑하는 작은 공유 라이브러리. 일부 시스템 콜을 유저 모드에서 처리한다.
seccomp
프로세스가 스스로에게 거는 시스템 콜 필터. BPF 프로그램으로 쓴다.
-ERESTARTSYS
시그널로 끊긴 시스템 콜을 다시 걸 수 있음을 뜻하는 커널 내부 오류 번호. 유저에게는 보이지 않는다.
