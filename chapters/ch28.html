28.1준비: 리눅스 머신과 소스#

커널은 리눅스에서 빌드합니다. macOS나 Windows를 쓴다면 리눅스 가상 머신을 하나 만들어 그 안에서 작업합니다. 이유 하나는 소스 트리 자체에 있습니다. v7.3 트리에는 xt_CONNMARK.h와 xt_connmark.h처럼 대소문자만 다른 경로가 13쌍 있어서, 대소문자를 구분하지 않는 파일시스템에는 온전히 받을 수 없습니다.

필요한 도구는 컴파일러와 몇 가지 유틸리티입니다. 커널 문서에 배포판별 설치 명령이 있습니다.

Documentation/admin-guide/quickly-build-trimmed-linux.rstv7.3
     sudo apt install bc binutils bison dwarves flex gcc git make openssl \
       pahole perl-base libssl-dev libelf-dev

각 도구의 최소 버전은 Documentation/process/changes.rst의 표에 있습니다. v7.3의 주요 항목입니다.

Documentation/process/changes.rstv7.3
Clang/LLVM (optional)  17.0.1           clang --version
[...]
GNU C                  8.1              gcc --version
GNU make               4.0              make --version
[...]
pahole                 1.26             pahole --version
[...]
Python                 3.9.x            python3 --version
[...]
Rust (optional)        1.85.0           rustc --version

pahole은 BPF가 쓰는 타입 정보(BTF)를 만들 때(24장), Rust는 CONFIG_RUST를 켤 때만 필요합니다.

소스는 git으로 받습니다.

터미널
$ git clone --depth 1 --branch v7.3 \
    https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git
$ cd linux

--depth 1은 v7.3 한 시점만 받으므로 빠릅니다. 대신 역사가 없어서 git log와 git blame을 쓸 수 없습니다. 뒤의 소스 고고학과 첫 패치를 하려면 --depth 없이 전체를 받습니다. 소스 트리의 구조는 0장에 있습니다.

28.2설정: .config 만들기#

커널의 빌드 설정은 최상위의 .config 파일 하나입니다. CONFIG_PREEMPT_LAZY=y 같은 줄이 수천 개 들어 있고, 각 줄은 Kconfig 심벌 하나의 값입니다(25장). 이 파일을 손으로 쓰지는 않습니다. 출발점을 하나 고르고 필요한 것을 더합니다.

명령 만드는 것
make defconfig 아키텍처의 기본 설정. x86-64에서는 arch/x86/configs/x86_64_defconfig
make localmodconfig 지금 쓰는 설정에서, 현재 로드되어 있지 않은 모듈을 끈 것
make menuconfig 메뉴 화면에서 고르기. /로 심벌을 검색
make olddefconfig 지금의 .config를 현재 소스에 맞춤. 새 심벌은 기본값으로
scripts/config 명령줄에서 심벌 하나를 켜고 끄기

가상 머신에서 부팅할 커널이라면 defconfig에 설정 조각(config fragment)을 더하는 방법이 가장 짧습니다.

터미널
$ make defconfig kvm_guest.config debug.config

이름.config를 목표로 주면 Kbuild가 kernel/configs/와 아키텍처의 configs/에서 그 파일을 찾아 합칩니다.

scripts/kconfig/Makefilev7.3
%.config: $(obj)/conf
    $(if $(config-fragments),, $(error $@ fragment does not exists on this architecture))
    $(call cmd,merge_fragments)
    $(Q)$(MAKE) -f $(srctree)/Makefile olddefconfig

조각을 .config에 덮어쓴 다음 olddefconfig를 돌립니다. 뒤의 단계가 중요합니다. 심벌 하나를 켜면 그것이 select하는 심벌과 의존 관계가 함께 풀려야 하는데, 그 계산을 Kconfig가 다시 합니다.

조각은 .config와 같은 문법의 짧은 파일입니다.

kernel/configs/kvm_guest.configv7.3
# Help: Bootable as a KVM guest
CONFIG_NET=y
# ...
CONFIG_SERIAL_8250=y
CONFIG_SERIAL_8250_CONSOLE=y
# ...
CONFIG_VIRTIO_PCI=y
CONFIG_VIRTIO_BLK=y
CONFIG_VIRTIO_CONSOLE=y
CONFIG_VIRTIO_NET=y
CONFIG_9P_FS=y

v7.3의 kernel/configs/에 있는 조각 가운데 쓸모 있는 것은 셋입니다.

  • kvm_guest.config: virtio 장치, 직렬 콘솔, 9p 파일시스템. QEMU에서 부팅하는 데 필요한 것들입니다.
  • debug.config: KASAN, lockdep(PROVE_LOCKING), DEBUG_ATOMIC_SLEEP, kmemleak, 디버그 정보. 27장의 검사기를 한 번에 켭니다. 느려지지만 개발용 커널에는 켜 두는 편이 낫습니다.
  • hardening.config: 27장의 하드닝 묶음.

낱개의 심벌은 scripts/config로 바꿉니다.

터미널
$ scripts/config -e GDB_SCRIPTS -d RANDOMIZE_BASE
$ make olddefconfig

-e가 켜기, -d가 끄기입니다. 이 스크립트는 파일의 글자만 고치므로 반드시 olddefconfig를 이어서 돌립니다. Clang으로 빌드하려면 모든 make 명령에 LLVM=1을 붙입니다. Rust를 켜려면 먼저 make LLVM=1 rustavailable로 도구가 갖춰졌는지 확인합니다.

28.3빌드: .config에서 bzImage까지#

터미널
$ make -j$(nproc)

처음에는 수천 개의 파일을 컴파일하므로 오래 걸립니다. 그 뒤로는 고친 파일과 그것에 기대는 것만 다시 빌드합니다.

단계는 최상위 Makefile에 그대로 적혀 있습니다.

Makefilev7.3
vmlinux.a: vmlinux_a
    @:

PHONY += vmlinux_o
vmlinux_o: vmlinux.a $(KBUILD_VMLINUX_LIBS)
    $(Q)$(MAKE) -f $(srctree)/scripts/Makefile.vmlinux_o

vmlinux.o: vmlinux_o
    @:
# ...
vmlinux: vmlinux.o $(KBUILD_LDS) modpost
    $(Q)$(MAKE) -f $(srctree)/scripts/Makefile.vmlinux
산출물 무엇인가
include/generated/autoconf.h .config를 #define CONFIG_...로 옮긴 헤더. 모든 C 파일에 들어감
디렉터리/built-in.a 그 디렉터리에서 =y로 빌드된 목적 파일의 묶음
vmlinux 링크가 끝난 커널. ELF 파일이며 심벌과 디버그 정보가 들어 있음. gdb와 perf가 읽음
arch/x86/boot/bzImage vmlinux를 압축하고 부팅 코드를 붙인 것. 부트로더와 QEMU가 읽음
*.ko =m으로 고른 모듈
System.map 심벌과 주소의 표

한 부분만 빌드할 수도 있습니다. 스케줄러를 고치는 중이라면 make kernel/sched/가 그 디렉터리만, make kernel/sched/core.o가 그 파일만 컴파일합니다. make kernel/sched/core.s는 어셈블리를 내 줍니다. 6장에서 본 preempt_enable()이 명령어 몇 개가 되는지 이것으로 확인할 수 있습니다.

소스를 읽는 도구도 빌드에서 나옵니다.

터미널
$ make compile_commands.json

이 파일에는 각 C 파일을 컴파일한 정확한 명령이 들어 있습니다. clangd 같은 언어 서버가 이것을 읽으면, 편집기에서 "정의로 가기"가 현재 설정에서 실제로 컴파일되는 정의로 갑니다. 커널에는 #ifdef로 갈린 같은 이름의 함수가 많아서 이 차이가 큽니다.

28.4QEMU로 부팅하기#

빌드한 커널을 쓰던 기계에 설치해 재부팅하는 것은 느리고 위험합니다. 가상 머신에서 부팅합니다. QEMU는 bzImage를 직접 읽어 부팅할 수 있어서 디스크 이미지도 부트로더도 필요 없습니다. 있어야 하는 것은 하나입니다. 커널이 부팅을 마치고 실행할 첫 유저 프로그램입니다.

가장 작은 답은 프로그램 하나만 든 initramfs입니다. 커널 문서의 예입니다.

Documentation/filesystems/ramfs-rootfs-initramfs.rstv7.3
  int main(int argc, char *argv[])
  {
    printf("Hello world!\n");
    sleep(999999999);
  }
  EOF
  gcc -static hello.c -o init
  echo init | cpio -o -H newc | gzip > test.cpio.gz

정적으로 링크한 실행 파일을 init이라는 이름으로 cpio 묶음에 넣습니다. 커널은 부팅 끝에 이 묶음을 메모리 파일시스템에 풀고 /init을 PID 1로 실행합니다(1장).

터미널
$ qemu-system-x86_64 -kernel arch/x86/boot/bzImage -initrd test.cpio.gz \
    -append "console=ttyS0" -nographic -enable-kvm -m 1G -smp 2
...
[    0.412345] Run /init as init process
Hello world!
옵션 뜻
-kernel, -initrd 부팅할 커널 이미지와 initramfs
-append 커널 명령줄. console=ttyS0은 커널 메시지를 직렬 포트로 보냄
-nographic 화면 없이 직렬 포트를 터미널에 연결. Ctrl-a x로 끝냄
-enable-kvm 하드웨어 가상화 사용(23장). 없으면 훨씬 느림

"Hello world" 대신 셸이 있는 환경이 필요하면 정적으로 링크한 busybox를 init으로 넣는 것이 흔한 방법입니다. 더 편한 길도 있습니다. virtme-ng는 호스트의 파일시스템을 그대로 게스트의 루트로 빌려 줍니다.

터미널
$ vng --build
$ vng
$ vng -- uname -r

첫 명령이 커널을 빌드합니다. .config가 없으면 가상 머신용 최소 설정을 만들어 씁니다. 둘째가 그 커널로 부팅해 셸을 줍니다. 게스트 안에서 호스트의 파일과 도구가 그대로 보이고, 게스트에서 바꾼 것은 호스트에 영향을 주지 않습니다. 셋째처럼 명령 하나만 돌리고 끝낼 수도 있습니다.

설계 노트

무엇이든 고치기 전에 재현 가능한 작은 순환부터 만듭니다. 한 바퀴가 한 시간이면 하루에 여덟 번 시도합니다. 한 바퀴가 1분이면 가설을 세우고 버리는 일이 가벼워집니다.

커널에서 이 순환을 짧게 만드는 요소는 셋입니다. 증분 빌드(고친 파일만 다시 컴파일), 디스크 없는 부팅(이미지를 만들고 설치하는 단계가 없음), 버려도 되는 환경(커널이 죽어도 잃을 것이 없음)입니다. 27장의 syzbot이 하는 일도 이 순환을 기계로 돌리는 것입니다. 큰 시스템을 다룰 때 가장 먼저 투자할 곳은 기능이 아니라 이 순환의 길이입니다.

28.5모듈 쓰기#

커널에 코드를 넣는 가장 가벼운 방법은 모듈입니다. 실행 중인 커널에 올리고 내릴 수 있는 목적 파일입니다. 다음 모듈은 일정한 간격으로 메시지를 찍습니다. 짧지만 이 책의 여러 장이 들어 있습니다.

hello.cC
// SPDX-License-Identifier: GPL-2.0
#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt

#include <linux/module.h>
#include <linux/workqueue.h>
#include <linux/jiffies.h>
#include <linux/sched.h>
#include <linux/preempt.h>
#include <linux/smp.h>

static unsigned int period_ms = 1000;
module_param(period_ms, uint, 0644);
MODULE_PARM_DESC(period_ms, "interval between messages in milliseconds");

static void hello_fn(struct work_struct *work);
static DECLARE_DELAYED_WORK(hello_work, hello_fn);

static void hello_fn(struct work_struct *work)
{
    pr_info("jiffies=%lu cpu=%d comm=%s in_task=%d\n",
        jiffies, raw_smp_processor_id(), current->comm, in_task());
    schedule_delayed_work(&hello_work, msecs_to_jiffies(period_ms));
}

static int __init hello_init(void)
{
    pr_info("loaded, period_ms=%u\n", period_ms);
    schedule_delayed_work(&hello_work, msecs_to_jiffies(period_ms));
    return 0;
}

static void __exit hello_exit(void)
{
    cancel_delayed_work_sync(&hello_work);
    pr_info("unloaded\n");
}

module_init(hello_init);
module_exit(hello_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Periodic message from a workqueue");

읽을 곳은 네 군데입니다.

  • module_init()과 module_exit(). 모듈로 빌드될 때 이 매크로는 hello_init에 init_module이라는 별명을 붙입니다. insmod가 finit_module() 시스템 콜로 .ko를 커널에 넘기면, 커널은 심벌을 연결한 뒤 이 함수를 부릅니다. 음수 오류 코드를 돌려주면 로드가 취소됩니다.
  • 지연된 작업. DECLARE_DELAYED_WORK는 타이머와 작업을 묶은 struct delayed_work를 만듭니다. schedule_delayed_work()는 지정한 jiffies만큼 뒤에 hello_fn을 워크큐에서 실행합니다(11장, 8장). 함수가 끝에서 자기 자신을 다시 예약하므로 주기적으로 돕니다.
  • in_task()와 current->comm. 워크큐의 함수는 커널 스레드에서 실행되므로 태스크 컨텍스트입니다(13장). 찍히는 이름은 kworker/...일 것입니다.
  • hello_exit()의 순서. 먼저 작업을 취소하고 끝날 때까지 기다립니다. 이 줄이 없으면 모듈의 코드가 메모리에서 사라진 뒤에 타이머가 hello_fn을 부릅니다. 해제 후 사용입니다.

첫 항목의 별명 붙이기는 매크로 정의에서 보입니다.

include/linux/module.hv7.3
/* Each module must use one module_init(). */
#define module_init(initfn)                 \
    static inline initcall_t __maybe_unused __inittest(void)        \
    { return initfn; }                  \
    int init_module(void) __copy(initfn)            \
        __attribute__((alias(#initfn)));        \
    ___ADDRESSABLE(init_module, __initdata);

같은 매크로가 모듈이 아니라 커널에 내장되어 빌드될 때는 부팅 중에 불리는 초기화 함수 목록에 등록하는 것으로 바뀝니다. 소스는 그대로이고 .config의 =y와 =m이 뜻을 가릅니다.

schedule_delayed_work()가 어느 워크큐를 쓰는지도 헤더에 있습니다.

include/linux/workqueue.hv7.3
static inline bool schedule_delayed_work(struct delayed_work *dwork,
                     unsigned long delay)
{
    return queue_delayed_work(system_percpu_wq, dwork, delay);
}

트리 밖에서 모듈을 빌드하는 Makefile은 세 줄이면 됩니다.

MakefileMakefile
obj-m := hello.o
KDIR ?= /lib/modules/$(shell uname -r)/build

all:
    $(MAKE) -C $(KDIR) M=$(CURDIR) modules

-C로 커널 빌드 디렉터리에 들어가 그쪽의 Kbuild를 쓰고, M=으로 모듈 소스의 위치를 알려 줍니다. 방금 빌드한 커널에 맞추려면 make KDIR=~/linux로 그 트리를 가리킵니다. 모듈은 자기가 빌드된 바로 그 커널에만 올라갑니다. 내부 API가 안정적이지 않다는 26장의 방침이 여기서 실감 납니다.

가상 머신 안에서 올려 봅니다.

터미널
# insmod hello.ko period_ms=500
# dmesg | tail -3
[   42.118302] hello: loaded, period_ms=500
[   42.620911] hello: jiffies=4294709916 cpu=1 comm=kworker/1:2 in_task=1
[   43.124803] hello: jiffies=4294710420 cpu=1 comm=kworker/1:2 in_task=1
# echo 2000 > /sys/module/hello/parameters/period_ms
# modinfo hello.ko | grep -E 'license|parm'
# rmmod hello

숫자는 예시입니다. 두 줄의 jiffies 차이를 시간 차이와 견주면 이 커널의 HZ가 나옵니다. 위에서는 0.504초에 504이므로 1000입니다. 파라미터 권한을 0644로 주었기 때문에 /sys/module/hello/parameters/에 파일이 생기고, 실행 중에 주기를 바꿀 수 있습니다.

주의

모듈은 커널과 같은 권한으로 돕니다. 널 포인터를 역참조하면 프로세스가 아니라 커널이 죽고, 락을 잘못 쓰면 시스템 전체가 멈춥니다. 실험은 가상 머신에서 합니다. debug.config로 빌드한 커널에서 돌리면 27장의 검사기가 실수를 바로 알려 줍니다.

예전 자료와 다른 점

오래된 모듈 튜토리얼의 코드는 v7.3에서 컴파일되지 않는 것이 많습니다. 타이머가 대표적입니다. 옛 자료의 init_timer(), del_timer_sync(), from_timer()는 include/linux/timer.h에 없습니다. v7.3의 이름은 timer_setup(), timer_delete_sync(), timer_container_of()입니다. 초기화 함수의 이름을 init_module()로 직접 짓는 방식, MODULE_LICENSE 없는 모듈도 옛 흔적입니다. 내부 API는 계속 바뀌므로, 예제를 찾을 때는 블로그보다 트리 안의 samples/와 실제 드라이버를 봅니다. Rust로 쓴 모듈의 본보기는 samples/rust/에 있습니다.

28.6관찰 도구의 지도#

커널을 들여다보는 도구는 많습니다. 고르는 기준은 "무엇을 알고 싶은가"입니다.

알고 싶은 것 도구 한 줄 사용법
이 코드가 실행되는가, 이 값이 무엇인가 pr_info(), pr_debug() 코드에 넣고 dmesg
이 함수가 불리는가, 누가 부르는가, 얼마나 걸리는가 ftrace echo function_graph > current_tracer
이 이벤트가 얼마나 자주, 어떤 인자로 일어나는가 추적점 + bpftrace bpftrace -e 'tracepoint:sched:sched_switch { ... }'
CPU 시간이 어디에서 쓰이는가 perf perf record -g, perf report
지금 각 CPU와 태스크가 무엇을 하고 있는가 SysRq echo l > /proc/sysrq-trigger
이 자료구조의 지금 값은 무엇인가 gdb + QEMU, drgn p $lx_current().comm
죽은 커널은 무엇을 하다 죽었는가 oops 해독, kdump + crash scripts/decode_stacktrace.sh

printk와 dynamic debug

가장 먼저 손이 가는 도구는 출력입니다. pr_info()는 언제나 찍힙니다. pr_debug()는 CONFIG_DYNAMIC_DEBUG가 켜진 커널에서 기본으로 꺼져 있다가, 실행 중에 골라 켤 수 있습니다.

터미널
# echo 'module hello +p' > /proc/dynamic_debug/control
# echo 'module hello -p' > /proc/dynamic_debug/control

module 자리에 file, func, line을 써서 파일, 함수, 줄 단위로도 고릅니다. 디버그 출력을 코드에 남겨 두어도 평소에는 비용이 거의 없는 것은 25장의 스태틱 키 덕분입니다.

ftrace: 다시 빌드하지 않고 함수 따라가기

출력을 넣으려면 다시 빌드해야 합니다. ftrace는 이미 컴파일된 커널의 함수 진입점을 실행 중에 고쳐 써서 호출을 기록합니다.

터미널
# cd /sys/kernel/tracing
# echo vfs_read > set_graph_function
# echo function_graph > current_tracer
# cat trace | head -20
# echo nop > current_tracer

vfs_read()가 불릴 때마다 그 안에서 불린 함수들이 들여쓰기된 나무로, 각각 걸린 시간과 함께 나옵니다. 20장의 읽기 경로를 실제 호출로 확인하는 방법입니다. 같은 디렉터리의 events/ 아래에는 커널이 미리 심어 둔 추적점(tracepoint)이 있습니다. 추적점은 이름과 인자가 정해진 관찰 지점입니다.

include/trace/events/sched.hv7.3
/*
 * Tracepoint for task switches, performed by the scheduler:
 */
TRACE_EVENT(sched_switch,

    TP_PROTO(bool preempt,
         struct task_struct *prev,
         struct task_struct *next,
         unsigned int prev_state),

4장의 __schedule()이 태스크를 바꿀 때마다 이 지점을 지납니다. 첫 인자 preempt가 6장의 SM_PREEMPT로 들어온 전환인지를 알려 줍니다. events/sched/sched_switch/enable에 1을 쓰면 전환마다 한 줄이 trace에 쌓입니다.

예전 자료와 다른 점

많은 자료가 ftrace의 경로를 /sys/kernel/debug/tracing으로 적습니다. 커널 문서에 따르면 4.1 이전에는 추적 제어 파일이 모두 debugfs 안에 있었습니다. 지금은 tracefs라는 별도의 파일시스템이 /sys/kernel/tracing에 마운트됩니다. 옛 경로도 호환을 위해 보이지만, debugfs를 막아 둔 시스템에서는 새 경로만 됩니다.

bpftrace와 perf

추적점에 작은 프로그램을 붙여 그 자리에서 집계하려면 bpftrace를 씁니다(24장).

터미널
# bpftrace -e 'tracepoint:sched:sched_switch { @[comm] = count(); }'

Ctrl-c를 누르면 태스크 이름별 컨텍스트 스위치 횟수가 나옵니다. 모든 이벤트를 유저 공간으로 퍼 올리지 않고 커널 안에서 세므로 부담이 작습니다. perf는 일정한 간격으로 CPU를 멈춰 "지금 어느 함수인가"를 표본으로 모읍니다. perf record -g -a -- sleep 10 뒤에 perf report를 보면 커널과 유저 공간을 통틀어 시간이 쓰이는 곳이 나옵니다.

멈춘 시스템과 죽은 커널

시스템이 응답하지 않을 때는 SysRq가 남은 창구입니다.

Documentation/admin-guide/sysrq.rstv7.3
``l``       Shows a stack backtrace for all active CPUs.
[...]
``t``       Will dump a list of current tasks and their information to your
            console.
[...]
``w``       Dumps tasks that are in uninterruptible (blocked) state.

l은 각 CPU가 지금 어디를 돌고 있는지, w는 잠들어 깨어나지 못하는 태스크가 어디에서 기다리는지를 보여 줍니다(3장). 교착을 의심할 때 맨 먼저 보는 출력입니다.

가상 머신이라면 커널을 통째로 멈추고 gdb로 볼 수 있습니다. QEMU에 -s -S를 주면 1234번 포트에서 gdb를 기다리며 멈춘 채 시작합니다. 커널은 CONFIG_GDB_SCRIPTS를 켜고 빌드하고, 명령줄에 nokaslr를 줍니다.

터미널
$ gdb vmlinux
(gdb) target remote :1234
(gdb) lx-symbols
(gdb) break sched_tick
(gdb) continue
(gdb) p $lx_current().comm

lx-로 시작하는 명령은 커널 트리의 scripts/gdb/가 주는 도우미입니다. lx-dmesg는 로그 버퍼를, lx-ps는 태스크 목록을 보여 줍니다.

커널이 죽으면서 남긴 oops의 스택은 함수+오프셋/크기 꼴입니다. vmlinux가 있으면 소스의 줄 번호로 바꿀 수 있습니다.

터미널
$ scripts/decode_stacktrace.sh vmlinux < oops.txt
$ scripts/faddr2line vmlinux schedule+0x1b/0x90
설계 노트

코드를 고치기 전에 관찰하는 수단부터 익힙니다. 커널처럼 큰 시스템에서 "이 함수가 문제일 것이다"라는 짐작은 자주 틀립니다. 짐작으로 코드를 고치고 다시 빌드하는 순환은 느리고, 틀린 짐작 위에 다음 짐작을 쌓게 됩니다.

위의 표는 비용 순서이기도 합니다. bpftrace 한 줄은 재부팅도 다시 빌드도 필요 없습니다. 그래서 순서는 이렇습니다. 가벼운 도구로 넓게 보고("어느 태스크가 컨텍스트 스위치를 많이 하는가"), 범위가 좁혀지면 무거운 도구로 깊이 봅니다("그 함수 안에서 무슨 일이 일어나는가"). 커널이 추적점, 동적 디버그, 함수 추적을 미리 심어 두는 까닭도 같습니다. 관찰 가능성은 나중에 덧붙이는 기능이 아니라 설계의 일부입니다.

28.7책의 내용을 직접 확인하기#

도구가 갖춰졌으니 앞 장들의 주장을 실행 중인 시스템에서 확인해 봅니다.

직접 확인하기

컨텍스트 스위치와 선점 모델 (4장, 6장). 한 태스크가 스스로 양보한 횟수와 빼앗긴 횟수는 /proc에 있습니다.

터미널
$ grep ctxt /proc/self/status
voluntary_ctxt_switches:    3
nonvoluntary_ctxt_switches: 1

CPU를 계속 쓰는 프로그램(yes > /dev/null)과 잠만 자는 프로그램(sleep 100)의 PID로 같은 파일을 보면 두 숫자의 비가 뒤집힙니다. 시스템 전체의 횟수는 추적점으로 셉니다.

터미널
# perf stat -e sched:sched_switch -a -- sleep 5
# cat /sys/kernel/debug/sched/preempt
# echo full > /sys/kernel/debug/sched/preempt
# rtla timerlat top -d 30s

커널 빌드 같은 부하를 걸어 둔 채 선점 모델을 lazy와 full로 바꿔 가며 견줍니다. 볼 것은 둘입니다. 5초 동안의 sched_switch 횟수, 그리고 rtla가 보여 주는 타이머 지연의 최댓값입니다. 6장의 표가 말한 맞바꿈이 숫자로 나옵니다.

직접 확인하기

인터럽트와 친화성 (10장). /proc/interrupts는 IRQ마다 CPU별 발생 횟수를 보여 줍니다.

터미널
$ watch -n1 -d 'grep -E "CPU|virtio|eth|nvme" /proc/interrupts'
# cat /proc/irq/44/smp_affinity_list
0-3
# echo 2 > /proc/irq/44/smp_affinity_list

44는 예시이고, 첫 명령의 출력에서 고른 IRQ 번호를 씁니다. 네트워크 부하를 걸어 둔 채 친화성을 CPU 2로 좁히면, 그 줄의 숫자가 CPU 2의 칸에서만 늘어나기 시작합니다. 같은 일을 irqbalance 데몬이 주기적으로 하고 있을 수 있으므로 실험하는 동안은 꺼 둡니다.

직접 확인하기

페이지 폴트 세기 (17장, 18장). 64MiB를 매핑하고 4KiB마다 한 바이트씩 쓰는 프로그램입니다.

touch.cC
#include <sys/mman.h>

#define SIZE (64UL << 20)

int main(void)
{
    char *p = mmap(NULL, SIZE, PROT_READ | PROT_WRITE,
               MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);

    if (p == MAP_FAILED)
        return 1;
    for (unsigned long off = 0; off < SIZE; off += 4096)
        p[off] = 1;
    return 0;
}
터미널
$ gcc -O2 -o touch touch.c
# echo never > /sys/kernel/mm/transparent_hugepage/enabled
$ perf stat -e page-faults ./touch
# echo always > /sys/kernel/mm/transparent_hugepage/enabled
$ perf stat -e page-faults ./touch

mmap()은 주소 범위만 예약하고 물리 페이지는 주지 않습니다. 처음 쓰는 순간마다 페이지 폴트가 나고 그때 페이지가 붙습니다. 64MiB는 4KiB 페이지 16,384개이므로, 첫 실행의 폴트 수는 그 숫자에 프로그램 시작에 드는 얼마간을 더한 값입니다. 투명 거대 페이지를 켠 둘째 실행에서는 폴트 한 번에 2MiB가 붙으므로 수가 크게 줄어듭니다.

28.8소스 고고학: 이 줄은 왜 여기 있는가#

커널 코드를 읽다 보면 왜 이렇게 했는지 알 수 없는 줄을 만납니다. 주석이 없어도 답은 대개 기록에 있습니다. 26장에서 본 커밋 메시지와 태그의 규율이 여기서 값을 합니다.

터미널
$ git blame -L 5782,5790 kernel/sched/core.c
$ git show <커밋>
$ git describe --contains <커밋>
$ git log -S'TIF_NEED_RESCHED_LAZY' --oneline -- kernel/sched/
$ git log --grep='lazy preempt' --oneline
$ b4 mbox <Message-ID>
  1. git blame은 각 줄을 마지막으로 고친 커밋을 알려 줍니다. -L로 줄 범위를 줍니다.
  2. git show로 그 커밋을 읽습니다. 본문에 "왜"가 있습니다. 들여쓰기만 고친 커밋이면 git blame 커밋^ -- 파일로 한 단계 더 거슬러 갑니다.
  3. git describe --contains는 그 커밋이 처음 들어간 릴리스를 알려 줍니다. "이 동작은 어느 버전부터인가"의 답입니다.
  4. git log -S는 어떤 문자열이 추가되거나 삭제된 커밋만 찾습니다. 함수나 플래그가 언제 생기고 사라졌는지 봅니다. --grep은 커밋 메시지를 뒤집니다.
  5. 커밋의 Link: 태그는 lore.kernel.org의 메일을 가리킵니다. 거기에 패치의 이전 버전들, 리뷰어의 반대, 작성자의 답이 있습니다. b4 mbox는 그 스레드를 통째로 내려받습니다.
  6. 큰 변경이면 LWN에 그 논의를 정리한 기사가 있을 때가 많습니다. 이 책의 "더 읽을거리"에 실린 기사들이 그런 것입니다.

저장소 없이 훑어볼 때는 식별자마다 정의와 사용처를 이어 주고 버전을 바꿔 볼 수 있는 elixir.bootlin.com이 편합니다.

설계 노트

이 프로젝트의 관례는 문서보다 역사에 더 정확히 적혀 있습니다. 어떤 파일을 고치려 한다면 git log --oneline -- 그_파일을 먼저 봅니다. 제목의 접두어를 어떻게 쓰는지, 한 커밋이 얼마나 작은지, 어떤 변경이 한 시리즈로 묶이는지가 거기 있습니다. 새로 합류한 코드베이스에서 "여기서는 어떻게 하는가"를 묻기 전에 기록을 읽는 습관은 어디서나 통합니다. 그리고 그 습관은 자기가 남기는 기록의 질에도 영향을 줍니다. 몇 해 뒤 같은 줄 앞에서 git blame을 치는 사람이 읽을 것은 지금 쓰는 커밋 메시지입니다.

28.9첫 패치 보내기#

무엇을 고칠까

처음에는 오타나 코딩 스타일 수정이 쉬워 보입니다. 커널 문서는 그런 패치가 소음이 되어 점점 환영받지 못한다고 적고, 다른 출발점을 권합니다.

Documentation/process/2.Process.rstv7.3
    The #1 project for all kernel beginners should surely be "make sure
    that the kernel runs perfectly at all times on all machines which
    you can lay your hands on".  Usually the way to do this is to work
    with others on getting things fixed up (this can require
    persistence!) but that's fine - it's a part of kernel development.

자기 기계에서 최신 커널을 돌려 보고, 안 되는 것을 찾아 고치라는 것입니다. 실제로 쓸 만한 출발점은 이렇습니다.

  • 가진 하드웨어에서 rc 커널을 부팅해 dmesg의 경고와 회귀를 찾습니다. 이등분으로 원인 커밋을 찾으면 그것만으로도 기여입니다.
  • 자기가 이해한 코드에 KUnit 테스트나 kselftest를 더합니다(27장).
  • syzbot 대시보드에서 재현기가 있는 버그를 골라 원인을 찾습니다.
  • 문서가 코드와 달라진 곳을 고칩니다. 코드를 읽으며 문서와 대조하다 보면 눈에 띕니다.

만들고, 검사하고, 보내기

터미널
$ git switch -c fix-foo
$ git log --oneline -5 -- drivers/foo/
$ git commit -s
$ scripts/checkpatch.pl --strict -g HEAD
$ make W=1 drivers/foo/
$ git format-patch -1
$ scripts/get_maintainer.pl 0001-*.patch
$ git send-email --to=<메인테이너> --cc=<리스트> 0001-*.patch

둘째 줄은 그 디렉터리의 제목 접두어 관례를 봅니다. commit -s가 Signed-off-by를 붙입니다. 보내기 전에 자기 주소로 먼저 보내 메일이 깨지지 않는지 확인합니다. 같은 일을 b4로 하면 받는 사람 찾기와 버전 관리가 자동이 됩니다.

터미널
$ b4 prep -n fix-foo
$ b4 prep --auto-to-cc
$ b4 prep --check
$ b4 send --reflect
$ b4 send

--reflect는 자기에게만 보내는 연습입니다. 메일 서버 설정이 어려우면 b4는 kernel.org의 웹 제출 창구를 거쳐 보낼 수도 있습니다.

정리#

  • .config는 기본 설정에 설정 조각을 덮어쓰고 olddefconfig로 의존 관계를 다시 풀어 만듭니다. kvm_guest.config와 debug.config가 개발용 출발점입니다.
  • 빌드는 .config → 목적 파일 → vmlinux → bzImage로 흐릅니다. vmlinux는 디버거가, bzImage는 부트로더와 QEMU가 읽습니다.
  • QEMU는 bzImage와 initramfs만으로 부팅합니다. virtme-ng는 호스트의 파일시스템을 빌려 그 준비마저 없앱니다. 고치고 돌려 보는 순환을 짧게 만드는 것이 첫째 일입니다.
  • 모듈의 초기화 함수는 insmod가 부른 시스템 콜 안에서 커널이 부릅니다. 내려갈 때는 예약해 둔 작업을 먼저 취소하고 끝나기를 기다려야 합니다.
  • 관찰 도구는 가벼운 것부터 씁니다. 출력, ftrace, bpftrace와 perf, SysRq, gdb 순으로 깊어집니다.
  • 한 줄의 내력은 git blame → 커밋 → Link: → 메일 스레드로 거슬러 찾습니다.
  • 첫 패치는 자기 기계에서 만난 실제 문제에서 시작합니다. 보내기 전에 checkpatch.pl과 get_maintainer.pl을 돌리고, 리뷰에는 평문으로 줄마다 답합니다.

확인 문제#

scripts/config -e PROVE_LOCKING을 실행한 뒤 바로 make를 했더니 빌드는 되었는데, 부팅한 커널에 /proc/lockdep_stats가 없습니다. .config를 열어 보니 CONFIG_PROVE_LOCKING이 꺼져 있습니다. 무슨 일이 일어났습니까?

답 보기

scripts/config는 .config의 글자만 고칩니다. 의존 관계는 보지 않습니다. PROVE_LOCKING은 DEBUG_KERNEL에 의존하는데, 그것이 꺼져 있었다면 빌드가 시작될 때 Kconfig가 설정을 다시 맞추면서 조건을 채우지 못한 PROVE_LOCKING을 도로 껐습니다. 의존하는 심벌까지 함께 켜고(-e DEBUG_KERNEL -e PROVE_LOCKING) make olddefconfig를 돌린 다음, scripts/config -s PROVE_LOCKING으로 값이 남아 있는지 확인해야 합니다. debug.config 같은 조각을 쓰면 필요한 심벌이 한 묶음으로 들어 있어 이런 일이 줄어듭니다.

본문의 hello.c에서 hello_exit()의 cancel_delayed_work_sync()를 cancel_delayed_work()로 바꾸면 어떤 일이 생길 수 있습니까? _sync가 하는 일로 설명해 보세요.

답 보기

cancel_delayed_work()는 아직 타이머에 걸려 있는 작업을 취소할 뿐, 이미 워크큐에서 실행되기 시작한 hello_fn을 기다리지 않습니다. rmmod가 그 순간에 진행되면 hello_fn이 도는 중에 모듈의 코드가 해제됩니다. 게다가 hello_fn은 끝에서 자기를 다시 예약하므로, 취소한 직후에 새 타이머가 걸릴 수 있습니다. 그 타이머가 만료되면 사라진 주소의 함수를 부릅니다. _sync는 대기 중인 작업을 취소하고, 실행 중이면 끝날 때까지 기다리며, 그 사이 다시 예약되는 것도 막습니다. 반환한 뒤에는 작업이 걸려 있지도 실행 중이지도 않다는 것이 보장됩니다.

어떤 시스템 콜이 가끔 수십 밀리초씩 걸린다는 보고를 받았습니다. 운영 중인 시스템이라 재부팅할 수 없습니다. 어떤 도구를 어떤 순서로 쓰겠습니까?

답 보기

다시 빌드하거나 멈추지 않아도 되는 도구부터 씁니다. 먼저 bpftrace로 그 시스템 콜의 진입과 복귀 추적점에서 걸린 시간의 분포를 모아, 느린 호출이 얼마나 자주 어떤 태스크에서 나는지 봅니다. 다음으로 ftrace의 function_graph를 그 시스템 콜 함수에 걸어, 느린 호출에서 어느 하위 함수가 시간을 쓰는지 봅니다. 시간이 CPU에서 쓰이는지 잠들어 기다리는 데 쓰이는지에 따라 길이 갈립니다. CPU라면 perf record로 표본을 모으고, 기다림이라면 sched_switch 추적점으로 어디에서 잠들었고 누가 깨웠는지를 봅니다. pr_info()를 넣거나 gdb로 멈추는 방법은 이 시스템에서는 쓸 수 없습니다.

kernel/sched/core.c의 한 if 문이 왜 있는지 알고 싶습니다. git blame이 가리킨 커밋은 "sched: Reformat comments"라는 제목의, 들여쓰기만 바꾼 커밋이었습니다. 어떻게 진행합니까? 원래 커밋을 찾은 뒤에는 무엇을 봅니까?

답 보기

그 커밋의 바로 앞 상태에서 다시 git blame을 합니다(git blame 커밋^ -- kernel/sched/core.c). 형식만 바꾼 커밋을 건너뛰어 그 줄을 실제로 들여온 커밋에 닿을 때까지 되풀이합니다. 조건식에 쓰인 식별자로 git log -S를 돌려 그 문자열이 처음 추가된 커밋을 찾는 방법도 있습니다. 원래 커밋을 찾으면 본문에서 어떤 문제를 풀려 했는지 읽고, Fixes:가 있으면 그것이 가리키는 커밋도 봅니다. Link: 태그를 따라 lore의 스레드로 가면 리뷰에서 나온 다른 방안과 그것이 채택되지 않은 이유가 있습니다. git describe --contains로 그 변경이 들어간 릴리스를 확인해 두면 LWN 기사를 찾기도 쉽습니다.

용어#

.config
커널 빌드 설정을 담은 파일. Kconfig 심벌마다 한 줄이다.
설정 조각config fragment
.config에 덮어쓸 심벌 몇 개만 적은 파일. make 이름.config로 합친다.
vmlinux
링크가 끝난 커널의 ELF 파일. 심벌과 디버그 정보가 들어 있다.
bzImage
vmlinux를 압축하고 부팅 코드를 붙인 x86의 부팅용 이미지.
initramfs
커널이 부팅 끝에 메모리에 푸는 cpio 묶음. 그 안의 /init이 첫 유저 프로세스가 된다.
모듈kernel module
실행 중인 커널에 올리고 내릴 수 있는 목적 파일(.ko).
ftrace
컴파일된 커널의 함수 진입점을 실행 중에 고쳐 써서 호출을 기록하는 추적기.
추적점tracepoint
커널 코드에 미리 심어 둔, 이름과 인자가 정해진 관찰 지점.
dynamic debug
pr_debug() 출력을 실행 중에 모듈·파일·줄 단위로 켜고 끄는 기능.
SysRq
멈춘 시스템에서도 커널에 직접 명령을 내리는 통로. /proc/sysrq-trigger로도 쓴다.
