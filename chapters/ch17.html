가상 주소 공간

페이지 테이블, VMA, 메이플 트리, 페이지 폴트

Linux v7.3 기준약 55분
읽는 소스arch/x86/include/asm/pgtable_types.hinclude/linux/mm_types.hinclude/linux/maple_tree.hmm/mmap_lock.cmm/vma.carch/x86/mm/fault.cmm/memory.c

프로세스는 128TB짜리 주소 공간을 혼자 쓰는 것처럼 동작합니다. 실제 메모리는 수 GB이고 그나마 수백 개의 프로세스가 나눠 씁니다. 이 간극을 메우려고 커널은 장부를 두 벌 둡니다. 하나는 "어느 주소 범위가 유효한가"를 적은 VMA이고, 다른 하나는 "그 주소가 지금 어느 물리 페이지인가"를 적은 페이지 테이블입니다. 두 장부가 어긋나는 순간이 페이지 폴트이고, 커널은 그때 비로소 메모리를 내줍니다. 이 장은 두 장부의 구조와 그 사이를 잇는 폴트 경로를 v7.3 소스로 따라갑니다.

이 장에서 답하는 질문

  • 가상 주소 하나가 물리 주소로 바뀌기까지 페이지 테이블을 몇 번 읽는가?
  • VMA와 페이지 테이블은 각각 무엇을 기록하고, 왜 따로 있는가?
  • VMA를 담는 자료구조는 왜 RB 트리에서 메이플 트리로 바뀌었는가?
  • 페이지 폴트가 mmap_lock을 잡지 않고 처리되는 길은 어떻게 생겼는가?
  • fork() 뒤의 쓰기 시 복사는 어느 함수에서 판정되는가?

17.1주소 공간의 지도#

x86-64의 포인터는 64비트지만 CPU는 그 전부를 번역하지 않습니다. 4단계 페이지 테이블에서는 아래 48비트, 5단계에서는 57비트만 씁니다. 그 위의 비트는 번역되는 최상위 비트를 그대로 복사한 값이어야 합니다. 이 규칙을 지킨 주소를 정규 주소(canonical address)라고 합니다. 규칙 때문에 주소 공간은 아래쪽 절반과 위쪽 절반으로 갈리고, 그 사이에는 쓸 수 없는 구멍이 생깁니다. 리눅스는 아래쪽을 유저 공간에, 위쪽을 커널에 줍니다.

커널 쪽의 칸 나눔은 Documentation/arch/x86/x86_64/mm.rst에 표로 정리되어 있습니다. 자주 만나는 영역만 추리면 이렇습니다.

시작 주소 크기 용도
0000000000000000 약 128TB 유저 공간. mm마다 다릅니다.
ffff888000000000 64TB 직접 매핑(direct mapping). 모든 물리 메모리를 차례대로 붙여 놓은 영역
ffffc90000000000 32TB vmalloc·ioremap 영역
ffffea0000000000 1TB vmemmap. struct page 배열이 놓이는 자리 (18장)
fffffe0000000000 0.5TB cpu_entry_area. 진입 코드가 쓰는 CPU별 영역
ffffffff80000000 512MB 커널 텍스트
ffffffffa0000000 1520MB 모듈

직접 매핑 덕분에 커널은 물리 주소에 상수 하나를 더해 가상 주소를 얻습니다. kmalloc()이 돌려주는 포인터가 이 영역의 주소입니다. 표의 시작 주소는 고정값이 아닙니다. CONFIG_RANDOMIZE_MEMORY가 켜져 있으면 직접 매핑, vmalloc, vmemmap 세 영역의 시작이 부팅 때마다 달라지고, CONFIG_RANDOMIZE_BASE는 커널 텍스트가 놓이는 위치를 바꿉니다. 이것이 KASLR입니다. 커널 주소를 미리 알아야 하는 공격을 어렵게 만드는 장치입니다.

5단계 페이지 테이블(LA57)을 켠 CPU에서는 유저 공간이 64PB로 늘어납니다. 다만 커널은 요청받지 않으면 47비트 위의 주소를 내주지 않습니다. 포인터의 윗비트에 자기 정보를 끼워 넣는 JIT 컴파일러 같은 프로그램이 있기 때문입니다. mmap()의 힌트 주소를 47비트 위로 주었을 때만 넓은 영역에서 찾습니다.

예전 자료와 다른 점

많은 교재가 "유저 3GB, 커널 1GB"로 나뉜 32비트 주소 공간을 그리고, 직접 매핑에 들어가지 못한 메모리를 다루는 ZONE_HIGHMEM과 kmap()을 길게 설명합니다. x86-64에서는 직접 매핑이 물리 메모리 전체를 덮으므로 그 문제가 없습니다. 또 5단계 페이징을 빌드 옵션(CONFIG_X86_5LEVEL)으로 설명한 자료가 있는데, v7.3의 x86 Kconfig에는 그 옵션이 없습니다. 부팅할 때 CPU 기능(X86_FEATURE_LA57)을 보고 4단계로 접을지 정합니다.

17.2페이지 테이블#

페이지 테이블(page table)은 가상 주소를 물리 주소로 바꾸는 표입니다. 표 하나로 만들면 48비트 주소 공간에 항목이 236개 필요하므로, 여러 단계의 트리로 만들어 쓰는 부분만 채웁니다. 리눅스의 공용 코드는 단계를 PGD, P4D, PUD, PMD, PTE 다섯으로 부릅니다. 아키텍처가 지원하는 단계가 더 적으면 남는 단계는 항목이 하나뿐인 표로 접힙니다. 4단계 x86-64에서는 P4D가 접힙니다.

각 표는 4KB 페이지 하나이고 8바이트 항목 512개가 들어갑니다. 그래서 단계마다 주소 9비트를 씁니다. TLB에 번역이 없으면 CPU는 CR3 레지스터가 가리키는 PGD에서 출발해 메모리를 네 번 읽고 나서야 물리 주소를 얻습니다. PMD 항목이 다음 표가 아니라 곧바로 2MB 페이지를 가리킬 수도 있습니다. PUD 항목이 그러면 1GB 페이지입니다. 큰 페이지는 워크를 한두 단계 줄이고 TLB 항목 하나로 넓은 범위를 덮습니다.

항목의 아래쪽과 위쪽 비트에는 권한과 상태가 들어 있습니다.

arch/x86/include/asm/pgtable_types.hv7.3
#define _PAGE_BIT_PRESENT   0   /* is present */
#define _PAGE_BIT_RW        1   /* writeable */
#define _PAGE_BIT_USER      2   /* userspace addressable */
#define _PAGE_BIT_PWT       3   /* page write through */
#define _PAGE_BIT_PCD       4   /* page cache disabled */
#define _PAGE_BIT_ACCESSED  5   /* was accessed (raised by CPU) */
#define _PAGE_BIT_DIRTY     6   /* was written to (raised by CPU) */
#define _PAGE_BIT_PSE       7   /* 4 MB (or 2MB) page */
/* ... */
#define _PAGE_BIT_NX        63  /* No execute: only valid after cpuid check */

읽을 곳은 세 군데입니다.

  • PRESENT가 0인 항목을 CPU가 만나면 페이지 폴트가 납니다. 이때 나머지 63비트는 CPU가 해석하지 않으므로 커널이 마음대로 씁니다. 스왑 위치 같은 정보를 여기에 적습니다.
  • RW가 0인데 쓰려고 하거나 USER가 0인데 유저 모드에서 접근해도 폴트가 납니다. 쓰기 시 복사는 RW를 일부러 꺼 두는 데서 시작합니다.
  • ACCESSED와 DIRTY는 CPU가 세웁니다. 커널은 이 두 비트를 읽어 어떤 페이지가 최근에 쓰였는지, 디스크에 다시 써야 하는지를 압니다. 회수 알고리즘의 재료입니다(18장).

TLB와 PCID

워크는 비쌉니다. CPU는 최근 번역 결과를 TLB에 담아 둡니다. 문제는 페이지 테이블을 고쳤을 때입니다. TLB에 남은 옛 번역을 지워야 하고, 같은 mm을 쓰는 스레드가 다른 CPU에서 돌고 있으면 그 CPU의 TLB도 지워야 합니다. 이것이 TLB 슛다운입니다. x86에서는 flush_tlb_mm_range()가 대상 CPU들에 IPI를 보내 각자 flush_tlb_func()를 실행하게 합니다. 스레드가 많은 프로세스에서 munmap()이나 mprotect()가 비싼 까닭입니다. v7.3의 arch/x86/mm/tlb.c에는 AMD의 INVLPGB처럼 IPI 없이 다른 CPU의 TLB를 지우는 경로도 있습니다.

컨텍스트 스위치로 CR3가 바뀌면 원래는 TLB 전체가 비워집니다. PCID는 TLB 항목에 12비트 꼬리표를 붙여 다른 주소 공간의 항목을 남겨 둘 수 있게 합니다. 리눅스는 CPU마다 최근에 돌린 mm 여섯 개(TLB_NR_DYN_ASIDS)에만 번호를 줍니다.

KPTI: 페이지 테이블을 둘로

예전에는 프로세스의 페이지 테이블 하나에 유저 매핑과 커널 매핑이 함께 들어 있었습니다. USER 비트가 꺼진 커널 페이지는 유저 모드에서 접근할 수 없으니 충분하다고 여겼습니다. 2018년에 공개된 Meltdown은 이 가정을 깼습니다. 권한 검사에 걸리는 접근도 추측 실행 중에는 잠깐 수행되고, 그 흔적이 캐시에 남아 커널 메모리를 읽어 낼 수 있었습니다.

KPTI(kernel page-table isolation)는 프로세스마다 최상위 표를 두 장 둡니다. 커널 모드용에는 전부가 매핑되어 있고, 유저 모드용에는 유저 매핑과 cpu_entry_area만 있습니다. 매핑이 없으면 추측 실행으로도 읽을 것이 없습니다. 두 PGD는 연속한 8KB에 나란히 놓여 주소의 비트 12만 뒤집으면 서로 오갈 수 있고, 아래 단계의 표는 공유합니다. 대가는 유저와 커널을 오갈 때마다 CR3를 바꾸는 비용입니다(19장). PCID가 있으면 TLB를 비우지 않고 바꿀 수 있어 부담이 줄어듭니다. Meltdown의 영향을 받지 않는 CPU에서는 KPTI가 켜지지 않습니다.

17.3mm_struct와 VMA#

주소 공간 하나를 대표하는 구조체가 mm_struct입니다. 같은 프로세스의 스레드들은 task_struct->mm이 같은 mm_struct를 가리킵니다(2장).

include/linux/mm_types.hv7.3
struct mm_struct {
    struct {
        /* ... */
        struct maple_tree mm_mt;
        /* ... */
        unsigned long task_size;    /* size of task vm space */
        pgd_t * pgd;
        /* ... */
        atomic_t mm_users;
        /* ... */
        int map_count;          /* number of VMAs */
        /* ... */
        struct rw_semaphore mmap_lock;
        /* ... */
        unsigned long start_brk, brk, start_stack;
        /* ... */
        struct percpu_counter rss_stat[NR_MM_COUNTERS];
        /* ... */
    } __randomize_layout;
    /* ... */
};

두 장부의 뿌리가 여기 있습니다. mm_mt는 VMA를 담은 메이플 트리이고 pgd는 페이지 테이블의 최상위 표입니다. mmap_lock은 주소 공간 전체를 지키는 읽기-쓰기 세마포어입니다. rss_stat은 실제로 물리 메모리를 차지한 페이지 수를 파일·익명·스왑·공유 메모리로 나눠 셉니다. /proc/PID/status의 VmRSS가 여기서 나옵니다.

참조 카운트는 둘입니다. mm_users는 이 주소 공간을 쓰는 스레드 수이고, 0이 되면 매핑을 모두 걷어 냅니다. mm_count는 mm_struct 구조체 자체를 붙든 수이고, 0이 되어야 구조체가 해제됩니다.

VMA(virtual memory area)는 성질이 같은 연속한 주소 범위 하나입니다.

include/linux/mm_types.hv7.3
struct vm_area_struct {
    /* ... */
    union {
        struct {
            /* VMA covers [vm_start; vm_end) addresses within mm */
            unsigned long vm_start;
            unsigned long vm_end;
        };
        freeptr_t vm_freeptr; /* Pointer used by SLAB_TYPESAFE_BY_RCU */
    };
    /* ... */
    struct mm_struct *vm_mm;
    pgprot_t vm_page_prot;          /* Access permissions of this VMA. */
    /* ... */
    union {
        /* Temporary while VMA flags are being converted. */
        const vm_flags_t vm_flags;
        vma_flags_t flags;
    };
    /* ... */
    struct anon_vma *anon_vma;  /* Serialized by page_table_lock */
    /* ... */
    const struct vm_operations_struct *vm_ops;
    /* ... */
    unsigned long vm_pgoff;     /* Offset (within vm_file) in PAGE_SIZE
                       units */
    struct file * vm_file;      /* File we map to (can be NULL). */
    /* ... */
    refcount_t vm_refcnt ____cacheline_aligned_in_smp;
    /* ... */
} __randomize_layout;
  • [vm_start, vm_end)가 범위입니다. 끝 주소는 포함하지 않습니다.
  • vm_flags는 VM_READ, VM_WRITE, VM_EXEC, VM_SHARED 같은 성질입니다. 주석이 말하듯 v7.3은 이 필드를 unsigned long 하나에서 비트맵 타입 vma_flags_t로 옮기는 중이라 두 표현이 union으로 겹쳐 있습니다.
  • vm_file이 NULL이 아니면 파일 매핑이고, vm_pgoff가 파일 안의 시작 위치입니다. NULL이면 익명 매핑입니다.
  • vm_ops는 이 영역에서 폴트가 났을 때 부를 함수들의 표입니다. 파일시스템이나 드라이버가 채웁니다.
  • vm_refcnt는 뒤에서 볼 per-VMA 락의 본체입니다.

VMA와 페이지 테이블이 따로 있는 까닭은 둘의 수명과 주인이 다르기 때문입니다. VMA는 프로그램이 mmap()으로 약속받은 범위이고 커널만 봅니다. 페이지 테이블은 그 약속 가운데 지금 물리 메모리가 붙어 있는 부분이고 CPU가 직접 읽습니다. 1GB를 mmap()하면 VMA 하나가 생길 뿐 페이지 테이블은 그대로입니다. 반대로 메모리가 모자라면 커널은 VMA는 그대로 두고 페이지 테이블 항목만 지워 물리 페이지를 거둬 갑니다.

직접 확인하기

VMA는 /proc/PID/maps의 한 줄입니다.

터미널
$ cat /proc/self/maps
55d0c4a2b000-55d0c4a2d000 r--p 00000000 fd:01 1311  /usr/bin/cat
55d0c4a2d000-55d0c4a32000 r-xp 00002000 fd:01 1311  /usr/bin/cat
...
55d0e5c1f000-55d0e5c40000 rw-p 00000000 00:00 0     [heap]
...
7ffd8a1e0000-7ffd8a201000 rw-p 00000000 00:00 0     [stack]

왼쪽부터 vm_start-vm_end, 권한(p는 private, s는 shared), vm_pgoff를 바이트로 바꾼 값, 장치와 아이노드, 파일 이름입니다. 실행 파일 하나가 권한이 다른 여러 VMA로 나뉘어 있습니다.

약속받은 크기와 실제로 쓰는 크기는 grep -E 'VmSize|VmRSS' /proc/self/status로 견줍니다. VmSize는 모든 VMA 크기의 합이고 VmRSS는 페이지 테이블에 물리 페이지가 붙은 양입니다. 영역별 내역은 /proc/PID/smaps_rollup에 있습니다.

17.4VMA를 담는 메이플 트리#

커널은 주소 하나를 받아 그것을 포함하는 VMA를 찾는 일을 폴트마다 합니다. 프로세스 하나의 VMA는 수십 개에서 수만 개에 이릅니다. v7.3에서 이 검색을 맡는 자료구조가 메이플 트리(maple tree)입니다. 겹치지 않는 범위를 키로 하는 B-트리 계열이고, RCU 아래에서 락 없이 읽을 수 있습니다.

include/linux/maple_tree.hv7.3
struct maple_range_64 {
    struct maple_pnode *parent;
    unsigned long pivot[MAPLE_RANGE64_SLOTS - 1];
    union {
        void __rcu *slot[MAPLE_RANGE64_SLOTS];
        /* ... */
    };
};

/* ... */
struct maple_arange_64 {
    struct maple_pnode *parent;
    unsigned long pivot[MAPLE_ARANGE64_SLOTS - 1];
    void __rcu *slot[MAPLE_ARANGE64_SLOTS];
    unsigned long gap[MAPLE_ARANGE64_SLOTS];
    struct maple_metadata meta;
};

노드 하나는 256바이트입니다. pivot[i]는 slot[i]가 맡는 범위의 마지막 주소입니다. 리프의 slot은 VMA 포인터를, 내부 노드의 slot은 자식 노드를 가리킵니다. 64비트에서 리프의 슬롯은 16개(MAPLE_RANGE64_SLOTS)입니다. VMA가 없는 빈 범위도 슬롯 하나를 차지하고 그 값은 NULL입니다.

mm의 트리는 MM_MT_FLAGS로 초기화됩니다. 그 안의 MT_FLAGS_ALLOC_RANGE는 내부 노드를 maple_arange_64로 만들어 gap 배열을 두게 합니다. mmap()이 "길이 N 이상인 빈 자리"를 찾을 때 이 값만 보고 가망 없는 서브트리를 건너뜁니다. MT_FLAGS_USE_RCU는 읽는 쪽이 락 없이 내려갈 수 있게 노드를 RCU 규칙대로 교체하게 합니다. 쓰는 쪽은 mmap_lock을 쓰기로 잡아 서로를 배제합니다(MT_FLAGS_LOCK_EXTERN).

예전 자료와 다른 점

오래된 자료는 VMA가 세 군데에 걸려 있다고 설명합니다. 주소순으로 훑기 위한 연결 리스트(vm_next, vm_prev), 주소로 찾기 위한 RB 트리(mm_rb), 직전에 찾은 VMA를 기억하는 캐시(vmacache)입니다. v7.3의 vm_area_struct에는 vm_next도 RB 노드도 없습니다. 6.1에서 셋이 메이플 트리 하나로 합쳐졌습니다. RB 트리는 노드마다 VMA 하나라 트리가 깊고, 세 구조를 함께 고쳐야 해서 읽는 쪽도 락 없이는 일관된 모습을 볼 수 없었습니다. 메이플 트리는 노드 하나에 범위 여러 개를 담아 깊이를 줄였고, 구조가 하나라 RCU로 읽을 수 있습니다. 다음 절의 per-VMA 락이 이 위에 서 있습니다.

VMA를 훑는 코드는 트리의 내부를 모릅니다. VMA_ITERATOR()로 반복자를 만들고 for_each_vma()로 돕니다. 주소 하나로 찾을 때는 vma_lookup()이나 find_vma()를 씁니다. find_vma()는 이름과 달리 주소를 포함하는 VMA가 없으면 그 다음 VMA를 돌려주므로, 결과의 vm_start를 확인해야 합니다.

설계 노트

자료구조를 바꾸는 작업은 두 단계로 진행되었습니다. 먼저 커널 전체에서 vma->vm_next를 직접 따라가던 코드를 반복자 API로 바꿨습니다. 이 단계에서는 동작이 달라지지 않습니다. 그다음 API 뒤의 구현을 메이플 트리로 갈아 끼우고 리스트를 지웠습니다. 수백 군데의 사용처와 핵심 자료구조를 한 번에 바꾸면 문제가 생겼을 때 원인을 좁힐 수 없습니다. 인터페이스를 먼저 세워 사용처를 그 뒤로 모으고 구현 교체는 한 곳에서 한다는 순서는 큰 코드베이스의 리팩터링에 그대로 통합니다. 2024년에 VMA 조작 코드를 mm/mmap.c에서 mm/vma.c로 떼어 낸 것도 같은 맥락입니다. 그 덕분에 이 코드를 유저 공간에서 컴파일해 단위 테스트(tools/testing/vma)로 돌릴 수 있게 되었습니다.

17.5mmap_lock과 per-VMA 락#

mmap_lock은 주소 공간에 하나뿐입니다. 옛 자료의 mmap_sem이 5.8에서 이름이 바뀐 것입니다. 페이지 폴트는 VMA를 읽기만 하므로 읽기 락을 잡고, mmap()·munmap()·mprotect()는 VMA를 고치므로 쓰기 락을 잡습니다. 읽는 쪽끼리는 동시에 들어갈 수 있지만, 스레드가 많은 프로그램에서는 두 가지 문제가 남습니다.

  • 스레드 하나가 mmap()을 부르면 그동안 다른 모든 스레드의 폴트가 멈춥니다. 서로 관계없는 주소인데도 그렇습니다.
  • 읽기 락도 공짜가 아닙니다. 세마포어의 카운터 하나를 여러 CPU가 번갈아 고치면서 그 캐시 라인이 CPU 사이를 오갑니다.

per-VMA 락은 폴트가 필요한 VMA 하나만 잠그게 합니다. 폴트 핸들러는 먼저 이 함수를 부릅니다.

mm/mmap_lock.cv7.3
struct vm_area_struct *lock_vma_under_rcu(struct mm_struct *mm,
                      unsigned long address)
{
    MA_STATE(mas, &mm->mm_mt, address, address);
    struct vm_area_struct *vma;

retry:
    rcu_read_lock();
    vma = mas_walk(&mas);
    if (!vma) {
        rcu_read_unlock();
        goto inval;
    }

    vma = vma_start_read(mm, vma);
    if (IS_ERR_OR_NULL(vma)) {
        /* ... */
        /* Failed to lock the VMA */
        goto inval;
    }
    /* ... */
    rcu_read_unlock();

    /* Check if the vma we locked is the right one. */
    if (unlikely(address < vma->vm_start || address >= vma->vm_end)) {
        vma_end_read(vma);
        goto inval;
    }

    return vma;

inval:
    count_vm_vma_lock_event(VMA_LOCK_ABORT);
    return NULL;
}

읽을 곳은 세 군데입니다.

  • mmap_lock을 잡지 않습니다. RCU 읽기 구간 안에서 메이플 트리를 내려가 VMA를 찾습니다(16장).
  • vma_start_read()가 그 VMA의 vm_refcnt를 하나 올립니다. 이것이 읽기 락입니다. 올리는 데 성공하면 RCU 구간을 벗어나도 VMA는 사라지지 않습니다.
  • 실패하면 기다리지 않고 NULL을 돌려줍니다. 호출한 쪽은 예전처럼 mmap_lock을 잡는 길로 갑니다.

쓰는 쪽은 mmap_lock을 쓰기로 잡은 뒤, 고치려는 VMA마다 vma_start_write()를 부릅니다. 이 함수는 그 VMA에 들어와 있는 읽는 쪽이 모두 나갈 때까지 기다린 다음, mm의 순번 mm_lock_seq를 VMA의 vm_lock_seq에 적습니다. 읽는 쪽은 두 순번이 같으면 "지금 쓰는 중"으로 알고 물러납니다. 쓰기 락을 하나하나 푸는 코드는 없습니다. mmap_write_unlock()이 mm_lock_seq를 올리면 그동안 잠근 VMA 전부가 한꺼번에 풀립니다.

v7.3에서 per-VMA 락을 쓰는 곳은 폴트만이 아닙니다. /proc/PID/maps·smaps·numa_maps 읽기, TCP 수신 제로카피, userfaultfd의 일부 연산이 같은 길을 씁니다. madvise()도 그렇습니다. mm/madvise.c의 get_lock_mode()는 MADV_DONTNEED, MADV_FREE, 가드 영역 설치·제거에 MADVISE_VMA_READ_LOCK을 돌려줍니다. 앞의 둘은 메모리 할당자가 쓰지 않는 페이지를 커널에 돌려줄 때 부르는 연산입니다. 스레드마다 아레나를 두는 할당자에서는 이 호출이 매우 잦으므로, VMA 하나만 잠그고 끝내는 효과가 큽니다.

설계 노트

per-VMA 락은 "빠른 길을 낙관적으로 시도하고, 안 되면 느린 길로 간다"는 패턴의 본보기입니다. 빠른 길은 흔한 경우만 맡습니다. VMA가 있고, 아무도 고치는 중이 아니고, 폴트를 그 자리에서 끝낼 수 있는 경우입니다. 그 밖의 경우(VMA가 없어 스택을 늘려야 할 때, 디스크에서 페이지가 올라오기를 기다려야 할 때)는 빠른 길에서 풀려 하지 않고 mmap_lock을 잡는 원래 경로로 넘깁니다. 느린 길이 그대로 남아 있으므로 빠른 길은 단순하게 유지됩니다. 큰 락을 쪼갤 때 읽기 경로부터, 실패해도 되는 방식으로 시작한 것도 눈여겨볼 점입니다. 락 구조를 한 번에 뒤집지 않고 가장 뜨거운 경로의 경합부터 걷어 냈습니다.

17.6mmap()이 하는 일#

mmap() 시스템 콜은 VMA 장부만 고칩니다. x86-64에서 호출은 SYSCALL_DEFINE6(mmap) → ksys_mmap_pgoff() → vm_mmap_pgoff()로 이어지고, 여기서 mmap_lock을 쓰기로 잡은 뒤 do_mmap()을 부릅니다. do_mmap()은 인자를 검사하고, 주소가 지정되지 않았으면 빈 자리를 고르고, prot와 flags를 VMA 플래그로 바꿉니다. 실제로 VMA를 만드는 일은 mm/vma.c의 __mmap_region()이 합니다.

mm/vma.cv7.3
static unsigned long __mmap_region(struct file *file, unsigned long addr,
        unsigned long len, vma_flags_t vma_flags,
        unsigned long pgoff, struct list_head *uf)
{
    /* ... */
    error = __mmap_setup(&map, &desc, uf);
    if (error)
        goto abort_munmap;
    if (have_mmap_prepare)
        error = call_mmap_prepare(&map, &desc);
    /* ... */

    /* Attempt to merge with adjacent VMAs... */
    if (map.prev || map.next) {
        VMG_MMAP_STATE(vmg, &map, /* vma = */ NULL);

        vma = vma_merge_new_range(&vmg);
    }

    /* ...but if we can't, allocate a new VMA. */
    if (!vma) {
        error = __mmap_new_vma(&map, &vma, &desc.action);
        if (error)
            goto unacct_error;
        allocated_new = true;
    }
    /* ... */
    __mmap_complete(&map, vma);
    /* ... */
    return addr;
    /* ... */
}

순서는 넷입니다. __mmap_setup()이 요청 범위와 겹치는 기존 매핑을 걷어 낼 준비를 하고(MAP_FIXED), 주소 공간 한도와 메모리 약정량을 확인합니다. 파일 매핑이면 call_mmap_prepare()가 파일시스템이나 드라이버의 mmap_prepare 훅을 불러 vm_ops 같은 값을 받습니다. 그다음이 병합입니다. 새 범위가 앞뒤 VMA와 맞닿아 있고 플래그, 파일, 오프셋이 이어지면 이웃을 늘립니다. 병합할 수 없을 때만 __mmap_new_vma()가 VMA를 할당해 메이플 트리에 넣습니다.

이 함수는 물리 페이지를 할당하지도 페이지 테이블을 건드리지도 않습니다. 그 일은 첫 접근 때의 페이지 폴트로 미룹니다(MAP_POPULATE는 예외). 이것이 요구 페이징(demand paging)입니다.

매핑의 종류는 두 축으로 나뉩니다.

private (MAP_PRIVATE) shared (MAP_SHARED)
파일 읽을 때는 페이지 캐시를 공유, 쓰면 사본을 만듦. 실행 파일의 데이터 영역 쓰면 파일에 반영됨. 프로세스 사이의 공유
익명 0으로 채워진 사적인 메모리. 힙, 스택 fork()한 자식과 공유하는 메모리

힙은 brk() 시스템 콜로 늘리는 익명 private VMA이고, 스택은 VM_GROWSDOWN 플래그가 붙은 익명 VMA입니다. 스택 아래의 주소에서 폴트가 나면 커널은 expand_downwards()로 VMA의 vm_start를 내려 줍니다. 이때 바로 아래의 다른 매핑과 stack_guard_gap(기본 256페이지)만큼의 간격이 유지되지 않으면 늘려 주지 않습니다. 스택이 자라다가 이웃 매핑을 덮어쓰는 공격을 막는 장치입니다.

참고 · 오버커밋

mmap()이 물리 메모리를 주지 않으므로 커널은 가진 것보다 많이 약속할 수 있습니다. vm.overcommit_memory가 그 정책입니다. 기본값 0은 터무니없이 큰 요청만 거절하고, 1은 무엇이든 받아 주고, 2는 스왑과 물리 메모리의 일정 비율(기본 50%)을 넘겨 약속하지 않습니다. 0이나 1에서는 malloc()이 성공하고도 그 메모리를 실제로 건드리는 순간 메모리가 모자랄 수 있습니다. 그때 벌어지는 일이 18장의 OOM 킬러입니다.

17.7페이지 폴트#

CPU가 가상 주소를 번역하다가 PRESENT가 꺼진 항목이나 권한이 맞지 않는 항목을 만나면 14번 예외를 일으킵니다. 폴트가 난 주소는 CR2 레지스터에, 이유는 오류 코드에 담깁니다. x86-64의 진입점 exc_page_fault()는 주소가 커널 영역인지 유저 영역인지에 따라 do_kern_addr_fault()나 do_user_addr_fault()로 갑니다. 대부분의 폴트는 뒤쪽입니다.

arch/x86/mm/fault.cv7.3

        goto lock_mmap;

retry:

        return;

앞 절에서 본 구조가 그대로 있습니다. 먼저 per-VMA 락으로 시도하고, VMA를 못 잠갔거나 처리 도중 VM_FAULT_RETRY가 돌아오면 lock_mmap으로 내려가 mmap_lock을 잡고 다시 합니다. 두 길 모두 같은 두 가지를 확인합니다.

  • 주소를 포함하는 VMA가 있는가. 없으면 bad_area_nosemaphore()가 SIGSEGV(SEGV_MAPERR)를 보냅니다. 단 lock_mm_and_find_vma()는 바로 위의 VMA가 VM_GROWSDOWN이면 스택 확장을 먼저 시도합니다.
  • VMA의 권한이 이 접근을 허용하는가. access_error()가 오류 코드와 vm_flags를 견줍니다. 읽기 전용 VMA에 쓰려 했다면 SIGSEGV(SEGV_ACCERR)입니다.

둘 다 통과하면 이 폴트는 프로그램의 잘못이 아닙니다. 약속된 주소인데 페이지 테이블이 아직 따라오지 못한 것입니다. 그 간격을 메우는 함수가 handle_mm_fault()입니다.

handle_mm_fault()가 부르는 __handle_mm_fault()는 위에서부터 표를 내려갑니다. p4d_alloc(), pud_alloc(), pmd_alloc()을 차례로 불러 없는 단계의 표를 만들고, 할당에 실패하면 VM_FAULT_OOM을 돌려줍니다. PMD 자리가 비어 있고 큰 페이지를 쓸 수 있는 VMA라면 create_huge_pmd()로 2MB 페이지를 통째로 넣고 끝냅니다. 아니면 마지막 단계로 내려갑니다. 갈림길은 handle_pte_fault()에 모여 있습니다.

mm/memory.cv7.3
static vm_fault_t handle_pte_fault(struct vm_fault *vmf)
{
    /* ... */
    if (!vmf->pte)
        return do_pte_missing(vmf);

    if (!pte_present(vmf->orig_pte))
        return do_swap_page(vmf);

    if (pte_protnone(vmf->orig_pte) && vma_is_accessible(vmf->vma)) {
        /* ... */
        return do_numa_page(vmf);
    }

    spin_lock(vmf->ptl);
    entry = vmf->orig_pte;
    /* ... */
    if (vmf->flags & (FAULT_FLAG_WRITE|FAULT_FLAG_UNSHARE)) {
        if (!pte_write(entry))
            return do_wp_page(vmf);
        else if (likely(vmf->flags & FAULT_FLAG_WRITE))
            entry = pte_mkdirty(entry);
    }
    /* ... */
}

비어 있음, 익명 VMA do_anonymous_page() 0으로 채운 새 페이지를 붙입니다.
비어 있음, 파일 VMA do_fault() vm_ops->fault를 불러 페이지 캐시의 페이지를 붙입니다. 읽기·private 쓰기·shared 쓰기로 다시 갈립니다.
비어 있지 않으나 PRESENT 아님 do_swap_page() 스왑에서 읽어 옵니다. 이주 중이라는 표시나 가드 영역 표시 같은 특수 항목도 여기서 처리합니다.
있지만 쓰기 금지, 쓰기 접근 do_wp_page() 쓰기 시 복사를 합니다.

mmap_lock이나 VMA 락은 VMA가 사라지지 않게 할 뿐 페이지 테이블 항목을 지켜 주지 않습니다. 항목을 고칠 때는 그 페이지 테이블 페이지에 딸린 스핀락 vmf->ptl을 잡습니다. 두 스레드가 같은 주소에서 동시에 폴트를 내면 한쪽이 먼저 채우고, 다른 쪽은 항목이 바뀐 것을 보고 그냥 돌아갑니다.

디스크를 읽지 않고 끝난 폴트를 minor 폴트, 파일이나 스왑에서 읽어 와야 했던 폴트를 major 폴트라고 합니다. mm_account_fault()가 VM_FAULT_MAJOR 여부를 보고 태스크의 min_flt나 maj_flt를 올립니다. major 폴트는 디스크를 기다리므로 지연 시간을 볼 때 따로 셉니다.

직접 확인하기

프로그램 하나가 낸 폴트 수를 셉니다.

터미널
$ perf stat -e page-faults,minor-faults,major-faults ls > /dev/null
               112      page-faults
               112      minor-faults
                 0      major-faults

ls처럼 작은 프로그램도 백여 번의 폴트를 냅니다. 실행 파일과 라이브러리를 매핑만 해 두고 처음 건드릴 때 채우기 때문입니다. 누가 폴트를 내는지는 추적점으로 봅니다.

터미널
# bpftrace -e 'tracepoint:exceptions:page_fault_user { @[comm] = count(); }'

CONFIG_PER_VMA_LOCK_STATS로 빌드한 커널은 /proc/vmstat의 vma_lock_success와 vma_lock_abort로 per-VMA 락의 성공률을 보여 줍니다.

커널 모드에서 유저 주소를 건드리다 난 폴트도 같은 경로를 탑니다. copy_from_user()가 아직 채워지지 않은 유저 페이지를 읽는 경우입니다. 주소가 아예 유효하지 않으면 커널 코드에는 시그널을 보낼 수 없습니다. 이때 kernelmode_fixup_or_oops()가 예외 테이블에서 폴트가 난 명령어를 찾아, 있으면 미리 정해 둔 복구 지점으로 건너뛰고 없으면 oops를 냅니다. 예외 테이블은 19장에서 다룹니다.

17.8쓰기 시 복사#

fork()는 부모의 주소 공간을 자식에게 복사합니다. 메모리 내용을 정말로 복사하면 느리고, 자식이 곧바로 exec()을 부르면 헛일이 됩니다. 그래서 커널은 페이지 테이블만 복사하고 물리 페이지는 공유합니다(1장). 그 대신 양쪽 모두에서 쓰기를 막습니다.

mm/memory.cv7.3
static __always_inline void __copy_present_ptes(struct vm_area_struct *dst_vma,
        struct vm_area_struct *src_vma, pte_t *dst_pte, pte_t *src_pte,
        pte_t pte, unsigned long addr, int nr)
{
    /* ... */
    /* If it's a COW mapping, write protect it both processes. */
    if (vma_is_cow_mapping(src_vma) && writable) {
        wrprotect_ptes(src_mm, addr, src_pte, nr);
        pte = pte_wrprotect(pte);
    }
    /* ... */
    set_ptes(dst_vma->vm_mm, addr, dst_pte, pte, nr);
}

VMA는 여전히 VM_WRITE인데 PTE의 RW 비트만 꺼집니다. 두 장부를 일부러 어긋나게 만든 것입니다. 이후 어느 쪽이든 그 페이지에 쓰면 CPU가 폴트를 내고, VMA가 쓰기를 허용하므로 access_error()는 통과하며, handle_pte_fault()가 "있지만 쓰기 금지"를 보고 do_wp_page()를 부릅니다. 이것이 쓰기 시 복사(copy-on-write, COW)입니다.

mm/memory.cv7.3
static vm_fault_t do_wp_page(struct vm_fault *vmf)
    __releases(vmf->ptl)
{
    /* ... */
    if (folio && folio_test_anon(folio) &&
        (PageAnonExclusive(vmf->page) || wp_can_reuse_anon_folio(folio, vma))) {
        if (!PageAnonExclusive(vmf->page))
            SetPageAnonExclusive(vmf->page);
        /* ... */
        wp_page_reuse(vmf, folio);
        return 0;
    }
    /*
     * Ok, we need to copy. Oh, well..
     */
    /* ... */
    return wp_page_copy(vmf);
}

복사하기 전에 먼저 복사할 필요가 있는지 봅니다. 상대가 이미 자기 사본을 받아 갔거나 종료했다면 이 페이지를 쓰는 것은 나뿐입니다. 그때는 wp_page_reuse()가 RW 비트만 다시 켭니다. 정말 공유 중일 때만 wp_page_copy()가 새 페이지를 할당해 내용을 복사하고 PTE를 새 페이지로 돌립니다.

같은 발상이 익명 메모리의 첫 접근에도 쓰입니다.

mm/memory.cv7.3
static vm_fault_t do_anonymous_page(struct vm_fault *vmf)
{
    /* ... */
    /* Use the zero-page for reads */
    if (!(vmf->flags & FAULT_FLAG_WRITE) &&
            !mm_forbids_zeropage(vma->vm_mm)) {
        entry = pte_mkspecial(pfn_pte(zero_pfn(vmf->address),
                        vma->vm_page_prot));
        /* ... */
        set_pte_at(vma->vm_mm, addr, vmf->pte, entry);
        /* ... */
        goto unlock;
    }

    /* Allocate our own private page. */
    /* ... */
    folio = alloc_anon_folio(vmf);
    /* ... */
}

아직 쓴 적 없는 익명 페이지를 읽으면 새 페이지를 주지 않습니다. 시스템에 하나뿐인, 0으로 채워진 제로 페이지를 읽기 전용으로 붙입니다. 나중에 쓰면 그때 COW로 진짜 페이지를 받습니다. 처음부터 쓰기 접근이면 alloc_anon_folio()가 바로 페이지를 할당합니다. v7.3에서는 이 함수가 한 페이지가 아니라 여러 페이지짜리 폴리오를 줄 수도 있습니다(18장).

흔한 오해

"fork()는 메모리를 두 배로 쓴다." 아닙니다. 복사되는 것은 VMA와 페이지 테이블이고, 물리 페이지는 누군가 쓸 때 한 장씩 갈라집니다. 다만 페이지 테이블 복사는 매핑된 크기에 비례하므로, 큰 프로세스의 fork()는 그것만으로도 느립니다.

17.9주소 공간을 다루는 그 밖의 인터페이스#

mmap(), munmap(), mprotect(), brk()가 기본이고, 그 위에 용도가 좁은 시스템 콜이 계속 붙어 왔습니다. v7.3에 있는 것 가운데 몇 가지입니다.

인터페이스 하는 일
madvise() 범위에 대한 힌트와 요청. MADV_DONTNEED(지금 돌려줌), MADV_FREE(모자라면 가져가도 됨) 등
process_madvise() 다른 프로세스의 주소 공간에 madvise()를 겁니다.
MADV_GUARD_INSTALL 가드 영역. VMA를 쪼개지 않고 페이지 테이블에 표시만 남겨, 그 페이지에 접근하면 SIGSEGV가 나게 합니다. 스레드 스택 끝이나 할당자의 버퍼 사이에 가드 페이지를 두어도 VMA 수가 늘지 않습니다.
mseal() 범위를 봉인합니다. 봉인된 VMA는 munmap(), mremap(), mprotect()로 바꿀 수 없습니다.
userfaultfd() 폴트 처리를 유저 공간에 맡깁니다. 가상 머신의 실시간 이주에 씁니다.
memfd_secret() 커널의 직접 매핑에서도 빠지는 메모리를 만듭니다.
map_shadow_stack() 복귀 주소만 담는 섀도 스택용 매핑을 만듭니다.

가드 영역은 두 장부의 구도를 잘 보여 줍니다. 예전에는 가드 페이지를 PROT_NONE 매핑으로 만들었고, 그러면 VMA가 셋으로 쪼개졌습니다. 가드 영역은 VMA 장부를 건드리지 않고 페이지 테이블의 빈 항목에 표시만 적습니다. 폴트가 나면 do_swap_page()가 이 표시를 보고 SIGSEGV를 보냅니다.

정리#

  • x86-64의 주소 공간은 정규 주소 규칙 때문에 아래쪽 유저 절반과 위쪽 커널 절반으로 나뉩니다.
  • 페이지 테이블은 단계마다 주소 9비트를 색인으로 쓰는 트리입니다. KPTI는 최상위 표를 유저용과 커널용 두 장으로 나눕니다.
  • 커널은 장부를 두 벌 둡니다. VMA는 유효한 주소 범위와 그 성질을, 페이지 테이블은 지금 붙어 있는 물리 페이지를 적습니다.
  • VMA는 mm_struct의 메이플 트리에 들어 있습니다. 범위를 키로 하고 RCU로 읽을 수 있습니다.
  • 페이지 폴트는 먼저 RCU와 per-VMA 락으로 처리를 시도하고, 안 되면 mmap_lock을 잡는 경로로 갑니다.
  • mmap()은 VMA만 만들고, 물리 페이지는 첫 접근의 폴트에서 붙습니다. handle_pte_fault()가 PTE의 상태를 보고 익명·파일·스왑·COW로 가릅니다.
  • COW는 VMA는 쓰기 가능으로 두고 PTE만 쓰기 금지로 만들어 둔 뒤, 쓰기 폴트에서 복사하거나 재사용하는 기법입니다.

확인 문제#

1GB를 mmap(MAP_PRIVATE|MAP_ANONYMOUS)로 받은 직후와, 그 영역 전체에 1바이트씩 쓴 뒤에 VmSize와 VmRSS는 각각 어떻게 달라집니까? 커널의 어느 자료구조가 바뀐 결과입니까?

답 보기

mmap() 직후에는 VmSize만 1GB 늘어납니다. 메이플 트리에 VMA 하나가 들어가거나 이웃 VMA가 늘어난 것이 전부이고 페이지 테이블은 그대로입니다. 영역에 쓰면 페이지마다 폴트가 나고 do_anonymous_page()가 물리 페이지를 할당해 PTE를 채웁니다. 이때 rss_stat의 익명 페이지 카운터가 올라가 VmRSS가 1GB 늘어납니다.

읽기 전용으로 매핑한 파일 영역에 쓰려고 한 경우와, fork() 직후 부모가 자기 힙에 쓰려고 한 경우는 CPU 입장에서 둘 다 "쓰기 금지 PTE에 쓰기"입니다. 커널은 어디에서 둘을 구분합니까?

답 보기

access_error()에서 구분합니다. 이 함수는 PTE가 아니라 VMA의 vm_flags를 봅니다. 앞의 경우는 VMA에 VM_WRITE가 없으므로 bad_area_access_error()로 가서 SIGSEGV(SEGV_ACCERR)가 나갑니다. 뒤의 경우는 VMA가 VM_WRITE이므로 통과하고, handle_pte_fault()가 PTE가 쓰기 금지인 것을 보고 do_wp_page()로 보냅니다. VMA가 "허용된 것"을, PTE가 "지금 상태"를 적기 때문에 가능한 구분입니다.

lock_vma_under_rcu()가 VMA를 찾은 뒤에 address가 [vm_start, vm_end) 안에 있는지 다시 확인하는 이유는 무엇입니까?

답 보기

VMA를 찾은 시점과 잠근 시점 사이에 빈틈이 있기 때문입니다. 트리를 내려가는 동안에는 RCU만 쥐고 있으므로 다른 스레드가 그 VMA를 줄이거나 쪼갤 수 있습니다. RCU는 구조체가 해제되지 않게 할 뿐 내용이 바뀌는 것은 막지 않습니다. vm_refcnt를 올린 뒤에야 범위가 고정되므로, 그때 다시 확인해 어긋나 있으면 mmap_lock 경로로 물러납니다.

스레드 64개가 각자 자기 아레나에서 malloc()과 free()를 반복하는 프로그램이 있습니다. per-VMA 락이 없던 커널에서 이 프로그램이 mmap_lock에서 경합하던 지점 두 곳과, v7.3에서 각각이 어떻게 달라졌는지 설명해 보세요.

답 보기

첫째는 페이지 폴트입니다. 새로 받은 메모리를 처음 건드릴 때마다 mmap_lock을 읽기로 잡았고, 다른 스레드가 mmap()으로 쓰기 락을 쥐면 전부 멈췄습니다. v7.3에서는 lock_vma_under_rcu()로 자기 아레나의 VMA만 잠급니다. 둘째는 할당자가 빈 페이지를 돌려주는 madvise(MADV_DONTNEED)나 MADV_FREE입니다. get_lock_mode()가 이 연산에 MADVISE_VMA_READ_LOCK을 돌려주므로 역시 VMA 하나만 읽기로 잠급니다. mmap()과 munmap() 자체는 여전히 mmap_lock을 쓰기로 잡습니다.

용어#

직접 매핑direct mapping
물리 메모리 전체를 커널 주소 공간의 한 영역에 차례대로 매핑해 둔 것.
페이지 테이블page table
가상 주소를 물리 주소로 바꾸는 다단계 표. PGD, P4D, PUD, PMD, PTE 순으로 내려간다.
KPTI
유저 모드에서 쓰는 페이지 테이블에서 커널 매핑을 빼는 Meltdown 대응책.
mm_struct
주소 공간 하나를 대표하는 구조체. VMA 트리와 페이지 테이블의 뿌리를 가진다.
VMAvirtual memory area
권한과 뒷받침하는 대상이 같은 연속한 가상 주소 범위. struct vm_area_struct.
메이플 트리maple tree
겹치지 않는 범위를 키로 하는 B-트리 계열 자료구조. RCU로 읽을 수 있다.
per-VMA 락
주소 공간 전체가 아니라 VMA 하나를 잠그는 락. 읽기 쪽은 vm_refcnt를 올려서 잡는다.
요구 페이징demand paging
매핑할 때가 아니라 처음 접근할 때 물리 페이지를 붙이는 방식.
쓰기 시 복사copy-on-write
페이지를 읽기 전용으로 공유하다가 쓰기 폴트가 났을 때 사본을 만드는 기법.
minor / major 폴트
디스크 I/O 없이 끝난 폴트와 I/O가 필요했던 폴트.
