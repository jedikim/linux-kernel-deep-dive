C로 쓴 객체지향

커널 코드에 반복해서 나오는 설계 패턴

Linux v7.3 기준약 50분
읽는 소스fs/pipe.cfs/sync.cinclude/linux/indirect_call_wrapper.hinclude/linux/container_of.hinclude/linux/list.hinclude/linux/kref.hvirt/kvm/kvm_main.ckernel/cgroup/namespace.c

리눅스 커널은 C로 쓰여 있습니다. 클래스도, 상속도, 소멸자도, 제네릭도, 예외도 없는 언어입니다. 그런데 커널은 파일시스템 수십 가지를 같은 read()로 다루고, 객체 하나를 리스트 여러 개에 동시에 매달고, 수천 명이 고치는 코드에서 자원이 새지 않게 관리합니다. 언어가 주지 않는 것을 커널은 관례로 만들었습니다. 같은 모양의 코드가 서브시스템마다 되풀이되고, 리뷰와 도구가 그 모양을 지킵니다. 이 장은 앞의 장들에서 스쳐 간 그 모양들을 한자리에 모아 이름을 붙입니다.

이 장에서 답하는 질문
  • 커널은 C에서 "인터페이스 하나, 구현 여럿"을 어떻게 표현하는가?
  • container_of()는 무엇을 계산하며, 리스트 노드를 객체 안에 넣으면 무엇을 얻는가?
  • 객체는 언제 해제되는가? 참조 카운트의 규약은 무엇인가?
  • goto 되돌리기 사다리와 guard()는 같은 문제를 어떻게 다르게 푸는가?
  • 설정 옵션 수천 개가 #ifdef 범벅이 되지 않게 하는 방법은 무엇인가?
  • 자주 도는 경로에서 분기와 간접 호출을 없애는 방법은 무엇인가?

25.1ops 테이블: 인터페이스와 구현#

문제. read() 시스템 콜은 대상이 ext4 파일인지, 파이프인지, /proc의 가상 파일인지 모릅니다. 호출하는 쪽을 고치지 않고 구현을 늘릴 수 있어야 합니다.

커널의 답. 함수 포인터를 모은 구조체를 인터페이스로 삼습니다. 이 책에서는 ops 테이블이라고 부르겠습니다. 구현하는 쪽은 그 구조체의 인스턴스를 하나 만들어 자기 함수로 채웁니다. 20장에서 ext4의 ext4_file_operations를 보았습니다. 파이프의 것은 이렇습니다.

fs/pipe.cv7.3
const struct file_operations pipefifo_fops = {
    .open       = fifo_open,
    .read_iter  = fifo_pipe_read,
    .write_iter = fifo_pipe_write,
    .poll       = pipe_poll,
    .unlocked_ioctl = pipe_ioctl,
    .release    = pipe_release,
    .fasync     = pipe_fasync,
    .splice_write   = iter_file_splice_write,
};

호출하는 쪽은 객체에 매달린 테이블을 거쳐 부릅니다. fsync() 시스템 콜이 닿는 함수입니다.

fs/sync.cv7.3
int vfs_fsync_range(struct file *file, loff_t start, loff_t end, int datasync)
{
    struct inode *inode = file->f_mapping->host;

    if (!file->f_op->fsync)
        return -EINVAL;
    if (!datasync)
        sync_lazytime(inode);
    return file->f_op->fsync(file, start, end, datasync);
}

읽을 곳은 세 군데입니다.

  • 테이블은 const입니다. 읽기 전용 영역에 놓이므로 실행 중에 함수 포인터를 덮어쓰는 공격이 어려워집니다.
  • 구현하지 않은 연산은 NULL로 둡니다. 지정 초기화에서 빠진 멤버는 0이 됩니다. 파이프의 테이블에는 .fsync가 없고, 호출하는 쪽이 그것을 확인합니다. 파이프에 fsync()를 부르면 -EINVAL이 돌아오는 까닭입니다. NULL이 "지원하지 않음"이라는 뜻의 값으로 쓰입니다.
  • 객체가 자기 테이블을 들고 다닙니다(file->f_op). C++의 가상 함수 테이블 포인터를 손으로 쓴 것입니다.

같은 모양이 커널 전체에 있습니다. 스케줄링 클래스의 struct sched_class(4장), 인터럽트 컨트롤러의 struct irq_chip(10장), KVM의 struct kvm_x86_ops(23장), BPF 맵의 struct bpf_map_ops(24장)가 모두 이것입니다. v7.3의 fs/ 아래에만 file_operations 인스턴스가 280개 넘게 정의되어 있습니다.

비용. 간접 호출은 직접 호출보다 느립니다. CPU가 목적지를 예측해야 하고, 추측 실행 공격 방어책인 retpoline을 켜면 예측 자체를 못 하게 막기 때문입니다. 커널은 자주 도는 경로에서 두 가지로 줄입니다. 하나는 구현이 사실상 한두 개일 때 그것을 직접 호출로 먼저 시도하는 것입니다.

include/linux/indirect_call_wrapper.hv7.3
#define INDIRECT_CALL_1(f, f1, ...)                 \
    ({                              \
        typeof(f) __f1 = (f);                   \
        likely(__f1 == f1) ? f1(__VA_ARGS__) : __f1(__VA_ARGS__);   \
    })

IP 계층이 상위 프로토콜 핸들러를 부를 때 INDIRECT_CALL_2(ipprot->handler, tcp_v4_rcv, udp_rcv, skb)로 씁니다. 포인터가 TCP나 UDP 핸들러와 같으면 직접 호출이 됩니다. 다른 하나는 뒤에서 볼 스태틱 콜입니다.

25.2내장과 container_of#

문제. 공통 부분을 여러 타입이 나눠 가져야 합니다. C에는 상속이 없습니다.

커널의 답. 공통 구조체를 구체적인 구조체 안에 멤버로 넣습니다. 공통 코드는 안쪽 구조체의 포인터만 다루고, 구체적인 코드는 그 포인터에서 바깥 구조체를 되찾습니다. 되찾는 매크로가 container_of()입니다.

include/linux/container_of.hv7.3
#define container_of(ptr, type, member) ({              \
    static_assert(__same_type(*(ptr), typeof_member(type, member)) || \
              __same_type(*(ptr), void),            \
              "pointer type mismatch in container_of()");   \
    (type *)((void *)(ptr) - offsetof(type, member)); })

마지막 줄이 전부입니다. 멤버의 주소에서 그 멤버의 오프셋을 뺍니다. 오프셋은 컴파일할 때 정해지는 상수이므로 실행 비용은 뺄셈 한 번이고, 오프셋이 0이면 그마저 없습니다. 그 위의 static_assert는 ptr이 정말 그 멤버의 타입인지 컴파일할 때 확인합니다.

23장의 KVM이 좋은 예입니다. struct kvm_vcpu에는 struct preempt_notifier가 들어 있고, 스케줄러는 이 알림자의 포인터만 알고 콜백을 부릅니다. 콜백은 container_of(pn, struct kvm_vcpu, preempt_notifier)로 자기 vCPU를 찾습니다. 스케줄러는 KVM을 몰라도 됩니다.

상속과 다른 점이 있습니다. 한 구조체에 공통 구조체를 여러 개 넣을 수 있고, 맨 앞이 아니어도 됩니다. 다중 상속에 따르는 문제 없이 "이 객체는 대기 큐에 매달릴 수 있고, 타이머를 가지며, 참조 카운트된다"를 멤버 셋으로 표현합니다.

예전 자료와 다른 점

container_of()를 "타입 검사 없는 포인터 뺄셈"이라고 설명하는 자료가 많습니다. v7.3의 정의는 static_assert로 타입을 검사합니다. 그리고 헤더의 주석은 새 코드에 container_of() 대신 container_of_const()를 쓰라고 적고 있습니다. container_of()는 const 포인터를 넣어도 const가 떨어진 포인터를 돌려주기 때문입니다. container_of_const()는 _Generic으로 입력의 const 여부를 결과에 그대로 옮깁니다.

25.3침습형 리스트#

문제. 연결 리스트가 필요한 곳이 수천 군데인데 원소의 타입이 전부 다릅니다.

커널의 답. 리스트가 원소를 담지 않습니다. 원소가 리스트 노드를 담습니다. 노드는 포인터 둘뿐입니다(struct list_head { struct list_head *next, *prev; }). 리스트 코드는 노드끼리만 잇고, 원소는 container_of()로 되찾습니다.

include/linux/list.hv7.3
#define list_for_each_entry(pos, head, member)              \
    for (pos = list_first_entry(head, typeof(*pos), member);    \
         !list_entry_is_head(pos, head, member);            \
         pos = list_next_entry(pos, member))

list_first_entry()와 list_next_entry()가 안에서 container_of()를 부릅니다. typeof(*pos) 덕분에 원소 타입을 따로 적지 않아도 됩니다. 쓰는 쪽은 list_for_each_entry(p, &rq->scx.runnable_list, scx.runnable_node)처럼 "어느 멤버로 이어져 있는지"만 말합니다.

얻는 것은 셋입니다.

  • 할당이 없습니다. 리스트에 넣는 일이 실패할 수 없습니다. 메모리가 모자랄 때나 인터럽트 컨텍스트에서 중요합니다.
  • 한 객체가 여러 리스트에 동시에 들어갑니다. task_struct는 tasks, children, sibling, thread_node 같은 노드를 여럿 갖고 있고 각각 다른 리스트에 매달립니다.
  • 객체를 알면 O(1)로 뺍니다. 노드를 찾으려고 리스트를 훑을 필요가 없습니다.

같은 방식의 자료구조가 더 있습니다. 해시 버킷용 hlist_node, 레드-블랙 트리의 rb_node가 모두 원소 안에 넣는 노드입니다. 대가는 타입 안전성입니다. 리스트에 엉뚱한 타입을 넣어도 컴파일러가 모릅니다.

25.4수명: 참조 카운트#

문제. 객체를 여러 곳에서 가리킵니다. 가비지 컬렉터가 없으므로 마지막 사용자가 손을 뗀 순간을 직접 알아내 해제해야 합니다.

커널의 답. 다른 스레드가 찾을 수 있는 객체에는 참조 카운트를 답니다. 규약은 get과 put 한 쌍입니다. 포인터를 얻어 보관하려면 get으로 카운트를 올리고, 다 쓰면 put으로 내립니다. 0이 되면 put이 해제 함수를 부릅니다.

include/linux/kref.hv7.3
static inline int kref_put(struct kref *kref, void (*release)(struct kref *kref))
{
    if (refcount_dec_and_test(&kref->refcount)) {
        release(kref);
        return 1;
    }
    return 0;
}

struct kref는 객체 안에 넣는 멤버이고 release는 container_of()로 객체를 찾아 해제합니다. 앞의 두 패턴이 그대로 쓰였습니다.

카운터의 타입은 atomic_t가 아니라 refcount_t입니다. 참조 카운트 버그는 보안 문제로 이어지기 쉽습니다. 카운터가 넘쳐 0으로 돌아가면 쓰는 중인 객체가 해제됩니다. refcount_t는 넘치거나 0 아래로 내려가려 하면 값을 REFCOUNT_SATURATED(INT_MIN / 2)에 고정하고 경고를 냅니다. 그 객체는 영영 해제되지 않습니다. 메모리 누수를 택해 해제 후 사용을 피한 것입니다. 0인 카운터를 올리려는 시도에도 경고합니다.

이 위에 쌓인 것들입니다.

  • kobject는 kref에 이름, 부모, sysfs 디렉터리를 더한 것입니다. 장치 모델의 객체가 모두 이것을 품습니다.
  • RCU로 찾은 객체는 그 사이에 카운트가 0이 되었을 수 있으므로 refcount_inc_not_zero()로 올립니다(16장).
  • 드라이버는 devm_kzalloc() 같은 devm 함수로 자원을 장치에 묶어 둡니다. 장치가 떨어질 때 묶인 자원이 역순으로 해제됩니다.
설계 노트

코딩 스타일 문서는 락과 참조 카운트를 구분합니다. 락은 자료구조를 일관되게 유지하는 도구이고, 참조 카운트는 메모리를 관리하는 기법입니다. 보통 둘 다 필요하고 서로를 대신하지 못합니다. 문서의 문장을 옮기면, 다른 스레드가 찾을 수 있는 자료구조에 참조 카운트 없이 접근하고 있다면 거의 확실히 버그입니다. 수명 규칙을 타입(kref)과 함수 쌍(get/put)으로 고정해 두면, 리뷰어는 "이 포인터의 참조는 누가 쥐고 있는가"라는 한 가지 질문으로 코드를 읽을 수 있습니다.

25.5오류 처리: errno, ERR_PTR, goto#

문제. 예외가 없습니다. 실패를 호출자에게 알려야 하고, 실패한 지점까지 얻은 자원을 빠짐없이 되돌려야 합니다.

알리기. 정수를 돌려주는 함수는 성공하면 0, 실패하면 음수 errno(-ENOMEM, -EINVAL)를 돌려줍니다. 포인터를 돌려주는 함수는 오류 코드를 포인터에 실어 보냅니다. 주소 공간의 맨 위 4095바이트(MAX_ERRNO)에는 유효한 객체가 있을 수 없다는 점을 이용합니다. ERR_PTR(-ENOMEM)은 정수 -12를 포인터로 바꾼 것이고, 받는 쪽은 IS_ERR()로 그 범위인지 확인한 뒤 PTR_ERR()로 코드를 꺼냅니다(include/linux/err.h). NULL과 오류를 구분할 수 있고 반환값 하나로 끝납니다.

되돌리기. 자원을 얻은 순서의 반대로 해제하는 레이블을 함수 끝에 쌓고, 실패한 지점에서 알맞은 레이블로 goto합니다. 23장에서 본 vCPU 생성 함수의 끝부분입니다.

virt/kvm/kvm_main.cv7.3
kvm_put_xa_erase:
    mutex_unlock(&vcpu->mutex);
    kvm_put_kvm_no_destroy(kvm);
    xa_erase(&kvm->vcpu_array, vcpu->vcpu_idx);
unlock_vcpu_destroy:
    vcpu->vcpu_idx = -1;
    kvm_dirty_ring_free(&vcpu->dirty_ring);
arch_vcpu_destroy:
    kvm_arch_vcpu_destroy(vcpu);
vcpu_free_run_page:
    free_page((unsigned long)vcpu->run);
vcpu_free:
    kmem_cache_free(kvm_vcpu_cache, vcpu);
vcpu_decrement:
    kvm->created_vcpus--;
    return r;
}

위에서 아래로 떨어지며 실행되므로, 늦게 실패할수록 위쪽 레이블로 가서 더 많은 것을 되돌립니다. 레이블 이름은 그 자리에서 하는 일을 말합니다. 1장의 copy_process()에는 이런 레이블이 bad_fork_로 시작하는 것만 21개 있습니다. 이 모양은 단순하고 눈에 보이지만, 자원을 하나 추가할 때 레이블 순서와 모든 goto의 목적지를 다시 맞춰야 합니다. 누수와 이중 해제 버그가 여기서 나옵니다.

25.6범위 기반 정리: guard()와 자동 해제#

컴파일러에는 변수가 범위를 벗어날 때 지정한 함수를 부르게 하는 cleanup 속성이 있습니다. include/linux/cleanup.h는 이 속성으로 C에 소멸자를 들여왔습니다.

kernel/cgroup/namespace.cv7.3
static struct cgroup_namespace *alloc_cgroup_ns(void)
{
    struct cgroup_namespace *new_ns __free(kfree) = NULL;
    int ret;

    new_ns = kzalloc_obj(struct cgroup_namespace, GFP_KERNEL_ACCOUNT);
    if (!new_ns)
        return ERR_PTR(-ENOMEM);
    ret = ns_common_init(new_ns);
    if (ret)
        return ERR_PTR(ret);
    return no_free_ptr(new_ns);
}

읽을 곳은 세 군데입니다.

  • __free(kfree)가 붙은 변수는 함수의 어느 return에서든 범위를 벗어날 때 kfree()됩니다. 중간의 오류 반환에 정리 코드가 없습니다.
  • 성공해서 포인터를 내보낼 때는 no_free_ptr()로 감쌉니다. 변수를 NULL로 바꾸고 원래 값을 돌려주므로 자동 해제가 일어나지 않습니다. 소유권을 넘긴다는 표시입니다.
  • ERR_PTR()과 함께 씁니다. 두 패턴은 겹치지 않습니다.

락에는 guard()를 씁니다. 파일시스템을 등록하는 함수입니다.

fs/filesystems.cv7.3
int register_filesystem(struct file_system_type *fs)
{
    /* ... */
    if (!hlist_unhashed_lockless(&fs->list))
        return -EBUSY;

    guard(spinlock)(&file_systems_lock);
    if (find_filesystem(fs->name, strlen(fs->name)))
        return -EBUSY;
    hlist_add_tail_rcu(&fs->list, &file_systems);
    invalidate_filesystems_string();
    return 0;
}

guard(spinlock)(&lock)은 그 자리에서 락을 잡고, 함수가 어디서 끝나든 풉니다. 그 아래의 return -EBUSY에 spin_unlock()이 없어도 됩니다. 구간을 더 좁히려면 scoped_guard(spinlock, &lock) { ... } 블록을 씁니다. 이 함수에는 이 장의 다른 패턴도 들어 있습니다. fs->list는 구조체에 넣어 둔 hlist_node이고, 넣는 연산은 RCU 판입니다.

어떤 타입에 어떤 정리 함수를 쓸지는 한 줄로 등록합니다. kfree는 include/linux/slab.h에 DEFINE_FREE(kfree, void *, if (!IS_ERR_OR_NULL(_T)) kfree(_T))로, 뮤텍스 가드는 include/linux/mutex.h에 DEFINE_LOCK_GUARD_1(mutex, struct mutex, mutex_lock(_T->lock), mutex_unlock(_T->lock))로 정의되어 있습니다. kfree 쪽 조건이 눈에 띕니다. 변수에 ERR_PTR() 값이 들어 있으면 해제하지 않습니다. 가드의 바탕은 생성자와 소멸자를 한 쌍으로 묶는 DEFINE_CLASS()입니다.

v7.3의 kernel/ 디렉터리에서 guard(와 scoped_guard(는 750번쯤, goto는 4,200번쯤 나옵니다. 전환은 진행 중입니다. cleanup.h의 주석은 한 함수 안에서 goto 정리와 범위 기반 정리를 섞지 말라고 적고 있습니다. goto가 범위를 넘나들면 어떤 정리가 실행될지 헷갈리기 때문입니다. 그래도 앞에서 본 vCPU 생성 함수처럼 락은 guard(mutex)로, 나머지는 레이블로 처리한 과도기의 코드가 남아 있습니다.

25.7설정: Kconfig에서 죽은 코드 제거까지#

문제. 커널에는 설정 옵션이 수천 개 있습니다. 옵션마다 #ifdef로 코드를 감싸면 읽을 수 없게 되고, 꺼진 쪽 코드는 컴파일되지 않으니 깨져도 모릅니다.

커널의 답. #ifdef를 .c 파일에서 몰아내 헤더에 가둡니다. 코딩 스타일 문서의 규칙입니다. 방법은 둘입니다.

첫째, 기능이 꺼졌을 때를 위한 빈 인라인 함수를 헤더에 둡니다.

include/linux/sched/ext.hv7.3
#else   /* !CONFIG_SCHED_CLASS_EXT */

static inline void sched_ext_dead(struct task_struct *p) {}
static inline void print_scx_info(const char *log_lvl, struct task_struct *p) {}
static inline void scx_softlockup(u32 dur_s) {}
static inline bool scx_hardlockup(int cpu) { return false; }
static inline bool scx_rcu_cpu_stall(const struct cpumask *stalled_mask) { return false; }

#endif  /* CONFIG_SCHED_CLASS_EXT */

호출하는 .c 파일은 sched_ext가 켜졌는지 묻지 않고 sched_ext_dead(p)를 부릅니다. 꺼져 있으면 빈 함수가 인라인되어 사라집니다.

둘째, 조건을 전처리기가 아니라 C의 if로 씁니다. IS_ENABLED(CONFIG_FOO)는 옵션이 켜져 있으면 1, 아니면 0이 되는 상수식입니다. 6장에서 본 if (IS_ENABLED(CONFIG_DEBUG_ENTRY))가 이 꼴입니다. 컴파일러는 if (0)의 본문을 타입 검사까지 한 뒤 버립니다. 꺼진 설정의 코드도 문법과 타입이 맞는지 항상 확인된다는 점이 #ifdef와 다릅니다.

25.8빠른 경로를 위해 코드를 고쳐 쓰기#

문제. 드물게 바뀌는 조건을 자주 도는 경로에서 매번 검사하기가 아깝습니다.

커널은 단계별로 대응합니다. 가장 가벼운 것은 likely()와 unlikely()입니다. 컴파일러에 어느 쪽이 흔한지 알려 흔한 쪽을 곧게 배치하게 합니다. 분기는 남습니다.

분기 자체를 없애는 것이 스태틱 키(static key)입니다. if (static_branch_unlikely(&key))는 기계어에서 조건 분기가 아닙니다. x86의 구현입니다.

arch/x86/include/asm/jump_label.hv7.3
static __always_inline bool arch_static_branch(struct static_key * const key, const bool branch)
{
    asm goto(ARCH_STATIC_BRANCH_ASM("%c0 + %c1", "%l[l_yes]")
        : :  "i" (key), "i" (branch) : : l_yes);

    return false;
l_yes:
    return true;
}

ARCH_STATIC_BRANCH_ASM은 그 자리에 5바이트 NOP을 놓고, __jump_table 섹션에 "이 주소, 건너뛸 목적지, 이 키"라는 항목을 남깁니다. 평소에는 NOP을 지나 return false로 갑니다. 누군가 static_branch_enable(&key)를 부르면 커널이 표를 뒤져 그 키를 쓰는 모든 자리의 NOP을 jmp l_yes로 고쳐 씁니다.

24장의 BPF 프로그램 호출부가 실행 시간 통계를 낼지 묻는 자리, sched_ext가 켜져 있는지 묻는 자리가 스태틱 키입니다. 꺼져 있을 때의 비용은 NOP 하나입니다. 대신 켜고 끄는 일은 모든 CPU를 맞춰 세워야 하는 느린 작업입니다.

같은 발상을 간접 호출에 적용한 것이 스태틱 콜(static call)입니다. 6장에서 선점 모델을 고를 때 보았습니다. KVM은 ops 테이블 전체를 스태틱 콜로 바꿉니다.

arch/x86/kvm/x86.cv7.3
static inline void kvm_ops_update(struct kvm_x86_init_ops *ops)
{
    memcpy(&kvm_x86_ops, ops->runtime_ops, sizeof(kvm_x86_ops));

#define __KVM_X86_OP(func) \
    static_call_update(kvm_x86_##func, kvm_x86_ops.func);
#define KVM_X86_OP(func) \
    WARN_ON(!kvm_x86_ops.func); __KVM_X86_OP(func)
#define KVM_X86_OP_OPTIONAL __KVM_X86_OP
/* ... */
#include <asm/kvm-x86-ops.h>
#undef __KVM_X86_OP
    /* ... */
}

모듈이 올라올 때 테이블의 함수 포인터 하나하나에 대해 static_call_update()를 불러 호출 명령어의 목적지를 고칩니다. 그 뒤 kvm_x86_call(vcpu_run)(...)은 인텔이면 vmx_vcpu_run()으로 가는 직접 호출입니다. ops 테이블의 유연함을 유지하면서 간접 호출의 비용만 없앴습니다.

이 계열에는 CPU 기능에 따라 부팅 때 명령어를 바꿔 넣는 alternatives(23장의 vmenter.S에 있던 ALTERNATIVE), 락 없이 쓰는 CPU별 변수, 거짓 공유를 막는 캐시 라인 정렬(13장)이 더 있습니다.

설계 노트

설정 가능성과 속도는 보통 맞바꿉니다. 실행 중에 바꿀 수 있게 하려면 변수를 읽고 분기해야 하기 때문입니다. 커널은 "바꾸는 일은 드물고 읽는 일은 잦다"는 비대칭을 이용해 비용을 바꾸는 쪽으로 몰았습니다. 읽는 쪽은 아무것도 읽지 않고, 바꾸는 쪽이 코드를 고쳐 씁니다. RCU가 자료구조에서 한 일을 코드에 대해 한 것입니다. 드문 쪽에 비용을 몰 수 있는지 따져 보는 것은 어디서나 통하는 질문입니다.

25.9매크로: 제네릭과 코드 생성#

C에는 템플릿이 없으므로 타입에 무관한 코드는 매크로로 씁니다. 앞에서 본 list_for_each_entry()가 그 예이고, typeof가 타입 인자 노릇을 합니다. 잘 만든 매크로는 함수보다 더 많은 검사를 합니다. min()의 핵심부입니다.

include/linux/minmax.hv7.3
#define __careful_cmp_once(op, x, y, ux, uy) ({     \
    auto ux = (x); auto uy = (y);           \
    BUILD_BUG_ON_MSG(!__types_ok(ux, uy),       \
        #op"("#x", "#y") signedness error");    \
    __cmp(op, ux, uy); })

인자를 임시 변수에 한 번만 담아 min(i++, j) 같은 호출에서 부작용이 두 번 일어나지 않게 하고, 부호 있는 값과 없는 값을 섞어 비교하면 빌드를 실패시킵니다. -1과 1U를 비교하면 -1이 큰 양수로 바뀌는 C의 함정을 컴파일할 때 잡는 것입니다. auto는 커널이 __auto_type으로 정의해 둔 것입니다(include/linux/compiler_types.h).

예전 자료와 다른 점

옛 자료의 min()은 (void)(&_x == &_y)라는 줄로 타입을 검사합니다. 두 인자의 타입이 정확히 같지 않으면 "서로 다른 포인터 타입의 비교" 경고가 나는 것을 이용한 요령이었습니다. int와 long처럼 안전한 조합도 걸려서 min_t()로 강제 변환하는 코드가 늘었고, 그 변환이 오히려 값을 자르는 버그를 만들기도 했습니다. v7.3의 min()은 타입이 달라도 부호만 맞으면 통과시킵니다.

자료구조의 API도 같은 방식입니다. 해시 테이블의 hash_for_each_possible(), xarray의 xa_for_each()가 모두 원소 타입을 인자로 받지 않는 순회 매크로입니다.

매크로의 두 번째 쓰임은 코드 생성입니다. 한 줄의 선언에서 여러 조각을 만들어 냅니다.

  • SYSCALL_DEFINE3(read, ...)는 함수 본체와 인자 변환 래퍼, 추적용 메타데이터를 만듭니다(19장).
  • DEFINE_PER_CPU(type, name)은 변수를 CPU별 데이터 섹션에 놓습니다.
  • TRACE_EVENT()는 추적점의 구조체, 기록 함수, 출력 형식을 한꺼번에 만듭니다.
  • 바로 위 KVM 코드의 #include <asm/kvm-x86-ops.h>는 목록 파일을 매크로 정의를 바꿔 가며 여러 번 포함하는 기법입니다. 그 헤더에는 KVM_X86_OP(vcpu_run) 같은 줄만 있고, 포함하는 쪽이 KVM_X86_OP를 어떻게 정의하느냐에 따라 선언이 되기도, 갱신 코드가 되기도 합니다. 연산을 추가할 때 고칠 곳이 한 줄입니다.

25.10등록, initcall, 링커 섹션#

문제. 코어는 드라이버를 몰라야 합니다. 그런데 부팅할 때 누군가는 모든 드라이버의 초기화 함수를 불러야 합니다.

등록. 코어가 register_*() 함수를 내놓고 구현이 자기 ops 테이블을 넘깁니다. 앞에서 본 register_filesystem()이 그 꼴입니다. ext4는 초기화 함수에서 register_filesystem(&ext4_fs_type)을 부릅니다. 의존의 방향이 구현에서 코어로만 향합니다. 사건을 알리는 쪽도 같습니다. 알림 사슬(notifier chain)은 콜백을 담은 struct notifier_block을 리스트에 걸어 두었다가 사건이 나면 차례로 부릅니다.

initcall. 그 초기화 함수는 누가 부를까요. 아무도 이름으로 부르지 않습니다. module_init(ext4_init_fs)는 함수 포인터 하나를 .initcall6.init 같은 이름의 링커 섹션에 넣습니다. 링커가 모든 오브젝트 파일의 같은 섹션을 이어 붙이면 함수 포인터 배열이 되고, 부팅 코드는 그 배열을 처음부터 끝까지 돕니다. 단계는 core_initcall(1)부터 late_initcall(7)까지이고 module_init은 6단계입니다. 같은 소스를 모듈로 빌드하면 module_init은 모듈 로더가 찾는 init_module의 별칭이 됩니다.

링커가 표를 모아 주는 이 기법은 곳곳에 쓰입니다. 스태틱 키의 __jump_table이 그랬고, 스케줄링 클래스는 DEFINE_SCHED_CLASS가 클래스마다 다른 섹션에 넣은 것을 링커 스크립트가 우선순위 순서로 늘어놓습니다. 그래서 다음 클래스로 가는 일이 class++입니다. __init이 붙은 함수는 .init.text 섹션에 모였다가 부팅이 끝나면 메모리째 해제됩니다.

내보내기. 모듈이 쓸 수 있는 심벌은 EXPORT_SYMBOL_GPL()로 표시한 것뿐입니다. 표시하지 않은 함수는 static이 아니어도 모듈에서 보이지 않습니다. 심벌 네임스페이스(EXPORT_SYMBOL_NS_GPL)로 범위를 더 좁힐 수 있고, v7.3에는 특정 모듈에만 여는 EXPORT_SYMBOL_FOR_MODULES()도 있습니다. 무엇이 인터페이스인지를 코드에 적는 것입니다(26장).

25.11도구가 읽는 주석#

문제. "이 포인터는 유저 공간 주소다", "이 함수는 락을 쥔 채 불러야 한다" 같은 규칙은 C의 타입으로 표현되지 않습니다. 주석으로 적으면 아무도 검사하지 않습니다.

커널의 답. 규칙을 컴파일러와 정적 분석기가 읽을 수 있는 속성으로 적습니다.

표시 뜻 검사하는 도구
__user, __iomem, __rcu 직접 역참조하면 안 되는 종류의 포인터 sparse
__must_check 반환값을 무시하면 안 된다 컴파일러 경고
__acquires(l), __releases(l), __must_hold(l) 함수가 락을 잡는다, 푼다, 쥔 채 불려야 한다 sparse, Clang
__guarded_by(l) 이 멤버는 그 락을 쥐고 접근한다 Clang
__counted_by(n) 이 가변 길이 배열의 원소 수는 멤버 n에 있다 컴파일러의 경계 검사

vfs_read()의 선언에서 버퍼는 char __user *buf입니다. 커널 코드가 *buf로 직접 읽으면 sparse가 경고합니다. copy_from_user()를 거쳐야 합니다(19장). ERR_PTR()의 선언에 붙은 __must_check는 오류 포인터를 버리는 호출을 잡습니다.

예전 자료와 다른 점

__acquires()와 __releases()를 "sparse만 읽는 표시"라고 설명한 자료가 많습니다. v7.0부터는 Clang의 컨텍스트 분석도 이 표시를 읽습니다(include/linux/compiler-context-analysis.h). CONFIG_WARN_CONTEXT_ANALYSIS를 켜고 대상 디렉터리의 Makefile에서 분석을 켜면, 락을 쥐지 않고 __guarded_by 멤버를 건드리는 코드나 __must_hold 함수를 락 없이 부르는 코드가 컴파일 경고로 나옵니다. 6장의 __raw_spin_lock() 선언에 있던 __acquires(lock) __no_context_analysis가 이 체계의 일부입니다.

품질 도구 전체는 27장에서 다룹니다. 여기서 볼 것은 방향입니다. 사람이 기억해야 하던 불변식을 코드에 적어 기계가 검사하게 옮겨 갑니다.

25.12코딩 스타일, 그리고 Rust#

Documentation/process/coding-style.rst는 짧은 문서입니다. 뼈대는 이렇습니다.

  • 들여쓰기는 탭이고 탭은 8칸입니다. 세 단계 넘게 들여쓰게 되면 함수를 고치라는 신호로 봅니다.
  • 함수는 짧게, 한 가지 일만 합니다. 지역 변수는 5–10개를 넘기지 않습니다.
  • 구조체와 포인터에 typedef를 쓰지 않습니다. struct task_struct *라고 써야 그것이 구조체의 포인터임이 보입니다.
  • 주석은 코드가 무엇을 하는지 적습니다. 어떻게는 코드가 말합니다.

취향처럼 보이지만 목적은 하나입니다. 수천 명이 쓴 코드가 한 사람이 쓴 것처럼 읽혀야 리뷰가 됩니다. 이 장의 패턴들도 같은 구실을 합니다. ops 테이블, 내장 노드, get/put을 한 번 익히면 처음 보는 서브시스템에서도 무엇을 찾아야 할지 압니다.

커널의 Rust 코드는 이 관례들을 언어 기능으로 옮깁니다(27장).

samples/rust/rust_minimal.rsv7.3
impl kernel::Module for RustMinimal {
    fn init(_module: &'static ThisModule) -> Result<Self> {
        pr_info!("Rust minimal sample (init)\n");
        // ...
        let mut numbers = KVec::new();
        numbers.push(72, GFP_KERNEL)?;
        numbers.push(108, GFP_KERNEL)?;
        numbers.push(200, GFP_KERNEL)?;

        Ok(RustMinimal { numbers })
    }
}

impl Drop for RustMinimal {
    fn drop(&mut self) {
        pr_info!("My numbers are {:?}\n", self.numbers);
        pr_info!("Rust minimal sample (exit)\n");
    }
}
C의 관례 Rust에서
ops 테이블 트레이트. 위의 kernel::Module, #[vtable]이 붙은 MiscDevice
음수 errno, ERR_PTR Result. ?가 오류면 바로 반환합니다.
goto 사다리, __free() Drop. 범위를 벗어나면 소멸자가 불립니다.
guard(mutex) 락을 잡으면 나오는 Guard. 버려질 때 풉니다.
kref, get/put Arc. 안에 refcount_t가 들어 있습니다.

위 코드의 push(...)?는 할당에 실패하면 그 자리에서 오류를 들고 함수를 떠납니다. 그때 numbers는 Drop으로 정리됩니다. C에서 관례와 리뷰로 지키던 것을 컴파일러가 강제한다는 점이 다릅니다.

정리#

  • 인터페이스는 함수 포인터 구조체로, 구현은 그 const 인스턴스로 표현합니다. 없는 연산은 NULL입니다.
  • 공통 부분은 구조체 안에 멤버로 넣고 container_of()로 바깥을 되찾습니다. 리스트 노드도 원소 안에 넣어, 할당 없이 여러 리스트에 동시에 매답니다.
  • 공유되는 객체의 수명은 참조 카운트와 get/put 규약이 정합니다. refcount_t는 넘치면 값을 고정해 해제 후 사용 대신 누수를 택합니다.
  • 실패는 음수 errno나 ERR_PTR()로 알립니다. 되돌리기는 goto 사다리에서 guard()와 __free()로 옮겨 가는 중입니다.
  • 설정은 헤더의 빈 인라인 함수와 IS_ENABLED()로 다뤄, .c 파일에 #ifdef를 두지 않고 컴파일러가 죽은 코드를 지우게 합니다.
  • 자주 도는 경로의 분기와 간접 호출은 스태틱 키와 스태틱 콜이 코드를 고쳐 써서 없앱니다.
  • 코어와 구현은 등록 함수, initcall, 링커 섹션으로 이어져 코어가 구현의 이름을 모릅니다.
  • 타입으로 못 적는 규칙은 __user, __must_check, __acquires 같은 속성으로 적어 도구가 검사합니다.

확인 문제#

struct file_operations에 새 연산 foo를 추가했습니다. 기존 파일시스템 수십 개의 테이블은 고치지 않았습니다. 그래도 빌드되고 동작하는 이유와, 호출부가 지켜야 할 것을 설명해 보세요.

답 보기

각 파일시스템의 테이블은 지정 초기화(.read_iter = ...)로 쓰여 있어서, 언급하지 않은 멤버 foo는 0, 곧 NULL이 됩니다. 구조체 정의만 바뀌고 인스턴스들은 다시 컴파일될 뿐입니다. 호출부는 vfs_fsync_range()가 file->f_op->fsync를 확인하듯 foo가 NULL인지 먼저 확인하고, NULL이면 기본 동작을 하거나 "지원하지 않음" 오류를 돌려줘야 합니다.

list_for_each_entry(p, &head, node)가 원소의 타입을 인자로 받지 않는데도 p에 올바른 구조체 포인터가 들어가는 과정을 설명해 보세요.

답 보기

매크로가 typeof(*pos)로 p가 가리키는 타입을 얻습니다. list_first_entry()와 list_next_entry()는 리스트 노드의 포인터와 이 타입, 멤버 이름 node를 container_of()에 넘기고, container_of()는 노드 주소에서 offsetof(타입, node)를 빼 바깥 구조체의 주소를 계산합니다. 오프셋은 컴파일 때 상수이므로 실행 비용은 뺄셈 한 번입니다.

refcount_t가 넘칠 때 값을 REFCOUNT_SATURATED에 고정하는 설계는 어떤 버그를 어떤 버그로 바꾸는 것입니까? 왜 그쪽이 낫습니까?

답 보기

넘친 카운터가 0 근처로 돌아가면 아직 쓰는 객체가 해제되어 해제 후 사용이 됩니다. 공격자가 그 메모리를 다른 내용으로 채우면 권한 상승으로 이어질 수 있습니다. 고정된 카운터는 다시 0이 되지 않으므로 객체가 영영 해제되지 않습니다. 메모리 누수입니다. 누수는 자원을 낭비할 뿐 메모리 안전을 깨지 않으므로 훨씬 덜 위험합니다. 경고도 함께 나오므로 버그가 드러납니다.

alloc_cgroup_ns()에서 return no_free_ptr(new_ns);를 return new_ns;로 바꾸면 무슨 일이 일어납니까?

답 보기

new_ns에는 __free(kfree)가 붙어 있어서 함수가 반환할 때 변수가 범위를 벗어나며 kfree(new_ns)가 실행됩니다. 호출자는 이미 해제된 메모리의 포인터를 받게 되어 해제 후 사용이 됩니다. no_free_ptr()는 변수를 NULL로 바꾸고 원래 값을 돌려주므로, 범위를 벗어날 때의 정리 함수가 NULL을 보고 아무것도 하지 않습니다.

전역 변수를 읽어 if로 가르는 것과 스태틱 키는 기계어에서 어떻게 다릅니까? 스태틱 키가 맞지 않는 경우는 언제입니까?

답 보기

전역 변수 방식은 실행할 때마다 메모리를 읽고 비교해 조건 분기합니다. 스태틱 키는 그 자리에 NOP 하나(꺼짐)나 무조건 jmp 하나(켜짐)만 있고 메모리를 읽지 않습니다. 상태를 바꿀 때 커널이 __jump_table을 보고 그 키를 쓰는 모든 자리의 명령어를 고쳐 씁니다. 이 패치는 모든 CPU와 맞춰야 하는 느린 작업이므로, 값이 자주 바뀌는 조건이나 객체마다 값이 다른 조건에는 맞지 않습니다.

용어#

ops 테이블
함수 포인터를 모은 구조체. 인터페이스 구실을 하며 구현마다 인스턴스를 하나씩 둔다.
container_of
멤버의 주소에서 그 멤버의 오프셋을 빼 바깥 구조체의 주소를 구하는 매크로.
침습형 리스트intrusive list
리스트 노드를 원소 구조체 안에 멤버로 넣는 방식의 리스트.
refcount_t
참조 카운트 전용 타입. 넘치거나 0 아래로 가려 하면 값을 고정하고 경고한다.
kref
refcount_t를 감싼 구조체. 0이 되면 넘겨받은 해제 함수를 부르는 kref_put()과 함께 쓴다.
ERR_PTR
음수 오류 코드를 포인터 값에 실어 돌려주는 방식. IS_ERR()로 확인하고 PTR_ERR()로 꺼낸다.
guard
락을 잡고, 변수가 범위를 벗어날 때 자동으로 푸는 범위 기반 정리 매크로.
IS_ENABLED
Kconfig 옵션이 켜졌는지를 컴파일 시점 상수 1이나 0으로 바꾸는 매크로.
스태틱 키static key
분기 자리의 명령어를 NOP과 jmp 사이에서 고쳐 써서, 조건 검사 없이 경로를 켜고 끄는 기법.
initcall
링커 섹션에 모아 둔 초기화 함수. 부팅 코드가 단계 순서대로 부른다.
알림 사슬notifier chain
사건이 나면 차례로 부를 콜백을 리스트로 걸어 두는 구조.
