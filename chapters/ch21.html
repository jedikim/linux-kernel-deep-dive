블록 계층과 io_uring

bio에서 blk-mq까지, 그리고 시스템 콜을 줄이는 I/O

Linux v7.3 기준약 55분
읽는 소스include/linux/blk_types.hblock/blk-mq.cdrivers/nvme/host/pci.cblock/elevator.cinclude/uapi/linux/io_uring.hinclude/linux/io_uring_types.hio_uring/io_uring.c

회전하는 디스크 시절에는 I/O 한 건에 밀리초가 걸렸습니다. 커널이 그 사이에 쓰는 마이크로초는 눈에 띄지 않았습니다. 플래시 저장 장치가 기계 부품 없이 수많은 요청을 동시에 처리하게 되자 사정이 뒤집혔습니다. 병목이 장치에서 운영체제로 옮겨 왔습니다. 락 하나를 두고 모든 CPU가 다투는 요청 큐와, 요청마다 한 번씩 넘어야 하는 시스템 콜 경계가 문제가 되었습니다. 이 장은 그 두 문제에 대한 답인 blk-mq와 io_uring을 읽습니다.

이 장에서 답하는 질문
  • 파일시스템이 블록 계층에 건네는 bio는 무엇을 담고 있는가?
  • blk-mq는 왜 큐를 두 단으로 나누는가? 요청은 언제 큐를 거치지 않고 드라이버로 바로 가는가?
  • I/O가 끝났다는 사실은 어느 CPU의 어떤 컨텍스트에서 처리되는가?
  • read(), POSIX AIO, Linux AIO, io_uring은 무엇이 다른가?
  • io_uring의 두 링에서 head와 tail은 각각 누가 쓰는가? 락 없이 성립하는 까닭은 무엇인가?
  • io_uring에 제출한 요청은 누가, 어떤 컨텍스트에서 실행하는가?

21.1블록 계층의 자리와 bio#

블록 계층(block layer)은 파일시스템과 저장 장치 드라이버 사이에 있습니다. 위에서는 "이 장치의 이 섹터부터 이 메모리 내용을 읽어라, 써라"는 요청을 받고, 아래로는 장치가 받아들일 수 있는 모양과 속도로 내려보냅니다.

요청의 단위가 struct bio입니다.

include/linux/blk_types.hv7.3
struct bio {
    struct bio      *bi_next;   /* request queue link */
    struct block_device *bi_bdev;
    blk_opf_t       bi_opf;     /* bottom bits REQ_OP, top bits
                         * req_flags.
                         */
    /* ... */
    blk_status_t        bi_status;
    /* ... */
    /* The actual vec list, preserved by bio_reset() */
    struct bio_vec      *bi_io_vec;
    struct bvec_iter    bi_iter;
    /* ... */
    bio_end_io_t        *bi_end_io;
    void            *bi_private;
    /* ... */
};

읽을 곳은 네 군데입니다.

  • bi_bdev와 bi_iter.bi_sector가 어디에를 정합니다. 섹터는 장치의 실제 블록 크기와 상관없이 512바이트 단위입니다.
  • bi_opf가 무엇을을 정합니다. 아래 비트는 연산(REQ_OP_READ, REQ_OP_WRITE, REQ_OP_FLUSH, REQ_OP_DISCARD), 위 비트는 REQ_SYNC나 REQ_NOWAIT 같은 플래그입니다.
  • bi_io_vec가 어느 메모리와를 정합니다. bio_vec의 배열이고, 원소 하나는 (페이지, 길이, 오프셋)으로 연속된 메모리 한 조각을 가리킵니다. 대개 페이지 캐시의 폴리오입니다.
  • bi_end_io는 완료 콜백입니다. 블록 계층은 I/O가 끝나면 이 함수를 부를 뿐, bio를 누가 왜 만들었는지 모릅니다.

메모리 쪽은 흩어져 있어도 되지만 장치 쪽은 연속이어야 합니다. 파일의 연속된 256KB가 디스크에서도 연속이면 bio 하나로 끝나고, 디스크에서 둘로 갈라져 있으면 bio 둘이 됩니다. 20장의 iomap이 "연속 구간"으로 답하는 것이 바로 bio를 크게 만들기 위해서입니다.

파일시스템은 bio를 채워 submit_bio()를 부릅니다. 이 함수는 완료를 기다리지 않고 돌아옵니다. 완료는 나중에 bi_end_io로 알려집니다.

21.2blk-mq: 소프트웨어 큐와 하드웨어 큐#

submit_bio()는 blk_mq_submit_bio()에 닿습니다. 여기서 bio는 struct request가 됩니다. request는 드라이버에 건네는 단위이고, 섹터가 이어지는 bio 여러 개를 하나로 묶을 수 있습니다.

request에는 태그(tag)가 붙습니다. 하드웨어 큐마다 깊이만큼의 정수가 있고, request는 그 가운데 빈 번호 하나를 받아야 장치로 갈 수 있습니다. 태그는 "장치에 동시에 걸려 있는 요청 수"를 제한하는 장치이자, 완료가 돌아왔을 때 request를 찾는 인덱스입니다. NVMe 드라이버는 태그를 명령 ID에 넣어 보내고, 완료 항목에 적혀 돌아온 ID로 blk_mq_tag_to_rq()를 불러 request를 꺼냅니다. 빈 태그 찾기는 여러 CPU가 캐시 라인을 덜 다투도록 만든 비트맵 sbitmap이 맡습니다.

blk-mq의 큐는 두 단입니다.

  • 소프트웨어 큐(struct blk_mq_ctx): CPU마다 하나. 스케줄러가 있거나 병합을 시도할 때 request가 잠시 머뭅니다.
  • 하드웨어 큐(struct blk_mq_hw_ctx): 장치가 가진 큐마다 하나. 드라이버의 queue_rq()가 여기서 request를 받습니다.

NVMe는 큐를 CPU 수만큼 만들려고 합니다. 그러면 CPU마다 자기 하드웨어 큐가 있고, 제출 경로에서 다른 CPU와 공유하는 락이 없습니다. 큐가 CPU보다 적으면 blk_mq_map_queues()가 CPU들을 고르게 묶어 큐에 나눠 줍니다.

request를 만든 다음의 갈림길은 blk_mq_submit_bio()의 끝에 있습니다.

block/blk-mq.cv7.3
    if (plug) {
        blk_add_rq_to_plug(plug, rq);
        return;
    }

    hctx = rq->mq_hctx;
    if ((rq->rq_flags & RQF_USE_SCHED) ||
        (hctx->dispatch_busy && (q->nr_hw_queues == 1 || !is_sync))) {
        blk_mq_insert_request(rq, 0);
        blk_mq_run_hw_queue(hctx, true);
    } else {
        blk_mq_run_dispatch_ops(q, blk_mq_try_issue_directly(hctx, rq));
    }
    return;

세 갈래입니다.

  • 플러그에 모은다. 플러그(plug)는 태스크가 "곧 I/O를 여러 건 낼 것"이라고 알리는 표시입니다. blk_start_plug()와 blk_finish_plug() 사이에 낸 request는 current->plug에 쌓였다가 한꺼번에 내려갑니다. 미리 읽기와 writeback이 이렇게 합니다. 모아 두면 이웃한 것끼리 병합할 기회가 생기고, 드라이버에 묶음으로 넘길 수 있습니다. 플러그를 쥔 채 잠들면 schedule()이 대신 비워 줍니다.
  • 큐에 넣는다. I/O 스케줄러가 붙어 있거나 장치가 바쁘면 큐에 넣고 blk_mq_run_hw_queue()로 큐를 돌립니다.
  • 바로 낸다. 그 밖에는 blk_mq_try_issue_directly()가 큐를 거치지 않고 드라이버의 queue_rq()를 곧장 부릅니다. 스케줄러 없는 NVMe에서는 이 길이 보통입니다.

NVMe의 queue_rq()입니다.

drivers/nvme/host/pci.cv7.3
static blk_status_t nvme_queue_rq(struct blk_mq_hw_ctx *hctx,
             const struct blk_mq_queue_data *bd)
{
    struct nvme_queue *nvmeq = hctx->driver_data;
    /* ... */
    ret = nvme_prep_rq(req);
    if (unlikely(ret))
        return ret;
    spin_lock(&nvmeq->sq_lock);
    nvme_sq_copy_cmd(nvmeq, &iod->cmd);
    nvme_write_sq_db(nvmeq, bd->last);
    spin_unlock(&nvmeq->sq_lock);
    return BLK_STS_OK;
}

nvme_prep_rq()가 request를 NVMe 명령으로 바꾸고 데이터 버퍼를 DMA 매핑합니다. 그다음 명령을 장치와 공유하는 제출 큐 메모리에 복사하고, 도어벨 레지스터에 새 tail을 씁니다. 장치는 도어벨을 보고 명령을 가져갑니다. bd->last가 거짓이면 뒤에 request가 더 온다는 뜻이므로 도어벨 쓰기를 미룹니다. MMIO 쓰기 한 번도 아끼는 것입니다. sq_lock은 이 큐 하나만의 락이므로 큐가 CPU마다 있으면 경합이 없습니다.

예전 자료와 다른 점

오래된 블록 계층 설명에는 장치마다 요청 큐 하나와 queue_lock 하나가 있고, 드라이버가 request_fn을 등록하며, I/O 스케줄러로 CFQ·deadline·noop 가운데 하나를 고른다고 나옵니다. 그 단일 큐 경로는 5.0에서 코드째로 사라졌습니다. blk-mq는 3.13에 들어와 몇 해 동안 옛 경로와 나란히 있었고, 남은 드라이버가 모두 옮겨 온 뒤 옛 경로와 그 스케줄러들이 지워졌습니다. v7.3에는 blk-mq만 있고, bio에 직접 있던 bi_sector·bi_size도 bi_iter 안으로 들어가 있습니다.

설계 노트

단일 큐가 버티지 못한 까닭은 락이 느려서가 아니라 공유해서입니다. 모든 CPU가 같은 큐의 같은 캐시 라인에 쓰면 그 캐시 라인이 CPU 사이를 오가는 비용이 I/O 한 건의 비용보다 커집니다. blk-mq는 자료구조를 CPU별로 쪼개 공유 자체를 없앴습니다. 소프트웨어 큐가 CPU마다 있고, 하드웨어도 큐를 여럿 주므로 끝까지 한 번도 합쳐지지 않습니다. 락을 더 빠르게 만드는 것보다 락이 지키는 데이터를 나누는 쪽이 멀리 간다는 것은 13장의 CPU별 데이터와 같은 결론입니다.

21.3I/O 스케줄러#

소프트웨어 큐와 하드웨어 큐 사이에 I/O 스케줄러를 끼울 수 있습니다. request의 순서를 바꾸거나 잠시 붙들어 두는 층입니다. v7.3의 block/Kconfig.iosched에 있는 것은 셋이고, 아무것도 끼우지 않는 none까지 선택지는 넷입니다.

스케줄러 하는 일 맞는 곳
none 순서를 바꾸지 않습니다. 큐가 여럿인 NVMe
mq-deadline 섹터 순으로 정렬하되, request마다 기한을 두어 굶지 않게 합니다. 하드 디스크, SATA SSD
kyber 읽기와 동기 쓰기의 목표 지연 시간에 맞춰 큐 깊이를 스스로 조절합니다. 빠른 장치에서 지연 시간을 관리할 때
bfq 프로세스별 가중치대로 장치의 처리량을 나눕니다. cgroup의 io 가중치를 따릅니다. 느린 장치, 데스크톱의 반응성

기본값을 고르는 코드는 짧습니다.

block/elevator.cv7.3
void elevator_set_default(struct request_queue *q)
{
    struct elv_change_ctx ctx = {
        .name = "mq-deadline",
        .no_uevent = true,
    };
    /* ... */
    /*
     * For single queue devices, default to using mq-deadline. If we
     * have multiple queues or mq-deadline is not available, default
     * to "none".
     */
    /* ... */
    if ((q->nr_hw_queues == 1 ||
            blk_mq_is_shared_tags(q->tag_set->flags))) {
        err = elevator_change(q, &ctx);
        /* ... */
    }
    /* ... */
}

하드웨어 큐가 하나면 mq-deadline, 여럿이면 none입니다. 하드 디스크는 헤드가 움직이는 거리가 곧 시간이므로 섹터 순으로 정렬하면 이득이 큽니다. NVMe에는 헤드가 없습니다. 정렬해서 얻는 것이 없고, 정렬하려고 request를 한 곳에 모으면 CPU별로 쪼개 둔 구조에 공유 지점이 다시 생깁니다.

직접 확인하기

장치의 큐 구성을 봅니다. 장치 이름은 lsblk로 확인해 바꿉니다.

터미널
$ cat /sys/block/nvme0n1/queue/scheduler
[none] mq-deadline kyber bfq
$ cat /sys/block/nvme0n1/queue/nr_requests
1023
$ ls /sys/block/nvme0n1/mq/
0  1  2  3  4  5  6  7
$ cat /sys/block/nvme0n1/mq/3/cpu_list
3

대괄호 안이 지금 쓰는 스케줄러입니다. 이 파일에 이름을 쓰면 바뀝니다. mq/ 아래의 디렉터리가 하드웨어 큐이고, cpu_list가 그 큐에 묶인 CPU입니다. 큐 수가 CPU 수보다 적으면 한 큐에 CPU가 여럿 나옵니다.

드라이버로 내려가는 request를 종류별로 세어 봅니다. R은 읽기, W는 쓰기, S는 동기, M은 메타데이터, FF는 캐시 비우기입니다.

터미널
# bpftrace -e 'tracepoint:block:block_rq_issue { @[args->rwbs] = count(); }'

iostat -x 1은 같은 계층의 통계를 장치별로 보여 줍니다. aqu-sz가 장치에 걸려 있는 request 수의 평균입니다.

21.4완료: 인터럽트에서 bio_endio()까지#

장치는 명령을 끝내면 완료 큐에 항목을 쓰고 인터럽트를 겁니다. NVMe는 큐마다 MSI-X 벡터를 따로 받고, 커널은 각 벡터를 그 큐에 묶인 CPU에 배달되도록 고정해 둡니다(10장의 관리형 친화성). 그래서 완료 인터럽트는 대개 요청을 낸 CPU로 돌아옵니다. 그 CPU의 캐시에는 request와 bio가 아직 남아 있습니다.

핸들러 nvme_irq()는 완료 큐를 훑어 명령 ID로 request를 찾고 blk_mq_complete_request_remote()에 묻습니다. 이 함수는 완료 처리를 어느 CPU에서 할지 정합니다.

block/blk-mq.cv7.3
bool blk_mq_complete_request_remote(struct request *rq)
{
    WRITE_ONCE(rq->state, MQ_RQ_COMPLETE);

    /* ... */
    if ((rq->mq_hctx->nr_ctx == 1 &&
         rq->mq_ctx->cpu == raw_smp_processor_id()) ||
         rq->cmd_flags & REQ_POLLED)
        return false;

    if (blk_mq_complete_need_ipi(rq)) {
        blk_mq_complete_send_ipi(rq);
        return true;
    }

    if (rq->q->nr_hw_queues == 1) {
        blk_mq_raise_softirq(rq);
        return true;
    }
    return false;
}
  • 요청을 낸 CPU에서 인터럽트를 받았으면 false를 돌려주고, 호출한 쪽이 그 자리에서 드라이버의 complete()를 부릅니다. hardirq 컨텍스트입니다.
  • 다른 CPU에서 받았고 두 CPU가 캐시도 공유하지 않으면, 요청을 낸 CPU에 IPI를 보내 거기서 BLOCK_SOFTIRQ로 처리합니다(11장).
  • 하드웨어 큐가 하나뿐인 장치는 인터럽트가 한 CPU에 몰리므로 softirq로 미룹니다.

complete()는 blk_mq_end_request()를 거쳐 request에 묶인 bio마다 bio_endio()를 부르고, 거기서 bi_end_io가 불립니다. 읽기였다면 이 콜백이 폴리오를 최신 상태로 표시하고 락을 풉니다. 20장에서 filemap_update_page()에 잠들어 있던 태스크가 여기서 깨어납니다. 태그도 이때 반납됩니다.

장치가 충분히 빠르면 인터럽트 자체가 부담입니다. 폴링 I/O는 인터럽트를 끄고 제출한 태스크가 완료 큐를 직접 들여다봅니다. NVMe 드라이버는 poll_queues 모듈 인자로 인터럽트 없는 큐를 따로 만들고, REQ_POLLED가 붙은 request가 그 큐로 갑니다. io_uring의 IORING_SETUP_IOPOLL이 이 경로를 씁니다.

21.5쌓기와 요즘 장치#

submit_bio()에 들어온 bio는 드라이버에 닿기 전에 주소가 몇 번 바뀔 수 있습니다.

  • 파티션: /dev/nvme0n1p2에 대한 bio는 blk_partition_remap()에서 섹터에 파티션 시작 위치가 더해져 디스크 전체에 대한 bio가 됩니다. 디스크 하나가 struct gendisk이고, 디스크 전체와 각 파티션이 struct block_device입니다.
  • 디바이스 매퍼와 md: LVM, dm-crypt, RAID는 대개 bio 단위로 동작합니다. 받은 bio를 고치거나 복제해 아래 장치에 다시 submit_bio()합니다. 암호화는 내용을 바꾸고, 스트라이핑은 장치와 섹터를 바꾸고, 미러링은 bio를 둘로 복제합니다.

이 층들이 모두 같은 bio를 주고받으므로 임의의 순서로 쌓을 수 있습니다. 암호화한 논리 볼륨 위의 RAID가 가능한 까닭입니다.

v7.3의 블록 계층에는 플래시와 대용량 디스크의 성질을 드러내는 기능도 들어 있습니다.

기능 내용
zoned 장치 구역 안에서 순서대로만 쓸 수 있는 장치(SMR 디스크, ZNS SSD). 블록 계층이 구역별로 쓰기 순서를 맞춥니다(block/blk-zoned.c).
원자적 쓰기 pwritev2()의 RWF_ATOMIC. 전원이 나가도 쓰기 한 건이 전부 반영되거나 전혀 반영되지 않습니다. 장치가 지원해야 합니다.
ublk 블록 장치의 로직을 유저 공간 프로그램으로 구현합니다. 커널과 그 프로그램 사이의 요청 전달에 io_uring을 씁니다.

21.6I/O API의 변천#

여기서부터는 유저 공간과 커널의 경계입니다. 프로그램이 I/O를 요청하는 방법은 네 세대를 거쳤습니다.

동기 read()·write(). 데이터가 준비될 때까지 스레드가 잠듭니다. 동시에 여러 I/O를 하려면 스레드가 그만큼 필요합니다. 소켓은 O_NONBLOCK과 epoll로 풀 수 있지만 일반 파일에는 통하지 않습니다. 일반 파일은 poll()에 언제나 "읽을 수 있음"으로 보고되고 epoll은 등록 자체를 거부합니다. 페이지 캐시에 없으면 read()가 그대로 잠듭니다.

POSIX AIO. aio_read() 계열입니다. 리눅스에서는 glibc가 유저 공간에서 구현합니다. 내부에서 스레드를 만들어 동기 read()를 대신 부릅니다. 스레드 문제를 라이브러리 안으로 옮겼을 뿐입니다.

Linux AIO. io_setup(), io_submit(), io_getevents(). 커널이 구현한 비동기 인터페이스입니다. 한계가 뚜렷했습니다. io_submit()은 파일의 read_iter를 그 자리에서 부르므로, 버퍼를 거치는 읽기는 페이지를 기다리며 제출 시스템 콜 안에서 잠듭니다. 비동기로 동작하는 것은 사실상 O_DIRECT뿐이었습니다. 제출과 수확에도 시스템 콜이 한 번씩 듭니다.

io_uring. 5.1에서 들어왔습니다. 겨냥한 것은 셋입니다. 버퍼 I/O, 직접 I/O, 소켓을 가리지 않고 비동기일 것. 시스템 콜 횟수를 요청 수와 무관하게 만들 것. 요청마다 드는 복사와 조회를 줄일 것.

21.7io_uring의 두 링#

io_uring 인스턴스는 fd 하나입니다. io_uring_setup()이 만들어 돌려주고, 프로그램은 그 fd를 mmap()해서 커널과 같은 메모리를 봅니다. 그 메모리에 링 버퍼가 둘 있습니다.

  • 제출 큐(submission queue, SQ): 유저가 쓰고 커널이 읽습니다. 원소는 struct io_uring_sqe입니다.
  • 완료 큐(completion queue, CQ): 커널이 쓰고 유저가 읽습니다. 원소는 struct io_uring_cqe입니다.
include/uapi/linux/io_uring.hv7.3
struct io_uring_sqe {
    __u8    opcode;     /* type of operation for this sqe */
    __u8    flags;      /* IOSQE_ flags */
    __u16   ioprio;     /* ioprio for the request */
    __s32   fd;     /* file descriptor to do IO on */
    union {
        __u64   off;    /* offset into file */
        /* ... */
    };
    union {
        __u64   addr;   /* pointer to buffer or iovecs */
        /* ... */
    };
    __u32   len;        /* buffer size or number of iovecs */
    /* ... */
    __u64   user_data;  /* data to be passed back at completion time */
    /* ... */
};
include/uapi/linux/io_uring.hv7.3
struct io_uring_cqe {
    __u64   user_data;  /* sqe->user_data value passed back */
    __s32   res;        /* result code for this event */
    __u32   flags;
    /* ... */
};

SQE는 시스템 콜 한 번의 인자를 구조체로 옮긴 것입니다. opcode가 IORING_OP_READ이면 fd, addr, len, off는 pread()의 인자입니다. v7.3의 enum io_uring_op에는 연산이 65개 있습니다. 읽기·쓰기만이 아니라 accept, connect, openat, statx, futex 대기까지 들어 있습니다. CQE의 res는 그 시스템 콜의 반환값이고, 오류면 음수 errno입니다. 완료는 제출한 순서대로 오지 않으므로 user_data로 짝을 맞춥니다. 커널은 이 값을 들여다보지 않고 그대로 돌려줍니다.

링의 상태는 인덱스 네 개가 전부입니다. 누가 어느 것을 쓰는지가 소스의 주석에 못 박혀 있습니다.

include/linux/io_uring_types.hv7.3
struct io_rings {
    /*
     * Head and tail offsets into the ring; the offsets need to be
     * masked to get valid indices.
     *
     * The kernel controls head of the sq ring and the tail of the cq ring,
     * and the application controls tail of the sq ring and the head of the
     * cq ring.
     */
    struct io_uring     sq, cq;
    /* ... */
    struct io_uring_cqe cqes[] ____cacheline_aligned_in_smp;
};

유저는 SQE를 채운 뒤 SQ tail을 올립니다. 커널은 SQE를 읽고 나서 SQ head를 올립니다.

io_uring/io_uring.cv7.3
static void io_commit_sqring(struct io_ring_ctx *ctx)
{
    struct io_rings *rings = ctx->rings;

    if (ctx->flags & IORING_SETUP_SQ_REWIND) {
        ctx->cached_sq_head = 0;
    } else {
        /*
         * Ensure any loads from the SQEs are done at this point,
         * since once we write the new head, the application could
         * write new data to them.
         */
        smp_store_release(&rings->sq.head, ctx->cached_sq_head);
    }
}

smp_store_release()가 핵심입니다. head를 올리는 순간 그 칸은 유저의 것으로 돌아가므로, 칸의 내용을 읽는 일이 head 쓰기보다 먼저 끝났음을 메모리 순서로 보장해야 합니다. 유저 쪽도 대칭입니다. SQE를 다 쓴 뒤에 tail을 올려야 하고, 그 순서를 smp_store_release에 해당하는 원자 연산으로 지킵니다. 메모리 순서와 배리어는 13장의 주제입니다.

커널은 이 메모리를 믿지 않습니다. 유저가 언제든 고쳐 쓸 수 있기 때문입니다. io_get_sqe()의 주석은 SQE의 필드를 검증한 뒤 다시 읽으면 안 된다고 경고하고, 코드는 공유 메모리에서 읽는 값마다 READ_ONCE()를 씁니다. 커널 쪽의 진짜 head는 유저가 볼 수 없는 ctx->cached_sq_head에 따로 있습니다.

설계 노트

이 링이 락 없이 성립하는 조건은 생산자 하나, 소비자 하나입니다. tail은 생산자만, head는 소비자만 쓰므로 한 변수에 쓰는 쪽이 둘이 될 일이 없습니다. 상대의 인덱스는 읽기만 하고, 조금 낡은 값을 읽어도 "실제보다 덜 찼다" 또는 "덜 비었다"고 보수적으로 판단할 뿐 틀린 동작을 하지 않습니다. 남는 문제는 "데이터를 쓴 뒤에 인덱스를 올린다"는 순서 하나이고, 그것은 배리어로 풉니다. 한쪽이 여럿이 되면 이 구조는 깨집니다. 여러 스레드가 한 링에 제출하려면 유저 공간에서 락을 잡아야 합니다. 스레드마다 링을 하나씩 두는 편이 보통입니다.

21.8요청이 실행되는 세 길#

SQ에 넣는 것만으로는 아무 일도 일어나지 않습니다. io_uring_enter(fd, to_submit, min_complete, flags, …)가 커널에 "SQ에 to_submit개 넣었으니 가져가고, 완료가 min_complete개 쌓일 때까지 기다리겠다"고 알립니다. 제출과 수확이 시스템 콜 한 번입니다. 커널은 SQE마다 요청 객체(struct io_kiocb)를 만들어 io_queue_sqe()로 보냅니다.

io_uring/io_uring.cv7.3
static void io_queue_async(struct io_kiocb *req, unsigned int issue_flags, int ret)
    __must_hold(&req->ctx->uring_lock)
{
    /* ... */
    switch (io_arm_poll_handler(req, 0)) {
    case IO_APOLL_READY:
        io_req_task_queue(req);
        break;
    case IO_APOLL_ABORTED:
        io_queue_iowq(req);
        break;
    case IO_APOLL_OK:
        break;
    }
}

static inline void io_queue_sqe(struct io_kiocb *req, unsigned int extra_flags)
    __must_hold(&req->ctx->uring_lock)
{
    unsigned int issue_flags = IO_URING_F_NONBLOCK |
                   IO_URING_F_COMPLETE_DEFER | extra_flags;
    int ret;

    ret = io_issue_sqe(req, issue_flags);

    /* ... */
    if (unlikely(ret))
        io_queue_async(req, issue_flags, ret);
}

이 두 함수에 io_uring의 실행 모델이 다 들어 있습니다.

첫째, 그 자리에서 논블로킹으로 해 본다. io_issue_sqe()가 IO_URING_F_NONBLOCK을 붙여 연산을 실행합니다. 페이지 캐시에 있는 파일 읽기, 수신 버퍼에 데이터가 있는 recv는 여기서 끝나고 CQE가 바로 생깁니다. 스레드도 컨텍스트 스위치도 없습니다.

둘째, 준비되면 알려 달라고 걸어 둔다. 지금은 할 수 없어 -EAGAIN이 나오면 io_arm_poll_handler()가 그 파일의 대기 큐에 콜백을 겁니다. epoll이 쓰는 것과 같은 ->poll() 장치입니다. 소켓에 데이터가 도착하면 콜백이 불리고, 요청을 다시 실행하도록 예약합니다. 유저는 이 재시도를 보지 못합니다. 소켓과 파이프가 이 길을 탑니다.

셋째, 워커 스레드에 넘긴다. 폴링할 수 없는 파일이면 io_queue_iowq()가 요청을 io-wq의 워커에 넘기고, 워커가 블로킹으로 실행합니다. 워커는 create_io_thread()로 만듭니다. 제출한 프로세스의 스레드처럼 주소 공간과 fd 테이블을 공유하지만 유저 모드로는 돌아가지 않는 태스크이고(2장), ps에 iou-wrk-<pid>로 보입니다.

흔한 오해

"io_uring은 커널 안의 스레드 풀이다." 아닙니다. 스레드 풀(io-wq)은 세 길 가운데 마지막입니다. 페이지 캐시에 없는 버퍼 읽기도 FOP_BUFFER_RASYNC를 선언한 파일시스템(ext4, XFS 등)에서는 워커로 가지 않습니다. 폴리오의 락이 풀릴 때 불리는 콜백을 걸어 두었다가 재시도합니다.

완료를 CQ에 쓰는 일도 정해진 자리에서 합니다. 인터럽트 컨텍스트에서 요청이 끝나면 io_uring은 CQE를 곧장 쓰지 않고 task_work로 제출한 태스크에 넘깁니다. task_work는 태스크가 커널에서 유저 모드로 돌아가기 직전에 실행되는 콜백 목록입니다. IORING_SETUP_DEFER_TASKRUN을 켜면 한 걸음 더 미룹니다. 태스크가 io_uring_enter()로 완료를 기다리러 들어올 때에만 이 작업을 돌립니다. 완료 처리가 유저 코드 실행 중간에 끼어들지 않으므로 캐시가 덜 흐트러지고, 여러 완료가 한 번에 처리됩니다.

SQPOLL(IORING_SETUP_SQPOLL)은 io_uring_enter()마저 없앱니다. 커널 스레드 iou-sqp-<pid>가 SQ의 tail을 계속 들여다보다가 새 SQE가 보이면 가져갑니다. 유저는 메모리에 쓰기만 하면 됩니다. 스레드는 한동안 일이 없으면 SQ 플래그에 IORING_SQ_NEED_WAKEUP을 세우고 잠들고, 유저는 이 플래그를 보았을 때만 io_uring_enter()로 깨웁니다. CPU 하나를 폴링에 쓰는 대신 시스템 콜을 0에 가깝게 만드는 거래입니다.

직접 확인하기

liburing으로 파일 하나를 읽어 표준 출력에 씁니다. liburing은 링의 mmap()과 인덱스 조작을 감싼 라이브러리입니다.

uring-cat.cC
#include <fcntl.h>
#include <liburing.h>
#include <unistd.h>

int main(int argc, char **argv)
{
    struct io_uring ring;
    struct io_uring_sqe *sqe;
    struct io_uring_cqe *cqe;
    char buf[4096];
    __u64 off = 0;
    int fd = open(argv[1], O_RDONLY);

    if (fd < 0 || io_uring_queue_init(8, &ring, 0) < 0)
        return 1;
    for (;;) {
        sqe = io_uring_get_sqe(&ring);  /* SQ의 빈 칸 */
        io_uring_prep_read(sqe, fd, buf, sizeof(buf), off);
        io_uring_submit(&ring);     /* SQ tail을 올리고 io_uring_enter() */
        io_uring_wait_cqe(&ring, &cqe); /* CQ에 항목이 생길 때까지 */
        int n = cqe->res;       /* read()의 반환값에 해당 */
        io_uring_cqe_seen(&ring, cqe);  /* CQ head를 올린다 */
        if (n <= 0)
            break;
        write(STDOUT_FILENO, buf, n);
        off += n;
    }
    io_uring_queue_exit(&ring);
    return 0;
}

io_uring_enter()의 둘째 인자가 제출한 개수입니다. 페이지 캐시에 있는 파일이면 제출하는 그 호출 안에서 첫째 길로 완료되므로, io_uring_wait_cqe()는 CQ에 이미 있는 항목을 보고 시스템 콜 없이 돌아옵니다. 실행 중인 프로세스의 링 상태는 cat /proc/PID/fdinfo/4로 봅니다. SqHead, SqTail, CqHead, CqTail이 앞의 네 인덱스입니다.

21.9경계를 넘는 비용 줄이기#

시스템 콜 횟수를 줄이고 나면 요청 하나하나에 드는 일이 눈에 들어옵니다. io_uring은 그것도 미리 해 둘 수 있게 합니다.

장치 없앤 비용 방법
고정 파일 요청마다 fd를 조회하고 참조를 올리고 내리는 일 io_uring_register()로 fd 묶음을 등록해 두고 SQE에 IOSQE_FIXED_FILE과 인덱스를 씁니다.
고정 버퍼 요청마다 유저 페이지를 고정하고 푸는 일 버퍼를 등록하면 한 번만 고정합니다. IORING_OP_READ_FIXED가 씁니다.
제공 버퍼 링 수신할지 모르는 연결마다 버퍼를 잡아 두는 일 버퍼 묶음을 링으로 넘겨 두면 커널이 데이터가 올 때 하나를 고릅니다. 고른 버퍼의 ID가 CQE의 flags에 실립니다.
멀티샷 완료될 때마다 같은 SQE를 다시 넣는 일 accept나 recv를 한 번 제출하면 사건마다 CQE가 나옵니다. IORING_CQE_F_MORE가 "더 온다"는 표시입니다.
연결된 SQE 앞 요청의 완료를 받아 다음 요청을 제출하는 왕복 IOSQE_IO_LINK로 이으면 앞이 성공해야 뒤가 실행됩니다.
zero-copy 유저 버퍼와 소켓 버퍼 사이의 복사 IORING_OP_SEND_ZC, IORING_OP_RECV_ZC

고정 파일은 20장에서 본 fdget()이 I/O마다 하는 일을 등록 한 번으로 바꾼 것입니다. 그 비용이 문제가 될 만큼 나머지가 가벼워졌다는 뜻이기도 합니다.

참고 · v7.3의 io_uring/ 디렉터리

io_uring/에는 C 파일이 43개 있습니다. 읽기·쓰기에서 출발한 인터페이스가 범용 비동기 시스템 콜 통로로 자랐습니다. IORING_OP_URING_CMD는 드라이버가 정의한 명령을 그대로 실어 나릅니다. NVMe 패스스루와 ublk가 씁니다. IORING_OP_EPOLL_WAIT는 epoll의 대기를 링 안으로 가져옵니다. IORING_REGISTER_RESIZE_RINGS는 쓰는 중인 링의 크기를 바꾸고, IORING_REGISTER_QUERY는 커널이 지원하는 연산과 플래그를 물어봅니다. io_uring/bpf-ops.c는 완료를 기다리는 루프의 한 걸음을 BPF 프로그램으로 바꿔 끼우는 struct_ops를 정의합니다(24장).

같은 네트워크 서버를 epoll로 쓸 때와 견주면 모델의 차이가 드러납니다. epoll은 준비 통지입니다. "이 소켓을 이제 읽을 수 있다"고 알려 주고, 읽는 일은 프로그램이 read()를 불러서 합니다. io_uring은 완료 통지입니다. "읽어 달라"고 맡기고 "읽었다"는 결과를 받습니다.

설계 노트

io_uring에 반복해서 나오는 발상은 둘입니다. 하나는 경계를 넘는 비용이 병목이면 경계를 넘는 횟수를 줄인다는 것입니다. 경계 자체를 싸게 만드는 데에는 한계가 있으므로, 한 번 넘을 때 여러 건을 싣고(배치), 미리 해 둘 수 있는 일은 등록으로 빼고, 끝내 경계를 공유 메모리로 바꿉니다. 다른 하나는 빠른 길을 먼저 시도하고 안 될 때만 비싼 길로 간다는 것입니다. 모든 요청을 워커에 넘기면 구현은 단순하지만 요청마다 컨텍스트 스위치를 치릅니다. 논블로킹 시도, 폴링, 워커의 세 단으로 나누면 흔한 경우의 비용이 0에 가까워집니다. 20장의 RCU-walk와 같은 구조입니다.

21.10공격 표면과 제한#

io_uring은 시스템 콜 65종에 해당하는 일을 시스템 콜 세 개 뒤에서 합니다. 이것이 보안에는 부담입니다. 새 코드가 많고 빠르게 바뀝니다. sysctl 문서도 io_uring을 끄면 "커널의 공격 표면이 줄어든다"고 적습니다. 그리고 seccomp가 들여다볼 수 없습니다. seccomp 필터는 시스템 콜 번호와 인자를 보는데(19장), io_uring의 연산은 공유 메모리의 SQE에 적혀 있어 필터를 지나가지 않습니다. openat()을 막아 둔 샌드박스 안에서 IORING_OP_OPENAT이 통할 수 있습니다. 그래서 샌드박스는 io_uring 시스템 콜 자체를 막아 두는 일이 많습니다.

커널이 주는 제한 장치는 세 단계입니다.

io_uring/io_uring.cv7.3
static inline int io_uring_allowed(void)
{
    int disabled = READ_ONCE(sysctl_io_uring_disabled);
    kgid_t io_uring_group;

    if (disabled == 2)
        return -EPERM;

    if (disabled == 0 || capable(CAP_SYS_ADMIN))
        goto allowed_lsm;

    io_uring_group = make_kgid(&init_user_ns, sysctl_io_uring_group);
    if (!gid_valid(io_uring_group))
        return -EPERM;

    if (!in_group_p(io_uring_group))
        return -EPERM;

allowed_lsm:
    return security_uring_allowed();
}
  • 시스템 전체: sysctl kernel.io_uring_disabled. 0이면 누구나, 1이면 CAP_SYS_ADMIN이나 kernel.io_uring_group에 속한 프로세스만, 2면 아무도 새 링을 만들 수 없습니다. 마지막 줄의 LSM 훅으로 SELinux 같은 보안 모듈도 거부할 수 있습니다.
  • 링 하나: IORING_REGISTER_RESTRICTIONS. 링을 만든 쪽이 허용할 연산과 플래그를 비트맵으로 정해 두고 나서 덜 신뢰하는 코드에 넘깁니다.
  • 연산의 인자까지: IORING_REGISTER_BPF_FILTER. 연산 종류마다 BPF 필터를 붙여 요청 내용을 보고 거부합니다(io_uring/bpf_filter.c). seccomp가 하지 못하던 일을 io_uring 안에서 합니다.

정리#

  • bio는 장치의 연속된 섹터 구간과 메모리 조각 목록을 잇는 요청 단위입니다. 제출은 기다리지 않고 돌아오고, 완료는 bi_end_io 콜백으로 옵니다.
  • blk-mq는 CPU별 소프트웨어 큐와 장치의 큐에 대응하는 하드웨어 큐로 이루어집니다. 스케줄러가 없고 장치가 한가하면 request는 큐를 거치지 않고 queue_rq()로 바로 갑니다.
  • 태그는 장치에 동시에 걸린 요청 수를 제한하고, 완료 때 request를 찾는 인덱스가 됩니다.
  • 완료는 되도록 요청을 낸 CPU에서 처리합니다. 다른 CPU로 인터럽트가 왔으면 IPI와 BLOCK_SOFTIRQ로 돌려보냅니다.
  • io_uring은 유저와 커널이 공유하는 링 둘입니다. 넣는 쪽은 tail만, 꺼내는 쪽은 head만 쓰므로 락이 없습니다.
  • 요청은 먼저 논블로킹으로 시도하고, 안 되면 폴링을 걸고, 그것도 안 되면 io-wq 워커로 갑니다. 완료는 task_work로 제출한 태스크에서 CQ에 씁니다.
  • 고정 파일·버퍼, 제공 버퍼 링, 멀티샷, SQPOLL은 모두 요청 하나에 드는 반복 비용을 등록이나 공유 메모리로 옮기는 장치입니다.

확인 문제#

CPU 16개인 서버에 NVMe SSD가 있고 I/O 스케줄러는 none입니다. CPU 5에서 도는 태스크가 O_DIRECT로 4KB 읽기를 한 건 냈습니다. 제출부터 완료까지 이 요청이 다른 CPU와 공유하는 락이나 큐를 거치는 곳이 있습니까?

답 보기

보통은 없습니다. blk_mq_submit_bio()는 request를 만들고 CPU 5에 묶인 하드웨어 큐의 태그를 받습니다. 스케줄러가 없으므로 blk_mq_try_issue_directly()가 nvme_queue_rq()를 바로 부르고, 거기서 잡는 sq_lock은 그 큐만의 락입니다. 큐가 CPU마다 있으면 다른 CPU는 이 락을 잡지 않습니다. 완료 인터럽트는 그 큐의 MSI-X 벡터가 묶인 CPU 5로 오고, blk_mq_complete_request_remote()가 같은 CPU임을 보고 그 자리에서 완료 처리를 합니다.

io_uring의 SQ에서 유저는 tail을, 커널은 head를 씁니다. 유저 프로그램이 버그로 SQE를 다 채우기 전에 tail을 먼저 올렸다면 어떤 일이 생길 수 있습니까? 커널은 이런 유저로부터 자신을 어떻게 지킵니까?

답 보기

커널이 덜 채워진 SQE를 읽어 엉뚱한 연산을 실행할 수 있습니다. 그 결과는 유저 자신의 요청이 잘못되는 것까지입니다. 커널은 공유 메모리를 믿지 않습니다. SQE의 필드를 READ_ONCE()로 한 번만 읽어 요청 객체에 복사한 뒤 그 복사본을 검증하고 사용하므로, 검증한 뒤에 유저가 값을 바꿔도 영향이 없습니다. 인덱스는 마스크를 씌워 링 범위를 벗어나지 못하게 하고, 커널의 진짜 head는 유저가 건드릴 수 없는 cached_sq_head에 둡니다. fd와 권한 검사도 시스템 콜과 같은 경로를 거칩니다.

io_uring으로 TCP 소켓에 IORING_OP_RECV를 제출했는데 아직 도착한 데이터가 없습니다. 이 요청은 어떻게 됩니까? 워커 스레드가 생깁니까?

답 보기

생기지 않습니다. io_queue_sqe()가 논블로킹으로 시도해 -EAGAIN을 받고, io_queue_async()가 io_arm_poll_handler()를 부릅니다. RECV는 연산 정의에 pollin이 서 있고 소켓은 ->poll()을 지원하므로 소켓의 대기 큐에 콜백이 걸리고 IO_APOLL_OK로 끝납니다. 데이터가 도착하면 콜백이 task_work를 예약하고, 제출한 태스크의 컨텍스트에서 recv를 다시 실행해 CQE를 씁니다.

seccomp로 openat을 막은 샌드박스가 있습니다. 이 샌드박스가 io_uring 시스템 콜 셋을 허용하면 무엇이 문제입니까? v7.3에서 io_uring을 허용하면서 이 구멍을 막는 방법은 무엇입니까?

답 보기

io_uring의 연산은 시스템 콜 인자가 아니라 공유 메모리의 SQE에 적혀 있어 seccomp 필터가 보지 못합니다. IORING_OP_OPENAT으로 파일을 열 수 있습니다. 막는 방법은 io_uring 쪽의 제한을 쓰는 것입니다. 링을 만들어 IORING_REGISTER_RESTRICTIONS로 허용할 연산을 비트맵으로 정하거나, IORING_REGISTER_BPF_FILTER로 연산별 BPF 필터를 붙여 인자까지 검사합니다. 필요가 없다면 kernel.io_uring_disabled나 seccomp로 io_uring_setup 자체를 막는 편이 단순합니다.

bio
장치의 연속된 섹터 구간에 대한 I/O 한 건. 메모리 조각의 목록과 완료 콜백을 가진다.
request
드라이버에 건네는 I/O 단위. 섹터가 이어지는 bio 여러 개를 묶을 수 있다.

CPU별 소프트웨어 큐와 다중 하드웨어 큐로 이루어진 블록 계층의 요청 처리 구조.
태그tag
하드웨어 큐 안에서 진행 중인 request를 식별하는 번호. 큐 깊이만큼만 있다.
플러그plug
태스크가 연달아 내는 request를 잠시 모았다가 한꺼번에 내려보내는 장치.
I/O 스케줄러I/O scheduler
request의 순서를 바꾸거나 붙들어 두는 층. none, mq-deadline, kyber, bfq.
제출 큐submission queue, SQ
io_uring에서 유저가 요청(SQE)을 넣고 커널이 꺼내는 링.
완료 큐completion queue, CQ
io_uring에서 커널이 결과(CQE)를 넣고 유저가 꺼내는 링.

논블로킹으로도 폴링으로도 처리할 수 없는 io_uring 요청을 블로킹으로 실행하는 워커 스레드 풀.

커널 스레드가 제출 큐를 폴링해 io_uring_enter() 없이 요청을 가져가는 모드.
task_work
태스크가 유저 모드로 돌아가기 직전에 그 태스크의 컨텍스트에서 실행되는 콜백 목록.
